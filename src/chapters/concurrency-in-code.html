Several things at once

The earlier chapters on transactions and distributed systems dealt with many machines touching the same data. The same problems appear inside a single program, and they need to be understood there first, because that is where most of them are written.

Two words are used for “several things at once”, and they mean different things.

  • Concurrency is dealing with several tasks whose lifetimes overlap. A server with a thousand open requests is concurrent, even if at any instant it is working on one of them.
  • Parallelism is executing several computations at the same instant, on separate processor cores.

Concurrency is about structure, and parallelism is about hardware. A program can have either without the other. The unit the operating system runs on a core is a thread: a sequence of instructions with its own call stack. A process is a running program with its own private memory, containing one or more threads that all share that memory.

Languages offer two main models for writing concurrent code.

This chapter works in the second model, because this part of the book is in TypeScript, and then shows real threads, because design interviews ask “how would you make this thread-safe?” whatever language you write. The reasoning carries over with one substitution: where a threaded program can be interrupted anywhere, an event-loop program can be interrupted only at an await.

The event loop

A JavaScript runtime runs your code on one thread. An event loop is the program at the center of it: it takes one waiting callback from a queue, runs it until it returns, then takes the next. Network data arriving, a timer expiring and a file finishing its read all become callbacks in that queue.

Two rules explain nearly all of its behavior.

  • Run to completion. Once a piece of code starts, it runs until it returns or reaches an await. Nothing else runs in between.
  • Two queues, one with priority. Callbacks from timers, the network and the disk are tasks, taken one at a time. Callbacks from promises, which includes everything after an await, are microtasks. All waiting microtasks run as soon as the current code finishes, before the next task.
// In what order do these lines run? The log answers.
export function order(): Promise {
  const log: string[] = [];
  return new Promise((done) => {
    log.push("A  synchronous code, first line");
    setTimeout(() => {
      log.push("F  timer callback: a new task");
      done(log);
    }, 0);
    Promise.resolve().then(() => log.push("D  promise callback: a microtask"));
    (async () => {
      log.push("B  async function, up to its first await");
      await null;
      log.push("E  async function, after the await: a microtask");
    })();
    log.push("C  synchronous code, last line");
  });
}

Run on Node.js, the log came out in the order A, B, C, D, E, F, as the letters predict. Three details are worth taking from it.

  • An async function starts synchronously. B is logged before C. Calling an async function runs it at once, up to its first await.
  • await always yields. Even await null, which has nothing to wait for, puts the rest of the function in the microtask queue and lets the caller continue.
  • A timer of zero is not immediate. F comes last. The delay is a minimum, and the callback waits for everything already in progress.

The first rule is a real guarantee, and a valuable one. Between two awaits your code has the program’s memory to itself. A stretch of code with no await in it cannot be interleaved with anything, and needs no lock.

Blocking the loop

The same rule has a price. If one callback runs for a long time, nothing else runs at all: no other request is answered, no timer fires, no health check gets a reply. This is called blocking the event loop.

The test below set a timer for 10 ms and then counted the prime numbers below three million, which takes most of a second.

// CPU-bound work, done in one go. Nothing else can run on this thread until it returns.
export function countPrimes(from: number, to: number): number {
  let count = 0;
  for (let n = from; n < to; n += 1) if (isPrime(n)) count += 1;
  return count;
}

// The same work in slices. After each slice it lets the event loop run whatever is waiting.
export async function countPrimesPolitely(from: number, to: number, slice = 20_000): Promise {
  let count = 0;
  for (let start = from; start < to; start += slice) {
    count += countPrimes(start, Math.min(to, start + slice));
    await nextTurn();
  }
  return count;
}

The timer stands for every other user of the server. In the first row they all waited the best part of a second, and had there been ten such calculations queued, they would have waited ten seconds. Work comes in two kinds, and only one of them is a problem here.

  • I/O-bound work spends its time waiting for something outside the program: a database, another service, a disk. It costs the thread nothing while it waits. The event loop handles it well.
  • CPU-bound work spends its time computing: resizing an image, hashing a password, parsing a 50 MB JSON document, a regular expression that backtracks. It occupies the thread for its whole duration.

There are three remedies, in order of how much they change.

  1. Slice it. Do a bounded amount, yield to the loop, continue. Simple, and still limited to one core.
  2. Move it to another thread. A worker thread computes while the main thread stays responsive. This is covered under real threads below.
  3. Move it out of the request. Put a job on a queue and let a separate worker process do it (). This is the usual answer for anything that takes seconds.

Not quite one threadNode.js runs your JavaScript on one thread, but the runtime has others. Network waiting is handled by the operating system. File access, DNS lookups and some cryptography run on a small internal pool, four threads by default. That pool can be exhausted too, by a burst of slow file reads for example.

Waiting for several things

An album page needs the sizes of three photos, each a network call of about 100 ms. The way the awaits are written decides whether the page takes 100 ms or 300.

// One after another: each await finishes before the next call starts.
export async function inSequence(items: T[], fn: (item: T) => Promise): Promise {
  const results: R[] = [];
  for (const item of items) results.push(await fn(item));
  return results;
}

// All at once: every call is started, then all are awaited together.
export function allAtOnce(items: T[], fn: (item: T) => Promise): Promise {
  return Promise.all(items.map(fn));
}

// At most `limit` at a time. Each of the `limit` runners takes the next item when it finishes one.
export async function mapLimit(items: T[], limit: number, fn: (item: T) => Promise): Promise {
  const results = new Array(items.length);
  let next = 0;
  const runner = async (): Promise => {
    while (next < items.length) {
      const index = next++; // no await between the check and the claim, so no two runners take the same item
      results[index] = await fn(items[index] as T);
    }
  };
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, runner));
  return results;
}

The measured times were 301 ms in sequence and 101 ms all at once. Ten calls of 50 ms, at most three at a time, took 201 ms and never had more than three in flight. Four points follow.

  • A promise is work already started. items.map(fn) starts every call. Promise.all starts nothing. It only waits for what is already running.
  • Promise.all fails fast and cancels nothing. If one call rejects, the combined promise rejects at once, and the other calls carry on with their results discarded. Use Promise.allSettled when you want every outcome, as in a page that should show the photos that did load.
  • Unlimited concurrency is an unbounded queue. “All at once” over ten thousand items opens ten thousand requests. The work has not got faster. It has moved to the database’s connection pool or the other service’s rate limiter, as a spike (). A limit gives most of the speed and keeps the load predictable.
  • A promise nobody awaits can fail silently. An event listener that is an async function returns a promise to an emitter that ignores it. In a test, the emitter’s try block caught nothing, emit returned at once, and the error arrived later as an unhandled rejection, which by default ends a Node.js process. Await every promise, or attach a catch to it.

Races without threads

A race condition is a bug in which the result depends on the order in which overlapping operations happen to run. It is often assumed that a single-threaded language cannot have one. It can, and the commonest form is a check followed by an await followed by an action that relied on the check.

export class Quota {
  readonly limit: number;
  private bytesUsed = 0;
  private readonly save: (bytes: number) => Promise;

  constructor(limit: number, save: (bytes: number) => Promise) {
    this.limit = limit;
    this.save = save;
  }
  get used(): number {
    return this.bytesUsed;
  }

  // Broken: the check and the update are separated by an await.
  async addRacy(bytes: number): Promise {
    if (this.bytesUsed + bytes > this.limit) return false;
    await this.save(bytes); // other calls run while this one waits here
    this.bytesUsed += bytes;
    return true;
  }

  // Fixed: claim the space before waiting, and give it back if the save fails.
  async addReserved(bytes: number): Promise {
    if (this.bytesUsed + bytes > this.limit) return false;
    this.bytesUsed += bytes;
    try {
      await this.save(bytes);
      return true;
    } catch (error) {
      this.bytesUsed -= bytes;
      throw error;
    }
  }
}

Five uploads of 30 MB were started together against a limit of 100.

MethodUploads acceptedRecorded as used
addRacy5 of 5150 of 100
addReserved3 of 590 of 100

This is the lost-update and check-then-act family that described for databases, and the asynchronous singleton of was another member of it. The rule for finding these bugs is short: treat every await as a point where anything you have read may have changed. Then there are three ways to fix one, in order of preference.

  1. Do not wait between the check and the action. addReserved moves the update in front of the await. The check and the claim are then one uninterrupted stretch of code, and the claim is undone if the slow part fails.
  2. Make the waiting callers take turns. When the check itself needs an await, serialize the whole operation with a lock, as below.
  3. Let the data store decide. One conditional write or constraint in the database does the check and the update as a single atomic step ().

A lock for asynchronous code

A mutex, short for mutual exclusion, is a lock that one holder at a time may have. The stretch of code that must not be run by two at once is called a critical section. JavaScript has no built-in mutex for asynchronous code, and a small one is a chain of promises.

// A lock for asynchronous code: the functions given to run() execute one at a time, in order of arrival.
export class Mutex {
  private tail: Promise = Promise.resolve();

  run(fn: () => Promise): Promise {
    const result = this.tail.then(fn);
    this.tail = result.catch(() => undefined); // a failure must not block the callers behind it
    return result;
  }
}

// One lock for each key, so that work on different keys does not wait.
export class KeyedMutex {
  private readonly locks = new Map();

  async run(key: string, fn: () => Promise): Promise {
    const entry = this.locks.get(key) ?? { mutex: new Mutex(), waiting: 0 };
    this.locks.set(key, entry);
    entry.waiting += 1;
    try {
      return await entry.mutex.run(fn);
    } finally {
      entry.waiting -= 1;
      if (entry.waiting === 0) this.locks.delete(key); // do not keep a lock for every key ever seen
    }
  }
  get size(): number {
    return this.locks.size;
  }
}

With the racy method wrapped as mutex.run(() => quota.addRacy(30)), the same five uploads gave the right answer: three accepted, 90 used. The test also showed what the lock costs. The five calls took 61 ms behind the mutex, against 20 ms with addReserved, because each call’s save now waited for the previous one’s.

That cost is the “lock held during a network call” that warned about. A mutex turns concurrent work back into a queue. Two habits keep the damage small.

  • Lock as narrowly as the invariant allows. One user’s quota has nothing to do with another’s. With KeyedMutex, two jobs for Ana and one for Ben, 40 ms each, finished in 81 ms: Ana’s two took turns, and Ben’s did not wait for either.
  • Hold it as briefly as possible. Prefer the first remedy, which holds nothing while waiting, whenever the logic permits it.

In production. A lock in memory protects one process. A real service runs several copies behind a load balancer, and two requests for the same user can land on two of them, each with its own Quota object and its own mutex. Then the only place the check can be made safely is the shared data store: an atomic update, a uniqueness constraint or, where neither fits, a distributed lock with all its caveats (). In-process locks remain useful for what lives in one process, such as a local cache or a connection being set up.

Answers that arrive in the wrong order

A search box sends a request on every keystroke. The user types “li” and then “lis”. Nothing guarantees that the answers return in the order the questions were asked. In a test, the first search took 80 ms and the second 20, and the screen ended up showing the results for “li” under a box that said “lis”.

// Wraps an asynchronous lookup so that only the most recent call's answer is delivered.
// An earlier call that finishes late resolves to undefined, and its signal is aborted so the work can stop.
export function latestOnly(fn: (arg: A, signal: AbortSignal) => Promise): (arg: A) => Promise {
  let current: AbortController | null = null;
  return async (arg) => {
    current?.abort();
    const mine = new AbortController();
    current = mine;
    const result = await fn(arg, mine.signal);
    return mine.signal.aborted ? undefined : result;
  };
}

// Gives up on a slow operation. The operation is told through the signal, so it can stop its own work.
export async function withTimeout(ms: number, fn: (signal: AbortSignal) => Promise): Promise {
  const signal = AbortSignal.timeout(ms);
  return Promise.race([
    fn(signal),
    new Promise((_, reject) => signal.addEventListener("abort", () => reject(signal.reason), { once: true })),
  ]);
}

Wrapped in latestOnly, the late answer for “li” was discarded and the screen showed “lis”. The wrapper also aborts the earlier request’s AbortSignal, the standard way to tell asynchronous work that its result is no longer wanted, so that a well-behaved fetch or database driver can stop. withTimeout uses the same mechanism: with a limit of 50 ms on an operation that would have taken 500, the caller got a TimeoutError after 51 ms and the operation was told to stop. A timeout that does not cancel leaves the work running to no purpose ().

Real threads

For CPU-bound work, one thread means one core. Node.js can start more with worker threads, each with its own event loop and its own memory. By default a worker shares nothing with the thread that started it. Data goes in and out as messages, which are copied.

const runWorker = (file: string, workerData: unknown): Promise =>
  new Promise((resolve, reject) => {
    const worker = new Worker(new URL(file, import.meta.url), { workerData });
    worker.once("message", resolve);
    worker.once("error", reject);
  });

// Splits the range into equal parts and counts each part on its own thread.
export async function countPrimesOnThreads(limit: number, threads: number): Promise {
  const size = Math.ceil(limit / threads);
  const parts = Array.from({ length: threads }, (_, i) => ({ from: i * size, to: Math.min(limit, (i + 1) * size) }));
  const counts = await Promise.all(parts.map((part) => runWorker("./primes.worker.ts", part)));
  return counts.reduce((sum, count) => sum + count, 0);
}

On a machine with two cores, counting the primes below six million took 2.1 to 2.7 s on one worker and about 1.5 s on two. The answer was the same, 412,849. Two cores did not make it twice as fast, for a reason worth noticing: the range was split into equal halves, but the upper half is more work, because larger numbers take longer to test. Parallel speed depends on dividing the work evenly, and on how much of it cannot be divided at all.

Copying messages is safe and sometimes too slow. Threads can instead share one block of memory, a SharedArrayBuffer, and then they face the problem every threaded language has.

// Adds one to a shared counter many times, either with a plain read-then-write or with an atomic operation.
import { parentPort, workerData } from "node:worker_threads";

const { shared, times, atomic } = workerData as { shared: SharedArrayBuffer; times: number; atomic: boolean };
const counter = new Int32Array(shared);
for (let i = 0; i < times; i += 1) {
  if (atomic) Atomics.add(counter, 0, 1);
  else counter[0] = (counter[0] as number) + 1; // read, add, write: three steps another thread can interleave with
}
parentPort?.postMessage("done");

A data race is two threads accessing the same memory at the same time, at least one of them writing, with nothing to order them. The first row shows its two worst properties. The result is wrong by a different amount each time. And in the second run it was wrong by only 1,296 in four million, close enough that a casual test would have passed. An atomic operation is one that the hardware carries out as a single indivisible step, so that no other thread can observe it half done.

Atomic operations cover single values. To keep several values consistent with each other, threaded languages use locks: Java’s synchronized, a Mutex in Go or Rust. They work as the async mutex above does, with the same costs, and one further hazard.

Deadlock

A deadlock is a state in which each of a group of tasks is waiting for a lock that another task in the group holds. None of them can proceed, and none of them will ever release what it has.

Moving a photo between two albums must lock both. In a test with the async mutex, one task locked album A and then asked for B, while another locked B and then asked for A. After 300 ms neither had finished, and neither ever would. The repair is a rule about order.

// Takes two locks in a fixed order, whatever order the caller named them in.
export function withBoth(a: [string, Mutex], b: [string, Mutex], fn: () => Promise): Promise {
  const [first, second] = a[0] < b[0] ? [a[1], b[1]] : [b[1], a[1]];
  return first.run(() => second.run(fn));
}

With both moves going through withBoth, which sorts the two locks by name before taking them, both completed. Databases meet the same problem with row locks and solve it by detecting the cycle and aborting one transaction (). Application code rarely has a detector, so it has to prevent the cycle.

  • Take locks in one global order, such as by identifier.
  • Hold one lock at a time wherever the design allows. A lock that is never held together with another cannot be part of a cycle.
  • Never call unknown code while holding a lock. A callback or an event listener may try to take a lock of its own.
  • Put a time limit on waiting, so that a deadlock becomes an error that can be seen and retried.

Designing for safety

Every problem in this chapter needs three ingredients: state that is shared, that can change, and that is touched by operations which overlap. Remove any one and the problem is gone. That gives an order in which to try things, safest first.

ApproachRemovesExample
Do not shareSharingEach request builds its own objects. Each worker thread has its own memory. Nothing in a module-level variable
Share only what cannot changeChangeFrozen configuration, value objects (). Any number of readers is safe
Give the state one owner and send it messagesOverlapA queue with a single consumer. A worker that owns a resource. This is the idea behind actors and behind Go’s channels
Use an atomic operationOverlap, for one stepAtomics.add. A conditional update in the database. Redis’s INCR
LockOverlap, for a critical sectionA mutex for each key, held briefly, never across a call you do not control

In an interview. “How would you make this thread-safe?” has a method. Name the shared mutable state: the cache’s map, the parking lot’s free spots, the rate limiter’s counters. State the invariant that must hold: no spot assigned twice, never more than the limit. Find the operations that read and then write, since those are the critical sections. Then choose the weakest tool that protects them, and say what granularity you would lock at and why. In TypeScript, add where the awaits are, because those are the only places another request can get in. Finish by saying what changes with several server instances: the lock has to move into the shared store.

Key points

  • Concurrency is overlapping tasks. Parallelism is simultaneous execution on several cores. JavaScript gives you the first on one thread.
  • The event loop runs one callback at a time to completion. Promise callbacks run before the next timer or network event.
  • CPU-bound work blocks every other request for as long as it runs. Slice it, move it to a worker thread, or move it to a queue.
  • Awaiting in a loop adds the waits together. Start independent calls together, and limit how many run at once.
  • Every await is a point where shared state may change. A check made before it may be false after it.
  • Fix a race by not waiting between the check and the action, by serializing with a lock for each key, or by making the data store do it atomically.
  • An in-memory lock protects one process. With several instances the protection has to live in the shared store.
  • Threads that share memory need atomic operations or locks. Locks taken in inconsistent order deadlock.
  • The safest designs do not share, share only immutable data, or give each piece of state a single owner.

Check yourself

What does this print, and why? setTimeout(() => console.log(1), 0); Promise.resolve().then(() => console.log(2)); console.log(3);

3, 2, 1. The synchronous code runs to its end first and prints 3. The promise callback is a microtask, and all microtasks run as soon as the current code finishes, so 2 is next. The timer callback is a task and waits for the next turn of the loop, even with a delay of zero.

A request handler resizes an uploaded image in 400 ms of pure computation. The service receives 5 such requests a second, among 500 ordinary ones. What happens, and what are two ways to fix it?

Five resizes a second need 2,000 ms of computation every second on a thread that has 1,000, so the event loop is overloaded on that work alone and every request queues without limit. Even one resize delays every other request by up to 400 ms. Move the resizing to a pool of worker threads, or put a job on a queue and resize in a separate worker process, so that the request thread only coordinates.

A function loads 200 user records with for (const id of ids) users.push(await load(id)), and each load takes 20 ms. How long does it take, and what would you change?

About 4 seconds, since the waits are added together. The loads are independent, so start them together with a limit, for example twenty at a time, which takes about 200 ms. Unlimited Promise.all would be fastest on paper and would open 200 connections at once, which may exhaust the database’s pool. Better still, one query that loads all 200.

Find the bug: if (!(await cache.has(key))) { const value = await compute(key); await cache.set(key, value); }, called by many requests for the same key.

Check, then await, then act. Every request that arrives before the first set completes sees that the key is missing and runs compute itself, so an expensive computation runs many times at once. This is a cache stampede. Remember the promise of the computation for each key as soon as it starts, so that later callers wait on the same one, or serialize callers with a lock for each key.

A service uses the KeyedMutex from this chapter to stop a user from exceeding their quota. It is then scaled from one instance to three. Is it still correct?

No. Each instance has its own mutex and its own view, so two uploads from the same user handled by different instances can both pass the check. The check and the update have to become one atomic operation in the shared database, for example an update that only succeeds if the new total is within the limit, or a row lock inside a transaction.

Two threads each run counter = counter + 1 a million times on shared memory and the result is 1,400,000. Explain the missing 600,000, and say why Atomics.add fixes it.

The statement is three steps: read, add, write. When both threads read the same value before either writes, both write the same result and one addition is lost. That happened 600,000 times. Atomics.add performs the three steps as one indivisible operation, so every addition starts from the result of the previous one.

Transfers between accounts lock the source account and then the destination. Under load the service occasionally hangs. Why, and what is the smallest fix?

A transfer from X to Y and another from Y to X can each take their first lock and then wait for the other’s: a deadlock. Lock the two accounts in a fixed order that does not depend on the direction of the transfer, such as the lower account identifier first. Then no circle of waiting can form.
