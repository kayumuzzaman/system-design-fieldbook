Who decides, and who is told

Structure answers the question “what is connected to what?”. It does not answer “when a photo is added, what else happens, and who is responsible for making it happen?”. That is a question about behavior, and the catalog introduced in has eleven patterns for it. Seven are in everyday use.

The cautions from the creational chapter apply here with more force, because behavior is where indirection hurts most. A reader can see structure in a diagram. To see behavior they have to follow calls, and every pattern in this chapter makes at least one call harder to follow in exchange for making one kind of change easier.

Strategy

An upload from a phone fails often: the train enters a tunnel, the wifi drops. The uploader retries. How long it should wait between attempts is a separate question with several reasonable answers, and the answer will change more often than the retry loop does ().

A strategy is one of several interchangeable ways of doing a step, written behind a common interface so that the code which needs the step done can be given any of them.

// The job that varies: how long to wait before retry number `attempt` (counted from 1), in milliseconds.

// The classic form: an interface, and a class for each way of doing the job.
export interface BackoffPolicy {
  delay(attempt: number): number;
}
export class FixedBackoff implements BackoffPolicy {
  private readonly ms: number;
  constructor(ms: number) {
    this.ms = ms;
  }
  delay(): number {
    return this.ms;
  }
}

// The TypeScript form: a strategy with one method is a function.
export type Backoff = (attempt: number) => number;

export const fixed = (ms: number): Backoff => () => ms;
export const exponential = (base: number, cap: number): Backoff => (attempt) => Math.min(cap, base * 2 ** (attempt - 1));
export const jittered = (inner: Backoff, random: () => number = Math.random): Backoff => (attempt) =>
  Math.round(inner(attempt) * random());

// The context: it retries, and has no opinion about how long to wait.
export class Uploader {
  private readonly backoff: Backoff;
  private readonly sleep: (ms: number) => Promise;

  constructor(backoff: Backoff, sleep: (ms: number) => Promise) {
    this.backoff = backoff;
    this.sleep = sleep;
  }

  async upload(send: () => Promise, maxAttempts = 4): Promise {
    for (let attempt = 1; ; attempt += 1) {
      try {
        await send();
        return attempt;
      } catch (error) {
        if (attempt === maxAttempts) throw error;
        await this.sleep(this.backoff(attempt));
      }
    }
  }
}

The same Uploader, given three different strategies and an upload that fails three times, waited as follows in a test.

Strategy passed inWaits before attempts 2, 3 and 4
fixed(200)200, 200, 200 ms
exponential(100, 5000)100, 200, 400 ms
jittered(exponential(100, 5000)), with the random number fixed at 0.5 for the test50, 100, 200 ms

Three things in the listing are worth noticing.

  • The class form and the function form are the same pattern. An interface with one method and a function type say the same thing. The function form needs no class for each variant, and a variant with settings is a function that returns a function.
  • Strategies compose. jittered takes a strategy and returns a strategy. That is a decorator for functions ().
  • The clock is passed in too. sleep is a second strategy, there so that the test can record the waits instead of waiting. returns to this.

You already use the pattern whenever you pass a comparison function to sort. It is the open/closed principle in its smallest form (): a new way of waiting is a new function, and the retry loop is not edited.

Common mistake. A strategy interface whose implementations need different inputs. If one pricing strategy needs the user’s country and another needs their purchase history, the shared method ends up taking everything any of them might want. That is a sign the variants are not doing the same job, and a strategy is the wrong tool.

Observer

When a photo is added to a shared album, the activity feed gets an entry, the search index learns about it, and the other members get a push message. If Album.add calls all three, then Album depends on all three, cannot be tested without them, and must be edited whenever a fourth reaction is wanted.

An observer is an object that has registered to be told when something happens to another object. The object being watched, called the subject, keeps a list of observers and calls each one when it has news. It knows them only as functions to call.

type Listener = (payload: T) => void;

// A small typed subject. Events is a map from event name to the data that comes with it.
export class Emitter> {
  private readonly listeners: { [K in keyof Events]?: Set> } = {};

  // Subscribing returns the function that unsubscribes.
  on(event: K, listener: Listener): () => void {
    const set = (this.listeners[event] ??= new Set());
    set.add(listener);
    return () => set.delete(listener);
  }

  // Every listener is told, even if an earlier one throws. The errors are returned to the caller.
  emit(event: K, payload: Events[K]): unknown[] {
    const errors: unknown[] = [];
    for (const listener of [...(this.listeners[event] ?? [])]) {
      try {
        listener(payload);
      } catch (error) {
        errors.push(error);
      }
    }
    return errors;
  }

  count(event: K): number {
    return this.listeners[event]?.size ?? 0;
  }
}

export type AlbumEvents = {
  photoAdded: { album: string; photo: string };
  shared: { album: string; with: string };
};

// The subject. It announces what happened and knows nothing about who is listening.
export class Album {
  readonly events = new Emitter();
  readonly name: string;
  private readonly photos: string[] = [];

  constructor(name: string) {
    this.name = name;
  }

  add(photo: string): void {
    this.photos.push(photo);
    this.events.emit("photoAdded", { album: this.name, photo });
  }
}

The type parameter does useful work. Subscribing to "photoAdded" gives the listener a payload with album and photo, checked by the compiler, and a misspelled event name is a compile error.

The pattern is simple to write and has four well-known ways of going wrong. The test for this chapter exercised the first two.

  • A listener that throws. This emitter caught the error and still told the remaining listeners. Node.js’s built-in EventEmitter behaves differently: given the same three listeners, it told the first, the second threw, the third was never called, and the error surfaced in the code that emitted. The browser’s EventTarget told all the others and reported the error separately. Know which behavior you have.
  • A listener that is never removed. The subject holds a reference to every listener, and so to everything the listener holds. A screen that subscribes when it opens and does not unsubscribe when it closes can never be freed, and keeps reacting to events after it is gone. Returning the unsubscribe function from on, as here, makes the cleanup hard to forget.
  • Listeners run inside the subject’s call. emit is an ordinary loop. A slow listener makes album.add slow, and a listener that changes the album during the loop can cause a second event to be delivered in the middle of the first.
  • Order that matters. Listeners run in the order they subscribed. Code that relies on that order has a dependency that appears nowhere in the types.

The same idea at the scale of a system is publish and subscribe: the subject and its observers are separate services and a broker carries the events between them (, ). The benefit is the same and so is the cost. Nothing at the point where the event is raised says what will happen as a result.

State

drew the life of an upload as six states and implemented it as a table: for each state, which events it accepts and where they lead. That is the right implementation while a state is only a name. It strains when states acquire behavior of their own: an uploading state that tracks progress and can pause, a failed state that holds the reason and decides whether a retry makes sense. Then every method of the class turns into a switch over the state.

The state pattern gives each state its own class, which implements what every event means in that state. The main object holds a reference to the current state object, forwards every event to it, and replaces it when the state changes.

import type { UploadEvent, UploadState as StateName } from "./table.ts";

// One method for each event. Each returns the state the upload is in afterward.
export type UploadState = { readonly name: StateName } & Record UploadState>;

// The default answer to every event is no. A state overrides only the events it accepts.
abstract class Refusing implements UploadState {
  abstract readonly name: StateName;
  start(_: Upload): UploadState { return this.refuse("start"); }
  received(_: Upload): UploadState { return this.refuse("received"); }
  processed(_: Upload): UploadState { return this.refuse("processed"); }
  error(_: Upload): UploadState { return this.refuse("error"); }
  retry(_: Upload): UploadState { return this.refuse("retry"); }
  cancel(_: Upload): UploadState { return this.refuse("cancel"); }
  private refuse(event: UploadEvent): never {
    throw new Error(`an upload that is ${this.name} cannot ${event}`);
  }
}

class Pending extends Refusing {
  readonly name = "pending";
  override start(upload: Upload): UploadState { return new Uploading(upload); }
  override cancel(): UploadState { return new Canceled(); }
}
class Uploading extends Refusing {
  readonly name = "uploading";
  constructor(upload: Upload) {
    super();
    upload.countAttempt(); // the action on the way in
  }
  override received(): UploadState { return new Processing(); }
  override error(): UploadState { return new Failed(); }
  override cancel(): UploadState { return new Canceled(); }
}
class Processing extends Refusing {
  readonly name = "processing";
  override processed(): UploadState { return new Ready(); }
  override error(): UploadState { return new Failed(); }
}
class Failed extends Refusing {
  readonly name = "failed";
  override retry(upload: Upload): UploadState {
    if (upload.attempts >= Upload.maxAttempts) throw new Error("no attempts left"); // the guard
    return new Uploading(upload);
  }
  override cancel(): UploadState { return new Canceled(); }
}
class Ready extends Refusing { readonly name = "ready"; }
class Canceled extends Refusing { readonly name = "canceled"; }

// The context. It holds the current state object and passes every event to it.
export class Upload {
  static readonly maxAttempts = 3;
  readonly id: string;
  private current: UploadState = new Pending();
  private tries = 0;

  constructor(id: string) {
    this.id = id;
  }
  get state(): StateName { return this.current.name; }
  get attempts(): number { return this.tries; }
  countAttempt(): void { this.tries += 1; }

  handle(event: UploadEvent): void {
    this.current = this.current[event](this);
  }
}

The two implementations ought to behave identically, and that is a claim a test can check. Every possible sequence of one to five events, 9,330 of them, was run against both. The resulting state, the attempt count and the wording of every refusal matched in all of them.

Low-level design interviews lean on this pattern heavily, because so many of the standard exercises are machines with modes: a vending machine that is idle, holding money or dispensing, an elevator that is moving or stopped with its doors open (, ).

Command

The photo editor lets a user crop, rotate and add filters, and take any of it back. A button handler that changes the picture directly leaves nothing behind to undo. The action happened and is gone.

A command is a request turned into an object. The object holds everything needed to carry the request out, and because it is an object it can be stored in a list, sent somewhere else, run later, run again or reversed.

export interface Command {
  readonly label: string;
  run(): void;
  undo(): void;
}

export class Crop implements Command {
  readonly label: string;
  private readonly picture: Picture;
  private readonly width: number;
  private readonly height: number;
  private before: { width: number; height: number } | null = null;

  constructor(picture: Picture, width: number, height: number) {
    this.picture = picture;
    this.width = width;
    this.height = height;
    this.label = `crop to ${width}x${height}`;
  }
  // Cropping cannot be reversed by arithmetic, so the command remembers what it replaced.
  run(): void {
    this.before = { width: this.picture.width, height: this.picture.height };
    this.picture.width = this.width;
    this.picture.height = this.height;
  }
  undo(): void {
    if (!this.before) throw new Error("undo before run");
    this.picture.width = this.before.width;
    this.picture.height = this.before.height;
  }
}

// …Rotate and AddFilter have the same shape, and reverse themselves by arithmetic…

// The invoker. It runs commands without knowing what any of them does.
export class History {
  private readonly done: Command[] = [];
  private readonly undone: Command[] = [];

  run(command: Command): void {
    command.run();
    this.done.push(command);
    this.undone.length = 0; // a new action ends the possibility of redo
  }
  undo(): boolean {
    const command = this.done.pop();
    if (!command) return false;
    command.undo();
    this.undone.push(command);
    return true;
  }
  redo(): boolean {
    const command = this.undone.pop();
    if (!command) return false;
    command.run();
    this.done.push(command);
    return true;
  }
  get labels(): string[] { return this.done.map((command) => command.label); }
  get redoable(): string[] { return this.undone.map((command) => command.label); }
}

The test ran the sequence in the figure and then undid everything. The picture returned to 4000 by 3000 with no rotation and no filters, which is the property that matters: undoing every command in reverse order restores the starting point exactly.

Two designs exist for the “take it back” half, and they trade memory against work.

Each command reverses itselfKeep a snapshot before each command
What is storedThe command and whatever it needs to reverse: a few numbersA full copy of the state. This is the memento pattern
Writing a new actionNeeds a correct undo, which is easy to get subtly wrongNothing extra. Undo is “put the old copy back”

A picture of 12 megapixels is 48 MB in memory at 4 bytes a pixel. A full copy before each of 50 edits takes 2.4 GB. The same history as commands of 64 bytes takes 3.2 kB. Commands are the only practical choice at this size, at the price of a correct undo for every kind of edit.

Real editors mix the two: commands for most actions, and an occasional snapshot so that a long history can be replayed from a recent copy instead of from the start. That combination, a log of changes plus periodic snapshots, is also how databases recover and how event-sourced systems rebuild state (, ).

Undo is the textbook use. In back-end code the pattern appears more often in other forms: a job placed on a queue is a command sent to another process (), an audit log is a list of commands that were run, and the “C” of CQRS is this word (). In those forms the command is plain data, such as { kind: "crop", width: 3000, height: 3000 }, and a separate function carries it out, because methods do not survive being written to a queue and read back.

Chain of responsibility

Before a request reaches the code that lists photos, several questions have to be answered. Is the caller signed in? Have they made too many requests? Should the request be logged? Each question is independent of the others, and each can end the request on its own.

In a chain of responsibility, a request is passed along a line of handlers. Each handler either deals with the request or passes it to the next, and the sender does not know which one will answer.

export interface Request {
  path: string;
  user?: string;
}
export interface Response {
  status: number;
  body: string;
}

export type Handler = (request: Request) => Promise;
// A link in the chain: answer the request itself, or pass it to the rest of the chain.
export type Middleware = (request: Request, next: Handler) => Promise;

// Builds one handler from a list of links and the final handler, innermost first.
export const chain = (links: Middleware[], last: Handler): Handler =>
  links.reduceRight((next, link) => (request) => link(request, next), last);

export const logged = (log: (line: string) => void): Middleware => async (request, next) => {
  const response = await next(request);
  log(`${request.path} ${response.status}`);
  return response;
};

export const signedIn: Middleware = async (request, next) =>
  request.user ? next(request) : { status: 401, body: "sign in first" };

export const limited = (perUser: number): Middleware => {
  const seen = new Map();
  return async (request, next) => {
    const user = request.user ?? "anonymous";
    const count = (seen.get(user) ?? 0) + 1;
    seen.set(user, count);
    return count > perUser ? { status: 429, body: "slow down" } : next(request);
  };
};

Five requests were sent through chain([logged, signedIn, limited(2)], photos) in a test: one with no user, three from Ana and one from Ben. The statuses were 401, 200, 200, 429 and 200. The photos handler ran three times, and the log had five lines, because logged is outermost and sees every response, including the refusals.

This is the shape of middleware in most web frameworks. Two properties need care.

  • Order is behavior. With limited before signedIn, anonymous requests would be counted against a shared “anonymous” user and could lock each other out. With logged innermost, refused requests would leave no trace. The list passed to chain is a design decision and deserves the same attention as the order of decorators in .
  • Something must answer. A classic chain can reach its end with nobody having handled the request. Giving the chain a required final handler, as here, removes that case.

A link that always calls next and only adds something, like logged, is a decorator. A link that may stop the request, like signedIn, is what makes it a chain. Middleware is both at once, which is why the two names are used loosely.

Template method

Photos can be imported from a folder, from a zip archive and from a memory card. Every import does the same things in the same order: list what is there, skip what is not a picture, read each file, save it, and report. Only the listing and the reading differ.

A template method is a method in a base class that defines the steps of an algorithm and their order, and calls other methods for the steps that vary. Subclasses supply those steps and cannot rearrange the whole.

export interface ImportReport {
  imported: string[];
  skipped: string[];
}
type Save = (name: string, bytes: Uint8Array) => Promise;

// The template method form: the base class owns the steps and their order.
export abstract class Importer {
  private readonly save: Save;
  constructor(save: Save) {
    this.save = save;
  }

  // The template method. Subclasses cannot change it, only fill in its steps.
  async run(source: string): Promise {
    const report: ImportReport = { imported: [], skipped: [] };
    for (const name of await this.list(source)) {
      if (!this.accepts(name)) {
        report.skipped.push(name);
        continue;
      }
      await this.save(name, await this.read(source, name));
      report.imported.push(name);
    }
    return report;
  }

  protected abstract list(source: string): Promise;
  protected abstract read(source: string, name: string): Promise;
  // A hook: a step with a default that a subclass may replace.
  protected accepts(name: string): boolean {
    return /\.(jpe?g|png|heic)$/i.test(name);
  }
}

A subclass for folders implements list and read, and that is all it can do. It never calls run’s steps itself. The base class calls the subclass, the reverse of the usual direction, and this is the arrangement every framework is built on: you write the pieces, and the framework decides when to call them. A step with a default, such as accepts, is called a hook.

The pattern uses inheritance, with the costs described in . In TypeScript the same guarantee is available without it: write the algorithm as a function, and pass the varying steps in as an object.

export interface Reader {
  list(source: string): Promise;
  read(source: string, name: string): Promise;
  accepts?(name: string): boolean;
}
const isImage = (name: string): boolean => /\.(jpe?g|png|heic)$/i.test(name);

export async function importFrom(reader: Reader, source: string, save: Save): Promise {
  const report: ImportReport = { imported: [], skipped: [] };
  for (const name of await reader.list(source)) {
    if (!(reader.accepts ?? isImage)(name)) {
      report.skipped.push(name);
      continue;
    }
    await save(name, await reader.read(source, name));
    report.imported.push(name);
  }
  return report;
}

In a test, both forms imported a.jpg, b.HEIC and c.png from the same folder and skipped notes.txt and clip.mov, with identical reports. The function form is a template method implemented with a strategy, and it is usually the better choice in new code. The class form remains common where a framework expects you to extend its classes.

Iterator

An album might keep its photos in an array, in a map grouped by year, or on a server that returns them a hundred at a time. Code that wants to look at each photo should not need to know which.

An iterator is an object that hands out the items of a collection one at a time, on request, without revealing how the collection is stored. JavaScript builds the pattern into the language: any object with a Symbol.iterator method works with for…of, spread syntax and destructuring, and a generator function, marked with *, is the short way to write one.

// A collection that can be walked without showing how it is stored.
export class Shelf implements Iterable {
  private readonly byYear = new Map();

  add(year: number, photo: string): void {
    const list = this.byYear.get(year) ?? [];
    list.push(photo);
    this.byYear.set(year, list);
  }

  // A generator function: each yield hands over one item and pauses until the next is asked for.
  *[Symbol.iterator](): Iterator {
    for (const year of [...this.byYear.keys()].sort()) yield* this.byYear.get(year) ?? [];
  }
}

export interface Page {
  photos: string[];
  next: string | null; // the cursor for the following page, or null on the last one
}
export type FetchPage = (cursor: string | null) => Promise;

// The same idea over a network: pages are fetched only as the consumer reaches them.
export async function* allPhotos(fetchPage: FetchPage): AsyncGenerator {
  let cursor: string | null = null;
  do {
    const page: Page = await fetchPage(cursor);
    yield* page.photos;
    cursor = page.next;
  } while (cursor !== null);
}

The important property is that an iterator is lazy. Nothing is produced until it is asked for. In the test, the server held 500 photos in pages of 100.

The consumer’s loop is the same in both rows, and it contains no cursor, no page size and no network call. The paging scheme of is hidden behind the one line for await (const photo of allPhotos(fetchPage)). Since ECMAScript 2025, synchronous iterators also have map, filter and take methods of their own, which stay lazy where the array methods of the same names build a whole new array at each step.

Common mistake. Collecting an iterator into an array “to be safe”. [...everything] or a loop that pushes every item into a list throws away the laziness, and for a large collection it loads into memory what was designed to stream past.

The other four

Four patterns from the catalog complete the group. They are rarer, and worth recognizing more than rehearsing.

In an interview. Three of these carry most low-level design answers. Strategy covers anything described as a policy: pricing, matching, scheduling, splitting a bill. State covers anything with modes. Observer covers “notify the user when…”. Introduce each at the point where the requirement that needs it comes up, say what would have to change without it, and keep going. A design that names six patterns in the first two minutes reads as recall, not judgment.

Connects to

  • : decorator and bridge, the nearest relatives of chain of responsibility and strategy.
  • : the state diagram this chapter’s state pattern implements.
  • : retry and backoff policies, which are strategies.

  • : choosing among these under interview time.

Key points

  • A strategy is a step passed in from outside. In TypeScript it is usually a function, and you have used one every time you passed a comparison to sort.
  • An observer lets a subject announce events without knowing who reacts. Decide what happens when a listener throws, and always provide a way to unsubscribe.
  • The state pattern gives each state a class. It has the structure of strategy, with the difference that the object replaces its own state from inside.
  • Use a transition table while states are labels, and state objects once states have behavior of their own.
  • A command is an action as an object, which is what makes undo, queues, logs and replay possible.
  • A chain of responsibility passes a request along until a link answers. In middleware, the order of the links is behavior.
  • A template method fixes the order of an algorithm and lets steps vary. A function that takes the steps does the same without inheritance.
  • Iterators are built into the language and are lazy. A consumer that stops early saves the work of producing the rest.

Strategy and state have nearly the same class diagram. What is the difference, and how would you tell which one a piece of code is?

Who changes the object that is held, and when. A strategy is chosen by the caller, passed in, and normally kept for the life of the object that uses it. A state is replaced by the state objects themselves as events arrive, and nothing outside picks it. Look for assignments to the field: one in the constructor suggests strategy, assignments in response to events suggest state.

An emitter has three listeners for an event and the second one throws. What happens to the third with the emitter in this chapter, with Node.js’s EventEmitter and with the browser’s EventTarget?

This chapter’s emitter catches the error, calls the third listener and returns the error to the code that emitted. Node.js’s EventEmitter does not catch: the error propagates out of emit and the third listener is never called. The browser’s EventTarget calls the third listener and reports the error separately, without throwing from dispatchEvent.

After saving a new photo, the service must charge the user’s storage quota and should also update the activity feed. Which of the two belongs in an observer, and why?

The feed. It is a reaction that may lag or fail without making the save wrong. Charging the quota is part of what it means for the save to have succeeded, so it should be a direct call whose failure fails the operation. An observer hides the call and, in most emitters, its errors too.

A user runs commands A, B and C, undoes twice, then runs D. What is on the done stack and the undone stack, and what does redo do now?

Done holds A and D. Undone is empty, because running a new command clears it: B and C described a future that no longer follows from the present state. Redo does nothing.

In the chain [logged, signedIn, limited(2)], what changes if limited(2) is moved in front of signedIn?

Requests are counted before the user is checked. Anonymous requests have no user and are all counted under the same key, so two of them use up the allowance and every later anonymous request gets 429 where it should get 401. Signed-in users are counted as before. The order of links is part of the behavior.

A paged async iterator serves 500 items in pages of 100. A consumer breaks out of its for await loop at the 150th item it reads. How many pages were fetched, and why?

Two. The generator fetches a page only when the consumer asks for an item beyond what it already has. Items 1 to 100 come from the first page and 101 to 150 from the second. When the loop exits, the generator is closed and the remaining three pages are never requested.

Rewrite this requirement as a pattern choice: “Shipping cost is flat within the country, by weight to neighboring countries, and quoted by a carrier’s API elsewhere, and marketing wants to add free shipping over a threshold.”

Strategy: a function or interface from an order to a cost, with one implementation for each rule. The threshold rule is a wrapper around another strategy, returning zero above the threshold and otherwise asking the wrapped one. The checkout code receives a strategy and never mentions countries or carriers.
