What cryptography is for

Every use of cryptography in a system serves one of three goals, and it helps to say which before reaching for a tool.

GoalMeaningToolIn the photo app
ConfidentialityOnly the intended parties can read itEncryptionA private photo on a disk, a password on the wire
IntegrityAny change is detectedHashes, authentication codes, signaturesA backup that restores exactly what was saved
AuthenticityIt came from who it claims to come fromAuthentication codes, signatures, certificatesA token that the sign-in service did issue

Three rules come before any detail.

  • Never design an algorithm or a protocol. Use the standard ones through a maintained library. The code in this chapter exists to show what such a library does, and it calls one for every primitive.
  • Encryption without integrity is a trap. Data that can be read by nobody but changed by anybody is not protected. The modern primitives provide both together.
  • The key is the secret. Algorithms are public. A system is exactly as secure as the handling of its keys, which is why half of this chapter is about that.
RandomnessKeys, nonces, salts and tokens must come from a cryptographic random generator: crypto.randomBytes in Node.js, never Math.random, whose output can be predicted from a few samples.

Hash functions

A cryptographic hash function turns input of any size into a short fixed-size value, called a digest, in such a way that the input cannot be recovered from the digest and no two different inputs with the same digest can be found. SHA-256 produces 32 bytes whatever it is given.

sha256("sunset123") = 6099f9b54e27c593…
sha256("sunset124") = d4b7efa4949d264a…      117 of 256 bits differ
UseHow the hash helps
Detecting corruptionStore the digest with a file. A different digest on reading means the bytes changed ()
Naming contentUse the digest as the identifier. Equal content gets the same name, which gives deduplication and safe caching for free
Fixing a versionA build that names its dependencies by digest cannot be handed different code under the same name
Inside other toolsSignatures, authentication codes and key derivation are all built on hashes

Use SHA-256, or SHA-3 or BLAKE3 where a library offers them. MD5 and SHA-1 are broken for security purposes: researchers can produce two different files with the same digest, which defeats every use above except detecting accidental corruption. A fast hash is also the wrong tool for passwords, for the reasons in .

A hash proves integrity only if the digest itself is trustworthy. Anyone who can change a file can recompute its digest. To prove where data came from, a key has to be involved.

Message authentication codes

A message authentication code, or MAC, is a short value computed from a message and a secret key. Anyone holding the same key can recompute it and so confirm two things at once: the message has not changed, and it came from someone who holds the key. The standard construction is HMAC, used here with SHA-256.

A typical use is a webhook (): your server receives a request claiming to be from a payment provider, and has to know that it is.

import { createHmac, timingSafeEqual } from "node:crypto";

// The sender signs the time and the body, so an old request cannot be replayed later.
export function sign(body: string, key: Buffer, at = Math.floor(Date.now() / 1000)): string {
  const mac = createHmac("sha256", key).update(`${at}.${body}`).digest("hex");
  return `t=${at},v1=${mac}`;
}

export function verify(body: string, header: string, key: Buffer, now = Math.floor(Date.now() / 1000)): boolean {
  const parts = Object.fromEntries(header.split(",").map((p) => p.split("=")));
  const at = Number(parts.t);
  if (!Number.isFinite(at) || Math.abs(now - at) > 300) return false; // older than five minutes
  const expected = createHmac("sha256", key).update(`${at}.${body}`).digest();
  const given = Buffer.from(String(parts.v1 ?? ""), "hex");
  return given.length === expected.length && timingSafeEqual(given, expected);
}

Tested with one valid request and four bad ones, the verifier accepted the first and refused a changed body, a request older than five minutes, a wrong key and a malformed header. Three details carry the weight.

  • Use HMAC, not a hash of the key followed by the message. With SHA-256 that naive form lets an attacker extend a signed message and compute a valid code for the longer one without knowing the key.
  • Sign the time. Otherwise a captured request can be sent again next month and will still verify.
  • Compare in constant time. A comparison that stops at the first wrong byte tells an attacker, through timing, how many bytes were right.

The limit of a MAC is that both sides hold the same key. Either could have produced the code, so it cannot prove to a third party which of them did, and every verifier is able to forge. Signatures, below, remove that limit.

Symmetric encryption

In symmetric encryption the same key encrypts and decrypts. It is fast, at gigabytes a second on ordinary hardware, and it is what protects nearly all data, both stored and in transit.

The algorithm is almost always AES with a 256-bit key. What matters is how it is used. A block cipher on its own encrypts one 16-byte block, and the obvious way to extend that to a longer message, encrypting each block separately, turns equal blocks of input into equal blocks of output, so patterns in the data show through. It also does nothing to stop the ciphertext being altered.

Authenticated encryption is encryption that also produces a tag proving the ciphertext has not been changed, so that tampered data is rejected instead of being decrypted into something wrong. Use it for everything. The two standard choices are AES-256-GCM and ChaCha20-Poly1305.

import { createCipheriv, createDecipheriv, randomBytes } from "node:crypto";

// A sealed value is: version (1 byte) | nonce (12) | tag (16) | ciphertext.
// `context` is not secret and not stored. It must be the same again to open the value.
export function seal(plaintext: string, key: Buffer, context: string): Buffer {
  const nonce = randomBytes(12); // new for every message: never reuse one with the same key
  const cipher = createCipheriv("aes-256-gcm", key, nonce);
  cipher.setAAD(Buffer.from(context));
  const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
  return Buffer.concat([Buffer.from([1]), nonce, cipher.getAuthTag(), ciphertext]);
}

export function open(sealed: Buffer, key: Buffer, context: string): string {
  if (sealed[0] !== 1) throw new Error("unknown format version");
  const decipher = createDecipheriv("aes-256-gcm", key, sealed.subarray(1, 13));
  decipher.setAAD(Buffer.from(context));
  decipher.setAuthTag(sealed.subarray(13, 29));
  // final() throws if a single bit of the nonce, tag, ciphertext or context is wrong.
  return Buffer.concat([decipher.update(sealed.subarray(29)), decipher.final()]).toString("utf8");
}

Sealing the same email address twice gave two different results, because the nonce differed. Opening was refused in each of three tests: one bit of the stored value changed, the right value presented for a different row, and the wrong key.

The second of those is the reason for the context. Without it, an attacker who can write to the database but cannot decrypt anything can still copy Ben’s encrypted value into Ana’s row. Binding each value to its place makes that copy fail to open.

The one rule: never reuse a nonce

A nonce is a value that must be used only once with a given key. It is not secret and is stored with the ciphertext. With AES-GCM, encrypting two messages under the same key and nonce is catastrophic: it reveals the relationship between the two plaintexts and lets an attacker forge further messages.

The code above picks 12 random bytes each time. That is safe only while the number of messages under one key stays small enough that a repeat is implausible, and the limit NIST sets for random nonces is 232 messages for each key, about 4.3 billion. The calculator starts with a busy service: 1,000 messages a second under a key replaced every 90 days.

At 1,000 messages a second, one key encrypts 7.78 billion messages in 90 days. That passes the limit of 2³² after 49.7 days. Replace the key more often than that, give each record its own data key, or use a construction made for more messages per key.

A single long-lived key for a whole table is therefore a design smell at scale. The pattern later in this chapter, a fresh data key for each record or each small group of records, makes the question disappear: no key ever sees more than a few messages.

Public-key cryptography

Symmetric encryption leaves one problem unsolved: both sides need the same key, and they may never have met. Public-key cryptography uses keys that come in pairs, a private key kept by its owner and a public key that can be given to anyone, such that what one does only the other can undo or check. It does three jobs.

JobHowUsed forCommon algorithms
Key agreementTwo parties exchange public values and each derives the same secretStarting every TLS connectionX25519, P-256
SignaturesThe private key signs, and anyone with the public key verifiesCertificates, tokens, software releasesEd25519, ECDSA, RSA
Encryption to a recipientAnyone encrypts with the public key, and only the private key decryptsSending a key or a small secret to one partyRSA, and hybrid schemes built on key agreement

Public-key operations are slow and limited to small inputs, so they are never used on bulk data. They establish a symmetric key, and symmetric encryption does the rest.

The key pairs in that figure are thrown away after one connection. This gives forward secrecy (): someone who records the traffic today and steals the server’s long-term key next year still cannot read it, because the long-term key was only ever used to sign.

Signatures

A digital signature is a value computed from a message with a private key, which anyone holding the matching public key can verify, and which nobody without the private key can produce. Unlike a MAC, verifying does not confer the ability to sign.

import { generateKeyPairSync, sign, verify } from "node:crypto";

// The private key stays with the signer. The public key can be given to anyone.
const { privateKey, publicKey } = generateKeyPairSync("ed25519");

const release = Buffer.from("photos-app 4.2.0 sha256:9f2c…");
const signature = sign(null, release, privateKey); // 64 bytes

verify(null, release, publicKey, signature); // true
verify(null, Buffer.from("photos-app 4.2.1 sha256:9f2c…"), publicKey, signature); // false

This is the mechanism behind the signed tokens of , behind certificates, and behind signed software releases (). In every case the hard question is not the mathematics. It is how the verifier came to trust that this public key belongs to that signer. A certificate is one answer: a public key and a name, signed by an authority the verifier already trusts.

Encryption in transit

For data moving between machines the answer is TLS, and describes how it works. From a design point of view four decisions remain.

  • Everywhere, not only at the edge. Traffic between your own services crosses networks you do not control as closely as you think. Encrypt internal hops too, with mutual TLS where services must identify each other ().
  • Know where it ends. Wherever TLS is terminated, the data is in the clear in that machine’s memory. Each such point is a place to defend ().
  • Use current versions. TLS 1.3, with 1.2 allowed for old clients, and nothing older.
  • Automate certificates. The permitted lifetime of a public certificate is being cut in steps.

The limits are set by the forum of browser makers and certificate authorities. Let’s Encrypt has gone further by choice and has offered certificates valid for six days since January 2026. Short lifetimes replace revocation, which never worked reliably: a stolen key for a six-day certificate is a six-day problem. The price is that issuing and renewing must be done entirely by software, and an expiring certificate must raise an alert long before it expires ().

Encryption at rest

Encryption at rest means that stored data is kept encrypted on its medium and decrypted only when read by something holding the key. The phrase covers designs with widely different protection, and the difference is in who holds the key at the moment of reading.

LayerWho decryptsCostUse it
Disk, volume or database filesThe operating system or database, for every reader it lets inNone that you will noticeAlways. It is one setting, and it covers lost hardware and discarded disks
Chosen fields, in the applicationYour service, one value at a time, through a key serviceThose fields cannot be searched, sorted or joined on in the usual wayFor the columns that would hurt most: identity numbers, access tokens for other systems, health data
End-to-end encryptionOnly the users’ devices. The server stores what it cannot readNo server-side search, processing or recovery. Key handling moves to the clientWhen the promise to users is that you cannot read their content

Backups, replicas, exports and logs are stored data too. An encrypted primary database beside an unencrypted nightly dump is an unencrypted database ().

Managing keys

Encrypting data creates a key that now needs protecting, and encrypting that key creates another. The chain has to end somewhere that is not a file on a disk. It ends in a key management service, or KMS: a service that holds master keys, never releases them, performs encryption and decryption on request, checks who is asking and records every use. Behind it sits a hardware security module, a device built so that keys can be used inside it and cannot be read out of it, even by its operators.

A key service is deliberately a poor place to encrypt data. It is a network call away, it accepts only a few kilobytes at a time, and sending it your data would mean it sees everything. The pattern that resolves this is envelope encryption: each piece of data is encrypted locally with its own data key, and only that small data key is sent to the key service to be encrypted under a master key. The encrypted data key is stored beside the data.

import { randomBytes } from "node:crypto";
import { open, seal } from "./aead";

// What a key management service offers. The key itself never leaves it.
interface Kms {
  wrap(keyId: string, dataKey: Buffer): Buffer;
  unwrap(keyId: string, wrapped: Buffer): Buffer;
}

type Stored = { keyId: string; wrappedKey: Buffer; sealed: Buffer };

export function encryptRecord(kms: Kms, keyId: string, plaintext: string, context: string): Stored {
  const dataKey = randomBytes(32); // a fresh key for this record
  const sealed = seal(plaintext, dataKey, context); // the data is encrypted locally
  const wrappedKey = kms.wrap(keyId, dataKey); // only the small key travels to the KMS
  dataKey.fill(0); // do not keep the plain key around
  return { keyId, wrappedKey, sealed };
}

export function decryptRecord(kms: Kms, stored: Stored, context: string): string {
  const dataKey = kms.unwrap(stored.keyId, stored.wrappedKey); // permission is checked, and the call is logged, here
  try {
    return open(stored.sealed, dataKey, context);
  } finally {
    dataKey.fill(0);
  }
}

// Rotating the master key re-wraps the small data key. The data itself is not touched.
export function rewrap(kms: Kms, stored: Stored, newKeyId: string): Stored {
  const dataKey = kms.unwrap(stored.keyId, stored.wrappedKey);
  const wrappedKey = kms.wrap(newKeyId, dataKey);
  dataKey.fill(0);
  return { ...stored, keyId: newKeyId, wrappedKey };
}

Run against a stand-in key service, a one-megabyte record needed one call to write and one to read, and the key service handled 32 bytes each time. Three properties follow from the shape.

  • Rotation is cheap. Key rotation is the replacement of a key by a new one on a schedule, so that any single key protects a bounded amount of data for a bounded time. Rotating the master key means re-wrapping small data keys, as rewrap does. In the test the megabyte of ciphertext was not touched, and the record still opened.
  • Access is one switch. A service reads data only by asking the key service. Remove its permission and everything it stored is unreadable to it, immediately, wherever the copies are.
  • Deletion can be exact. Crypto-shredding is destroying a key to make everything encrypted under it permanently unreadable, including copies in backups that cannot be edited. In the test, destroying the old master key made the record that still depended on it impossible to open. A key for each tenant turns “delete this customer’s data everywhere” into one operation ().

The same structure answers a request that enterprise customers make: to hold the master key themselves, in their own key service, and be able to withdraw it. The data keys are wrapped under the customer’s key, and your system must be built to fail cleanly for that tenant when the answer is no.

In production. Unwrapping a key for every request adds a network call to every read, and key services limit request rates. Cache plain data keys in memory for a short time, minutes not hours, and treat that cache as what it is: the place an attacker with access to the process will look. Also decide what happens when the key service is unreachable. It has become a dependency of every read of encrypted data, and it needs the treatment in .

Secrets

A secret, in operations, is any value that grants access: a database password, an API key for another company’s service, a signing key, a token. Keys protect data. Secrets are what let your software reach the keys and everything else, and they are stolen far more often than cryptography is broken.

The commonest leak is the plainest. A survey of public commits on GitHub found about 29 million secrets pushed during 2025, and found that 64% of the valid secrets it had detected in 2022 still worked. Private repositories are not safer in kind: one compromised laptop or one mistaken permission exposes everything in them.

PracticeWhat it means
Out of the codeNo secret in source, in a container image or in a configuration file that is committed. A scanner checks every commit before it is accepted
In a secrets managerA service that stores secrets encrypted, hands them out to identified callers only, and records each access. The application fetches what it needs at start, or receives it from the platform at run time
Short-lived where possibleA dynamic secret is created on request and expires by itself: a database account that exists for one hour for one service. A leaked one is soon worthless
No secret at all where possibleWorkload identity lets a service prove what it is to the platform and receive temporary credentials, with nothing stored ()
Rotated without an outageTwo versions valid at once: add the new one, move every user of it over, remove the old one. A secret that cannot be rotated without downtime will not be rotated
NarrowOne secret for each service and purpose, with the least access that works, so that a leak is small and its source is obvious

Common mistake. Responding to a leaked secret by deleting the commit. The secret was copied the moment it was pushed, by automated scanners that watch public repositories, and it stays in every clone and in the history. The only fix is to revoke it and issue a new one, immediately. Then find out what it was used for while it was exposed.

Preparing for quantum computers

A large enough quantum computer would break the public-key algorithms in use today: RSA, and the elliptic-curve algorithms behind key agreement and signatures. No such machine is known to exist. The reason to act anyway is that encrypted traffic can be recorded now and decrypted later, an approach known as harvest now, decrypt later. Anything that must stay secret for ten or twenty years is already exposed to it.

KindEffect of a quantum computerWhat to do
Symmetric encryption and hashesWeakened, not brokenUse 256-bit keys, which you should already
Key agreementBroken, and recorded traffic becomes readableHybrid key agreement: a classical and a post-quantum algorithm together, secure if either holds. Most urgent, because of recording
SignaturesBroken, from the day such a machine existsPost-quantum signatures. Less urgent: a signature cannot be forged retroactively

The standards exist. NIST published three in August 2024: one for key agreement and two for signatures. Deployment of the first is well advanced, and it happened mostly without application developers doing anything, through upgrades to browsers, libraries and content delivery networks. In September 2026 Cloudflare reported that about 70% of the browser traffic reaching it used hybrid post-quantum key agreement, against about 15% of the origin servers it connects to. Signatures and certificates are further behind. NIST’s draft timetable would deprecate today’s public-key algorithms after 2030 and disallow them after 2035.

For a system designer the task is crypto agility: building so that an algorithm can be replaced without redesigning the system. In practice that means three habits. Record the algorithm and key version with everything you encrypt or sign, as the format byte and key identifier in this chapter’s code do. Keep an inventory of where cryptography is used. And keep libraries and TLS endpoints current, because that is how most of the migration will reach you.

Key points

  • Cryptography reduces protecting data to protecting keys. Use standard algorithms through maintained libraries and spend your effort on the keys.
  • A hash detects change. A message authentication code proves origin between two holders of a key. A signature proves it to anyone, and verifying does not allow forging.
  • Always use authenticated encryption, never reuse a nonce with a key, and bind each encrypted value to its context.
  • Public-key cryptography agrees on keys and signs. Symmetric encryption does the bulk work.
  • Encrypt every hop, and automate certificates: their permitted lifetime falls to 47 days by 2029.
  • “Encrypted at rest” ranges from stopping a stolen disk to stopping the operator. Ask who holds the key when the data is read.
  • Envelope encryption keeps master keys inside a key service and makes rotation, revocation and deletion practical.
  • Keep secrets out of code, short-lived and rotatable, and prefer workload identity to any stored secret.
  • Store an algorithm and key version with everything protected, so that algorithms can be replaced, as they are about to be.

Check yourself

A download page publishes a file and its SHA-256 digest on the same server. What does checking the digest prove, and what does it not?

It proves the file was not corrupted in transit or storage. It does not prove the file is the one the publisher made, because anyone able to replace the file on that server can replace the digest too. Proving origin needs a signature made with a private key that is not on that server, verified with a public key the user obtained some other way.

Why can a webhook be authenticated with an HMAC, while a token verified by forty services should use a signature?

An HMAC uses one shared key, and anyone who can verify can also create valid codes. Between two parties that is acceptable. With forty verifying services, every one of them would hold a key able to forge tokens, so compromising any one compromises all. With a signature, services hold only the public key, which verifies and cannot sign.

An application encrypts each user’s stored access token with AES-GCM under one key, with nothing binding the value to its row. An attacker can write to the database and cannot decrypt. What can they still do, and what prevents it?

They can copy one user’s encrypted token into another user’s row, and the application will decrypt it and use it as if it belonged there. Supplying the row’s identity as associated data when sealing, and again when opening, makes a value moved to another row fail authentication.

A service encrypts 1,000 messages a second with random 12-byte nonces under a key replaced every 90 days. Is that within the limit for random nonces, and what are the remedies?

No. 1,000 a second for 90 days is about 7.8 billion messages, and the limit is 232, about 4.3 billion, which is reached after about 50 days. Replace the key more often, or better, use envelope encryption so that each record or small batch has its own data key and no key encrypts more than a handful of messages.

In envelope encryption, what travels to the key management service, and why does rotating the master key not require re-encrypting the data?

Only the data key travels, a few dozen bytes, to be wrapped or unwrapped. The data is encrypted locally under the data key and never sent. Rotating the master key means unwrapping each data key with the old master key and wrapping it with the new one. The data key, and therefore the ciphertext of the data, does not change.

A database runs on encrypted volumes. An attacker exploits an injection flaw in the application and reads the users table. What did the encryption protect?

Nothing in this attack. Volume encryption is undone transparently for anything that reads through the running database, and the injected query does exactly that. It protects against the disk or a raw copy of it being taken. Fields encrypted in the application would have come back as ciphertext.

An engineer pushes a cloud access key to a public repository, notices a minute later, and force-pushes to remove the commit. What is the state of the key, and what is the correct response?

The key must be considered stolen. Public repositories are scanned continuously, and the key was copied when it was pushed. Removing the commit does not recall it. Revoke the key at once, issue a new one through the secrets manager, and review the logs for what the old key was used for while it was exposed.

Why is post-quantum key agreement more urgent to deploy than post-quantum signatures?

Because of recording. Traffic captured today can be stored and decrypted once a capable quantum computer exists, so data that must stay secret for years is already at risk, and only a quantum-resistant key agreement used now prevents that. A signature only needs to resist forgery at the time it is checked, so classical signatures remain safe until such a machine exists.
