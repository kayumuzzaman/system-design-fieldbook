The problem

The problem. Design the autocomplete for a search box. As the user types, show up to ten completions of what they have typed, ranked by how popular they are, in their language and region. Popular new searches should appear quickly, the user’s own recent searches should be offered, and offensive suggestions must never be shown.

The difficulty is the request rate against the time budget. Every keystroke is a request, so the service receives several times as many requests as the search engine behind it, and an answer that arrives after the next keystroke is useless. That rules out any work at request time beyond a lookup: no counting, no sorting, no scanning. In the terms of , it is a read-heavy problem whose answer is to precompute, and the interesting questions are what to precompute, how often, and how to keep it fresh.

Step 2: Estimates

Assume each search produces five lookups after the browser skips keystrokes that come in quick succession, and that an edge cache answers half of them (; the simulation later in this chapter measured fewer lookups and more cache hits, so these are cautious).

searches: 1 billion a day ÷ 86,400 s ≈ 11,600 a second, about 35,000 at a peak of three times that
lookups: 5 per search ≈ 58,000 a second on average, about 174,000 at the peak
reaching the servers: half of the peak ≈ 87,000 a second
index: 100 million distinct queries × about 90 bytes ≈ 9 GB
logs into the counting job: 1 billion searches × about 100 bytes = 100 GB a day

The index fits in the memory of one ordinary server, which decides the shape of the design: copy the whole index to every server and spread requests across the copies, rather than splitting it. The 90 bytes per query come from counts measured below, 1.35 tree nodes per query, with assumed sizes of 32 bytes per node, a 4-byte id for each of five stored suggestions and the query’s text. The request rate is high but each request is a lookup in memory; in one run of the chapter’s code, one core did 2.5 million lookups a second, so the cost of a request is its network handling, not the search.

The public lookup depends only on the prefix, the language and the region, so the same answer serves everyone and can be cached by the browser, the edge and the service (). Anything personal goes in a separate request marked private, or is merged in the browser, because a shared cache that stored one user’s history would show it to the next. The seq number lets the browser ignore an answer that arrives after a newer one. There is no pagination: ten results is the whole answer.

The index is built, never updated in place. A builder produces a complete new version, the servers load it beside the old one and switch, and a bad version is undone by switching back. That is simpler and safer than updating a tree that is serving 87,000 lookups a second, and it costs only memory for two copies during the switch.

Step 5: The design

The data path runs on the scale of hours. The search service writes an event for every search to a queue. A counting job, a streaming aggregation (), keeps a count per query that fades with age. Every hour the builder takes the counts above a threshold, removes anything on the blocklist, computes the best completions of every prefix and writes a new index. The request path runs in milliseconds and only reads.

The browser does real work in this design. It waits a few tens of milliseconds after each keystroke before asking, a technique called debouncing: a key pressed before the wait is over cancels the pending request, so a fast typist sends one request for several letters. It keeps the answers it has received, so deleting a letter costs nothing. And it numbers its requests, because answers from different servers can arrive out of order.

// Called on every keystroke with the whole text typed so far.
  typed(prefix: string): void {
    if (this.pending !== null) this.timer.clear(this.pending); // a new key cancels the wait
    const seq = this.nextSeq++;
    const known = this.cache.get(prefix);
    if (known) { this.show(seq, known); return; } // deleting a letter costs nothing
    this.pending = this.timer.set(() => {
      this.pending = null;
      this.requests += 1;
      this.fetch(prefix, seq).then((r) => {
        this.cache.set(prefix, r.suggestions);
        this.show(r.seq, r.suggestions);
      }, () => {}); // a failed lookup leaves the box working, without suggestions
    }, this.waitMs);
  }

  private show(seq: number, suggestions: string[]): void {
    if (seq <= this.shownSeq) return; // an answer older than what is on screen
    this.shownSeq = seq;
    this.shown = suggestions;
  }
}

In the chapter’s test, four quick keystrokes and a backspace sent two requests, and an answer that arrived late was not shown.

Step 6a: A trie with the answers stored in it

A trie is a tree for strings with one node for every distinct prefix: the path from the root to a node spells the prefix, and the node’s children are the letters that can follow it. Finding the node for a prefix takes one step per character, whatever the number of strings stored. The name comes from “retrieval”, from Edward Fredkin’s paper of 1960.

Finding the node is not the same as finding the answer. The best completions of “te” are somewhere in the subtree below it, and without help the lookup must visit that whole subtree and sort what it finds. The fix is to do that work once, when the index is built: each node stores the best k completions of everything below it. A node’s list is the best k of its own query and its children’s lists, so building visits each node once, children first.

// Store at every node the best k completions below it, children first. The list of a node is
  // the best k of its own query and its children's lists, so each node merges a few short lists.
  build(): void {
    const visit = (n: TrieNode): Suggestion[] => {
      const all: Suggestion[] = n.score > 0 ? [{ text: n.text, score: n.score }] : [];
      for (const c of n.children.values()) all.push(...visit(c));
      n.top = all.sort(better).slice(0, this.k);
      return n.top;
    };
    visit(this.root);
  }

  // With precomputed lists: walk down the prefix, read the list. Cost: the length of the prefix.
  complete(prefix: string): { results: Suggestion[]; visited: number } {
    const { node, visited } = this.find(prefix);
    return { results: node ? node.top : [], visited };
  }

The chapter’s code built a trie of 100,000 synthetic queries with a long-tailed popularity, and replayed 100,000 searches in which users typed one letter at a time and stopped when their query was suggested. The test checks the stored lists against sorting all matching queries, for 300 random prefixes.

The cost of walking the subtree is worst exactly where it matters most. A one-letter prefix has a subtree of tens of thousands of nodes, about 53,000 on average here, and one-letter prefixes were 32% of all requests. With stored lists, every lookup is two to seven node visits.

The price is memory. The 100,000 queries, 12.6 characters long on average, made 586,460 nodes, 5.86 per query, and with five suggestions at every node, 736,366 stored entries. Most nodes have a single child: merging each chain of single-child nodes into one node, a radix tree, left 135,089 nodes, 1.35 per query, and only those need lists, since every prefix inside a chain has the same completions as the node at its end. Storing each suggestion as a 4-byte id into a table of query texts, rather than as the text itself, keeps the lists small. That is where the estimate of about 90 bytes per query came from.

Other ways to store itA hash table from every prefix to its list does the same job with a plain key-value store, at the cost of storing each prefix as a key; it is the easiest version to build in an interview. Search engines offer a compact form of the trie called a finite state transducer, which shares suffixes as well as prefixes: Elasticsearch’s completion suggester is built this way, and its documentation describes the structure as “entirely heap resident” and “optimized for speed”.

Step 6b: Counting so that trends appear

The ranking is only as good as the counts. Counting every search since the service began makes the list stable and blind: a query searched a million times last year outranks one searched a hundred thousand times this morning. The usual answer is to let old searches count for less. With exponential decay, a count loses half its weight every fixed period, its half-life, so the score of a query is a sum in which recent searches dominate. It can be updated as each search arrives, by multiplying the stored count by the decay since its last update and adding one, which suits a streaming job.

// Counts that lose half their weight every `halfLife` hours, updated as each search arrives.
// Only the count and the time of its last update are kept for each query.
export class DecayedCounts {
  private readonly halfLife: number;
  private readonly entries = new Map();
  constructor(halfLifeHours: number) {
    this.halfLife = halfLifeHours;
  }
  add(query: string, at: number, weight = 1): void {
    this.entries.set(query, { value: this.value(query, at) + weight, at });
  }
  value(query: string, now: number): number {
    const e = this.entries.get(query);
    return e ? e.value * 0.5 ** ((now - e.at) / this.halfLife) : 0;
  }
}

How the counting is done decides how soon a trend shows up and how long it stays. The chapter’s model takes one prefix with ten established queries and adds a new one that rises over three hours to twice the volume of the most popular, holds for a day, then halves every 12 hours.

A window reacts late because the trend’s total must catch up with a week of the others’ totals, and then holds on for the rest of the week after interest has gone. Decay reacts within hours, ranks the trend first while it is at its peak, and lets go a few days after it fades. Rebuilding more often helps only as much as the counts allow. A design can go further with a separate fast path that detects queries rising sharply above their usual rate and boosts them, at the risk of amplifying something nobody should see, which is why the blocklist and human review sit on the same path.

Common mistake. Counting searches rather than people. One script repeating a query ten thousand times an hour would put it in everyone’s suggestions. Count distinct users per query and period, ignore traffic from clients already flagged as automated, and require a query to come from many users before it can be suggested at all. Requiring a minimum number of users also keeps rare queries, which may contain names or other private details, out of the index.

Step 6c: Serving the short prefixes

In the simulation, queries were 10.7 characters long on average and users found the one they wanted among five suggestions after 3.1 characters, in 99.2% of searches. That makes the request stream lopsided: 32% of requests were for one-letter prefixes, 20% for two and 17% for three, and only 18,352 distinct prefixes were requested at all. Caching the 100 most requested prefixes would have answered 60% of requests, the 1,000 most requested 83%, and 10,000 answered 97%. A small cache at the edge, or in the browser for the first letter, absorbs most of the load. Real query logs have a longer tail than this model, so expect a lower hit rate, which is why the estimate assumed half.

If the index outgrows one server’s memory, it must be split, and how matters. Splitting by first letter, all prefixes from a to c on one shard and so on, puts each hot one-letter prefix on one shard together with everything that starts with it: with eight shards, the busiest received 2.23 times the average load. Splitting by a hash of the whole prefix spreads them better, 1.58 times the average, because each prefix’s list is independent of every other’s (). It cannot do better than that: a single prefix such as “s” cannot be split, so it needs replicas or a cache in front of it, the hot key problem of .

Step 6d: Personal suggestions and filtering

The user’s own history is small, private and changes with every search, so it does not belong in the shared index. The suggestion service fetches the global list for the prefix, with more candidates than it will show, say twenty, and the user’s recent searches that start with the prefix, then ranks the combination with a boost for the user’s own and for the user’s location. Facebook described this split in 2010: an aggregator with no index of its own queries one service for global objects and one for the user’s own neighborhood in the social graph, while the browser prefetches the user’s friends and pages as soon as the search box gets focus.

Filtering happens twice. The builder drops blocked queries so they never enter the index, and the suggestion service checks again at request time, because a pattern added to the blocklist must take effect in minutes, not at the next hourly build. The check at request time is a lookup in a small set, and it is the one place where the request path does more than read.

At ten times the scale, 10 billion searches a day, the peak reaches about 1.7 million lookups a second and 870,000 reach the servers at the same cache rate: more replicas, not a different design. The index grows with distinct queries rather than with traffic, and a billion of them, about 90 GB, still fits in a large server’s memory or splits by hash across a few. One index per language and region keeps each smaller. At a hundred times, the edge cache carries more of the load and the counting pipeline becomes a large streaming system in its own right, sharded by query ( counts events at that scale).

In the real world

  • Google explained in October 2020 that its predictions “reflect searches that have been done on Google”, starting from common and trending queries that match what was typed, shaped by language and location, with freshness able to lift a rising topic above more common ones. Automated systems try to block predictions that are violent, sexually explicit, hateful, disparaging or dangerous, and enforcement teams remove those that get through, often with closely related variations.
  • Facebook’s typeahead, described in May 2010, prefetched the user’s friends, pages, groups, applications and events to the browser as soon as the search box was focused, and sent other prefixes to a stateless aggregator that queried a global service and a social-graph service in parallel. The post notes that spending more than 100 milliseconds on a result makes the typeahead “stutter”.
  • Elasticsearch’s completion suggester, as documented in 2026, keeps its lookup structures in memory, describes the completion index as “entirely heap resident” and itself as “optimized for speed”, and supports a weight for ranking each suggestion and contexts for filtering.

In an interview. Five minutes on requirements, then estimates that end with “the index fits in memory, so replicate it”. Draw the two paths early and say that the request path only reads. Key points

  • Split the design into a request path that only reads and a data path that counts, ranks, filters and builds, on a schedule of hours.
  • Store the best completions at every trie node. A lookup becomes one step per character: 2 node visits instead of about 53,000 for a one-letter prefix in the test.
  • Merge single-child chains and store ids, not texts: about 1.35 nodes and 90 bytes per query, so a large index fits in memory and is replicated, not sharded.
  • Count with decay. All-time counts never showed a sudden trend; a one-day half-life showed it within 6 hours and let it go within days.
  • Short prefixes are most of the traffic and are the same for everyone: cache them at the edge and in the browser.
  • Keep personal suggestions out of shared caches, count people rather than searches, and filter both when building and when serving.

Check yourself

Why is finding the trie node for a prefix not enough to answer a lookup quickly?

The node only marks where the completions are. They are spread through its subtree, which for a short prefix holds a large share of all queries, so finding the best ones means visiting and sorting all of them. Storing the best k at each node when the index is built moves that work out of the request.

Why does a radix tree need lists only at its nodes, not at every character?

A chain of single-child nodes has exactly one way to continue, so every prefix inside the chain has the same set of completions as the node at the end of the chain. One list serves them all.

A query spikes this morning. Why does ranking by all-time counts never suggest it?

Its few hours of searches are compared with years of searches for established queries. Even at twice their hourly rate, it cannot catch up with their totals before interest fades.

How can a decayed count be updated as each search arrives, without keeping the history?

Store the count and the time it was last updated. On a new search, multiply the stored count by one half raised to the time elapsed divided by the half-life, add one, and store the new time.

Why is a one-letter prefix a problem for sharding, and what solves it?

All requests for that prefix go to whichever shard holds it, and no way of splitting can divide a single key. Splitting by hash spreads different prefixes evenly but not one hot prefix. Replicas of the shard, or caching that prefix’s answer at the edge and in the browser, carry its load.

The answer for “we” arrives after the answer for “wea”. What should the browser do and how does it know?

Drop it. Each request carries an increasing sequence number that the answer echoes, and the browser shows an answer only if its number is higher than the one on screen.

Why must the blocklist be applied at request time as well as when the index is built?

Because the index is rebuilt every hour or so, and a newly harmful suggestion must disappear in minutes. The request-time check is a small set lookup, cheap enough for every request.
