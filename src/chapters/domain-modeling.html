Where the rules live

The photo app has started selling paper prints. A customer builds an order from their photos, places it, and it is printed and shipped. The business has rules, as every business does: an order must contain something before it can be placed, a quantity is a whole number of at least one, an order that has been placed cannot be changed, and one that has shipped cannot be canceled.

The domain is the area of the real world a program is about. A domain model is the set of types and rules in the code that represent it. The question this chapter asks of any design is: where does each rule live, and what stops code from going around it?

The commonest answer in practice is “nowhere in particular”.

// An "anemic" model: the order is a bag of public fields, and every rule lives in whoever touches it.
export interface OrderRecord {
  id: string;
  status: string;
  lines: { photo: string; size: string; quantity: number; unitPrice: number }[];
  total: number;
}

// One of several places that add to an order. This one remembered two of the rules.
export function addToOrder(order: OrderRecord, photo: string, size: string, quantity: number, unitPrice: number): void {
  if (order.status !== "draft") throw new Error("order is not open");
  if (quantity < 1) throw new Error("bad quantity");
  order.lines.push({ photo, size, quantity, unitPrice });
  order.total += quantity * unitPrice;
}

// Another place, written later by someone else. Nothing stops it.
export function applyAdminFix(order: OrderRecord): void {
  order.lines.push({ photo: "p9", size: "big", quantity: -2, unitPrice: 0.1 });
  order.status = "placed";
}

Every line of this compiles. After a test ran both functions, the order had a stored total of 0.9000000000000001 while its lines added up to 0.7000000000000002, a line with a quantity of −2 in a size that does not exist, and the status “placed”. Three separate problems are visible.

  • The rules are optional. They are enforced by the functions that remembered them. The data structure itself accepts anything.
  • The types say almost nothing. A status is any string, a price is any number, an identifier is any string and can be passed where a different kind of identifier was expected.
  • Derived data is stored and drifts. The total is kept in a field and updated by hand, so it can disagree with the lines it summarizes.

A model with data and no behavior is called an anemic domain model. The rest of the chapter rebuilds the order so that all three problems become impossible, using a vocabulary that comes from Eric Evans’s 2003 book Domain-Driven Design. The vocabulary is useful on its own, whether or not a team adopts the rest of that approach.

Finding the model

A model starts from how the people in the business talk. Listen to a description of the work, and sort what you hear.

You hearIt is probablyIn the print shop
A noun with a lifetime, tracked individuallyAn entityAn order, a customer, a photo
A noun that only describes or measuresA value objectA price, a print size, a delivery address
A verbAn operation on an entityAdd prints, place, cancel, ship
“Must”, “never”, “only if”, “at most”An invariantAn empty order cannot be placed
“When … happens, then …”A domain event and a reaction to itWhen an order is placed, the printer is told

An invariant is a condition that must hold whenever anyone looks. Invariants are the reason to model at all: a type that has none can be a plain record.

Two habits pay for themselves at this stage. Use the business’s own words as the names in the code, so that a sentence spoken in a meeting and a line in the program describe the same thing. Evans called this a ubiquitous language. And notice when one word is used for two different things, because that marks a boundary. The last section returns to it.

Value objects

A value object is a small object defined entirely by its contents. It has no identity of its own, it never changes after it is created, and two of them with the same contents are interchangeable. A price, a date range, a pair of coordinates and an email address are values.

Money is the standard first example, because representing it as a plain number goes wrong in three ways at once: fractions of a cent appear from nowhere, currencies get added to each other, and division loses or invents cents.

export type Currency = "EUR" | "USD" | "GBP";

// A value object: no identity, never changes, equal when its contents are equal, valid from the moment it exists.
export class Money {
  readonly cents: number;
  readonly currency: Currency;

  private constructor(cents: number, currency: Currency) {
    this.cents = cents;
    this.currency = currency;
    Object.freeze(this);
  }

  static of(cents: number, currency: Currency): Money {
    if (!Number.isSafeInteger(cents)) throw new Error(`money is a whole number of cents, got ${cents}`);
    return new Money(cents, currency);
  }
  static zero(currency: Currency): Money {
    return new Money(0, currency);
  }

  plus(other: Money): Money {
    if (other.currency !== this.currency) throw new Error(`cannot add ${other.currency} to ${this.currency}`);
    return Money.of(this.cents + other.cents, this.currency);
  }
  times(count: number): Money {
    if (!Number.isInteger(count)) throw new Error("multiply money by a whole number");
    return Money.of(this.cents * count, this.currency);
  }
  equals(other: Money): boolean {
    return this.cents === other.cents && this.currency === other.currency;
  }

  // Divides without losing or inventing a cent: the remainder goes to the first shares.
  split(shares: number): Money[] {
    if (!Number.isInteger(shares) || shares < 1) throw new Error("split into at least one share");
    const base = Math.floor(this.cents / shares);
    const extra = this.cents - base * shares;
    return Array.from({ length: shares }, (_, i) => Money.of(base + (i < extra ? 1 : 0), this.currency));
  }

  toString(): string {
    return `${(this.cents / 100).toFixed(2)} ${this.currency}`;
  }
}

Four properties make this more than a wrapper.

  • Valid or nonexistent. The constructor is private and the only way in is Money.of, which checks. Code that receives a Money never needs to check it again. This is the idea summarized as “parse, don’t validate”: check once at the edge, and return a type that carries the proof.
  • Immutable. plus returns a new value. A value that cannot change can be shared freely, including between concurrent operations ().
  • Equal by contents. Two separately created 5.00 EUR objects are different objects and the same value, so comparison is a method, equals.
  • Behavior lives with the data. The rule for splitting without losing a cent is written once, here, and not in each place that divides a bill ().

Not every value needs a class. A print size is one of three strings, and a union type says so exactly. An identifier can be given a branded type: a string to the running program, a distinct type to the compiler, so that a photo’s identifier cannot be passed where an order’s is expected. Both appear at the top of the next listing.

Common mistake. Primitive obsession: representing every concept as a string or number. A function with the signature (string, string, number, number) accepts its arguments in any order and any units. Each primitive that has rules of its own, such as an email address, a percentage or a quantity, is a candidate for a value type.

Entities

An entity is an object with an identity that persists while its contents change. An order that gains a line is the same order. Two customers who happen to share a name and an address are two customers. Entities are compared by identifier, and they have a lifecycle: they are created, change through defined operations and reach final states.

EntityValue object
Equal whenIdentifiers matchContents match
Changes over timeYes, through its own methodsNever. A change produces a new value
Question to ask“Which one?”“How much?” or “what kind?”

The same real thing can be either, depending on the domain. To the print shop an address is a value: where to send the parcel. To a postal service an address is an entity with a history.

Aggregates

An order and its lines have rules that span both: at most fifty lines, no line without an order, a total that is the sum of the lines. If lines could be created, changed and saved independently, no single piece of code would be in a position to enforce any of that.

An aggregate is a cluster of objects treated as one unit for the purpose of changes. One entity is its aggregate root. Code outside the aggregate holds references only to the root and asks the root to make every change, and the root keeps the whole cluster valid.

// Branded identifiers: all strings at run time, different types at compile time.
export type OrderId = string & { readonly __brand: "OrderId" };
export type CustomerId = string & { readonly __brand: "CustomerId" };
export type PhotoId = string & { readonly __brand: "PhotoId" };

export type PrintSize = "10x15" | "13x18" | "20x30";
export type OrderStatus = "draft" | "placed" | "shipped" | "canceled";

export interface OrderLine {
  readonly photo: PhotoId; // another aggregate, referred to by identifier only
  readonly size: PrintSize;
  readonly quantity: number;
  readonly unitPrice: Money; // the price when the line was added, kept with the order
}

export type OrderEvent =
  | { type: "OrderPlaced"; order: OrderId; customer: CustomerId; total: Money }
  | { type: "OrderCanceled"; order: OrderId };

export class DomainError extends Error {}

// The aggregate root. Lines exist only inside an order and are reached only through it.
export class Order {
  static readonly maxLines = 50;
  static readonly maxPerLine = 100;

  readonly id: OrderId;
  readonly customer: CustomerId;
  readonly currency: Currency;
  private state: OrderStatus = "draft";
  private readonly lines: OrderLine[] = [];
  private readonly events: OrderEvent[] = [];

  constructor(id: OrderId, customer: CustomerId, currency: Currency = "EUR") {
    this.id = id;
    this.customer = customer;
    this.currency = currency;
  }

  get status(): OrderStatus {
    return this.state;
  }
  get items(): readonly OrderLine[] {
    return [...this.lines];
  }
  // Derived every time it is asked for, so it cannot disagree with the lines.
  get total(): Money {
    return this.lines.reduce((sum, line) => sum.plus(line.unitPrice.times(line.quantity)), Money.zero(this.currency));
  }

  addPrints(photo: PhotoId, size: PrintSize, quantity: number, unitPrice: Money): void {
    this.mustBeDraft("add prints to");
    if (!Number.isInteger(quantity) || quantity < 1) throw new DomainError("quantity must be a whole number, at least 1");
    if (unitPrice.currency !== this.currency) throw new DomainError(`this order is priced in ${this.currency}`);
    const at = this.lines.findIndex((line) => line.photo === photo && line.size === size);
    const existing = at >= 0 ? (this.lines[at] as OrderLine).quantity : 0;
    if (existing + quantity > Order.maxPerLine) throw new DomainError(`at most ${Order.maxPerLine} prints of one photo in one size`);
    if (at < 0 && this.lines.length >= Order.maxLines) throw new DomainError(`an order holds at most ${Order.maxLines} lines`);
    const line: OrderLine = { photo, size, quantity: existing + quantity, unitPrice };
    if (at >= 0) this.lines[at] = line;
    else this.lines.push(line);
  }

  place(): void {
    this.mustBeDraft("place");
    if (this.lines.length === 0) throw new DomainError("an empty order cannot be placed");
    this.state = "placed";
    this.events.push({ type: "OrderPlaced", order: this.id, customer: this.customer, total: this.total });
  }

  cancel(): void {
    if (this.state === "shipped") throw new DomainError("a shipped order cannot be canceled");
    if (this.state === "canceled") return; // canceling twice is harmless
    this.state = "canceled";
    this.events.push({ type: "OrderCanceled", order: this.id });
  }

  markShipped(): void {
    if (this.state !== "placed") throw new DomainError(`an order that is ${this.state} cannot be shipped`);
    this.state = "shipped";
  }

  // Hands over what happened since the last call, for publishing after the order is saved.
  pullEvents(): OrderEvent[] {
    return this.events.splice(0);
  }

  private mustBeDraft(action: string): void {
    if (this.state !== "draft") throw new DomainError(`cannot ${action} an order that is ${this.state}`);
  }
}

The test put the same pressure on this class that broke the first version. Ten invalid operations were attempted, including placing an empty order, quantities of 0, −1 and 1.5, a 51st line, a price in the wrong currency, a change after placing and an attempt to cancel after shipping. All ten were refused with a message in the business’s own terms. The order ended with two lines and a total of 5.75 EUR.

Compare it with the anemic version point by point.

  • State is private and changes only through named operations. There is no setStatus. There is place(), which is a thing the business does.
  • Each rule is written once, beside the data it protects ().
  • The total is computed, not stored, so it cannot drift.
  • The unit price is copied onto the line. An order is a record of an agreement, and must not change when the price list does. In the test, the shop raised its prices after the lines were added, and the order still totaled what the customer had been shown.
  • Callers get copies. items returns a new array, and pushing onto it left the order untouched.

Four rules govern how aggregates relate to everything else.

  1. Reference other aggregates by identifier. A line holds a PhotoId, not a Photo. Otherwise loading an order would load its photos, and their albums, and so on without end.
  2. One aggregate, one transaction. Each change loads one aggregate, changes it and saves it whole. Its invariants are therefore true after every commit.
  3. Between aggregates, consistency comes later. When placing an order must reduce a stock of paper, that happens in reaction to an event, shortly afterward ().
  4. Keep them small. The next section explains why.

How large to make an aggregate

It is tempting to follow containment in the real world: an album contains photos, so Album should hold a list of Photo objects. The aggregate boundary is a different thing. It says what must be consistent at every instant, and therefore what is loaded, locked and saved together.

The question to ask of each candidate rule is: what happens if this is briefly untrue? If the answer is “a customer is charged for nothing” or “the same seat is sold twice”, the data involved belongs in one aggregate. If the answer is “a counter is off by one for a second”, it does not, and paying for instant consistency with every write is a poor trade.

The cost of a large aggregate can be estimated. With the versioning scheme of the next section, a change fails and must be retried whenever someone else saved the same aggregate between its load and its save.

At 0.2 changes a second to the same aggregate and 50 ms between loading and saving, about 0.01 other changes land inside each change’s window on average. A change collides 0.995% of the time. Collisions are rare, and a retry handles them without anyone noticing.

One customer’s order is changed by one person a few times a minute, and collisions are a curiosity. An album that is an aggregate of all its photos, receiving twenty uploads a second during a shared event, is a different matter: try 20 in the first field.

Repositories

A repository is an object that stores and retrieves whole aggregates, and presents itself as if it were a collection in memory. There is one for each aggregate root. Code that uses it never sees a table, a query or a join.

import { Order, type OrderId, type OrderSnapshot } from "./order.ts";

// A repository looks like a collection of whole aggregates. Callers never see tables or queries.
export interface OrderRepository {
  get(id: OrderId): Promise;
  save(order: Order): Promise;
}

export class ConflictError extends Error {}

// Good enough for tests, and it enforces the same rule a database implementation would:
// a save succeeds only if nobody else has saved this order since it was loaded.
export class InMemoryOrders implements OrderRepository {
  private readonly rows = new Map();
  private readonly loadedAt = new WeakMap(); // the version each order object was read at

  async get(id: OrderId): Promise {
    const row = this.rows.get(id);
    if (!row) return null;
    const order = Order.fromSnapshot(structuredClone(row.data));
    this.loadedAt.set(order, row.version);
    return order;
  }

  async save(order: Order): Promise {
    const expected = this.loadedAt.get(order) ?? 0;
    const stored = this.rows.get(order.id)?.version ?? 0;
    if (stored !== expected) throw new ConflictError(`order ${order.id} was changed by someone else (version ${stored}, expected ${expected})`);
    this.rows.set(order.id, { version: stored + 1, data: structuredClone(order.toSnapshot()) });
    this.loadedAt.set(order, stored + 1);
  }
}

The interface has two methods because that is all the domain needs: get one, save one. A production implementation would map the aggregate to an orders table and an order_lines table and write both in one transaction (). The model does not change when that implementation is swapped in, which is the dependency inversion principle doing its job ().

The version check deserves attention, because two requests changing the same order is a race of the kind described in . The repository turns it from a silent loss into a visible refusal.

In the test, two copies of an order were loaded, the first was saved, and the second save was refused with a ConflictError, leaving the stored order as the first had written it. This is optimistic locking () with the aggregate as its unit. In SQL it is one extra condition: UPDATE orders SET …, version = version + 1 WHERE id = $1 AND version = $2, and a check that one row was changed.

Use cases, events and services

Something has to load the aggregate, call it and save it. That code is an application service, also called a use case: one method for each thing a user can do. It contains the sequence and none of the rules.

export type PriceList = (size: PrintSize) => Money;
export type Publish = (event: OrderEvent) => Promise;

// Every use case has the same shape: load one aggregate, tell it what to do, save it, publish what happened.
export class OrderService {
  private readonly orders: OrderRepository;
  private readonly priceOf: PriceList;
  private readonly publish: Publish;

  constructor(orders: OrderRepository, priceOf: PriceList, publish: Publish) {
    this.orders = orders;
    this.priceOf = priceOf;
    this.publish = publish;
  }

  addPrints(id: OrderId, photo: PhotoId, size: PrintSize, quantity: number): Promise {
    return this.change(id, (order) => order.addPrints(photo, size, quantity, this.priceOf(size)));
  }

  place(id: OrderId): Promise {
    return this.change(id, (order) => order.place());
  }

  // On a conflict the change is applied again to a fresh copy. The rules are checked again each time.
  private async change(id: OrderId, apply: (order: Order) => void, attempts = 3): Promise {
    for (let attempt = 1; ; attempt += 1) {
      const order = await this.orders.get(id);
      if (!order) throw new Error(`no order ${id}`);
      apply(order);
      try {
        await this.orders.save(order);
      } catch (error) {
        if (error instanceof ConflictError && attempt < attempts) continue;
        throw error;
      }
      for (const event of order.pullEvents()) await this.publish(event);
      return;
    }
  }
}

Two requests that added prints to the same order at the same moment were both kept in the test: one save conflicted, the service loaded a fresh copy, applied the change again and succeeded. The retry is safe because it re-runs the order’s own checks against the new state. Had the first request placed the order, the retried addition would have been refused.

Three smaller ideas appear in this listing.

  • Domain events. A domain event is a record that something the business cares about has happened, named in the past tense: OrderPlaced. The aggregate records its events as it changes, and the service publishes them after the save succeeds. The printing floor, the email sender and the billing system react to the event, and the order knows none of them ().
  • Domain services. Some logic belongs to the domain and to no single entity. Looking up the current price of a print size is not something an order should do for itself. Here it is a function, PriceList, passed in.
  • The gap between saving and publishing. If the process stops after the save and before the publish, the order is placed and nobody is told. Closing that gap takes the outbox pattern: write the event to the same database, in the same transaction, and deliver it from there ().

States as types

The Order class checks its state at run time: place() throws if the order is not a draft. TypeScript offers a stronger option for some rules, which is to give each state its own type, carrying only the data that exists in that state.

import type { Money } from "./money.ts";
import type { OrderLine } from "./order.ts";

// Each state carries exactly the data that exists in that state. A draft has no shipping date to get wrong.
export type Draft = { status: "draft"; lines: OrderLine[] };
export type Placed = { status: "placed"; lines: OrderLine[]; total: Money; placedAt: Date };
export type Shipped = { status: "shipped"; lines: OrderLine[]; total: Money; placedAt: Date; shippedAt: Date; tracking: string };
export type Canceled = { status: "canceled"; canceledAt: Date; reason: string };
export type OrderState = Draft | Placed | Shipped | Canceled;

// Only a placed order can be shipped, and the compiler enforces it: the parameter's type is Placed.
export function ship(order: Placed, tracking: string, now: Date): Shipped {
  return { ...order, status: "shipped", shippedAt: now, tracking };
}

export function describe(order: OrderState): string {
  switch (order.status) {
    case "draft": return `draft with ${order.lines.length} lines`;
    case "placed": return `placed, ${order.total}`;
    case "shipped": return `shipped, tracking ${order.tracking}`;
    case "canceled": return `canceled: ${order.reason}`;
  }
}

With these types, calling ship on a draft does not compile, and neither does reading shippedAt from one. The test file contains both lines, each marked as an expected compile error, and the type checker confirms them on every run. The approach is often summarized as making illegal states unrepresentable: an order that is “shipped” with no shipping date cannot be written down, so no code has to defend against it.

The two styles combine well. Use types for rules about shape, such as which fields exist in which state. Use methods on the aggregate for rules about values, such as “at most fifty lines”, which no type can express.

Bounded contexts

Ask three teams what a “photo” is. To the library team it has an owner, a date, albums and the people in it. To the print team it is a rectangle of pixels with a size that determines how large it can be printed. To billing it does not exist: there are invoices with line items. Each answer is right, and a single Photo class that tried to serve all three would be right for none.

A bounded context is a part of a system within which one model applies and every term has one meaning. Each context has its own model, even of things that share a name.

Contexts exchange as little as they can: identifiers and events, in an agreed format. Where one context must consume another’s model, it translates at the edge into its own terms, with an adapter (). When the other model is one you do not control, such as a payment provider’s, that translating layer is called an anticorruption layer, because its job is to stop foreign concepts leaking inward.

Bounded contexts are the strongest available guide to where services should be divided (). They are a way of dividing the model, not the deployment. One well-structured application can hold several contexts as modules, and for most teams that is the right place to start.

When not to

Everything in this chapter costs something: more types, an indirection between the handler and the data, mapping code between the model and its tables. It pays where there are real rules to protect. Much software has few.

The work is mostlyA fitting design
Storing and showing records, with validation of single fieldsPlain records and a thin layer over the database. A user’s profile settings need no aggregate
A sequence of steps with a few conditionsA function for each operation, sometimes called a transaction script
Rules that span several pieces of data, states with restricted moves, money, quotas, bookingsA domain model as described here
Reports and searches over many recordsQueries written directly against the database, bypassing the model. Reads do not need aggregates ()

The value objects are the exception to this weighing. A Money type or a branded identifier costs a few lines and removes whole classes of mistake in any codebase, simple or not.

In an interview. A low-level design round is domain modeling against the clock. Underline the nouns and verbs in the prompt. Say which nouns are entities and which are values, and state two or three invariants out loud before drawing anything: “a spot holds at most one vehicle”, “a seat cannot be sold twice”. Then put each invariant inside exactly one class that can enforce it. That last step, naming the rule and its owner, is what distinguishes a design from a list of classes.

Key points

  • A domain model exists to protect invariants. Ask of every rule where it lives and what prevents code from going around it.
  • Value objects are immutable, compared by contents and valid from creation. Money is a whole number of minor units with a currency, never a float.
  • Entities have identity and a lifecycle, and change only through operations named after what the business does.
  • An aggregate is a consistency boundary with one root. Load it whole, change it through the root, save it in one transaction.
  • Refer to other aggregates by identifier, and keep each aggregate as small as its true invariants allow.
  • A repository stores and returns whole aggregates behind a collection-like interface, and a version check turns concurrent changes into visible conflicts.
  • Application services sequence: load, tell, save, publish. They hold no rules.
  • A bounded context is where one model and one vocabulary apply. The same real thing is modeled differently in each.
  • Use the full approach where there are rules to protect, and plain records where there are not.

Check yourself

Classify each as an entity or a value object in a ride-hailing system, and say why: a trip, a pickup location, a driver, a fare.

A trip and a driver are entities: each is tracked individually over time and remains the same trip or driver as its details change. A pickup location and a fare are value objects: a pair of coordinates and an amount with a currency, defined entirely by their contents, immutable, and interchangeable with any equal value.

A bill of 100.00 is split among three people with amount / 3 rounded to two places. What goes wrong, and how does the Money class in this chapter avoid it?

Each share is 33.33, and three of them make 99.99. A cent has vanished. split works in whole cents: it gives each share the floor of the division and hands the leftover cents, one each, to the first shares, giving 33.34, 33.33 and 33.33. The shares always add up to the original amount.

Why does an order line hold a PhotoId and a copy of the unit price, where it could hold a reference to the Photo and look the price up when needed?

The photo is a different aggregate. Holding the object would mean loading it with every order and risk saving changes to it by accident. An identifier keeps the boundary. The price is copied because an order records what was agreed: if it were looked up later, a change to the price list would silently alter past orders.

A team models Album as an aggregate containing every Photo, to enforce “an album holds at most 10,000 photos”. What will they observe in production, and what would you suggest?

Every upload loads and saves the whole album, which is slow, and simultaneous uploads to one album conflict and retry. Make each photo its own aggregate holding the album’s identifier. Enforce the limit with a counter on the album updated atomically, or check it with a query and accept that it may be exceeded by a few during a burst, since nothing bad follows from 10,003 photos.

Two requests load the same order at version 4. The first adds a line and saves. The second cancels the order and saves. What happens with the repository in this chapter, and why is that better than letting the second save go through?

The second save is refused with a conflict, because the stored version is now 5 and it expected 4. Had it gone through, it would have written its copy of the order, made before the line was added, over the first request’s change. On retry, the cancel request is applied to the current order, and the order’s own rules decide whether it is still allowed.

Where should each of these go: checking that an email address is well formed, checking that an order has at least one line before placing, sending the confirmation email, and deciding which of two warehouses ships the order?

The email format belongs in a value object, checked when the value is created. The non-empty rule belongs in the Order aggregate’s place method. Sending the email is a reaction to the OrderPlaced event, outside the model. Choosing a warehouse involves orders and warehouses and belongs to neither, so it is a domain service.

The word “account” means a login to the identity team, a ledger to the finance team and a company to the sales team. What does that tell you, and what should the code do about it?

There are three bounded contexts. Each should have its own model, ideally with a more precise name such as Login, LedgerAccount and ClientCompany, and they should refer to each other by identifier and translate at their edges. One shared Account class would accumulate the fields and rules of all three and belong to nobody.
