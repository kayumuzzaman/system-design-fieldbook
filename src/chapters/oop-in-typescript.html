Inside one box

The photo app’s high-level design has a box labeled “photos service”. Someone has to write it. The first version will be a few hundred lines and will work. Two years later it is forty thousand lines, six people change it every week, and the question that decides whether they can do so safely is one the box never showed: how is the code inside it divided up?

Object-oriented design is one answer to that question, and the most common one. It divides a program into objects. An object is a small bundle of data together with the functions that are allowed to work on that data. A class is the description from which objects of one kind are made: it names the data each object holds and the operations each object offers. Album is a class. The album called “Lisbon” that Ana created on Tuesday is an object.

Four ideas do nearly all the work, and this chapter takes them in turn.

IdeaIn one sentenceWhat it buys
EncapsulationAn object’s data can be changed only through its own operationsRules about the data are enforced in one place
AbstractionCallers depend on what something does, not on howThe “how” can change without the callers changing
PolymorphismOne call does different things for different kinds of objectNew kinds can be added without editing the callers
CompositionObjects are built by combining other objectsBehavior can be mixed and reused without deep class hierarchies

TypeScript does not force this style. A great deal of good TypeScript is plain data and functions, and this chapter says where that is the better choice. Classes earn their place when there is state with rules attached to it.

Encapsulation

An album in the photo app has two rules. It holds at most a thousand photos. And if it has any photos, exactly one of them is its cover. A rule like this, which must be true whenever anyone looks, is called an invariant.

Here is an album as a plain record with open fields, followed by one that protects its invariants.

export type Photo = { readonly id: string; readonly bytes: number };

// Before: every field is open. Any caller can leave the album in a state that makes no sense.
export class OpenAlbum {
  photos: Photo[] = [];
  coverId: string | null = null;
}

// After: the fields are private, and every change goes through a method that keeps the rules.
export class Album {
  private readonly photos = new Map();
  private coverId: string | null = null;
  readonly limit: number;

  constructor(limit = 1000) {
    this.limit = limit;
  }

  add(photo: Photo): void {
    if (this.photos.size >= this.limit) throw new Error(`an album holds at most ${this.limit} photos`);
    this.photos.set(photo.id, photo);
    this.coverId ??= photo.id; // rule: an album with photos always has a cover
  }

  remove(id: string): void {
    if (!this.photos.delete(id)) return;
    if (this.coverId === id) this.coverId = this.photos.keys().next().value ?? null; // rule: the cover is one of the photos
  }

  setCover(id: string): void {
    if (!this.photos.has(id)) throw new Error("the cover must be a photo in the album");
    this.coverId = id;
  }

  get cover(): Photo | null {
    return this.coverId === null ? null : this.photos.get(this.coverId) ?? null;
  }

  get size(): number {
    return this.photos.size;
  }

  list(): readonly Photo[] {
    return [...this.photos.values()]; // a copy: callers get the photos, not the album's own collection
  }
}

The first class cannot keep its rules, because it has no say in what happens to its fields. In a test, a caller emptied the list of photos with one assignment and the cover went on pointing at a photo that no longer existed. Nothing failed at that moment.

Encapsulation is the practice of keeping an object’s data private and allowing changes only through operations that the object itself defines, so that the object can guarantee its own invariants. Four habits in the second class are worth copying.

  • Fields are private by default. Make something public only when a caller needs it, and then prefer a method or a read-only getter to the field itself.
  • Every method leaves the object valid. remove does two things because the rule connects two fields. A caller cannot do one and forget the other.
  • Bad requests fail immediately. setCover throws at the line that made the mistake, not three screens later.
  • What goes out is a copy or a read-only view. list returns a new array. Handing out the internal collection would give every caller a back door.

Two kinds of private

TypeScript offers two ways to hide a field, and they differ in when the hiding is enforced.

private secret#hidden
Enforced byThe type checker, before the program runsThe JavaScript engine, while it runs
At run timeAn ordinary property. In a test it appeared in Object.keys and in JSON.stringify, and could be read by code that sidestepped the typesUnreachable from outside the class. It appeared in neither
Use it whenThe goal is a clear design, which is nearly always. This book uses itThe value must not leak even to code that ignores the types, such as a secret key

Add readonly to any field that is set once in the constructor and never again. A field that cannot change is a field nobody has to reason about.

Abstraction and interfaces

The photos service has to keep image files somewhere. On a developer’s laptop that is a folder. In tests it is memory. In production it is object storage (). The code that handles an upload should not care which.

An interface in TypeScript is a named description of what an object can do: its methods, their parameters and what they return, with no code. Abstraction is designing so that callers depend on such a description and not on any particular class that fulfills it.

// What any place that keeps photo files must be able to do. Nothing here says how.
export interface PhotoStore {
  save(id: string, bytes: Uint8Array): Promise;
  load(id: string): Promise;
  delete(id: string): Promise;
}

export class MemoryStore implements PhotoStore {
  private readonly files = new Map();

  async save(id: string, bytes: Uint8Array): Promise {
    this.files.set(id, bytes);
  }
  async load(id: string): Promise {
    return this.files.get(id) ?? null;
  }
  async delete(id: string): Promise {
    this.files.delete(id);
  }
}

// The library is written against the interface. It cannot tell which store it was given.
export class Library {
  private readonly store: PhotoStore;
  private readonly maxBytes: number;

  constructor(store: PhotoStore, maxBytes = 20_000_000) {
    this.store = store;
    this.maxBytes = maxBytes;
  }

  async upload(id: string, bytes: Uint8Array): Promise {
    if (bytes.length === 0) throw new Error("the file is empty");
    if (bytes.length > this.maxBytes) throw new Error("the file is too large");
    await this.store.save(id, bytes);
  }

  async download(id: string): Promise {
    const bytes = await this.store.load(id);
    if (bytes === null) throw new Error(`no photo ${id}`);
    return bytes;
  }
}

Library was tested against three stores: the one above, a DiskStore that writes files into a folder, and a bare object with three functions. It behaved identically with each, and it could not have told them apart. That is the point. The decision “where do files live?” has been moved out of the code that uses files and into the one line that constructs the library.

The third store shows something particular to TypeScript. In Java or C#, a class is a PhotoStore only if it says implements PhotoStore. TypeScript uses structural typing: a value has a type if it has the right shape, whatever it is called and wherever it came from. The word implements is optional. Write it anyway on classes, because it makes the compiler report a missing method at the class, where the mistake is, and not at some distant call.

ToolWhat it isReach for it when
interfaceA shape with no code. A class may implement severalYou are describing what a collaborator must be able to do
typeA name for any type, including unions such as "email" | "push"You are describing data, or one of several alternatives
abstract classA class with some methods left unwritten. A class may extend only oneSeveral implementations share real code as well as a shape

Keep interfaces small and name them for the role they play to the caller. PhotoStore has three methods because Library needs three. An interface that lists everything a storage product can do is a description of the product, not of what this code needs from it.

Polymorphism

When Chi shares an album, the people she shares it with are told, by email and by a push message to their phones. The obvious first version is a function that checks which channel it was asked for.

export type User = { name: string; email: string; deviceToken?: string };
type Sent = (line: string) => void; // stands in for a mail server or a push service

// Before: one function that knows every channel. Each new channel means editing it again.
export function notifyBefore(channel: "email" | "push", to: User, text: string, sent: Sent): void {
  if (channel === "email") {
    sent(`email to ${to.email}: ${text}`);
  } else if (channel === "push") {
    if (to.deviceToken) sent(`push to ${to.deviceToken}: ${text.slice(0, 40)}`);
  }
}

// After: one interface, one class for each channel.
export interface Notifier {
  send(to: User, text: string): void;
}

export class EmailNotifier implements Notifier {
  private readonly sent: Sent;
  constructor(sent: Sent) {
    this.sent = sent;
  }
  send(to: User, text: string): void {
    this.sent(`email to ${to.email}: ${text}`);
  }
}

export class PushNotifier implements Notifier {
  private readonly sent: Sent;
  constructor(sent: Sent) {
    this.sent = sent;
  }
  send(to: User, text: string): void {
    if (to.deviceToken) this.sent(`push to ${to.deviceToken}: ${text.slice(0, 40)}`); // a push message is short
  }
}

// The caller holds a list of notifiers and treats them all alike.
export class NotificationCenter {
  private readonly channels: Notifier[];
  constructor(channels: Notifier[]) {
    this.channels = channels;
  }
  announce(to: User, text: string): void {
    for (const channel of this.channels) channel.send(to, text); // which send runs is decided here, at run time
  }
}

Polymorphism is the ability of one call, written once, to run different code depending on the kind of object it is made on. NotificationCenter contains a single call to send. Which send runs is decided by the object, while the program is running.

The two versions produced the same three messages in a test, so nothing was gained in behavior. What changed is where a new channel has to be written. In the first version, adding text messages means opening a function that already works and adding a branch, and doing the same in every other function that switches on the channel. In the second it means adding a class.

The other tool: a union of plain data

Classes are not the only way to model “one of several kinds”. TypeScript has a second, which is often better for data that only needs to be read.

// The other way to model "one of several kinds": a union of plain data, and functions that switch on it.
export type AlbumEvent =
  | { kind: "shared"; album: string; by: string }
  | { kind: "comment"; photo: string; by: string; text: string }
  | { kind: "removed"; album: string; by: string };

export function describe(event: AlbumEvent): string {
  switch (event.kind) {
    case "shared":
      return `${event.by} shared the album ${event.album} with you`;
    case "comment":
      return `${event.by} commented: ${event.text}`;
    case "removed":
      return `${event.by} removed you from ${event.album}`;
    default: {
      const missed: never = event; // a compile error here means a kind was added and not handled
      throw new Error(`unhandled event: ${JSON.stringify(missed)}`);
    }
  }
}

A discriminated union is a type made of several object shapes that share one field, here kind, whose value says which shape this is. Inside each case the compiler knows exactly which fields exist. The never line makes the compiler reject the program if a fourth kind is added to the type and this function is not updated.

The two tools are mirror images, and choosing between them is a real design decision.

Classes behind an interfaceA union and functions
Adding a new kindEasy: one new class, nothing else is touchedEvery function that switches on the kind must be updated, and the compiler lists them
Adding a new operationEvery class must gain a methodEasy: one new function
FitsThings that do something and may hold state or resources: stores, notifiers, payment providersThings that are something: events, messages, results, the nodes of a tree

Inheritance

Inheritance lets one class be defined as an extension of another: the new class, the subclass, starts with all the fields and methods of the existing one, the base class, and may add to them or replace some. In TypeScript the keyword is extends, a replaced method is marked override, and the base class’s version is reached through super.

It looks like the natural way to reuse code. It is also the feature of object-oriented languages that causes the most trouble, and one small example shows why. A Bag collects items. The task is to make a bag that also counts how many items were ever added to it.

export class Bag {
  protected readonly items: T[] = [];

  add(item: T): void {
    this.items.push(item);
  }
  addAll(items: T[]): void {
    for (const item of items) this.add(item); // a detail of how Bag works: addAll is built on add
  }
  get size(): number {
    return this.items.length;
  }
}

// By inheritance: a bag that also counts every item ever added.
export class CountingBag extends Bag {
  added = 0;

  override add(item: T): void {
    this.added += 1;
    super.add(item);
  }
  override addAll(items: T[]): void {
    this.added += items.length;
    super.addAll(items); // which calls this.add for each item, so each is counted a second time
  }
}

// By composition: an object that has a bag, and forwards to it.
export class CountedBag {
  added = 0;
  private readonly bag = new Bag();

  add(item: T): void {
    this.added += 1;
    this.bag.add(item);
  }
  addAll(items: T[]): void {
    this.added += items.length;
    this.bag.addAll(items); // whatever the bag does inside stays inside
  }
  get size(): number {
    return this.bag.size;
  }
}

Both counting classes look correct. After addAll(["a", "b", "c"]), the inherited one reported six items added to a bag that held three. The composed one reported three.

This is the fragile base class problem: a subclass depends on how its base class is implemented, not only on what the base class promises, so a change inside the base class, or a detail of it that nobody documented, can break a subclass that was never touched. The remedy for the example could be to stop counting in addAll. That fixes it until someone rewrites Bag.addAll to push the items directly, at which point the count is wrong in the other direction.

The underlying cause is that inheritance is a closer relationship than it appears. A caller of a class sees its public methods. A subclass is tangled up with the base class’s internal calls as well.

Inheritance is reasonable whenIt is a warning sign when
The subclass is a special kind of the base class, and can be used anywhere the base class can ( makes this precise)The reason is “that class already has a method I need”
The base class was written to be extended, and says which methods may be overridden and what they may assumeThe base class comes from someone else’s library and says nothing about extension
The hierarchy is shallow: one level, occasionally twoYou need to trace four classes to find out what a call does
A framework requires itThe same variation is being added along two or more axes at once

Composition over inheritance

Composition means building an object out of other objects that it holds and calls, instead of out of a base class that it extends. CountedBag does not claim to be a kind of bag. It has a bag, and passes work to it. It sees only the bag’s public methods, so nothing the bag does internally can reach back into it.

The advice “prefer composition to inheritance” comes from the book that named the design patterns, and three decades of practice have only strengthened it. Its second advantage appears when behavior varies in more than one way at once. Suppose notifications must sometimes be retried when sending fails, and sometimes be logged, for either channel.

With inheritance each combination is its own class, written in advance. With composition there is one small class for each idea, and they are combined when the objects are created. The calculator shows how quickly the two diverge.

3 kinds and 2 optional behaviors give 12 combinations. With a subclass for each, that is 12 classes, and one more behavior doubles it to 24. With one class for each kind and one wrapper for each behavior it is 5, and one more behavior makes 6.

The wrapper classes on the right of have a name, the decorator pattern, and builds them. For now the shape is what matters: an object that implements an interface and holds another object of the same interface.

Composition has a price. There are more objects, someone has to assemble them, and a call passes through several small classes instead of one. For a design that varies along a single axis and always will, a base class and two subclasses is less code and easier to read. The rule is a default, not a ban.

How objects relate

Once a program is a set of objects, its design is mostly the set of connections between them. Four kinds are worth telling apart, because they differ in how tightly they bind.

RelationshipIn codeExampleHow tight
UsesReceives it as a parameter, calls it, and lets goA function that is passed a User to read its email addressLoosest
HasKeeps a reference in a field. The other object exists independentlyNotificationCenter has notifiers. Library has a storeModerate
OwnsCreates and controls it. The part has no life outside the wholeAn Album owns its internal map of photosTight, and contained
Is a kind ofextendsCountingBag is a kind of BagTightest

Two words describe the quality of the whole arrangement, and every principle and pattern in the next five chapters is a technique for improving one of them.

  • Coupling is how much one part of a program must know about another to work. The less each part knows, the more freely either can change. Library knows three method names about its store, which is low coupling. A class that reaches into another’s fields is as coupled as it can be.
  • Cohesion is how closely the things inside one part belong together. Album is cohesive: every field and method concerns one album’s photos and cover. A class called Utils with forty unrelated functions is not.

The aim is low coupling between classes and high cohesion within each. A quick test for both: can you say what a class is for in one sentence, without the word “and”?

Key points

  • Low-level design decides which objects exist, what each knows and does, and which others it may talk to.
  • Encapsulation keeps data private so that the object can enforce its own rules in one place. Every method leaves the object valid.
  • TypeScript’s private is checked before the program runs and is an ordinary property afterward. #field is private at run time.
  • Depend on small interfaces named for a role. TypeScript matches types by shape, so anything with the right methods fits.
  • Polymorphism lets callers stop asking what kind something is. Use classes behind an interface for things that act, and discriminated unions for data.
  • Inheritance ties a subclass to the internals of its base class. Keep hierarchies shallow and extend only classes designed for it.
  • Prefer composition: hold other objects and call their public methods. It keeps combinations from multiplying.
  • Judge any design by coupling between parts, which should be low, and cohesion within each, which should be high.

Check yourself

A Cart class has a public items array and a public total number. What can go wrong, and how would you redesign it?

The total is supposed to equal the sum of the items, and nothing enforces it: any caller can push an item without updating the total, or set the total directly. Make both private, offer add and remove methods that update them together, or better, compute the total from the items in a getter so that it cannot disagree. Return a copy of the items from any method that exposes them.

A field is declared private apiKey: string. A colleague says it is therefore safe from other code in the process. Is that right?

No. The private keyword is enforced by the type checker only. At run time the field is an ordinary property: it shows up in Object.keys and JSON.stringify, and any code that bypasses the types can read it. A #apiKey field is private at run time. The keyword is still the right default for expressing a design, because its purpose is to guide the people writing the code.

Why can an object literal with save, load and delete functions be passed where a PhotoStore is expected, although it never mentions the interface?

TypeScript uses structural typing. A value is acceptable if it has the members the type requires, with compatible types. Names and declarations of intent do not enter into it. This is why test doubles are easy to write in TypeScript, and it is also why writing implements on a class is worthwhile: it asks the compiler to check the shape at the class itself.

You are modeling the events a photo can produce: uploaded, shared, commented, deleted. New operations on events are added often (formatting, filtering, counting), and new kinds rarely. Classes or a discriminated union?

A discriminated union. Each new operation is one new function with a switch over the kinds, and nothing else changes. With classes, each new operation would mean adding a method to every class. When a kind is eventually added, the never check makes the compiler point at every function that must handle it.

CountingBag overrides add and addAll to count items, and reports six after three items are added with addAll. Trace why.

The subclass’s addAll adds three to the counter and calls super.addAll. The base class implements addAll by calling this.add for each item. Because the object is a CountingBag, this.add is the overridden method, which adds one to the counter each time before storing the item. Three plus three is six. The subclass relied on an undocumented detail of the base class.

Notifications come in 3 channels, and each can optionally be retried, logged and rate-limited. How many classes with a subclass for each combination, and how many with composition?

Three optional behaviors give 23 = 8 combinations for each channel, so 24 classes by inheritance. With composition there are three channel classes and three wrappers, six in all. A fourth behavior doubles the first number to 48 and raises the second to 7.

What is the difference between coupling and cohesion, and what does a class named PhotoManager with methods for uploading, resizing, emailing and billing suggest about each?

Coupling is how much a part must know about other parts. Cohesion is how well the contents of one part belong together. That class has low cohesion: four unrelated jobs under one name. It will also be highly coupled, because storage, image processing, mail and payments all meet inside it, and a change in any of them is a change to this class.
