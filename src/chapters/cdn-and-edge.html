Distance is the problem

showed that a request to a server on another continent spends most of its time in transit. A round trip between Sydney and Virginia takes about 200 ms, and no amount of server tuning changes that, because it is set by the length of the cable and the speed of light in glass. A new HTTPS connection needs several round trips before the first byte of the response arrives.

A content delivery network (CDN) is a fleet of servers placed in hundreds of locations around the world, operated as a service, that sits between your users and your own servers. Each location is called a point of presence (PoP) or edge location. Your own servers, where the content really lives, are the origin. The CDN is a reverse proxy () with two unusual properties: it is close to nearly everyone, and it remembers responses.

A CDN therefore gives you three things at once:

  • Lower latency, because the response travels a short distance.
  • Lower origin load, because most requests never reach your servers. This is often the larger benefit. A site that could not survive its own traffic can survive it when the origin sees one request in twenty.
  • Absorption, because a network sized for a large share of the world’s traffic can take a flood, accidental or malicious, that would overwhelm any single site.

The scale is worth knowing. As of October 2026, Cloudflare lists data centers in 348 cities, and Amazon CloudFront lists more than 750 points of presence in over 100 cities. Cloudflare states that 95% of the world’s internet users are within 50 ms of one of its locations.

How a request finds a nearby edge

The user types your domain name, and somehow arrives at a server in their own city. Two mechanisms from earlier chapters do this, and CDNs use one or both.

  • Anycast. Every edge location announces the same IP address, and the internet’s routing delivers each packet to the nearest one by network distance (). Failover is automatic: a location that goes down stops announcing, and its traffic flows to the next nearest.
  • DNS steering. The CDN’s name servers answer each lookup with the address of an edge location chosen for that user, by geography or by measured latency (). This allows finer control, such as avoiding a location that is near capacity, and it reacts only as fast as cached DNS answers expire.

You connect your site to a CDN by pointing your domain’s DNS record at it, and telling the CDN where your origin is. From then on the CDN holds your TLS certificate and terminates your users’ connections (). That last point deserves a moment of thought. The CDN sees all of your traffic in the clear, and its availability becomes part of yours.

The cache key

When a request arrives, the edge must decide whether it already holds a suitable response. It does so by computing a cache key from the request and looking that up. Two requests with the same key receive the same stored response. Two requests with different keys are cached separately. Everything about a CDN’s efficiency and correctness follows from what goes into that key.

The default key is usually the host and the full URL including the query string. That default goes wrong in both directions.

Too much in the key fragments the cache. If a tracking parameter such as utm_source is part of the key, every email campaign creates a new copy of every page, and each copy starts cold. The same happens when parameters arrive in different orders, or when a response varies on a header with thousands of possible values, as User-Agent has. The hit ratio falls and the origin does the work the CDN was meant to save. The fix is to list the parameters and headers that really change the response and leave everything else out.

Too little in the key is worse, because it serves the wrong content. If the response depends on something that is not in the key, one user receives a response built for another. Leave Accept-Language out when the page is translated, and a visitor in Paris gets the German page cached a moment earlier. Leave out the cookie on a page that shows account details, and you have published one user’s data to the next visitor.

The Vary response header is the standard way for an origin to declare which request headers matter (). CDNs also let you define the key in their own configuration, which gives more control, such as varying on the user’s country as detected by the edge instead of on a raw header.

Common mistake. Caching a personalized response is the most serious error you can make with a CDN. Any response that depends on who is asking must either be marked Cache-Control: private or no-store, or have the distinguishing value in its cache key. Treat responses that set cookies as uncacheable by default. An attack called web cache deception looks for exactly this gap: it tricks the CDN into treating a private page as a static file, for example by requesting /account/x.css, and then reads the victim’s cached page.

Freshness and invalidation

A cached copy is a snapshot, and the origin may have changed since it was taken. The rules for how long a copy can be used are the HTTP caching rules from , with a few additions aimed at shared caches.

DirectiveMeaning for a CDN
max-age=60Any cache, including the browser, may reuse this for 60 seconds
s-maxage=600Shared caches such as a CDN may reuse it for 600 seconds, overriding max-age for them
privateOnly the user’s own browser may store it. A CDN must not.
no-storeNobody may store it
stale-while-revalidate=30For 30 seconds after expiry, serve the old copy at once and refresh it in the background
stale-if-error=86400If the origin is failing, keep serving the old copy for up to a day
immutableThis will never change, so do not even revalidate it

A useful header for a page that changes occasionally combines several of these:

Cache-Control: public, max-age=0, s-maxage=600, stale-while-revalidate=30, stale-if-error=86400

Read it as four instructions. Browsers must check back every time, so a user never sees a copy older than the CDN’s. The CDN may serve its copy for ten minutes. When that expires, the next user is not made to wait, because the CDN serves the old copy and fetches a new one behind the scenes. If the origin is down, the CDN keeps the site up with what it has for a day. That last directive turns the CDN into a cushion against origin outages, and it costs nothing to add.

The separation of browser lifetime from CDN lifetime matters because of what you can take back. You can purge a CDN. You cannot purge a browser. A long max-age on something you may need to change is a promise you cannot withdraw.

Changing content before it expires

There are three ways to get new content to users, and they suit different kinds of content.

MethodHow it worksUse it for
Versioned URLsPut a hash of the content in the file name, such as app.3f9a1c.js. A new version has a new URL, so nothing is ever invalidated. Cache it for a year and mark it immutable.Scripts, style sheets, fonts, images: anything referenced from a page you control
Short lifetimesLet copies expire quickly and accept that users may see content up to that oldHTML pages and API responses where a minute of staleness is acceptable
PurgingTell the CDN to discard copies now, by URL, by prefix, or by a tag you attached to the responseContent at fixed URLs that must update promptly: a corrected article, a product whose price changed

Versioned URLs are the best of the three wherever they apply, because they remove the question. Build tools generate the hashed names automatically. The HTML that refers to them is then the only thing with a short lifetime.

Purging by tag is the practical tool for the rest. The origin labels each response with the things it was built from, for example product-871 and category-shoes, in a header the CDN understands. When product 871 changes, one purge of that tag removes every page that included it, without your having to know their URLs. Purges take from under a second to a few minutes to reach every location, depending on the provider, so check that figure before designing around it.

The number that matters: cache hit ratio

The cache hit ratio is the share of requests answered from the edge without contacting the origin. It is the main measure of whether your CDN is doing its job, and its effect on the origin is not linear in the way people expect.

The origin serves 10% of requests. From here, one more point of hit ratio removes 10% of the origin’s load. That is why the last few points matter most.

Going from 90% to 95% sounds like a small improvement, and it halves the traffic your servers see. Going from 95% to 99% cuts it by a further 80%. The origin’s load depends on the miss ratio, and near the top each point of hit ratio is a large fraction of what remains. This is why CDN tuning concentrates on the last few percent.

The usual causes of a poor hit ratio, in rough order of how often they turn out to be the problem:

  1. A fragmented cache key: tracking parameters, unordered query strings, or an unnecessary Vary.
  2. Responses that forbid caching: a framework that adds Cache-Control: private or sets a cookie on every response, including static ones.
  3. Lifetimes that are too short for how rarely the content changes.
  4. A long tail of rarely requested objects. An item requested once a day in each of 300 locations is never in cache when it is needed. The next section addresses this.
Two hit ratiosCDNs report the ratio by requests and by bytes. They can differ widely. A site whose small files are cached and whose large videos are not may show 95% by requests and 40% by bytes. Requests drive origin CPU, and bytes drive the bandwidth bill, so look at the one that matches the cost you are trying to reduce.

Tiered caching and origin shields

Each edge location has its own cache. With 300 locations, a new or expired object can be requested from the origin 300 times, once by each location, before the whole network holds it. For popular objects that cost is spread over millions of hits. For the long tail it dominates.

Tiered caching adds a second layer. Edge locations that miss ask a regional cache before going to the origin. An origin shield is the extreme form: one designated location, chosen close to the origin, through which all origin traffic passes. The trade is one extra hop on a miss in exchange for far fewer misses reaching you.

Two related protections belong here. Request collapsing means that when a thousand users request the same uncached object in the same instant, the edge sends one request to the origin and gives its response to all of them. Without it, the expiry of a popular object sends a burst to the origin known as a cache stampede. covers stampedes in application caches, where you have to build the protection yourself.

Speeding up what cannot be cached

A personalized API response has to come from the origin every time. A CDN still makes it faster, for reasons that have nothing to do with caching.

The gain comes from where the connection setup happens. Take the user in Sydney and the origin in Virginia again, with a round trip of 200 ms between them and 10 ms from the user to the nearest edge.

Direct to the originThrough the edge
TCP and TLS handshakes2 round trips of 200 ms: 400 ms2 round trips of 10 ms: 20 ms
Request and response1 round trip of 200 ms: 200 ms10 ms to the edge, plus 200 ms from edge to origin over a connection that is already open: 210 ms
Network time to first byte600 ms230 ms

The edge keeps warm connections to the origin, so the expensive handshakes are done over the short hop only. The long hop is crossed once instead of three times. On top of that, large CDNs carry the edge-to-origin leg over their own backbone and choose routes by measured performance instead of accepting whatever path BGP offers. They also speak the newest protocols to the user, such as HTTP/3, whatever your origin supports. The figures in the table are for a first request on a new connection. Later requests on the same connection save less, since the handshake is already paid for.

The edge can also reduce the bytes: compressing text with Brotli or Zstandard, and converting and resizing images to suit each device. Images are usually the heaviest part of a page, and this is often the largest single saving available.

Security at the edge

Because a CDN stands in front of the origin and has enormous capacity, it has become the standard place to stop attacks.

  • DDoS absorption. A distributed denial-of-service attack tries to exhaust a target with traffic from many sources. The attacks are far larger than any single company’s connection. The largest reported so far, mitigated by Cloudflare in late 2025, peaked at 31.4 terabits per second, and Cloudflare counted 805 attacks above 1 terabit per second in the second quarter of 2026, against 130 in the first. Anycast spreads such a flood across hundreds of locations, each of which drops its share.
  • A web application firewall (WAF) inspects requests for known attack patterns before they reach your code.
  • Rate limiting and bot management at the edge stop abusive clients without spending origin capacity on them.
  • TLS is handled with modern settings and automatically renewed certificates.

All of this protects the origin only if the origin cannot be reached any other way. If an attacker finds your origin’s real IP address, from an old DNS record or a certificate log, they can send traffic to it directly and bypass everything. Close that path: accept connections only from the CDN’s address ranges, or better, require the CDN to present a client certificate or a secret header that the origin verifies.

The CDN can also serve private content without becoming an open door. A signed URL contains an expiry time and a signature computed with a key the application shares with the CDN. The application hands a signed URL to a user who is allowed to see a file, and the edge checks the signature on each request without calling the origin. This is how paid video and private downloads are delivered from a cache. returns to it.

Running code at the edge

If the edge can cache and filter, the next step is to let it run your code. Edge computing, in the sense used by CDNs, means small programs that execute in the edge location on each request, before or instead of the origin.

To start in a millisecond in hundreds of locations, edge platforms cannot use ordinary containers. Two designs are common:

  • Isolates. Many customers’ code runs inside one process, separated by the same sandbox a browser uses to separate tabs. Start-up takes a few milliseconds or less. The price is a restricted environment: a web-standard JavaScript API instead of the full Node runtime, and tight limits on CPU time and memory. Cloudflare Workers is the best-known example.
  • WebAssembly. Code compiled from Rust, Go and other languages runs in a lightweight sandbox with similar start-up times. Fastly Compute works this way.

Some providers also offer fuller runtimes at fewer, regional locations, such as AWS Lambda@Edge, alongside a very restricted and very fast option for simple header and URL changes, such as CloudFront Functions.

What suits the edge is work that needs the request and little else:

  • Routing and rewriting: redirects, choosing an origin, gradual rollouts, A/B test assignment.
  • Checks that reject early: validating a signed token, blocking by country, rate limiting.
  • Shaping responses: adding security headers, choosing an image format, assembling a page from cached fragments.
  • Personalizing cached content: serving a shared cached page and inserting a small per-user part.
export default {
  async fetch(request: Request): Promise {
    const url = new URL(request.url);

    // 1. Reject early. No origin capacity is spent on blocked requests.
    if (url.pathname.startsWith("/admin")) {
      return new Response("Not found", { status: 404 });
    }

    // 2. Normalize, so that links from marketing emails share one cached copy.
    for (const name of [...url.searchParams.keys()]) {
      if (name.startsWith("utm_")) url.searchParams.delete(name);
    }
    url.searchParams.sort();

    // 3. Fetch through the cache. A hit never reaches the origin.
    const response = await fetch(new Request(url, request));

    // 4. Shape the response on the way out.
    const shaped = new Response(response.body, response);
    shaped.headers.set("Strict-Transport-Security", "max-age=31536000");
    return shaped;
  },
};

This uses the standard Request, Response and fetch interfaces in the module style that Cloudflare Workers and several other platforms accept. Details differ between providers.

What does not suit the edge is anything that talks repeatedly to a database in one region. A function in Sydney that makes five queries to a database in Virginia spends five long round trips doing so, and is slower than running the whole request in Virginia, where the queries take a millisecond each. Compute moved to the edge and the data did not.

Providers have responded with data stores that are themselves distributed: key-value stores replicated to every location, and small replicated databases. Nearly all of them are eventually consistent, meaning a write in one place takes time to appear in others. They suit configuration, feature flags, sessions and other data that is read far more than written. They do not suit an order or a payment. explains what that trade means, and compares edge functions with regional ones.

In an interview. When you add a CDN to a design, say three things: what is cached there (static assets, images, video segments, perhaps public API responses), how it stays correct (versioned URLs for assets, short lifetimes or tag purges for the rest), and what the origin’s load becomes as a result. Mentioning the hit ratio and what happens on a miss shows you understand it as a cache and not as a box that makes things fast.

Depending on a CDN

A CDN is in front of everything. When it fails, your site is down even if every server you own is healthy. CDNs are engineered to a very high standard and their outages are rare. They are also large when they happen, because a CDN applies one configuration to the whole world in seconds.

  • Fastly, 8 June 2021. A customer made a valid configuration change that triggered a bug introduced by a software deployment four weeks earlier. Within a minute, 85% of Fastly’s network was returning errors, and a large number of major sites went down together. Fastly detected it within a minute, and 95% of the network was normal again after 49 minutes.
  • Cloudflare, 18 November 2025. An automatically generated configuration file grew past a limit in the proxy software and was distributed everywhere. examines it.

Both were caused by a change that passed validation and was applied globally at once. The lesson for your own design is to decide in advance what you will do when the CDN is the thing that is broken.

  • Keep the ability to bypass it. If your DNS is hosted separately from the CDN, you can point traffic straight at the origin in an emergency. That only helps if the origin can take the full load for a while, which is a capacity decision to make deliberately.
  • Use two CDNs if the cost of an outage justifies it. Traffic is split or switched by DNS. The difficulty is that every rule, purge and certificate must then work on both, and features that exist on only one cannot be used. Most teams are better served by one CDN used well.
  • Watch it from outside. Monitor from real locations around the world, since a problem in one region is invisible from your office. Track hit ratio, origin error rate and edge error rate separately, so that you can tell at a glance whether a problem is yours or theirs.
  • Understand the bill. CDN traffic is usually charged by bytes delivered and by request. Delivering through a CDN is often cheaper than serving the same bytes from a cloud provider’s region directly, and a poor hit ratio means paying for both. looks at data transfer costs.

Common mistakes

  • Caching personalized responses. One user’s data is shown to another. Nothing else on this list is as serious.
  • Leaving the origin reachable directly. Attackers bypass the CDN and every protection on it.
  • Long browser lifetimes on content at fixed URLs. You can purge the CDN and you cannot purge browsers.
  • Never checking the hit ratio. A CDN that is configured and missing most requests adds a hop and saves little.
  • Letting tracking parameters into the cache key. Every campaign link is a cold cache.
  • Relying on purge for correctness without knowing its delay. A purge is fast and is not instantaneous.
  • Running database-heavy code at the edge. It is slower than running it beside the database.
  • No plan for a CDN outage. The first time you think about bypassing it should not be during one.

Key points

  • A CDN is a worldwide reverse proxy that caches. It cuts latency by being near users and cuts origin load by answering for you.
  • The cache key decides everything. Too much in it wastes the cache, and too little serves the wrong response to the wrong person.
  • Use versioned URLs for assets, short shared lifetimes with stale-while-revalidate for pages, and purge by tag for the rest.
  • Origin load follows the miss ratio. Moving from 90% to 95% hits halves it.
  • Tiered caches and origin shields stop every edge location from fetching the same object separately.
  • Uncacheable requests still gain from short handshakes, warm origin connections and better routes.
  • The edge is the standard place to absorb DDoS attacks and filter requests, provided the origin accepts traffic only from the CDN.
  • Edge code is close to users and far from data. Use it for routing, checks and response shaping.
  • A CDN is a dependency for your whole site. Decide beforehand what you do when it fails.

Check yourself

Your CDN reports a hit ratio of 96% by requests and 35% by bytes. What is probably happening, and does it matter?

Small objects such as scripts and thumbnails are cached well, and a smaller number of large objects, perhaps videos or downloads, are not. It matters if bandwidth is the cost you care about, because most bytes are still coming from the origin. Find out why the large objects miss: they may be marked uncacheable, requested with unique query strings, or too rarely requested per location, in which case tiered caching helps.

After a marketing email goes out, origin load triples although the pages are cached. What would you check first?

The cache key. Links in the email probably carry tracking parameters such as utm_campaign, and if the full query string is part of the key, each distinct link is a separate entry that starts cold. Exclude those parameters from the key.

Why is Cache-Control: max-age=31536000 safe for app.3f9a1c.js and dangerous for app.js?

The hashed name changes whenever the content changes, so the old URL never needs updating and can be cached forever. A fixed name with a one-year lifetime means browsers that have it will not ask again for a year, and you have no means of telling them to.

A page shows “Hello, Ana” to a user who is not Ana. What went wrong?

A personalized response was stored in a shared cache under a key that did not include the user’s identity, so it was served to the next visitor. The response should have been marked private or no-store, or the personalized part should be fetched separately from an uncached endpoint.

An API response cannot be cached at all. Give two reasons it may still be faster through a CDN.

The TCP and TLS handshakes happen over the short distance to the edge instead of the long distance to the origin, and the edge reuses connections to the origin that are already open. The CDN may also carry the request over a faster route on its own network, and can compress the response.

You move a function that makes four database queries from your region to the edge and it becomes slower. Why?

The database is still in the region. Each query now crosses the long distance from the edge to the region, where before it took about a millisecond. Four long round trips cost more than the single one saved by running near the user.
