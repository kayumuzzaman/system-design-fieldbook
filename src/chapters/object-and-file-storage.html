Three kinds of storage

Everything a system stores ends up on one of three kinds of storage service. They differ in the interface they present, and the interface decides what they are good for.

Block storage is a virtual disk. The operating system puts a file system on it, and a database puts its pages on that. It is what was writing to all along. A cloud block volume lives on the network, survives the failure of the machine it is attached to, and has performance you pay for in operations per second. Fast local disks inside the machine are quicker still and are lost when the machine is.

File storage is a shared folder: many servers see the same directory tree and can read and write the same files. It exists mostly for software that expects a file system. New systems rarely need it, because sharing files between servers is better done with object storage.

Object storage is the subject of the rest of this chapter. It is where the photo app’s photos go, and where the bulk of the world’s data now lives.

Why files do not belong in the database

A database can hold a 4 MB photo in a column, and it is tempting to keep everything in one place. It is a poor trade for anything but small files.

  • It crowds out what the database is for. The buffer pool that should hold rows and indexes fills with image bytes.
  • Everything operational gets slower. Backups, restores, replication and migrations all scale with size, and the files are almost all of the size.
  • It costs more. Database storage is fast block storage, replicated. Object storage costs a small fraction per gigabyte.
  • It forces every download through your servers. Object storage and a CDN can serve files directly.

The standard arrangement is to keep the file in object storage and a row in the database that records its key, size, type, owner and status. The database stays small and answers the questions (“which photos does Ana have?”). The object store holds the bytes.

How object storage works, from the outside

The model is deliberately minimal.

  • A bucket is a named container.
  • An object is a sequence of bytes of any size, plus a little metadata such as its content type.
  • A key is the object’s name within the bucket, such as photos/42/871.jpg.

The operations are few: put an object, get it (or a byte range of it), delete it, and list keys that start with a given prefix. All of them are HTTP requests. Three properties follow from this simplicity and shape every design that uses it.

The namespace is flat. There are no real folders. The slashes in a key are ordinary characters, and “folders” in a console are a display convention built on listing by prefix. Renaming a folder therefore means copying every object under it.

Objects are immutable. There is no way to change bytes in the middle or append to the end. To change an object you upload a complete replacement. This rules out using object storage as a database or a log file, and it is what makes the service so easy to replicate and cache.

There are no transactions and no queries. You cannot update two objects atomically or ask for “all objects larger than 1 MB uploaded by Ana”. That is the database’s job, which is the reason for the metadata row.

One thing has improved in recent years. Amazon S3 originally gave only eventual consistency, where a read just after a write might return the old object. Since late 2020 it has been strongly consistent: a successful write is visible to every read that follows. The other major providers behave the same way. Limits have grown too. The largest single object S3 accepts is about 50 TB (48.8 TiB) since December 2025, ten times the earlier limit.

Durability, and how it is achieved

Object stores advertise striking durability figures. Amazon S3 is designed for 99.999999999% durability of objects over a year, eleven nines. Amazon’s own illustration is that if you store ten million objects, you can expect to lose one every ten thousand years. The figure is a design target derived from modeling, and it describes hardware failure. It is achieved with four techniques working together.

  1. Redundancy across failure domains. Each object is stored on many devices in at least three availability zones, so that losing a disk, a rack or a whole data center loses no data ().
  2. Erasure coding, explained below, which provides that redundancy at much lower cost than full copies.
  3. Checksums. Every piece is stored with a checksum, so silent corruption on a disk is detected when the piece is read.
  4. Continuous repair. Background processes read everything periodically, verify it, and rebuild any piece that is missing or damaged from the others, before enough pieces are lost to matter.

Erasure coding

The simple way to survive disk failures is to keep three copies of everything, which triples the storage bill. Erasure coding gets the same or better protection for far less. An object is cut into k data pieces, and m additional parity pieces are computed from them, in such a way that any k of the k + m pieces are enough to rebuild the object.

The saving is paid for elsewhere. Writing requires computing the parity. Reading normally needs only the data pieces, and a read that hits a failed machine must fetch several other pieces and reconstruct. Repairing one lost piece means reading k others, which for wide codes is a great deal of network traffic. Systems often keep new, frequently read data as plain replicas and convert it to an erasure code as it cools.

Common mistake. Reading eleven nines as “this data cannot be lost”. The figure covers hardware faults. It does not cover a script that deletes the wrong prefix, a compromised credential, an application bug that overwrites objects with garbage, or a closed account. Those are the realistic ways data in object storage is lost. The defenses are different: object versioning, which keeps old versions when an object is overwritten or deleted, retention locks, tightly scoped permissions, and for critical data a copy in another region or account.

Durability is also not availability. The same service that promises eleven nines of durability is designed for 99.99% availability, which allows about an hour a year in which requests may fail. Your data is safe during that hour, and you cannot reach it.

Getting files in

The obvious upload path sends the file from the browser to your API server, which then sends it to object storage. Every byte crosses your servers twice, uploads tie up request handlers for seconds or minutes, and a large upload on a slow connection can hold a server’s memory or disk for a long time. There is a better way.

Direct upload with a signed URL

A presigned URL is an object storage URL with a signature attached that grants permission for one specific operation for a limited time. Your server creates it, which needs no network call, and hands it to the client. The client then talks to object storage directly.

import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

const s3 = new S3Client({ region: "eu-west-1" });
const ALLOWED = ["image/jpeg", "image/png", "image/webp"];

export async function createUploadUrl(userId: number, contentType: string) {
  if (!ALLOWED.includes(contentType)) throw new BadRequest("unsupported type");

  const key = `uploads/${userId}/${crypto.randomUUID()}`;     // the server chooses the key, never the client
  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({ Bucket: "photo-app-uploads", Key: key, ContentType: contentType }),
    { expiresIn: 300 },                                        // seconds
  );

  await db.query(
    "INSERT INTO uploads (key, user_id, status) VALUES ($1, $2, 'pending')", [key, userId]);
  return { key, url };
}

The details in that function are the security of the scheme.

  • The server picks the key. A client allowed to choose could overwrite someone else’s object.
  • The URL is short-lived and for one operation. Anyone who obtains it can use it until it expires.
  • The upload is recorded as pending. Nothing treats the file as real until storage confirms it arrived, and pending rows that never complete can be cleaned up.
  • Uploads land in a separate bucket that is never served to the public.

What arrives is untrusted. A client can claim a file is a JPEG and send anything. After the upload, a background job should check the size and the real type, scan it if your product requires that, produce the resized versions you will actually serve, and only then mark the photo as ready. The trigger is an event that object storage emits when an object is created, delivered to a queue (). This “upload, then process asynchronously” pipeline is one of the most common structures in system design.

Large files: multipart upload

A single request is a poor way to send a 2 GB video. If the connection drops at 95% the whole upload starts again. Multipart upload splits the file into parts that are uploaded separately and assembled by the storage service at the end.

  • Parts upload in parallel, using the full bandwidth available.
  • A failed part is retried alone.
  • An upload can be paused and resumed, since the service remembers which parts it has.

In S3, parts are between 5 MiB and 5 GiB each, with at most 10,000 parts, and AWS suggests multipart once a file passes about 100 MB. One operational detail matters: parts of an upload that is never completed stay in storage, invisible in listings and billed every month, until something removes them. Set a lifecycle rule that aborts incomplete uploads after a few days.

Getting files out

Serving follows the same principle as uploading: keep your application servers out of the path.

  • Public files go through a CDN with the bucket as its origin (). The bucket itself stays private and accepts requests only from the CDN.
  • Private files use signed URLs or signed cookies. The application checks that the user may see the file and returns a URL that works for a few minutes. The check is done once by your code, and the bytes are delivered by storage or the CDN.
  • Large media uses range requests. A video player asks for the bytes it needs, which is how seeking works without downloading the whole file. builds on this.
  • Serve derived versions, not originals. A 12-megapixel original is the wrong thing to send to a phone showing a thumbnail. Generate a few sizes at upload, or transform on demand at the CDN and cache the result.

In production. Publicly readable buckets are a leading cause of data leaks. Providers now block public access by default, and the setting should stay that way. Serve public content through a CDN that authenticates to a private bucket. Check, as a routine, that no bucket holding user data allows anonymous listing or reads.

Storage classes and lifecycle

Most stored data is rarely read. A photo is viewed often in its first week and almost never after a year. Backups and logs may never be read at all. Object stores offer cheaper classes of storage for such data, with a penalty for reading it: a retrieval fee, a delay, or both. The classes of Amazon S3 illustrate the range, and other providers have equivalents.

A lifecycle rule moves objects between classes, or deletes them, by age: originals to infrequent access after 30 days, to archive after a year, logs deleted after 90 days. There is also a class that watches access patterns and moves objects automatically.

The cost of object storage has four parts, and designs go wrong by counting only the first.

  1. Storage, per gigabyte per month. The headline price.
  2. Requests. Each put, get and list has a small price. Billions of tiny objects make this the larger part.
  3. Retrieval from the colder classes, and early deletion before the minimum period.
  4. Data transfer out to the internet, called egress. For a service that serves media this often exceeds everything else. Serving through a CDN usually reduces it, and some providers, Cloudflare R2 for one, do not charge for egress at all.

The colder classes suit large objects that are truly cold. Moving millions of small objects into them can cost more than leaving them, because of per-object fees and minimum billable sizes. returns to cost modeling.

Keys, listing and performance

Object storage scales by spreading keys across many internal partitions, in the manner of . S3 documents at least 3,500 writes and 5,500 reads per second for each key prefix, scaling further as load spreads over more prefixes. For nearly all applications that is far more than enough. Two habits keep you out of trouble.

  • Do not use listing as a query. Listing returns keys in pages of up to a thousand, in key order, and is slow and billed. To find “Ana’s photos”, ask the database, which holds the keys. Treat object storage as something you look up by exact key.
  • Avoid billions of tiny objects. Each object carries overhead in requests, metadata and billing. If you have very many small records, such as events or thumbnails by the hundred million, pack them into larger files and keep an index of what is where.

Remember the latency too. A request to object storage typically takes tens of milliseconds before the first byte arrives. That is excellent for a photo and far too slow for something read on every request, such as a session or a configuration value.

Object storage as a foundation

Because it is cheap, durable and effectively limitless, object storage has become the base layer for other data systems, and the pattern is worth recognizing.

  • Data lakes. Analytical data is stored as column-oriented files, usually Parquet, in object storage, and query engines read them in place. Table formats such as Apache Iceberg add what plain files lack: a consistent list of which files make up a table, so that many writers and readers can work safely. covers this.
  • Databases and logs with separated storage. Many newer systems keep only recent data on local disks and move older data to object storage, or keep all durable state there and treat their servers as replaceable. Cloud data warehouses work this way, and so do the tiered-storage modes of streaming systems.
  • Backups of nearly everything else ().

The design principle behind all three is to put durable state in the one system built to never lose it, and to make everything else stateless enough to replace.

Running your ownMost teams use their cloud provider’s object storage. If you must run one yourself, Ceph is the long-established choice, and smaller S3-compatible servers such as SeaweedFS and Garage exist. MinIO was for years the usual recommendation. Its community edition has been scaled back since 2025, so check its current status before choosing it. Nearly everything speaks the S3 API, which has become the common interface.

When you need block or file storage

Object storage is the default for files. The other two have their places.

  • Block storage for databases and anything that modifies data in place. Choose it by the operations per second and throughput it guarantees. Know which kind you have: a network volume survives the loss of its machine and can be detached and snapshotted, and a local disk is faster and disappears with the machine, which is acceptable only when the data is replicated elsewhere.
  • File storage when software requires a shared file system: older applications, some content management and media tools, and shared working directories for computation. It costs more than object storage and scales less well. If the code is yours to change, change it to use object storage.

In an interview. Any design with images, video or documents should say: “files go to object storage, with a metadata row in the database, uploaded directly with presigned URLs and served through a CDN”. That one sentence removes a class of follow-up questions. If the files are large, add multipart upload. If they are processed, add the event that triggers a worker.

Common mistakes

  • Storing files in the database, or on an application server’s local disk, where the next deployment or scale-in deletes them.
  • Routing uploads and downloads through application servers.
  • Letting clients choose object keys.
  • Trusting an uploaded file’s declared type and size.
  • Public buckets.
  • No versioning or second copy for data that matters, on the strength of the durability figure.
  • Listing a bucket to answer a question the database should answer.
  • Forgetting incomplete multipart uploads, which are billed until removed.
  • Ignoring egress and request costs when estimating the bill.
  • Using object storage for small, hot, frequently changing data.

Key points

  • Block storage is a disk for one machine, file storage is a shared folder, and object storage holds whole objects under keys, reached over HTTP.
  • Keep files in object storage and their metadata in the database.
  • Objects are immutable and the namespace is flat. There are no queries and no transactions.
  • Durability comes from redundancy across zones, erasure coding, checksums and constant repair. It protects against hardware failure and not against deletion or misuse.
  • Erasure coding gives the protection of several copies for a fraction of the space.
  • Upload directly with presigned URLs, use multipart for large files, and validate and process after the upload.
  • Serve through a CDN from a private bucket, with signed URLs for private content.
  • Use colder storage classes and lifecycle rules for data that is rarely read, and count request, retrieval and egress costs as well as storage.

Check yourself

Why can you not append a line to a log file stored as an object?

Objects are immutable. The only write operation replaces the whole object. To add a line you would download the object, add the line and upload all of it again. Logs are therefore written as many separate objects, typically one per time interval, or kept elsewhere and moved to object storage in batches.

A 6 + 3 erasure code and three full copies both protect a 900 MB object. How much raw storage does each use, and how many lost machines can each survive?

Three copies use 2,700 MB and survive the loss of any two. The 6 + 3 code stores nine pieces of 150 MB each, 1,350 MB in total, and survives the loss of any three.

Your provider promises eleven nines of durability. A developer’s script deletes a production prefix. What does the durability figure do for you, and what would have helped?

Nothing. The deletion was a valid request and the service carried it out faithfully. Object versioning would have kept the previous versions recoverable, a retention lock would have refused the deletion, narrower permissions would have prevented the script from having that access, and a copy in another account would have been unaffected.

Why should the server, and not the client, choose the object key for an upload?

If the client chooses, it can pick a key that already belongs to another user’s object and overwrite it, or place files where other parts of the system will trust them. A key generated by the server under a prefix tied to the authenticated user removes that possibility.

A 3 GB upload fails at 90% over a mobile connection. How does multipart upload change what happens next?

Only the part that was in flight is lost. The parts already uploaded are kept by the storage service, so the client retries that one part and continues, instead of starting from the beginning.

You move 400 million thumbnails of 20 KB each to an archive class to save money, and the bill goes up. Why?

Cold classes charge per object for transitions and requests and often bill a minimum size per object that is larger than a thumbnail, so small objects cost more there than in standard storage. Cold classes pay off for large objects that are rarely read.
