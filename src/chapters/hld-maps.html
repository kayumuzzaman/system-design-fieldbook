The problem

The problem. Design a maps and navigation service. Users see a map of the world that they can pan and zoom, search for places and addresses, and ask for driving directions between two points. They get up to three routes with travel times that account for current traffic, then follow one turn by turn, with the arrival time kept up to date and a new route when they leave the planned one.

Three things make it hard, and they pull in different directions. The map is a static data set far too large to send whole, so it is cut into pieces that a content delivery network can cache. Routing is a search over a road graph of continental size, and the plain algorithm settles millions of nodes per query, so the graph is preprocessed to make searches thousands of times cheaper. Then traffic changes the cost of every road all day, which undoes exactly that preprocessing. In the terms of , this is a location problem whose central difficulty is routes over a continent’s roads, timed by live traffic.

The numbers sort the problem (). A continent’s graph fits in one server’s memory, so each routing server holds a whole region and the query rate decides only how many copies there are; fourteen thousand searches a second is modest at a millisecond each and impossible at the two seconds a plain search of Europe takes. Positions are the heavy write path, a job for a partitioned stream (). Tiles are the heavy read path, and as images at every zoom they are far too many to make in advance.

The tile path carries the map’s version, so a tile never changes once published and can be cached for a year at every layer (); a new map build is a new version, not an invalidation. Directions return the typical time beside the time with traffic, which is what lets the app say “12 minutes slower than usual”. Positions travel in batches because sending each one would multiply the request rate by fifteen and wake the phone’s radio every second. A batch can be retried safely: each fix is keyed by trip and time, so a repeat overwrites itself (). The reply to a batch is where the server delivers a new arrival time or a new route.

Step 5: The design

Showing the map. An offline map build cuts the map data (roads, buildings, borders, places) into tiles for every zoom level, written to object storage under a new version. Phones fetch the tiles that cover the screen from the CDN. Nothing on this path runs code per request.

Directions. The gateway sends names to a geocoding service and the two points to a routing server for the region. A routing server holds the region’s graph and its preprocessing in memory, loads the latest speeds every minute, and answers in milliseconds. Roads rarely cross oceans, so a region can be a continent.

Navigation and traffic. Navigating phones send positions to a location service, which answers with the new arrival time and appends the positions to a stream. A traffic service reads the stream, works out which road each car is on and how fast it is moving, and publishes speeds per segment. The same positions, archived, are turned each night into the typical speed of every segment for every quarter hour of the week.

Two loops run at different speeds. The fast one is a single trip: positions go up, an arrival time comes back. The slow one is everyone at once: positions become speeds, speeds become the weights of the graph, and the weights decide the next driver’s route.

Step 6a: Map tiles

The map is drawn on a square. The usual projection, Web Mercator, stretches the globe into a square that stops at about 85 degrees north and south, and at zoom level 0 that square is one picture 256 pixels wide. Each level up doubles the width and height, so at zoom z the world is 256 × 2z pixels across. A map tile is one square of that picture, 256 pixels on a side, named by its zoom level, column and row: tile 14/4823/6160 is column 4,823 and row 6,160 of zoom 14.

A phone screen of 412 by 915 points overlaps at most 15 tiles of 256 pixels, or 6 of 512, by the chapter’s tile code, so moving the map means fetching a handful of small files, the same for every user and cacheable at the edge. At zoom 18 a pixel covers 0.60 m of ground at the equator.

A quadkey is a tile’s name written as one digit from 0 to 3 for each zoom level, the digit saying which quarter of the parent the tile is in. Microsoft’s documentation of the Bing Maps tile system gives the example that the figure follows: column 3, row 5 at zoom 3 is quadkey 213. Every tile’s quadkey starts with its parent’s, so tiles of one area sort together, which makes quadkeys good storage keys, for the same reason as the geohash of .

A tile can hold a picture or the data to draw one. A vector tile holds the features inside its square (road lines, building outlines, labels, each with its attributes) in a compact binary format, and the device draws them. The common format is the Mapbox Vector Tile specification, version 2.1, encoded with protocol buffers and stored as .mvt files.

That difference decides whether tiles can be made in advance. Images down to zoom 18 would be 91.6 billion tiles, about 550 TB at the estimate’s assumptions, mostly ocean and fields nobody zooms into, so image tiles are rendered on the first request and then cached, and only the popular ones exist. Vector tiles stop at about zoom 15 and the device enlarges the last level’s data for closer views, which is why a whole planet fits in one file: the Protomaps project publishes a daily planet build of about 120 GB covering zooms 0 to 15. The calculator in Step 2 shows why the deepest levels dominate: each holds four times the tiles of the one above, so the last level alone is three quarters of everything.

Either way the CDN does the serving (), and a new build is a new version in the URL, never an invalidation. The traffic colors on roads, which change by the minute, go in their own small layer of tiles cached for a minute, drawn over the immutable base map.

Step 6b: Finding the fastest route

For routing, the map becomes a graph. Intersections are nodes; each road segment is an edge in each direction it can be driven, weighted by the time it takes. Forbidden turns are modeled by making segments the nodes, so a turn is an edge that can be left out. The two ends are snapped to the nearest segments first.

Dijkstra’s algorithm finds the fastest route by settling nodes in order of their travel time from the start: it repeatedly takes the unsettled node with the smallest known time, which is then final, and offers each neighbor a time through it. It stops when the destination is settled. The work is the number of nodes settled, the measure used below.

The chapter measures every method on a generated city: a grid of 128 by 128 intersections 250 m apart, moved a little at random, with local streets at 30 km/h, an arterial at 50 km/h on every eighth line, a highway at 100 km/h on every 32nd, and 12% of local streets missing. Times are whole tenths of a second, so that the answers of all the methods can be compared exactly. Over 300 random trips, all five methods below found the same fastest time every time; they differ only in how many nodes they settled.

Dijkstra settled 8,457 nodes on average, half the city. Its search grows as a disc around the start, and a trip across a continent settles most of the continent. A* search adds to each node’s time an estimate of the time still to go, which must never be too high, and so steers the search toward the destination. For travel time the only safe estimate is the straight-line distance at the top speed of any road, as if a highway led straight there, which is far from the truth in town, so A* settled 2,935 nodes: 35% of Dijkstra. A bidirectional search runs Dijkstra from both ends and stops when the two meet; two small discs cover half the area of one large one, and it settled 4,200, or 50%.

All three still grow with the size of the map. What makes routing fast in practice is preprocessing, which uses the fact that road networks have a hierarchy: a long trip leaves the local streets quickly, joins larger roads, and comes back down near the end. A contraction hierarchy makes that hierarchy explicit. Preprocessing removes the nodes one at a time, least important first; whenever removing a node would break a fastest path between two of its neighbors, it adds a shortcut edge between them with the path’s time. A query then searches from both ends using only edges that lead to more important nodes, and the two searches meet near the top.

const order = new NodeHeap(n);
  for (let v = 0; v < n; v += 1) order.push(priority(v), v);
  const rank = new Int32Array(n);
  const upFrom: number[] = [], upTo: number[] = [], upTime: number[] = [], upMid: number[] = [];
  let shortcuts = 0, next = 0;
  while (order.size > 0) {
    const v = order.pop();
    if (contracted[v]) continue;
    const p = priority(v);                       // lazy update: priorities go stale as neighbors go
    if (order.size > 0 && p > order.topKey()) { order.push(p, v); continue; }
    for (const [a, b, w] of needed(v)) {
      addOrLower(a, b, w, v); addOrLower(b, a, w, v);
      shortcuts += 1;
    }
    const vs = nbr[v] as number[], ws = wt[v] as number[], ms = via[v] as number[];
    for (let i = 0; i < vs.length; i += 1) {
      const u = vs[i] as number;
      if (contracted[u]) continue;
      upFrom.push(v); upTo.push(u); upTime.push(ws[i] as number); upMid.push(ms[i] as number);
      deletedNeighbors[u] += 1;
    }
    contracted[v] = 1;
    rank[v] = next++;
  }

Importance here is the number of shortcuts a node’s removal would add minus the edges it removes, a standard choice, and checking whether a shortcut is needed means a small search for another path of the same time that avoids the node. For the test city, preprocessing added 32,885 shortcuts to the 29,145 road segments and took 1.3 seconds in one run. A query then settled 164 nodes on average, 1.9% of Dijkstra, and unpacking each shortcut into the two edges it stands for gave back real roads with exactly the fastest time.

The gap widens with the map. On grids from 4,096 to 65,536 intersections, sixteen times larger, Dijkstra’s work grew fifteen times, from 2,273 to 34,131 nodes, and the hierarchy’s less than three times, from 102 to 295. The published comparison on a real network says the same at continental scale: on the road graph of Western Europe, 18.0 million intersections, a survey by Bast and colleagues reports Dijkstra settling 9.3 million nodes in 2.2 seconds, and a contraction hierarchy settling 280 in 110 microseconds after five minutes of preprocessing.

Step 6c: Live traffic

Traffic data comes from the phones. A position from GPS is off by several meters, and roads run side by side, so the first step is map matching: finding the sequence of road segments a car most likely drove, given a sequence of noisy positions and the shape of the network, usually by weighing each candidate segment’s distance from the fix against how plausible the move from the previous one is. Then the traffic service averages speeds per segment over the last few minutes, a windowed aggregation (). One car might be a van stopping at every door, so a segment needs several before its speed is used; below that, the typical speed stands in. Dropping the first and last minutes of each trip keeps homes out of the data.

Then the speeds have to reach the router, and here preprocessing turns against the design. The shortcuts of a contraction hierarchy carry times computed from the old speeds. The test slowed 3 km of one highway to a sixth of its speed, a jam, and asked the hierarchy built before it for 100 trips past it: it gave a wrong time for all 100, routes through a jam it did not know about. Rebuilding fixes that, but it took 1.3 seconds for 16,384 intersections and 5.5 seconds for 65,536 in one run, and on the order of minutes for a continent. Speeds change everywhere every minute.

Customizable route planning splits the preprocessing in two so that weights can change cheaply. The slow part depends only on the shape of the network: cut the map into cells, and note each cell’s boundary nodes, those with a road leading out. The fast part, customization, uses the current weights: for each cell, compute the fastest time across it between every pair of its boundary nodes, staying inside. A query searches the cells of its start and destination in full and crosses every other cell in one hop between boundary nodes.

const c = this.cell[u] as number;
      const inside = c === cs || c === ct;
      for (let e = g.first[u] as number; e < (g.first[u + 1] as number); e += 1) {
        const v = g.head[e] as number;
        if (inside || this.cell[v] !== c) relax(v, d + (g.time[e] as number)); // roads leaving the cell always count
      }
      if (!inside) {
        const nodes = this.boundary[c] as number[], k = nodes.length, i = this.slot[u] as number;
        const table = this.clique[c] as Float64Array;
        for (let j = 0; j < k; j += 1) if (j !== i) relax(nodes[j] as number, d + (table[i * k + j] as number));
      }
    }

With cells of 16 by 16 intersections, the test city has 64 cells and 147,160 precomputed hops. A query settled 2,010 nodes on average, 24% of Dijkstra: more than the hierarchy, because the end cells are searched in full and the boundaries are crossed node by node. When the highway jammed, only the one cell it runs through needed customizing again, and after that the overlay was right on all 100 trips past the jam. Customizing one cell took about 2.1 ms in one run, the same on every size of map, because a cell does not grow when the map does; customizing all of them took between 47 and 690 ms.

A single level of cells divides the work by a constant, as the growth chart above shows. Production systems stack levels, cells of cells, so that a long trip crosses a few large cells. The same survey reports this method answering a query on Western Europe in 1.65 ms after settling 2,766 nodes, with a new set of weights applied in about 370 ms on a 12-core machine. The two are not rivals: OSRM, below, offers both, the overlay by default and the hierarchy for large tables of travel times between many points, where its cheap queries matter most and traffic matters less.

Step 6d: Predicting the travel time

The arrival time is a forecast. A car leaving now reaches the far end of a 36 km route half an hour from now, when the traffic there will be different. The chapter tests four ways of forecasting on a simulated commute into a city: 36 one-kilometer segments, town streets at both ends and a motorway between, each segment slowing around its own rush hour, with the jam starting near the city and spreading outward. Mornings differ in how bad the rush is, and a quarter of them have a crash that cuts 3 km to 15 km/h for 20 to 60 minutes. Speeds observed at departure carry 5% of measurement noise. Over 300 mornings with departures every ten minutes from 06:00 to 10:00, each forecast was compared with the time the drive took.

The four forecasts, made at departure, drive the route in steps of 100 m at a predicted speed. Free flow uses the speed limit; “traffic now” uses each segment’s current speed for the whole trip; “typical” looks up each segment’s usual speed at the time the car will reach it; the last combines them, as in code/91-hld-maps/eta.ts:

speed(segment, t) = typical(segment, t) × (live(segment) ÷ typical(segment, now))w, with w = e−(t − now) ÷ 15 min

The surprise is that today’s live speeds, used for the whole trip, did worse than history. A jam near the city at 07:40 will have cleared by the time a car leaving now gets there, and the road ahead that is clear now will be jammed when it arrives. The typical pattern, looked up for the time the car will reach each segment, knows the shape of a morning. Live data is best used for what it knows: today’s difference from typical, trusted fully for the next few minutes and fading toward typical after that. The crash shows the limit of any forecast: one that starts after departure cannot be foreseen, and the error on those mornings stays twice the average.

The same applies to choosing the route: a search that uses each segment’s speed at the time the car reaches it can avoid a jam that is still building. During the trip, the forecast is recomputed for the remaining route with every batch of positions, and a background search proposes a new route only if it saves several minutes, so that routes do not flip back and forth.

At ten times the users, everything grows by adding copies: routing servers, stream partitions, CDN capacity. The graph does not grow, since the roads do not. What changes the design is other services asking for tables of travel times, hundreds of drivers by hundreds of riders (), done as one many-to-many search on the hierarchy. At a hundred times, shipping the traffic snapshot to every routing server each minute becomes the bottleneck, so it is sent as changes, cell by cell, and each server customizes only what changed.

In the real world

  • Bing Maps’ tile system (Microsoft’s documentation, updated 22 May 2024) makes the map 256 × 2level pixels wide and names tiles by quadkeys; OpenStreetMap’s standard tiles are 256-pixel PNG images addressed as zoom/x/y (its wiki, May 2026).
  • Protomaps publishes a daily build of an OpenStreetMap basemap for the whole planet as a single file of about 120 GB with zoom levels 0 to 15 (its documentation, as of October 2026).
  • Bing Maps moved its directions to a new routing engine built on customizable route planning from Microsoft Research, announced on 5 January 2012, and reported processing requests twice as fast as before.
  • The open-source router OSRM offers both contraction hierarchies and a multi-level overlay it calls multi-level Dijkstra, and its README (as of October 2026) recommends the overlay by default “except for special use cases such as very large distance matrices”.
  • Google and DeepMind wrote on 3 September 2020 that Google Maps combines live traffic with historical patterns, that its arrival times had been accurate for over 97% of trips, and that a graph neural network over “supersegments” of adjacent roads improved accuracy by up to 50% in cities such as Berlin, Sydney and Tokyo.
  • Google’s Routes API (documentation updated 5 October 2026) lets a caller choose between ignoring traffic, the fastest response; using traffic with performance optimizations; and using traffic without them, the slowest response.

In an interview. Say early that this is three systems, and spend the deep dives where the difficulty is. Tiles take five minutes: the pyramid, versioned files on a CDN, vector against raster. Key points

  • A maps service is three systems: static tiles served from the edge, a search over an in-memory road graph, and a stream of positions turned into speeds.
  • Tiles form a pyramid with four times as many at each zoom level. Version them in the URL and cache them forever; prefer vector tiles, which stop at about zoom 15.
  • Dijkstra settles about half the map for a typical trip. A* and a bidirectional search help by constant factors; preprocessing helps by orders of magnitude.
  • A contraction hierarchy settled 164 nodes where Dijkstra settled 8,457, and its work hardly grows with the map, but it is built for one set of weights.
  • Traffic changes weights every minute. Cells with precomputed crossings let a change be absorbed by recomputing one cell, in milliseconds.
  • An arrival time is a forecast: use typical speeds for when each segment will be reached, corrected by today’s difference, which fades with distance ahead.

Check yourself

How many tiles are there at zoom 10, and why does the deepest zoom level dominate storage?

410, about 1.05 million. Each level has four times as many tiles as the one above, so the levels above the deepest one together hold about a third as many as it does: the deepest level is about three quarters of the total.

Why do tile URLs contain a version number?

So that a tile, once published, never changes. Every cache can keep it for as long as it likes, and a new map build is published under a new version instead of invalidating millions of cached files. The app switches versions by a configuration change.

Why does A* help less for the fastest route than for the shortest?

Its estimate of the time still to go must never be too high, so it assumes a highway all the way. In town that is far below the real time, and a weak estimate steers the search only a little. For distance, the straight line is a much closer bound.

What is a shortcut in a contraction hierarchy, and when is one added?

An edge between two neighbors of a node being removed, carrying the time of the path through it. It is added only if no other path between them is as fast, which a small search checks. With shortcuts in place, a query never descends to unimportant nodes mid-route.

A jam appears on a highway. What must a contraction hierarchy do, and what must a cell overlay do?

The hierarchy’s shortcuts carry times computed before the jam, so it gives wrong answers until it is rebuilt, which takes minutes for a continent. The overlay recomputes the crossing times of the cell the highway runs through, which took about 2 ms in the test, and is correct again.

Why did using the current speeds for the whole trip do worse than using typical speeds for the time of day?

The car reaches the far segments later, when their traffic has changed: a jam at its worst now may have eased, and an empty road may have jammed. Typical speeds for the time of arrival capture that; live speeds are best used to adjust them for the next few minutes.

A trip’s positions arrive twice because the phone retried a batch. What happens?

Nothing harmful. Each position is keyed by trip and time, so the repeat overwrites itself, and the traffic service, which averages speeds per segment, sees each car once per time. The reply, an updated arrival time, is the same either way.
