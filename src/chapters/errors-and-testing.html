Three kinds of failure

“Error handling” covers three situations that have little in common. Treating them alike is the root of most bad error handling, so the first step is to tell them apart.

An expected outcomeAn infrastructure failureA bug
ExampleThe card was declined. The order is already placed. No such photoThe database timed out. The disk is full. The mail service returned 503A field read from undefined. An impossible state. A wrong assumption
Whose faultNobody’s. The request cannot be grantedThe environment’sThe program’s
Who can act on itThe caller, and usually the userSometimes a retry. Otherwise an operatorA programmer, later
The right responseSay so plainly, as a normal resultRetry if it is safe to. Otherwise fail the request cleanlyStop the operation, record everything, hide the details from the client
To the clientA 4xx status and a specific messageA 503, or a 500A 500 with no internal detail
In the logInformation, if anythingA warning or an errorAn error, with the stack trace

The first column is not exceptional at all. A declined card is one of the things a payment does, and code that calls a payment function has to deal with it as surely as it deals with success. The last column is the opposite: there is nothing the surrounding code can sensibly do about a bug except stop and report.

Errors as part of the interface

TypeScript has one mechanism for failure built in, throw, and it has a weakness for the first kind of failure. A function’s type says what it returns and nothing about what it throws. The compiler does not check that a caller handles anything, and inside a catch block the error has the type unknown in strict mode.

For outcomes that every caller must handle, there is an alternative: return them. A result type is a union of a success carrying a value and a failure carrying an error, so that the possible failures appear in the function’s signature.

// A result is either a value or an error, and the type says which errors are possible.
export type Result = { ok: true; value: T } | { ok: false; error: E };
export const ok = (value: T): Result => ({ ok: true, value });
export const err = (error: E): Result => ({ ok: false, error });

// Every way that paying for an order can turn out badly, as data.
export type PayError =
  | { kind: "order-not-found"; orderId: string }
  | { kind: "already-paid"; orderId: string }
  | { kind: "card-declined"; reason: "insufficient-funds" | "expired" | "suspected-fraud" }
  | { kind: "gateway-unavailable"; retryAfterSeconds: number };

export interface Receipt {
  orderId: string;
  amountCents: number;
  reference: string;
}

// The signature is the documentation: callers can see every outcome, and must deal with the union to reach the value.
export async function payForOrder(orderId: string, charge: Gateway): Promise> {
  const order = orders.get(orderId);
  if (!order) return err({ kind: "order-not-found", orderId });
  if (order.paid) return err({ kind: "already-paid", orderId });
  const outcome = await charge(order.amountCents);
  if (outcome.status === "declined") return err({ kind: "card-declined", reason: outcome.reason });
  if (outcome.status === "down") return err({ kind: "gateway-unavailable", retryAfterSeconds: 30 });
  order.paid = true;
  return ok({ orderId, amountCents: order.amountCents, reference: outcome.reference });
}

// One place decides what each outcome means to the user. A new kind of error will not compile until it is added here.
export function toHttp(result: Result): { status: number; body: unknown } {
  if (result.ok) return { status: 200, body: result.value };
  const error = result.error;
  switch (error.kind) {
    case "order-not-found": return { status: 404, body: { error: `no order ${error.orderId}` } };
    case "already-paid": return { status: 409, body: { error: "this order has already been paid" } };
    case "card-declined": return { status: 402, body: { error: `card declined: ${error.reason}` } };
    case "gateway-unavailable": return { status: 503, body: { error: "payments are briefly unavailable", retryAfter: error.retryAfterSeconds } };
    default: { const missed: never = error; throw new Error(`unhandled: ${JSON.stringify(missed)}`); }
  }
}

In a test, five calls produced the statuses 200, 409, 404, 402 and 503, one for success and one for each kind of error. Three properties of this style matter.

  • The caller cannot forget. The value is reachable only by first checking ok. Code that reads result.value without checking does not compile.
  • The list of errors is closed and checked. If a fifth kind is added to PayError, the switch in toHttp stops compiling at the never line until someone decides what the new kind means to the user ().
  • Errors carry data. A declined card has a reason, and an unavailable gateway says when to retry. They are fields, not text to be parsed out of a message.

Results have a cost: every caller between the failure and its handler must pass the result along explicitly, where an exception would travel unaided. That suggests a division of labor.

UseForBecause
A returned result or unionExpected outcomes that the immediate caller should decide aboutThe compiler makes the caller look
A thrown errorInfrastructure failures and bugs, and expected outcomes that are handled several layers awayIt travels through layers that have nothing to add, and no one has to remember to pass it on

Both styles appear in good codebases, and the previous chapters used thrown DomainErrors caught at the HTTP adapter. What matters is that the choice is deliberate and that expected outcomes are distinguishable from bugs, whichever carrier they use.

Error classes

When errors are thrown, give them types of their own. An error is then recognized by what it is, with instanceof, and never by matching the text of its message.

// A base class for the application's own errors: a stable code for programs, a message for people, the cause for engineers.
export class AppError extends Error {
  readonly code: string;
  readonly status: number;

  constructor(code: string, status: number, message: string, options?: { cause?: unknown }) {
    super(message, options);
    this.name = new.target.name; // "ConflictError", not "Error", in logs and stack traces
    this.code = code;
    this.status = status;
  }
}
export class NotFoundError extends AppError {
  constructor(what: string, options?: { cause?: unknown }) { super("not-found", 404, `${what} does not exist`, options); }
}
export class ConflictError extends AppError {
  constructor(message: string, options?: { cause?: unknown }) { super("conflict", 409, message, options); }
}
export class RuleError extends AppError {
  constructor(message: string) { super("rule-violated", 422, message); }
}

// At a boundary: turn a low-level failure into one of ours, and keep the original attached as the cause.
export async function savingOrder(orderId: string, write: () => Promise): Promise {
  try {
    return await write();
  } catch (error) {
    if (error instanceof Error && /UNIQUE constraint failed/.test(error.message)) {
      throw new ConflictError(`order ${orderId} already exists`, { cause: error });
    }
    throw error; // not ours to interpret: let it travel
  }
}

Two details in the listing repay attention.

  • The cause. Since ECMAScript 2022 an error can be created with a cause, the lower-level error that led to it. Wrapping without it throws away the one piece of information an engineer needs. In the test, the ConflictError carried the original database error, and the log line showed both.
  • The narrow catch. savingOrder translates exactly one failure, the uniqueness violation it understands, and rethrows everything else untouched. A “disk I/O error” passed straight through it in the test. Catching broadly and converting every failure into “conflict” would turn an outage into a stream of misleading 409s.

Common mistake. Logging an error with JSON.stringify. An Error’s message and stack are not enumerable properties, so JSON.stringify(new Error("lost")) produces {}, as the test confirmed, and the log records that something happened and nothing about what. Use a logger that knows about errors, or copy name, message, stack and cause out by hand ().

Where to handle an error

An error should be dealt with at the first place that can do something useful about it, and nowhere before. In the layered application of , that gives each layer a small, fixed job.

LayerIts job with errors
DomainDetect broken rules and throw or return an error in business terms. Never catch
Driven adaptersTranslate the specific failures of their technology into the application’s terms, keeping the cause. Let the rest pass
ApplicationHandle what it can truly handle: retry a version conflict, undo a reservation. Let the rest pass
Driving adaptersOne outer handler: turn known errors into specific responses, turn unknown ones into a generic failure, and log
 
export interface Problem {
  type: string;
  title: string;
  status: number;
  detail?: string;
}
export interface LogEntry {
  level: "info" | "error";
  code: string;
  message: string;
  causes: string[];
  stack?: string;
}

// The outermost handler: the only place that turns an error into a response and a log line.
export function toResponse(error: unknown, log: (entry: LogEntry) => void): { status: number; body: Problem } {
  const causes: string[] = [];
  for (let e = error instanceof Error ? error.cause : undefined; e instanceof Error; e = e.cause) causes.push(`${e.name}: ${e.message}`);
  if (error instanceof AppError) {
    // An expected outcome. The client is told what happened, and the log records it without alarm.
    log({ level: "info", code: error.code, message: error.message, causes });
    return { status: error.status, body: { type: `https://photos.example/problems/${error.code}`, title: error.name, status: error.status, detail: error.message } };
  }
  // Anything else is a bug or a broken dependency. Log everything, and tell the client nothing about the inside.
  const unknown = error instanceof Error ? error : new Error(String(error));
  log({ level: "error", code: "internal", message: unknown.message, causes, ...(unknown.stack ? { stack: unknown.stack } : {}) });
  return { status: 500, body: { type: "https://photos.example/problems/internal", title: "Internal error", status: 500 } };
}

Given the wrapped conflict, the handler answered 409 with a body in the problem details format of and logged one line at the information level, including the cause. Given a TypeError from a real bug, it answered 500 with a body that said only “Internal error”, and logged the message and the full stack. The response to the bug contained no word of the internal message, which matters: error text routinely includes table names, file paths and fragments of data ().

A few rules cover most of the remaining decisions.

  • Fail early. Check inputs at the edge and turn them into types that cannot be invalid (). An error found at the door is cheap. The same error found three layers in, after two writes, is not.
  • Never swallow. An empty catch block is a decision that this failure does not matter, made for every failure that will ever reach it. If ignoring is right, say why in a comment and log it.
  • Do not catch what you cannot handle. Catching only to log and rethrow at every layer produces five log entries for one failure. Log once, at the outer handler.
  • Retry only what is transient and safe to repeat (, ). A declined card will be declined again. A bug will fail the same way every time.
  • Clean up in finally. Locks, file handles and transactions must be released on every path out.

A trap in asynchronous code

One asynchronous detail defeats error handling that looks correct.

const fragile = async (): Promise => {
  throw new Error("the database is down");
};

// The promise is returned before it rejects, so this try block has already been left. The catch never runs.
export async function withoutAwait(): Promise {
  try {
    return fragile();
  } catch {
    return "fallback";
  }
}

// Awaiting inside the try keeps the function here until the promise settles, so the catch can see the failure.
export async function withAwait(): Promise {
  try {
    return await fragile();
  } catch {
    return "fallback";
  }
}

In the test, withoutAwait() rejected with “the database is down” and its catch never ran, while withAwait() returned “fallback”. The rule: inside a try block, always await a promise before returning it. The same reasoning explains the floating promises of . A try only covers what is awaited inside it.

What makes code testable

A test does three things: it arranges a situation, performs one action and checks the outcome. Code is hard to test exactly when one of those is hard: the situation cannot be arranged, or the outcome cannot be observed. Both come from the same cause, which is a dependency the code reaches for itself.

export interface Shipment {
  orderId: string;
  placedAt: Date;
  shippedAt: Date | null;
}

// Hard to test. The answer depends on two things that do not appear in the signature: today's date and a remote service.
export async function isLateHidden(orderId: string): Promise {
  const response = await fetch(`https://shipping.example/orders/${orderId}`);
  const shipment = (await response.json()) as { placedAt: string; shippedAt: string | null };
  const days = (Date.now() - new Date(shipment.placedAt).getTime()) / 86_400_000;
  return shipment.shippedAt === null && days > 3;
}

// The decision, as a pure function: everything it needs comes in as arguments, and the answer is its only effect.
export function isLate(shipment: Shipment, now: Date, allowedDays = 3): boolean {
  if (shipment.shippedAt !== null) return false;
  const days = (now.getTime() - shipment.placedAt.getTime()) / 86_400_000;
  return days > allowedDays;
}

// The shell: fetches what the decision needs, calls it, and acts. Its collaborators are passed in.
export interface LateDeps {
  loadShipment(orderId: string): Promise;
  now(): Date;
  notify(orderId: string, message: string): Promise;
}
export async function chaseLateOrder(orderId: string, deps: LateDeps): Promise {
  const shipment = await deps.loadShipment(orderId);
  if (!isLate(shipment, deps.now())) return false;
  await deps.notify(orderId, "Your prints are taking longer than usual. We are on it.");
  return true;
}

The first function has one parameter and three inputs. Two of them, the current time and the reply of a remote service, are invisible in its signature and outside a test’s control. To test “three days and one second is late” you would have to wait three days, or own the shipping service.

Dependency injection is the practice of giving a piece of code its collaborators from outside, as parameters, where it would otherwise create or find them itself. It needs no framework. A constructor parameter or a function argument is the whole mechanism, and the wiring happens once, in the composition root of .

The listing goes one step further than injecting, and the step is worth more than the injection. It separates the decision from the effects.

  • The decision is a pure function: its result depends only on its arguments, and it changes nothing. isLate was tested with a table of five cases, including the boundary at exactly three days, by passing dates. No doubles, no setup, about a quarter of a microsecond a call.
  • The effects are a thin shell that gathers inputs, calls the decision and acts on the answer. chaseLateOrder has one branch. Two tests cover it.

This arrangement is known as “functional core, imperative shell”. The more of a program’s logic that can be moved into functions of that first kind, the less of it needs anything but plain values to test. The usual hidden inputs to look for are the same in every codebase.

Hidden dependencyWhy it hurts a testPass in instead

The network, the database, the file systemSlow, needs setup, fails for unrelated reasonsA port, with a fake behind it
Global state: singletons, module-level variables, environment variablesTests affect each other, and must run in a particular orderThe value or object itself
new ConcreteThing() in the middle of the logicThe collaborator cannot be replacedThe thing, or a factory for it

Test doubles

When the unit being tested needs a collaborator, the test supplies a stand-in. The general term is test double, and there are five kinds, named in Gerard Meszaros’s xUnit Test Patterns. “Mock” is often used loosely for all of them, which hides useful differences.

DoubleWhat it doesUse it to
DummyNothing. It fills a parameterSatisfy a signature when the collaborator is irrelevant to this test
StubReturns canned answersPut the unit in a situation: “the gateway declines”
SpyRecords how it was calledCheck an effect: “one receipt was sent, to Ana”
MockIs told in advance which calls to expect, and fails the test itself if they differThe same as a spy, with the checking built in. Usually created by a mocking library
FakeA working implementation with a shortcut, such as a repository in memoryRun realistic scenarios quickly. The most valuable kind
 
export interface PaymentGateway {
  charge(customer: string, cents: number): Promise<{ ok: true; reference: string } | { ok: false; reason: string }>;
}
export interface Mailer {
  send(to: string, subject: string): Promise;
}
export interface AuditLog {
  record(entry: string): void;
}

// The unit under test. It has three collaborators and receives all of them.
export class Checkout {
  private readonly gateway: PaymentGateway;
  private readonly mailer: Mailer;
  private readonly audit: AuditLog;

  constructor(gateway: PaymentGateway, mailer: Mailer, audit: AuditLog) {
    this.gateway = gateway;
    this.mailer = mailer;
    this.audit = audit;
  }

  async pay(customer: string, cents: number): Promise<"paid" | "declined"> {
    const outcome = await this.gateway.charge(customer, cents);
    if (!outcome.ok) return "declined";
    await this.mailer.send(customer, `Receipt ${outcome.reference}`);
    return "paid";
  }
}

// A dummy fills a parameter that this test never exercises.
export const dummyAudit: AuditLog = { record: () => {} };

// A stub returns a canned answer, to steer the unit down one path.
export const stubGateway = (answer: Awaited>): PaymentGateway => ({ charge: async () => answer });

// A spy also remembers how it was called, so that the test can ask afterward.
export class SpyMailer implements Mailer {
  readonly sent: { to: string; subject: string }[] = [];
  async send(to: string, subject: string): Promise {
    this.sent.push({ to, subject });
  }
}

// A fake is a working implementation that takes a shortcut: here, balances in a map where the real one calls a bank.
export class FakeGateway implements PaymentGateway {
  private readonly balances: Map;
  private count = 0;
  constructor(balances: Record) {
    this.balances = new Map(Object.entries(balances));
  }
  async charge(customer: string, cents: number): Promise<{ ok: true; reference: string } | { ok: false; reason: string }> {
    const balance = this.balances.get(customer) ?? 0;
    if (balance < cents) return { ok: false, reason: "insufficient-funds" };
    this.balances.set(customer, balance - cents);
    this.count += 1;
    return { ok: true, reference: `ref-${this.count}` };
  }
  balanceOf(customer: string): number {
    return this.balances.get(customer) ?? 0;
  }
}

Three tests were run with these. With a stub that approves, pay returned “paid” and the spy held one receipt. With a stub that declines, it returned “declined” and the spy held none. With the fake bank holding 10.00 for Ana, charges of 5.50, 3.00 and 3.00 came back paid, paid and declined, leaving 1.50.

The third test shows why fakes are worth the effort of writing. No stub was told what to answer. The fake has behavior, so the test describes a scenario and checks its outcome, and stays valid if Checkout is rewritten to call its collaborators differently. Tests built from many stubs and mocks tend to restate the implementation call by call, and then every refactoring breaks them while no bug does.

Two guidelines keep doubles honest.

  • Double your own interfaces, not other people’s. A stub of a vendor’s client encodes your guess about how it behaves. Wrap the vendor in an adapter behind your own port (), fake the port, and test the adapter against the real thing.
  • Keep fakes and real adapters in agreement with the contract tests of , which run one set of expectations against both.

Levels of testing

Tests differ in how much of the system they exercise at once, and that determines what they cost and what a failure tells you.

  • A unit test checks one small piece, a function or a class or an aggregate, in memory, with doubles for anything slow.
  • An integration test checks that a piece works with a real external technology: that the SQL is valid, that the HTTP adapter maps errors to the right statuses.
  • An end-to-end test drives the whole deployed system the way a user would.

The classical advice, the test pyramid, is to have many of the first, fewer of the second and only a handful of the third. The reason is arithmetic.

3,320 tests take 3.63 min run one after another. The end-to-end tests account for 91.7% of that, though they are only 0.602% of the tests. If every one of these checks were made end to end, the suite would take 9.22 hours. This suite can run before every commit, but not on every save.

The pyramid is a default, not a law. A service that is mostly glue between a database and an API has few rules to unit test and much wiring that can only be checked with the real parts, and for such code a suite weighted toward integration tests is the better shape. The principle underneath every shape is the same: check each thing at the lowest level that can prove it. A pricing rule needs a unit test. A SQL query needs a database. That the login page leads to the dashboard needs a browser, once.

Whatever the level, a few properties separate tests that help from tests that are merely present.

  • Test behavior, through the public interface. “Placing an empty order is refused” survives any rewrite of Order. “place calls validateLines once” does not.
  • One reason to fail. A test with a name that states a rule, and a failure that points at it.
  • Deterministic. A flaky test passes and fails on the same code. The causes are the hidden inputs in the table above, plus timing and shared state between tests. A flaky test teaches a team to ignore failures, which is worse than having no test.
  • Fast enough to run constantly. Feedback that takes seconds is used while writing code. Feedback that takes an hour is used once a day.

Checking a property

An example-based test checks the cases its author thought of. A property-based test states something that must be true for every input and lets the machine search for a counterexample. Money.split from makes two such promises: the shares add up to the original amount, and no two shares differ by more than a cent.

// A property: a statement that must hold for every input. Here, two of them, for any amount and any number of shares.
export function checkSplit(runs: number, seed: number): { runs: number; failure: string | null } {
  const random = seeded(seed);
  for (let i = 0; i < runs; i += 1) {
    const cents = Math.floor(random() * 10_000_000);
    const shares = 1 + Math.floor(random() * 50);
    const parts = Money.of(cents, "EUR").split(shares).map((money) => money.cents);
    const sum = parts.reduce((a, b) => a + b, 0);
    const spread = Math.max(...parts) - Math.min(...parts);
    if (sum !== cents) return { runs: i + 1, failure: `${cents} split ${shares} ways adds up to ${sum}` };
    if (spread > 1) return { runs: i + 1, failure: `${cents} split ${shares} ways has shares ${spread} cents apart` };
  }
  return { runs, failure: null };
}

// The same property against the obvious wrong implementation, to show that the check can fail.
export function checkNaiveSplit(runs: number, seed: number): { runs: number; failure: string | null } {
  const random = seeded(seed);
  for (let i = 0; i < runs; i += 1) {
    const cents = Math.floor(random() * 10_000_000);
    const shares = 1 + Math.floor(random() * 50);
    const sum = Math.round(cents / shares) * shares;
    if (sum !== cents) return { runs: i + 1, failure: `${cents} split ${shares} ways adds up to ${sum}` };
  }
  return { runs, failure: null };
}

The property held for 10,000 random amounts and share counts. Run against the obvious wrong implementation, rounding each share, the same check failed on the first input it tried: 60,110.37 split 23 ways added up to 60,110.27. The generator is seeded, so the failing case can be replayed exactly, and a second run with the same seed failed in the same place. Libraries such as fast-check add smarter generators and reduce a failing input to the smallest one that still fails.

In an interview. “How would you test this?” is asked at the end of most low-level design rounds, and a design that has followed this part of the book answers it by construction. Point to the rules, and say they are tested directly on the domain classes with no doubles. Point to each interface you passed in, such as the clock, the repository and the payment gateway, and say what fake stands behind it in a test. Name two or three cases at the edges: the last free spot, exactly at the limit, the same request twice. Then say what you would not unit test: the real database adapter and the HTTP mapping get a few integration tests.

Key points

  • Expected outcomes, infrastructure failures and bugs are different things. Represent, report and log each in its own way.
  • An expected outcome is part of a function’s interface. A result type puts it in the signature and makes the compiler check that callers deal with it.
  • Give thrown errors types, stable codes and causes. Recognize them by type, never by message.
  • Translate an error where its meaning changes, handle it where something useful can be done, and let it pass everywhere else. One outer handler responds and logs.
  • Inside a try, await a promise before returning it.
  • Code is testable when its dependencies are passed in. Clocks, randomness, networks and globals are the usual hidden ones.
  • Keep decisions in pure functions and effects in a thin shell around them.
  • Stubs supply inputs, spies observe outputs, and fakes are working substitutes. Prefer fakes, and keep them honest with contract tests.
  • Check each thing at the lowest level that can prove it, and keep every test deterministic.

Check yourself

Classify each failure and say what the client should receive: the user’s storage quota is full, the database connection pool is exhausted, and a function received null where its type says it cannot.

A full quota is an expected outcome: a 4xx response with a specific message, since the user can act on it. An exhausted pool is an infrastructure failure: a 503, possibly after a retry, with nothing internal revealed, and an alert for operators. The null is a bug: a 500 with a generic body, and an error log with the stack trace for a programmer.

A function is declared charge(card): Promise<Result<Receipt, "declined" | "expired">>. What does a caller gain compared with a version that throws for a declined card?

The possible failures are visible in the signature, so the caller knows them without reading the implementation. The compiler will not allow the receipt to be used until the caller has checked which branch it has. And if a third failure is added to the union later, every exhaustive switch over it stops compiling until it is handled.

A repository adapter catches every error from the database driver and rethrows new Error("save failed"). Name two things wrong with that.

It discards the cause, so nobody can tell from the log whether the disk was full, a constraint failed or the connection dropped. And it erases the distinctions callers need: a version conflict that could be retried, a duplicate that should be a 409 and an outage that should be a 503 all become the same anonymous error. Translate only the failures the adapter understands, attach the original as the cause, and let the rest pass unchanged.

What does this function return when load() rejects, and why? async function f() { try { return load(); } catch { return null; } }

It returns a promise that rejects. The catch does not run. return load() hands the pending promise back and leaves the try block before the rejection happens, so there is no longer a handler in place when it does. Writing return await load() keeps the function inside the try until the promise settles, and then null is returned.

A function decides whether a discount code is still valid by comparing its expiry with new Date(). Why is that a problem for testing, and what are two ways to fix it?

The current time is an input the test cannot set, so “expires in one second” and “expired yesterday” cannot both be tested reliably, and results depend on when the suite runs. Either pass the current time in as an argument, which makes the function pure, or pass in a clock object and give tests a fixed one.

For each need, name the kind of double: making the payment gateway time out, checking that no email was sent, running twenty checkout scenarios against something that behaves like a bank, filling a required logger argument in a test about arithmetic.

A stub, set up to fail with a timeout. A spy on the mailer, whose record of calls should be empty. A fake gateway with real balance logic in memory. A dummy logger that does nothing.

A team has 150 end-to-end tests that take 40 minutes and fail at random about one run in five. What would you change first?

Sort the tests by what they prove. Most will be checking business rules and error cases that need no browser or network, and those should move down to unit tests against the domain and use cases, where they run in milliseconds and cannot flake. Keep a small set of end-to-end tests for the critical journeys. For the flaky ones that remain, find the uncontrolled input, usually timing, shared data or an external service, and remove it.
