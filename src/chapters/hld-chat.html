The problem

The problem. Design a chat service like WhatsApp or Messenger. Users send messages to one another and to groups. Each message shows whether it has been sent, delivered and read. Users have a phone and possibly a laptop, and every device shows the whole conversation, including what arrived while it was offline.

Sending a message from one connected device to another is easy. What is hard is everything around it. Hundreds of millions of devices hold open connections, and those connections break without warning. A message must survive that: it may not be lost, may not appear twice when a send is retried, and must sit in the same place in the conversation on every device. Groups multiply each message by their size, and receipts multiply it again. stated the rule this chapter builds on: a connection is not a queue. The method of takes these in order.

Try a ping every 5 minutes, as a phone saving battery might: heartbeats fall to 667,000 a second, below the receipts. The trade is slower detection of dead connections, which the delivery protocol of step 6a tolerates.

  • Ids and retries. The device chooses each message’s id, here its own device number and a counter. A retried send carries the same id, and the server answers it with the sequence number it gave the first time ().
  • Receipts are positions. received and read say “everything up to 4103”, never a single message. Step 6c explains why.
  • Catching up. Each user has a conversation list with a version number that rises whenever any of their conversations changes. A device that has been away asks what changed since the version it last saw, then fetches each changed conversation after the last number it holds. The after cursor pages through long gaps ().
  • Errors. A send to a conversation the user has left is refused with its id, so the device can mark that message as failed; a client over its limit is slowed ().

A group message is stored once, in the conversation. What is written per member is small: their conversation list and, later, their receipts. Copying the message into an inbox per member would multiply the 4 TB a day by the average group size.

Step 5: The design

Gateways hold connections and nothing else, so they can be restarted and scaled without touching messages. Each conversation is owned by one chat service instance at a time, chosen by consistent hashing on its id (), and that owner gives out its sequence numbers. The sender is acknowledged when the message is stored; delivering it to the other members, which for a large group is a thousand lookups and pushes, is queued work.

Two details in the flows carry the design. The tick Ana sees first means “stored”, not “sent to Ben”, because the store is the only place a message is safe. And Ben’s phone never trusts that it has everything: the numbers tell it what is missing, and the store has it.

Step 6a: Delivery that survives disconnects

A sequence number is a message’s position in its conversation, given by the server when it stores the message: 4101, 4102, 4103, with no gaps. It is what lets a device know what it is missing. To measure what each part of the protocol buys, the simulation runs a group of five members on seven devices for an hour. Each member writes a message every 6 seconds on average. Each device stays connected for 5 minutes on average and then disappears for one, 2% of transmissions on a live connection are lost, and anything in flight when a device disconnects is lost too. Three protocols ran on the same people, writing at the same moments on the same devices.

  • Push only. The writer’s gateway relays the message to each connected device, once. Nothing is stored.
  • Stored, no message ids. The server stores each message it receives and numbers it. Writers retry until acknowledged; devices fill gaps from the store.
  • Stored, ids and sequence numbers. The same, but each message carries the id its device chose, and the server keeps one copy per id.

Push only loses almost a quarter of deliveries: everything sent while a device was away, and everything a broken connection swallowed. Storing first and filling gaps loses nothing, but a writer whose acknowledgment was lost sends again, and without an id the server cannot tell the retry from a new message. About one delivery in 46 then shows twice. The id makes the retry harmless, which is the at-least-once delivery with deduplication of . The cost is 47% more transmissions than push only, for acknowledgments, retries and gap repairs.

The server’s side is short. It answers a retry with the number it already gave, and it accepts a device’s messages only in the order they were written, for a reason step 6b explains.

case 'toServer': {
  const d = devices[e.dev] as Device;
  if (!d.online || d.epoch !== e.epoch) break;
  if (!stored) { pushToAll({ seq: 0, msg: e.msg }); break; }
  const known = ids ? byClientId.get(e.msg.clientId) : undefined;
  if (known === undefined) {
    // With ids, a message that overtook an earlier one from the same device waits for its retry.
    if (ids && e.msg.deviceSeq !== nextFromDevice[d.id]) break;
    if (ids) nextFromDevice[d.id] = e.msg.deviceSeq + 1;
    const entry: Entry = { seq: log.length + 1, msg: e.msg };
    log.push(entry);
    byClientId.set(e.msg.clientId, entry);
    pushToAll(entry);
  }
  transmit({ kind: 'ack', dev: d.id, epoch: d.epoch, clientId: e.msg.clientId }, down(d));
  break;
}

The device’s side is a counter and a small buffer. It shows a message only when it has every number below it; a gap, or a ping naming a newer number than it has, makes it ask the store for the rest.

const receive = (d: Device, entries: Entry[], newest: number) => {
  if (!stored) { for (const e of entries) show(d, e); return; }
  for (const e of entries) if (e.seq > d.lastSeq) d.early.set(e.seq, e);
  while (d.early.has(d.lastSeq + 1)) {
    const e = d.early.get(d.lastSeq + 1) as Entry;
    d.early.delete(e.seq);
    d.lastSeq = e.seq;
    show(d, e);
  }
  // A gap, or a ping that names a newer message: something was lost. Ask for everything after the last shown.
  if (d.early.size > 0 || newest > d.lastSeq) resume(d);
};

Between two devices that stayed connected, half the deliveries took 134 ms and 96.1% took under a second. The rest are lost transmissions, repaired when the next message reveals the gap or the writer’s 2-second retry fires, and they put the 99th percentile at 2.23 seconds, slightly over the target. With 0.5% of transmissions lost instead of 2%, 98.9% arrived within a second and the 99th percentile was 1.60 seconds. Counting devices that were away, the 99th percentile is 201 seconds: those messages waited, safely stored, for the device to come back.

Step 6b: One order for every device

Sorting by the time each message was written looks natural and is wrong, because each device’s clock is its own (). With clocks off by a second on average and replies written at least 2 seconds after the message they answer, sorting by the writer’s clock would have put 12 of 1,524 replies above the message they answer. Sorting by the server’s sequence number put none there: a device can only answer a message it has received, and it receives only what the server has already numbered.

One case escapes that argument: a device’s own messages. If the first of two messages from a phone is lost and the second gets through, the second is numbered first, and an answer to oneself appears above its question. Without ids, that happened 3 times in the hour. The fix is the device counter in the code above: the server takes a device’s messages only in the order written, and a message that overtakes an earlier one waits for its retry. That is head-of-line blocking (), and it is one reason the 99th percentile above is two seconds, not one.

Numbering needs one place that decides. Each conversation’s numbers come from the chat service instance that owns it, which allows a conversation as many messages a second as one machine can number, thousands, far beyond what a group of people writes. When an owner fails, another takes over its conversations, reads the newest number from the store, and continues. The store accepts a number only if it is free, so a former owner that has not noticed it was replaced cannot write a duplicate ().

Step 6c: Groups and receipts

A delivery receipt tells the sender that a message has reached a recipient’s device; a read receipt tells them the recipient has seen it. Sent once per message per member, receipts are the largest message load in step 2. But receipts have the same property as messages: they arrive in order. A device that has received 4112 has received everything before it. So a receipt can be a position, “everything up to 4112”, kept as one number per device and one per member, and the sender’s ticks are computed from those numbers.

A position also covers many messages at once. A phone that reconnects after an hour reports one number for the whole backlog, and an open chat in a busy group reports at most one number every few seconds. The simulation compared the two in a group of 100 whose phones connect about once an hour for 5 minutes, with the chat opened in half of those connections.

One receipt of each kind per message costs about 1.9 per member per message, whatever the group does. Positions cost 0.27 at 200 messages a day, 7 times fewer, and 0.14 at 1,000 a day, 13 times fewer. In a group of 1,000 at that rate, each message brings about 1,880 receipts sent one by one, or about 143 as positions. For the sender, the server keeps the pointers and sends updated counts at most every few seconds, and in large groups only when the sender opens the message’s details.

The message itself is stored once per group and delivered by the queued workers: for each member, look up the connected devices, push to them, and update the member’s conversation list. For a member with no connected device, the worker asks the notification service to wake the phone (). A 1,000-member group with 1.5 devices per member is about 1,500 pushes per message, which is why delivery is queued work rather than part of sending.

Step 6d: Presence and many devices

Presence is whether a user is connected now, or when they were last seen. It changes every time a phone connects or disconnects, which on mobile networks is often, and each change interests everyone who might look. Sending every change to every contact would cost more than the messages. So presence is kept in the connection registry, with an expiry renewed by heartbeats, and a device asks for the presence of the people in the conversation on screen, subscribing to changes only while it is open (). Typing indicators are presence for one conversation: never stored, and dropped if they arrive late.

Each device keeps its own “received up to” number, because each must receive every message. “Read up to” belongs to the member: reading on the laptop is sent to the phone as a position, and the phone clears its unread count without receiving anything new. A new device starts from the conversation list and fetches recent messages of each conversation as it is opened, rather than downloading years of history.

At ten times the users, the connection tier is the largest fleet: 4,000 gateways and 67 million heartbeats a second at a 30-second interval, which pushes the interval up and the connections per gateway toward what each can safely lose at once. Users connect to the nearest region; a conversation is owned in one region, and members elsewhere pay a cross-region round trip for each send (). At a hundred times the messages, storage dominates, 440 PB a year in three copies, and history older than a few months moves to object storage in compressed weekly blocks. The numbering, the receipts and the gateway split do not change.

In the real world

  • Discord, 2017. Discord stored messages in Cassandra with the key ((channel_id, bucket), message_id), where a bucket is a static time window of about 10 days, chosen to keep partitions under 100 MB, and the message id is a time-ordered Snowflake id. It was storing well over 120 million messages a day.
  • Discord, 2023. Discord moved its trillions of messages from 177 Cassandra nodes to 72 ScyllaDB nodes. The 99th percentile for fetching history fell from 40 to 125 ms to 15 ms, and for inserts from 5 to 70 ms to a steady 5 ms. Hot partitions, a busy channel’s bucket, were a recurring problem; services in front of the database now merge identical concurrent requests, routed by channel id with consistent hashing.
  • Facebook Messenger, 2014. Messenger’s Iris system keeps a totally ordered queue of messaging updates for each user, with pointers to the last update sent to each app, and pushes new updates over MQTT. Facebook reported that the change cut Messenger’s non-media data use by about 40% and the number of people who saw errors when sending by about 20%.

Key points

  • Store the message first, number it within its conversation, then push. A connection is never the only copy.
  • A device shows messages only in number order, notices gaps, and asks the store for what it missed.
  • Retries are unavoidable; an id chosen by the device makes them harmless.
  • One owner per conversation gives out numbers, so every device shows the same order and replies stay below their questions.
  • Receipts are positions, “everything up to 4112”, which cost 7 to 24 times fewer messages than one receipt per message in the simulation.
  • Store a group message once; deliver it to members as queued work after the sender’s acknowledgment.
  • Gateways only hold connections. Their heartbeats and presence can outweigh the messages, so both are kept cheap.

Check yourself

Ana’s phone shows one tick. What exactly does it know?

That the server has stored the message in three copies and given it a sequence number. It does not know that any recipient has it; that is the second tick, from a delivery receipt.

Ben’s phone has shown up to 4103 and receives 4105. What does it do?

It holds 4105 back, because 4104 is missing, and asks the server for everything after 4103. When 4104 and 4105 arrive it shows both, in order.

A send times out and the phone sends it again. How does the design avoid a duplicate?

The retry carries the same id the phone chose the first time. The server finds that id already stored and answers with the same sequence number instead of storing a second copy. Without ids, the simulation showed 2.2% of deliveries twice.

Why not order messages by the time on the sender’s phone?

Phone clocks disagree. With clocks off by about a second, sorting by them put 12 of 1,524 replies above the messages they answered. A server-given sequence number cannot, because a device only answers what the server has already numbered.

Why are receipts sent as “everything up to N”?

Messages arrive in order, so one number says everything a device has received or a member has read. It covers a whole backlog in one message and needs one stored number per device or member, not a flag per message.

A gateway holding 500,000 connections crashes. What happens to messages sent to those devices meanwhile?

They are already stored. The devices reconnect to other gateways after random delays and ask for everything after their last number, so the messages arrive late but none is lost.

Why are group messages delivered by queued workers rather than during the send?

A message to a 1,000-member group is about 1,500 pushes and as many registry lookups. Doing them before acknowledging the sender would make sending slow and fragile; once the message is stored, delivery can safely happen afterward.
