What scalability means

A system is scalable if adding resources lets it handle proportionally more load. Double the servers and it should serve close to double the traffic, at the same response time. A system that does this is said to scale linearly, and that is the ideal every design is measured against.

The definition has two words that need pinning down before it is useful.

Load is not one number. A system can be stressed along several independent dimensions, and it may cope well with one and badly with another:

  • requests per second, with reads and writes counted separately,
  • the total volume of data stored,
  • the number of connections held open at once,
  • the size of the largest single item, such as the user with the most followers,
  • the number of tenants, regions or teams sharing the system.

“Does it scale?” is therefore an incomplete question. The complete one is “if this particular dimension grows tenfold, what do we add, and what breaks first?”

Scalability is also not the same as performance. Performance is how fast the system is for one user at today’s load. Scalability is how that changes as load grows. A program can be very fast and not scalable at all, if its speed depends on everything living in the memory of one machine. Another can be slow and perfectly scalable. If the system is slow for a single user on an idle server, you have a performance problem, and adding machines will not help. If it is fast when idle and slow when busy, you have a scalability problem.

Scaling up: a bigger machine

The first way to add resources is to replace the machine with a larger one: more CPU cores, more memory, faster disks. This is vertical scaling, or scaling up.

It is the most underrated tool in the field. Nothing about the software has to change. There is still one copy of the data, so there is nothing to keep in sync. Every technique in the second half of this book that deals with machines disagreeing with each other is simply not needed. And the ceiling is far higher than most people assume.

How big can one machine be?In October 2026 the largest instance in Amazon’s EC2 catalog, u7inh-32tb.480xlarge, offered 1,920 virtual CPUs and 32 TiB of memory. Few datasets outgrow 32 TiB of RAM. The price of such a machine is another matter, and that is usually the constraint that bites first.

Scaling up has four limits, and you should know which one you will hit.

  • A hard ceiling. Eventually there is no larger machine to buy.
  • Cost that ignores demand. Within a family of cloud machines, twice the size costs about twice the price, so size brings no discount. A machine large enough for the evening peak is paid for at four in the morning too.
  • A single point of failure. One machine, however large, is down when it is down. Scaling up does nothing for availability.
  • Disruptive upgrades. Moving to a bigger machine usually means stopping the old one. As the system grows, the maintenance window becomes harder to find.

Scaling out: more machines

The second way is to add more machines of ordinary size and spread the work across them. This is horizontal scaling, or scaling out.

Scaling out has no ceiling in principle, uses ordinary hardware, and gives you redundancy as a side effect: with ten servers, losing one costs a tenth of your capacity instead of all of it. It also lets capacity follow demand hour by hour, which a single large machine cannot do.

The price is that you now run a distributed system. Something must route each request to a server. The servers must not depend on anything stored only in one of them. Where they share data, they must agree on it, and the network between them can delay or drop messages. Part IV of this book exists because of these problems.

Scale upScale out
Change to the softwareNoneOften significant

Effect on availabilityNone: still one machineImproves: survives the loss of a machine

The two are not rivals. A sensible system scales up while that is cheap and simple, and scales out the parts where it is easy, which usually means the stateless application servers first and the database last.

Common mistake. Distributing too early. A team with two thousand users adopts a sharded database and a dozen services because large companies use them. It now has the hardest problems in computing and none of the load that justifies them. One well-chosen server with a standby replica carries most products much further than their builders expect. Know the next step, and take it when a measurement tells you to.

The precondition: stateless servers

A load balancer can send a request to any server only if every server can handle it equally well. That holds when the servers are stateless: each request carries or can look up everything needed to process it, and the server keeps nothing between requests that another server would need.

The classic way to break this is the login session. A user signs in, and the server remembers them by storing a session object in its own memory. It works with one server. With two, the trouble in appears.

There are three ways out, and each trades something.

ApproachHow it worksCost
Sticky sessionsThe load balancer always sends a given user to the same server.Load spreads unevenly. When that server dies or is replaced, its users lose their sessions. Scaling in becomes painful.
Shared session storeSessions live in a fast store that all servers read, such as Redis.One extra lookup per request, and a new component that must itself be highly available.
State held by the clientThe session data travels with each request in a signed cookie or token that any server can verify.Hard to revoke before it expires. Size limits. The signing key must be protected and rotated.

The second and third are the common choices today, and compares them in depth. Sessions are only the most visible kind of server state. Before you scale an application out, look for these others:

  • Files written to local disk. An upload saved on server A is not there when the next request lands on server B. Store files in object storage.
  • In-memory caches. Each server builds its own, so they disagree with each other and all start empty after a deployment. That is acceptable for some data and wrong for other data, and it should be a decision.
  • Scheduled jobs. A nightly job configured on “the server” runs ten times when there are ten servers. Move scheduling to one place. See .
  • Long-lived connections. A WebSocket is attached to one server for its whole life. To send a message to a user you must find the server holding their connection. See .
  • Counters and rate limits. A limit of 100 requests per minute enforced in each server’s memory becomes 100 times the number of servers.

The rule that covers all of them: push state out of the application servers and into systems built to hold it. The servers become disposable, and the difficulty of scaling moves to the data stores, which is where the rest of the book spends most of its effort.

In an interview. “I’ll add more servers behind a load balancer” earns nothing unless you also say why that works here. State it: “the application servers are stateless, session data is in a signed token, uploads go straight to object storage, so any server can take any request.” Then turn to the database at once, since that is where the interviewer will look next.

How an architecture grows

Systems do not start distributed. They start as one server and acquire parts one at a time, each added to relieve a specific pressure. The order below is typical. The trigger for each step is a symptom you can observe, never a user count, because how much load a stage can carry depends entirely on what the application does.

StageSymptom that triggers itWhat it buysNew problem it brings
1 One serverThe beginningSimplicity. One thing to deploy, back up and debug.Application and database compete for the same CPU and memory.
2 Separate databaseThe two compete for resources, or you want to scale them differentlyEach can be sized for its own workload.A network hop on every query.
3 Load balancerApplication CPU is the limit, or a deploy or crash takes the site downMore capacity and no single application server to lose.Servers must be stateless. Deployments become rolling.
4 Cache and CDNThe same data is read again and again. Static files use your bandwidth.Most reads never touch the database. Files are served near the user.Stale data and cache invalidation.
5 Read replicasRead queries saturate the database even with a cache. You need a standby.Read capacity that grows with the number of replicas, and a machine ready to take over.Replicas lag. A user may not see their own write.
6 Queue and workersSome requests are slow or bursty: sending email, resizing images, calling a partnerFast responses, and work that survives a spike by waiting.Work happens later and may happen twice.
7 Partitioned dataWrites or data volume exceed one database serverWrite capacity and storage that grow with the number of partitions.Queries across partitions, rebalancing, uneven partitions.
8 More regionsUsers far away are slow. A whole data center failing is unacceptable. Law requires local storage.Low latency everywhere and survival of a regional outage.Data in several places must be reconciled. Everything costs more.

Three observations about this sequence are worth more than the sequence itself.

Each stage removes one bottleneck and reveals the next. Adding application servers in stage 3 does not make the system ten times faster. It moves the limit to the database. This is why you measure before each step: the purpose is always to relieve the current constraint, and there is only ever one of those at a time.

The cheap steps come first. Stages 2 to 4 are routine and reversible, and a managed cloud service provides each of them in an afternoon. Stage 5 introduces the first real consistency problem. Stages 7 and 8 change how every query is written and are hard to undo. The cost rises steeply toward the end, which is the argument for getting everything possible out of the earlier stages.

Every stage adds a way to be wrong. Look at the last column. Stale caches, lagging replicas, duplicate messages and cross-partition queries are what the middle of this book is about. Scalability is bought with complexity, and each purchase should be forced by evidence.

Reads, writes and storage scale differently

The estimate in separated reads from writes for a reason. They are relieved by different techniques, and a technique that helps one often hurts the other.

If the pressure is on…These helpBecause
ReadsCaching, CDN, read replicas, indexes, precomputed viewsA read can be answered from any copy, so you add copies.
WritesPartitioning, queues that absorb bursts, batching, append-only storageA write must reach the authoritative copy, so you split the data so that there are several authoritative copies of different parts.
Data volumePartitioning, object storage for large items, moving old data to cheaper tiers, deletion policiesNo machine holds everything, so you divide it and stop paying top price for what is rarely read.
Open connectionsEvent-driven servers, connection pooling, dedicated gateway serversEach connection costs memory even when idle.

Reads are the easy case, and most systems are read-heavy, which is fortunate. Copies are cheap to add, and the only cost is that a copy may be slightly out of date. Writes are the hard case. Every extra index, replica and cached view that speeds up reads is one more thing each write has to update, so the techniques in the first row make the second row worse. A design has to decide which side it favors, and the read-to-write ratio from the estimate is what decides it.

Three directions of scaling out

“Add more machines” can mean three different things. Martin Abbott and Michael Fisher describe them as three axes of a cube, a model that helps when deciding what kind of split a problem calls for.

Why twice the servers is not twice the capacity

Linear scaling is the ideal, and real systems fall short of it for two reasons that can be stated exactly.

The first is that some part of the work cannot be spread out. However many application servers you add, every write still goes through the one primary database. Every request still takes the same lock, or reads the same configuration, or passes through the same network link. Amdahl’s law, stated by Gene Amdahl in 1967, gives the consequence. If a fraction p of the work can be done in parallel and the rest cannot, then with n servers the best possible speed-up is:

speed-up = 1 ÷ ( (1 − p) + p ÷ n )

The lesson is that the serial fraction decides everything at scale. A system in which 95% of the work spreads perfectly can never run more than 20 times faster than one server, and reaches only three-quarters of that with 64 of them. Finding and shrinking the shared part, which is usually a database, a lock or a coordinator, is worth more than adding machines.

The second reason is worse. Machines that share work have to talk to each other to stay consistent, and the amount of talking grows faster than the number of machines. Neil Gunther’s Universal Scalability Law adds this cost to Amdahl’s formula and predicts something Amdahl’s law does not: past a certain size, adding a machine makes the system slower, because the extra coordination costs more than the extra capacity is worth. Anyone who has watched a database cluster get slower as nodes were added has seen that curve.

Both laws point to the same design goal. Capacity grows with machines only when the machines can work without consulting each other. Stateless servers manage it. Partitions that never need each other’s data manage it. Anything that requires global agreement on every operation does not, and should be kept small and off the main path.

Elasticity and autoscaling

Load changes through the day and the week. A fleet sized for the evening peak sits mostly idle at four in the morning. Elasticity is the ability to add and remove capacity as load changes, and autoscaling is doing it automatically.

KindHow it decidesSuits
ReactiveA metric crosses a threshold: CPU above 60%, queue longer than 1,000 items, requests per server above a targetGradual, unpredictable changes
ScheduledThe clock: add servers at 08:00 on weekdaysRegular daily and weekly cycles
PredictiveA forecast from past traffic adds capacity ahead of the expected riseCycles that are regular, with some variation
Manual, ahead of an eventA person raises capacity before a launch, a sale or a broadcastKnown spikes that are too sudden for any of the above

Autoscaling is a control loop, and it has the weaknesses of one.

  • It reacts late. A new server takes from tens of seconds to several minutes to start, load its code and warm its caches. A spike that arrives in ten seconds is over, or has done its damage, before help arrives. This is why the threshold sits well below saturation, as the utilization curve in requires.
  • It can oscillate. Add servers, the metric drops, remove servers, the metric rises. Cool-down periods, and removing capacity more slowly than adding it, damp this.
  • It only helps the tier it controls. Fifty new application servers each open twenty database connections. PostgreSQL’s default limit is 100 connections. Scaling one tier can knock over the next, so limits and connection pooling have to be designed with the scaling policy.
  • Scaling in is harder than scaling out. Removing a server means first letting its in-flight requests finish and its long-lived connections move elsewhere. A server holding state cannot simply be switched off.

In production. Autoscaling protects you from gradual growth and from paying for idle machines. It does not protect you from a sudden surge, a retry storm or a dependency that has slowed down, and in the last case adding application servers makes things worse by sending more traffic at the struggling dependency. Keep a rate limit and a load-shedding policy as the backstop. Both are covered in .

Problems that appear only at scale

Some failure modes do not exist on one server and are routine on a hundred. They recur throughout the book, and it helps to know their names early.

  • Hot keys and skew. Dividing data evenly does not divide load evenly. One celebrity account, one viral post or one enormous customer can send most of the traffic to a single partition while the others idle. Scaling out helps the average and does nothing for the hottest item.
  • The thundering herd. When a popular cache entry expires, or a service comes back after an outage, every waiting client asks for the same thing at the same moment. The burst can be many times normal load and can knock the service down again.
  • Retry amplification. A struggling service fails some requests, clients retry, and the retries add load to the service that was already struggling. Across several layers that each retry three times, one user request can become dozens.
  • Fan-out. One action that touches many things, such as a post that must reach ten million followers, is cheap to ask for and expensive to carry out. The work is proportional to something other than the request rate.
  • Noisy neighbors. When many customers share machines, one customer’s heavy use degrades everyone else’s service unless isolation is designed in. See .
  • Operational scale. At a thousand servers, something is always broken. Deployment, configuration and monitoring have to be automated, and the system has to keep working while some of it is failing. That is the subject of the next chapter.

Connects to

  • Economics. Scaling decisions are cost decisions. A larger machine may be cheaper than the engineering time to distribute a system, and for a while it usually is. works through the comparison.
  • Organization design. The Y axis of the scale cube is also how teams are divided. Splitting a system by function and splitting an organization by function tend to happen together, as Conway’s law in Chapter 1 predicts.
  • Parallel computing. Amdahl’s law was written about processors inside one computer. It applies to servers in a data center, and to people on a project, for the same reason.
  • Low-level design. Statelessness is decided in code. A class that caches results in a static field, or a module that writes to a local temporary directory, is an architectural constraint however small it looks.

Key points

  • Scalability is about a specific dimension of load. Ask what grows, what you add in response, and what breaks first.
  • Scaling up is simple and goes further than expected. Scaling out has no ceiling and adds redundancy, at the cost of running a distributed system.
  • Scaling out requires stateless servers. Sessions, files, scheduled jobs, connections and counters all have to live somewhere shared.
  • Architectures grow in a typical order, each step triggered by a measured bottleneck and each bringing a new kind of problem.
  • Reads scale by adding copies. Writes and data volume scale by splitting the data. Helping one often hurts the other.
  • The work that cannot be shared sets the ceiling. Reduce shared state and coordination before adding machines.
  • Autoscaling handles gradual change and saves money. It reacts too slowly for sudden spikes.

Check yourself

An application is slow even when one person uses it on an otherwise idle server. Will adding servers behind a load balancer help?

No. That is a performance problem. Each request will be just as slow on any of the new servers. Find where the time goes within one request first: usually a missing index, a slow external call, or too much work done while the user waits.

You add a second application server and users start getting logged out at random. What happened, and what are the options?

Sessions are stored in each server’s memory, so a request that lands on the other server finds no session. The options are sticky sessions, a shared session store, or a signed token carried by the client. The last two keep the servers interchangeable.

A system’s read traffic has grown tenfold and writes have not changed. Which stage of growth applies, and which does not?

Caching and read replicas, stages 4 and 5. Partitioning the data is not called for, since it addresses write volume and data size and adds a great deal of complexity.

90% of a job can be parallelized. What is the largest speed-up possible, however many servers are used? How much do 8 servers give?

The limit is 1 ÷ (1 − 0.9) = 10 times. Eight servers give 1 ÷ (0.1 + 0.9 ÷ 8), which is about 4.7 times. To do better you must shrink the 10% that is serial.

Traffic doubles within fifteen seconds when a television advertisement airs. Your autoscaler adds servers when CPU passes 70%, and a server takes three minutes to become ready. What will happen, and what would you change?

The existing servers will be overloaded for about three minutes, which is long enough for timeouts, retries and possibly a cascade. The autoscaler is correct and too slow for this event. Since the time of the advertisement is known, raise capacity beforehand, and keep rate limiting and load shedding in place for surges that are not known in advance.
