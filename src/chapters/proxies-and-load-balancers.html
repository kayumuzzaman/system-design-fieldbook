Programs that stand in the middle

A proxy is a program that receives a request and makes a request of its own on behalf of whoever sent the first one. It is a client to one side and a server to the other. Which side it works for gives the two kinds their names.

A forward proxy sits with the clients and makes outbound requests for them. Companies use one to filter and log what leaves their network. In system design it appears as an egress proxy: all outbound calls from your services pass through one place that enforces a list of allowed destinations. That gives you a single, auditable exit and a stable source address to give to partners who restrict access by IP.

A reverse proxy sits with the servers and accepts inbound requests for them. Clients believe they are talking to the application. This is the kind that matters for most of this book, because it is a natural place to put everything that should happen to every request:

  • Load balancing: choosing which of many servers handles each request.
  • TLS termination: holding the certificates and doing the encryption ().
  • Routing: sending /api to one service and /images to another.
  • Caching and compression of responses.
  • Protection: limiting request rates and sizes, and keeping malformed traffic away from the application.
  • Hiding the layout: servers can be added, moved or replaced, and the address clients use never changes.

The names in this chapter (reverse proxy, load balancer, API gateway, ingress controller, service mesh sidecar) describe roles, and one piece of software often plays several. NGINX, HAProxy and Envoy can each act as any of them. Learn the roles and the vocabulary will stop being confusing.

What a load balancer is for

scaled the photo app by running many identical servers. A load balancer is what makes many servers look like one. It does four jobs, and spreading load is only the first.

  1. Spread work so that no server is overloaded while others are idle.
  2. Hide failures by noticing dead or sick servers and sending work elsewhere.
  3. Allow change by taking servers out of rotation gracefully, so deployments and scaling events do not drop requests.
  4. Provide one stable address in front of a set of servers that changes constantly.

The second and third jobs are where designs succeed or fail. A balancer that distributes load perfectly and handles failure badly will cause outages. One that distributes load crudely and handles failure well will not.

Layer 4 and layer 7

Load balancers are classified by the layer of the network stack at which they make decisions (the layers are in ). The two that matter are layer 4, the transport layer, and layer 7, the application layer.

A layer 4 load balancer works with TCP connections and UDP packets. When a connection arrives it picks a server, and from then on it forwards that connection’s packets to the same server. It never interprets the bytes. That makes it fast and cheap per connection, and it works for any protocol: HTTP, database traffic, game traffic, anything.

A layer 7 load balancer is a reverse proxy that understands the application protocol, almost always HTTP. It accepts the client’s connection, completes the TLS handshake, reads each request, and then makes its own request to a server over a separate connection. Because it sees requests, it can route by host name, path, header or cookie, retry a failed request on another server, add headers, and record a metric for every request.

The weakness of layer 4 is that it balances connections, and connections are not equal. Modern clients keep connections open and reuse them. One connection may carry a single request, and another may carry ten thousand. With HTTP/2 and gRPC, a calling service typically opens one connection and sends everything over it, so a layer 4 balancer sends all of that caller’s traffic to one server. The section on HTTP/2 below returns to this.

The rule of thumb: use layer 7 for HTTP traffic unless you have a reason not to, because per-request balancing, routing and retries are worth the cost. Use layer 4 for other protocols, for extreme volume, or as a first tier in front of the layer 7 proxies themselves.

Choosing a server

Given a request and a list of healthy servers, which one gets it? The common algorithms differ in how much they know about the servers’ current state.

AlgorithmHow it choosesGood atWeakness
Round robinEach server in turnSimple, even counts, no state to shareIgnores how busy servers are and how expensive requests are
Weighted round robinIn turn, in proportion to assigned weightsServers of different sizes, and shifting a small share of traffic to a new versionWeights are set by hand and go stale
RandomAny server, by chanceNothing to coordinateUneven in the short run

Two random choicesPick two at random, send to the less busyNearly as good as least connections, with far less coordinationSlightly worse than a perfect global view
HashingHash a key such as the user ID or URL to pick a serverSending the same key to the same server, which keeps caches warmPopular keys overload their server

How much do they differ? I simulated 20 servers at 80% utilization, with requests arriving at random and service times that vary. The setup is the same as the queueing model in .

Three lessons come out of this.

  • Knowing anything about load helps a great deal. Random assignment leaves some servers with queues while others sit idle. Its 99th percentile is more than four times that of least connections, on the same hardware and the same traffic.
  • Two random choices get most of the benefit. Checking two servers and taking the less busy cuts the tail to a third of the random value. Checking all twenty does better still, by a smaller step.
  • Round robin is better than random, because taking turns spaces out the arrivals at each server. It still cannot react to a server that is slow or to a request that is expensive.
Why two choices are used in practiceLeast connections looks best in a simulation with one balancer that knows everything. Real systems have many balancers, each with a partial and slightly stale view. If all of them send to the server that looked emptiest a moment ago, they overload it together. Choosing between two random candidates avoids that herd, which is why Envoy’s least-request policy and NGINX’s random two work this way.

Hashing, and why it needs to be consistent

Sometimes the goal is not even load but repeatability: the same user or the same URL should reach the same server, because that server has the relevant data cached in memory. Hashing a key and taking the remainder after dividing by the number of servers achieves this, until the number of servers changes. Then almost every key maps to a different server and every cache goes cold at once.

Consistent hashing is a family of schemes in which adding or removing one server out of n moves only about 1/n of the keys. Layer 4 balancers also rely on it so that every balancer in a fleet independently sends a given connection to the same server. Google’s Maglev is the best-known design. The technique matters even more for data storage, and explains it in full.

Common mistake. Least connections has a dangerous failure mode. A server that is broken and returns errors instantly finishes its requests faster than healthy servers, so it always has the fewest in progress, and the balancer sends it more and more traffic. One bad server can absorb most requests this way. The defense is to judge servers by errors as well as by load, which is the subject of the next section.

Health checks

A balancer can only hide failures it knows about. There are two ways it finds out.

Active checks. The balancer sends each server a probe on a timer, usually an HTTP request to a path such as /healthz, and expects a 200 within a time limit. Several consecutive failures mark the server unhealthy, and several successes bring it back. The thresholds prevent one lost packet from removing a server.

Passive checks. The balancer watches real traffic. A server that returns too many errors or timeouts is ejected for a while, then cautiously tried again. Envoy calls this outlier detection.

Use both. Active checks find a dead server even when there is no traffic, and detect it slowly: the time to notice is the interval multiplied by the failure threshold. With the Application Load Balancer’s defaults of a 30-second interval and 2 failures, a server can be dead for up to a minute while still receiving requests. Passive checks react within a few requests, and they catch a server that answers its health probe correctly while failing real work.

What the health endpoint should check

This looks like a detail and is one of the more consequential decisions in the chapter. It helps to separate two questions that are often merged.

  • Liveness: is this process broken in a way that only a restart will fix? The response to failure is to kill and replace it.
  • Readiness: should this instance receive traffic right now? It may be starting up, warming a cache, or shutting down. The response is to stop routing to it and leave it alone.

The tempting design is a deep health check that tests everything the server depends on: the database, the cache, other services. Consider what happens when the database has a 30-second problem. Every server’s check fails at the same moment. The balancer now sees no healthy servers, and what could have been 30 seconds of slow requests becomes a full outage, followed by a rush as every server returns at once.

A sounder rule is that a health check should report on the instance and nothing shared. Check that the process is up, has loaded its configuration, and can do its own work. A failure of a shared dependency is not something removing one server can fix, so handle it in the request path with timeouts and fallbacks ().

Balancers defend against this pattern by failing open: when all or most servers look unhealthy, they conclude that the health information is more likely wrong than the whole fleet, and send traffic anyway. AWS load balancers route to all targets when none pass their checks. Envoy does the same when fewer than half are healthy, by default, and calls it panic mode. Know which behavior your balancer has, because it decides what a bad health check does to you.

In production. Health checks create load of their own. With 10 balancer nodes checking 500 servers every 5 seconds, each server answers 2 probes a second, and the fleet answers 1,000. Keep the endpoint cheap, and never make it do work that scales with data size.

Removing a server without dropping requests

Servers leave rotation constantly: for every deployment, every scale-in and every hardware replacement. If a server is killed while it holds requests in progress, those requests fail. Connection draining is the procedure that avoids this, and it requires the balancer and the application to cooperate.

On the application side, this means handling the termination signal properly. Most platforms send SIGTERM, wait for a grace period, and then kill the process outright.

import { createServer } from "node:http";

let draining = false;

const server = createServer((req, res) => {
  if (req.url === "/ready") { res.writeHead(draining ? 503 : 200).end(); return; }
  if (draining) res.setHeader("Connection", "close");   // ask the caller to open a new connection elsewhere
  handle(req, res);
});
server.listen(8080);

process.on("SIGTERM", () => {
  draining = true;                              // step 1: readiness fails from now on

  setTimeout(() => {                            // step 2: give the balancer time to notice
    server.close(() => process.exit(0));        // steps 3 and 5: stop accepting, exit when requests finish
    server.closeIdleConnections();              // step 4
  }, 15_000);

  setTimeout(() => process.exit(1), 45_000).unref();   // hard limit, shorter than the platform's grace period
});

The wait before closing is the part people leave out. In any system where routing information spreads asynchronously, and Kubernetes is the usual example, the instruction to stop a server and the instruction to stop routing to it travel separately. For a short time after the signal arrives, balancers that have not yet heard the news still send requests. A server that stops listening at once refuses them. Continuing to serve for a few seconds while failing readiness closes that gap.

The balancer has its own setting for the same process. AWS calls it the deregistration delay, 300 seconds by default, which is how long a deregistered target is allowed to finish existing work. The opposite problem exists on the way in: a server that has just started has cold caches and an empty connection pool, and under least connections it looks like the emptiest server in the fleet. Slow start ramps a new server’s share of traffic up over a period instead of giving it a full share at once.

Session affinity

Session affinity, or sticky sessions, means sending all of one user’s requests to the same server. A layer 7 balancer does it by setting a cookie that names the server. A layer 4 balancer does it by hashing the client’s IP address.

The usual reason is a server that keeps session data in its own memory, and that reason is a design flaw being accommodated, as argued. Affinity has real costs:

  • Uneven load. Users differ enormously in activity, and the balancer can no longer move the heavy ones.
  • Failure loses the session. When the server dies, its users are logged out or lose their work.
  • Scaling is slow to take effect. New servers receive only new users. Existing users stay where they were.
  • IP hashing is unreliable. Thousands of users behind one corporate NAT share an address, and a phone changes address as it moves between networks.

Prefer to keep session state in a shared store or in a signed token, so that any server can handle any request. Affinity is legitimate when it is an optimization and not a requirement for correctness. Routing a user to the server that has their data cached is fine if a different server would produce the same answer more slowly. A WebSocket is sticky by nature for the life of its connection (), which is a property of the connection and needs no feature.

Who balances the balancer?

Putting one load balancer in front of twenty servers removes twenty single points of failure and adds one. The balancer has to be redundant too, and since it is the thing clients connect to, the methods differ from those used for the servers behind it.

  • An active and a standby sharing an address. Two balancers share a virtual IP address. One holds it and serves traffic, and the other watches. If the active one stops responding, the standby claims the address and traffic follows within a second or two. This is simple and wastes half the capacity.
  • Many active balancers behind the routers. Several balancers announce the same address to the network, and routers spread packets across them. This is equal-cost multipath routing (ECMP), the same idea as anycast in . Since the router may send different packets of one connection to different balancers after a change, the balancers use consistent hashing so that all of them pick the same server for a given connection.
  • DNS. Publish several addresses, one per balancer or per region, and remove the unhealthy ones. DNS is slow to react because of caching (), so it is the outermost layer and never the only one.

Large systems stack these, with a cheap, fast layer 4 tier spreading connections across a larger layer 7 tier that does the expensive per-request work.

If you use a cloud provider’s load balancer, this structure exists and is operated for you. A managed balancer is a fleet of nodes across several availability zones behind one DNS name. What remains your responsibility is registering targets in more than one zone and understanding the defaults. One worth knowing: AWS Network Load Balancer nodes send traffic only to targets in their own zone unless cross-zone balancing is turned on, so zones with unequal numbers of servers receive unequal load per server.

Details that cause incidents

Most real trouble with load balancers comes from a handful of specifics that are rarely mentioned in an overview.

The client’s address disappears

Behind a proxy, every connection the application receives comes from the proxy. Rate limiting, audit logs and location lookups all need the real client address. A layer 7 proxy passes it along in a header:

GET /api/photos HTTP/1.1
Host: api.example.com
X-Forwarded-For: 203.0.113.7, 198.51.100.20
X-Forwarded-Proto: https

Each proxy appends the address it received the request from, so the list reads from the original client on the left to the most recent proxy on the right. The trap is that the client controls the starting value. Anyone can send a request that already contains X-Forwarded-For: 1.2.3.4, and your proxy will append to it. Code that trusts the leftmost entry can be told any address at all.

The correct reading is from the right. Count back past the proxies you operate, and the entry your own outermost proxy added is the one you can trust. Everything to its left is a claim. For layer 4 balancers, which cannot add headers, the equivalent is either preserving the original source address in the packets or the PROXY protocol, a short preamble sent at the start of each connection that the server must be configured to expect.

Timeouts that disagree

A balancer keeps idle connections to its servers open for reuse, and both ends have a timer for closing them. If the server’s timer is shorter, there is a moment when the server has decided to close a connection and the balancer, not yet aware, sends a request on it. The request fails, and the client receives a 502 Bad Gateway that appears in no application log, because the application never saw the request.

These failures are rare, random and unrelated to load, which makes them hard to diagnose. The rule that prevents them is that the side that receives requests should keep idle connections open longer than the side that sends them. Node’s HTTP server closes idle connections after 5 seconds by default, and an Application Load Balancer holds them for 60, so this pairing produces the problem unless it is changed:

server.keepAliveTimeout = 65_000;   // longer than the balancer's 60-second idle timeout

The same reasoning applies to every hop. Request timeouts should get shorter as you go deeper into the system, so that the outer layers do not give up and retry while the inner ones are still working.

HTTP/2, gRPC and one very busy server

HTTP/2 sends many requests concurrently over a single long-lived connection (), and gRPC is built on it. Put a layer 4 balancer between two services using gRPC and it will balance the connections, of which there may be one per calling instance, held for hours. Requests go wherever those few connections happened to land. New servers added during a traffic spike receive nothing.

There are three fixes: balance at layer 7 with a proxy that understands HTTP/2 and distributes individual requests; have the client hold connections to every server and balance for itself; or set a maximum connection age on the servers so that connections are regularly closed and re-established. The first two are the real answers. The third is a partial remedy that is simple to apply.

Retries multiply load

A layer 7 balancer can retry a failed request on another server, which hides individual failures well. Two limits are essential. Retry only requests that are safe to repeat (). And cap retries as a share of total traffic, because when a whole service is overloaded, retrying every failure doubles the load on it at the worst possible moment.

Running out of ports

A proxy opens connections to its servers from its own address, and each connection needs a distinct source port. Between one proxy address and one server address and port there are roughly 64,000 available. A proxy that opens a new connection for every request, to a small number of servers, can run out. Connections then fail even though every machine has spare CPU and memory. Reusing connections, as the configuration below does with keepalive, is the first fix, and adding addresses is the second.

upstream photo_api {
    least_conn;
    server 10.0.1.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.12:8080 max_fails=3 fail_timeout=10s;
    server 10.0.1.13:8080 backup;
    keepalive 64;                       # idle connections kept open to the servers
}

server {
    listen 443 ssl;
    http2 on;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://photo_api;
        proxy_http_version 1.1;
        proxy_set_header Connection "";                 # needed for connection reuse
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;
        proxy_next_upstream error timeout http_503;     # retry these on another server
    }
}

Most of this chapter is visible in those twenty lines: the algorithm, passive health checks through max_fails, a standby server, connection reuse, forwarding headers, timeouts and limited retries.

Balancing without a box in the middle

Inside a data center, a dedicated balancer between every pair of services adds a network hop, a cost and a component that can fail. The alternative is client-side load balancing. The calling service obtains the list of healthy instances from a registry and chooses among them itself, using the same algorithms as above. gRPC clients can work this way.

The cost is that every client, in every language you use, needs this logic. A service mesh removes that cost by putting the logic in a small proxy that runs alongside each service instance, or once per machine, and handles its network calls. Applications make plain requests, and the mesh proxies do the balancing, retries, encryption and metrics. examines when that is worth its considerable complexity.

API gateways

An API gateway is a reverse proxy placed at the outer boundary of a system that takes on work specific to APIs. It became common with microservices, for a simple reason: if twenty services each implement authentication, rate limiting and request logging, they will do it in twenty slightly different ways. A gateway does these things once, in front of all of them.

ConcernWhat the gateway doesMore in
AuthenticationValidates tokens or API keys and rejects anonymous traffic before it reaches a service
Rate limiting and quotasLimits requests per client, per key or per plan
RoutingMaps public paths and versions to internal services
Validation and limitsRejects oversized or malformed requests early
TranslationAccepts REST from outside and calls gRPC inside, for example
ObservabilityEmits uniform logs, metrics and trace IDs for every call

A gateway can also aggregate: accept one request from a client and call several services to build the response, saving a mobile app several round trips. When a separate gateway of this kind is built for each kind of client, with one for the mobile app and one for the web app, the pattern is called a back end for a front end (BFF). Each one is shaped to what its client needs and is usually owned by the team that builds that client.

Gateways attract two problems. The first is that logic accumulates in them. A rule added to the gateway is easier than a change to a service, and a gateway that started as a router ends up knowing about discounts and user types, at which point every team must change it to ship anything. Keep it to concerns that apply to all traffic, and keep business rules in services. The second is that it is on the path of every request, so it needs the redundancy described earlier, and its own latency is added to everything.

In an interview. Draw a load balancer wherever there is more than one instance of something, and say what kind: “a layer 7 load balancer here, terminating TLS and routing by path”. Mention health checks and that the balancer itself is redundant. If you add an API gateway, name the two or three things it does in your design. A box labeled “gateway” with no stated purpose invites questions you may not want.

What people run, as of October 2026

  • Open-source proxies. NGINX and HAProxy are the long-established choices, configured with files. Envoy was designed to be reconfigured continuously through an API with no restarts, and is the foundation of most service meshes and many gateways. Traefik and Caddy aim at simpler setups with automatic certificates.
  • Managed cloud balancers. Every major provider offers layer 4 and layer 7 balancers as services. For most teams this is the right default, since the redundancy and scaling of the balancer become someone else’s job.
  • Large-scale layer 4. Google’s Maglev and Meta’s Katran are software balancers on ordinary servers that use ECMP and consistent hashing as described above. Katran is open source.
  • Kubernetes. The original Ingress API is frozen and the Gateway API is its successor, with richer routing and a cleaner split between the people who run the infrastructure and those who define routes. The community Ingress NGINX controller, for years the most widely used, was retired in March 2026 and receives no further fixes. New clusters should start with a Gateway API implementation.
  • Gateways for AI traffic. A recent category of API gateway sits in front of language model providers and applies the usual ideas with different units: limits counted in tokens instead of requests, routing between providers, and fallback when one is unavailable. covers this.

Common mistakes

  • A single load balancer. The component added to remove single points of failure becomes one.
  • Deep health checks. A shared dependency blinks and every server is removed at once.
  • No draining. Every deployment produces a burst of failed requests that is written off as normal.
  • Trusting the leftmost X-Forwarded-For entry. Clients choose their own IP address, which defeats rate limits and corrupts audit logs.
  • Server idle timeout shorter than the balancer’s. Occasional unexplained 502 errors.
  • Layer 4 balancing for gRPC. One server takes most of the traffic and scaling out has no effect.
  • Sticky sessions to work around server-side state. Uneven load, sessions lost on failure and slow scaling.
  • Unlimited retries at the balancer. An overloaded service receives double the traffic.
  • Business logic in the gateway. Every team is blocked on one shared component.

Key points

  • A reverse proxy accepts requests on behalf of servers. Load balancers, API gateways and mesh proxies are all reverse proxies with a particular job.
  • Layer 4 balances connections without reading them. Layer 7 terminates TLS and balances individual requests, and can route, retry and measure them.
  • Any algorithm that uses load information beats one that does not. Choosing the less busy of two random servers is robust and close to the best.
  • Combine active and passive health checks. Make the health endpoint report on the instance itself and not on shared dependencies.
  • Drain before stopping: fail readiness, keep serving briefly, finish requests in progress, then exit.
  • The balancer must be redundant: a standby with a shared address, many nodes behind ECMP, or a managed service that does this for you.
  • Read X-Forwarded-For from the right, and keep server idle timeouts longer than the balancer’s.
  • An API gateway centralizes authentication, rate limiting and routing. Keep business logic out of it.

Check yourself

Two services communicate with gRPC through a layer 4 load balancer. You double the number of servers and the load on the original ones barely changes. Why?

gRPC uses long-lived HTTP/2 connections, and a layer 4 balancer chooses a server only when a connection is opened. The existing connections stay on the original servers and carry all the requests. Balance at layer 7, balance in the client, or limit connection age so that connections are re-established.

Your health endpoint queries the database. The database becomes slow for a minute. What happens, and what would be better?

Every server’s health check times out at the same time, so the balancer sees no healthy servers. Depending on the balancer it either rejects all traffic or fails open and sends it everywhere. Either way the health check added nothing, since removing servers cannot fix a shared database. The endpoint should check only the instance itself, and database trouble should be handled in the request path with timeouts and fallbacks.

Why can “least connections” make an outage worse when one server starts returning errors immediately?

A server that fails instantly completes its requests faster than healthy servers, so it always has the fewest in progress and the algorithm keeps choosing it. It draws in a growing share of traffic and fails all of it. Passive health checks that eject servers with high error rates prevent this.

A request arrives with the header X-Forwarded-For: 10.9.9.9, 203.0.113.7, 198.51.100.20, and you operate two proxies in front of the application. Which address is the client’s?

Count from the right. The application received the connection from your inner proxy. The rightmost entry, 198.51.100.20, was appended by that inner proxy and is the address of your outer proxy. The entry before it, 203.0.113.7, was appended by your outer proxy and is the address that actually connected to you, so it is the one to use. The leftmost entry was supplied by the client and may be invented.

Users occasionally receive a 502 error, about once in several thousand requests, with nothing in the application logs. What do you check first?

Idle connection timeouts. If the application closes idle keep-alive connections sooner than the balancer does, the balancer will sometimes send a request on a connection the server is in the middle of closing. Set the server’s keep-alive timeout longer than the balancer’s idle timeout.

What does an API gateway add that a plain load balancer does not, and what should it not contain?

It applies policy that is specific to APIs and common to all services: authentication, rate limits and quotas per client, request validation, version routing and uniform logging. It should not contain business rules, because then every product change requires changing a component that all teams share.
