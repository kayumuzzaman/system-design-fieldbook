Exact answers that cost too much

Three questions come up again and again in large systems. Each has an obvious exact answer, and each exact answer needs memory in proportion to the amount of data.

QuestionExact methodCost at scaleApproximate structureIts cost

The structures on the right are called probabilistic data structures, or sketches. They do not store the items. They store a small summary from which an answer can be estimated. The answer is sometimes wrong, and the important word is how. Each structure errs in one known direction and by an amount you choose in advance by deciding how much memory to give it.

That makes them engineering tools and not gambles. A filter that says “definitely not present” or “probably present”, and is never wrong about the first, can be put in front of an expensive lookup with no risk to correctness. A count that is within 1% is as good as an exact one on a dashboard. The skill is in matching the kind of error to a place where it does no harm.

All of them rest on the hash functions introduced in : a function that turns any item into a number that looks random and is always the same for the same item.

Bloom filters

A Bloom filter answers one question about a set: is this item in it? It was described by Burton Bloom in 1970 and is the most widely used structure in this chapter.

The filter is an array of bits, all starting at 0, and a small number of hash functions. To add an item, hash it with each function to get that many positions in the array, and set those bits to 1. To test an item, hash it the same way and look at the same positions. If any of them is 0, the item was never added, because adding it would have set that bit. If all are 1, the item was probably added.

The fourth lookup in shows the one mistake a Bloom filter can make. The bits that “dee” maps to were all set by other items, so the filter reports it as possibly present. This is a false positive. The opposite mistake, a false negative, cannot happen: an item that was added always finds its own bits set.

So the two answers have different strengths.

  • “No” is certain. The item is not in the set.
  • “Maybe” means the item is in the set, or it is one of the small fraction of absent items that collide.

Every good use of a Bloom filter is arranged so that the certain answer is the common and valuable one, and the uncertain answer leads to a check that would have happened anyway.

Choosing the size

Two numbers decide how often false positives happen: how many bits the filter has for each item stored, and how many hash functions it uses. The formulas are short.

bits per item = −ln(p) ÷ (ln 2)² ≈ 1.44 × log₂(1 ÷ p) hash functions = bits per item × ln 2 ≈ 0.69 × bits per item p is the false positive rate you will accept, as a fraction

For a 1% rate that gives 9.6 bits per item and 7 hash functions. Two things about this result are worth remembering. First, the size of the items does not appear. A 2,000-character URL and a 4-byte number each cost the same ten bits, because the filter stores neither. Second, accuracy is cheap. Each additional 4.8 bits per item divides the false positive rate by ten.

The filter needs 1.2 MB, about 7.49% of the 16 MB the items themselves occupy. It never misses an item that is present, and wrongly reports an absent one as possibly present about once in 100 lookups. Halving that error rate costs about 1.44 more bits per item.

The number of items is a promise you make when you create the filter. If more arrive than it was sized for, nothing breaks and no error is raised. The bits simply fill up, and the false positive rate climbs.

A Bloom filter cannot be enlarged afterward, because it does not hold the items needed to fill a bigger one. The choices are to rebuild it from the original data, or to use a scalable Bloom filter, which adds a second, larger filter when the first is full and checks both. Redis does the latter automatically unless told not to.

In code

A working filter is a few dozen lines. The only subtlety is producing several hash values cheaply. A standard technique computes two hashes and combines them, taking the first plus one, two, three times the second, which behaves as well as fully independent functions.

// A small non-cryptographic hash: FNV-1a, then a mixing step so that similar
// strings land far apart. The seed gives independent variants.
function hash32(text: string, seed: number): number {
  let h = (0x811c9dc5 ^ seed) >>> 0;
  for (let i = 0; i < text.length; i++) {
    h ^= text.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  h ^= h >>> 16; h = Math.imul(h, 0x85ebca6b);
  h ^= h >>> 13; h = Math.imul(h, 0xc2b2ae35);
  return (h ^ (h >>> 16)) >>> 0;
}

class BloomFilter {
  private readonly bits: Uint8Array;
  readonly size: number;        // m: number of bits
  readonly hashes: number;      // k: bits set per item

  constructor(expectedItems: number, falsePositiveRate: number) {
    this.size = Math.ceil(-expectedItems * Math.log(falsePositiveRate) / (Math.LN2 * Math.LN2));
    this.hashes = Math.max(1, Math.round((this.size / expectedItems) * Math.LN2));
    this.bits = new Uint8Array(Math.ceil(this.size / 8));
  }

  // Two real hashes are enough: position i is h1 + i * h2.
  private positions(item: string): number[] {
    const h1 = hash32(item, 0);
    const h2 = (hash32(item, 0x9e3779b9) | 1) >>> 0;  // odd, and kept unsigned
    const out: number[] = [];
    for (let i = 0; i < this.hashes; i++) out.push((h1 + i * h2) % this.size);
    return out;
  }

  add(item: string): void {
    for (const p of this.positions(item)) this.bits[p >> 3] |= 1 << (p & 7);
  }

  // false: definitely never added. true: probably added.
  mightContain(item: string): boolean {
    return this.positions(item).every((p) => (this.bits[p >> 3] & (1 << (p & 7))) !== 0);
  }
}

const taken = new BloomFilter(1_000_000, 0.01);        // about 1.2 MB
taken.add("ana");
taken.mightContain("ana");                             // true
taken.mightContain("zed");                             // false, or true about 1 time in 100

Filled with a million keys and tested against half a million keys that were never added, this code reported 1.0% of them as possibly present and missed none of the real ones. Filled with two million, it reported 15.7%, as the curve in predicts.

The method is named mightContain on purpose. Calling it contains invites the next reader to trust a “yes”.

Common mistake. A weak hash function. The formulas assume hash values spread evenly. The first version of the code above lacked the mixing step, and on keys such as user-1, user-2 its measured error rate was half the predicted one, which looks like good news and is a sign that the positions were not random. With differently shaped keys the same flaw raises the error rate. Use a well-tested hash such as MurmurHash3 or xxHash, as the libraries do, and measure the false positive rate on your own keys.

Where Bloom filters are used

The pattern is always the same: a small filter in memory stands in front of something slow, and turns most pointless trips into an immediate “no”.

  • Storage engines. An LSM tree may hold a key in any of several files. Each file carries a Bloom filter of its keys, so a read skips the files that cannot contain the key (). RocksDB’s commonly used setting of ten bits per key gives about a 1% false positive rate. Cassandra, HBase and most other LSM stores do the same.
  • Caches in front of databases. Requests for keys that do not exist can never be cache hits, so each one reaches the database (). A filter of the keys that do exist rejects most of them first.
  • Content delivery. Akamai found that in one group of servers about three-quarters of 400 million objects were requested only once in two days. Writing those to disk was wasted effort. With a Bloom filter remembering which objects had been requested before, servers cached an object only on its second request. Disk writes fell by 44%, and the share of bytes served from cache rose from 74% to 83%, because popular objects were no longer pushed out by ones nobody would ask for again.
  • “Is this name taken?” A sign-up form can check a filter of existing usernames as the user types. “No” means the name is free. “Maybe” means ask the database.
  • Crawlers and pipelines. A web crawler keeps a filter of URLs it has already fetched (). Here a false positive means a page is wrongly skipped, which a crawler can tolerate.
  • Joins across machines. Before shipping a large table across the network to be joined with a small one, a query engine can send a Bloom filter of the small table’s keys and have the other side drop rows that cannot match.

The crawler example shows that the direction of the error has to be thought through for each use. In the cache example a false positive costs one unnecessary database query. In the crawler it costs a missed page. In a system that blocks sign-ups from a list of banned email addresses, it would turn away about one innocent person in a hundred, which is not acceptable unless a “maybe” is followed by an exact check.

In production. A filter is a cache of knowledge about a set, and it goes stale like any cache. If a username is added to the database and not to the filter, the filter now gives a false “no”, the one answer it was supposed to never get wrong. Either update the filter in the same code path as the write, or treat it as a hint and let a unique constraint in the database make the final decision. Always do the second for anything that must be unique.

Deleting, and newer filters

You cannot remove an item from a Bloom filter. Clearing its bits would also clear them for every other item that shares them, creating false negatives. Where the set shrinks as well as grows, there are three options.

  • Rebuild periodically. Create a fresh filter from the current data and swap it in. This is what LSM engines do naturally: each file’s filter is written once and discarded with the file.
  • Counting Bloom filter. Replace each bit with a small counter, usually four bits. Adding increments the counters and deleting decrements them. It uses four times the memory, and deleting an item that was never added corrupts it.
  • Cuckoo filter. A different design that stores a short fingerprint of each item in one of two possible slots. It supports deletion, and its authors showed that it needs less space than a Bloom filter when the target false positive rate is below about 3%. Insertion can fail when the filter is nearly full.

Newer static filters, such as the xor filter and the ribbon filter that RocksDB offers, use around 30% less memory than a Bloom filter for the same error rate, at the price of more work to build. They suit data that is written once, which is exactly the case of an LSM file.

Counting distinct items with HyperLogLog

How many different users were active today? How many distinct IP addresses hit this endpoint? How many unique search queries were there this month? These are cardinality questions, and the exact method is to remember every item seen. For a hundred million users that is hundreds of megabytes for each count you want, and a product wants many: per day, per country, per feature.

HyperLogLog, published by Philippe Flajolet and colleagues in 2007, estimates the count from a fixed, tiny amount of memory. The idea rests on one observation about random bits. If you flip coins and write down the results, a sequence that begins with three tails in a row is unusual: it happens one time in eight. If someone tells you only that the longest run of tails at the start of any of their sequences was ten, you can guess they produced about a thousand sequences, because a run that long turns up about once in 1,024 tries.

A hash function turns each item into such a sequence of random-looking bits. HyperLogLog remembers only the longest run of leading zeros it has seen. To make the guess stable, it splits the items among many small registers using the first few bits of the hash, keeps a longest run for each, and combines them with a particular kind of average.

Three properties follow from this design.

  • Duplicates are free. The same item always produces the same hash, so adding it again changes nothing. The structure counts distinct items without ever recording which ones it has seen.
  • The size is fixed. It depends on the number of registers, not on the number of items. Counting a thousand items and counting a billion use the same memory.
  • The error is known. With m registers the typical error is 1.04 ÷ √m.

Redis uses 16,384 registers: at most 12 KB for each count, a standard error of 0.81%, and room for more distinct items than any system will see. “Standard error” means that about two estimates in three fall within 0.81% of the truth and nearly all within three times that. For a million real users, expect an answer between about 992,000 and 1,008,000 most of the time. Halving the error takes four times the memory, so there is little point in chasing precision this way. If you need the exact number, you need a different tool.

Merging: the property that matters most

The last two commands show why HyperLogLog is so useful in distributed systems. Two sketches can be combined into one by keeping the larger value of each register, and the result is identical to the sketch you would have had if a single machine had seen all the items.

Distinct counts do not add up. The number of unique visitors this week is not the sum of the seven daily numbers, because many people visit on several days. With exact sets, answering for an arbitrary week means going back to the raw data. With sketches, you store one 12 KB sketch for each day, or each hour, or each hour for each country, and merge whichever ones a query covers. The same holds across machines: each shard builds its own sketch and a coordinator merges them. This is how analytical databases compute approximate distinct counts over data spread across hundreds of nodes.

The limits are these.

  • No membership. It cannot tell you whether a particular user was counted.
  • No removal. You cannot subtract yesterday’s visitors from a weekly sketch. Keep the daily sketches and merge a different set.
  • Weak intersections. “How many users did both A and B?” can be estimated as count(A) + count(B) − count(A or B), but the errors of three estimates combine. When the overlap is small compared with the sets, the result is unreliable.

You rarely implement HyperLogLog yourself. It is built in: PFCOUNT in Redis, the cardinality aggregation in Elasticsearch and OpenSearch, APPROX_COUNT_DISTINCT in BigQuery, Snowflake and Spark, approx_distinct in Trino, and uniqCombined in ClickHouse. Most use a refined version, often called HyperLogLog++, that is more accurate for small counts. Elasticsearch, for example, counts almost exactly up to a threshold you set, 3,000 by default, and estimates beyond it.

In an interview. Whenever a design needs “unique” something at scale, such as unique viewers of a video or daily active users, say that exact counting needs a set per counter, and offer HyperLogLog: “about 12 KB per counter, under 1% error, and mergeable across shards and days”. Then say when it is not acceptable: anything billed or audited needs exact counts from the source data.

Counting frequencies with a count-min sketch

The third question is how many times each item has appeared: views per photo, requests per IP address, occurrences of each search term. The exact answer is a map from item to counter. That works until the number of distinct items is huge, or until you need such a map for every minute of the day.

A count-min sketch, introduced by Graham Cormode and S. Muthukrishnan in 2003, uses a fixed grid of counters instead. Each row has its own hash function. To record an item, hash it once for each row and add one to the counter it lands on in that row. To ask how often an item has appeared, read its counter in each row and take the smallest.

The error again runs one way. Different items share counters, and sharing can only add. So the estimate is never below the true count and is sometimes above it. Taking the minimum across rows picks the counter with the fewest unwanted additions.

The two dimensions control two different things. Width sets how large the overestimate can be, and depth sets how sure you are of staying within it.

width = e ÷ ε the overestimate is at most ε × (total events counted) depth = ln(1 ÷ δ) with probability at least 1 − δ ε = 0.001 and δ = 0.01: width 2,719, depth 5, which is 13,595 counters or about 54 KB
class CountMinSketch {
  private readonly rows: Uint32Array[];

  constructor(private readonly width: number, depth: number) {
    this.rows = Array.from({ length: depth }, () => new Uint32Array(width));
  }

  add(item: string, count = 1): void {
    this.rows.forEach((row, i) => { row[hash32(item, i * 0x9e3779b9) % this.width] += count; });
  }

  // Never less than the true count. Collisions can only push it up.
  estimate(item: string): number {
    return Math.min(...this.rows.map((row, i) => row[hash32(item, i * 0x9e3779b9) % this.width]));
  }
}

const views = new CountMinSketch(2719, 5);             // 13,595 counters, about 54 KB
views.add("photo-17");
views.estimate("photo-17");                            // at least 1

Notice what the error is measured against: the total number of events, not the item’s own count. This decides what the sketch is good for. In a test of this code with one million views spread unevenly over 157,000 photos, the most viewed photo had 130,641 real views and an estimate of 130,837, an error of 0.15%. A photo viewed once had an estimate of about 170. Both errors are within the promised 1,000. One is negligible and the other is useless.

A count-min sketch is therefore a tool for finding and measuring the large items in a stream. It says nothing reliable about the small ones.

Heavy hitters and top-k

The items that dominate a stream are called heavy hitters, and finding them is the usual reason to count frequencies at all: trending searches, the most viewed photos this hour, the IP addresses sending the most requests, the keys receiving the most traffic.

The sketch alone cannot list them, since it does not store item names. The common arrangement pairs it with a small list of the current top candidates. For each event, update the sketch, read the item’s new estimate, and if it is larger than the smallest entry in the list, put the item in the list in its place. Memory stays fixed however many distinct items go by. Other algorithms, such as Space-Saving, keep only the list and replace its smallest entry on each miss. Redis provides a ready-made top-k structure built on a similar idea.

Uses in system design include these.

  • Hot key detection. A cache or database node tracks its most requested keys so that they can be split, replicated or cached locally ().
  • Abuse detection. Identify the clients sending the most requests without keeping a counter for every client that ever connects ().
  • Trending lists. Count per time window, then compare windows to find what is rising.
  • Cache admission. Some caches keep a compact frequency sketch of recent requests and admit a new entry only if it has been requested more often than the entry it would evict.

Results near the bottom of a top-k list are approximate. If the tenth and eleventh items have nearly equal counts, either may appear. For a trending list that is fine. For a prize draw it is not.

Percentiles from a summary

Percentiles were introduced in as the right way to describe response times. Computing one exactly means sorting every measurement. A service handling 10,000 requests per second produces 864 million measurements a day, on many servers, and nobody keeps them all.

There is a second problem, the same one as with distinct counts. Percentiles cannot be combined. The 99th percentile of a service is not the average of each server’s 99th percentile, and the 99th percentile for an hour is not the average of sixty one-minute values. A dashboard that averages percentiles shows a number with no meaning. What can be combined is a summary of the distribution, from which a percentile is then read.

All four can be merged, a few kilobytes in size. This is the machinery under the latency charts in monitoring systems (): each server records a histogram or sketch, and the monitoring system merges them across servers and time before computing a percentile. Elasticsearch’s percentile aggregation uses t-digest by default, Redis includes it as a data type, and Prometheus uses bucketed histograms.

Common mistake. Letting each server compute its own 99th percentile and then averaging them, or averaging per-minute percentiles into an hourly one. If one server out of ten is slow, the average hides it. Export the histogram or sketch, merge those, and compute the percentile last.

Similarity, and sampling

Two more ideas appear often enough to recognize.

Is this nearly the same as something I already have? Exact duplicates are found by comparing hashes. Near duplicates, such as the same article with a different advertisement or a copied essay with a few words changed, need a measure of similarity, and comparing every pair of documents is impossible at scale. MinHash reduces each document to a short signature of a few hundred numbers, built so that the fraction of positions at which two signatures agree estimates how much the documents overlap. SimHash reduces each document to a single 64-bit fingerprint in which similar documents differ in only a few bits. Google described using SimHash to find near-duplicate pages across a crawl of eight billion. Both are forms of locality-sensitive hashing: hashing designed so that similar inputs collide, the opposite of an ordinary hash. The approximate nearest-neighbor indexes behind vector search () pursue the same goal by other means.

Can I keep a fair sample of a stream whose length I do not know? Reservoir sampling keeps a fixed number of items, say a thousand, such that at every moment each item seen so far has had the same chance of being in the sample. Keep the first thousand. For item number n after that, keep it with probability 1,000 ÷ n, replacing a randomly chosen member of the sample. It is how a tracing or logging system can keep a representative thousand requests from a day of billions.

Before reaching for any of them, ask whether the exact structure is affordable. A million user IDs in an ordinary set take perhaps 50 MB. That fits in memory on any server, gives exact answers, supports deletion and can list its members. Approximation earns its place when the exact structure would not fit, when there are a great many of them, or when results from many machines must be combined.

Then ask what happens when the answer is wrong.

  • Acceptable: dashboards, trend detection, capacity planning, skipping work that would have found nothing, deciding what to cache.
  • Acceptable with an exact check behind it: uniqueness tests, deduplication, blocklists. The sketch handles the common case and the database confirms the rest.
  • Not acceptable: billing, account balances, quotas that customers pay for, legal or audit counts, and any place where a single wrong answer harms a person.

Finally, consider who controls the input. Someone who knows your hash function can construct items that collide on purpose, filling a Bloom filter with false positives or inflating a counter. Where the items come from untrusted users and the stakes justify it, use a hash function with a secret key.

Key points

  • Probabilistic structures trade a small, chosen error for memory that is smaller by orders of magnitude.
  • Know the direction of the error. A Bloom filter gives false positives and never false negatives. A count-min sketch overestimates and never underestimates. HyperLogLog can be off either way by about 1%.
  • A Bloom filter needs about 10 bits per item for a 1% false positive rate, whatever the size of the items, and 4.8 more bits for each further factor of ten.
  • Filters degrade quietly when overfilled and cannot be enlarged or have items removed. Plan for growth and rebuilding.
  • HyperLogLog counts distinct items in a fixed 12 KB with under 1% error.
  • Distinct counts and percentiles cannot be added or averaged. Sketches can be merged, across machines and across time, and that is their main value in distributed systems.
  • Count-min sketches and top-k structures are accurate for the heavy hitters and unreliable for rare items.
  • Use an exact structure when it fits, and always when the number is billed, audited or decides something for a person.

Check yourself

A Bloom filter says a key is present. Another says a different key is absent. Which answer can you rely on, and why?

The “absent” answer. Adding an item sets all of its bits, so finding any of them at 0 proves it was never added. “Present” only means all the bits are 1, which other items may have caused. With a filter sized for 1%, about one absent item in a hundred gets that answer.

You need a Bloom filter for 50 million keys with a 0.1% false positive rate. Roughly how much memory is that?

A 0.1% rate needs about 14.4 bits per item: ten for 1%, plus 4.8 for the next factor of ten. 50 million × 14.4 bits is 720 million bits, or 90 MB, with 10 hash functions. The size of the keys does not matter.

A filter built for one million items at 1% now holds three million. What has happened, and what are the options?

The false positive rate has risen to over 40%, with no error or warning. A Bloom filter cannot be resized because it does not contain its items. Rebuild a larger one from the source data, or use a scalable filter that adds further filters as it fills. Monitoring the number of items added would have shown the problem early.

Daily unique visitors for seven days were 40,000 each day. A report gives the weekly unique visitors as 280,000. What is wrong, and how should it be computed?

The report added distinct counts, so anyone who visited on several days was counted once for each. The weekly figure is somewhere between 40,000 and 280,000. Keep a HyperLogLog sketch for each day and merge the seven, which gives the count of distinct visitors across the week to within about 1%.

A count-min sketch has counted ten million events with ε = 0.001. It reports 12,000 for one item and 9,000 for another. What can you conclude about each?

The possible overestimate is up to 0.001 × 10 million = 10,000. The first item’s true count is between 2,000 and 12,000. The second’s is between 0 and 9,000, so the sketch says almost nothing about it. Estimates are meaningful only for items whose counts are well above the error bound. A wider sketch lowers the bound.

Ten servers each report their 99th percentile latency every minute. Why is the average of those ten numbers not the service’s 99th percentile, and what should be collected instead?

A percentile depends on the whole distribution. If nine servers report 50 ms and one reports 2 seconds, the average is 245 ms, but the true 99th percentile depends on how much traffic the slow server took and could be near 2 seconds. Each server should export a histogram or a sketch such as a t-digest. Those are merged, and the percentile is computed from the merged result.

A team proposes HyperLogLog to count API calls per customer for monthly invoices, to save memory. What do you say?

It is the wrong tool twice over. HyperLogLog counts distinct items, not events, and it is approximate. Counting calls needs a plain counter for each customer, which is small. Anything billed must be exact and reproducible from stored records, so that a disputed invoice can be checked.
