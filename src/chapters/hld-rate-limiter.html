The problem

The problem. Design the rate limiter for a public API. Every API key has limits, such as 100 requests a second, and a request over a limit is refused with status 429. The API runs on many servers.

The algorithms are settled: compared them, and wrote them as tested classes. What is hard is that the count is shared state, read and changed on every request by many servers at once. The check is on the path of every request, so it must cost close to nothing. And the limiter exists to protect the API, so its own failure must not become the API’s outage.

The accuracy line is the one that decides the design. “Exactly the limit, always” and “never a millisecond added” cannot both hold across many servers, so the requirement says how much error is acceptable, and in which direction.

Step 5: The design

The gateways are where API keys are known, so they enforce the per-key limits. The edge has only addresses, and counts them per data center. The services know their own load and limit concurrent work. The rules travel the other way, from the rules service into each gateway’s memory, so that reading a rule never costs a network call.

The second scene is the part of the design an interviewer will press on. Step 6d measures the three things a gateway can do when the store does not answer.

Step 6a: Counting in a shared store

showed the race with twenty requests fired at once. Under steady load it does not go away. The chapter’s simulation runs a store that executes one command at a time, 20 gateways that reach it over a network taking 0.2 to 0.6 ms each way, and one client whose requests arrive at random times and land on random gateways, against a token bucket of 100 a second.

Reading, deciding and writing in three steps lets through 180 requests a second when the client sends 1,000, and 509 when it sends 5,000. Each request that reads before the previous one has written sees the same tokens, and the faster the client sends, the more requests fall into that gap. The script holds 100 at every rate. It is also faster, one round trip instead of two: a median decision of 0.82 ms against 1.62 ms.

The script works because the decision is a pure function of the stored state and the time, so the whole function can be sent to the data. Redis runs a script with all other activity blocked, so its effects either have all happened or have not started. In the simulation the store runs the same function as the gateways would:

// 2. One script that reads, decides and writes inside the store, using the clock of the store.
export class AtomicScript implements Limiter {
  private readonly sim: Sim;
  private readonly store: CounterStore;
  private readonly algorithm: Algorithm;
  constructor(sim: Sim, store: CounterStore, algorithm: Algorithm) {
    this.sim = sim;
    this.store = store;
    this.algorithm = algorithm;
  }
  handle(key: string, done: (outcome: Outcome) => void): void {
    const started = this.sim.now;
    const algorithm = this.algorithm;
    this.store.eval(
      key,
      (state, now) => {
        const { decision, next } = algorithm.decide(state ?? algorithm.start(now), now, 1);
        return { next, result: decision.allowed };
      },
      (allowed) => done({ allowed, ms: this.sim.now - started, by: "store" }),
    );
  }
}

Three details make this correct in production. The time comes from the store’s own clock, read inside the script, so that gateways whose clocks disagree by a few milliseconds still agree on how many tokens have refilled; a reset time computed from two different clocks is what made GitHub’s reported reset times jump by a second. The decision is read from the shard’s primary, never a replica, because a replica can be behind and answer from a window that has already ended. And every key a script touches is passed to it by name, as Redis requires, which the hash tag keeps on one shard.

Which algorithm to keep in the store is a question of state and of the operation that changes it.

The memory line of step 2 assumed one or two small numbers for each limit. A sliding log for a limit of 3,000 a minute keeps up to 3,000 entries for each key, and for 2 million active keys that is up to 6 billion entries: the store would then be sized by memory after all. Token buckets keep the estimate true.

Step 6b: Local and global limits

A global limit is counted once for all servers together, in a shared store; a local share is the alternative in which each of n servers enforces the limit divided by n, in its own memory, with nothing shared. Local shares cost nothing per request and cannot be raced. The simulation measured what they get wrong.

Against an abusive client, local shares are exact: 100 a second at every fleet size, because no server can let through more than its share. The error falls on clients that behave. Requests are not spread perfectly evenly, so some servers see more than their share in a given second: a client sending exactly its limit was served 92.5% of the time with 20 servers and 76.2% with 50. A client that keeps one connection to one server, which HTTP/2 encourages, gets one share: 4.9% of its requests with 20 servers. Local shares break the requirement that a client within its limit is not refused.

Between the two lies counting locally and syncing: each gateway counts what it lets through, and every interval adds its count to the shared one and reads the total back. Decisions are made from memory, on a total up to one interval old.

The excess is close to the client’s rate times the interval: 49 extra a second at 50 ms, 96 at 100 ms. A client at 80% of its limit was always served in full, so the error runs in the safe direction for well-behaved clients and the wrong direction for abusive ones. The cost surprised: syncing every 10 ms took 3,408 store commands a second against 1,090 for counting every request, because each of 20 gateways synced each key 100 times a second whether or not it had new requests. Syncing saves work only for a key that sends many requests to each gateway within one interval.

That makes it the right tool for exactly one case, the hot key of step 2. The design counts every request in the store, which meets the accuracy target, and switches a key to local counting with a 10 ms sync when its rate passes a threshold, accepting about 10% excess for that one key. The other remedy is to split a hot key’s counter into several parts on different shards, each holding a share of its limit, with each request sent to one part at random: the local-share trade-off again, with shards in place of servers. Envoy describes the same two-stage arrangement: a local token bucket absorbs large bursts, so that the global rate limit service sees less load.

Step 6c: Where to limit

The serviceIts own queue and work in progressConcurrent requests, expensive operationsLocally, as load shedding ()

Each layer stops what the next cannot afford to see. The edge counts per data center, which is the local-share trade-off at continental scale: an attacker spread over 30 data centers gets up to 30 times the limit. That is acceptable for a coarse flood limit of thousands a second for each address, and is why a limit that must be exact for each customer lives at the gateway, behind the edge, in one region. Limiting in the client is courtesy, never enforcement.

Step 6d: When the counter store is down

A gateway that cannot reach the store has three choices. It can let the request through, which calls failing open; refuse it; or decide with a local share, as if it were one of n independent limiters. The simulation took the store away for 30 seconds, with a 5 ms timeout on every call, a client sending half its limit and another sending ten times its limit.

During the outageClient at half its limit, servedClient at 10 × its limit, let throughDecisions that waited 5 ms
Fail open100%1,005 a second100%
Fail closed0%0100%
Local share99.9%100 a second100%
Local share and a breaker99.9%100 a second2.4%

Failing closed turns a counter store outage into an API outage, which the availability requirement forbids. Failing open keeps the API up and removes the protection for exactly as long as the store is down, which is acceptable when load shedding stands behind it, and is what Stripe recommends. The local share keeps both: the well-behaved client was served, and the abusive one was held to its limit, because local shares are exact against abuse. Their weakness, refusing clients concentrated on one server, matters little for 30 seconds.

The timeout needs a breaker. Without one, every request waited the full 5 ms for an answer that would not come, which breaks the 2 ms latency target for the whole outage. With a breaker that skips the store for a second after five timeouts in a row, 2.4% of decisions waited (). The timeout itself should be short: Envoy’s default for its rate limit call is 20 ms. Last, the store’s state is disposable. A shard that restarts empty gives every key on it a full bucket, a few seconds of loose limits, so the store needs replicas for availability but no backups.

At ten times the load, 5 million decisions a second need 100 shards at the planning figure, and the busiest-key problem grows with the customers: more keys cross the threshold for local counting. At a hundred times, the API is likely in several regions, and one global count across regions would add a cross-region round trip, tens of milliseconds (), to every request. Each region then enforces its own share of a key’s limit, and shares are moved between regions every few seconds according to where the key’s traffic is: a local share, with regions in place of servers.

In the real world

  • Stripe described four limiters in 2017: a request rate limiter per user, a concurrent request limiter, and two load shedders. They use token buckets in Redis, launch each limiter in a dark mode that only reports what it would block, and say that if the limiter fails, requests should not be affected.
  • GitHub moved its API rate limiter from a shared Memcached cluster to sharded, replicated Redis with Lua scripts in 2021. Two bugs followed: a reset time computed from Ruby’s clock and Redis’s expiry moved by a second between requests, and a check read from a replica saw an expired window. They fixed both by storing the reset time with the counter and reusing the check’s answer for the headers.
  • Cloudflare’s rate limiting rules count in each data center separately, and its documentation says it does not support global counters across its network (checked October 2026).
  • Envoy calls an external global rate limit service over gRPC, whose reference implementation uses Redis, with a default timeout of 20 ms. It recommends a local token bucket in front to reduce the load on that service (checked October 2026).

In an interview. Spend the first minutes on where the limit is enforced and how exact it must be, because those two answers choose the design. Draw the gateway and the counter store, then go straight to the race and the script. Keep time for the two questions an interviewer is most likely to ask: what happens with many gateways and no shared store, and what happens when the store is down.

Key points

  • A limit kept in each server’s memory is multiplied by the number of servers. The count must be shared, or the limit divided.
  • Reading, deciding and writing in separate calls lets through more the faster a client sends: 180 a second against a limit of 100 at 1,000 offered, in the simulation.
  • One script that decides inside the store holds the limit exactly, in one round trip, with the store’s clock.
  • The counter store is sized by commands a second, not memory, and the busiest key’s shard carries that key alone.
  • Local shares are exact against abuse and refuse clients that behave; syncing local counts lets through roughly the client’s rate times the interval in excess.
  • Limit addresses at the edge, keys at the gateway, and concurrent work in the service.
  • When the store is down, fall back to local shares behind a short timeout and a breaker; failing closed turns the limiter into the outage.

Check yourself

Twenty gateways each run the limiter of chapter 71 in memory with a limit of 100 a second. What does a client get?

Up to 2,000 a second, 100 from each gateway, if its requests are spread across all of them. The limit has to be counted in one shared place, or each gateway must enforce only its share, 5 a second.

Why does the read-then-write limiter let through more requests the faster the client sends?

Every request that reads the state before the previous request has written its result sees the same tokens. The gap between a read and its write is a round trip, so the more requests arrive within one round trip, the more pass on the same tokens.

Why should the script read the time from the store rather than receive it from the gateway?

Gateways’ clocks differ by small amounts. If each sends its own time, refills and reset times depend on which gateway handled the request, and a request with a slightly older time can even make the bucket go backwards. One clock, the store’s, gives every decision the same reference.

Local shares hold an abusive client to its limit exactly. Why are they still not enough?

They refuse clients that keep to their limit whenever their requests are spread unevenly: 7.5% of requests with 20 servers in the simulation, and 95% of the requests of a client on one connection.

Syncing local counts every 10 ms used more store commands than counting every request. Why, and when does syncing help?

Each gateway synced each key every 10 ms whether or not it had new requests, which for keys sending a few requests a second to each gateway is more work than one command per request. Syncing helps only for a key that sends many requests to each gateway within an interval: a hot key.

The counter store is down. Compare failing open and falling back to local shares.

Both keep the API up. Failing open also lets an abusive client through at its full rate, 1,005 a second in the simulation. Local shares held it to 100 while serving the well-behaved client 99.9% of the time.

Why does the limiter’s store need replicas but no backups?

Its contents are short-lived counts that rebuild themselves within one window. Losing them gives some keys a little extra for a few seconds. Replicas keep the store available; backups would protect data nobody needs.
