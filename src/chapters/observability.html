Knowing what a system is doing

The photo app’s feed has become slow for some users. Not all of them, and not all the time. Nothing has crashed, every server reports healthy, and average response time has barely moved. Someone has to find out which users, since when, and why.

Two words describe the tools for this, and they are often used loosely.

  • Monitoring watches for conditions you decided in advance to care about: the error rate is above 1%, a disk is nearly full. It answers questions you knew to ask.
  • Observability is a property of the system: how well its internal state can be understood from what it emits. It is what lets you answer a question nobody anticipated, such as “why is the feed slow for users with more than a thousand follows, on the new version, in one region?”.

The more parts a system has, the more the second matters. In a single program a debugger and a log file go a long way. In forty services, the request that failed passed through six of them, and the evidence is in six places.

Three kinds of evidence

Systems emit three kinds of telemetry, often called signals. They describe the same events at different levels of detail and cost.

MetricsLogsTraces
What it isNumbers measured over timeTimestamped records of eventsThe path of one request through the system
AnswersIs something wrong? How much? Since when?What exactly happened at this point?Where did this request spend its time?
Cost grows withThe number of distinct series, not trafficTraffic: every event is storedTraffic, reduced by sampling

Weak atIndividual requestsAggregates and anything across servicesCompleteness: most requests are not kept

A fourth signal, profiles, records where a program spends CPU time and memory, down to the function. Run continuously at low overhead in production, profiling answers “which code is using the CPU?”, a question the other three cannot.

The usual route through them during an incident is from cheap to detailed: a metric raises the alarm, a trace shows which service and call are responsible, and logs from that service explain what it was doing.

Metrics

A metric is a named number, sampled at regular intervals and stored as a time series, the data shape from . There are three basic types.

TypeBehaviorExampleHow it is read
CounterOnly goes up, and resets to zero on restartRequests served, errors, bytes sentAs a rate: the increase per second over a window
GaugeGoes up and downQueue length, memory in use, connections openAs its current value
HistogramCounts observations into rangesRequest duration, response sizeAs percentiles and distributions

Each metric carries labels, key-value pairs that split it into separate series: the request counter for service="feed", status="500" is one series, and the same counter for status="200" is another. Labels are what make a metric useful, and they are also its cost. Every distinct combination of label values is a series that must be stored and indexed, so five services, twenty endpoints, five status classes and fifty instances already make 25,000 series for one metric. Adding a label with a million values, such as a user ID, multiplies that by a million. This is the cardinality problem from , and the rule is the one given there: labels are for dimensions with a bounded, small set of values. Identifiers of users and requests go in logs and traces.

What to measure

Two short checklists cover most of what a service and its resources should report.

For every service: REDFor every resource: USE
Rate: requests per secondUtilization: how busy it is, as a share of capacity
Errors: the share that failSaturation: how much work is waiting
Duration: how long they take, as a distributionErrors: failures of the resource itself

RED describes what users experience and belongs on every request-serving component. USE describes machines, disks, connection pools and queues, and explains why the first set looks the way it does. Google’s four “golden signals”, latency, traffic, errors and saturation, are the same idea in one list.

In a query language for metrics, the first two RED numbers for the feed service look like this in Prometheus, a widely used open-source metrics system.

# requests per second, averaged over the last 5 minutes
sum(rate(http_requests_total{service="feed"}[5m]))

# share of requests that failed
sum(rate(http_requests_total{service="feed", status=~"5.."}[5m]))
  /
sum(rate(http_requests_total{service="feed"}[5m]))

Histograms and percentiles

argued that latency must be described by percentiles, because an average hides the slow requests that users notice. Computing a percentile exactly needs every individual value, which is far too much to keep for every request on every server. A histogram keeps counts instead: how many requests took up to 10 ms, how many up to 25 ms, and so on.

export class Histogram {
  readonly counts: number[];            // counts[i] = observations <= bounds[i]; last slot is "above all bounds"
  sum = 0;
  constructor(readonly bounds: number[]) { this.counts = new Array(bounds.length + 1).fill(0); }

  observe(value: number): void {
    let i = this.bounds.findIndex((b) => value <= b);
    if (i < 0) i = this.bounds.length;
    this.counts[i]++; this.sum += value;
  }

  get total(): number { return this.counts.reduce((a, b) => a + b, 0); }

  /** Estimates a quantile by assuming values are spread evenly inside the bucket it falls in. */
  quantile(q: number): number {
    const rank = q * this.total;
    let seen = 0;
    for (let i = 0; i < this.counts.length; i++) {
      if (seen + this.counts[i] >= rank && this.counts[i] > 0) {
        if (i === this.bounds.length) return this.bounds[i - 1];      // above the last bound: unknown, report the bound
        const lower = i === 0 ? 0 : this.bounds[i - 1];
        return lower + ((rank - seen) / this.counts[i]) * (this.bounds[i] - lower);
      }
      seen += this.counts[i];
    }
    return NaN;
  }

  /** Histograms with the same bounds add: this is what makes them work across servers. */
  merge(other: Histogram): Histogram {
    const h = new Histogram(this.bounds);
    for (let i = 0; i < h.counts.length; i++) h.counts[i] = this.counts[i] + other.counts[i];
    h.sum = this.sum + other.sum;
    return h;
  }
}

A test with two servers shows both the strength and the weakness. Server A handled 10,000 requests, nearly all between 12 and 28 ms. Server B handled 100, and half of them took 600 ms or more.

Three results from that test are worth remembering.

QuestionHistogram’s answerExact answer
99th percentile of both servers together74.5 ms79.1 ms
99th percentile of server A alone50.0 ms28.0 ms
Average of the two servers’ 99th percentiles520 ms, which describes nothing

Histograms merge. Adding the counts of two histograms gives the histogram of the combined traffic. That is why a percentile across a hundred servers, or across the last hour, can be computed after the fact.

Percentiles do not. Server A’s 99th percentile was 50 ms and server B’s was 990 ms. Their average, 520 ms, is wrong by a factor of seven, because server B handled one request in a hundred. You cannot average percentiles, or take a percentile of percentiles. Aggregate the buckets first and compute the percentile last.

The estimate is only as fine as the buckets. For server A alone the histogram said 50 ms when the truth was 28 ms, because the 99th percentile fell at the very top of the 25 to 50 ms bucket and the histogram cannot see inside it. An estimate can be wrong by up to the width of a bucket. Put bucket boundaries where precision matters, above all at the threshold of your latency objective, so that “the share of requests under 250 ms” is counted exactly. Newer histogram formats choose many fine buckets automatically, and the sketches in give bounded relative error by construction.

histogram_quantile(0.99,
  sum by (le) (rate(http_request_duration_seconds_bucket{service="feed"}[5m])))

The query has the right order built in: sum by (le) adds the buckets across instances, and only then is the quantile estimated.

Logs

A log is a record of one event. Logs are the oldest signal and the most detailed, and at scale the most expensive, because their volume follows traffic.

Two habits make them far more useful.

Structure. Write each line as fields, usually JSON, and not as a sentence. A machine can then filter by level, group by user and join on trace_id. A free-text line has to be picked apart with patterns that break when someone rewords it.

Context. Every line written while handling a request should carry the same identifiers: the trace ID, the user or tenant, the route. Set them once when the request arrives and have the logger attach them automatically, using the same request-scoped context that carried the tenant in . One search by trace ID then returns everything every service logged for that request.

{"time":"2026-10-10T12:01:07.412Z","level":"error","service":"feed","version":"2026-10-10.3",
 "msg":"tags lookup timed out","duration_ms":138,"trace_id":"4bf92f3577b34da6a3ce929d0e0e4736",
 "route":"GET /feed","tenant":"acme","region":"eu"}

What to leave out matters as much. Passwords, tokens, card numbers and personal data do not belong in logs, which are widely readable inside a company, copied to several systems and kept for a long time. Treat a logged secret as leaked.

Because logs are paid for by the byte, volume needs managing. Log errors and unusual events in full. For routine success, keep a sample, or record it as a metric and not at all as a log. Keep recent logs searchable and move older ones to cheap storage. A service that writes a line for every cache hit will cost more to observe than to run.

Traces

A trace follows one request through every service it touches. It is made of spans. A span is one unit of work, such as handling a request or running a query, with a start time, a duration, a name, and a reference to the span that caused it. Drawn against time, the spans of a trace form a waterfall.

For spans from different services to join into one trace, each service must know which trace it is part of. This is context propagation: the caller sends the trace’s identity with the request, in a header that a W3C standard defines.

import { randomBytes } from "node:crypto";

type TraceContext = { traceId: string; spanId: string; sampled: boolean };

export function parseTraceparent(header: string): TraceContext | undefined {
  const m = /^00-([0-9a-f]{32})-([0-9a-f]{16})-([0-9a-f]{2})$/.exec(header);
  if (!m || /^0+$/.test(m[1]) || /^0+$/.test(m[2])) return undefined;
  return { traceId: m[1], spanId: m[2], sampled: (parseInt(m[3], 16) & 1) === 1 };
}

export function formatTraceparent(c: TraceContext): string {
  return `00-${c.traceId}-${c.spanId}-${c.sampled ? "01" : "00"}`;
}

/** A new span in the same trace: the trace ID is kept, the span ID is new. */
export function childOf(parent: TraceContext): TraceContext {
  return { traceId: parent.traceId, spanId: randomBytes(8).toString("hex"), sampled: parent.sampled };
}

/** Starts a trace, deciding once whether it is sampled. Every service downstream follows the decision. */
export function startTrace(sampleRate: number): TraceContext {
  const traceId = randomBytes(16).toString("hex");
  const sampled = parseInt(traceId.slice(-8), 16) / 2 ** 32 < sampleRate;
  return { traceId, spanId: randomBytes(8).toString("hex"), sampled };
}

In practice you rarely write this. Instrumentation libraries create spans for incoming requests, outgoing calls and database queries, and pass the header along. What you add by hand are spans around your own important operations, and the propagation through anything the libraries do not know about, which usually means messages and jobs, as described.

Sampling

Recording every span of every request is rarely affordable, so traces are sampled. There are two places to decide.

Head samplingTail sampling
DecidedAt the first service, before anything is knownAfter the trace is complete
KeepsA random share, such as 1 in 100Whatever is interesting: errors, slow requests, plus a random share
CostLow: unsampled requests record nothingEvery span must be collected and held until the trace ends
WeaknessThe one failing request in ten thousand is probably not keptMore machinery, and more data in motion

The function above is a head sampler. Deciding from the trace ID, and carrying the decision in the header’s flag, means every service agrees and a trace is either kept whole or not at all. In a test of 20,000 traces at a rate of 10%, it kept 2,035.

Collecting it: OpenTelemetry

For years each monitoring vendor had its own libraries, and changing vendor meant re-instrumenting every service. OpenTelemetry is the open standard that replaced them. It defines an API for producing all the signals, libraries that implement it for each language, a wire protocol called OTLP, and a collector: a separate process that receives telemetry, batches and filters it, and forwards it wherever you choose.

As of October 2026, OpenTelemetry’s tracing, metrics and logs are stable, and its profiling signal entered public alpha in March 2026. Metrics are also still widely collected the way Prometheus introduced, in which the monitoring system fetches, or scrapes, a page of current values from every instance on a schedule. Pulling has a useful side effect, since an instance that cannot be scraped is itself a signal, and the two approaches coexist in most systems.

Designing the storage side, a system that ingests and queries this data at scale, is a problem of its own and the subject of .

Alerting

An alert interrupts a person. That is expensive, and the cost is not only the interruption. A team that is paged often for things that turn out not to matter learns to ignore pages, and then ignores the one that matters. Good alerting is mostly a matter of alerting on less.

The principle is to alert on symptoms, the things users experience, and not on causes. A node at 95% CPU may be working exactly as intended. A restarted pod was replaced before anyone noticed. Meanwhile an outage caused by an expired certificate raises no CPU alarm at all. An alert on the error rate catches every cause, including the ones nobody predicted.

“Users see errors” needs a number, and supplied one: the service level objective and its error budget. A 99.9% objective over 30 days allows 0.1% of requests to fail. The alerting question becomes: is the budget being spent too fast?

The burn rate is the answer as a single number: the current error rate divided by the error rate the objective allows. At a burn rate of 1 the budget lasts exactly the 30 days. At 10 it is gone in three.

An objective of 99.9% leaves an error budget of 0.1%: over 30 days, the equivalent of 43.2 min of total failure. An error rate of 1% spends it at 10 times the rate the objective allows, so the whole budget would be gone in 3 days. At that rate 8.33% of the budget goes every six hours, at or above the 5% that calls for a page. Page someone if it has lasted that long.

Google’s Site Reliability Workbook recommends a set of burn-rate alerts that has become the common starting point. For a 30-day window:

Budget usedInBurn rateAlso checked overAction
2%1 hour14.45 minutesPage
5%6 hours630 minutesPage
10%3 days16 hoursTicket

Each row uses two windows, and an alert fires only when both are above the threshold. The long window shows that the problem is sustained and has cost real budget. The short window shows that it is still happening, so the alert stops soon after the problem does and does not keep paging for an hour about something already fixed.

export function burnRate(errorRate: number, slo: number): number {
  return errorRate / (1 - slo);
}

type Window = { long: number; short: number };   // observed error rates over the two windows
type Alert = "page" | "ticket" | "none";

/** Fires only if both the long and the short window are burning fast: sustained, and still happening. */
export function sloAlert(slo: number, oneHour: Window, sixHours: Window, threeDays: Window): Alert {
  const both = (w: Window, threshold: number) => burnRate(w.long, slo) >= threshold && burnRate(w.short, slo) >= threshold;
  if (both(oneHour, 14.4) || both(sixHours, 6)) return "page";
  if (both(threeDays, 1)) return "ticket";
  return "none";
}

Four cases confirm the behavior. A five-minute blip of 20% errors does not page, because the hour as a whole stayed within its rate. A steady 2% error rate for an hour pages. An outage that ended twenty minutes ago does not page again, because the last five minutes are clean. A slow leak of 0.15% errors for three days opens a ticket and wakes nobody.

Whatever the mechanism, every alert that pages should pass three tests. It is about something users feel, or will feel soon. A person can do something about it now. And it links to a runbook that says what to check first. An alert that fails these belongs on a dashboard or in a ticket queue.

Dashboards

A dashboard is for orientation: is this service healthy, and if not, where should I look? A useful one for a service is short.

  • At the top, the user’s view: request rate, error ratio and latency percentiles, against the objective.
  • Below, the explanations: saturation of the resources it depends on, and the same three numbers for each dependency it calls.
  • On every chart, markers for changes: deployments, flag changes, configuration pushes. The question “what changed?” resolves more incidents than any other, as explained.
  • Breakdowns one click away: by version, region, endpoint and, where it exists, tenant.

A wall of sixty charts answers no question. If a chart has never helped anyone decide anything, remove it.

Finding the fault: a worked example

Return to the slow feed. Here is the investigation, with each step using a different signal.

  1. The alert. The feed’s latency objective is burning budget at six times the allowed rate. This says there is a problem and roughly how bad. It came from a metric.
  2. Narrow it. On the dashboard, split the 99th percentile by each dimension in turn. By region: all regions. By endpoint: only GET /feed. By version: only the version deployed forty minutes ago. A marker on the chart shows the deployment at the moment the line rises. Still metrics.
  3. Look at one. Open a slow trace of GET /feed on the new version, the one in the waterfall figure above. Most of the time is in the tags service, inside one database query. Now traces.
  4. Read the detail. Search the tags service’s logs for that trace ID. The query log shows the statement and its duration. It filters on a column the new version started using.
  5. Confirm the cause. The database’s slow-query log shows the same statement thousands of times, each scanning the whole table. The column has no index, the problem that walked through.
  6. Mitigate, then fix. Roll back the deployment, which takes minutes and stops the harm. Add the index, then deploy again.

Two things made this quick. Every signal carried the same dimensions, version, region and endpoint, so the problem could be narrowed by slicing. And the signals were linked: the latency chart led to an example trace, and the trace ID led to the logs. A slow request that is recorded as a metric, a trace and a log line with nothing in common between them is three separate puzzles.

Looking from outside

Everything so far is reported by the system about itself, which has a blind spot: a service that is unreachable reports nothing, and a system that is fast at the server can be slow for the user. Two outside views close the gap.

  • Synthetic checks are scripted requests sent from outside on a schedule, from several places: load the home page, log in, upload a photo. They detect an outage even at 4 a.m. when no real user is trying, and they are the right check for certificates, DNS and anything else between the user and the first server.
  • Real user monitoring has the client report what it experienced: page load times, errors in the browser or app, by device and network. It is the only measurement of the last mile, the part of that the server never sees.

When the alert fires

Telemetry serves people responding to incidents, and how they respond matters as much as the tooling.

  • Mitigate first. Stop the harm with the fastest safe action: roll back, turn off a flag, shift traffic, add capacity. Understanding why can wait until users are no longer affected.
  • One person coordinates. In a large incident someone who is not typing commands keeps track of what is known, who is doing what, and what has been told to customers.
  • Write it down as you go. A timeline kept during the incident is worth far more than one reconstructed afterward.
  • Review without blame. Afterward, write up what happened, why the system allowed it, and what will change. The useful question is why a reasonable action led to a bad result, and it is answered only if people can speak freely. The incident accounts quoted throughout this book are public examples of the form.
  • Close the loop. If the alert was late, noisy or missing, or the dashboard lacked the breakdown that would have helped, fixing that is part of the follow-up.

What observability costs

Telemetry is data, and at scale it is a great deal of data. A system that logs a kilobyte for each request at ten thousand requests a second writes about 860 GB a day before anything is indexed or replicated. Left unmanaged, the bill for observing a system can approach the bill for running it.

SignalWhat drives the costHow to control it
MetricsThe number of seriesBounded labels. Drop series nobody queries. Keep fine resolution for days and coarse for months
LogsBytes writtenSample routine events. Shorter retention for verbose levels. Cheap storage for old logs
TracesSpans keptSampling, weighted toward errors and slow requests

The aim is to keep what answers questions and drop what does not, and to decide that deliberately. A common pattern is full detail for a short time, when an incident is being investigated, and aggregates for the long term, when only trends matter.

In an interview. Add observability to a design in two sentences. First, every service emits rate, errors and duration, with traces propagated across calls and queues. Second, alerts are on user-facing objectives by burn rate, not on machine metrics. If asked how you would debug a slow request, describe the path from alert to breakdown to trace to logs. If the design has a queue, mention the age of the oldest message as its key signal.

Common mistakes

  • Averaging latency. The mean hides the slow tail that users feel.
  • Averaging percentiles across servers or time windows. Aggregate histograms, then compute.
  • Unbounded labels. A user ID or full URL as a metric label, and the metrics system falls over.
  • Unstructured logs with no identifiers in common, impossible to join.
  • Secrets and personal data in logs.
  • Broken propagation. A proxy, a queue or one old service drops the trace header.
  • Alerting on causes. Pages for CPU and restarts, and none for the outage with a cause nobody listed.
  • Alerts nobody can act on. They train people to ignore alerts.
  • Only internal checks. Everything reports healthy while users cannot connect.
  • No deployment markers. Twenty minutes spent discovering that something changed.
  • Observability added after the incident. The data needed to explain it was never collected.

Key points

  • Metrics say that something is wrong and how much. Traces say where. Logs say what happened there. Link them with shared identifiers and dimensions.
  • Metric cost follows the number of series. Keep labels bounded, and put identifiers in logs and traces.
  • Measure rate, errors and duration for every service, and utilization, saturation and errors for every resource.
  • Histograms can be added across servers and time. Percentiles cannot. Aggregate buckets first, and place bucket boundaries at your objectives.
  • A trace needs its context passed on every hop, including through queues. Sampling decides which traces are kept.
  • Alert on symptoms users feel, measured against an objective, using burn rate over a long and a short window. Send everything else to dashboards and tickets.
  • Check from outside as well as inside, mark every change on every chart, and manage telemetry volume deliberately.

Check yourself

Which signal would you use first for each question: “is the error rate rising?”, “which service made this request slow?”, “what did the payment service receive for order 1042?”

A metric for the error rate, since it is an aggregate over time. A trace for the slow request, since it shows time spent in each service. Logs for the specific order, since they hold the detail of one event.

Why is a user ID a bad metric label and a fine log field?

Each distinct label value creates a separate time series, so a label with a million values multiplies the number of series by a million and overwhelms the metrics store. A log line is stored once whatever its fields contain, so a high-cardinality field costs nothing extra there.

Server A has a 99th percentile of 40 ms over 50,000 requests. Server B has 900 ms over 500 requests. Why is 470 ms not the combined 99th percentile, and how is the real one obtained?

The average of two percentiles ignores how many requests each describes. B handled 1% of the traffic, so the combined 99th percentile sits near the boundary between A’s requests and B’s slow ones, far below 470 ms. Add the two servers’ histogram buckets, then estimate the percentile from the combined counts.

A histogram’s buckets end at 100, 250 and 500 ms and your objective is “99% of requests under 300 ms”. What is the problem?

There is no boundary at 300 ms, so the share of requests under 300 ms can only be estimated by assuming an even spread between 250 and 500. Add a bucket boundary at exactly 300 ms so that the count is exact.

What must stay the same and what must change in the traceparent header as a request passes from one service to the next?

The trace ID stays the same, so all spans can be joined. The span ID changes to the ID of the calling span, so the callee can record its parent. The sampled flag is passed on unchanged so that every service makes the same keep-or-drop decision.

An objective is 99.5% over 30 days and the current error rate is 3%. What is the burn rate, how long would the budget last, and what should happen?

The budget is 0.5%, so the burn rate is 3 ÷ 0.5 = 6, and the budget would last 30 ÷ 6 = 5 days. That meets the threshold of 6, which uses 5% of the budget in six hours, so it should page if it has been sustained over that window and is still happening.

Why does a burn-rate alert check a short window as well as a long one?

The long window alone keeps firing long after a problem ends, because the past errors remain inside it. Requiring the short window to be over the threshold too means the alert fires only while the problem is continuing, and clears soon after it stops.

All internal dashboards are green and users report that the site does not load. Name two kinds of check that would have caught it.

Synthetic checks, scripted requests from outside that exercise DNS, certificates, the network path and the front door. And real user monitoring, where clients report failed loads. Internal telemetry cannot see a request that never arrives.
