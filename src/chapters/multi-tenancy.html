One system, many customers

Suppose the photo app adds a product for organizations. A design studio called Acme, a school called Birch and a newspaper called Cedar each sign up, add their staff as users, and keep their photos there. Each organization is a tenant: a customer that owns a set of users and data and expects it to be separate from every other customer’s.

There are two basic ways to serve them. In a single-tenant arrangement every customer gets a separate copy of the software, on separate machines. In a multi-tenant arrangement one running system serves all of them. Nearly every business product delivered over the internet is multi-tenant to some degree, for three reasons:

  • Cost. Most tenants are small and mostly idle. A thousand of them fit comfortably on hardware that would be wasted on one.
  • Operations. One system to deploy, monitor and upgrade, instead of a thousand. Everyone is on the same version.
  • Onboarding. A new customer is a new row in a table, ready in seconds, instead of new infrastructure.

Sharing has a price, and it is the subject of the rest of the chapter. Two promises that come free with separate copies must now be kept by design:

  • Data isolation. No tenant ever sees or changes another’s data.
  • Performance isolation. No tenant’s activity degrades another’s service.

A failure of the first is a security incident, of the kind that ends contracts. A failure of the second is an outage with a particular shape: one customer does something unusual and others suffer for it.

Silo, pool and bridge

The choice is not all or nothing. It is made separately for each part of the system, and three words from AWS’s guidance for software-as-a-service have become the common vocabulary.

For the database, which is where the decision matters most, there are three standard positions between the ends.

The tenant counts are rough guides, not limits. What sets them is operations: a schema migration that must be applied ten thousand times, with some failing halfway, becomes a project of its own, and a database server with hundreds of thousands of tables behaves poorly in ways its makers did not optimize for.

A workable default for a new product is shared tables, with the option kept open to move a large or sensitive tenant onto separate storage later. The sections below show how to build shared tables so that the option stays open.

Shared tables done properly

In the pooled model, every table that holds tenant data carries the tenant’s identifier, and the identifier takes part in every key.

create table tenants (
  id   uuid primary key,
  name text not null
);

create table users (
  tenant_id uuid not null references tenants (id),
  id        uuid not null default gen_random_uuid(),
  email     text not null,
  primary key (tenant_id, id),
  unique (tenant_id, email)
);

create table photos (
  tenant_id uuid not null,
  id        uuid not null default gen_random_uuid(),
  owner_id  uuid not null,
  caption   text,
  taken_at  timestamptz not null default now(),
  primary key (tenant_id, id),
  foreign key (tenant_id, owner_id) references users (tenant_id, id)
);

create index photos_recent on photos (tenant_id, taken_at desc);

Four details in this schema do work.

  • The tenant leads every primary key. A photo is identified by tenant and ID together. Rows of one tenant sit next to each other in the index, and the table is ready to be partitioned or sharded by tenant, as recommended.
  • Uniqueness is per tenant. unique (tenant_id, email) lets Ana have an account at Acme and another at Birch with the same address. A plain unique (email) would let one tenant discover, by a failed signup, who is a customer of another.
  • Foreign keys include the tenant. The photo’s owner must be a user of the same tenant. Without the tenant in the key, a bug could attach Acme’s photo to Birch’s user and the database would accept it.
  • Indexes lead with the tenant. Every query filters by tenant first, so every index should start there. explains why the order matters.

Row-level security as a second lock

With shared tables, isolation depends on every query including where tenant_id = …. Application code gets this right nearly always, and nearly always is not good enough: one forgotten condition in one report query exposes every tenant.

PostgreSQL can enforce the condition itself. With row-level security, a policy attached to a table is added to every query on it, whatever the query says.

alter table photos enable row level security;
alter table photos force row level security;

create policy tenant_isolation on photos
  using (tenant_id = current_setting('app.tenant_id')::uuid);

The policy reads a setting that the application supplies at the start of each transaction.

begin;
select set_config('app.tenant_id', '11111111-1111-1111-1111-111111111111', true);
select caption from photos order by taken_at desc limit 20;   -- only this tenant's rows
commit;

Running this schema with two tenants confirms the behavior. Each tenant sees only its own photos from select * from photos. An update photos set … with no where clause, run as Birch, changes one row, Birch’s, and leaves Acme’s two alone. An insert that names another tenant is refused with new row violates row-level security policy. A query with no tenant set fails with an error instead of returning everything. The query plan shows the policy’s condition used as an index condition on photos_recent, so the protection does not cost a table scan.

Row-level security is a second lock, not a replacement for the first. It has edges that must be known to rely on it.

  • Owners and superusers bypass it. By default a table’s owner is not subject to its policies. force row level security removes that exception. Superusers and roles with the BYPASSRLS attribute always bypass. The application must connect as an ordinary role that owns nothing, or the policy does nothing at all.
  • The setting must be local to the transaction. The third argument true in set_config makes the value disappear at commit. With false it stays on the connection. Connections are pooled and reused, so the next request on that connection, for a different tenant, would inherit it. In the test, a request that forgot to set its tenant after a session-level setting read the previous tenant’s photos.
  • Integrity checks see everything. The PostgreSQL manual warns that unique and foreign-key checks bypass row security to keep data correct, so an error from a constraint can reveal that a value exists in another tenant. Tenant-scoped keys, as in the schema above, close this.
  • It covers one database. The cache, the search index, the object store and the message queue know nothing about it.

Common mistake. Enabling row-level security, testing as the database owner, seeing every row, and concluding it is broken, or worse, testing nothing and assuming it works. Test it as the role the application really uses, with an automated test that logs in as one tenant and tries to read another’s rows.

Carrying the tenant through the code

Every request belongs to exactly one tenant, and every layer needs to know which. Two questions follow: where the answer comes from, and how it travels.

Where it comes from. The tenant must be derived from something the caller cannot forge: the verified login token, an API key looked up on the server, or a subdomain checked against the token. It must never be taken from a field the client can set freely, such as a tenantId in the request body or an X-Tenant header. A client that can name its tenant can name someone else’s.

How it travels. Passing a tenant ID as an argument to every function works and is easy to get wrong, because any caller can pass the wrong one. The safer design sets the tenant once for the whole request and makes the data layer read it from there. In Node.js, AsyncLocalStorage holds a value that follows one request through all its asynchronous calls, without leaking into other requests running at the same time.

import { AsyncLocalStorage } from "node:async_hooks";

type TenantContext = { tenantId: string; userId: string };
const store = new AsyncLocalStorage();

export function runAs(ctx: TenantContext, fn: () => Promise): Promise {
  return store.run(ctx, fn);
}

export function currentTenant(): string {
  const ctx = store.getStore();
  if (!ctx) throw new Error("no tenant in context");   // fail closed
  return ctx.tenantId;
}

interface Tx { query(sql: string, params?: unknown[]): Promise }
interface Pool { transaction(fn: (tx: Tx) => Promise): Promise }

export class TenantDb {
  constructor(private pool: Pool) {}

  /** Every query runs in a transaction that has the tenant set for row-level security. */
  run(fn: (tx: Tx) => Promise): Promise {
    const tenantId = currentTenant();
    return this.pool.transaction(async (tx) => {
      await tx.query("select set_config('app.tenant_id', $1, true)", [tenantId]);
      return fn(tx);
    });
  }
}

// Keys that always carry the tenant
export const cacheKey = (name: string) => `t:${currentTenant()}:${name}`;
export const objectKey = (path: string) => `tenants/${currentTenant()}/${path}`;

The request handler calls runAs once, after authentication. From then on the only way to reach the database is TenantDb.run, which cannot be called without a tenant, and the only way to build a cache key or a storage path adds the tenant to it. A test with three overlapping requests confirms that each sees its own tenant throughout.

The important property is that code with no tenant fails. The alternative, a default tenant or an unfiltered query when none is set, turns every missed case into a leak.

The context stops at the edge of the process. A message put on a queue must carry its tenant ID in the message, and the consumer must call runAs with it before doing anything. A scheduled job that works across tenants should loop over them and enter each one’s context in turn, so that the per-tenant code path is the same one requests use.

Where data leaks

Cross-tenant leaks rarely come from the main query path, which is tested daily by every user. They come from the edges.

The second row is among the most common web vulnerabilities, and multi-tenancy raises its cost: the stranger whose record is exposed is a different company.

The durable defense is a test suite that attacks the boundary. Create two tenants. For every endpoint, log in as the first and request the second’s resources by ID. Every response must be “not found”. Add the test when the endpoint is added, so that isolation is checked by a machine on every change.

Noisy neighbors

A noisy neighbor is a tenant whose load degrades the service for others who share its resources. It is seldom malicious. Acme’s new intern runs an export of every photo since 2015. Cedar’s integration script has a bug and retries in a tight loop. A customer simply grows ten times larger than the rest.

Whatever is pooled can be monopolized: database connections and CPU, worker threads, queue position, cache memory, an outbound API’s rate limit. The defenses give each tenant a bounded share of each.

  • Rate limits for each tenant. A token bucket keyed by tenant, as in , with a size that can differ by plan.
  • Concurrency limits for each tenant. A cap on requests in progress, which is the bulkhead of with one compartment per tenant. This matters more than a rate limit for expensive operations: ten simultaneous exports can hurt more than a thousand quick reads.
  • Quotas. Limits on stored bytes, rows, users or API calls a month, which also keep costs in line with what the tenant pays.
  • Fair scheduling. For background work, take jobs from tenants in turn instead of in arrival order.
export class FairQueue {
  private queues = new Map();
  private order: string[] = [];          // tenants that have work, in turn order

  push(tenantId: string, job: T): void {
    let q = this.queues.get(tenantId);
    if (!q) { q = []; this.queues.set(tenantId, q); this.order.push(tenantId); }
    q.push(job);
  }

  /** Takes one job from the tenant whose turn it is, then moves that tenant to the back. */
  pop(): { tenantId: string; job: T } | undefined {
    const tenantId = this.order.shift();
    if (tenantId === undefined) return undefined;
    const q = this.queues.get(tenantId)!;
    const job = q.shift()!;
    if (q.length > 0) this.order.push(tenantId);
    else this.queues.delete(tenantId);
    return { tenantId, job };
  }
}

With 1,000 jobs from Acme queued first, then two from Birch and one from Cedar, this serves them in the order a1, b1, c1, a2, b2, a3. In a single queue Birch’s first job would have been number 1,001. Production systems refine the idea with weights, so that a tenant on a larger plan gets more turns, and with a cap on how many of one tenant’s jobs run at once.

None of this works without measurement. Record the tenant on every request, query and job, and keep a view of the top tenants by load. When the system is slow, the first question is whether everyone is slow or one tenant is making it so, and only tenant-tagged metrics can answer it. Tagging every metric with a tenant ID multiplies the number of time series, the cardinality problem from , so the usual compromise is tenant tags on logs and traces and on a few key metrics.

Placing tenants

When one database is no longer enough, tenants are spread across several. The tenant is the natural shard key: almost every query stays inside one tenant, so almost every query stays on one shard. The usual mechanism is the directory from : a small table that records where each tenant lives.

Tenant sizes are very uneven. In most business products a few customers account for a large share of all data and traffic. Hashing tenants evenly across shards therefore does not spread load evenly: whichever shard receives the largest tenant is the hot one. The directory handles this by placing tenants deliberately. Small ones are packed together, and the largest get shards to themselves.

Notion’s account of sharding its PostgreSQL database, published in 2021, is a well-documented example. It partitioned by workspace ID, its tenant. It created 480 logical shards, each a PostgreSQL schema, spread over 32 physical databases with 15 schemas on each. The number 480 was chosen because it divides evenly by many numbers, so the logical shards can later be redistributed over 40 or 48 machines without splitting any of them. This is the fixed-partitions technique from .

Moving a tenant between shards while it is in use follows the migration steps in : copy, keep in step, verify, switch the directory entry, clean up. Build this operation early. It is what makes every later change possible: rebalancing, isolating a noisy tenant, upgrading a customer to dedicated hardware, and moving a customer’s data to another country.

Cells

Sharding the database limits how much data one failure can touch. The stateless layers above it are usually still one shared pool, so a bad deployment or an overload there still reaches every tenant. A cell-based architecture applies the shard idea to the whole stack.

A cell is a complete, independent copy of the system: its own web servers, services, queues, caches and databases. Each tenant is assigned to one cell. In front of the cells sits a thin router whose only job is to send each request to its tenant’s cell.

Cells buy three things.

  • A bounded blast radius. A fault in one cell, whether from hardware, a bad change, corrupt data or one abusive tenant, affects that cell’s tenants and no others. With N equal cells, that is 1/N of customers.
  • Safer deployment. A change goes to one cell, is watched, and then goes to the next. Most bad changes are caught having reached a small fraction of customers.
  • A tested unit of scale. A cell has a maximum size that has been load-tested. Growth means adding cells of a known size, instead of growing one system into territory nobody has tested.

Slack moved to a cellular design after an incident in June 2021, in which a network fault in one availability zone degraded the whole service because its internal services called each other freely across zones. In Slack’s design each availability zone is a cell, traffic stays inside its cell, and an operator can drain all traffic away from a failing cell in under five minutes. AWS describes many of its own services as cellular and publishes guidance on the pattern.

The costs are real and should be stated in any design that proposes cells.

  • The router is shared by everyone. It is the one part whose failure reaches all tenants, so it must be as simple and as static as possible: a lookup and a forward, with its table cached at the edge.
  • Nothing crosses cells cheaply. A feature that needs data from two tenants in different cells, such as sharing an album between organizations, has to go through a slow, explicit path. Global features such as login, billing and search across tenants need a home outside the cells, and that home is another shared dependency.
  • More to run. Many small copies cost more than one large system, in machines and in the tooling to deploy, observe and rebalance them.
  • Migration between cells is needed from the first day a cell fills up.

Cells are a tool for systems that are large and for which a full outage is very expensive. A product with a hundred tenants does not need them. It does benefit from the habits that make them possible later: a tenant directory, tenant-scoped keys, and no cross-tenant queries.

Shuffle sharding

Cells give each tenant one fixed group of resources, shared with every other tenant in the cell. For a shared stateless layer there is a cleverer assignment, described by Colm MacCárthaigh of AWS, that shrinks the group of tenants who share a fate.

Take eight workers. Plain sharding divides them into four shards of two and assigns each tenant to a shard. If one tenant sends requests that crash or exhaust its workers, both workers of that shard go down and every tenant on it, a quarter of all tenants, loses service.

Shuffle sharding instead gives each tenant its own combination of two workers, chosen from all eight. There are 28 such pairs. Two tenants rarely have the same pair, so a tenant that takes down its two workers fully takes down only those tenants who share both.

Plain sharding gives 4 shards, so one tenant that overloads its shard takes 25% of all tenants down with it. Shuffle sharding gives 28 possible sets of 2 workers. Another tenant has exactly the same set only 3.57% of the time. 42.9% share some but not all of the bad tenant’s workers, and still have a healthy one to retry on.

Try 100 workers with 5 for each tenant: over 75 million combinations. AWS reports that Route 53 uses 2,048 virtual name servers in shuffle shards of four, which gives about 730 billion combinations, enough that every customer domain can have a set that overlaps fully with no other.

The assignment needs no table. Score each worker by hashing the tenant ID together with the worker’s name and take the highest scores. The same tenant always gets the same workers, and different tenants get different mixes. This is called rendezvous hashing.

import { createHash } from "node:crypto";

function score(tenantId: string, worker: string): number {
  return createHash("sha256").update(`${tenantId}/${worker}`).digest().readUInt32BE(0);
}

/** The same tenant always gets the same `size` workers. Different tenants get different mixes. */
export function shuffleShard(tenantId: string, workers: string[], size: number): string[] {
  return [...workers]
    .sort((a, b) => score(tenantId, b) - score(tenantId, a))
    .slice(0, size)
    .sort();
}

Assigning 20,000 tenants to eight workers with this function used all 28 pairs. Compared with one chosen tenant, 3.4% of the others had the same pair and 43.3% shared one worker, close to the 3.57% and 42.9% that the arithmetic predicts.

The figure and the numbers rest on one condition: the client must retry on its other worker when one fails. Tenants who share one worker with the bad tenant are safe only because they have a second to turn to. Shuffle sharding also suits stateless workers far better than databases, since a tenant’s data cannot be spread over an arbitrary pair of servers as easily as its requests can.

Isolation as a product

How much isolation a tenant gets is often part of what it buys. A common arrangement:

Free and small teamsPooledShared tables on pooled shardsTight rate limits and quotas
BusinessPooledPooled shards with fewer tenants on eachHigher limits
EnterprisePooled, or a dedicated cellA dedicated database, a chosen region, the customer’s own encryption keyNegotiated

This is the bridge model as a price list, and the tenant directory is what makes it cheap to offer: the plan decides where the directory points.

What must not vary by tenant is the code. Every large customer eventually asks for something special. Build it as configuration or a feature flag in the one codebase, never as a separate branch or build for that customer. A separate version for each large customer brings back, one customer at a time, the operations problem that multi-tenancy was adopted to solve.

Two enterprise requirements shape architecture more than the rest. Customers increasingly require that their data stay in a named country or region, which is covered in . Some require that their data be encrypted with a key they control and can revoke, which is covered in . Both are much easier when every piece of data already knows its tenant.

The life of a tenant

  • Onboarding should be fully automatic: a directory entry, default settings, a first user. If creating a tenant needs a person, the silo parts of the design will limit growth.
  • Metering. Record usage for each tenant: requests, storage, active users. It feeds billing, quota enforcement, capacity planning and the question of which customers cost more than they pay.
  • Schema changes. With shared tables, one migration serves everyone, and it must be an online migration of the kind in , because there is no quiet hour that suits every customer. With a schema or database per tenant, a migration is a batch job that must record progress and be safe to resume.
  • Restore. “Please restore our data to last Tuesday” is simple for a tenant with its own database and hard for one whose rows are mixed into shared tables, since a full restore would rewind every tenant. Decide early what you will offer: per-tenant export on a schedule, soft deletion with an undo period, or history tables.
  • Offboarding. A departing tenant’s data must be exported on request and then deleted everywhere: tables, caches, search indexes, object storage, analytics copies and, on a stated schedule, backups. Tenant-scoped keys and paths turn this into a list of prefixes to remove. Without them it is an investigation.

In an interview. When a design serves businesses, say early that the tenant ID is part of every key, cache entry and message, and that it is the shard key. Then address both isolations by name: data isolation, by scoped queries with row-level security behind them, and performance isolation, by per-tenant limits and fair queuing. Mention the directory, and that the largest tenants can be moved to dedicated shards. Raise cells only if the scale or the availability target calls for them, and name the router as their shared dependency.

Common mistakes

  • Adding the tenant later. Retrofitting tenant_id onto tables, keys, caches and messages of a running system is one of the more painful migrations there is. Put it in from the first table, even with one customer.
  • Trusting the client’s word for its tenant. Reading the tenant from a request field instead of from the verified identity.
  • Filtering by hand in every query. One forgotten condition is a breach. Centralize the scoping and back it with row-level security.
  • Session-level tenant settings on pooled connections. The next request inherits them.
  • Caches, search and files without the tenant. Isolation enforced in the database alone.
  • Global uniqueness on tenant data. It leaks existence across tenants and blocks legitimate duplicates.
  • No per-tenant limits. The first runaway script becomes everyone’s outage.
  • No per-tenant metrics. Without them, “the system is slow” cannot be told apart from “one tenant is making it slow”.
  • A code fork for a big customer. It never merges back.
  • Cells too early. The operational cost arrives at once and the benefit only at scale.
  • No way to move a tenant. Every fix for skew, noise and residency depends on it.

Key points

  • Multi-tenancy trades the automatic isolation of separate copies for lower cost and simpler operations. Data isolation and performance isolation must then be designed.
  • Silo, pool and bridge describe how much is shared. The choice is made per layer, and most systems end up as bridges.
  • In shared tables the tenant ID leads every primary key, foreign key, unique constraint and index. Row-level security backs up the application’s own filtering.
  • Resolve the tenant once from the verified identity, carry it in the request context, and make code without a tenant fail.
  • Leaks happen at the edges: caches, identifiers, search, files, background jobs. Test the boundary automatically.
  • Per-tenant rate limits, concurrency limits, quotas and fair queues contain noisy neighbors. Per-tenant metrics reveal them.
  • A tenant directory makes placement a matter of data: pack small tenants, isolate large ones, and move them when needed.
  • Cells bound the blast radius of any failure to a fraction of tenants. Shuffle sharding shrinks the group that shares a fate further, provided clients retry.

Check yourself

What are the two kinds of isolation a multi-tenant system must provide, and what does a failure of each look like?

Data isolation: no tenant can see or change another’s data. Its failure is a security breach. Performance isolation: no tenant’s load degrades another’s service. Its failure is an outage or slowdown caused by one customer and felt by others.

Why should a users table in a pooled design use unique (tenant_id, email) and not unique (email)?

The same person may legitimately have accounts in two tenants, which a global constraint would forbid. A global constraint also leaks information: a signup that fails with “email already in use” tells one tenant that the address exists in another.

Row-level security is enabled on a table, yet the application still sees every tenant’s rows. Give two likely causes.

The application connects as the table’s owner and force row level security was not set, since owners bypass policies by default. Or it connects as a superuser or a role with BYPASSRLS, which always bypass. A third possibility is a tenant setting left on a pooled connection at session level by an earlier request.

Why must the tenant setting be local to the transaction when connections are pooled?

A pooled connection is reused by later requests for other tenants. A session-level setting stays on the connection after the request ends, so a later request that fails to set its own tenant would run with the previous one and read that tenant’s data. A transaction-local setting disappears at commit or rollback.

One tenant queues 5,000 report jobs. Ten other tenants then queue one job each. Compare when the ten are served under a single first-in, first-out queue and under round-robin across tenants.

In a single queue they wait behind all 5,000. With round-robin, the queue alternates between tenants that have work, so the ten jobs are all served within the first eleven turns, and the large tenant’s remaining jobs follow.

A system has 12 workers and gives each tenant 3. How many tenants are affected by one bad tenant with plain sharding? With shuffle sharding, how many combinations are there and what share of tenants has exactly the same one?

Plain sharding makes 4 shards of 3, so a quarter of tenants, 25%, are affected. Shuffle sharding has 12 × 11 × 10 ÷ 6 = 220 combinations, so about 0.45% of tenants share all three workers. The widget confirms it.

What is the one component of a cell-based architecture whose failure affects every tenant, and how is the risk kept small?

The cell router, which maps tenants to cells. It is kept as simple as possible: a lookup and a forward, with no business logic, a mapping that changes rarely and is cached widely, and changes to it rolled out with great care.

A customer asks for all its data to be restored to its state three days ago. Why is this hard in a shared-table design, and what can be prepared in advance?

The backup contains every tenant’s rows together, so restoring it would rewind everyone. Restoring one tenant means loading the backup elsewhere and copying just that tenant’s rows back, across every table and store. Preparing means tenant-scoped keys throughout, scheduled per-tenant exports, soft deletion with an undo period, or history tables.
