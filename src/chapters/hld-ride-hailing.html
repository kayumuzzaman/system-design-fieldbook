The problem

The problem. Design a ride-hailing service. Drivers go online and their apps report where they are. A rider requests a ride from a pickup point to a destination; the service finds a driver, the driver accepts, the rider watches the car approach, and the trip is recorded from pickup to drop-off.

Three things make it hard, and they pull in different directions. The positions of drivers change constantly, so the index of where cars are is mostly writes. Choosing a driver for one rider changes the choice for the next, so matching is an optimization over everyone waiting, not a lookup. And a driver is a resource that two parts of the system may try to hand out at the same moment, which is a concurrency problem with real cars in it. met the same dispatching question inside one building; here it spans a city. In the terms of , it is a real-time matching problem over fast-changing state.

Step 2: Estimates

Uber described driver apps reporting a position every four seconds in 2015, which is a good starting assumption ():

location reports: 1 million drivers ÷ 4 s = 250,000 a second at the peak
ingest: 250,000 × about 100 bytes = 25 MB a second ≈ 200 Mbit/s
current positions: 1 million × about 100 bytes = 100 MB, which fits in memory many times over
trips: 30 million ÷ 86,400 s ≈ 350 requests a second on average, about 1,000 at the peak; about 10 state changes each
history: averaging half the peak, 125,000 reports a second × 100 bytes × 86,400 s ≈ 1.1 TB a day

The numbers sort the design into two parts. Positions are a high write rate on a small data set that may be lost, so they live in memory, partitioned by area, and are never written to a database on the request path; the history is streamed off to cheap storage. Trips are a modest write rate on data that must be durable and consistent, so they live in a sharded database with transactions. Matching sits between them, a thousand searches a second that each read a few dozen nearby drivers.

The rider’s request carries an idempotency key, so a request retried after a dropped connection returns the same trip instead of booking two cars (). The driver’s messages carry a sequence number, so a report that arrives late, behind a newer one, is ignored rather than moving the car backward on the map. Every trip event carries an id, so an acceptance delivered twice is applied once (). An offer expires: a driver who does not answer in ten seconds is treated as having declined.

Everything about free drivers is partitioned by geography: one city, or one part of a large city, belongs to one set of location and matching servers. Matching rarely needs a driver from another area, so each area can be matched by a single owner, which makes claiming a driver a local operation. Trips are partitioned differently, by trip id, because they are looked up by id from anywhere.

Step 5: The design

Driver apps keep a WebSocket to a gateway (), which routes each report to the location service owning the driver’s area. That service overwrites the driver’s position in memory and, if the driver crossed into another cell, moves the id between cells. A request goes to the trip service, which writes the trip and asks the area’s matching service for a driver.

Step 6a: A quarter of a million positions a second

Most of the 250,000 reports a second change almost nothing. A car at 25 km/h moves about 28 m in four seconds, and the index only changes when a car crosses into another cell. For a car moving in a straight line, the chance of crossing a boundary between two reports is about (4/π) × distance ÷ cell size. The chapter’s code drove 2,000 simulated cars around a city for half an hour and measured it:

With 500 m cells, 93% of reports are a single overwrite in memory, and the rest move an id between two sets. That is why positions live in an in-memory grid, or in a store such as Redis with its geospatial commands, and never in a database that would write each report to disk (). The cell size is a trade-off: smaller cells make the index change more often, larger ones make each search read more drivers.

// A location report. Returns true when the driver moved into another cell, the only case
  // that touches the index; otherwise only the stored position changes.
  report(id: string, p: Point): boolean {
    const cell = this.cellOf(p);
    const old = this.where.get(id);
    this.where.set(id, { x: p.x, y: p.y, cell });
    if (old && old.cell === cell) return false;
    if (old) this.cells.get(old.cell)?.delete(id);
    let set = this.cells.get(cell);
    if (!set) this.cells.set(cell, (set = new Set()));
    set.add(id);
    return true;
  }

Finding nearby drivers is a search outward in rings of cells: the request’s own cell, then the eight around it, and so on, stopping when the drivers found are closer than any cell not yet searched could be.

// The k nearest drivers in straight-line distance: search rings of cells outward until the
  // nearest k found are closer than any cell not yet searched could be.
  nearest(p: Point, k: number, maxMeters = 10_000): { ids: string[]; examined: number; cells: number } {
    const cx = Math.floor(p.x / this.size), cy = Math.floor(p.y / this.size);
    const found: Array<{ id: string; d: number }> = [];
    let examined = 0, cells = 0;
    for (let ring = 0; ring * this.size <= maxMeters + this.size; ring += 1) {
      for (let dx = -ring; dx <= ring; dx += 1) {
        for (let dy = -ring; dy <= ring; dy += 1) {
          if (Math.max(Math.abs(dx), Math.abs(dy)) !== ring) continue; // only the ring's edge
          cells += 1;
          for (const id of this.cells.get(this.key(cx + dx, cy + dy)) ?? []) {
            const w = this.where.get(id) as { x: number; y: number };
            examined += 1;
            found.push({ id, d: Math.hypot(w.x - p.x, w.y - p.y) });
          }
        }
      }
      found.sort((a, b) => a.d - b.d);
      // Anything in a ring not yet searched is at least `ring * size` away from p.
      if (found.length >= k && (found[k - 1] as { d: number }).d <= ring * this.size) break;
    }
    return { ids: found.slice(0, k).filter((f) => f.d <= maxMeters).map((f) => f.id), examined, cells };
  }

In the test, with 20,000 drivers in a 20 km city and 500 m cells, finding the five nearest examined 109 drivers on average and always agreed with a full scan of all 20,000. Straight-line distance only makes the shortlist: a driver 300 m away across a river may be ten minutes away by road, so the shortlist goes to the routing service for travel times, and those decide.

In production. Reports cost the driver’s battery and data plan as well as the servers. Apps commonly report less often when the car is parked or the driver is offline, and more often during a pickup, when the rider is watching. Each report carries its own time and sequence number, because a phone that loses signal sends a burst of old positions when it reconnects, and only the newest should move the car.

Step 6b: Matching one at a time, or together

The obvious rule is to give each rider, as they arrive, the nearest free driver. It is fast and fair to that rider, and it can be poor for the next. If rider A is 1 minute from driver X and 2 minutes from driver Y, while rider B is 1 minute from X and 9 minutes from Y, serving A first with X costs 1 + 9 = 10 minutes of pickup, where the other pairing costs 3. Batched matching waits a few seconds, collects everyone waiting and every free driver nearby, and chooses the pairs that minimize the total time to pickup. That choice is the assignment problem, solved exactly by the Hungarian method.

When free drivers are plentiful, the nearest one is nearly always the best one, and batching only adds its few seconds of delay. As drivers become scarce, each match takes a driver someone else needed, and choosing pairs together shortened the wait by 12 to 19%. The near-capacity rows show something else as well: waits grew much faster than demand, because a driver sent across town to a pickup is a driver not carrying anyone, which leaves fewer free drivers and makes the next pickup longer still. Uber describes its matching in the same terms: in the seconds after a request, nearby riders and drivers are evaluated in one batch, to reduce the average wait for everyone rather than to give each rider the closest car.

Common mistake. Matching by straight-line distance. It is the right way to shortlist and the wrong way to choose: rivers, one-way streets and motorways make the nearest car a slow one surprisingly often. Shortlist by distance, then rank by travel time from the routing service.

Step 6c: Never sending one car to two riders

The same driver can look free to two matching decisions at once: two batches in overlapping areas, a retry of a request, or a driver who is still being offered one trip when another needs them. If each decision reads “free” and then writes “taken”, both succeed. In the chapter’s test, two dispatchers that did exactly that against a store with a delay between the read and the write both got the driver. The fix is a single compare-and-set: take the driver only if they are still free, as one operation, the atomic update of . The same test with a claim assigned the driver once.

// Each driver is either free or held by one trip. Claiming is a compare-and-set, so two
// dispatchers that pick the same driver at the same moment cannot both get them.
export class Drivers {
  private readonly holder = new Map();
  add(driver: string): void {
    this.holder.set(driver, null);
  }
  claim(driver: string, trip: string): boolean {
    if (this.holder.get(driver) !== null) return false; // unknown, or already held
    this.holder.set(driver, trip);
    return true;
  }
  release(driver: string, trip: string): boolean {
    if (this.holder.get(driver) !== trip) return false; // only the holder may release
    this.holder.set(driver, null);
    return true;
  }
  heldBy(driver: string): string | null | undefined {
    return this.holder.get(driver);
  }
}
apply(e: TripEvent): "applied" | "duplicate" | "refused" {
    if (this.seen.has(e.id)) return "duplicate";
    const rule = allowed[e.type];
    if (!rule.from.includes(this.state)) return "refused";
    this.seen.add(e.id);
    this.state = rule.to;
    if (e.type === "offer") this.driver = e.driver;
    if (e.type === "decline" || e.type === "expire") this.driver = null;
    this.history.push(this.state);
    return "applied";
  }
}

A trip is a small state machine (). Every change arrives as an event with an id, is applied only if the current state allows it, and is recorded with the trip in one transaction. That makes the messy parts of mobile networks harmless: an acceptance delivered twice is recognized as a duplicate, and an event that makes no sense in the current state, such as completing a trip that never started, is refused rather than corrupting the record. An offer that expires returns the trip to requested and releases the driver, and matching tries the next candidate.

At ten times the scale, 10 million drivers online, reports reach 2.5 million a second and positions 1 GB. Since areas are independent, that is more areas and more servers, and busy cities are split into several areas, with matching near a boundary allowed to consider drivers from the neighbor. The trips database grows to 3,500 requests a second on average, still modest for a sharded database. At a hundred times the limit is not throughput but the size of each area’s matching problem: the densest areas at peak can hold thousands of riders and drivers in one batch, and the matcher must split them into smaller regions or settle for faster approximate assignments.

In the real world

  • Uber’s dispatch system, as described in March 2015, received driver locations “every four seconds”, indexed them with Google’s S2 cells, spread its state over servers with Ringpop, a consistent hash ring with SWIM gossip for membership (), and was mostly written in Node.js. Instead of replicating dispatch state between data centers, the server returned an encrypted digest of a driver’s state with each location update, so that after a data center failure another one could resume from the digest the driver’s phone sent back.
  • H3, Uber’s hexagonal grid, described in June 2018 and open-sourced that year, has 16 resolutions, each cell one seventh the area of its parent, built from 122 base cells. Uber used it for pricing by supply and demand within hexagons, and for dispatch and marketplace analysis.
  • Batched matching is how Uber describes its current matching, as of October 2026: nearby drivers and riders are evaluated together in the seconds after a request, to reduce the average wait for everyone. Its earlier approach matched each rider immediately to the closest available driver.

Key points

  • Two kinds of state: positions, a high write rate that may be lost, in memory by area; trips, durable and consistent, in a sharded database by id.
  • Most location reports do not change cell: 7% with 500 m cells at city speeds, matching (4/π) × distance ÷ cell size. The rest are overwrites.
  • Search nearby drivers outward in rings of cells; in the test that read about 100 drivers instead of 20,000. Then rank the shortlist by travel time.
  • Greedy matching is fine when cars are plentiful. Near capacity, batching everyone waiting and solving the assignment cut waits by 12 to 19% in the simulation.
  • Claim a driver with one compare-and-set; reading “free” and then writing “taken” double-booked in the test.
  • Model the trip as a state machine whose events carry ids, and make requests idempotent, so retries and duplicates change nothing.
  • Partition by area so each city is matched by one owner, and let positions rebuild themselves from the next reports after a failure.

Check yourself

Why are driver positions kept in memory rather than in a database?

There are hundreds of thousands of reports a second, each replacing the last, and a position is worthless a minute later. Losing them costs nothing, since every driver reports again within seconds. A database would spend durable writes on data that does not need durability.

A car moves 28 m between reports. About what share of reports moves it into another cell of 500 m, and why does that matter?

About (4/π) × 28 ÷ 500 ≈ 7%, which the simulation confirmed. Only those reports change the cell index; the other 93% overwrite a position, so the index costs almost nothing to keep current.

When does the ring search stop, and why is that correct?

When it has found at least k drivers and the k-th nearest is closer than the inner edge of the next ring. Any driver in an unsearched ring is at least that far away, so none can be nearer than those already found.

Riders A and B and drivers X and Y: A is 1 min from X and 2 from Y; B is 1 min from X and 9 from Y. Compare greedy and batched matching.

Greedy, serving A first, gives A the nearest, X, and leaves B with Y: 1 + 9 = 10 minutes of pickup. Batched matching considers both and gives A Y and B X: 2 + 1 = 3 minutes.

Why did batching help little when drivers were plentiful in the simulation?

With many free drivers spread around, the nearest driver for each rider is rarely the one another rider needs, so the greedy choice is already close to the best, and batching only adds its few seconds of waiting.

Two matchers both see driver d235 as free. What goes wrong without a compare-and-set, and what does the claim guarantee?

Each reads “free”, then writes “taken”, and both offer the driver a trip, so one rider is promised a car that will not come. A claim is one atomic operation that succeeds only if the driver is still free, so exactly one matcher gets the driver and the other moves on to its next candidate.

A driver’s “accept” arrives twice because the app retried. What does the trip do with the second one?

Nothing. The event carries an id that the trip has already applied, so it is recognized as a duplicate and ignored, and the trip’s state and history are unchanged.
