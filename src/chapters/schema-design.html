Design for the changes you cannot see yet

argued for starting with a relational database. This chapter is about using one well. A schema is the definition of the tables, columns, types, keys and constraints. A good one has two properties that pull against each other: it makes wrong data hard to store, and it can be changed as the product changes.

The method is short. Identify the things the system must remember, called entities. Give each a table. Work out how they relate. Then check the result against the queries from your access patterns.

Entities and relationships

Relationships between entities come in three shapes, and each has one standard representation.

RelationshipExampleHow to store it
One to manyA user posts many photos. Each photo has one owner.A foreign key on the “many” side: photos.owner_id
Many to manyA user likes many photos. A photo is liked by many users.A third table with one row per pair: likes (user_id, photo_id)
One to oneA user has one set of notification settingsExtra columns on the same table, or a second table whose primary key is also a foreign key

The table that represents a many-to-many relationship is called a join table. Its primary key is usually the pair of foreign keys, which has a useful side effect: the database itself guarantees that a user cannot like the same photo twice. Join tables often turn out to be entities in their own right. A like has a time. A follow may have a notification preference. Give them the columns they need.

Choosing keys

Every table needs a primary key, and the choice is hard to change later because other tables refer to it.

  • A natural key is something meaningful that is already unique, such as an email address or a country code. The trouble is that meaningful things change. People change email addresses, and a key that changes must be updated in every table that refers to it.
  • A surrogate key is an identifier with no meaning, generated by the system. It never needs to change. Use one for nearly every table, and enforce the natural uniqueness with a separate unique constraint: id as the primary key, and UNIQUE (email) beside it.

The two common kinds of surrogate key have different strengths.

Sequential integerUUID
Size8 bytes16 bytes
Generated byThe database, one at a timeAnyone, anywhere, with no coordination
RevealsHow many rows exist and roughly when each was made. Easy to guess neighbors.Nothing, for random UUIDs

A sensible default is a 64-bit integer for internal tables and a time-ordered UUID (version 7) where IDs are created outside the database or shown to the outside world. Whatever you choose, do not let an ID in a URL serve as the access check. That the ID is hard to guess is no substitute for verifying that the caller may see the record (). covers generation schemes in depth.

Normalization

Normalization is the process of arranging tables so that each fact is stored in exactly one place. The reason is easiest to see from a table that breaks the rule.

The single wide table suffers from three problems, traditionally called anomalies:

  • Update anomaly. Ana changes her email. Three rows must change, and if one is missed the data contradicts itself.
  • Insert anomaly. A new product cannot be recorded until someone orders it, because there is no row to put it in.
  • Delete anomaly. Deleting Ben’s only order erases the fact that Ben is a customer.

The normal forms are a sequence of rules that remove these problems. Three are enough for practical work.

FormRuleWhat it rules out
First (1NF)Each column holds one value, and there are no repeating groups of columnsA tags column holding "beach,sunset", or columns phone1, phone2, phone3
Second (2NF)Every non-key column depends on the whole key, not on part of itIn a table keyed by (order, product), storing the customer’s email, which depends on the order alone
Third (3NF)Non-key columns depend on the key and not on each otherStoring both postcode and city on an order when the city follows from the postcode

An old summary covers all three: every non-key column must provide a fact about the key, the whole key, and nothing but the key. In practice, people who think in terms of entities arrive at third normal form without consulting the rules. If a table mixes facts about two different things, split it.

A fact, or a copy of a fact?The paid column in order_items looks like a duplicate of the product’s price. It is a different fact: what this customer was charged at the time. If the product’s price rises next month, past orders must not change. A value that records history is not redundancy, and removing it would be a bug.

Start normalized. A normalized schema is correct by construction, compact, and flexible in the queries it supports. Its cost is that reads need joins, and that is the cost the next section addresses.

Denormalization, on purpose

Denormalization means storing a fact in more than one place, or storing a value that could be computed, to make reads cheaper. Every feed in the photo app shows a like count beside each photo. Counting rows in likes for each of twenty photos on every page view is wasteful when the same number is requested thousands of times between changes. So the schema gains a like_count column on photos.

That column is a second copy of information that the likes table already holds, and from this moment the two can disagree. Denormalization is a trade of write complexity for read speed, and it should be made knowingly. The common forms:

FormExampleHow it goes stale
Counter or aggregatephotos.like_count, users.follower_countA like is recorded and the counter update fails or is forgotten
Copied columnThe author’s username stored on each commentThe user renames and old comments keep the old name
Precomputed resultA table holding each user’s feed, ready to readAny change to the inputs not propagated
Materialized viewA stored query result that the database refreshesStale between refreshes

Three rules keep it under control.

  1. One copy is the truth. Decide which, and treat the others as derived data that could be rebuilt from it. The likes table is the truth. The counter is a cache that happens to live in a column.
  2. Choose how the copies are kept in step. In the same transaction as the original write, which is always consistent and makes the write slower. Or afterward, by a background process reacting to changes, which is faster and leaves the copy briefly behind. Pick according to how wrong the value is allowed to be, and for how long.
  3. Be able to repair it. Have a job that recomputes derived values from the source, and run it periodically. Counters drift in every real system.

Denormalization is the first of several techniques with the same shape: a cache (), a search index () and a read model in an event-driven system () are all derived copies with the same three questions attached.

Types and constraints

The schema is the last line of defense against bad data. Code changes weekly and has bugs. A constraint holds for every writer, forever. Some choices matter more than they look.

  • Money is never a floating-point number. Binary floating point cannot represent most decimal fractions, so 0.1 + 0.2 gives 0.30000000000000004. Store an integer count of the smallest unit, such as cents, or use an exact decimal type. Store the currency next to it.
  • Timestamps are stored in UTC, with a type that knows about time zones. In PostgreSQL that is TIMESTAMPTZ. Convert to local time when displaying. A timestamp without a zone is a number whose meaning depends on which server wrote it.
  • Columns are NOT NULL unless absence is meaningful. Every nullable column is a case that all code reading it must handle.
  • Use the database’s rules. UNIQUE for uniqueness, foreign keys for references, CHECK for ranges and allowed values. explained why checks in application code are unreliable under concurrency.
  • Use a JSON column for the part that really varies, such as per-integration settings, and ordinary columns for anything you filter, join or constrain on.
  • Store files elsewhere. Images and documents belong in object storage, with the object’s key in a column ().
  • Add created_at and updated_at to almost every table. You will want them during the first incident.
CREATE TABLE order_items (
  order_id    BIGINT  NOT NULL REFERENCES orders (id),
  product_id  BIGINT  NOT NULL REFERENCES products (id),
  quantity    INTEGER NOT NULL CHECK (quantity > 0),
  paid_cents  BIGINT  NOT NULL CHECK (paid_cents >= 0),
  currency    CHAR(3) NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (order_id, product_id)
);

Soft deletes

A soft delete marks a row as deleted, typically with a deleted_at timestamp, instead of removing it. It allows undo and preserves history, and it has costs that are easy to miss. Every query must remember to exclude deleted rows, and one that forgets shows users data they removed. Unique constraints stop working as intended, since a deleted user’s email still occupies the slot. A partial unique index over only the live rows solves that. And the data is not gone, which matters when a law gives users the right to have it erased. Use soft deletes where undo has real value, and prefer moving rows to an archive table when the goal is only to keep history.

Patterns that come up repeatedly

  • Hierarchies, such as comment threads or folders. The simplest form is a parent_id column pointing at the same table. Reading a whole subtree then needs a recursive query, which SQL supports. If subtrees are read far more often than they change, store each row’s full path as well.
  • Status and history. A status column answers “what state is this order in?”. It cannot answer “when did it ship, and who canceled it?”. For anything that moves through states, add a table of transitions with one row per change. The status column is then a denormalized copy of the latest one.
  • One reference, several possible targets. A comment might attach to a photo or to a video. A pair of columns target_type and target_id is tempting and cannot be protected by a foreign key. Alternatives are a separate nullable foreign key column for each target type with a check that exactly one is set, or a shared parent table that both photos and videos refer to.
  • Many tenants in one database. Put the tenant’s ID on every table and at the front of every index, so that one customer’s queries never scan another’s rows. covers the options.

Changing a schema on a live system

A schema is never finished. The hard part is that the database and the application cannot be changed at the same instant. During any deployment, old and new versions of the code run side by side for minutes (), and a rollback puts the old code back entirely. So there is one governing rule:

Every schema change must work with both the previous and the next version of the application.

Renaming a column in one step breaks this at once. The old code asks for a column that no longer exists. The answer is to split every breaking change into small steps, each compatible with its neighbors. This is known as the expand and contract pattern.

Migrations are written as numbered scripts kept in version control and applied in order by a migration tool, so that every environment reaches the same schema by the same path. Treat them as code: review them, and test them against a copy of production-sized data.

The lock problem

The second hazard is specific to large tables. Many schema changes need a brief exclusive lock on the table. The change itself may take a millisecond, and the danger is in the waiting. If a long-running query is using the table, the schema change waits behind it. Every other query on that table then queues behind the waiting schema change. A one-millisecond change behind a ten-minute report becomes a ten-minute outage of that table.

The defense is to make the migration give up quickly and try again later:

SET lock_timeout = '3s';
ALTER TABLE photos ADD COLUMN alt_text TEXT;

Beyond that, each kind of change has a safe form. The table lists them for PostgreSQL. MySQL has equivalents, and for very large tables its users rely on tools such as gh-ost and pt-online-schema-change, which build a new copy of the table in the background and swap it in.

Add a columnSmall. Fast even with a constant default.Add it nullable, or with a constant default, under a lock timeout

ALTER TABLE users ADD CONSTRAINT display_name_present
  CHECK (display_name IS NOT NULL) NOT VALID;                -- instant: applies to new writes only
ALTER TABLE users VALIDATE CONSTRAINT display_name_present;  -- scans, without blocking writes
ALTER TABLE users ALTER COLUMN display_name SET NOT NULL;    -- instant: the constraint proves it
ALTER TABLE users DROP CONSTRAINT display_name_present;

UPDATE users SET display_name = name
WHERE id IN (SELECT id FROM users WHERE display_name IS NULL LIMIT 5000);

In production. Separate schema changes from code deployments. A release that needs a schema change is at least two deployments: the migration, which the current code must tolerate, and then the code that uses it. Contracting steps, such as dropping a column, should trail by days. Once a column is dropped, rolling back the application no longer works.

In an interview. When sketching tables, state the primary key, the foreign keys and the one or two indexes each query needs, and mention any deliberate denormalization with how it is kept in step: “a like_count column on photos, updated in the same transaction as the like”. If asked how you would change the schema later, “expand and contract, so old and new code both work throughout” is the answer that shows production experience.

Schemas outside relational databases

Databases that do not enforce a schema still have one. It lives in the code that reads the data, and the migration problem takes a different form. Old documents are not rewritten when the code changes, so every shape ever written stays in the database. Two habits help. Include a version number in each document so readers know what they are looking at. And make readers tolerant: ignore fields they do not know, and supply defaults for fields that are missing. The same discipline applies to messages on a queue and to API payloads, both of which are also read by code older or newer than the code that wrote them. returns to this under the name schema evolution.

Common mistakes

  • Lists in a column, such as comma-separated IDs, where a join table belongs.
  • Natural keys as primary keys, followed by the day the “permanent” value changes.
  • Denormalizing first, before measuring that a join is the problem.
  • Derived values with no way to recompute them.
  • Floating-point money and timestamps without zones.
  • Everything nullable, and rules enforced only in application code.
  • Renaming or dropping in one step on a system that deploys gradually.
  • Schema changes without a lock timeout on busy tables.
  • Updating millions of rows in one transaction.
  • Migrations tested only on an empty database.

Key points

  • Model entities as tables, one-to-many relationships as foreign keys and many-to-many relationships as join tables.
  • Use surrogate primary keys and enforce natural uniqueness with separate constraints.
  • Normalize first: each fact in one place. Third normal form is the practical target.
  • Denormalize deliberately, for measured read costs. Name the source of truth, choose how copies stay in step, and keep a way to rebuild them.
  • Let the schema defend the data with types, NOT NULL, uniqueness, foreign keys and checks.
  • Every schema change must be compatible with the application version before it and the one after. Breaking changes are done as expand, migrate, contract.
  • On large tables, use lock timeouts, concurrent index builds, unvalidated constraints and batched backfills.

Check yourself

A table enrollments (student_id, course_id, course_title, grade) has the primary key (student_id, course_id). Which normal form does it violate, and what goes wrong?

Second normal form. The course title depends on the course alone, which is only part of the key. The title is repeated on every enrollment, so renaming a course means updating many rows and risks leaving some unchanged. Move the title to a courses table.

An order stores the price the customer paid, although the product table also has a price. Is that denormalization?

No. The price paid is a historical fact about the order and must not change when the product’s current price does. It is a separate fact that happens to start with the same value.

You add a follower_count column to users. What three things should you decide at the same time?

Which data is the source of truth, here the follows table. How the counter is kept in step, in the same transaction as each follow or asynchronously. And how to repair it when it drifts, with a job that recounts from the follows table.

Why is renaming a column in a single migration dangerous on a system that deploys without downtime?

During the deployment both old and new code are running. The old code refers to the old name and fails as soon as the rename is applied, and if the new code has to be rolled back, the old code is broken entirely. The rename has to be split into steps where both names work for a while.

A migration that adds a column, normally instant, takes a busy table offline for several minutes. What happened?

The change needed an exclusive lock and had to wait for a long-running query to finish. While it waited, every new query on the table queued behind it. A lock timeout on the migration would have made it give up after a few seconds so it could be retried at a better moment.

Why should a backfill of ten million rows be done in batches?

A single statement would run as one long transaction, holding row locks throughout, generating a very large amount of log at once, delaying replicas and preventing cleanup of old row versions. Small batches keep each transaction short and let the system keep up.
