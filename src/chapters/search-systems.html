Why a database query is not search

Suppose the photo app wants a search box over captions. The first attempt is one line of SQL:

SELECT id, caption FROM photos WHERE caption LIKE '%sunset%';

This fails in three separate ways, and each points to a part of what a search system does.

  • It is slow. A pattern that starts with a wildcard cannot use a B-tree index (), so the database reads every caption. With a hundred million photos that is seconds per query.
  • It matches characters, and people search for meanings. It will not find “Sunsets” with a capital letter, or “sun set”, or “sunsett” typed in a hurry, and it will happily match “sunsetter” and other strings that merely contain the letters.
  • It has no notion of better and worse. Ten thousand rows come back in whatever order the database finds them. A search user looks at the first five results and nothing else.

A search system addresses each: a different index structure for speed, a text processing step for language, and a scoring function for order.

The inverted index

A table maps each document to its words. Search needs the reverse: for each word, the documents that contain it. That reversed mapping is the inverted index, and it is the same structure as the index at the back of a book.

Each distinct word is a term, and the list of documents for a term is its postings list. The terms are kept in a sorted, compact structure so that any one can be found in a few steps. Postings lists are kept sorted by document ID, which makes combining them cheap: a query for two words walks both lists together and keeps the IDs that appear in both, in a single pass. The same walk handles OR and NOT.

Real postings hold more than IDs. They record how many times the term occurs in each document, which ranking needs, and at which positions, which makes it possible to search for an exact phrase or for words near each other.

Analysis: from text to terms

The index in the figure contains “light” where the caption said “lights”, and has no entry for “at” or “the”. Text is not indexed as written. It passes through an analyzer, a small pipeline that turns a string into the terms that will represent it.

The usual stages are these:

  1. Tokenizing splits text into words. This is easy for English and hard for languages written without spaces, such as Chinese, Japanese and Thai, which need dictionaries or statistical models.
  2. Normalizing removes differences that should not matter: case, accents, variant forms of the same character.
  3. Removing stop words drops extremely common words such as “the” and “at”. Modern systems often keep them, since they are needed for phrases like “to be or not to be”.
  4. Stemming reduces words to a common root, so that “running”, “runs” and “runner” can match one another. The rules are specific to each language.
  5. Expanding synonyms, so that “tv” also matches “television”.

The rule that makes this work is that the same analysis is applied to the query. The user’s “RUNNERS café” becomes runner and cafe, and those are looked up. If documents and queries are analyzed differently, nothing matches, which is the first thing to check when a search mysteriously returns no results.

Analysis is also where search quality is won or lost. Stem too aggressively and “university” matches “universe”. Too little and “shoes” does not match “shoe”. Each field of a document can have its own analyzer: a product name analyzed for language, a product code indexed exactly as written.

Ranking: which results come first

Finding matching documents is the easy half. Ordering them is the half that users judge. Every match is given a relevance score, and results are returned in order of score. The standard scoring function for text is BM25, the default in Lucene, Elasticsearch and OpenSearch. It combines three ideas that are each intuitive.

  • Term frequency. A document that mentions “sunset” three times is probably more about sunsets than one that mentions it once. The benefit levels off, so the tenth mention adds almost nothing. That stops a document from winning by repetition.
  • Inverse document frequency. A rare term tells you more than a common one. In a query for “blue heron”, a match on “heron” is worth far more than a match on “blue”, because few documents contain it.
  • Length normalization. A word appearing once in a five-word caption matters more than once in a five-page article.
score(query, doc) = sum over each query term t of IDF(t) × tf × (k + 1) ÷ (tf + k × (1 − b + b × length ÷ average length)) tf = times t occurs in doc k = 1.2 and b = 0.75 by default

You will rarely compute this by hand. What matters is knowing that the score is built from these three ingredients, so that when a result ranks strangely you can ask which one caused it.

Text relevance alone is seldom the right order for a product. Two photos matching “sunset” equally well should not be tied if one has ten thousand likes and the other has none. Production ranking blends the text score with other signals:

  • Field weights. A match in the title counts for more than a match in the description.
  • Quality and popularity: likes, sales, ratings, click-through rate.
  • Freshness, for news and social content.
  • Personalization: the user’s language, location and history.

Large systems go further and train a model on what users clicked to combine hundreds of such signals, usually applied only to the top few hundred candidates that the cheap text score has already selected. returns to this two-stage pattern.

Measuring qualityRelevance is judged by people, so it has to be measured. Keep a set of real queries with the results that should appear for each, and score every ranking change against it. Watch live signals too: the share of searches with no results, the share with no click, and how far down the list people click. A change that looks better to its author and worse on these numbers is worse.

The distinction between a filter and a scored query is worth holding on to. “Photos by Ana from this year matching sunset” has two filters and one text query. Only the text part needs scoring. Search engines execute filters first and cheaply, and it is a common inefficiency to express a filter as a scored clause.

How the index is stored

Most open-source search engines are built on the Apache Lucene library, and its storage design will be familiar from . An inverted index is expensive to modify in place, since adding one document touches the postings of every term in it. So Lucene never modifies. New documents are collected in memory and written out periodically as a small, complete, immutable index called a segment. A search queries all segments and combines the results. A background process merges small segments into larger ones.

The consequences mirror those of an LSM tree.

  • Search is near real time, not real time. A document becomes searchable when its segment is opened to readers, an operation called a refresh. In Elasticsearch this happens once a second by default. Something indexed now may not appear in a search for up to a second.
  • Deletes are markers. A deleted document is flagged and skipped at query time. Its space is reclaimed when its segment is merged.
  • Updates are a delete and an insert. There is no changing one field in place. The whole document is indexed again.
  • Indexing fast and searching fast compete. Frequent refreshes create many small segments, which slows searches until they are merged. Bulk loads go faster with refreshes turned down.

Alongside the inverted index, the engine keeps a column-oriented copy of the fields used for sorting, filtering and facets, since those need “the values for this document” and not “the documents for this value”.

Search across many machines

An index too large for one machine is divided into shards, each a complete Lucene index holding a subset of the documents, and each shard has replicas. This is the partitioning and replication of the previous two chapters with one notable difference. Documents are assigned to shards by a hash of their ID. A search for a word could match documents on any shard, so nearly every query is a scatter-gather.

Three practical consequences follow.

  • Deep pagination is expensive. To return results 10,001 to 10,010, every shard must produce its top 10,010 and the coordinator must sort all of them. Engines cap how deep ordinary paging can go. The alternative is the same as for databases: continue from the last result’s sort values (). Few people read page 500 of search results, so it is reasonable for the product not to offer it.
  • Tail latency grows with shard count, since the query waits for the slowest shard (). More shards are not free.
  • The number of primary shards is hard to change. As with any hash partitioning, it is fixed when the index is created, and changing it means rebuilding. Elastic’s guidance is to aim for shards of tens of gigabytes, which gives a way to choose the number from the expected data size.

When queries always concern one tenant or one user, documents can be routed to a shard by that key instead, and a search then visits one shard. For time-based data such as logs, the standard practice is one index per day or week, so that searches over recent data touch only recent indexes and old data is removed by deleting an index.

Keeping the index in step with the database

A search index is not where data is first written. The database is the source of truth, and the index is a copy in a different shape, derived data in the sense of . Every design must answer how changes get from one to the other.

ApproachHow it worksProblem
Dual writeThe application writes to the database and then to the search indexNo transaction spans the two. If the second write fails, or two requests’ writes arrive in different orders, the index is wrong and stays wrong.
Periodic rebuildA job reindexes everything, or everything changed since the last runSimple and robust, and the index is stale between runs. Deletes are easy to miss.
Queue of changesThe application records each change in an outbox table within the same transaction, and a worker indexes from itReliable. Requires discipline in every code path that writes.
Change data captureA process reads the database’s own log and feeds every committed change to an indexerReliable and needs no application changes. More infrastructure to run.

The last two rows are the ones to use for anything that matters, and covers the mechanics. Whichever you pick, four details need attention.

  • The index lags. A user who creates something and immediately searches for it may not find it. Either show the user’s own new item from the database, or accept and explain the delay.
  • Deletes and permission changes must propagate, and faster than anything else. A document that still appears in search after being deleted or made private is a privacy incident.
  • Plan to rebuild. Changing an analyzer or a field’s type requires reindexing every document. Build the new index beside the old one, switch a name that points to the current index (an alias), and delete the old one. If you cannot rebuild the index from the database at will, the index has quietly become a second source of truth.
  • Return IDs, then load. A common pattern has the search engine return only matching IDs in order, and the application load the current rows from the database. Results then reflect current data and current permissions, at the cost of a second lookup.

Common mistake. Using the search engine as the primary database because it can store documents and is already there. It gives up what a database is for: there are no multi-document transactions, writes are not visible until the next refresh, and replicas have historically been able to lose acknowledged writes under some failures. Keep the authoritative copy in a database and treat the index as disposable.

Searching by meaning

Everything so far matches words. A search for “dog on a beach” will not find a photo captioned “golden retriever by the sea”, because no words are shared. Semantic search closes that gap. A machine learning model turns each text, or image, into an embedding, a list of a few hundred to a few thousand numbers, arranged so that items with similar meaning have nearby values. The query is embedded the same way, and the search returns the items whose embeddings are closest.

Finding the nearest among millions of such vectors exactly would mean comparing against all of them, so vector indexes find approximate nearest neighbors, trading a little accuracy for a great deal of speed. describes how.

Each method has blind spots the other covers.

Keyword search (BM25)Vector search
FindsThe exact wordsSimilar meanings, with no words in common
Strong onNames, codes, part numbers, rare terms, exact phrasesNatural-language questions, synonyms, other languages
Weak onParaphrase and vocabulary mismatchExact identifiers, and terms the model never saw
Explaining a resultEasy: these words matchedHard
CostLowEmbedding every document and query, and a memory-heavy index

The current standard practice is hybrid search: run both, and merge the two ranked lists. A simple and effective way to merge is reciprocal rank fusion, which scores each document by its positions in the two lists, without needing the two kinds of score to be comparable. A stronger model then often re-ranks the top few dozen. Elasticsearch, OpenSearch and PostgreSQL with the pgvector extension all support storing vectors beside text, so hybrid search does not require a separate system.

When a design needs search, say that it is a separate index derived from the primary database, name how it is kept current (“change data capture into a queue, an indexer consuming it”), and acknowledge the lag. Common mistakes

  • LIKE '%term%' on a large table.
  • Writing to the database and the index from application code with nothing to reconcile them.
  • Treating the search index as the source of truth.
  • Analyzing queries differently from documents.
  • Judging relevance by a handful of queries the developer thought of, with no measurements.
  • Offering unlimited deep pagination.
  • Too many small shards, or a shard count chosen without estimating data size.
  • Forgetting deletes and permission changes in the indexing pipeline.
  • Exposing the search cluster to the internet, or letting users send arbitrary query syntax to it.
  • Vector search alone for a catalog full of product codes and names.

Key points

  • Search needs speed, an understanding of language and an ordering by relevance. A database’s pattern matching provides none of them.
  • An inverted index maps each term to the documents containing it. Queries look up terms and combine sorted lists.
  • Analysis turns text into terms by tokenizing, normalizing and stemming. The same analysis must be applied to queries.
  • BM25 scores a match from term frequency, term rarity and document length. Products blend it with popularity, freshness and other signals, and measure the result.
  • Indexes are stored as immutable segments that are merged in the background, which makes search near real time.
  • A distributed search fans out to every shard and merges. Deep pagination and many shards are costly.
  • The index is derived data. Feed it from the database’s committed changes, expect lag, and be able to rebuild it.
  • Keyword search and vector search fail in different ways. Hybrid search combines them.

Check yourself

A user searches for “Running Shoes” and a product titled “running shoe” is not found. Where would you look first?

At the analyzers. The query and the document must be reduced to the same terms. If the document field is stemmed and lower-cased and the query is not, or the reverse, “shoes” and “shoe” or “Running” and “running” do not match. Check that both sides use the same analysis.

In a query for “vintage camera”, a document matches only “vintage” and another matches only “camera”. The index has 200 documents containing “vintage” and 50,000 containing “camera”. Which is likely to score higher, and why?

The one matching “vintage”. Rare terms carry more weight because they discriminate better between documents. That is the inverse document frequency part of the score.

A user publishes a post and searches for it at once. It is missing. Thirty seconds later it appears. Name two contributing causes.

The pipeline from the database to the index is asynchronous, so the change takes time to arrive at the indexer. And once indexed, a document becomes searchable only at the next refresh. Both add delay. The usual remedy is to show the user’s own new content from the database.

Why is requesting page 2,000 of search results across 20 shards so much more expensive than page 1?

For page 1, each shard returns its top 10 and the coordinator sorts 200 entries. For page 2,000, each shard must return its top 20,000, and the coordinator must sort 400,000 entries to find ten. The cost grows with the depth multiplied by the number of shards.

Your code writes to the database and then to the search index. Describe a sequence that leaves them permanently inconsistent.

The database write commits and the index write fails because of a timeout or a crash in between, so the index never learns of the change. Or two updates to the same record commit in one order and reach the index in the other, leaving the older version indexed. Feeding the index from the database’s ordered change stream avoids both.

A catalog search must handle “waterproof jacket for hiking” and also “SKU-88213-B”. Which kind of search suits each, and what do you build?

The descriptive phrase benefits from vector search, which matches meaning. The product code needs exact keyword matching, which vector search handles poorly. Build hybrid search that runs both and merges the rankings.
