A contract about what clients may see

showed a user posting a comment and failing to see it a moment later, because her read went to a copy that had not caught up. Whether that is a bug depends on what the system promised. A consistency model is that promise: a statement of which results a client may observe when it reads and writes data that is stored in more than one place.

The word “consistency” is badly overloaded, so it helps to fix the meaning here.

Stronger models are easier to program against, since the system behaves more like a single machine. They are also slower and less available, because they need machines to coordinate before answering. The models form a ladder, and the art is to stand on the lowest rung that keeps each feature correct.

Linearizability: the illusion of one copy

The strongest model in common use is linearizability. A linearizable system behaves as if there were a single copy of the data and every operation took effect at one instant, somewhere between the moment the request was sent and the moment the reply arrived. Two consequences follow, and they are what you would expect from a variable in a single program.

  • Once a write has completed, every read that starts afterward returns that value or a newer one.
  • Once any client has read a new value, no later read by anyone returns the older one.

Some things cannot be built correctly on anything weaker.

  • Locks and leader election. If two nodes can each read “the lock is free” and each take it, it is not a lock.
  • Uniqueness. Guaranteeing that a username, a seat or an order number is claimed once requires everyone to agree on who got there first.
  • Limits that must not be crossed, such as a balance that may not go negative or stock that may not be oversold.

The cost is coordination. To be sure a read reflects the latest write, a replica must confirm with others that it is not out of date, or all reads must go to one node that is known to be current. Every operation waits for network round trips, and when the network between replicas fails, some of them cannot answer at all. That last point is the subject of the most quoted theorem in distributed systems.

The CAP theorem

The CAP theorem concerns three properties of a system that stores data on several nodes.

  • Consistency, meaning linearizability as defined above.
  • Availability, meaning every request to a node that has not crashed receives a real answer, not an error or a timeout.
  • Partition tolerance, meaning the system keeps operating when the network drops messages between nodes.

The theorem, conjectured by Eric Brewer in 2000 and proved by Seth Gilbert and Nancy Lynch in 2002, says that when a network partition occurs, a system cannot provide both consistency and availability. The argument fits in one picture.

There is no third option, because the information replica 2 needs is on the other side of a broken link. Systems are therefore described by which way they lean when a partition happens.

What CAP does not say

The theorem is often summarized as “consistency, availability, partition tolerance: pick two”. That phrasing is misleading in several ways, and the misunderstandings lead to poor designs.

  • Partition tolerance is not optional. Networks fail whether you permit it or not. A system that “gives up P” is simply one whose behavior during a partition is undefined. The real choice is between C and A, and it arises only while a partition lasts.
  • It says nothing about normal operation. When the network is healthy, which is nearly always, a system can be both consistent and available. CAP is about a rare event.
  • Its definitions are narrow. “Consistency” means linearizability and nothing weaker. “Availability” means every non-failed node answers every request, which is stricter than any real system’s availability target and ignores how slow the answer is.
  • It is not a property of a whole system. Different operations in one product can make different choices, and many databases let each request choose.
  • It ignores everything else that goes wrong. A system can be unavailable through overload, bugs or a bad deployment with no partition involved.

CAP is best treated as a warning that there is a choice to make, and as vocabulary for stating which way a system leans. As a tool for designing, the next idea is more useful.

PACELC: the trade-off you make every day

Partitions are rare. The coordination that strong consistency needs is paid for on every request, partition or not. PACELC, proposed by Daniel Abadi, extends CAP to say so: if there is a Partition, choose between Availability and Consistency, Else, in normal operation, choose between Latency and Consistency.

The second half is the one that shapes ordinary design. A write that must be confirmed by replicas in three regions before it is acknowledged is consistent and slow. A write acknowledged by one node and copied later is fast and can be lost or read stale. This is the synchronous and asynchronous choice from , and the quorum settings from , under another name.

The models between the extremes

Between “behaves like one copy” and “copies agree eventually” there are useful intermediate promises. Four cover most of practice.

Eventual consistency

Eventual consistency promises one thing: if no new writes arrive, all copies will in time hold the same value. It says nothing about how long that takes or what is returned in the meantime. A read may return an old value, two successive reads may return a newer value and then an older one, and two clients may see different things at the same moment.

That sounds alarming, and it is what you already have whenever you read from an asynchronous replica, a cache, a CDN or a search index. It is acceptable for a great deal of data: like counts, view counts, recommendations, timelines, analytics. The system must also have a rule for making the copies agree when they have accepted conflicting writes, and listed the options.

Session guarantees

Most complaints about eventual consistency come from one person seeing their own actions undone. Session guarantees fix that without the cost of strong consistency, by making promises to each client about its own sequence of operations.

  • Read your writes. After you write something, your reads reflect it.
  • Monotonic reads. Once you have seen a value, you never see an older one.

Other users may still see stale data, and usually nobody minds. The implementation is a token: each write returns a marker of how far the log had advanced, the client presents it on later reads, and a replica that has not reached that point either waits or passes the request on. Azure Cosmos DB’s session level works this way, and so does the “read from the leader briefly after writing” policy described in the replication chapter. For user-facing products this is very often the right default.

Causal consistency

Causal consistency promises that if one operation could have influenced another, everyone sees them in that order. A reply is never visible before the comment it answers. A photo is never visible to someone who was removed from the album before it was added. Operations with no causal connection, the concurrent ones from , may be seen in different orders by different clients.

Causal consistency matters for a theoretical reason. It is about the strongest model that can be provided while remaining available during a partition, since it requires each replica to hold back only what it has not yet received the cause of, and never requires asking another replica for permission. It is implemented by attaching version information to each write, in the manner of vector clocks.

Linearizability is not serializability

Two similar words name the strongest guarantees of two different areas, and they are frequently confused.

SerializabilityLinearizability
Comes fromDatabases: transaction isolationDistributed systems: replicated data

PromisesThe result equals some one-at-a-time ordering of the transactionsEach operation takes effect at an instant, in real-time order

A database can be serializable and still return stale data from a replica. A key-value store can be linearizable and have no transactions at all. A system with both is called strictly serializable: transactions behave as if run one at a time, in an order consistent with real time. That is what Spanner and the databases modeled on it provide, and it is the closest thing to a single machine that a distributed database offers.

Choosing, one operation at a time

Consistency is best decided for each operation, by asking what breaks if this read is stale or these two writes conflict. For the photo app:

A pattern is visible. Operations that enforce a rule involving more than one party need strong consistency, and they are a small minority of the traffic. Everything else can use something cheaper. A design that routes the few critical operations through a strongly consistent path and serves the bulk of reads from replicas and caches gets correctness where it matters and speed everywhere else.

When no coordination is neededA useful rule of thumb from research: if an operation only ever adds information and never needs to know that something is absent, replicas can apply it in any order and still agree, so no coordination is required. Adding a like fits. “Reserve this seat only if nobody else has” does not, because it depends on an absence. Asking which of your operations depend on an absence is a quick way to find the ones that need strong consistency.

Common mistake. Describing a design as “CP” or “AP” and stopping there. The label says little about how the system behaves on a normal day, when the question is latency against staleness, and nothing about which operations need what. State the guarantee each important operation requires and how it is provided.

In an interview. When asked about consistency, avoid reciting CAP. Say which operations must be strongly consistent and why, and which can be eventual: “seat reservation goes through the primary in a transaction, and the seat map users browse is served from a cache a second or two behind”. If the interviewer raises CAP, say that it applies during partitions, that the daily trade-off is latency against consistency, and which way your design leans for each kind of operation.

Common mistakes

  • Reading CAP as “pick two of three”, or believing a system can opt out of partitions.
  • One consistency level for a whole system, when operations differ.
  • Confusing linearizability with serializability, or either with the C in ACID.
  • Assuming a read after a write returns that write on a system that reads from replicas.
  • Building a lock, a counter that must be exact, or a uniqueness check on an eventually consistent store.
  • Paying for strong consistency on data nobody needs fresh.
  • Forgetting the caches. A strongly consistent database behind a cache with a five-minute lifetime is an eventually consistent system.

Key points

  • A consistency model states what clients may observe when data is replicated.
  • Linearizability makes a replicated system behave like one copy. Locks, uniqueness and hard limits need it, and it costs coordination on every operation.
  • CAP: during a network partition a system must choose between linearizability and answering every request. It is not “pick two”, and partitions cannot be opted out of.
  • PACELC adds the everyday trade-off: without a partition, the choice is between latency and consistency.
  • Session guarantees give each user a coherent view of their own actions cheaply. Causal consistency preserves cause and effect and stays available.
  • Eventual consistency promises only convergence. It is what replicas, caches and search indexes already give you.
  • Serializability is about transactions and linearizability about recency. They are independent.
  • Choose a level for each operation by asking what breaks if it is stale.

Check yourself

A system has three replicas. A network fault isolates one of them, and a client connected to that one sends a read. What are its two options, and which does a CP system take?

It can refuse or time out, since it cannot confirm it has the latest data, or it can answer with what it has, which may be stale. A CP system refuses, because the isolated replica is in the minority and cannot be sure.

Why is “we chose CA: consistency and availability, without partition tolerance” not a meaningful design choice for a distributed system?

Partitions are a fact of networks and not a feature to decline. When one happens, the system will either refuse some requests or return possibly inconsistent data, so it has made the C or A choice whether or not anyone decided it.

A user changes their profile photo and still sees the old one, while a friend sees the new one. Which guarantee was violated, and what is a cheap fix?

Read your writes. The user’s read went to a replica or cache that had not caught up. Route that user’s reads of their own profile to the leader for a short time after a write, or use a token from the write to pick a replica that has reached it.

Can a database be serializable without being linearizable? Give an example.

Yes. A database can run every transaction with serializable isolation on its leader, while a read sent to an asynchronous replica returns data from a few seconds ago. The transactions are equivalent to some serial order, and a read after a completed write still does not see it.

According to PACELC, what is a database with asynchronous replication trading away in normal operation, and what does it gain?

It gives up consistency for latency. Writes are acknowledged without waiting for replicas, so they are fast, and reads from replicas may be stale and recently acknowledged writes may be lost in a failover.

For each of these, would you accept eventual consistency: the number of unread notifications, the check that a coupon code is used at most once, a product’s average rating?

The unread count and the average rating can be eventual, since a brief error harms nobody. The coupon check cannot, because two requests reading “not yet used” at the same time would both redeem it. It needs a linearizable check, such as a conditional update or unique constraint on a single leader.
