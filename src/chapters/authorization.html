Allowed to do what?

Ana is signed in to the photo app. That fact was established in , and it answers none of the questions the system now has to ask. May she open this album? Delete that photo? See who else it is shared with? Read a photo that belongs to Ben?

Authorization is the decision whether a given caller may perform a given action on a given object. Every such decision has the same three parts.

PartQuestionExamples
PrincipalWho is asking?The user Ana, the tags service, a support agent acting for a customer
ActionWhat do they want to do?View, edit, delete, share, export
ResourceTo which object?Photo 871, the Lisbon album, Ben’s account

The third part is the one that gets forgotten. Here is the most common serious flaw in web applications, in five steps.

The flaw is called broken object level authorization: an operation checks that the caller is signed in and allowed to use it, and never checks that the particular object belongs to them. It heads the OWASP list of API security risks, and the wider category of broken access control is first in the OWASP Top 10 for 2025. It is common for a plain reason. Nothing fails when the check is missing. Every test in which users open their own photos passes.

In production. In May 2019 the title insurer First American Financial was found to be serving about 885 million documents, going back to 2003 and including bank account numbers and tax records, to anyone who had a link to one of them. Changing a digit in the link returned the next customer’s file, and no sign-in was required. A real estate developer noticed it and, getting no answer from the company, took it to a journalist.

A random, unguessable identifier would have slowed that down. It would not have fixed it: identifiers leak through logs, shared links and browser histories, and knowing a name must never be the same as having permission ().

Three levels of check

One request can need three separate decisions, and each has its own way of going missing.

The property level deserves a word, because it hides in convenience. Mass assignment is what happens when a handler copies every field of a request body onto a stored object: a caller adds "owner_id" or "is_admin" to the request, and the field is saved along with the legitimate ones. The same level applies to output. A handler that returns the whole database row sends the client fields that the page never shows and the user should never see. Name the fields that may be written and the fields that may be returned. Do not rely on a list of exceptions.

Put the caller in the query

The surest way to make the object-level check is to make it impossible to load an object without it.

type Photo = { id: string; ownerId: string; url: string };
type Db = { query(sql: string, params: unknown[]): Photo[] };

class NotFound extends Error {}

// Wrong: fetches by ID alone. Anyone who is signed in can read any photo by changing the number.
export function getPhotoUnsafe(db: Db, _userId: string, photoId: string): Photo {
  const [photo] = db.query("SELECT * FROM photos WHERE id = $1", [photoId]);
  if (!photo) throw new NotFound();
  return photo;
}

// Right: the caller's identity is part of the query, so a row the caller may not see is never loaded.
export function getPhoto(db: Db, userId: string, photoId: string): Photo {
  const [photo] = db.query(
    `SELECT p.* FROM photos p
      WHERE p.id = $1
        AND (p.owner_id = $2
             OR EXISTS (SELECT 1 FROM shares s WHERE s.photo_id = p.id AND s.user_id = $2))`,
    [photoId, userId],
  );
  if (!photo) throw new NotFound(); // the same answer for "does not exist" and "not yours"
  return photo;
}

Run against PostgreSQL with two photos and one share, the second query returned photo 871 to its owner and to the user it was shared with, and no row at all to anyone else. Three details matter.

  • Check, then fetch, in one step. Loading the row first and comparing afterward works until somebody adds a code path that forgets the comparison.
  • Answer 404, not 403, for objects the caller may not know about. “Forbidden” confirms that photo 872 exists. Use 403 when the caller can already see the object and is refused one action on it.
  • Lists are checks too. A search or a feed must build the permission into its query, as this one does. Fetching a page of rows and then removing the ones the caller may not see leaks through counts and timing, and returns pages of uneven length ().

The tenant boundary in a shared database is the same idea one level up, and the database can enforce it as a second lock ().

Four rules that hold in every model

  • Deny by default means that a request is refused unless a rule explicitly allows it. A new endpoint with no rule attached must fail closed, not open.
  • Least privilege means giving each user and each service only the access its work requires, for only as long as it is required.
  • Decide on the server, on every request. A hidden button is a courtesy to the user. It is not a control, because the request can be sent without the button.
  • Decide in one place. A rule copied into forty handlers will be wrong in one of them.

Models for who may do what

The checks need rules, and rules need a shape. Four shapes are in common use. They are not rivals so much as tools for different questions, and most systems of any size use more than one.

An access control list, or ACL, is the oldest form: each object carries a list of principals and what each may do. File permissions are ACLs, and so is the shares table in the query above.

Roles

In role-based access control, permissions are attached to roles, and users are given roles. Nobody is granted a permission directly. Changing what moderators may do is one edit, and removing someone’s access is removing a role.

type Permission = "photo:view" | "photo:delete" | "report:review" | "user:suspend" | "billing:refund";

// Roles are named bundles of permissions. Code checks permissions, never role names.
const ROLES: Record = {
  support: ["photo:view"],
  moderator: ["photo:view", "photo:delete", "report:review", "user:suspend"],
  billing: ["billing:refund"],
};

export function can(user: { roles: string[] }, permission: Permission): boolean {
  return user.roles.some((role) => ROLES[role]?.includes(permission) ?? false);
}

The one rule worth memorizing is in the comment. Code asks can(user, "photo:delete"), never user.role === "moderator". The day a second role needs to delete photos, the first form needs a line of configuration and the second needs a search through the whole codebase.

Roles answer “what kind of thing may this person do?”. They cannot answer “to which objects?”. The usual attempt to make them is a role for each combination, which is known as role explosion: the number of roles grows as the product of everything a role is asked to encode.

If a role has to say what someone does, where and for which team, every combination needs its own: 6 × 5 × 12 = 360 roles to create, assign and review. Keeping 6 roles and comparing two attributes of the user with the same attributes of the object does the same job, and a new region or team needs no new role.

Attributes and policies

In attribute-based access control, a decision is computed by rules over attributes: of the principal, of the resource, of the action and of the circumstances, such as the time or the network. The rules are written as policies in a language made for the purpose, kept apart from application code, reviewed and versioned like code.

These four policies are written in Cedar, an open-source policy language. They were evaluated with the Cedar engine against the nine requests in the table that follows.

// 1. Owners may do anything with their own photos.
permit (principal, action, resource is Photo)
when { resource.owner == principal };

// 2. Members of a group that an album is shared with may view its photos.
permit (principal, action == Action::"view", resource is Photo)
when { principal in resource.album.sharedWith };

// 3. Support staff may view a photo while its owner has a support case open,
//    and only from the office network.
permit (principal in Role::"support", action == Action::"view", resource is Photo)
when { resource.owner.openCase && context.network == "office" };

// 4. A photo under legal hold can be deleted by nobody. A forbid always wins.
forbid (principal, action == Action::"delete", resource is Photo)
when { resource.legalHold };

Two properties of the engine did the work, and both are worth insisting on in any policy system. Nothing is allowed unless some policy permits it, so the two plain denials needed no rule. And an explicit forbid always wins, so a guardrail such as the legal hold cannot be undone by a permit written later by someone who had not heard of it.

The cost of this power is legibility. “Who can see photo 871?” has no stored answer. It can only be computed, by evaluating every policy against every user. Keep policies few, and test them as code.

Relationships

Sharing is the hard case for roles and attributes alike. Ana shares an album with her family group. Chi is in the group. The album holds four hundred photos. Whether Chi may see one of them depends on a chain of facts, none of which mentions Chi and the photo together.

In relationship-based access control, permissions follow from relationships between things, stored as small facts and combined by rules: an owner of a photo may view it, and so may a viewer of the album that contains it. Each fact is a triple of an object, a relation and a subject.
