The problem

The problem. Design an email service like Gmail or Outlook.com. Users get an address, receive mail from anyone on the internet, read it on the web, phones and desktop programs, search all of it, and send mail to anyone. Spam should not reach the inbox, and mail sent from the service should not land in other people’s spam folders.

Most systems in Part XI control both ends of every conversation. Email does not. The sender of a message to your users is a server you have never heard of, and the receiver of your users’ mail is someone else’s server with its own rules. So the design is shaped by a protocol from 1982, revised in 2008, by DNS records that say who may send for a domain, and by reputation: other providers decide from your behavior whether to trust you. Inside, the difficulty is storage. Mail is kept for years, almost never deleted, and must be searchable at once. The method of takes these in order.

Step 3: The API

An email service has two kinds of interface: protocols spoken with other servers and with standard programs, which the design must follow exactly, and its own API for its apps. The Simple Mail Transfer Protocol (SMTP) is the text protocol, defined in RFC 5321, by which one server hands a message to another: the sender names the envelope sender and recipients, sends the message, and the receiver answers with a three-digit code. A 2xx code means accepted, 4xx means try again later, 5xx means refused for good.

The split between small records and large blobs is the main storage decision. A mailbox list of 50 messages reads 50 records of about 1.5 KB from one partition; opening a message reads one blob.

Step 5: The design

The inbound path refuses early. Before any data is sent, the connecting address is checked against reputation lists and rate limits, and the recipient is checked to exist; a server that sends to thousands of made-up addresses is cut off at RCPT. Only then does the message arrive, get its checks, and get stored. The outbound path is the mirror image: the service is now the stranger knocking on other doors, and it must look trustworthy.

The 250 in the first flow is a promise. Under RFC 5321 the receiver now owns the message, and the sender deletes its copy, so the receiver must have stored it durably before answering. The 451 in the second flow is what makes email resilient: a sender keeps mail it could not deliver and tries again, for days.

Step 6a: Who sent this, and is it spam

Anyone can connect to port 25 and write any address in From:. Three standards, all published in DNS by the domain that claims to send, let a receiver check the claim (). The Sender Policy Framework (SPF, RFC 7208) is a list of the servers allowed to send mail whose envelope sender is in a domain; the receiver compares the connecting address with it. DomainKeys Identified Mail (DKIM, RFC 6376) is a signature over chosen headers and the body, made with a domain’s private key and checked with the public key the domain publishes. DMARC (RFC 9989, May 2026, replacing RFC 7489) ties them to what the reader sees: a message passes if SPF or DKIM passes for a domain aligned with the From: domain, and the domain’s policy says what to do with one that does not: nothing, quarantine or reject.

The chapter’s code implements the three checks, with real Ed25519 signatures for DKIM (RFC 8463), and runs them on six messages that all show the same sender.

export function evaluate(dns: Dns, m: Message): Verdict {
  const from = domainOf(m.headers['from'] ?? '');
  const s = spf(dns, m), k = dkim(dns, m);
  const record = dns.get(`_dmarc.${from}`) ?? dns.get(`_dmarc.${organizational(from)}`);
  const aligned = (d: string) => organizational(d) === organizational(from);
  const pass = (s === 'pass' && aligned(domainOf(m.mailFrom))) || (k === 'pass' && aligned(m.dkim?.d ?? ''));
  if (!record?.startsWith('v=DMARC1')) return { spf: s, dkim: k, dmarc: 'none', action: 'deliver' };
  const policy = record.match(/p=(\w+)/)?.[1] ?? 'none';
  const action = pass || policy === 'none' ? 'deliver' : policy === 'reject' ? 'reject' : 'quarantine';
  return { spf: s, dkim: k, dmarc: pass ? 'pass' : 'fail', action };
}

Each row teaches something. Forwarding keeps the message intact but changes the server that delivers it, so SPF fails and DKIM carries the message through. A mailing list that tags the subject and adds a footer breaks the signature, and with SPF passing only for the list’s own domain, DMARC rejects the message; lists therefore rewrite From: or use ARC (RFC 8617, an experimental standard of 2019) to vouch for what they received. An email service sending for the shop passes because the shop published a DKIM key for it. The forger fails everything. And the look-alike domain passes everything: authentication proves which domain sent a message, not that the domain is honest.

That last row is why spam filtering is layered. Cheap checks run first, while the sender is still connected: the address’s reputation, the rate at which it connects, whether the recipient exists. Then authentication, then a content classifier that scores the message, trained on what users mark as spam and as not spam. Its threshold trades two errors: wanted mail in the spam folder, which users notice and resent, against spam in the inbox. Reject only what is certain, such as a DMARC reject; put the uncertain in the spam folder, where a user can still find it.

Step 6b: Sending: queues, retries and reputation

A sender must expect refusals. RFC 5321 says a sender must wait before retrying a destination, that the interval should generally be at least 30 minutes but that smarter strategies help, that it should keep trying for at least 4 to 5 days, and that it should keep a list of hosts it cannot reach rather than retrying every queued message. Two common refusals shape the queue. Greylisting is a receiver’s temporary refusal of the first attempt from an unfamiliar sender, on the bet that real servers retry and many spam tools do not. A bounce is the message a sending server returns to the envelope sender when it gives up on a delivery, after a permanent refusal or after days of temporary ones.

The simulation sends 50 messages a second for two hours to 1,000 receiving domains whose sizes follow Zipf’s law, over 200 connections. A tenth of the domains greylist for 5 minutes, 2% of attempts are refused temporarily and 1% permanently. From minute 10 to minute 70 the largest domain, with 13% of the mail, stops answering, and each attempt to it holds a connection until a 30-second timeout. Three ways of running the queue were compared.

In a shared pool, mail to the dead domain keeps arriving and each attempt ties up a connection for 30 seconds, so all 200 end up waiting on it and everyone else’s mail waits too: a median of 4 minutes, and 40 minutes at the 99th percentile. Retrying sooner makes it worse, because there are more attempts to time out. A limit per domain caps the damage at 20 connections, and the down list stops the attempts altogether: after five timeouts in a row the domain is marked down, its mail is parked, and one message is tried every 5 minutes. When it gets through, everything parked is released, which drained the backlog within 14 minutes of recovery. Backoff from a minute instead of a fixed 30 minutes also delivered greylisted mail in 6 minutes instead of 34. RFC 5321 asks for at least 30 minutes in general but expects smarter strategies when the reason for a refusal is known, and a refusal that names greylisting is such a case.

Deliverability is the share of a sender’s mail that reaches the recipients’ inboxes rather than their spam folders or nowhere. It is earned. Receivers judge sending addresses and domains by their history: volume, complaints, bounces to addresses that do not exist. So the service sends from pools of addresses with a reputation to protect, keeps transactional mail apart from bulk mail, starts new addresses slowly, and limits how much a new or suddenly busy account can send, because a hijacked account sending spam damages everyone on its address (). Since February 2024 Gmail has required every sender to authenticate with SPF or DKIM and to keep its reported spam rate below 0.3%, and senders of more than 5,000 messages a day to Gmail accounts to publish DMARC, align From: with SPF or DKIM, and offer one-click unsubscribe.

Step 6c: Mailbox storage and search

Each user’s mail is a partition: records keyed by user and message id in the database, and blobs in the blob store. A mailbox with a million messages is still one user’s partition, read a page at a time in date order (). Most reads are of recent mail, so blobs older than a few months move to a colder, cheaper tier and are fetched on the rare day someone opens them ().

The same attachment often arrives many times: sent to a team, forwarded, sent again. Storing each distinct attachment once, under the hash of its content, with a reference from each message, saves those copies. On the chapter’s assumed mix of personal mail and bulk mail, attachments were 52% of the bytes and storing them once cut the total to 75.3% of a full copy per mailbox. Bodies are not shared: bulk mail is usually personalized, with the reader’s name and tracking links, so its copies differ. A shared blob is deleted only when no message refers to it any more, which needs a reference count or a periodic sweep.

Every search is inside one mailbox, which decides the index layout. An index that grouped all users’ mail by term would make a search for “invoice” read the postings of every user’s invoices and throw away all but one user’s. Instead the index is partitioned by user, like the records: many users’ small indexes share a shard, every term is prefixed with the user id, and a query reads only that user’s postings (). New mail reaches the index through a queue, so a message can be visible in the inbox a few seconds before search finds it. Sync follows the same partition: each change to a mailbox gets the next number of that user’s change counter, and IMAP and JMAP clients ask for everything after the number they hold.

At ten times the mailboxes, storage is the system: two exabytes a year, which means erasure coding, cold tiers and compression matter more than any server count. The inbound edge grows with connections and the checks with messages, both stateless. At a hundred times, which no provider has, the database of records would be split by region of the user, each region running its own inbound and outbound paths behind the same MX names.

In the real world

  • The standards. SMTP is RFC 5321 (October 2008), the message format RFC 5322. SPF is RFC 7208 (2014), DKIM RFC 6376 (2011) with Ed25519 signatures added by RFC 8463 (2018). DMARC was revised as RFC 9989 in May 2026, with reporting in RFC 9990 and 9991, replacing RFC 7489; it defines a walk up the DNS tree to find a domain’s organizational domain, where RFC 7489 relied on a public suffix list. IMAP4rev2 is RFC 9051 (2021), JMAP RFC 8620 and 8621 (2019). All checked at the RFC Editor in October 2026.
  • Retries. RFC 5321 suggests, from experience, two connection attempts in the first hour a message is queued, then one every two or three hours, and notes that a client typically learns an attempt has failed only after a timeout of several minutes.
  • Gmail’s sender requirements. Google’s guidelines, in force since 1 February 2024 and checked in October 2026, require all senders to Gmail accounts to use SPF or DKIM, TLS, valid forward and reverse DNS, and a spam rate below 0.3%; senders of more than 5,000 messages a day must also publish DMARC (a policy of none is allowed), align the From: domain with SPF or DKIM, and support one-click unsubscribe for marketing mail.

Key points

  • SMTP moves responsibility with the 250 reply: store before answering, and keep what you could not deliver for days.
  • SPF checks the sending server, DKIM signs the content, and DMARC requires one of them to pass for the domain the reader sees.
  • Authentication proves the domain, not the intent; layer reputation and content filtering on top.
  • Queue outgoing mail per receiving domain, with a connection limit and a down list, so one dead domain cannot delay the rest.
  • Deliverability is reputation: authenticated mail, separate pools, slow starts and limits on hijackable accounts.
  • Split small records from large blobs, partition both by user, and store each distinct attachment once.
  • Partition the search index by user, because every search is inside one mailbox.

Check yourself

Why must the inbound server store a message before it answers 250?

The 250 transfers responsibility: the sending server deletes its copy. If the receiver crashed after answering and before storing, the message would be gone with no one left to retry it.

A message is forwarded unchanged by an old university address. Which of SPF and DKIM survive, and does DMARC pass?

SPF fails, because the forwarder’s server is not on the original domain’s list. DKIM passes, because the signed headers and body are unchanged. DMARC passes, since DKIM passed for the aligned domain.

Why does a look-alike domain pass all three checks?

Its owner published correct SPF, DKIM and DMARC records for it. The checks prove which domain sent the message, not that the domain is the one the reader thinks it is.

The largest receiving domain stops answering. Why does all outgoing mail slow down in a shared pool?

Mail to that domain keeps arriving, and each attempt holds a connection until its timeout. Soon most connections are waiting on the dead domain, and mail to everyone else queues behind them: a median of about 4 minutes in the simulation.

How does a down list help, and what happens when the domain recovers?

After a few timeouts in a row the domain is marked down: its mail is parked without attempts, and one message is tried every few minutes. When the probe gets through, all parked mail is released; in the simulation the backlog was delivered within 14 minutes of recovery.

Why keep message bodies in a blob store and records in a database?

Lists, counts, sync and search need the small records constantly; bodies are large, written once and read rarely. Keeping them apart puts hundreds of petabytes on cheap durable storage and keeps the hot data small.

Why partition the search index by user rather than by term?

Every search is in one mailbox. A term-partitioned index would read every user’s postings for each term and discard almost all of them; a user-partitioned index reads only the searcher’s.
