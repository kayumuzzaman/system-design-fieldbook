Fitting objects together

A program that follows the earlier chapters is made of small objects that know each other only through interfaces. The structural patterns are the standard ways of connecting such objects so that the whole does more than the parts, and of doing so without any part needing to be rewritten.

PatternProblemIn one sentence
AdapterSomething useful has the wrong interfaceWrap it in an object that has the interface you need
DecoratorBehavior should be added to an object without changing its classWrap it in an object with the same interface that does a little extra
ProxyAccess to an object should be delayed, checked or redirectedPut a stand-in with the same interface in front of it
FacadeA group of objects is awkward to use correctlyOffer one simple object in front of them
CompositeThings contain things, and both should be handled alikeGive a container the same interface as its contents
BridgeA design varies in two independent waysSplit it into two hierarchies, one holding a reference to the other
FlyweightHuge numbers of objects repeat the same dataStore the repeated part once and share it

The first four share a shape: a class that holds a reference to another object and forwards calls to it. They are told apart by the interfaces on each side of the wrapper and by its reason for existing.

Adapter

The photos service was written against its own PhotoStore interface (). In production the files go to a cloud vendor whose client library has its own vocabulary: buckets, keys, bodies, and an error with a particular name when something is missing. The vendor will not change its library to suit this application, and the application should not be rewritten to suit the vendor.

An adapter is an object that implements the interface a caller expects by translating each call into calls on an object with a different interface.

// The interface the rest of the photos service is written against.
export interface PhotoStore {
  save(id: string, bytes: Uint8Array): Promise;
  load(id: string): Promise;
}

// The shape of a storage vendor's client library. We did not design it and cannot change it.
export interface BucketClient {
  putObject(input: { Bucket: string; Key: string; Body: Uint8Array }): Promise<{ ETag: string }>;
  getObject(input: { Bucket: string; Key: string }): Promise<{ Body: Uint8Array }>; // throws an error named "NoSuchKey"
}

// The adapter: implements our interface by translating each call into theirs.
export class BucketPhotoStore implements PhotoStore {
  private readonly client: BucketClient;
  private readonly bucket: string;

  constructor(client: BucketClient, bucket: string) {
    this.client = client;
    this.bucket = bucket;
  }

  async save(id: string, bytes: Uint8Array): Promise {
    await this.client.putObject({ Bucket: this.bucket, Key: `photos/${id}`, Body: bytes });
  }

  async load(id: string): Promise {
    try {
      return (await this.client.getObject({ Bucket: this.bucket, Key: `photos/${id}` })).Body;
    } catch (error) {
      if (error instanceof Error && error.name === "NoSuchKey") return null; // their "missing" becomes ours
      throw error;
    }
  }
}

Tested with a stand-in for the vendor’s client, the adapter stored a photo under the key photos/p1, returned null for a missing photo where the client threw, and let an unrelated error, a dropped connection, pass through unchanged.

The translation is more than renaming methods. Three kinds of difference get absorbed here, and noticing all three is what makes an adapter good.

  • Names and shapes. save(id, bytes) becomes putObject({ Bucket, Key, Body }).
  • Conventions. The application says “not found” with null. The vendor says it with an exception. The adapter converts one into the other, and only that one.
  • Policy. The key prefix photos/ is a decision about how this application lays out its bucket. It lives in the adapter, not scattered through callers.

The benefit is containment. Every line of the program that knows the vendor exists is in one file. Replacing the vendor, or surviving a breaking change in its library, means rewriting that file. The same idea applied between whole systems is the reason a service translates another team’s data model at its edge instead of letting it spread inward ().

Decorator

Sending a notification sometimes fails, and should then be retried. Every send should also be logged. Neither concern belongs inside EmailNotifier, whose job is to talk to a mail server, and both apply equally to push messages. showed what happens if each combination becomes a subclass.

A decorator is an object that has the same interface as the object it wraps and adds behavior before or after passing each call along. Because the interface is the same on both sides, decorators can be stacked, and neither the caller nor the wrapped object can tell.

export interface Notifier {
  send(to: string, text: string): Promise;
}

// Each decorator is a Notifier that holds another Notifier.
export class Retrying implements Notifier {
  private readonly inner: Notifier;
  private readonly attempts: number;

  constructor(inner: Notifier, attempts = 3) {
    this.inner = inner;
    this.attempts = attempts;
  }

  async send(to: string, text: string): Promise {
    for (let attempt = 1; ; attempt++) {
      try {
        return await this.inner.send(to, text);
      } catch (error) {
        if (attempt >= this.attempts) throw error;
      }
    }
  }
}

export class Logging implements Notifier {
  private readonly inner: Notifier;
  private readonly log: (line: string) => void;

  constructor(inner: Notifier, log: (line: string) => void) {
    this.inner = inner;
    this.log = log;
  }

  async send(to: string, text: string): Promise {
    this.log(`sending to ${to}`);
    try {
      await this.inner.send(to, text);
      this.log("sent");
    } catch (error) {
      this.log(`failed: ${(error as Error).message}`);
      throw error;
    }
  }
}

The order of wrapping is a design decision, and the test shows the difference. With a mail server that fails twice and then succeeds:

Assembled asAttemptsWhat the log shows
new Logging(new Retrying(email))3“sending”, “sent”. The retries are invisible
new Retrying(new Logging(email))3“sending”, “failed”, “sending”, “failed”, “sending”, “sent”. Every attempt is recorded

Both are correct. Which one is wanted depends on whether the log is for users, who care that the message went, or for operators, who care that the mail server is struggling.

The pattern suits what are called cross-cutting concerns: retries, timeouts, logging, metrics, caching, access checks, rate limits. Each can be written once against an interface and applied to any implementation of it. A service mesh applies the same idea to network calls between services (), and so does the middleware chain in a web framework.

The other “decorator”TypeScript and JavaScript also have a syntax called decorators, written @name above a class or method. It is a language feature for attaching behavior to declarations. It was named after this pattern and serves similar purposes, but it is a different mechanism, and nothing in this chapter depends on it.

Proxy

A proxy is an object that stands in for another, with the same interface, so that it can control access to it. In code it is nearly indistinguishable from a decorator. The difference is intent. A decorator adds to what the object does. A proxy decides whether, when or where the real object gets involved.

KindWhat it controlsExample
Lazy, or virtualWhen the real object is created or loadedAn image that fetches its pixels only when first displayed
ProtectionWhether the caller is allowedA reader that checks permission before every load ()
RemoteWhere the real object isA local object whose methods make network calls to a service, such as a generated gRPC client ()
CachingWhether the real object needs to be asked againA store that remembers recent answers ()
 
export interface Image {
  readonly id: string;
  pixels(): Promise;
}

// A proxy that puts off loading until somebody asks, and loads only once.
export class LazyImage implements Image {
  readonly id: string;
  private readonly load: (id: string) => Promise;
  private loaded: Promise | undefined;

  constructor(id: string, load: (id: string) => Promise) {
    this.id = id;
    this.load = load;
  }

  pixels(): Promise {
    this.loaded ??= this.load(this.id);
    return this.loaded;
  }
}

export interface PhotoReader {
  load(id: string): Promise;
}

// A proxy that decides whether the call may go through at all.
export class GuardedReader implements PhotoReader {
  private readonly inner: PhotoReader;
  private readonly user: string;
  private readonly maySee: (user: string, id: string) => boolean;

  constructor(inner: PhotoReader, user: string, maySee: (user: string, id: string) => boolean) {
    this.inner = inner;
    this.user = user;
    this.maySee = maySee;
  }

  async load(id: string): Promise {
    if (!this.maySee(this.user, id)) return null; // the same answer as "no such photo"
    return this.inner.load(id);
  }
}

In the test, an album view created a hundred LazyImage objects and loaded nothing. Asking one of them for its pixels three times, twice at the same moment, caused one load. That works because the proxy remembers the promise, the same technique as in . The guarded reader returned null for a photo Ben may not see, exactly as it does for a photo that does not exist.

A remote proxy deserves a warning. It makes a network call look like a method call, and a network call can be slow, can fail halfway and can be repeated, none of which a method call does. The convenience is real, and the differences have to be handled somewhere ().

Facade

Accepting a new photo involves five parts of the media subsystem: scan the file, read when it was taken, store the original, make and store a thumbnail, and add it to the search index. The order matters. Three different callers need to do it: the upload handler, the bulk importer and the mobile sync.

A facade is a single object that offers a simple interface to a group of objects, for the tasks callers most often need.

// The facade: one call for the thing nearly every caller wants.
export class PhotoIntake {
  private readonly scanner: Scanner;
  private readonly metadata: MetadataReader;
  private readonly thumbnails: Thumbnailer;
  private readonly files: Files;
  private readonly index: SearchIndex;

  constructor(scanner: Scanner, metadata: MetadataReader, thumbnails: Thumbnailer, files: Files, index: SearchIndex) {
    this.scanner = scanner;
    this.metadata = metadata;
    this.thumbnails = thumbnails;
    this.files = files;
    this.index = index;
  }

  accept(id: string, bytes: Uint8Array): void {
    if (!this.scanner.isSafe(bytes)) throw new Error("the file failed the safety scan");
    const takenAt = this.metadata.takenAt(bytes);
    this.files.put(`original/${id}`, bytes);
    this.files.put(`thumb/${id}`, this.thumbnails.make(bytes, 200));
    this.index.add(id, takenAt);
  }
}

In the test, one call to accept produced six calls on the parts, in the right order, and a file that failed the scan produced one call and stopped. Each of the three callers is now one line, and the rule “scan before storing” exists in one place.

A facade differs from the other wrappers in two ways. It fronts several objects, not one. And it defines a new interface instead of matching an existing one. It also does not lock anything away: a caller with an unusual need can still use the parts directly. When a facade starts to grow a method for every caller’s special case, it has stopped being a simplification and has become the Manager class that the single responsibility principle warns about.

The same idea one level up is the API gateway, which presents one front door to many services ().

Composite

Users of the photo app organize photos into folders, and folders into folders. The interface shows a size and a photo count beside everything, whether it is a single photo or a folder with ten levels inside it.

The code that draws that list should not have to ask what kind of thing each row is. The composite pattern arranges objects in a tree and gives the containers the same interface as the individual items, so that a caller can treat one item and a whole subtree alike.

// One interface for a single photo and for a folder of things.
export interface LibraryItem {
  readonly name: string;
  photoCount(): number;
  bytes(): number;
}

export class PhotoItem implements LibraryItem {
  readonly name: string;
  private readonly size: number;

  constructor(name: string, size: number) {
    this.name = name;
    this.size = size;
  }
  photoCount(): number {
    return 1;
  }
  bytes(): number {
    return this.size;
  }
}

export class Folder implements LibraryItem {
  readonly name: string;
  private readonly children: LibraryItem[] = [];

  constructor(name: string) {
    this.name = name;
  }

  add(item: LibraryItem): this {
    if (item === this || (item instanceof Folder && item.contains(this))) throw new Error("a folder cannot contain itself");
    this.children.push(item);
    return this;
  }
  contains(item: LibraryItem): boolean {
    return this.children.some((child) => child === item || (child instanceof Folder && child.contains(item)));
  }

  // A folder answers by asking each child the same question. It does not care what kind each child is.
  photoCount(): number {
    return this.children.reduce((sum, child) => sum + child.photoCount(), 0);
  }
  bytes(): number {
    return this.children.reduce((sum, child) => sum + child.bytes(), 0);
  }
}

A folder of two folders and a loose photo reported 6 photos and 21 MB, and its two inner folders reported 12 MB and 8 MB, all through the same two methods. The caller’s code contains no loop and no test for folders.

Two practical points come with any tree.

  • Prevent cycles when adding. A folder placed inside one of its own descendants would make every recursive method run forever. add refuses it, and the test confirmed that adding a folder to itself or to its own child throws.
  • Watch the depth and the cost. Each call walks the whole subtree. For a tree with millions of nodes that is asked for its size on every page view, the totals should be stored at each folder and updated when contents change, which trades a cheap read for a more careful write.

The pattern appears wherever structure is recursive: files and directories, the elements of a page, groups that contain groups in a permission system, and expressions made of smaller expressions.

Bridge

Notifications vary in two ways that have nothing to do with each other. There are kinds of notice: an album was shared, a weekly digest. And there are channels: email, push. A class for each pairing gives four classes now and nine after one more of each.

The bridge pattern separates a design that varies along two independent lines into two hierarchies, and connects them by giving objects of one a reference to an object of the other.

// One side: how a message travels.
export interface Channel {
  deliver(to: string, title: string, body: string): string;
}
export const email: Channel = { deliver: (to, title, body) => `email to ${to}: [${title}] ${body}` };
export const push: Channel = { deliver: (to, title, body) => `push to ${to}: ${title}: ${body.slice(0, 30)}` };

// The other side: what the message says. Each notice holds a channel and does not care which.
export abstract class Notice {
  protected readonly channel: Channel;
  constructor(channel: Channel) {
    this.channel = channel;
  }
  abstract send(to: string): string;
}

export class ShareNotice extends Notice {
  private readonly by: string;
  private readonly album: string;
  constructor(channel: Channel, by: string, album: string) {
    super(channel);
    this.by = by;
    this.album = album;
  }
  send(to: string): string {
    return this.channel.deliver(to, "New shared album", `${this.by} shared the album ${this.album} with you`);
  }
}

export class DigestNotice extends Notice {
  private readonly newPhotos: number;
  constructor(channel: Channel, newPhotos: number) {
    super(channel);
    this.newPhotos = newPhotos;
  }
  send(to: string): string {
    return this.channel.deliver(to, "Your week in photos", `${this.newPhotos} new photos in albums you follow`);
  }
}

Both kinds of notice were sent through both channels in the test. Adding a text-message channel is one new object, and every existing notice can use it. Adding a “comment” notice is one new class, and it works on every channel. Kinds and channels now add up where they used to multiply, which is the arithmetic of the calculator in .

Bridge is the pattern people find hardest to recognize, because its code is ordinary composition. It differs from its neighbors in when it is applied and why.

BridgeAdapter
WhenDesigned in from the startAdded afterward
WhyTo let two things you own vary independentlyTo make something you do not own fit

Flyweight

Each photo records the camera that took it: maker, model, lens and sensor. A library of a million photos was taken with perhaps fifty cameras. If every photo record carries its own camera object, the same fifty descriptions are stored twenty thousand times each.

The flyweight pattern stores state that many objects have in common once, in a shared immutable object, and gives each of the many objects a reference to it.

export type Camera = Readonly<{ make: string; model: string; lens: string; sensor: string }>;

const cameras = new Map();

// Returns the one shared object for this camera, creating it the first time it is asked for.
export function cameraFor(make: string, model: string, lens: string, sensor: string): Camera {
  const key = `${make}|${model}|${lens}|${sensor}`;
  let camera = cameras.get(key);
  if (!camera) {
    camera = Object.freeze({ make, model, lens, sensor }); // frozen: it is shared, so nobody may change it
    cameras.set(key, camera);
  }
  return camera;
}

export function distinctCameras(): number {
  return cameras.size;
}

Measured on Node.js 22, a million small records that each held their own four-field camera object occupied 104 MB of heap. The same million records sharing fifty frozen camera objects occupied 48 MB. Each private copy had been costing 56 bytes, a million times over.

1 million objects that each carry their own copy of a 56-byte part use 56 MB for those parts. If only 50 distinct values exist, sharing them takes 2.8 kB and saves 56 MB. Each shared part serves about 20 thousand objects, which is the condition that makes the pattern pay.

Two conditions make the pattern safe and worthwhile.

  • The shared part must never change. The camera objects are frozen, and the test confirmed that assigning to one throws. If a record could edit “its” camera, it would be editing the camera of every other record that shares it.
  • There must be far fewer distinct values than objects. With the ratio at twenty thousand to one, sharing removes nearly all of the cost. As the ratio approaches one, the lookup table costs more than it saves.

The language already does this for you in one case: identical string literals are generally stored once. The pattern is the same idea applied by hand to larger values. It is an optimization, and like every optimization it should follow a measurement, not precede one.

In an interview. Structural patterns appear in low-level design answers mostly without their names. A parking lot with floors that contain rows that contain spots is a composite. A payment provider’s client behind your own PaymentGateway interface is an adapter. “Rate limiting and logging wrap the handler” is a decorator. Use the name once, to show you know it, and spend the time on why the wrapper sits where it does.

Common mistake. Wrapping for its own sake. Each wrapper is a place where a call can be delayed, fail or be misunderstood, and a stack of six of them makes a simple question, “what happens when I call send?”, into an investigation. Add a layer when it removes a real duplication or isolates a real boundary, and assemble the stack in one visible place so that it can be read.

Key points

  • Adapter, decorator, proxy and facade all put one object in front of another. Tell them apart by the interfaces on each side and the reason for the wrapper.
  • An adapter gives something foreign the interface you need, and translates its conventions as well as its names.
  • A decorator keeps the interface and adds behavior. Decorators stack, and their order changes what happens.
  • A proxy keeps the interface and controls access: later, only if allowed, somewhere else, or not again.
  • A facade offers one simple entry point to several objects without hiding them.
  • A composite gives a container the interface of its contents, so trees can be used like single items. Guard against cycles.
  • A bridge splits two independent kinds of variation so that they add up and do not multiply.
  • A flyweight shares immutable data among many objects. Measure first, and freeze what is shared.

Check yourself

A class holds a PaymentProvider and implements PaymentProvider, adding a timeout to every call. Another holds a vendor’s StripeClient and implements your PaymentProvider. Name each pattern and say how you can tell.

The first is a decorator: the same interface on both sides, with behavior added. The second is an adapter: the interface it presents differs from the interface of what it holds, and its purpose is translation. The structure of the code is the same in both, a field and forwarding methods. The interfaces and the intent decide the name.

The vendor’s client throws an error named NoSuchKey for a missing object, and your interface returns null for a missing photo. Where should the conversion happen, and what should happen to other errors?

In the adapter, and only for that specific error. Catch it, check that it is the “missing” error and return null. Any other error, such as a timeout or a permission failure, must be rethrown, because turning it into null would tell callers that a photo does not exist when in fact the store could not be reached.

A notifier is wrapped as new Retrying(new Logging(email)). The mail server fails twice and then succeeds. How many lines does the log contain, and how many with the wrappers the other way round?

Six: “sending” and “failed” for each of the two failures, then “sending” and “sent”. The logging wrapper is inside the retries, so it sees every attempt. As new Logging(new Retrying(email)) there are two lines, “sending” and “sent”, because the logging wrapper is outside and sees a single call that eventually succeeded.

What distinguishes a proxy from a decorator if both have the same interface as the object they wrap?

Purpose. A decorator adds to the behavior of a call that goes ahead. A proxy governs the call itself: whether it happens (protection), when the real object comes into existence (lazy), where it is carried out (remote) or whether it needs to happen again (caching). In practice the line is blurry, and a caching wrapper is called either.

Why is a facade not a violation of the single responsibility principle, and when does it become one?

A facade has one responsibility: coordinating the parts for a common task, in the right order. It does not do the scanning or the storing itself. It becomes a problem when it accumulates methods for unrelated tasks or special cases of individual callers, at which point several groups have reasons to change it and everything depends on it.

In a composite of folders and photos, what does new Folder("empty").bytes() return, and why does the code need no special case for it?

Zero. bytes adds up the answers of the children starting from zero, and with no children the sum is the starting value. This is typical of composites: the empty container and the single item are handled by the same code as a deep tree.

A game has 500,000 trees on a map. Each has a position, and one of eight species with its own texture and shape data of about 2 MB. Apply the flyweight pattern and estimate the saving.

Split each tree into what differs, its position, and what is shared, the species data. Store eight immutable species objects and give each tree a reference to one. Without sharing, the species data alone would be 500,000 × 2 MB, a million megabytes. Shared, it is 16 MB, plus a few bytes for each tree’s position and reference.
