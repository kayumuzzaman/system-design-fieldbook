The decision that outlives the code

Part II followed a request across the network to your servers. From here on, the book is about what those servers do with it, and nearly always the answer is that they read or write data. Part III covers how data is stored on one machine and then across many.

The choice of database deserves more care than most early decisions, for three reasons.

  • Data outlives code. An application can be rewritten in a new language over a few months. Moving ten years of customer records to a different kind of database is a project measured in quarters, done while the system stays live.
  • The model decides which questions are cheap. Every database makes some queries fast by arranging data to suit them, and that same arrangement makes other queries slow.
  • Correctness lives here. Whether two people can buy the last ticket, or whether a payment can be half recorded, is settled by what the database guarantees and not by application code.

A data model is the set of shapes a database lets you put data into and the operations it offers on those shapes. There are five in wide use for application data. This chapter describes each using the photo app from Part I, with users who post photos, comment on them and follow one another.

The relational model

The relational model stores data as tables. Each table holds one kind of thing, each row is one instance of it, and each column is one attribute with a declared type. A primary key identifies each row. A foreign key is a column holding the primary key of a row in another table, and that is how rows refer to each other.

CREATE TABLE users (
  id         BIGINT PRIMARY KEY,
  username   TEXT NOT NULL UNIQUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE photos (
  id         BIGINT PRIMARY KEY,
  owner_id   BIGINT NOT NULL REFERENCES users (id),
  caption    TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE comments (
  id         BIGINT PRIMARY KEY,
  photo_id   BIGINT NOT NULL REFERENCES photos (id),
  user_id    BIGINT NOT NULL REFERENCES users (id),
  body       TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

Each fact is stored once. Ana’s username appears in one row of users, and every photo and comment of hers points to it. Change the username and every page that shows it is correct at once. The database also enforces the declared rules: it will refuse a comment on a photo that does not exist, or a second user with the same name. This checking when data is written is called schema on write.

The model’s great strength is the join: combining rows from several tables in a query. Because data is stored in small independent pieces, it can be recombined to answer questions nobody had in mind when the tables were designed.

SELECT u.username, count(*) AS comments
FROM comments c
JOIN photos p ON p.id = c.photo_id
JOIN users  u ON u.id = c.user_id
WHERE p.owner_id = 42
GROUP BY u.username
ORDER BY comments DESC
LIMIT 10;

The language is SQL. It is declarative: the query states what result is wanted, and a component called the query planner decides how to get it (). Relational databases also provide transactions, which let a group of changes succeed or fail as one ().

The costs are real too.

  • Assembling a result takes work. Showing one photo page needs rows from three tables. With good indexes this is fast, and it is still more work than fetching one pre-assembled record.
  • The shape of the data and the shape of the code differ. Programs work with nested objects, and tables are flat. Translating between the two is the job of an object-relational mapper, a kind of library that is convenient and that hides costly queries from the people writing them.
  • Writes are hard to spread across machines. Joins and transactions are easy when all the data is on one server. Splitting a relational database across many servers is possible and is one of the harder tasks in this book ().

Examples: PostgreSQL, MySQL, SQLite, Microsoft SQL Server, Oracle.

The document model

A document database stores each record as a self-contained document, usually in a JSON-like format, that can contain nested objects and lists. Documents live in collections, and documents in one collection need not have the same fields.

{
  "_id": 871,
  "caption": "Sunset",
  "owner": { "id": 42, "username": "ana" },
  "tags": ["beach", "evening"],
  "comments": [
    { "by": "ben", "body": "Great shot", "at": "2026-10-01T18:04:00Z" },
    { "by": "ana", "body": "Thanks",     "at": "2026-10-01T18:09:00Z" }
  ]
}

Everything needed to show the photo page arrives in one read, with no joins. The document also matches the object in application code, so little translation is needed. Because the database does not insist on a fixed structure, adding a field is a change to the code alone. This is called schema on read: the structure is interpreted by whoever reads the data. The schema has not gone away. It has moved into the application, which must now cope with every shape of document ever written.

The central design decision is embedding against referencing. The document above embeds its comments and a copy of the owner’s username. Embedding is right for data that belongs to its parent, is read with it, and is limited in size. It goes wrong in two situations.

  • Shared data gets copied. Ana’s username is now inside every one of her photos. If she changes it, every copy must be found and updated, or some pages will show the old name.
  • Lists grow without limit. A popular photo with 200,000 comments makes a document too large to read or rewrite efficiently, and databases cap document size. MongoDB’s limit is 16 MB.

The alternative is to store comments as their own documents that hold the photo’s ID, which is a foreign key under another name, and to fetch them separately. Do that for every relationship and you have rebuilt the relational model without its guarantees. Document databases suit data that naturally forms separate, self-contained units: a product catalog where each product has different attributes, a content management system, user profiles and settings, the state of a game session.

You may not need a separate databasePostgreSQL and MySQL both store and index JSON columns. A table can have ordinary typed columns for the fields you query and join on, and one JSON column for the parts that vary. For many applications this gives the flexibility of documents where it helps, without running a second system.

Examples: MongoDB, Couchbase, Google Firestore, Amazon DocumentDB.

The key-value model

A key-value store is the simplest model: it keeps values under keys and retrieves them by exact key. To the store the value is opaque bytes. There are no joins and no queries by content, only get, put and delete.

What you get in return for giving up so much is speed and scale. A lookup by key is the cheapest operation a database can perform, and since no operation involves more than one key, the data can be spread over many machines by key with no coordination between them. Stores that keep everything in memory, such as Redis, Valkey and Memcached, answer in well under a millisecond and are the usual home for caches, sessions, rate-limit counters and leaderboards (). Durable ones such as Amazon DynamoDB hold primary data at very large scale.

Designing for a key-value store reverses the relational habit. With tables you model the data and work out the queries later. Here you must list the questions first, because each question needs a key that answers it directly. For the photo app:

QuestionKeyValue
Show a photophoto:871The photo’s data
Who is logged in with this session?session:9f2c…A user ID, with an expiry time
What is in Ana’s feed?feed:42A list of recent photo IDs
How many likes does this photo have?likes:871A counter

A question you did not plan for, such as “which photos mention beaches?”, cannot be answered without reading everything. Many stores soften this with richer value types (lists, sets, sorted sets and counters in Redis) or with secondary indexes, at which point they begin to shade into the next two models.

The wide-column model

A wide-column store sits between key-value and relational. Data is in tables with rows and columns, and each table is designed around exactly one query. The primary key has two parts:

  • The partition key decides which machine holds the row. All rows with the same partition key are stored together.
  • The clustering key decides the order of rows inside a partition. They are kept sorted on disk.
CREATE TABLE messages_by_channel (
  channel_id BIGINT,
  sent_at    TIMESTAMP,
  author     TEXT,
  body       TEXT,
  PRIMARY KEY ((channel_id), sent_at)
) WITH CLUSTERING ORDER BY (sent_at DESC);

SELECT * FROM messages_by_channel WHERE channel_id = 7 LIMIT 50;

That query is as fast with a trillion messages in the table as with a thousand, because it goes to one partition and reads fifty adjacent rows. Writes are fast as well, for reasons that explains, and the cluster grows by adding machines. Discord stores its message history this way. In 2023 it described moving trillions of messages from 177 Cassandra nodes to 72 ScyllaDB nodes, with messages partitioned by channel and a time window.

The price is rigidity. There are no joins, and a query that does not start with a partition key is rejected or painfully slow. A second question needs a second table holding the same data under a different key, which your application must write to as well. A partition that grows too large or receives too much traffic becomes a hot spot, which is the problem Discord’s time window exists to limit.

Use this model when the write volume is beyond what one machine can take, the queries are few and known, and the data has a natural grouping: messages by conversation, events by device, measurements by sensor. Examples: Apache Cassandra, ScyllaDB, Google Bigtable, Apache HBase.

The graph model

A graph database stores nodes (things) and edges (relationships between two things), either of which can carry properties. Its special ability is the traversal: starting at a node and following edges, hop after hop.

Relational databases can represent a graph with a table of edges, and can follow one or two hops with joins. The difficulty comes when the number of hops is large or unknown. “People followed by the people I follow” is two joins. “The shortest chain of follows between Ana and Chi” has no fixed number of joins. A graph database stores each node with direct pointers to its neighbors, so the cost of each hop depends on how many neighbors a node has and not on the size of the whole data set.

MATCH (me:User {id: 42})-[:FOLLOWS]->(:User)-[:FOLLOWS]->(suggestion:User)
WHERE NOT (me)-[:FOLLOWS]->(suggestion) AND suggestion <> me
RETURN suggestion.name, count(*) AS mutual
ORDER BY mutual DESC LIMIT 10

Graph databases fit problems where the relationships are the point: fraud rings in which many accounts share a device or a card, permission systems where access is inherited through groups and folders, recommendation, network and dependency maps. They are harder to spread across machines than the other models, because a traversal can wander anywhere and no way of cutting up the graph keeps related nodes together for every query.

Many products with a “social graph” do not use a graph database. A follows table in a relational or wide-column store answers “who does Ana follow?” perfectly well. Reach for a graph database when the queries are multi-hop and varied. A query language for graphs, GQL, became an ISO standard in April 2024. Examples: Neo4j, Amazon Neptune, Memgraph.

Two kinds of work: transactions and analytics

Cutting across the models is a distinction that explains a great deal of database design. It is about the kind of work being done.

Transaction processing (OLTP)Analytics (OLAP)
Typical questionShow order 5512. Add a comment.What was revenue per country per week this year?
Rows touched per queryA handfulMillions or billions
Columns touchedMost of the rowA few out of many
Who asksThe application, on behalf of users, thousands of times a secondAnalysts, dashboards and reports, far less often
What mattersLow latency and correctness under concurrencyScan speed over large volumes
DataCurrent stateHistory

The two workloads want opposite storage layouts.

A column-oriented database gains twice. It reads only the columns a query mentions, and since a column holds values of one type that often repeat, it compresses to a fraction of its size. Summing one column out of fifty reads perhaps a hundredth of the bytes a row store would.

The standard arrangement is to run the application on a row-oriented database and copy the data continuously into a column-oriented one for analysis. Running heavy reports against the database that serves users is one of the most common ways to slow a product down for everyone. covers the analytical side. Examples of column-oriented systems: ClickHouse, DuckDB, Snowflake, Google BigQuery, Amazon Redshift.

Several further models exist for particular kinds of data: time series, full-text search, geospatial and vector search. and cover them.

What “NoSQL” gave up, and what came back

Some history makes the present landscape easier to read. Until the mid-2000s, nearly all application data lived in relational databases on a single large server. Web companies then met volumes that no single server could hold, and found that joins and transactions were exactly the features that prevented spreading data across many machines. Google’s Bigtable paper in 2006 and Amazon’s Dynamo paper in 2007 described systems that dropped those features to gain scale and availability. The open-source databases built on their ideas were grouped under the name NoSQL.

The trade was real, and each side has been moving toward the other ever since.

  • NoSQL systems added back what they had removed. MongoDB has multi-document transactions. Cassandra and DynamoDB have query languages that look like SQL and limited transactions.
  • Relational systems learned to scale out. Google’s Spanner showed in 2012 that a database could offer SQL and transactions across data centers. CockroachDB, YugabyteDB, TiDB and Amazon Aurora DSQL follow that design and are known as distributed SQL.
  • Relational systems absorbed other models. PostgreSQL has JSON documents, full-text search, geospatial types and, through extensions, vector search and time-series features.

The practical result is that “SQL or NoSQL” is no longer a useful question. The useful questions are about access patterns, scale and guarantees, which the next section turns into a procedure.

Choosing a database

Start from the workload and not from the product. Write down the answers to five questions before naming any database.

  1. What are the access patterns? List the actual reads and writes, as in the key-value table above. Note which are by key, which are ranges, which combine several kinds of record, and which you cannot predict.
  2. How much, and how fast? Use the estimation method from for data volume, reads per second and writes per second. Most systems fit comfortably on one well-provisioned database server with replicas, and that is worth knowing before designing for a scale you do not have.
  3. What must never go wrong? Money, inventory and anything with uniqueness rules need transactions and constraints. A view counter does not.
  4. How will the data change shape? Stable and well understood, or varied and evolving?
  5. Who will operate it? A database your team knows well, with mature backups and monitoring, is worth more than a theoretically better one nobody has run in production.

The advice to begin with a relational database is a statement about risk. Early in a product’s life you know least about how the data will be queried. The relational model is the only one that handles questions you did not anticipate, and it gives you transactions and constraints while the rules of the business are still being discovered. If one workload later outgrows it, such as a feed, a message history or a search box, you can move that workload to a specialized store with real measurements to guide you. Going the other way, from a store built for one query to a general one, is much harder.

Developers’ habits reflect this. In the 2025 Stack Overflow survey, the most recent I could verify, the four most used databases were all relational.

Large systems end up using several databases, each for the workload it suits. The photo app at scale might keep users and photo records in PostgreSQL, sessions and feeds in a key-value store, message history in a wide-column store, the image files in object storage and a search index beside them. This is called polyglot persistence, and it has a cost that is easy to underestimate. Every additional database needs its own backups, monitoring, upgrades, capacity planning and expertise. Worse, data that lives in two systems must be kept in agreement, and there is no transaction that spans them. covers how to do that properly.

In an interview. Name the kind of database and give the reason in terms of the workload: “a relational database for orders, because we need transactions and will query them in several ways”, or “a wide-column store for the event log, because it is write-heavy and we only ever read by device and time range”. Naming a product without a reason, or choosing a distributed database for 10 GB of data, invites the question you least want.

Common mistakes

  • Choosing by fashion or by scale you do not have. A distributed database solves problems most systems never meet and brings limits that every system feels.
  • Choosing “schemaless” to avoid thinking about the schema. The structure still exists. It is now enforced by nothing.
  • Embedding lists that grow without limit in a document.
  • Designing a key-value or wide-column table before listing the queries. In those models the queries are the design.
  • Running analytics on the transactional database. One large report can slow every user request.
  • Adding a database for every new feature. Each one is a system to run and a copy of the data to keep consistent.
  • Using a graph database because the product has a “graph”. What matters is whether the queries traverse many hops.

Key points

  • A data model makes some questions cheap by arranging data to suit them, and other questions expensive.
  • Relational: facts stored once in tables and recombined with joins. The only model that handles unplanned queries, with transactions and constraints.
  • Document: self-contained nested records. Good when data is read as a whole. Embed what belongs to the parent and is bounded in size.
  • Key-value: lookups by exact key, extremely fast and easy to spread across machines. Every question needs its own key.
  • Wide-column: tables built around one query, with a partition key and a sort order. Very high write rates, no flexibility.
  • Graph: for queries that follow relationships across many hops.
  • Row storage serves transactions and column storage serves analytics. Keep the two workloads on separate systems.
  • Start with a relational database unless the workload clearly says otherwise, and add specialized stores when measurements justify them.

Check yourself

A document for each blog post embeds the author’s display name. What happens when an author changes their name, and what are the two ways to handle it?

Every post by that author holds a stale copy. Either update all the copies whenever a name changes, accepting a period of inconsistency and the cost of the update, or store only the author’s ID in the post and look the name up when reading. The first favors fast reads, and the second favors correctness and simple writes.

Why can a wide-column store answer “the last 50 messages in channel 7” quickly however large the table is, and not “all messages by Ana”?

The table is partitioned by channel and sorted by time within each partition, so the first query goes to one partition and reads 50 adjacent rows. Ana’s messages are scattered through every partition, and there is no structure that finds them without scanning everything. Serving that query needs a second table partitioned by author.

Your team wants to run a monthly revenue report directly on the production order database. What is the risk and what is the usual alternative?

The report scans a large share of the table, competing with user requests for memory, disk and CPU, and can slow or stall them. The usual arrangement is to copy the data to a separate column-oriented system built for scans and run reports there, or at least to run them against a read replica.

What does “schema on read” move, and to where?

It moves the responsibility for knowing the structure of the data from the database to the application. The database accepts any shape, so every reader must handle every shape that has ever been written, including old versions and mistakes.

A new product has uncertain requirements and about 20 GB of data expected in its first two years. Which model would you start with, and why?

Relational. The data fits easily on one server, the queries are not yet known and the relational model is the one that answers unplanned questions, and transactions and constraints protect the data while the rules are still changing.

When is a graph database justified for a social product?

When the important queries follow relationships across several hops or a variable number of them, such as friend-of-friend recommendations, shortest paths or detecting rings of connected accounts. If the queries are single hops such as “who follows Ana?”, an ordinary table of follows is simpler and scales more easily.
