Bounded and unbounded data

The photo app records an event every time someone views a photo. Two requests arrive from the product team.

  • A report, each morning, of yesterday’s views by country.
  • A “trending now” list on the home page, showing the most viewed photos of the last hour.

The first works on a bounded dataset. Yesterday is over, its events are all in, and the job can read them from start to finish and stop. The second works on an unbounded one. The stream of views never ends, and the answer must be kept up to date as it flows.

InputA complete, fixed datasetEvents as they arrive, without end
RunsOn a schedule, then exitsContinuously
Results areComplete, and hours oldSeconds old, and possibly revised later
If it failsRun it againIt must recover its position and its state
Hard partVolumeTime, state and never stopping

Batch is simpler in every respect but one: you wait. The choice between them is a question of how fresh the answer must be, and what that freshness is worth.

Batch processing

The problem batch systems solve is size. Yesterday’s views might be 500 million records, too many for one machine to process in reasonable time. The work has to be split across hundreds of machines, some of which will fail during the run.

Google’s MapReduce paper of 2004 showed that a large class of jobs can be expressed as two functions, with the framework handling distribution and failure. The programmer writes:

  • a map function, applied to every input record independently, which emits key-value pairs,
  • a reduce function, which receives all the values for one key and combines them.

Between them the framework performs the shuffle: it brings every pair with the same key to the same machine.

Three properties made this scale, and they remain the foundation of batch systems.

  • Tasks are independent. A map task needs only its own chunk. A thousand of them can run at once.
  • Tasks are deterministic and have no side effects. They read fixed input and write output files. If a machine dies, the framework reruns its tasks elsewhere and gets the same result. This is idempotency () as an architectural principle.
  • Code goes to the data. Tasks are scheduled where the input already is, instead of moving terabytes across the network.

What replaced MapReduce

MapReduce itself is rarely written by hand now. Its successors keep the model and remove its limitations.

  • Dataflow engines. Apache Spark represents a job as a graph of many operations, keeps intermediate data in memory where it can, and offers tables and SQL instead of raw map and reduce functions. Version 4.2 was released in July 2026.
  • Distributed SQL engines. Trino, and the engines inside BigQuery, Snowflake and similar warehouses, plan and run ordinary SQL across many machines. For most analytical questions a SQL query is the batch job.
  • Columnar files. Data is stored in formats such as Parquet, which keep each column together, so that a query reads only the columns it needs ().

The practical concerns of batch work are the same whichever engine runs it.

  • The shuffle is the expensive step. Grouping and joining move data between machines. Filter early, and avoid shuffling data you will discard.
  • Skew. If one key has far more records than the others, such as one celebrity’s photos, the task handling that key runs long after the rest have finished. It is the hot key problem of in another setting.
  • Write output atomically. Write to a temporary location and switch it into place when complete, so that readers never see half a result and a rerun replaces the output instead of adding to it.
  • Partition by date. Storing each day separately lets a job process or reprocess one day without touching the rest.

Stream processing

A stream processor reads events from a log (), applies a chain of operations to each, and writes results out, without ever finishing. The operations are of two kinds.

  • Stateless operations look at one event at a time: filter out bot traffic, convert a format, add a field. They need no memory, and they scale and recover trivially.
  • Stateful operations combine events: count views per photo, keep a running total, join a view to the profile of the viewer. They must remember something between events, and that memory is the source of nearly all the difficulty.

The state is partitioned by key, like the log it is computed from. All events for photo 871 go to the same worker, which holds the count for photo 871 locally, in memory or on local disk. Keeping state next to the computation is what lets a stream processor handle hundreds of thousands of events a second, where a database lookup for each event would not.

The widely used engines differ mostly in packaging.

Two kinds of time

To count “views in the last hour”, you must decide which hour a view belongs to. There are two candidates.

  • Event time: when the view happened, according to the device it happened on.
  • Processing time: when the event reached the system that is counting.

In a perfect world they would be equal. In practice an event crosses a mobile network, a load balancer, a log and a consumer that may be lagging. Most arrive within a second or two. Some arrive much later: a phone in a tunnel buffers its events and sends them when it has signal again, twenty minutes after they happened.

Counting by processing time is easy and wrong in a specific way. Events are credited to the moment they were processed, not when they occurred. If a consumer is down for ten minutes and then catches up, ten minutes of events are all counted in one minute, and the chart shows a gap followed by a spike that never happened. Rerunning the job gives different numbers each time.

Counting by event time gives the true picture, and the same answer whenever the job is run. Its cost is the subject of the next two sections: because events arrive out of order and late, the system can never be certain that it has seen everything for a given period.

Use event time for anything that describes what users did. Use processing time only for measuring the system itself, such as how many events a consumer handled in the last minute.

Windows

An unbounded stream has no total. To compute anything, it is cut into finite pieces called windows, and results are produced for each.

WindowShapeAnswers questions like
TumblingFixed length, end to end, no overlapViews in each minute. Revenue in each hour.
Hopping, or slidingFixed length, starting at regular intervals shorter than the length, so they overlapViews in the last hour, refreshed every minute
SessionVariable length, closed by a period of inactivityHow long was each visit? How many photos in one sitting?

The “trending now” list is a hopping window: the top photos of the last 60 minutes, recomputed every minute. Each event falls into 60 overlapping windows, which is why processors implement it by keeping a count for each minute and adding up the most recent 60, instead of storing each event 60 times.

Watermarks and late data

A window by event time raises a question with no perfect answer: when is it finished? The window for 10:00 to 10:01 cannot be closed at 10:01:00, because events from that minute are still in transit. Wait ten seconds and most will have arrived. Wait an hour and nearly all will. Wait forever and the result is never published.

A watermark is the processor’s running estimate of how far event time has progressed. A watermark of 10:00:52 is the claim “I do not expect to see any more events from before 10:00:52”. When the watermark passes the end of a window, the window is closed and its result is emitted.

The common way to produce a watermark is the one drawn in : take the newest event time seen so far and subtract an allowance for disorder. The allowance is a dial.

  • A small allowance gives fast results and misclassifies more events as late.
  • A large allowance captures more events and delays every result by that much.

Whatever the setting, some events will arrive after their window has closed. These are late data, and there are three things to do with them.

  • Drop them. Acceptable for a trending list. Count how many are dropped.
  • Update the result. Keep the window’s state for a further period and emit a corrected result when a late event arrives. Whatever consumes the results must then accept revisions.
  • Divert them. Send late events to a separate output, to be folded in by a later batch job.

The mechanism is compact enough to show whole.

interface ViewEvent { photoId: number; eventTime: number; }      // eventTime: when it happened, in ms

type Emit = (windowStart: number, counts: Map) => void;

class TumblingWindowCounter {
  private open = new Map>();         // window start -> photo -> count
  private watermark = -Infinity;

  constructor(private sizeMs: number, private maxDelayMs: number, private emit: Emit) {}

  add(event: ViewEvent): "counted" | "late" {
    const start = Math.floor(event.eventTime / this.sizeMs) * this.sizeMs;
    if (start + this.sizeMs <= this.watermark) return "late";    // that window has already been closed

    const counts = this.open.get(start) ?? new Map();
    counts.set(event.photoId, (counts.get(event.photoId) ?? 0) + 1);
    this.open.set(start, counts);

    this.advance(event.eventTime - this.maxDelayMs);
    return "counted";
  }

  // The watermark is a claim: "nothing older than this is still on its way".
  private advance(candidate: number): void {
    if (candidate <= this.watermark) return;                     // watermarks never move backward
    this.watermark = candidate;
    for (const start of [...this.open.keys()].sort((a, b) => a - b)) {
      if (start + this.sizeMs > this.watermark) break;
      this.emit(start, this.open.get(start)!);                   // the window is complete: publish it
      this.open.delete(start);
    }
  }
}

With one-minute windows and a ten-second allowance, an event stamped 0:58 that arrives after one stamped 1:01 is still counted in the first minute, because the watermark has only reached 0:51. Once an event stamped 1:12 arrives, the watermark reaches 1:02, the first window is published, and an event stamped 0:55 arriving after that is reported as late.

Notice that this code never reads a clock. Time advances only as events arrive, which is why a stream job replaying last week’s data produces the same windows as it did live. It also means that if events stop arriving, the watermark stops, and the last windows stay open. Real processors handle idle sources explicitly.

Common mistake. Trusting the device’s clock without limits. Event time comes from phones and browsers, and some have clocks that are wrong by hours or years. One event stamped a year in the future drags a naive watermark forward and makes every later event late. Reject or clamp timestamps that are far from the server’s receive time, and record both times on every event.

State and recovery

A stream job that has been counting for three weeks holds three weeks of accumulated state in the memory and local disks of its workers. When a worker crashes, that state must come back, exactly as it was, or the counts are wrong from then on.

The standard solution is the checkpoint. Periodically the processor saves a consistent snapshot of the whole job to durable storage: the offset each input had been read to, and the state of every operator at exactly that point.

Recovery resets every operator to the last checkpoint and rewinds the input to the saved offset. Events after that offset are processed a second time, but onto state that does not yet include them. So each event is reflected in the state exactly once, even though some were processed twice. This depends on the input being replayable, which is one more reason stream processors are fed from logs and not from queues. Flink takes these snapshots without pausing the job, using an algorithm derived from Chandy and Lamport’s work on distributed snapshots.

That guarantee covers the processor’s internal state. Output is a separate matter. Results emitted after the last checkpoint and before the crash will be emitted again on recovery. To make the effect on the outside world exactly-once as well, the sink must cooperate, in one of two ways ().

  • Idempotent writes. Each result is written under a deterministic key, such as photo and window start, so that writing it twice changes nothing.
  • Transactional writes. Output is committed atomically with the checkpoint, so that either both happen or neither does. Kafka’s transactions provide this for output to Kafka ().

State also has to be bounded. A count for each photo for each minute, kept forever, will grow without limit. Windows are discarded once they close and their lateness allowance has passed, and other state is given a time to live. Unbounded state is the most common reason a stream job that ran well for a month falls over in the second.

Joining streams

Events are often useless alone. A view event carries a photo ID and a user ID, and the report wants the photo’s category and the user’s country. Joins in a stream come in three forms.

JoinExampleHow it works
Stream with tableAdd the viewer’s country to each viewThe processor keeps a local copy of the users table, updated from a change stream (), and looks up each event in it
Stream with streamMatch each ad impression to a click within ten minutesBoth sides are buffered for the length of a window, and matches are emitted as they are found
Table with tableKeep a joined view of photos and their owners currentBoth tables are kept as state, and the result is updated when either side changes

The stream-with-table join has a subtlety that matters for correctness. If a user moves from Germany to France, should yesterday’s views, when reprocessed, be attributed to Germany or France? Joining against the table as it is now gives a different answer on each rerun. Joining against the table as it was at the event’s time is repeatable and needs a history of the table to be kept.

Lambda and kappa

For years, stream processors could not be trusted to be correct. They lost state on failure and handled late data poorly. Batch was correct and slow. The lambda architecture, proposed by Nathan Marz around 2011, ran both.

In lambda, a batch layer periodically recomputes results from all the raw data, a speed layer computes approximate results for the recent period the batch has not reached, and a serving layer combines them. It works, and its cost is plain: the same logic written twice, in two systems, that must agree.

The kappa architecture, proposed by Jay Kreps in 2014, observed that if the log keeps history and the stream processor is correct, the batch layer is unnecessary. Recomputation is the same streaming job, started again from the beginning of the log. When the logic changes, the new version is run alongside the old, and reads are switched over once it has caught up.

Modern practice sits between the two. Stream processors now have exact state and proper handling of event time, so one streaming pipeline is commonly the main path. Long history lives in cheap object storage in table formats that both streaming and batch engines can read, and engines increasingly run the same code in either mode. One piece of lambda survives almost everywhere money or billing is involved: a periodic batch job that recomputes totals from raw data and compares them with what the stream produced. That is reconciliation (), and builds a design around it.

Running stream jobs

  • Lag is the health metric. A job whose consumer lag grows is falling behind and its results are getting staler ().
  • Backpressure is built in. When a downstream operator is slow, upstream operators slow down and the job reads less from the log. Nothing is dropped. The delay shows up as lag.
  • Scaling changes the partitioning of state. Adding workers means moving keyed state between them, which requires stopping at a checkpoint and restarting with a new layout.
  • Hot keys limit parallelism. All events for one key go to one worker. If one key is a large share of the traffic, more workers do not help. Split the aggregation into two stages: first by key plus a random suffix, then combine.
  • Changing the code of a running job is delicate. New code must be able to read the state the old code saved. Plan state schemas for evolution, as you would events.
  • Reprocessing is a normal operation. Bugs are found and logic changes. Keep the raw events long enough to recompute, and design outputs so that a recomputation overwrites instead of duplicating.

Choosing an approach

How fresh must the answer be?Reasonable choice
Tomorrow, or hourlyA scheduled batch job or SQL query in the warehouse
A few minutesFrequent small batches, or an incrementally refreshed materialized view
SecondsStream processing
Immediately, for one user’s own actionNeither. Compute it in the request, or update a counter in the write path.

Start with the simplest thing that meets the requirement. A SQL query on a schedule answers most questions, can be written in an afternoon and can be rerun at will. A stream job is a service that runs forever, holds state and needs operating. Reach for it when the product needs results within seconds, or when the reaction itself must be continuous, as with fraud checks, alerting and live dashboards.

In an interview. If you propose a streaming aggregation, three follow-ups are predictable. Which time? “Event time, with watermarks.” What about late events? “An allowance of a few minutes, then they go to a side output that a nightly batch reconciles.” What if the job crashes? “It restarts from a checkpoint and replays the log from the saved offset, and the sink writes are idempotent on key and window.” Having those three answers ready covers most of the depth interviewers look for here.

Key points

  • Batch processes a complete dataset and is simple, repeatable and hours behind. Streaming processes events as they arrive and is seconds behind, at the cost of state and continuous operation.
  • Batch systems scale by splitting work into independent, deterministic tasks that can be rerun. The shuffle is the expensive step.
  • Event time is when something happened. Processing time is when the system saw it. Use event time for anything about user behavior.
  • Windows cut an endless stream into finite pieces: tumbling, hopping or session.
  • A watermark estimates how far event time has progressed and decides when a window closes. It trades completeness against delay, and some data will always be late.
  • Checkpoints save input offsets together with operator state. Recovery replays from the checkpoint, giving exactly-once state.
  • Exactly-once output needs idempotent or transactional sinks.
  • Prefer one pipeline over two. Keep raw data, and reconcile important totals with a batch job.

Check yourself

A stream consumer is down for 15 minutes and then catches up. A per-minute chart built on processing time shows a gap and then a tall spike. What would the same chart show with event time, and why?

A normal, even line. With event time each event is assigned to the minute in which it happened, however late it was processed, so the 15 minutes of events fill in their own minutes. With processing time they are all credited to the minute in which the consumer caught up.

What does a watermark of 10:05:00 mean, and what happens to an event stamped 10:03:40 that arrives after it?

It is the processor’s assertion that it expects no more events with a time before 10:05:00. Windows that end at or before that time are closed and their results emitted. The event stamped 10:03:40 is late: its window has closed. Depending on policy it is dropped, used to emit a corrected result, or sent to a side output.

You need “the top photos of the last 24 hours, updated every 5 minutes”. Which kind of window is that, and how many windows does each event belong to?

A hopping window, 24 hours long, advancing every 5 minutes. Each event belongs to 288 windows, since 24 hours contains 288 five-minute steps. Implementations avoid storing it 288 times by keeping a count for each 5-minute slice and summing the most recent 288 slices.

A stream job crashes and restarts from a checkpoint taken 30 seconds earlier. Why are its internal counts still correct, and why might its output contain duplicates?

The checkpoint holds the input offset and the operator state from the same instant. On restart the state is restored and the input replayed from that offset, so the events of the last 30 seconds are applied once to state that did not yet include them. Any results emitted during those 30 seconds were already sent, and are sent again. The sink must be idempotent or transactional to hide that.

Why can a map task in a batch job be safely rerun on another machine after a failure?

It reads a fixed chunk of input, performs a deterministic computation and writes its output to files, with no other side effects. Running it again produces the same output, which replaces whatever the failed attempt left. That property is what lets batch frameworks treat machine failure as routine.

What does the kappa architecture remove from the lambda architecture, and what does it need in order to do so?

It removes the separate batch layer and the need to implement the logic twice. It needs a log that retains enough history to recompute from, and a stream processor that produces correct results, with exact state and event-time handling. Recomputing is done by replaying the log through a new instance of the streaming job.

The team wants a daily revenue report and proposes a Flink job. What do you ask?

How fresh the report needs to be. If it is read once a day, a scheduled SQL query in the warehouse is simpler, cheaper, trivially rerunnable and easier to verify. A stream job is justified only if someone needs the figure within seconds or minutes, or if the same pipeline also drives something continuous.
