The problem

The problem. Design the core of an expense-sharing app. People in a group record expenses: one person pays, and the cost is split among some members equally, by exact amounts, by percentages, or by shares. The app shows each person’s balance and who owes whom, records repayments, and can suggest the fewest payments that settle everyone.

The app most associated with this is Splitwise, and the interview problem is often named after it. In the terms of , it is a design of rules about money between people: value objects, a strategy for each kind of split, and totals that must add up. The money type comes from , which promised that the rule for dividing without losing a cent would be written once and used here.

Step 4: The classes

Two decisions shape the diagram.

A split is data, not an object with behavior. The classic answer to “four kinds of split” is the strategy pattern of : an interface with four classes. But a split must be stored with its expense and shown again a year later (“dinner, split 1:1:2”), and a class instance does not survive being saved as JSON and read back. So Split is a union of four plain records, told apart by kind, and the behavior lives in one function with a case for each. The compiler checks that every kind is handled. This is still a strategy, chosen by a value instead of by a class.

The shares are stored, not recomputed. When an expense is added, its split is turned into an amount for each person, and that result is kept beside the rule that produced it. If the rounding rule changes next year, old expenses keep the amounts everyone saw and agreed to.

Step 6: The code

Dividing without losing a cent

The domain modeling chapter divided an amount into equal parts and gave the leftover cents to the first parts. Sharing expenses needs division in proportion to weights: shares of 1, 1 and 2, or percentages such as 33.33, 33.33 and 33.34. The method that never loses a cent is the one used to divide seats in a parliament among parties, the largest remainder method: give each part the whole cents of its exact share, then hand out the cents left over, one each, to the parts that lost the largest fractions.

// Divides in proportion to whole-number weights. Each part gets the whole cents of its exact share, and the cents
  // left over go one each to the parts with the largest fractions; ties go to the earlier part.
  allocate(weights: readonly number[]): Money[] {
    if (weights.length === 0 || weights.some((w) => !Number.isSafeInteger(w) || w < 0)) throw new Error("weights are whole numbers, at least one");
    const total = weights.reduce((a, b) => a + b, 0);
    if (total === 0) throw new Error("weights must not all be zero");
    if (!Number.isSafeInteger(Math.abs(this.cents) * total)) throw new Error("amount too large to divide exactly");
    const sign = this.cents < 0 ? -1 : 1;
    const cents = Math.abs(this.cents);
    const rests = weights.map((w) => (cents * w) % total);             // each fraction left over, times total
    const parts = weights.map((w, i) => (cents * w - (rests[i] as number)) / total); // whole cents, exactly
    const order = rests.map((rest, i) => ({ i, rest })).sort((a, b) => b.rest - a.rest || a.i - b.i);
    let left = cents - parts.reduce((a, b) => a + b, 0);
    for (const { i } of order) {
      if (left === 0) break;
      parts[i] = (parts[i] as number) + 1;
      left -= 1;
    }
    return parts.map((p) => Money.of(sign * p, this.currency));
  }

Everything is integer arithmetic. The fraction each part lost is kept as a remainder, (cents × weight) mod total, so comparing fractions never involves a number that cannot be stored exactly. The test divided 10,000 random amounts by random weights: every time the parts added up to the amount, and every part was within one cent of its exact share. Rounding each part on its own, the method most code reaches for first, missed the total in 4,115 of the 10,000 cases.

One property the method lacks is worth knowing. With weights 1, 3 and 3, an amount of 10 cents divides as 2, 4 and 4, and 11 cents as 1, 5 and 5: one cent more in total, one cent less for the first person. Parliaments know this as the Alabama paradox. For money it is harmless, since every part stays within a cent of its exact share, but a test that assumes parts grow with the total will fail.

The four kinds of split

export type UserId = string;

// How an expense is divided. It is plain data, because it is stored with the expense and shown again later.
export type Split =
  | { kind: "equal"; among: readonly UserId[] }
  | { kind: "exact"; amounts: Readonly> }   // cents
  | { kind: "percent"; percents: Readonly> } // up to two decimal places, adding up to 100
  | { kind: "shares"; shares: Readonly> };   // whole numbers, such as 2 for a couple

export class SplitError extends Error {}

// Each kind of split, as a function from the total to each person's part. Three of the four are the same
// calculation, allocate, with different weights; only "exact" is checked rather than computed.
export function sharesOf(total: Money, split: Split): Map {
  const weighted = (people: readonly UserId[], weights: readonly number[]) => {
    if (people.length === 0) throw new SplitError("a split needs at least one person");
    if (new Set(people).size !== people.length) throw new SplitError("a person appears twice in the split");
    const parts = total.allocate(weights);
    return new Map(people.map((p, i) => [p, parts[i] as Money]));
  };
  switch (split.kind) {
    case "equal":
      return weighted(split.among, split.among.map(() => 1));
    case "shares": {
      const people = Object.keys(split.shares);
      const weights = people.map((p) => split.shares[p] as number);
      if (weights.some((w) => !Number.isInteger(w) || w < 1)) throw new SplitError("shares are whole numbers of at least 1");
      return weighted(people, weights);
    }
    case "percent": {
      const people = Object.keys(split.percents);
      const basisPoints = people.map((p) => Math.round((split.percents[p] as number) * 100));
      if (basisPoints.some((b, i) => b < 0 || Math.abs(b - (split.percents[people[i] as UserId] as number) * 100) > 1e-6)) {
        throw new SplitError("percentages have at most two decimal places and are not negative");
      }
      if (basisPoints.reduce((a, b) => a + b, 0) !== 10_000) throw new SplitError("percentages must add up to 100");
      return weighted(people, basisPoints);
    }
    case "exact": {
      const people = Object.keys(split.amounts);
      const parts = people.map((p) => Money.of(split.amounts[p] as number, total.currency));
      const sum = parts.reduce((a, b) => a.plus(b), Money.zero(total.currency));
      if (!sum.equals(total)) throw new SplitError(`exact amounts add up to ${sum}, not ${total}`);
      if (parts.some((m) => m.cents < 0)) throw new SplitError("an amount cannot be negative");
      return new Map(people.map((p, i) => [p, parts[i] as Money]));
    }
  }
}

Three of the four kinds are the same calculation with different weights: 1 each for equal, the shares for shares, and the percentages in hundredths, so that 33.33% becomes the whole number 3,333. Only exact amounts are checked rather than computed, and the check is that they add up to the total. The validation is strict for a reason: a percentage split that adds up to 99% would leave a percent of the bill owed by nobody, and an error now is better than a balance that cannot be explained later. The test tries eight invalid splits, from an empty list to a negative amount, and every one is refused.

The group and its history

// The aggregate: members, and an append-only list of what happened. Balances are worked out from the list.
export class Group {
  readonly currency: Currency;
  private readonly members = new Set();
  private readonly entries: Entry[] = [];

  constructor(currency: Currency, members: readonly UserId[]) {
    this.currency = currency;
    for (const m of members) this.members.add(m);
  }

  addExpense(input: { id: string; description: string; paidBy: UserId; cents: number; split: Split }): Expense {
    if (this.findExpense(input.id)) throw new Error(`expense ${input.id} already exists`);
    if (!Number.isInteger(input.cents) || input.cents <= 0) throw new Error("an expense is a positive amount");
    this.requireMember(input.paidBy);
    const amount = Money.of(input.cents, this.currency);
    const shares = sharesOf(amount, input.split);
    for (const person of shares.keys()) this.requireMember(person);
    const expense: Expense = { id: input.id, description: input.description, paidBy: input.paidBy, amount, split: input.split, shares };
    this.entries.push({ kind: "expense", expense });
    return expense;
  }

  // …recordPayment(from, to, cents) appends a payment, after the same kind of checks…

// A mistake is undone by a new entry that cancels it. Nothing is ever edited or removed.
  reverse(expenseId: string): void {
    if (!this.findExpense(expenseId)) throw new Error(`no expense ${expenseId}`);
    if (this.entries.some((e) => e.kind === "reversal" && e.of === expenseId)) throw new Error(`expense ${expenseId} is already reversed`);
    this.entries.push({ kind: "reversal", of: expenseId });
  }
// Each person's net position: positive if the group owes them, negative if they owe the group.
  balances(): Map {
    const net = new Map([...this.members].map((m) => [m, Money.zero(this.currency)]));
    const add = (who: UserId, m: Money) => net.set(who, (net.get(who) as Money).plus(m));
    for (const e of this.live()) {
      if (e.kind === "expense") {
        add(e.expense.paidBy, e.expense.amount);
        for (const [who, share] of e.expense.shares) add(who, share.negate());
      } else if (e.kind === "payment") {
        add(e.payment.from, e.payment.amount);
        add(e.payment.to, e.payment.amount.negate());
      }
    }
    return net;
  }

A balance is everything a person paid minus all their shares, plus repayments they made minus repayments they received. Each expense adds its amount to the payer and takes the same total from the people who shared it, so the balances of a group add up to zero after every entry. The test checks that after each of 20,000 random entries, a mixture of expenses, repayments and reversals, of which 1,447 were refused as invalid.

Nothing is edited. A wrong expense is undone by a reversal, an entry that says “ignore expense e5”, and the corrected expense is added as a new one. The balances return to exactly where they were, which the test checks, and the history still shows what happened and when. That matters in an app where friends will ask why their balance changed. It is event sourcing () at the scale of one object.

Who owes whom

A balance says how much a person is owed or owes in total, not to whom. There are two ways to answer that, and they give different answers.

  • Pair by pair. Every expense creates a debt from each sharer to the payer. Netting those for each pair of people gives a list that can be traced back to expenses: “Chloe owes Ben 42.75 for dinner.” With n people it can have up to n(n − 1) ÷ 2 entries.
  • From the balances. Ignore where the debts came from, and find any set of payments that brings every balance to zero. Fewer payments, at the cost of “why am I paying Ana when I owe Ben?”

The test found a consequence that is easy to miss. After the four friends settled by the three payments on the right, every balance was zero, but the pair-by-pair view still listed six debts, such as Chloe owing Ben 42.75, each person’s adding up to nothing. Both views are correct, but they cannot be shown side by side once people have paid by one of them. An app has to choose for each group, and Splitwise does exactly this with a setting, “simplify debts”, which it describes as restructuring “who owes whom within a group to minimize the total number of payments”, adding that it “never changes anyone’s total balance”.

Settling up

Greedy, in at most n − 1 payments

// The largest debt paid to the largest credit, again and again. Each transfer settles at least one person,
// so there are never more than n - 1 transfers for n people who are not already settled.
export function greedy(balances: ReadonlyMap): Transfer[] {
  check(balances);
  const people = [...balances].filter(([, c]) => c !== 0).map(([who, cents]) => ({ who, cents }));
  const transfers: Transfer[] = [];
  for (;;) {
    let creditor = null, debtor = null;
    for (const p of people) {
      if (p.cents > 0 && (!creditor || p.cents > creditor.cents)) creditor = p;
      if (p.cents < 0 && (!debtor || p.cents < debtor.cents)) debtor = p;
    }
    if (!creditor || !debtor) return transfers;
    const cents = Math.min(creditor.cents, -debtor.cents);
    transfers.push({ from: debtor.who, to: creditor.who, cents });
    creditor.cents -= cents;
    debtor.cents += cents;
  }
}

Each payment is the smaller of the largest debt and the largest credit, so it brings at least one of the two people to zero, and they take no further part. With n people whose balances are not zero, the last payment settles two at once, so there are at most n − 1 payments. For the weekend away, greedy produced the three payments of the figure above.

The fewest payments

Greedy is not always the best. Here is a group of five where it needs four payments and three are enough.

The reason generalizes. If some people’s balances add up to zero on their own, they can settle among themselves, and a group of k such people needs k − 1 payments. Splitting everyone into as many separate zero-sum parts as possible therefore gives the fewest payments: the number of people minus the number of parts. Finding the largest number of such parts is hard. Tom Verhoeff showed in 2004 that minimizing the number of payments is NP-hard, by reduction from a known hard partitioning problem, so no method is known that is fast for every large group.

For groups of the usual size, trying every subset is fine. The code below builds, for every set of people, the most zero-sum parts it can be split into, by removing one person at a time.

// The fewest transfers. A group of people whose balances add up to zero can settle among themselves in
// (size - 1) transfers, so the fewest transfers for everyone is n minus the largest number of separate
// zero-sum groups. Finding that number is NP-hard; this tries every subset, which is fine up to about 20 people.
export function fewest(balances: ReadonlyMap): Transfer[] {
  check(balances);
  const people = [...balances].filter(([, c]) => c !== 0);
  const n = people.length;
  if (n > 22) throw new Error("too many people to search every subset");
  const size = 1 << n;
  const sum = new Float64Array(size);
  const best = new Int8Array(size);   // the most zero-sum groups that this set of people can be split into
  const last = new Int8Array(size);   // the person added last on the way to that best
  for (let mask = 1; mask < size; mask += 1) {
    const low = 31 - Math.clz32(mask & -mask);
    sum[mask] = (sum[mask & (mask - 1)] as number) + (people[low] as [string, number])[1];
    let top = -1, who = -1;
    for (let i = 0; i < n; i += 1) {
      if (mask & (1 << i) && (best[mask ^ (1 << i)] as number) > top) { top = best[mask ^ (1 << i)] as number; who = i; }
    }
    best[mask] = top + (sum[mask] === 0 ? 1 : 0);
    last[mask] = who;
  }
  // Walk back to recover an order of people in which every zero-sum prefix closes a group, then settle each group.
  const order: number[] = [];
  for (let mask = size - 1; mask; mask ^= 1 << (last[mask] as number)) order.unshift(last[mask] as number);
  const transfers: Transfer[] = [];
  let group = new Map(), running = 0;
  for (const i of order) {
    const [who, cents] = people[i] as [string, number];
    group.set(who, cents); running += cents;
    if (running === 0) { transfers.push(...greedy(group)); group = new Map(); }
  }
  return transfers;
}

It does 2n × n steps. In one run of the chapter’s code it took 0.1 milliseconds for 10 people, 1.6 for 14, 6.9 for 16, 29 for 18 and 145 for 20, roughly quadrupling for every two people. Somewhere in the twenties it stops being an option, and greedy is the fallback. The test checked it against a slower method still, listing every way of dividing up to seven people into groups, on 300 random cases.

How often it matters

The answer depends on the amounts. When expenses are arbitrary numbers of cents, two people’s balances almost never cancel exactly, no smaller part of the group adds up to zero, and greedy is already optimal: in groups of 10 it was beaten in 11 cases out of 2,000. Friends who split round numbers, “ten euros each”, create such coincidences constantly, and in groups of 10 greedy needed an extra payment in 48% of cases. Almost always one extra, occasionally two. So an app can run the exact search for groups up to about fifteen people, where it takes milliseconds, and greedy beyond that, and the users will rarely see the difference.

Step 7: Walk it

Follow Ben adding the dinner: 85.50, shares of 1 for Ana, 1 for himself and 2 for Chloe.

  1. addExpense checks that the id is new, the amount is positive and Ben is a member.
  2. sharesOf sees kind: "shares", checks that the shares are whole numbers of at least 1, and calls allocate with weights 1, 1 and 2: Ana 21.38, Ben 21.37, Chloe 42.75.
  3. The group checks that Ana and Chloe are members, then appends the expense, with the split as entered and the three shares as computed.
  4. Later, balances walks the history: Ben gains 85.50 and loses his own 21.37, Ana loses 21.38 and Chloe 42.75. The four balances still add up to zero.
  5. When the weekend is over, greedy or fewest turns the balances into payments. As each is made, recordPayment adds it to the history, and the balances move to zero.

Key points

  • Money is whole cents in a value type, and every division of it must add up to what was divided.
  • The largest remainder method divides by any weights without losing a cent. Equal, percentage and share splits are the same method with different weights.
  • Store a split as plain data, and store the shares it produced beside it.
  • Balances add up to zero because every entry adds to one side what it takes from the other. Test that after every entry.
  • Never edit history. Reverse and re-add.
  • Pair-by-pair debts and debts from balances are both correct, and must not be mixed once people pay by one of them.
  • Greedy settles in at most n − 1 payments. The fewest is n minus the most zero-sum parts, NP-hard in general and quick by subset search for small groups. Round amounts make greedy’s extra payment common.

Check yourself

A dinner of 100.00 is split by percentages 33.33, 33.33 and 33.34. What does each person pay, and how are the percentages turned into weights?

The percentages become whole hundredths: 3,333, 3,333 and 3,334, adding up to 10,000. The exact shares are 33.33, 33.33 and 33.34 euros, which are already whole cents, so there is nothing left over and each pays exactly that.

Why does a percentage split that adds up to 99 have to be refused rather than scaled up?

Scaling would silently change what the person entering it asked for, and leaving it would make one percent of the bill owed by nobody, so the balances could no longer be explained from the expenses. Either way the error surfaces later and further from its cause. Refusing it at entry asks the one person who knows the intended split to fix it.

Why are the shares stored with the expense instead of being recomputed from the split when needed?

Because the rule that turns a split into shares may change, for example to rotate who gets leftover cents. Recomputing would change old balances that nobody touched. Storing the result keeps every past expense exactly as everyone saw it.

Prove that greedy never needs more than n − 1 payments for n people with balances that are not zero.

Each payment is the smaller of the largest credit and the largest debt, so it brings at least one of those two people to zero, and a person at zero never takes part again. After n − 2 payments at most two people remain unsettled, and since balances add up to zero, their balances are equal and opposite, so one more payment settles both.

Balances are Ana +30, Ben +20, Chloe +20, Dev −40, Eve −30. What is the fewest number of payments, and how do you know it cannot be fewer?

Three. Ana and Eve add up to zero, as do Ben, Chloe and Dev, so they settle in 1 + 2 payments. It cannot be fewer: the payments equal the number of people minus the number of zero-sum parts, so two payments would need three parts. Each part needs at least two people, one owed and one owing, so three parts need at least six people.

After a group settles using the payments suggested from balances, a user opens the pair-by-pair view and sees that she owes someone money. Is the app wrong?

Not in its arithmetic. The pair-by-pair view still lists debts traced to individual expenses, and those were not paid directly; her total across them is zero. The app is wrong to show that view for a group that settles from balances. It should show one view per group.

With weights 1, 3 and 3, ten cents divides as 2, 4 and 4, and eleven cents as 1, 5 and 5. Is that a bug?

No. It is a known property of the largest remainder method, the Alabama paradox: the leftover cents are reassigned as the fractions change, so a part can fall by a cent when the total rises. Every part is still within one cent of its exact share, and the parts still add up. Only a test that assumes parts grow with the total would object.
