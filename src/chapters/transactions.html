Two ways for data to go wrong

Suppose the photo app sells prints, and a customer pays from an account balance. Moving 50 units from the customer’s account to the seller’s takes two changes:

UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;

Consider what can interrupt this.

  • A failure in the middle. The process crashes, the network drops, or the server loses power after the first statement. The customer has paid and the seller has not been credited. Fifty units have vanished.
  • Another request at the same time. While this runs, a report adds up all balances. If it reads account 1 after the debit and account 2 before the credit, its total is short by 50, though nothing is wrong.

Application code cannot solve either problem by being careful. It cannot run cleanup code after a power failure, and it cannot see what other requests are doing. A transaction hands both problems to the database. It is a group of operations that the database treats as a single unit:

BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;

Everything between BEGIN and COMMIT takes effect together or not at all. If anything fails before the commit, or the application issues ROLLBACK, the database undoes all of it.

ACID

The guarantees of a transaction are summarized by four words whose initials spell ACID. They are worth knowing precisely, because two of them mean something narrower than they sound.

PropertyGuaranteeWhat it protects against
AtomicityAll of the transaction’s changes happen, or none doFailures partway through
ConsistencyThe declared rules (constraints, foreign keys, uniqueness) hold before and afterChanges that would break a rule
IsolationTransactions running at the same time do not interfere, to a degree you chooseConcurrent access
DurabilityOnce the database says “committed”, the change survives a crashLosing acknowledged work

Atomicity here has nothing to do with concurrency. It means abortability: an incomplete transaction leaves no trace. Durability is implemented by writing every change to a log on disk before acknowledging the commit, which the next chapter describes. On a single server it means surviving a restart, and it does not mean surviving the loss of the disk, which is what is for.

Consistency is the odd one. It depends on rules you declare. The database will stop a foreign key from pointing nowhere, and it has no idea that balances should not go negative unless you add a constraint saying so. Many rules of a business cannot be expressed as constraints, and for those the correctness is the application’s to maintain, using the other three properties as tools.

Isolation is where the difficulty is. Full isolation is expensive, so databases offer weaker levels and use one of them by default. The rest of this chapter is mostly about what those weaker levels let through.

What can go wrong between concurrent transactions

A concurrency bug is called an anomaly. There are five worth knowing by name. All of them are invisible in testing with one user and appear under load, at a rate that grows with traffic.

AnomalyWhat happensExample
Dirty readA transaction reads changes another has made and not yet committedA report sees the debit from a transfer that is then rolled back
Non-repeatable readReading the same row twice in one transaction gives different answers, because another transaction committed in betweenA check passes on the first read, and the code acts on a value that has since changed
Phantom readRunning the same query twice returns a different set of rows, because another transaction inserted or deleted some“No booking overlaps this slot” is true, and then a booking appears
Lost updateTwo transactions read a value, each computes a new one, and the second write overwrites the firstTwo likes arrive together and the counter rises by one
Write skewTwo transactions read the same data, each makes a decision that was valid on what it read, and they write different rowsTwo doctors each see two on call and both go off call

The last two are the ones that reach production, because they survive the isolation level most applications run at. Both follow one pattern: read, decide in application code, write. Whenever a decision is made on data read earlier in a transaction, ask what happens if that data changes before the write.

Isolation levels

The SQL standard defines four isolation levels, each ruling out more anomalies than the one before. What each level means in practice varies by database, so the table shows the two most common ones.

Read uncommittedPossiblePossiblePossiblePossiblePossible

Repeatable read in PostgreSQLPreventedPreventedPreventedPrevented: the second writer is abortedPossible

Serializable is the level that means what people assume “isolation” means: the result is the same as if the transactions had run one after another in some order. Everything weaker is a trade of correctness for speed.

The fact that matters most is the default. PostgreSQL, Oracle and SQL Server default to read committed. MySQL’s InnoDB defaults to repeatable read. Under read committed, each statement sees the data as committed at the moment that statement began, so two statements in the same transaction can see different states. Every anomaly in the table except dirty reads is possible. Most applications run this way without their authors having chosen it.

The names are unreliableIsolation level names promise less than they seem to. PostgreSQL’s “repeatable read” is a stronger thing usually called snapshot isolation. Oracle’s “serializable” is snapshot isolation too, and permits write skew. PostgreSQL accepts “read uncommitted” and gives you read committed. Independent testing, notably by the Jepsen project, has repeatedly found databases that do not deliver the level they document. Check the documentation of the system you use.

You can raise the level for one transaction when the work calls for it:

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- reads and writes
COMMIT;

Stronger levels are not free. Under repeatable read and serializable, the database prevents anomalies by aborting one of the conflicting transactions with a serialization error. The application must be ready to run the whole transaction again, which a later section shows.

How isolation is implemented

There are two basic mechanisms, and modern databases combine them.

Locks. A transaction marks the rows it uses so that others must wait. A shared lock lets others read and blocks writers. An exclusive lock blocks everyone else. Locking everything a transaction reads and writes until it commits gives serializability and terrible concurrency: readers block writers, writers block readers, and one slow report stalls the system.

Multi-version concurrency control (MVCC). Instead of changing a row in place, a write creates a new version of it and keeps the old one. Each transaction is given a snapshot, a consistent view of the database as of one moment, and reads whichever version of each row belongs to that snapshot.

The great benefit is that readers do not block writers and writers do not block readers. A long report and a stream of updates can run together, each seeing a consistent picture. Writers still conflict with other writers of the same row, and for that the database uses row locks.

MVCC has a cost that causes real incidents. Old versions accumulate and must be cleaned up, a process PostgreSQL calls vacuum. Cleanup can only remove versions that no open transaction could still need. One transaction left open for hours, perhaps by a forgotten console session or a stuck job, forces the database to keep every version created since it began. Tables and indexes swell and queries slow down. This is one reason for the rule below about keeping transactions short.

Preventing lost updates

The lost update is the anomaly you will meet most, so it is worth knowing every remedy. Take the simplest case, a like counter, and then a harder one, booking a seat.

Let the database do the arithmetic

The bug comes from reading a value into the application, changing it there, and writing it back. If the change can be expressed in one statement, the database performs it atomically and there is no gap for another transaction to slip into:

UPDATE photos SET like_count = like_count + 1 WHERE id = 871;

The same idea handles many “check then act” cases, by putting the check in the WHERE clause:

UPDATE seats SET booked_by = 42 WHERE id = 7 AND booked_by IS NULL;
-- One row updated: the seat is yours. Zero rows: someone else got there first.

This is the first thing to reach for. It is correct at every isolation level, needs no explicit transaction and holds a lock for the shortest possible time.

Pessimistic locking

When the decision needs real application logic between the read and the write, you can lock the row as you read it. SELECT … FOR UPDATE takes an exclusive lock, and any other transaction that tries to lock or change the same row waits until this one finishes.

await db.transaction(async (tx) => {
  const seat = await tx.queryOne(
    "SELECT id, booked_by, price FROM seats WHERE id = $1 FOR UPDATE", [seatId]);   // others wait here

  if (seat.booked_by !== null) throw new SeatTaken();
  if (!(await canAfford(tx, userId, seat.price))) throw new InsufficientFunds();

  await tx.query("UPDATE seats SET booked_by = $1 WHERE id = $2", [userId, seatId]);
});

This is called pessimistic because it assumes a conflict will happen and pays the cost of locking every time. It suits short operations on data that many requests contend for.

Optimistic concurrency control

The alternative assumes conflicts are rare. Take no lock. When writing, check that the row has not changed since it was read, and if it has, give up and let the caller decide what to do. The usual way to detect a change is a version number on the row.

const doc = await db.queryOne("SELECT id, body, version FROM documents WHERE id = $1", [id]);

// ... the user edits for five minutes. No lock is held and no transaction is open ...

const result = await db.query(
  "UPDATE documents SET body = $1, version = version + 1 WHERE id = $2 AND version = $3",
  [newBody, id, doc.version]);

if (result.rowCount === 0) throw new EditConflict();   // someone saved first: reload, merge, try again

This is the only approach that works when a person is in the loop, since you cannot hold a database lock while someone thinks. It is the same mechanism as the ETag and If-Match headers from , and the two are often connected directly: the version number becomes the ETag.

Serializable isolation with retries

The remedies above each protect one row that you identified in advance. Write skew does not have such a row: the two doctors updated different rows. PostgreSQL’s serializable level tracks what each transaction read and aborts one of any set whose combined effect could not have come from running them one at a time. You write plain read-then-write code and wrap it in a retry loop.

async function withRetry(work: (tx: Tx) => Promise, attempts = 5): Promise {
  for (let i = 0; ; i++) {
    try {
      return await db.transaction(work, { isolation: "serializable" });
    } catch (err) {
      const code = (err as { code?: string }).code;
      const retryable = code === "40001" || code === "40P01";   // serialization failure, deadlock
      if (!retryable || i === attempts - 1) throw err;
      await sleep(Math.random() * 20 * 2 ** i);                 // back off, with jitter
    }
  }
}

The function passed in will run more than once, so it must not do anything outside the database that cannot be repeated, such as sending an email. Serializable isolation costs some throughput and causes retries under contention. For the small number of transactions that enforce a rule spanning several rows, that is a reasonable price for not having to reason about every interleaving.

Let constraints do the work

The most dependable concurrency control is a rule the database enforces itself, because it holds no matter what application code does.

  • Unique constraints. “Check that the username is free, then insert” is a race. Insert, and let the unique index reject the duplicate. INSERT … ON CONFLICT DO NOTHING turns that rejection into a normal result.
  • Check constraints. CHECK (balance >= 0) makes an overdraft impossible, whichever code path attempts it.
  • Exclusion constraints. PostgreSQL can refuse two rows whose ranges overlap, which solves double booking declaratively:
ALTER TABLE bookings ADD CONSTRAINT no_double_booking
  EXCLUDE USING gist (room_id WITH =, during WITH &&);

Row locks are also the basis of a useful pattern for work queues. Many workers ask for a pending job, and each must get a different one without waiting for the others:

BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending'
ORDER BY run_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
-- do the work, then mark the job that was returned:
UPDATE jobs SET status = 'done' WHERE id = 9001;
COMMIT;

builds on this.

Deadlocks

Locks introduce a failure of their own. A deadlock is a cycle of transactions each waiting for a lock that another holds.

Databases detect the cycle after a short wait and resolve it by aborting one transaction with an error. That transaction should be retried, which the function above already does for PostgreSQL’s deadlock code. Deadlocks cannot be eliminated entirely, and they can be made rare:

  • Lock rows in a consistent order. If every transfer locks the account with the lower ID first, a cycle cannot form.
  • Keep transactions short, so locks are held briefly.
  • Touch as few rows as possible and make sure the query that finds them uses an index. Without one, the database may examine and lock far more rows than you meant.

Rules for application code

  1. Keep transactions short. A transaction holds locks, pins old row versions and occupies a connection from the pool. Milliseconds are fine. Seconds are a problem.
  2. Never call another service inside a transaction. An HTTP call to a payment provider that takes two seconds, or hangs, holds everything above for that long. Do the remote work before or after, and see the next section for how to keep the two in step.
  3. Never hold a transaction open across user interaction. Use optimistic concurrency.
  4. Expect to retry. Serialization failures and deadlocks are normal results. Make the transaction’s body safe to run again.
  5. Know your isolation level and what it allows. For each read-decide-write sequence, choose a remedy from this chapter deliberately.
  6. Prefer one statement to several, and constraints to checks in code.
  7. Watch for transactions left open. “Idle in transaction” sessions are worth alerting on. Most databases can be configured to end them after a timeout.

Common mistake. Object-relational mappers and web frameworks often open a transaction at the start of each request and commit at the end. That is convenient and it means the transaction stays open while the request renders templates, calls other services and waits on anything slow. Under load this exhausts the connection pool. Scope transactions to the few statements that need to be atomic.

In an interview. Booking, payment and inventory questions exist to test this chapter. When two users can compete for one thing, say how you prevent the double sale: “a conditional update that only succeeds if the seat is still free”, or “a unique constraint on seat and event”, or “a row lock around the check”. Then say what the loser sees. Naming the anomaly you are preventing shows you know why the mechanism is there.

Where transactions stop

Everything in this chapter applies inside one database. A transaction cannot include a call to a payment provider, a message put on a queue, a write to a second database or an update to a cache. When an operation spans two systems, one of them can succeed and the other fail, and no ROLLBACK covers both.

This boundary shapes a great deal of system design. Splitting one database into several services turns what were transactions into coordination problems, which is a strong argument against splitting early (). The techniques for crossing the boundary safely are two-phase commit, sagas and the outbox pattern, covered in , and making operations safe to repeat, covered in .

Common mistakes

  • Read, modify in code, write back, with no lock, version check or atomic statement.
  • Checking uniqueness in code instead of with a constraint.
  • Assuming the default isolation level is serializable. It almost never is.
  • Remote calls inside a transaction.
  • No retry on serialization failures and deadlocks, so users see errors for conditions the database expects you to handle.
  • Retrying a transaction whose body has outside effects, such as sending a message each time.
  • Long-running or forgotten transactions that block cleanup and hold locks.
  • Locking rows in different orders in different code paths.
  • Treating a multi-system operation as if it were atomic.

Key points

  • A transaction makes a group of changes atomic and durable, and isolates them from concurrent transactions to a chosen degree.
  • The default isolation level in most databases is read committed, which allows lost updates, phantoms and write skew.
  • The pattern to watch for is read, decide in the application, write.
  • Fix lost updates with an atomic statement first, then a row lock, a version check, or serializable isolation with retries.
  • MVCC lets readers and writers proceed without blocking each other by keeping several versions of each row. Long transactions prevent cleanup.
  • Constraints enforce rules under any concurrency. Use them in preference to checks in code.
  • Keep transactions short, never make remote calls inside them, and be ready to retry.
  • A transaction ends at the edge of one database. Work that spans systems needs different techniques.

Check yourself

Two requests read a product’s stock of 1, both see that it is available, and both write an order. Which anomaly is this, and what is the simplest fix?

A lost update, or more generally a check-then-act race. The simplest fix is a conditional update that decrements the stock only if it is still positive, such as UPDATE products SET stock = stock - 1 WHERE id = … AND stock > 0, and treating “zero rows updated” as sold out.

What does “atomicity” guarantee, and what does it not?

It guarantees that a transaction’s changes are applied completely or not at all, so a failure cannot leave half of them in place. It says nothing about other transactions running at the same time. That is isolation.

Why can you not use SELECT … FOR UPDATE to protect a form that a user is editing?

The lock would have to be held, and a transaction kept open, for as long as the user takes. That ties up a connection, blocks others, prevents cleanup of old row versions, and never ends if the user walks away. Use a version number and reject the save if the version has changed.

A rule says a meeting room cannot have overlapping bookings. Two requests each check for overlaps, find none, and insert. Which isolation level would have prevented the double booking, and what else would?

Serializable, which detects that each transaction’s read would have been affected by the other’s write and aborts one. The alternative is a constraint: an exclusion constraint on room and time range makes the database reject the second insert at any isolation level.

How does MVCC let a long report run without blocking updates?

Updates create new versions of rows and leave the old versions in place. The report reads from a snapshot taken when it started, so it keeps seeing the old versions and never needs to wait for, or block, the writers.

Your code opens a transaction, charges a card through a payment provider, then inserts an order. Name two problems.

The transaction and its locks and connection are held for the full duration of a remote call that may be slow or hang. And the two actions are not atomic together: if the insert fails after the charge succeeds, rolling back the database does not refund the card. The charge needs to be outside the transaction and coordinated by other means.
