What the transport layer adds

The internet layer described in makes one promise: it will try to deliver a packet to a machine. Packets can be lost, duplicated, delayed or reordered, and the machine has no way to tell which of its many programs a packet is for.

The transport layer fixes the last problem first. It adds ports, 16-bit numbers from 0 to 65,535 that identify a program on a machine. A server program listens on a well-known port, such as 443 for HTTPS or 5432 for PostgreSQL. A client program is given a temporary one, an ephemeral port, by its operating system for each connection it opens.

A connection is then identified by five values together, often called the five-tuple: the protocol, the source address and port, and the destination address and port.

This settles a common misunderstanding. A server is not limited to 65,535 connections because there are 65,535 ports. Every connection in the figure uses the same server port. What limits a server is memory and the number of open files its operating system allows, and well-tuned machines hold hundreds of thousands or millions of connections.

Beyond ports, the three transports in use today differ in what else they provide.

UDP: almost nothing, on purpose

The User Datagram Protocol adds ports and a checksum to an IP packet and stops there. Its header is eight bytes. There is no connection to set up, no acknowledgement, no retransmission and no ordering. An application hands UDP a message, called a datagram, and it is sent once. Whether it arrives is the application’s problem.

That minimalism is the point in three situations:

  • One question, one answer. A DNS lookup fits in one packet each way. Setting up a connection would cost more than the exchange itself, and if no answer arrives the client simply asks again.
  • Late data is worthless. In a voice call, a packet of audio that arrives 300 milliseconds late cannot be played. Resending it helps nobody. It is better to skip it and keep going.
  • You want to build the rest yourself. Games, video conferencing and, most importantly, QUIC put their own reliability and ordering on top of UDP, choosing exactly the guarantees they need.

TCP: a reliable stream

The Transmission Control Protocol gives an application something much more convenient: a pair of byte streams, one in each direction, where every byte written at one end comes out at the other end exactly once and in order. Most of what runs on the internet was built on that abstraction: the web until recently, email, SSH, and nearly every database protocol.

TCP produces it from unreliable packets with three mechanisms.

  • Sequence numbers. Every byte in the stream has a number. The receiver uses them to put data in order and to discard duplicates.
  • Acknowledgements. The receiver continually tells the sender which byte it expects next, which confirms everything before it.
  • Retransmission. If data is not acknowledged in time, or the receiver’s acknowledgements show a gap, the sender sends it again.

The price of order: head-of-line blocking

Strict ordering has a cost that shapes the design of everything built on TCP. When one packet is lost, the packets that arrive after it cannot be given to the application, even though they are sitting in the receiver’s memory. They wait until the missing one has been resent and has arrived. This is head-of-line blocking.

If the stream carries one thing, such as a single file, this is harmless: the bytes after the gap could not be used anyway. It becomes a real cost when one TCP connection carries several independent conversations. That is exactly what HTTP/2 does, and it is the main reason HTTP/3 left TCP behind, as the last part of this chapter explains.

Two speed limits

A sender that transmits as fast as it can will overwhelm something. TCP limits itself in two separate ways, and they are easy to confuse.

Flow control protects the receiver. The receiver advertises how much buffer space it has left, its receive window, and the sender never has more than that outstanding. If the receiving application reads slowly, the window shrinks and the sender slows down. This is backpressure built into the protocol: a slow consumer automatically throttles a fast producer.

Congestion control protects the network. Nobody tells the sender how much capacity the path has, and that capacity is shared with strangers. So the sender keeps its own estimate, the congestion window, and adjusts it by experiment: increase the rate while things go well, and cut it back sharply at signs of congestion, which traditionally means a lost packet.

A new connection knows nothing about the path, so it begins cautiously with a small window and doubles it every round trip. This phase is called slow start, a name that makes sense only in comparison with sending everything at once. When loss occurs, the window is reduced and growth becomes gradual.

Which algorithm?Linux uses one called CUBIC by default. Google developed another, BBR, which estimates the path’s capacity and delay directly and does not treat every lost packet as congestion. It behaves better on links with random loss, such as mobile networks. The choice is a server setting, invisible to applications.

Slow start has a consequence every web engineer should know. The initial window on modern systems is ten packets, which is about 14,600 bytes. That is all a server may send in the first round trip of a new connection. A larger response takes additional round trips while the window grows, however fast the network is.

The sender may transmit 14.6 KB, then 29.2 KB, then 58.4 KB, doubling each round trip. A response of 100 KB therefore needs 3 round trips on a new connection, before any time the server spends thinking.

Three practical rules follow from this one mechanism.

  • Make the first 14 KB count. If the HTML needed to start rendering a page fits in the first flight, the browser can begin work a full round trip earlier. This is the origin of the advice to keep critical page content small.
  • Reuse connections. A connection that has been in use has already grown its window. A new one starts from the bottom. Connection reuse saves the handshake and also the slow start.
  • Expect bursts to behave differently from steady traffic. A server that looks fast in a benchmark over warm connections will look slower to real users arriving on cold ones.

What a connection costs

TCP connections are not free to create, to hold or to close, and each of those costs shows up in system design.

PhaseWhat happensCost to design around
OpenThe three-way handshake, then usually a TLS handshake on topOne to three round trips before any useful data. Painful if done per request.
Warm upSlow start grows the congestion windowThe first responses on a new connection are slower.
HoldBoth ends keep buffers and state for the connectionMemory on the server, typically some kilobytes each, and one file descriptor.

The response to these costs is the same everywhere: open connections once and keep using them. HTTP keeps connections alive between requests. Database drivers, HTTP clients and service meshes keep connection pools, a set of open connections that requests borrow and return.

import { Agent, setGlobalDispatcher } from 'undici';

setGlobalDispatcher(new Agent({
  connections: 50,              // at most 50 open sockets per destination
  keepAliveTimeout: 30_000,     // close a socket after 30 s idle, before anything in between drops it
  connect: { timeout: 2_000 },  // give up on connecting after 2 s
  headersTimeout: 5_000,        // give up if no response starts within 5 s
  bodyTimeout: 10_000,          // give up if the response stalls for 10 s
}));

Pools introduce their own limits, and two of them cause incidents regularly.

Outbound port exhaustion. Each outgoing connection needs a local ephemeral port, and toward any single destination address and port they must all differ. Linux offers about 28,000 by default. A service that opens a new connection for every call to one backend, at a high rate, can use them all, because closed connections hold their port for a while. New connections then fail with an error about addresses being unavailable. The cure is reuse.

Pool exhaustion. A pool of 20 connections serves 20 requests at a time. When the backend slows down, every connection is busy, further requests queue for a connection, and by Little’s law in Chapter 4 the queue grows without any change in traffic. A pool needs a size, a timeout on waiting for a connection, and monitoring of how often it is full.

Three behaviors that surprise people

Idle connections that die silently

Between a client and a server sit devices that track connections: NAT gateways, firewalls, load balancers. Each remembers a connection only while it sees traffic, and removes it after an idle period. AWS’s application load balancer, for instance, closes a connection that has been idle for 60 seconds unless configured otherwise.

Neither end is told. The connection looks open to both until one of them next sends something, which is then dropped or refused. The symptom is an error on the first request after a quiet period.

The defenses are keepalives, small packets sent on an idle connection to keep it in every table along the way, and sensible ordering of timeouts: whoever reuses a connection should give up on an idle one sooner than anything downstream will drop it.

A 40-millisecond delay from nowhere

To avoid flooding the network with tiny packets, TCP by default holds back a small write for a moment if earlier data is still unacknowledged, hoping to combine it with the next one. This is Nagle’s algorithm. Separately, receivers delay acknowledgements briefly, hoping to send them along with data going the other way. Each rule is sensible alone. Together they can deadlock briefly: the sender waits for an acknowledgement, and the receiver waits before sending it. The result is a stall of tens of milliseconds, typically 40 on Linux, on a request made of two small writes.

Interactive protocols turn Nagle’s algorithm off with a socket option called TCP_NODELAY, and most HTTP and database libraries do so already. It is worth knowing by name, because a latency histogram with a suspicious spike at 40 ms usually leads here.

A peer that vanished

If a machine loses power or a cable is cut, the other end receives nothing: no close, no error. A connection in that state is half-open. A program that is only waiting to read from it will wait forever.

TCP alone does not detect this quickly. Applications must: with read timeouts on every call, and with application-level heartbeats on long-lived connections, as described for WebSockets in .

Common mistake. Making a network call with no timeout. Many libraries default to waiting indefinitely. Combined with half-open connections and slow dependencies, one stuck call holds a thread and a pooled connection forever, and enough of them stop the service. Every call across a network needs a connect timeout and a response timeout, chosen on purpose.

QUIC: a transport rebuilt on UDP

By the 2010s TCP’s limits had become the web’s limits, and TCP itself had become very hard to change. It is implemented in operating system kernels, which update slowly, and in countless routers and firewalls that inspect TCP headers and drop anything unfamiliar. Engineers call this ossification: a protocol so widely deployed, and so widely interfered with, that it can no longer evolve.

QUIC, standardized in 2021, sidesteps the problem. It is a new reliable transport that runs on top of UDP, which networks already pass, and it encrypts almost all of its own headers so that devices in the middle cannot depend on their contents. It usually lives in the application as a library, so it can be updated as easily as the application.

Designing a transport from scratch allowed four improvements at once.

ChangeWhat it fixes
Streams inside the transportA QUIC connection carries many streams, each ordered independently. A lost packet delays only the stream it belonged to. Head-of-line blocking between requests is gone.
Encryption built inThe transport handshake and the TLS 1.3 handshake are one exchange, so a new connection is ready in one round trip, and a resumed one can send data immediately.
Connection identifiersA connection is named by an ID carried in each packet, not by the five-tuple. When a phone moves from Wi-Fi to mobile data and its address changes, the connection continues.
Room to evolveWith headers encrypted and the code in user space, new versions and congestion control algorithms can be deployed without waiting for kernels or middleboxes.

It also has costs, which is why TCP is not going away.

  • More CPU per byte. Kernels and network cards have decades of optimization for TCP. QUIC does more of its work in user space and encrypts every packet, and at high volume that is measurable.
  • Some networks block UDP. Corporate firewalls in particular. Clients therefore keep the ability to fall back to TCP, and servers must support both.
  • Harder to observe. Encrypted headers mean network tools that diagnosed TCP by watching it see far less. Diagnosis moves into the endpoints.
  • Load balancers must cooperate. A layer 4 balancer that routes by five-tuple will send a migrated connection to the wrong server. QUIC-aware balancers route by connection ID.

As a transport for the web, QUIC is past the experimental stage: in October 2026, W3Techs found HTTP/3, which runs only on QUIC, in use on 40.9% of websites. Inside data centers, where loss is rare, round trips are short and hardware offload matters, TCP remains the norm.

In practice you rarely pick a transport directly. You pick an application protocol, and it brings its transport with it. The choice becomes yours in two situations: when you design something real-time, where the question is whether late data should be resent or dropped, and when you configure the edge of your system, where enabling HTTP/3 is usually a setting on a CDN or load balancer.

In an interview. “TCP is reliable, UDP is fast” is the answer of someone who has memorized a table. A better one names the trade: “for video calls I’d use UDP-based transport, because a late frame is useless and TCP would stall the whole stream to resend it; for the chat messages in the same app I want reliability and ordering, so TCP or a reliable QUIC stream.” If you mention HTTP/3, be ready to say what problem it solves: head-of-line blocking across requests, and setup latency.

What this means for design

  • Keep connections, do not make them. Pool and reuse everywhere: client to edge, edge to service, service to database. Size the pools, and put a timeout on waiting for one.
  • Bound every wait. Connect timeouts, response timeouts and heartbeats turn silent failures into errors you can handle.
  • Align idle timeouts. The component that reuses a connection must retire idle ones before the load balancer, firewall or NAT in front of the other end does.
  • Remember the cold start. New connections are slow twice over: handshakes, then slow start. After a deploy or a failover, when every pool is empty, expect a latency bump and avoid flooding a recovering backend with new connections all at once.
  • Let backpressure work. TCP slows a sender when the receiver stops reading. If your service reads everything into an unbounded in-memory queue, you have defeated that mechanism and moved the overload into your own memory.

Key points

  • Ports identify programs. A connection is identified by protocol, source address and port, and destination address and port, so one server port can hold a vast number of connections.
  • UDP sends single datagrams with no guarantees. It suits one-shot exchanges, real-time media, and protocols that build their own reliability.
  • TCP provides an ordered, reliable byte stream. The cost of ordering is head-of-line blocking after a loss.
  • Flow control protects the receiver. Congestion control protects the network, and makes new connections start slowly: about 14 KB in the first round trip.
  • Connections are costly to open and warm up, so reuse them through keep-alive and pools, with sizes and timeouts set deliberately.
  • Idle connections are dropped silently by devices in between, and vanished peers are not detected by TCP. Use keepalives, heartbeats and timeouts.
  • QUIC rebuilds a reliable transport over UDP with independent streams, built-in TLS, faster setup and connection migration. It powers HTTP/3 at the edge, while TCP remains standard inside data centers.

Check yourself

A colleague says a server can accept at most 65,535 simultaneous connections because that is how many ports exist. What is wrong with that?

All incoming connections use the same server port. Each is distinguished by the client’s address and port, so the number of possible connections is enormous. The real limits are memory and the operating system’s limit on open files.

A new connection has a 100 ms round-trip time and no loss. Roughly how long does the network take to deliver a 50 KB response once the request has been sent, with the default initial window?

About 300 ms. The sender can deliver roughly 14.6 KB in the first round trip, 29.2 KB in the second and 58.4 KB in the third, so 50 KB needs three round trips. On a connection that was already warm it could arrive in one.

A dashboard polls an API through a load balancer every 90 seconds over a kept-alive connection. Every poll fails once and then succeeds on retry. What is happening?

The load balancer closes connections idle for longer than its timeout, here probably 60 seconds. The client does not know, reuses the dead connection, and fails. Then it opens a new one, which works. Poll more often, send keepalives, or have the client discard connections idle for longer than the balancer’s limit.

Why did multiplexing many requests over one TCP connection, as HTTP/2 does, make packet loss more harmful than it was with several connections?

With one connection, a single lost packet blocks delivery of every byte behind it, which now belongs to all the requests at once. With six separate connections, a loss stalled only the one request on that connection.

For a multiplayer game sending player positions thirty times a second, would you want lost updates retransmitted?

No. By the time a retransmitted position arrived, newer ones would have superseded it, and holding those back to preserve order would add visible lag. Send positions unreliably and let the next update correct things. Events that must not be lost, such as a purchase, go over a reliable channel.
