What every service-to-service call needs

When the web service asks the feed service for Ana’s feed, the business logic is one line. Around that line sits a list of concerns that have nothing to do with feeds.

ConcernThe question
DiscoveryWhat addresses does the feed service have at this moment?
Load balancingWhich of its instances gets this request?
HealthWhich instances should be avoided?
SecurityIs the connection encrypted? Is the caller really the web service, and is it allowed to make this call?
ResilienceHow long to wait, whether to retry, when to give up
ObservabilityHow long did it take, did it fail, and which request was it part of?
Release controlCan 5% of calls go to a new version first?

Every pair of services needs all seven. The question for an architecture is where the answers live: in each application’s code, in a shared library, in the platform, or in a proxy. The chapter moves through those options in the order they were invented.

Service discovery

In a modern deployment, instances of a service have no fixed addresses. They are started and stopped by autoscaling, replaced on every deployment, and moved when a machine fails. An address written into a configuration file is wrong within the hour.

Service discovery is the mechanism that turns a stable name, such as feed, into the current set of healthy addresses. described its core: a registry that instances are added to when they start and removed from when they stop or fail a health check. What varies is who consults the registry.

Client-side and server-side

With client-side discovery, the caller fetches the list of instances, keeps it current by watching the registry, and chooses one for each request. There is no extra network hop, and the caller can balance intelligently because it sees its own in-flight requests. The cost is that this logic must exist in every calling service, in every language in use.

With server-side discovery, the caller sends to one stable address, and a load balancer behind that address tracks the instances (). Callers stay simple. The balancer is an extra hop and one more thing that must be highly available.

The client-side version is small enough to read in full, and it shows what any of these mechanisms does internally.

interface Instance { address: string; inFlight: number; failures: number; ejectedUntil: number; }

class ServiceClient {
  private instances = new Map();

  // Called with the full current list whenever the registry reports a change.
  update(addresses: string[]): void {
    for (const address of addresses) {
      if (!this.instances.has(address)) {
        this.instances.set(address, { address, inFlight: 0, failures: 0, ejectedUntil: 0 });
      }
    }
    for (const known of [...this.instances.keys()]) {
      if (!addresses.includes(known)) this.instances.delete(known);
    }
  }

  // Take two instances at random and use the one with fewer requests in flight.
  private pick(now: number): Instance {
    const all = [...this.instances.values()];
    const healthy = all.filter((i) => i.ejectedUntil <= now);
    const pool = healthy.length > 0 ? healthy : all;          // if every instance is ejected, try anyway
    if (pool.length === 0) throw new Error("no instances known");
    const a = pool[Math.floor(Math.random() * pool.length)];
    const b = pool[Math.floor(Math.random() * pool.length)];
    return a.inFlight <= b.inFlight ? a : b;
  }

  async call(request: (address: string) => Promise, now = Date.now()): Promise {
    const instance = this.pick(now);
    instance.inFlight += 1;
    try {
      const result = await request(instance.address);
      instance.failures = 0;
      return result;
    } catch (error) {
      instance.failures += 1;
      if (instance.failures >= 3) instance.ejectedUntil = now + 30_000;   // rest it for 30 seconds
      throw error;
    } finally {
      instance.inFlight -= 1;
    }
  }
}

Three ideas are in those forty lines. The list follows the registry. The choice between two random instances by load is the technique from . And an instance that fails three times in a row is left alone for thirty seconds, which is the passive health checking that Envoy calls outlier detection. In a test with three instances of which one refused every connection, callers saw three failures out of 300 calls, after which the bad instance received no traffic. With one slow instance among three, it received about a quarter as many calls as each healthy one.

The line that says “if every instance is ejected, try anyway” matters more than it looks. A client that ejects all instances has cut itself off entirely, often because the client’s own network is the problem. Systems that remove unhealthy targets should refuse to remove all of them.

How Kubernetes does it

Most teams never build the above, because the platform provides server-side discovery as a primitive. Kubernetes is the common case, and its mechanism is worth knowing since so much is built on it.

apiVersion: v1
kind: Service
metadata:
  name: feed
  namespace: social
spec:
  selector:
    app: feed            # every ready pod with this label is an instance
  ports:
    - port: 80           # callers connect to feed:80
      targetPort: 8080   # the pods listen on 8080

Three parts cooperate.

  • A name. The cluster’s DNS answers feed.social.svc.cluster.local, or simply feed from inside the same namespace, with the Service’s virtual address.
  • A virtual address. It belongs to no machine. Rules installed in the kernel of every node intercept connections to it and redirect each to a real pod.
  • A list of endpoints. Kubernetes maintains the set of pods that match the selector and pass their readiness check. A pod that is starting, shutting down or unhealthy is absent from the list.

The readiness check is therefore the control that matters. It should report ready only when the pod can really serve, and should stop reporting ready as soon as shutdown begins, so that traffic drains before the process exits ().

Two traps

Stale DNS. Where discovery returns instance addresses through DNS, clients and libraries may cache answers longer than they should, or forever. A client holding the address of a pod that no longer exists fails until restarted (). The virtual-address design above sidesteps this, since the address that DNS returns never changes.

Long-lived connections. The kernel rules choose a pod when a connection is opened. HTTP/1.1 clients open many short connections, so load spreads. HTTP/2 and gRPC open one connection and send every request down it for hours. All of one caller’s traffic then lands on a single pod, and new pods added by autoscaling receive nothing. This is the commonest surprise for teams adopting gRPC on Kubernetes. The fixes are to balance each request, with a proxy that understands HTTP/2 or with client-side balancing in the gRPC library, or as a blunt measure to close connections periodically ().

The service mesh

Discovery and basic balancing come with the platform. The remaining concerns from the opening table, encryption and identity, retries and timeouts, uniform metrics, gradual releases, were first solved with libraries: Netflix and Twitter each published one around 2012. A library works well in a company with one language. With five languages it must be written and maintained five times, and upgrading it means redeploying every service.

A service mesh moves that logic out of the application and into a proxy that sits next to it. The classic arrangement is the sidecar: a small proxy container added to every pod, with the pod’s network configured so that all traffic in and out passes through it.

The mesh has two halves.

  • The data plane is the set of proxies. Every request between services passes through two of them, one on each side. Envoy is the proxy most meshes use.
  • The control plane watches the cluster and pushes each proxy its configuration: where every service’s instances are, what the routing rules and policies say, and the certificates it should present. It handles no requests, so if it stops, the proxies carry on with the configuration they last received. That is the right way round, and the lesson of applied.

What the mesh provides, for every service in any language without a line of application code:

  • encryption and authenticated identity on every connection, covered in the next section,
  • request-level load balancing, including for HTTP/2 and gRPC,
  • timeouts, retries and circuit breaking (),
  • the same metrics for every call: rate, errors and latency, by caller and callee,
  • trace context passed along, provided the application forwards the headers it receives,
  • weighted routing between versions.

What it costs:

  • Latency. Two extra proxy hops on every call, typically a few milliseconds in total at the tail.
  • Resources. A proxy in every pod uses memory and CPU. Across thousands of pods that is a noticeable share of the bill.
  • Complexity. A mesh is a distributed system of its own, with its own upgrades and failure modes. When a call fails, there are now two more components where the cause might be.
  • Hidden behavior. Retries and timeouts that live in mesh configuration are invisible to someone reading the application’s code.

Meshes without sidecars

The per-pod cost led to designs that share the proxy.

Istio’s ambient mode, generally available since late 2024, runs one lightweight proxy on each node that gives every pod encryption and identity. Features that need to understand HTTP, such as routing by path or retrying by status code, are handled by separate shared proxies that are deployed only for the services that want them. Other projects reach a similar place by doing the low-level work in the kernel with eBPF, and gRPC libraries can receive mesh configuration directly and act on it with no proxy at all. The direction is the same in each: pay for what you use.

As of October 2026, Istio, at version 1.31, and Linkerd are the most widely used meshes, with Cilium’s mesh common where Cilium already provides the cluster’s networking.

Identity and encryption between services

Inside a private network it was once normal for services to trust any caller that could reach them. That makes the network perimeter the only defense: one compromised service, or one misconfigured firewall rule, and everything is open. The modern position, usually called zero trust, is that being on the network proves nothing. Every call is encrypted, and both ends prove who they are.

The mechanism is mutual TLS, or mTLS. Ordinary TLS has the server present a certificate so that the client knows who it is talking to (). In mutual TLS the client presents one as well. Each side then knows the other’s identity with cryptographic certainty.

The certificates name workloads, not machines. An identity looks like spiffe://cluster.local/ns/social/sa/feed: the feed service’s account in the social namespace. The format comes from SPIFFE, a standard for workload identity. The mesh’s control plane acts as the certificate authority. It issues each workload a certificate when it starts, valid for hours, and replaces it automatically before it expires. Nobody handles a key, and a stolen certificate is useless by the next day.

Knowing who is calling makes it possible to decide what they may do.

apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: feed-callers
  namespace: social
spec:
  selector:
    matchLabels:
      app: feed
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/web/sa/web-frontend"]
      to:
        - operation:
            methods: ["GET"]
            paths: ["/feed/*"]

This answers “which service is calling?”. It does not answer “on behalf of which user?”. That is carried separately, as a token in the request that each service validates (, ). Both are needed: the service identity stops a compromised internal system from calling anything it likes, and the user identity stops one user from reading another’s data.

Steering traffic

Because every request passes through a proxy that the control plane configures, routing becomes something you declare instead of something you deploy.

TechniqueWhat it doesUsed for
Weighted routingSend a percentage of requests to a different versionCanary releases: 1%, then 10%, then all ()
Matching on headersRoute requests carrying a particular header to a particular versionTesting a new version with internal users only
MirroringCopy live requests to a second version and discard its responsesTesting with real traffic and no user impact
Fault injectionDelay or fail a percentage of requests on purposeChecking that callers cope ()
Locality preferencePrefer instances in the caller’s own zoneLower latency and lower transfer cost, with spill-over when the zone is unhealthy

In Kubernetes these rules are increasingly written with the Gateway API, a standard set of resources that most gateways and meshes now implement, so that the same definition works across products. It has been stable since 2023 and reached version 1.6 in mid-2026.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: feed
  namespace: social
spec:
  parentRefs:
    - group: ""
      kind: Service
      name: feed           # applies to calls made to the "feed" Service
  rules:
    - backendRefs:
        - name: feed-v1
          port: 8080
          weight: 90
        - name: feed-v2
          port: 8080
          weight: 10
      timeouts:
        request: 2s

Gateway and mesh

Traffic is described by direction. North-south traffic enters the system from outside. East-west traffic flows between services inside it. The two have different needs and are handled by different components.

API gatewayService mesh
TrafficFrom outside clientsBetween internal services
IdentifiesUsers and API keysServices
Typical workAuthentication, quotas, public routing, request validation ()mTLS, balancing, retries, telemetry, release control
Where it runsAt the edge, as a few shared instancesBeside or beneath every service

Both are proxies, often the same proxy software, and products increasingly do both. They remain worth separating in a design because the trust model differs: the gateway assumes the caller may be hostile.

Contracts between services

Infrastructure delivers the bytes. Whether the two services still understand each other after next week’s deployment is a separate problem, and it causes at least as many outages.

  • Define the interface in a schema. OpenAPI for REST, Protocol Buffers for gRPC. Generate clients and servers from it, so that the definition and the code cannot drift.
  • Change compatibly. Add optional fields. Never remove, rename or repurpose a field that a caller may still send or read. Services are deployed one at a time, so for a while old callers talk to new servers and new callers to old servers. Both combinations must work ().
  • Test the contract, not the whole system. A consumer-driven contract test records what each caller actually relies on and runs those expectations against the provider in its own build. A breaking change fails the provider’s pipeline before it is deployed, without an environment containing every service.
  • Pass deadlines along. If the web service has 800 ms left to answer the user, it should tell the feed service so, and the feed service should tell whatever it calls. Work that cannot finish in time should not start. gRPC carries deadlines natively ().
  • Pass context along. Trace identifiers and the user’s token travel in headers that each service must forward on its outgoing calls. The mesh cannot do this part, because only the application knows which outgoing call belongs to which incoming request.

Do you need a mesh?

A mesh solves real problems and adds a real system to operate. The decision follows from how many of its problems you have.

SituationReasonable choice
A monolith, or a handful of services in one languageThe platform’s Services, and a well-configured HTTP or gRPC client library. No mesh.
gRPC everywhere, with uneven load across podsClient-side balancing in gRPC, or a request-level proxy. A mesh is one way, not the only one.
A requirement that all internal traffic be encrypted and authenticatedA mesh, possibly in its lightest mode, is usually the cheapest way to get it everywhere
Dozens of services in several languages, owned by many teamsA mesh, run by a platform team
Gradual releases and traffic shifting as routine practiceA mesh, or a gateway that implements the Gateway API

Adopt it for a reason you can state, begin with the feature that reason needs, which is usually mTLS and metrics, and add routing features later. A mesh installed “because we will need it” tends to be remembered mostly for the incidents it took part in.

In an interview. You are rarely asked to design a mesh. You are often asked “how does service A find service B?” or “how do you secure calls between services?”. Short, concrete answers serve best: “Each service has a stable DNS name backed by a virtual address, and the platform routes only to instances passing readiness checks. Between services we use mutual TLS with short-lived workload certificates issued by the mesh, and authorization policies saying which service may call which.” Mention the gRPC connection problem if you have proposed gRPC.

Key points

  • Every call between services needs discovery, balancing, health, security, resilience, observability and release control. The design question is where each of those lives.
  • Discovery maps a stable name to the current healthy instances. The caller can hold the list, a balancer can, or the platform can.
  • A Kubernetes Service is a name, a virtual address that never changes, and a list of pods that pass their readiness check.
  • Connection-level balancing fails for HTTP/2 and gRPC, because one long-lived connection carries everything. Balance requests.
  • A service mesh puts the communication logic in proxies configured by a control plane, giving every service the same behavior in any language.
  • Mutual TLS with short-lived workload certificates gives every call encryption and a verified service identity. User identity travels separately.
  • The gateway handles traffic from outside, and the mesh handles traffic between services.
  • Compatible schemas and contract tests keep services able to talk across deployments.

Check yourself

After moving from REST over HTTP/1.1 to gRPC, a team sees one pod of a service at 90% CPU while four others are idle. What is happening?

gRPC uses one long-lived HTTP/2 connection for all requests. The platform’s balancing chooses a pod when a connection is opened, so every request from that caller goes to the same pod, and pods added later receive nothing. Balancing must be done for each request, by a proxy that understands HTTP/2 or by client-side balancing in the gRPC library.

What three things make up a Kubernetes Service, and which one decides whether a particular pod receives traffic?

A DNS name, a virtual address that does not change, and the list of endpoints. The list contains only pods that match the selector and pass their readiness check, so the readiness check decides. A pod that reports ready when it cannot serve will receive traffic and fail it.

In a service mesh, the control plane goes down for ten minutes. What happens to requests between services?

They continue. Requests pass through the data plane, the proxies, which keep operating with the configuration and certificates they already hold. What stops is change: new instances may not be learned about, policy updates do not arrive and certificates are not renewed. A short outage is therefore tolerable, which is the purpose of the separation.

What does mutual TLS between services establish, and what does it not?

It encrypts the connection and proves to each side which service the other is. That allows policies such as “only the web service may call the feed service”. It says nothing about which user the request is for. The user’s identity must be carried in the request as a token that the receiving service validates.

Why do the client in this chapter and real load balancers refuse to eject every instance, even when all appear to be failing?

If every instance looks unhealthy, the likelier explanation is a problem with the observer, its network or the health check itself, than the simultaneous failure of all instances. Ejecting them all guarantees total failure. Sending traffic anyway gives some chance of success and lets recovery be noticed.

A team adds a field rename to an internal API and deploys the provider first. Callers begin failing at once. Which two practices would have prevented this?

Compatible change: add the new field and keep the old one until every caller has moved, since old and new versions run side by side during any rollout. And consumer-driven contract tests in the provider’s build, which would have failed when the field that callers depend on disappeared.

A company has six services, all in Go, run by two teams. Someone proposes a service mesh. What do you ask?

Which problem it would solve. With one language and few services, a shared client library and the platform’s own discovery cover balancing, timeouts and retries cheaply. A mesh becomes worthwhile for a specific need, such as a requirement for mutual TLS on all internal traffic, or uniform telemetry and traffic shifting across many teams and languages. Without such a need it adds a system to operate for little return.
