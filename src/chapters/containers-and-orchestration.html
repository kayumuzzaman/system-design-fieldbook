The problem: running software on machines you did not set up

The photo app is now about a dozen services. Each needs a particular version of a language runtime, a set of libraries, some configuration, and a machine to run on. Installing these by hand on every server leads to two familiar failures. A service works on the developer’s laptop and fails in production because a library differs. Two services on one server need different versions of the same thing.

Operating the services raises more questions. Which of forty servers should run the new copy of the feed service? What restarts it when it crashes at night? How do the other services find it after it moves? How does a new version replace the old one without dropping requests?

Containers answer the packaging problem. Orchestrators answer the operating problem. Kubernetes is the orchestrator most systems use, and it is the one described here, though the ideas carry over to the others.

What a container is

A container is an ordinary process, running on an ordinary Linux kernel, that has been given a restricted view of the machine. Two kernel features do the restricting.

  • Namespaces limit what the process can see. Inside its own namespaces a process has its own list of processes, its own network interfaces and IP address, its own hostname, and its own filesystem root.
  • Control groups, usually written cgroups, limit what it can use: how much CPU time, how much memory, how much disk and network throughput.

There is no “container” object in the kernel. The word names the combination. You can make one by hand, and doing so removes much of the mystery. This command starts a shell in a new process namespace on a machine that is running about 70 processes.

$ unshare --pid --fork --mount-proc sh -c 'echo "my pid is $$"; ps -e -o pid,comm'
my pid is 1
    PID COMMAND
      1 sh
      2 ps

The shell believes it is process 1 and can see nothing but itself and its child. It is still an ordinary process on the host, visible there under its real number. A container runtime does the same for the network, the filesystem and the rest, applies cgroup limits, and starts your program.

The last row matters when the code is not yours. A provider that runs strangers’ code does not rely on plain containers. It wraps each one in a small virtual machine or a kernel that intercepts system calls, as the function platforms in do. For your own services on your own machines, plain containers are the normal choice.

Images

A container needs a filesystem to start from: the program, its libraries, the runtime, and enough of an operating system’s files for them to work. That bundle is an image. An image is built once and can then be run any number of times, on any machine with a container runtime, and it is the same bytes everywhere. This is what ends “works on my machine”.

An image is made of layers. Each layer records a set of file changes, and each is named by a hash of its contents.

An image is described by a build file. This one builds a TypeScript service in two stages, so that compilers and development dependencies do not end up in what is shipped.

# Stage 1: build. This stage is thrown away.
FROM node:24-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build && npm prune --omit=dev

# Stage 2: what actually ships.
FROM node:24-slim
WORKDIR /app
ENV NODE_ENV=production
COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
USER node
EXPOSE 8080
CMD ["node", "dist/server.js"]

Three habits in this file are worth copying.

  • Order instructions from least to most often changed. Each instruction makes a layer, and a changed layer forces every later one to be rebuilt. Copying the dependency list and installing before copying the source means a code change does not reinstall dependencies.
  • Ship only what runs. A smaller image downloads faster, starts sooner on a new machine, and contains fewer programs for an attacker to use.
  • Do not run as root. The USER line means that a flaw in the service gives an intruder an unprivileged account inside the container, which is a much weaker starting point.

Images live in a registry, a server that stores and serves them. An image is referred to by a name and either a tag, such as feed:2026-10-10.3, or a digest, the hash of its contents. A tag is a label that can be moved to a different image. A digest cannot. The tag latest in particular means “whatever was pushed most recently”, so two machines that pull it an hour apart can end up running different code. Give every build a unique tag and deploy that.

Configuration and secrets stay out of the image. The same image should run in test and in production, differing only in what it is told at start-up through environment variables or mounted files. builds on this.

What an orchestrator does

With images, running one container on one machine is a single command. Running three hundred containers of twelve services on forty machines, and keeping them running, is a different problem. An orchestrator takes a description of what should be running and makes it so:

  • Placement. It chooses a machine for each container that has room for it.
  • Healing. It restarts containers that crash and replaces those on machines that die.
  • Scaling. It adds and removes copies as load changes.
  • Discovery and load balancing. It gives each service a stable name and spreads requests over its copies, as described.
  • Rollout. It replaces an old version with a new one gradually, and can go back.

Kubernetes was released by Google in 2014, drawing on a decade of running its internal systems Borg and Omega, and is now maintained by a foundation with contributors from most of the industry. As of October 2026 the current release is 1.37. There are about three releases a year, and each is supported for a little over a year, so running Kubernetes includes upgrading it regularly.

How a cluster is put together

A Kubernetes cluster has two kinds of machine. Nodes run your containers. The control plane decides what the nodes should run.

PartJob
API serverThe front door. Every read and change of cluster state goes through it, from people and from the cluster’s own components.
etcdA small, consistent key-value store that holds all cluster state, replicated with the Raft protocol from . Usually three or five copies.
SchedulerWatches for pods with no node and assigns each one.
ControllersA set of loops, each responsible for one kind of object, that make reality match what is recorded.
kubeletAn agent on every node. It starts and stops the containers assigned to its node and reports their health.
Container runtimeThe program that actually pulls images and runs containers, such as containerd.

One property of this design deserves attention. If the whole control plane goes down, containers that are already running keep running and keep serving. Nothing new can be scheduled and nothing that fails will be replaced, but the service stays up. This is the separation of control plane from data plane discussed in , and it is why a control plane outage is serious without being an immediate outage of everything on the cluster.

Most teams do not run the control plane themselves. Every large cloud offers it as a managed service, and you supply the nodes or let the provider manage those too. The published scale limits are generous: as of version 1.37 a cluster is supported up to 5,000 nodes and, by long-standing guidance, 150,000 pods with no more than 110 on a node.

Desired state and reconciliation

The central idea of Kubernetes is how you tell it what to do. You do not issue commands such as “start three copies of the feed service”. You record a fact: “there should be three copies of the feed service, running this image”. The system’s job is to make the fact true and keep it true.

The recorded fact is the desired state. What is really running is the actual state. A controller is a loop that compares them and acts on the difference. This is called reconciliation.

Reduced to its core, a controller for a set of identical pods is a short function.

type Pod = { name: string; image: string; healthy: boolean };
type Desired = { replicas: number; image: string };
type Action = { kind: "create"; image: string } | { kind: "delete"; name: string };

/** Compares what should exist with what does, and returns the steps that close the gap. */
export function reconcile(desired: Desired, actual: Pod[]): Action[] {
  const actions: Action[] = [];
  // 1. anything broken or running the wrong image is removed
  const good = actual.filter((p) => p.healthy && p.image === desired.image);
  for (const p of actual) if (!good.includes(p)) actions.push({ kind: "delete", name: p.name });
  // 2. too few: create the difference. Too many: delete the surplus.
  for (let i = good.length; i < desired.replicas; i++) actions.push({ kind: "create", image: desired.image });
  for (const p of good.slice(desired.replicas)) actions.push({ kind: "delete", name: p.name });
  return actions;
}

Given a desired state of three pods on version 2, and an actual state of one healthy pod on version 2, one unhealthy pod, and one healthy pod still on version 1, the function returns two deletions and two creations. Run again after those are applied, it returns nothing. Real controllers are more careful, especially about replacing versions gradually, but the shape is this.

The function looks only at the current state. It does not need to know what happened: whether a pod crashed, a node died, or someone changed the number. A system built on events can miss one and stay wrong. A system that repeatedly compares states corrects itself the next time it looks, whatever it missed. The same reasoning made state-based repair attractive in .

Objects are connected by labels, not by pointers. The Deployment manages every pod labeled app: feed, and a Service selects pods the same way. These files are kept in version control and applied by an automated pipeline, so the repository is a record of what the cluster should be running.

Health probes

The orchestrator needs to know two different things about a container: whether it is broken, and whether it can take traffic right now. Kubernetes asks them with separate probes, each a small request it sends on a timer.

ProbeQuestionIf it fails
StartupHas the program finished starting?Keep waiting, up to a limit. The other probes do not run yet
ReadinessCan it serve requests now?Remove it from the Service until it passes again
LivenessIs it stuck beyond recovery?Restart the container

The advice from applies with more force here, because a liveness probe can restart things.

Common mistake. A liveness probe that checks dependencies. If /healthz queries the database and the database slows down, every pod fails its liveness probe at once and every pod is restarted, which adds a wave of cold starts and reconnections to a database that was already struggling. A liveness probe should answer one question: is this process itself stuck? It should touch nothing outside the process. Dependency checks, used with care, belong in readiness.

Requests and limits

Each container declares how much CPU and memory it needs. There are two numbers for each resource, and they do different jobs.

  • The request is a reservation. The scheduler adds up the requests of the pods on a node and will not place a pod where its request does not fit. Requests that are too low pack nodes too tightly. Requests that are too high leave paid-for capacity idle.
  • The limit is a ceiling enforced by the kernel through cgroups. What happens at the ceiling depends on the resource. CPU can be taken away and given back, so a container at its CPU limit is throttled: paused for the rest of each short accounting period. Memory cannot be taken back, so a container that exceeds its memory limit is killed and restarted.

Two practical rules follow, and the Deployment above uses both.

Set the memory limit equal to the memory request. Then a container can never be using memory it was not guaranteed, and a node cannot run out because several containers burst at once.

Be cautious with CPU limits. Throttling shows up as latency: a request that needed 20 ms of CPU waits for the next accounting period and takes 100 ms, while the node has idle cores. Many teams set a CPU request, which guarantees a share under contention, and no CPU limit. Others need limits for predictability. Either way, measure throttling before trusting a latency number.

When a node itself runs short, the kubelet evicts pods to protect it, starting with those using more than they requested. Honest requests are therefore protection as well as bookkeeping.

Scheduling

The scheduler assigns each new pod to a node in two steps. It first filters out the nodes that cannot run the pod, then scores the rest and picks the best.

type Resources = { cpu: number; memory: number };            // CPU in millicores, memory in MiB
type Node = { name: string; capacity: Resources; requested: Resources };

function fits(node: Node, pod: Resources): boolean {
  return node.requested.cpu + pod.cpu <= node.capacity.cpu &&
         node.requested.memory + pod.memory <= node.capacity.memory;
}

/** Fraction of the node that would be in use after placing the pod, averaged over CPU and memory. */
function fullness(node: Node, pod: Resources): number {
  return ((node.requested.cpu + pod.cpu) / node.capacity.cpu +
          (node.requested.memory + pod.memory) / node.capacity.memory) / 2;
}

export function schedule(nodes: Node[], pod: Resources, strategy: "spread" | "pack"): Node | undefined {
  const candidates = nodes.filter((n) => fits(n, pod));       // filter
  if (candidates.length === 0) return undefined;              // the pod stays Pending
  const score = (n: Node) => (strategy === "pack" ? fullness(n, pod) : 1 - fullness(n, pod));
  const chosen = candidates.reduce((best, n) => (score(n) > score(best) ? n : best));
  chosen.requested.cpu += pod.cpu;                            // bind
  chosen.requested.memory += pod.memory;
  return chosen;
}

The two strategies pull in opposite directions. Spreading puts each pod on the emptiest node, which leaves room everywhere for bursts and limits the damage when a node dies. Packing fills nodes one at a time, which leaves whole nodes empty so that they can be removed and not paid for. The default leans toward spreading, and cost-conscious clusters lean toward packing.

The function also shows a common source of waste. Place pods that request 500m of CPU and 1 GiB of memory on an empty node with 4 CPUs and 16 GiB, and it holds eight. The CPU is then fully reserved and half the memory, 8 GiB, can never be used. Node shapes should match the shape of what runs on them.

Real scheduling takes more into account, and you can state most of it as rules:

  • Spread across failure domains. A rule can require the copies of a service to be divided evenly among availability zones, or forbid two copies on one node. Without one, the scheduler may place all three copies on the same machine, and a single failure takes the service down.
  • Attract or repel. Pods can ask to be near certain others or away from them, and nodes can be marked so that only pods which explicitly accept the mark land there, which is how GPU nodes are kept for workloads that need a GPU.

A pod that fits nowhere stays in the state Pending. It is one of the most common things to debug, and the cause is nearly always that no node has enough unreserved CPU or memory, or that a rule excludes every node.

Autoscaling

Three separate mechanisms adjust capacity, at three levels.

MechanismChangesReacts in
Horizontal pod autoscalerThe number of pods of a serviceTens of seconds, plus pod start time
Vertical autoscalingThe requests of each podSlowly, from days of observed usage
Cluster autoscalerThe number of nodesMinutes: a new machine must boot and join

The horizontal autoscaler is a controller like any other. Every 15 seconds by default it reads a metric, usually average CPU use as a percentage of what pods requested, and applies one formula.

desired pods = ⌈ current pods × current value ÷ target value ⌉

If ten pods average 90% against a target of 60%, it wants fifteen. Two refinements keep it from thrashing. A change is skipped when the ratio is within 10% of 1. And it scales up at once but waits five minutes before scaling down, using the highest recommendation from that period.

Each of the 10 pods uses 90% of the CPU it requested, against a target of 60%. The ratio is 1.5, so the formula asks for 15 pods. That is 5 more. Spread over 15 pods, the same load comes to about 60% each.

Three things about autoscaling matter for design.

The target is your headroom. A target of 60% means pods normally run with 40% spare, which is what absorbs a surge during the time it takes new pods to arrive. A target of 90% is cheaper and leaves almost nothing. explains why latency climbs steeply long before 100%.

The levels chain, and the delays add. The pod autoscaler asks for five more pods. If the nodes are full, those pods wait as Pending until the cluster autoscaler notices, requests machines, and the machines boot. A surge that outruns free node capacity is answered in minutes. Keeping some spare node capacity is the remedy.

CPU is not always the right signal. A service that waits on a slow database has low CPU while its users queue. A queue consumer should scale on the length or age of its queue, as suggested. Autoscalers can use such metrics, and choosing the signal that actually tracks load is most of the work.

Autoscaling also needs limits in the other direction. A maximum protects the budget and whatever lies downstream, for the reasons in : fifty copies of a service can open fifty times the database connections.

Stopping gracefully

Pods are stopped all the time: on every deployment, every scale-down, every node replacement. Each stop is a chance to drop requests, and avoiding that takes cooperation between the platform and the program.

When a pod is deleted, the container is sent the signal SIGTERM and given a grace period, 30 seconds by default, before it is killed outright. At the same moment, the pod is removed from its Service. Those two things are not coordinated, and the removal takes a moment to reach every proxy and load balancer. A program that exits the instant it receives SIGTERM will refuse requests that are still on their way.

The fix has two parts. A short pause before the signal, the preStop line in the Deployment above, covers the gap. Then the program handles the signal properly.

import http from "node:http";

let ready = true;                 // what the readiness endpoint reports

const server = http.createServer((req, res) => {
  if (req.url === "/ready") { res.writeHead(ready ? 200 : 503).end(); return; }
  setTimeout(() => res.end("done\n"), 300);      // stands in for real work
});
server.listen(8080);

process.on("SIGTERM", () => {
  ready = false;                  // fail readiness so no new traffic is sent here
  server.close(() => process.exit(0));           // stop accepting, finish what is in flight, then exit
  setTimeout(() => process.exit(1), 25_000).unref();   // give up before the platform's 30 s deadline
});

In a test, a request that was 100 ms into its 300 ms of work when the signal arrived still received its response, the process then exited with status 0, and a new connection afterward was refused. The same discipline applies to consumers of queues: stop taking new messages, finish or release the current one, then exit.

Some stops are planned by an operator, such as emptying a node to upgrade it. A disruption budget tells Kubernetes how many pods of a service may be down at once for such reasons, so that draining three nodes at the same time cannot remove every copy.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: feed
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: feed

Stateful workloads

Everything above assumes pods are interchangeable. A database is not. Its copies have distinct roles, each owns particular data, and they must be started, upgraded and replaced in a careful order.

Kubernetes supports this with two things. A persistent volume is storage that exists independently of any pod and is reattached when a pod is replaced. A StatefulSet gives pods stable names such as db-0 and db-1, starts them in order, and gives each its own volume that follows it. For real databases this is rarely enough, so an operator is added: a custom controller that encodes the procedures a database administrator would follow, such as promoting a replica or taking a backup, in the same reconciliation style.

Whether to run databases this way is a judgment about your team. It works, and large companies do it. It also makes you responsible for failover, backups and upgrades of software where mistakes lose data. For most teams a managed database outside the cluster is the better trade, with Kubernetes running the stateless services that are easy to replace.

What Kubernetes costs, and the alternatives

Kubernetes solves real problems and brings a large surface of its own: networking, storage, access control, upgrades three times a year, and a long list of settings whose defaults are not always safe. A small team can spend more time on the cluster than on its product.

The usual advice from holds: adopt the heavier tool when a problem you actually have requires it. Containers are worth using from the first day. An orchestrator of this size is worth it when the number of services and people makes a shared platform cheaper than each team’s own arrangements.

In an interview. You will rarely be asked to design Kubernetes, and often be expected to design for it. Say that services are stateless containers behind a load balancer, scaled on a named metric with a stated minimum, maximum and target. Mention readiness probes when you describe deployments, zone spreading when you discuss availability, and connection limits when you mention autoscaling. If asked how a failed instance is replaced, describe the reconciliation loop in a sentence.

Common mistakes

  • Deploying the tag latest. Nobody can say what is running or go back to what ran yesterday.
  • No requests. The scheduler packs nodes blindly and the first busy hour ends in evictions.
  • Memory limit above the request. Nodes run out of memory when several containers grow at once.
  • Liveness probes that check dependencies. A slow database becomes a restart of the whole fleet.
  • No readiness probe. Traffic reaches pods that have not finished starting, and every deployment produces errors.
  • Ignoring SIGTERM. Every deployment and scale-down drops the requests in flight.
  • All copies in one place. Three replicas on one node or in one zone are one failure away from none.
  • Autoscaling on the wrong signal. CPU for a service whose bottleneck is elsewhere.
  • No maximum. A traffic spike, or a bug, scales a service until it overwhelms its database or the budget.
  • Local state in a pod. Files written inside a container vanish when it is replaced, which is often.
  • Adopting Kubernetes for three services. The platform becomes the project.

Key points

  • A container is a process that the kernel isolates with namespaces and limits with cgroups. It shares the host’s kernel, which makes it light and less isolated than a virtual machine.
  • An image is an immutable, layered bundle of a program and its dependencies. Build it once, tag it uniquely, and run the same bytes everywhere.
  • An orchestrator places containers, replaces failed ones, scales them, connects them and rolls out new versions.
  • Kubernetes records desired state and runs controllers that reconcile actual state toward it. Deployment, scaling and recovery are the same loop.
  • Readiness decides whether a pod gets traffic. Liveness decides whether it is restarted, and should check only the process itself.
  • Requests reserve capacity for scheduling. Limits are enforced: CPU is throttled, memory overuse is fatal.
  • The pod autoscaler follows one formula toward a target. The target is the headroom, and new nodes take minutes.
  • Handle SIGTERM: stop accepting, finish work in flight, exit. Pods are stopped constantly.

Check yourself

What two kernel features make a container, and what does each restrict?

Namespaces restrict what the process can see: its own process list, network, hostname and filesystem. Control groups restrict what it can use: CPU, memory and I/O. A container is a normal process with both applied.

Why does the order of instructions in an image build file affect build time?

Each instruction produces a layer, and a layer is rebuilt when it or anything before it changes. Putting rarely changed steps first, such as installing dependencies, means a code change rebuilds only the last layers and reuses the rest from cache.

A Deployment asks for 4 replicas. One node fails, taking 2 pods with it. Describe what happens without mentioning any event.

The controller compares desired state, 4 pods, with actual state, 2 healthy pods. The difference is 2, so it creates 2 pods. The scheduler assigns them to nodes with room, and the kubelets there start them. The controller did not need to know why pods were missing.

What is the difference between a readiness probe failing and a liveness probe failing?

A failing readiness probe removes the pod from its Service, so it gets no traffic, and leaves it running. It returns when the probe passes. A failing liveness probe restarts the container. Readiness is for “not now”. Liveness is for “never, unless restarted”.

A container has a CPU limit of 1 core and a memory limit of 1 GiB. What happens when it tries to use 2 cores? When it tries to use 1.5 GiB?

CPU use above the limit is throttled: the container is paused for part of each accounting period, which appears as added latency. Memory above the limit cannot be throttled, so the container is killed for being out of memory and restarted.

Twelve pods average 45% CPU against a target of 75%. What does the horizontal autoscaler want, and when does it act?

12 × 45 ÷ 75 = 7.2, rounded up to 8 pods. The ratio 0.6 is outside the 10% tolerance, so it will scale down, after the default five-minute stabilization period during which it keeps the highest recommendation. The widget shows that 8 pods would then run at about 67.5% each.

Why can a program that exits immediately on SIGTERM cause failed requests, even though the pod was removed from the Service at the same time?

The removal has to reach every load balancer and proxy, which takes a few seconds, and it is not coordinated with the signal. Requests already routed to the pod, or routed in that gap, arrive after the program has gone. A short pre-stop pause and finishing in-flight requests before exiting close the gap.

The pod autoscaler asks for 20 more pods and they stay Pending for four minutes. What is the likely cause, and what reduces the delay?

The existing nodes have no unreserved capacity, so the pods cannot be scheduled until the cluster autoscaler adds nodes, which must boot and join. Keeping spare node capacity, using nodes that start faster, or scaling nodes ahead of known peaks reduces the wait.
