A system is more than its code

Suppose you write a small program that lets people upload a photo and see it again later. On your laptop it is thirty lines: accept a file, write it to a folder, record its name in a database table, and serve it back when asked. It works the first time you try it.

Now put the same program in front of ten million people. Nothing about the thirty lines is wrong, and yet almost everything goes wrong. One machine cannot accept that many connections. Its disk fills in days. When it restarts, the service disappears for everyone at once. A user in Dhaka waits a second for bytes stored in Virginia. Two uploads with the same file name overwrite each other. A single slow database query holds up every other request behind it.

None of these problems live in the code you wrote. They live in the arrangement around it: how many machines there are, where data is kept, what happens when a part fails, and how the parts talk to each other. System design is the work of deciding that arrangement on purpose.

A useful working definition: design is the set of decisions that are expensive to change later. Renaming a variable is cheap, so it is not design. Choosing how photos are identified, which database stores their metadata, and whether uploads are processed while the user waits are all expensive to reverse once real data and real traffic depend on them. Those are the decisions this book is about.

Two levels of zoom: high-level and low-level design

The same system can be described at several distances, in the way a city can be shown on a country map, a street map, or a floor plan. Two distances matter enough to have names.

High-level design (HLD) describes the system as a set of running components and the connections between them: load balancers, application servers, databases, caches, queues. It answers questions such as “where does this data live?” and “what happens if this machine dies?” The picture it produces is the box-and-arrow architecture diagram.

Low-level design (LLD) describes the inside of one component: its classes, interfaces, data structures and the way they call one another. It answers questions such as “which object owns this rule?” and “how do I add a new payment method without editing ten files?” The pictures it produces are class and sequence diagrams, and its final form is code.

The C4 modelSimon Brown’s C4 model formalizes this zooming into four levels: context, containers, components and code. “Container” there means any separately running unit, such as a web app or a database, and has nothing to do with Docker. If a team asks you for “a C4 container diagram”, they want the middle panel of .

They are not separate subjects. A high-level decision constrains the code: if you choose to process uploads through a queue, some class now has to deal with a message arriving twice. A low-level decision constrains the architecture: if session data is kept in a variable inside the server process, you cannot add a second server without breaking logins. Good designers move between the two levels without noticing, and this book will ask you to do the same.

Requirements: what the system must do, and how well

You cannot judge a design without knowing what it is for. The first step in any design is therefore to pin down requirements, and they come in two kinds.

Functional requirements state what the system does. They are the features, and they can usually be written as “a user can…” sentences: a user can upload a photo, a user can follow another user, a user sees a feed of photos from the people they follow.

A clumsy name“Non-functional” sounds like “does not work”. You will also see quality attributes, cross-functional requirements, or simply “the -ilities”. The standard ISO/IEC 25010 lists them formally. They all mean the same thing: the standards the system must meet while doing its job.

Non-functional requirements state how well it does those things. A feed that takes forty seconds to load satisfies the functional requirement and is still a failed product. The non-functional requirements that drive most architecture decisions are these:

Two habits make requirements useful. First, attach a number. “Fast” cannot be designed for or tested; “99% of requests under 300 milliseconds” can. Second, ask what is out of scope. A photo app that does not need video, direct messages or advertising in its first version is a far smaller design problem, and saying so early stops you from designing three systems at once.

In an interview. The prompt is vague on purpose. “Design Instagram” describes a product with hundreds of features. Spend the first few minutes agreeing on three or four functional requirements and the two or three non-functional ones that matter most. Candidates who start drawing boxes at once are usually solving a problem the interviewer did not ask.

Constraints and trade-offs

If every quality could be maximized at once, design would be easy. It cannot, because the qualities pull against each other. Keeping three copies of data improves durability and availability, and it raises cost and makes it harder for all copies to agree. Checking every write with every copy before answering makes the copies agree, and it makes the write slower. This is why experienced engineers answer so many questions with “it depends”. What it depends on is the requirements.

These are the trade-offs you will meet most often. Each gets its own treatment later in the book.

You can have more of……by giving up some…A concrete case
ConsistencyAvailability or latencyWait for all replicas to confirm a bank transfer, and refuse it if one is unreachable

A design decision, then, has three parts: the option you chose, the options you rejected, and the requirement that made the difference. A design that lists only the first part is a description. One that includes all three is an argument, and an argument can be checked by someone else.

Common mistake. Naming a technology in place of a reason. “We’ll use Kafka” does not describe a design. “Uploads must not be lost if the resizing service is down, so they go onto a durable log first” does, and it would still be a design if you swapped Kafka for something else.

Conway’s lawIn 1968 Melvin Conway observed that organizations produce designs that copy their own communication structure. Four teams tend to build a four-part system. It is why “how should we split this into services?” is often a question about who works with whom, and why architecture and team structure are usually changed together.

Constraints are the trade-offs someone has already made for you. A deadline, a budget, a law that says certain data must stay in one country, a team that knows PostgreSQL and has never run Cassandra: each removes options before you start. They belong in the requirements, since they often decide more than the technical arguments do.

A method you can repeat

Design looks like inspiration from the outside. In practice it is closer to a checklist that you loop through, and the same loop works for a one-hour interview, a design document at work, and a system you are building alone.

  1. Requirements. Agree on the few features that matter and the numbers the system must hit. Write down what is out of scope.
  2. Estimates. Turn “ten million users” into requests per second, bytes stored per year and bytes sent per second. The result tells you whether one database is enough or whether you have a distribution problem. teaches this.
  3. Interface and data. List the operations the outside world can call, and the main things you store and how they relate. This step is short and it exposes misunderstandings early. If you cannot say what POST /photos returns, you are not ready to draw servers.
  4. Architecture. Draw the simplest set of components that satisfies the functional requirements, and trace one read and one write through it from the client to storage and back.
  5. Deep dives. Pick the two or three places where the numbers from step 2 break the simple picture, and design those properly: the hot table, the fan-out, the large file.
  6. Stress it. For each component ask what happens when it is slow, when it is down, and when traffic is ten times higher. Fix what you find, or say out loud that you are accepting the risk.

The loop matters as much as the steps. An estimate in step 2 may show that a requirement from step 1 is unaffordable, and the right response is to go back and renegotiate it. A failure found in step 6 may change the data model from step 3. A first pass that goes through all six steps quickly, followed by a second pass that goes deeper, is better than one slow pass that perfects step 4 and never reaches step 6.

The method on a small example

Here is a first pass for the photo app. It is deliberately quick, and every line of it is expanded somewhere later in the book.

StepFirst-pass answer
1 RequirementsUpload a photo. View one photo. See a feed of recent photos from people you follow. Feed loads in under 300 ms for 99% of requests. No acknowledged upload is lost. Out of scope: video, messages, search.
2 Estimates10 million daily users. About 23 uploads and 5,800 photo views per second on average, roughly three times that at peak. About 5 TB of new photo data per day. Reads outnumber writes 250 to 1. (Derived in .)
3 Interface, dataPOST /photos, GET /photos/{id}, GET /feed, POST /follows. Stored: users, photos (metadata), follows, and the image bytes themselves.
4 ArchitectureLoad balancer, stateless API servers, a relational database for metadata, an object store for image bytes, a CDN in front of the images.
5 Deep divesImage delivery: about 9 Gbit/s on average is too much to serve from our own servers, so the CDN is essential. Feed: computing it per request means reading from hundreds of followed accounts, so precompute or cache it.
6 Stress itThe database is a single point of failure, so add a replica and automatic failover. Resizing images during the upload request makes uploads slow and fragile, so move it to a queue and workers.

Notice what the estimates did. Without them, step 4 is guesswork. With them, two facts stand out: the system is overwhelmingly read-heavy, and nearly all of its bytes are images. Those two facts justify the CDN, the object store and the cached feed, and they also say what does not need attention yet. Twenty-three writes per second is a load that one ordinary database handles comfortably.

Design in an interview and design at work

The method is the same in both settings. The conditions are very different, and knowing the differences keeps you from applying interview habits where they do harm.

In an interviewAt work
Time45 to 60 minutesDays to months, revisited for years
Starting pointA blank boardAn existing system with users, data and history
ScaleUsually stated as very large, to force the interesting problemsUsually modest today, uncertain tomorrow
What is judgedYour reasoning, and whether you see the trade-offsWhether it works, what it costs, and whether the team can run it
Biggest riskRunning out of time before reaching the hard partBuilding for a scale or a feature that never arrives
OutputA diagram and a conversationA written design, a migration plan, and working software

In production. Most real design work is changing a system that already runs. The hard question is rarely “what is the ideal architecture?” It is “how do we get from here to there without downtime, while the old and new versions run side by side?” Migration is a design problem in its own right, and it comes up in and .

Mistakes beginners make

  • Designing for a scale you do not have. A system for a thousand users that copies an architecture built for a billion pays the full complexity cost and gets none of the benefit. Start with the simplest design that meets the stated requirements, and know which part you would change first when load grows.
  • Skipping the numbers. “A lot of traffic” supports any design and therefore none. One rough estimate removes most of the wrong options.
  • Ignoring the data model. Servers are replaceable in an afternoon. The shape of stored data lasts for years and is the hardest thing to migrate. Give it more attention than the boxes.
  • Drawing only the path where everything works. Every arrow on a diagram is a network call that can be slow, fail, or succeed twice. A design that does not say what happens then is half a design.
  • Treating a product name as an answer. “Add Redis” is a purchase. Say what is cached, for how long, and what happens when the cache is empty.
  • Forgetting the people. Someone will be woken at night by this system. If nobody on the team can operate a component, it is a liability however elegant it looks.

How the rest of the book fits together

System design is wide, and it is easy to learn forty topics without seeing how they connect. The system map on the contents page is the picture to keep in mind. A request leaves a client, crosses the network (Part II), reaches services arranged in some architecture (Part VI), which read and write data (Part III) and hand off slower work to be done later (Part V). Because all of this runs on many machines that fail independently, the rules of distributed systems (Part IV) apply everywhere, as do operations (Part VII) and security (Part VIII). Open any one service and you are in low-level design (Parts IX and X).

The remaining chapters of Part I give you the vocabulary every later chapter uses: what happens during one request, how to estimate, and how to reason about speed, growth and failure.

Key points

  • Design is the set of decisions that are expensive to change later: where data lives, how components talk, what happens on failure.
  • High-level design arranges running components. Low-level design arranges the classes inside one component. Each constrains the other.
  • Functional requirements say what the system does. Non-functional requirements say how well, and they need numbers.
  • Qualities trade against each other. A decision is the option chosen, the options rejected, and the requirement that decided it.
  • The loop is requirements, estimates, interface and data, architecture, deep dives, stress. Expect to go around more than once.

Check yourself

A team says “the checkout page must be reliable”. Rewrite that as a requirement a design could be tested against.

One possible answer: “99.95% of checkout requests succeed, measured monthly at the load balancer, and no order that was confirmed to the customer is ever lost.” The first half is an availability target and the second is a durability target. Both have something you can measure.

Is “store the session in the server’s memory” a high-level or a low-level decision?

Both, which is the point. It looks like a code detail, and it decides whether a second server can be added, which is an architectural property. returns to this exact case.

You add an index so a search query runs faster. What did you trade away?

Write speed and storage. Every insert and update now also has to update the index, and the index occupies disk and memory.

Why estimate before drawing the architecture, when the estimate is only rough?

Because an order of magnitude is enough to choose between kinds of design. 20 writes per second and 200,000 writes per second lead to different architectures, and the difference between 20 and 30 leads to the same one.
