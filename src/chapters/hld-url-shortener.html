The problem

The problem. Design a URL shortener. A user submits a long URL and gets back a short link. Anyone who opens the short link is sent to the long URL. The owner can see how many times the link was clicked.

Each part is easy alone. What makes the whole hard is that the parts pull against each other. Codes must be as short as possible, but there must be enough of them for decades of links, and no two may ever be equal. Redirects must be fast, which argues for caching them everywhere, but every cached redirect is a click the analytics never sees and a deleted link that keeps working. And the system is read a hundred times for every write, so the read path must not share anything slow with the write path. The method of takes these in order.

Step 5: The design

The redirect servers and the API servers are separate fleets behind the same load balancer. They scale for different loads, a hundred to one, and a surge of creates cannot slow the redirects. The safety checks that scan new URLs for malware and phishing run after the create returns, and disable a link if they find something. A synchronous scan would put a third-party service on the create path.

Two choices in the flows are deliberate. The new link goes into the shared cache at creation, because most of a link’s clicks come in its first hours (step 6b). And the click is sent after the redirect has been answered, in a batch, so that analytics can be slow or down without a redirect noticing (step 6c).

Step 6a: Generating short keys

The short code is the part of a short link after the domain, such as aZ3kQ9x, that identifies the link. Seven characters from the 62 digits and letters give 627, about 3.5 trillion, codes (). There are three ways to choose one: draw it at random, hash the long URL, or count.

Random codes need no coordination, but they repeat sooner than intuition suggests. The birthday bound is the number of values drawn at random from N possibilities at which a repeat becomes as likely as not: about 1.18 times the square root of N. For 7 characters that is 2.2 million codes, 32 minutes of creates at this system’s rate.

So a repeat is certain within the first day, and every scheme needs the store to refuse a code that is taken: an insert that succeeds only if the key is absent, and a new draw when it fails. The cost of the retry depends on how full the space is. The simulation filled a small space with random codes and counted the attempts each insert needed.

At the 10% this system reaches after ten years, one insert in ten needs a second try. Random codes are a sound design here, as long as the space stays mostly empty.

Hashing the URL makes the same URL always give the same code, which deduplicates links. It does not avoid collisions: two different URLs whose hashes agree in the first 7 characters collide exactly as often as random draws do. Over 200 sets of 1,000 links in a space of 238,328 codes, the simulation found 2.03 equal pairs per set for hashed codes, 1.89 for random ones, and the formula predicts 2.10. Deduplication is also a product decision with costs: two owners would share one link’s counts, and one owner’s delete would break the other’s link.

Counting gives codes that never repeat, but a single counter incremented for every link is a shared step on every create, and a single point of failure. The fix is a counter range: a block of consecutive numbers that one server takes from the shared counter in one atomic step and then hands out alone.

The range size trades coordination against waste. The simulation ran 20 servers issuing 10 million codes at this system’s rate, with 40 restarts at random moments.

A counter written in base 62 has one flaw: neighbors are neighbors. Anyone holding aZ3kQ9x can try aZ3kQ9y and read other people’s links. The answer, promised in , is to scramble each counter value with a keyed shuffle of the whole space before encoding it. The chapter uses a Feistel network: the bits of a number are split into two halves, and in each of several rounds one half is mixed into the other through a function of a secret key. Each round can be undone, so the result is a permutation, and two counter values never give the same code. The test confirmed it on every one of the 14,776,336 values of a 4-character space. Counter values 0 to 4 become s1rruso, 12bjS6f, IrbSgvz, GWJnvs8 and F7YzKBq. With a million links issued, the 1,000 codes after a known one were all real links with a plain counter, and none with the scrambled one.

export class CodeServer {
  private readonly coordinator: RangeCoordinator;
  private readonly scrambler: Scrambler | null;
  private nextValue = 0;
  private end = 0; // exclusive: the server starts with an empty range

  constructor(coordinator: RangeCoordinator, scrambler: Scrambler | null = null) {
    this.coordinator = coordinator;
    this.scrambler = scrambler;
  }

  // The next counter value. Nothing shared is touched until the range runs out.
  nextNumber(): number {
    if (this.nextValue === this.end) {
      const range = this.coordinator.lease();
      this.nextValue = range.start;
      this.end = range.end;
    }
    return this.nextValue++;
  }

  nextCode(length = 7): string {
    const n = this.nextNumber();
    return encode(this.scrambler ? this.scrambler.permute(n) : n, length);
  }

  // A restart loses what was left of the range. Those values are never issued, which wastes them
  // but can never cause a duplicate.
  restart(): number {
    const lost = this.end - this.nextValue;
    this.nextValue = 0;
    this.end = 0;
    return lost;
  }
}

The mixing function here is a fast hash, not a cipher. It stops anyone counting through the links, but a patient analyst with many codes might work out the key. Links that must stay secret need long random codes instead. The design uses counter ranges of 1,000, scrambled, with insert-if-absent kept as a guard against a bug or a misconfigured range. Random codes with a retry would be an equally defensible answer.

Step 6b: Redirects and caching

The fastest redirect is one that never reaches the servers. Whether a browser reuses a redirect is decided by its status code and its Cache-Control header (). HTTP’s specification, RFC 9110, lets a cache store a 301 or 308 response with no explicit lifetime, and does not let it for a 302 or 307. The chapter measured what that means in practice: a local server answered a short link in each of seven ways, and a fresh browser clicked each one three times.

A bare 301 is the worst of both: the browser keeps it for as long as it likes, so the owner sees one click where there were three, and a deleted link keeps working in that browser. A 302 or a no-store brings every click back, which costs a request each time. The design answers 301 with Cache-Control: private, max-age=60. A browser reuses the redirect for a minute, shared caches such as CDNs never store it, and a deleted link stops within the minute that step 1 allowed. A repeat click from the same browser within that minute is not counted, which is acceptable for counts that are allowed to miss a little. The 301 also tells search engines that the short link stands for the long one.

Behind the browser, two server-side caches hold links. Their size follows from how clicks arrive. A link’s half-life is the time after its peak in which it receives half of all the clicks it will ever get. Bitly measured 2.8 hours for links shared on Twitter and 3.2 for Facebook in 2011. That is why the design writes a new link into the shared cache at creation, as the pastebin of did: the first clicks come within minutes. The older links follow a skewed popularity, which the simulation models with a Zipf distribution over a million links.

With steep skew, a cache of 1% of the links answers 58% of the clicks, and 20% answers 84%. With gentler skew the same sizes answer 23% and 61%. The gap to the best possible cache, which always holds the most popular links, is the price of not knowing the future. About 6% of clicks were the first click on their link in the run, so a cache filled only on a miss can never answer them. Two smaller rules complete the read path. Each redirect server keeps a small in-process cache for the hottest links, so one viral link does not land on one node of the shared cache. And an unknown code is remembered for 5 seconds, so that a scanner trying random codes reads the store once per code, not once per try ().

Step 6c: Counting clicks

A redirect must not wait for analytics, so the click is recorded after the reply. Each redirect server adds the click to a buffer in memory, and about once a second the buffer leaves as one batch for the click log. Aggregators read the log, count clicks per link per minute, and write the counts. The test checks the property that matters: a call to the analytics side that hangs never delays a redirect.

export class ClickBuffer {
  dropped = 0;
  private pending: Click[] = [];
  private readonly send: (batch: Click[]) => Promise;
  private readonly maxPending: number;

  constructor(send: (batch: Click[]) => Promise, maxPending = 100_000) {
    this.send = send;
    this.maxPending = maxPending;
  }

  add(click: Click): void {
    this.pending.push(click);
    if (this.pending.length > this.maxPending) {
      this.pending.shift();
      this.dropped++;
    }
  }

  // Called on a timer, about once a second.
  async flush(): Promise {
    const batch = this.pending;
    this.pending = [];
    if (batch.length === 0) return 0;
    try {
      await this.send(batch);
      return batch.length;
    } catch {
      this.pending = batch.concat(this.pending); // try again at the next flush
      return 0;
    }
  }

  get waiting(): number {
    return this.pending.length;
  }
}

Counting first is what makes the writes affordable. At 115,741 clicks a second over a million links with steep skew, the simulation found the most popular link clicked 8,046 times a second: one counter written that often is a hot key on one partition. Counting per minute in the aggregators turned the 115,741 writes a second into 11,047, ten times fewer, and the hottest counter is written once a minute. The buffer is bounded: when the log is down for long, the oldest clicks are dropped. Counts may then miss clicks, as step 1 allowed, and redirects carry on. If counts had to be exact, the aggregators would record the log offset with each count in one write, so that a restart neither loses nor repeats a batch (). Unique visitors would add a HyperLogLog sketch per link and day ().

At ten times the links, a billion a day, seven characters run out in 9.6 years: switch new links to eight characters, which last for centuries, and keep old codes working. Redirects reach 1.2 million a second, which means more redirect servers and a larger cache, but no new component. At a hundred times, the store holds 55 PB in three copies and the partitioning becomes the main operational work: rebalancing, repair and backups across thousands of nodes. The redirect logic, the API and the key scheme do not change.

In the real world

  • X’s t.co. Every link shared on X, including in direct messages, is rewritten to a t.co link. X says the service checks links against a list of potentially dangerous sites, warns before following a flagged one, and measures clicks as a signal for ranking (X Help Center, checked October 2026).
  • Google’s goo.gl. Google stopped creating goo.gl links after announcing the shutdown in 2018, and later said existing links would stop working after 25 August 2025. On 1 August 2025 it changed course: links that were still in use would keep working, and only those with no activity in late 2024 would be turned off. A short link is a promise that can outlive its product.
  • How long links are clicked. A 2011 Bitly study of 1,000 popular links measured a mean half-life of 2.8 hours on Twitter, 3.2 hours on Facebook and 7.4 hours on YouTube, as reported by Search Engine Land.
  • The rules for caching redirects. RFC 9110, the HTTP semantics standard of June 2022, makes 301 and 308 responses cacheable by default and 302 and 307 responses not, which is what the browser in step 6b did.

Key points

  • Reads outnumber writes a hundred to one, so redirects and creates run on separate fleets and share only the store.
  • Seven base-62 characters give 3.5 trillion codes, enough for decades at 100 million links a day.
  • Random codes repeat after about 2.2 million draws, so every scheme needs an insert that fails when the code is taken.
  • Hashing the URL deduplicates links but collides as often as random codes.
  • Counter ranges remove the shared step from each create, waste a little on restarts, and never duplicate. Scramble the counter so codes cannot be counted through.
  • A bare 301 is cached by browsers indefinitely; a 301 with private, max-age=60 bounds both lost clicks and stale deletes.
  • Write new links into the cache at creation, because most clicks come in a link’s first hours.
  • Record clicks after the redirect, in batches, and count per minute before writing.

Check yourself

With random 7-character codes and 100 million new links a day, how long until two links are as likely as not to have drawn the same code?

About 2.2 million codes, the birthday bound for 3.5 trillion possibilities, which is 32 minutes of creates. So the store must refuse a code that is taken from the first day.

Why does hashing the long URL not solve collisions?

Different URLs can have hashes that agree in the characters kept. Cut to 7 characters, the hash behaves like a random draw, and the simulation found as many equal pairs for hashed codes as for random ones. Hashing only makes the same URL give the same code.

A server holding the range 5,000 to 5,999 crashes after issuing 5,000 to 5,320. What happens to 5,321 to 5,999?

They are never issued. After the restart the server leases a fresh range from the coordinator, which has already moved past 5,999. The values are wasted, about 0.2% of all values with ranges of 1,000 in the simulation, but no code is ever given twice.

Why scramble the counter value before writing it in base 62?

A plain counter makes consecutive links consecutive codes, so anyone can find other people’s links by counting from their own. A keyed permutation keeps every code unique while placing neighbors far apart.

What does a 301 with no Cache-Control header do to the owner’s click counts?

The browser keeps the redirect and follows it without asking again, so repeat clicks from that browser never reach the shortener and are not counted. In the measurement, one of three clicks arrived.

Analytics is down for ten minutes. What do users and owners see?

Users see nothing: redirects are answered before the click is sent. Owners see counts stop rising, then catch up from the buffers, minus any clicks dropped once a buffer reached its bound.

Why write a new link into the cache when it is created?

Most of a link’s clicks come in its first hours, so its busiest minutes are its first. A cache filled only on a miss would send each new link’s first clicks to the store.
