Identity across a boundary

The photo app can now sign Ana in and remember her (). Four further demands arrive as soon as the product meets the rest of the world.

SituationWhat is neededAnswered by
A printing service wants to read Ana’s photosLimited access to her data, without her passwordOAuth 2.0
Ben would like to sign in with the account he already has elsewhereA trustworthy statement of who signed in, from another systemOpenID Connect
A company buys the photo app for its staffOne sign-in, controlled by the company, for every applicationSingle sign-on
A partner’s server, and your own services, call the APIAn identity for a programAPI keys, certificates, workload identity

All four rest on the same mechanism. Somebody both sides trust, an issuer, checks the caller once and hands over a token: a statement of who or what the holder is and what it may do, signed so that it cannot be altered, and short-lived so that a stolen copy soon stops working. The protocols in this chapter differ mainly in who the issuer is and who reads the token.

OAuth 2.0: access without the password

Ana wants a printing service, Printly, to make a book from her photos. The worst design is the one that was once common: Printly asks for her photo app password and signs in as her. Printly could then do anything Ana can, forever, and the only way to stop it would be to change the password, which also cuts off every other service she gave it to.

OAuth 2.0 is the standard protocol for letting one application act on a user’s resources in another, with the user’s consent and without the user’s password. It names four parties.

RoleIn this exampleWhat it does
Resource ownerAnaOwns the data and gives consent
ClientPrintlyWants access
Authorization serverThe photo app’s sign-in serviceAuthenticates Ana, asks her, and issues tokens
Resource serverThe photo app’s APIHolds the data and accepts tokens

What Printly receives is an access token limited by a scope: a named permission, such as photos:read, that the user approved and the API enforces. The recommended way to obtain it is the authorization code flow.

The flow uses two channels on purpose. The front channel is the user’s browser being redirected from one site to the other. It is the only way to involve the user, and it leaks: addresses end up in browser history, in logs and in referrer headers. So only a short-lived, single-use code travels that way. The back channel is a direct call from Printly’s server to the authorization server, and tokens travel only there.

One gap remains. On a phone, a malicious app can sometimes arrange to receive the redirect meant for the real app, and with it the code. PKCE, pronounced “pixy” and short for Proof Key for Code Exchange, closes it. The client invents a random secret at the start, sends only its hash with the first request, and must present the secret itself when it exchanges the code. An intercepted code is useless without it.

import { createHash, randomBytes } from "node:crypto";

export function createVerifier(): string {
  return randomBytes(32).toString("base64url"); // 43 characters, kept by the app
}

export function challengeFor(verifier: string): string {
  return createHash("sha256").update(verifier).digest("base64url"); // sent in the first request
}

// On the authorization server, when the code is exchanged:
export function verifierMatches(verifier: string, storedChallenge: string): boolean {
  return challengeFor(verifier) === storedChallenge;
}

PKCE began as a fix for mobile apps and is now expected of every client. The OAuth security best practice published as RFC 9700 in 2025 requires it for clients that cannot keep a secret, recommends it for the rest, and requires authorization servers to compare redirect addresses exactly, character for character. OAuth 2.1, which gathers these rules into one document, was still an Internet-Draft when this chapter was written.

What the API must check

Issuing a token is half the protocol. The other half is the resource server refusing everything the token does not cover. The function below is what the photo API runs on every request. It builds on the token verifier from .

import { verify, type Claims } from "./jwt";

const EXPECT = { iss: "https://id.photos.example", aud: "photos-api" };

// What the API does with every request that carries an access token.
export function requireScope(authorization: string | undefined, needed: string, key: Buffer, now?: number): Claims {
  const token = /^Bearer (.+)$/.exec(authorization ?? "")?.[1];
  if (!token) throw new Error("401: no token");
  const claims = verify(token, key, EXPECT, now); // signature, issuer, audience, expiry
  const granted = String(claims.scope ?? "").split(" ");
  if (!granted.includes(needed)) throw new Error(`403: token lacks ${needed}`);
  return claims; // claims.sub is the user. What that user may do is a separate check.
}

Three points about scopes are often misunderstood.

  • A scope limits the client, not the user. photos:read says Printly may read photos on Ana’s behalf. Which photos Ana herself may read is a separate question, answered by the checks in . A token never grants more than its user has.
  • Compare whole scope names. Tested against the code above, a token carrying photos:readonly was refused when photos:read was required. A check written as “starts with” would have let it through.
  • Ask for little. Users approve what they are shown. A client that asks for everything gets refused by careful users and becomes a larger loss when its tokens are stolen.

In production. Tokens held by third parties are part of your attack surface. Between 8 and 18 August 2025 an attacker used OAuth tokens stolen from Salesloft’s Drift integration to query the Salesforce data of hundreds of companies that had connected it, searching the results for cloud keys and passwords. No password or second factor was involved at any of those companies: the tokens were enough. Every Drift token was revoked on 20 August. Know which integrations hold tokens for your system, keep their scopes narrow, and be able to revoke all of one client’s tokens at once.

How long should a token live?

A short access token limits what a thief gets and how long a revoked user keeps access. A long one spares the authorization server work. The calculator shows the trade for a service with 100,000 clients connected at once, each making 20 requests a minute, and a 15-minute access token.

With 100 thousand clients and an access token that lives for 15 min, the issuer handles 111 refreshes a second, and each token serves about 300 API requests with no lookup. Checking a server-side session on every request would mean 33.3 thousand lookups a second. The price is that a token revoked at the issuer keeps working for up to 15 min. Between five minutes and an hour is the usual range.

The curve is steep at the left and nearly flat at the right. Shortening a token from an hour to fifteen minutes costs little. Shortening it from five minutes to one multiplies the issuer’s load by five and makes the issuer something every request soon depends on, which is the property tokens were chosen to avoid.

Two refinements exist for cases where a bearer token is not good enough. An API can ask the authorization server about each token instead of verifying it locally, called introspection, which restores instant revocation at the price of a call per request. And a token can be bound to a key held by the client, so that a stolen copy is useless without the key. Both are worth knowing by name and are rarely the first thing to reach for.

Where a web application keeps its tokens

A server can keep a secret. A page running in a browser cannot: anything the page’s own code can read, a script injected into the page can read too (). The IETF’s best practice for browser-based applications, published as RFC 10017 in August 2026, describes three architectures and ranks them by what such a script can get.

A backend for frontend is a server-side component belonging to one web application that holds the tokens, runs the OAuth flow as a client able to keep a secret, and calls APIs on the browser’s behalf. The browser holds only a session cookie with the attributes described in . RFC 10017 strongly recommends this pattern for business applications and anything handling personal data.

ClientRecommended arrangement
Web application with a backendBackend for frontend. Tokens never reach the browser
Single-page app with no backend of its ownAuthorization code with PKCE in the browser, tokens kept in memory, short lifetimes, refresh tokens that rotate. Accept that it is the weakest of the three
Mobile appAuthorization code with PKCE through the system browser, never an embedded web view, so the app cannot see the password. Tokens in the platform’s secure storage
Command-line tool or televisionDevice authorization

OpenID Connect: signing in with another account

OAuth answers “what may this application do?”. It was not designed to answer “who just signed in?”, and using it for that has caused real vulnerabilities. An access token says what its holder may do. It does not say that the person in front of this browser is the person it was issued for, and it is addressed to the API, not to the application.

OpenID Connect, or OIDC, is a thin layer on top of OAuth 2.0 that adds exactly that missing statement. It stands behind every “Sign in with Google” or “Sign in with Apple” button. The flow is the same authorization code flow, with the scope openid, and the token response contains one more item.

An ID token is a signed token, addressed to the client application, that says which user authenticated, with which provider, when and how.

{
  "iss": "https://accounts.example",      who vouches for this
  "sub": "110169484474386276334",         the user, as the provider knows them: stable and never reused
  "aud": "photos-web",                    the application this token is for
  "exp": 1800000600,  "iat": 1800000000,  valid for ten minutes
  "nonce": "n-0S6_WzA2Mj",                the random value this application sent with its request
  "auth_time": 1799999990,                when the user actually signed in
  "amr": ["hwk", "user"],                 how: a hardware-backed key, with the user present
  "email": "ben@example.net",  "email_verified": true
}
TokenAudienceSaysSend it to
ID tokenThe application that asked for the sign-inWho signed in, when, and by what methodNobody. Verify it, read it, start your own session
Access tokenAn APIWhat the holder may do thereThat API only
Refresh tokenThe authorization serverNothing readableThe authorization server only

Three details save trouble later.

  • Identify the user by issuer and subject. Store the pair of iss and sub. Do not key accounts on the email address: addresses change hands, and a provider may return one the user never verified.
  • Check the nonce. The application invents it, stores it with the browser’s session, and refuses an ID token that does not carry it back. That ties the token to the sign-in this browser started.
  • Use discovery. A provider publishes its endpoints and signing keys at a well-known address under its domain. Libraries read it and follow key changes automatically. Do not copy keys into configuration by hand.

In production. A token is only as trustworthy as the issuer’s signing key and the care taken in checking which key signed it. In 2023 an attacker obtained a signing key belonging to Microsoft’s consumer account system and used it to forge tokens for the email of about 25 organizations, government agencies among them. The forgeries worked because of a second fault: a validation error let a key meant only for consumer accounts be accepted for enterprise ones. Keep signing keys in hardware, rotate them, and make every verifier pin down exactly which issuer and which keys it accepts.

Single sign-on

A company with forty internal applications does not want forty passwords per employee, forty places to add a second factor, and forty accounts to remember to close when someone leaves.

Single sign-on, or SSO, is an arrangement in which applications hand authentication to one shared service and accept its signed statement about who the user is. That service is the identity provider. The applications that trust it are called relying parties or service providers.

What makes it single is the provider’s own session. The first application of the day causes a sign-in. Every later one gets its answer without the user doing anything.

Two protocols carry the statement. OpenID Connect is the choice for anything built now. SAML 2.0 is an older standard, from 2005, that carries signed XML documents through the browser, and it is still what many large organizations require. A product sold to enterprises generally has to support both. They do the same job.

QuestionWhat to know
How are accounts created and removed?A companion standard, SCIM, lets the identity provider create, update and deactivate accounts in each application. Without it, a departed employee’s account lingers until someone remembers
What happens at sign-out?The application’s own session ends easily. Ending the session in every other application at once is unreliable in practice, so keep application sessions short and let them renew silently from the provider
What if the provider is down?Nobody can sign in anywhere. Existing sessions keep working until they expire. It is a single point of failure that deserves the engineering of
What if the provider is breached?Everything behind it is exposed. Concentrating the risk is still the right trade, because one well-defended system is easier to protect than forty

For a product with business customers, single sign-on is also a tenancy feature. Each customer brings its own identity provider, and the application must work out which provider to send a user to, usually from the domain of the email address, and map the returned identity to the right tenant and to no other ().

API keys

An API key is a long random secret, issued to a customer or a program, that identifies and authenticates the caller on every request. API keys are simple, which is why they are everywhere, and long-lived, which is why they leak. One survey found about 29 million secrets in public commits on GitHub during 2025, and that most of the valid ones it had found in 2022 were still working years later.

import { createHash, randomBytes, timingSafeEqual } from "node:crypto";

type StoredKey = { id: string; hash: Buffer; scopes: string[]; lastUsed?: Date };

const sha256 = (text: string) => createHash("sha256").update(text).digest();

// Called once, when the customer creates a key. The full key is shown to them and never stored.
export function createApiKey(scopes: string[]): { key: string; stored: StoredKey } {
  const id = randomBytes(6).toString("hex"); // public: appears in logs and in the dashboard
  const secret = randomBytes(32).toString("base64url"); // 256 random bits
  const key = `photos_live_${id}_${secret}`;
  return { key, stored: { id, hash: sha256(key), scopes } };
}

// Called on every request. `find` looks a key up by its public id.
export function checkApiKey(presented: string, find: (id: string) => StoredKey | undefined): StoredKey | null {
  const match = /^photos_live_([0-9a-f]{12})_[A-Za-z0-9_-]{43}$/.exec(presented);
  if (!match) return null;
  const stored = find(match[1]);
  if (!stored) return null;
  // A fast hash is enough: the key is random, so there is nothing to guess.
  return timingSafeEqual(sha256(presented), stored.hash) ? stored : null;
}

The code shows three of the habits that limit the damage, and a fourth belongs around it.

  • Show the key once and store only its hash. A key is long and random, so a single fast hash is enough. The slow hash of is for secrets that people choose.
  • Give keys a recognizable prefix. Support staff can tell what a key is, and automated scanners can find leaked ones in public code and report them.
  • Scope every key, so that a key for uploads cannot delete, and a leaked key can be traced to one integration.
  • Make rotation painless: allow two keys to be valid at once, show when each was last used, and let keys expire.

No stored secret at all

The better direction is to have no long-lived secret. Workload identity means that a running program is given its identity by the platform that started it, as a short-lived credential that is replaced automatically, instead of holding a secret that somebody had to copy into it. A cloud platform does this for virtual machines and functions. Kubernetes does it for pods. A build pipeline can present a signed statement of which repository and branch it is running for, and a cloud account can be configured to trust that statement and nothing else. Nothing is stored in code or configuration, so there is nothing to leak. returns to this under secrets management.

The user’s identity between services

When a user’s request passes through several services, which identity do the inner calls carry? Both.

The gateway is the natural place to reject requests with no valid token at all (), and it is not a reason for the services behind it to stop checking. A service that accepts “this is on behalf of user 871” from any caller on the internal network, without proof, has no authentication left once one service is compromised. That is the practical meaning of zero trust ().

One refinement matters at scale. If the gateway forwards the user’s original token everywhere, every internal service holds a token that the public API would accept. Many systems instead have the gateway, or each service, exchange the incoming token for a new one addressed to the next service only, with a narrower scope and a short lifetime. A token captured deep inside the system then opens one door, briefly.

In an interview. Name the caller before the mechanism. “Third parties get scoped OAuth tokens, our own web app uses a session to a backend that holds the tokens, and services authenticate each other with mutual TLS and pass the user’s token along” covers most designs in one sentence. Expect a follow-up on revocation: say how long an access token lives and what deleting a refresh token does.

Key points

  • OAuth 2.0 gives an application limited, revocable access to a user’s data without the user’s password. Use the authorization code flow with PKCE.
  • Only a single-use code crosses the browser. Tokens travel on a direct call between servers.
  • A scope limits what the client may do. The API must check it on every request, and what the user may do is a separate check.
  • Token lifetime trades load on the issuer against how long a revoked token works. Minutes, not days.
  • In a web application, keep tokens on a backend and give the browser a session cookie.
  • OpenID Connect adds an ID token: a signed statement, for the application, of who signed in. Identify users by issuer and subject.
  • Single sign-on moves authentication into one identity provider, which makes that provider both the best-defended and the most critical system you depend on.
  • Programs authenticate with keys, certificates or identities issued by the platform. Prefer credentials that expire by themselves to secrets that are stored.
  • Inside a system, every hop verifies two things for itself: which service is calling and which user the request is for.

Check yourself

Why does the authorization code flow return a code through the browser and not the access token itself?

The browser redirect is a leaky channel: addresses are recorded in history, logs and referrer headers, and on a phone another app may receive the redirect. A code is single-use, expires within minutes and, with PKCE, is useless without the verifier that only the real client holds. The token is then delivered on a direct call between the client and the authorization server, where none of those leaks apply.

A mobile app starts the flow with a code challenge. An attacker’s app on the same phone intercepts the redirect and obtains the code. What happens when it tries to use it?

The token request must include the code verifier whose hash equals the challenge sent at the start. The attacker’s app saw the code but never the verifier, which stayed in the real app’s memory, and it cannot be derived from the challenge. The authorization server refuses the exchange.

Printly holds a token with the scope photos:read for Ana. It requests a photo that belongs to Ben and is not shared with Ana. Which check refuses it?

Not the scope check, which passes: the token does allow reading photos. The refusal comes from the API’s authorization check for the user in the token, Ana, against the photo requested. A scope limits what the client may do on the user’s behalf and can never grant more than the user has.

A service has 100,000 connected clients, each making 20 requests a minute, and 15-minute access tokens. How many refreshes a second does the issuer handle, and how does that compare with checking a session on every request?

Each client refreshes once every 900 seconds, so the issuer sees about 111 refreshes a second. The API handles about 33,000 requests a second, so a session store would be consulted 300 times as often. The cost of the saving is that a revoked token keeps working for up to fifteen minutes.

An application lets users sign in with an external provider and links accounts by the email address in the ID token. Describe a way this goes wrong.

If the provider returns an email address the user has not verified, an attacker can register there with the victim’s address and be signed in to the victim’s account. Addresses are also reassigned over time. The stable identifier is the pair of issuer and subject, and an email should be used for linking only when the provider states that it is verified, and preferably after the user confirms.

In a backend-for-frontend design, a script is injected into the page. What can it do, and what can it not do?

It can make requests through the backend while the user has the page open, because the browser attaches the session cookie to them, so it can read or change what the user could. It cannot read the cookie, which is marked HttpOnly, and there are no tokens in the browser to copy. The attack ends when the page closes, and nothing reusable leaves with the attacker.

Why can an API key be stored as a fast hash when a password cannot?

The slow hash exists because people choose from a small set of likely passwords, which makes guessing feasible. An API key is 256 bits from a random generator. No number of guesses per second covers a meaningful fraction of that space, so a single fast hash already prevents recovery, and it keeps the check on every request cheap.

The gateway validates every user token. Why should the services behind it validate the token again?

Because the internal network is not a guarantee of who is calling. If any internal service, job or machine is compromised, it can call other services directly and claim to act for any user. A service that verifies the token itself, and verifies which service is on the other end of the connection, cannot be fooled that way.
