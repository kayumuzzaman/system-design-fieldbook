A model as a component

The photo app adds a help assistant. Users ask questions in their own words (“how do I get back a photo I deleted?”) and get an answer drawn from the app’s help articles. covers how the right articles are found, and lets the assistant take actions. This chapter is about the call to the model itself and the system around it.

A model reads and writes text as tokens. A token is the unit a language model reads and writes: a common word, a piece of a longer word, or a punctuation mark. In English a token is about four characters, or three quarters of a word, on average. The chapter’s rough tokenizer agrees: a 242-character help paragraph is 60 tokens, 4.0 characters each. Prices, limits and speeds are all stated in tokens.

The context window is the most tokens a model can take in one call, the prompt and the answer together. A model keeps nothing between calls. To hold a conversation, the application sends the whole conversation every time, so each turn costs more than the one before it.

A model call differs from the calls the rest of this book makes in four ways.

DurationMillisecondsSeconds, growing with the length of the answer

So the application does more than forward a question. It assembles the prompt, sends it through a gateway that enforces budgets and picks a provider, and streams the answer back.

How a model produces text

A model produces its answer one token at a time, and each new token depends on all the tokens before it. A request has two phases with different costs.

Prefill is the first phase: the model reads the whole prompt in one pass, all its tokens processed in parallel. Decode is the second: the model produces the answer one token per pass, each pass taking the previous token as new input. A prompt of 1,500 tokens costs one pass. An answer of 200 tokens costs 200 passes.

Each decode pass must read every weight of the model from the GPU’s memory. A model with 8 billion parameters stored in 2 bytes each is 16 GB. The H100 GPU’s datasheet gives a memory bandwidth of 3.35 TB per second, so a pass takes at least 16 / 3,350 of a second, about 4.8 ms, however fast the arithmetic is. One sequence alone can therefore get at most about 200 tokens a second from this GPU. This estimate explains most of what follows: decode is limited by reading memory, and the same read can serve many sequences at once.

The past is not recomputed at every pass. The KV cache holds the intermediate results (the attention keys and values) of every token so far, in GPU memory, for each sequence being served. Its size per token is two (keys and values) × layers × key-value heads × numbers per head × bytes per number. For Llama 3 8B, with 32 layers and 8 key-value heads of 128 numbers in 16 bits, that is 131,072 bytes, about 131 KB per token. For Llama 3 70B, with 80 layers, it is about 328 KB. A 1,500-token conversation on the smaller model holds 197 MB of KV cache, and a hundred such conversations need about 20 GB beside the 16 GB of weights. Memory for the KV cache is what limits how many sequences a server can work on together.

Two latency numbers describe what a user sees. The time to first token is the time from sending the request to receiving the first token of the answer: waiting in a queue, plus prefill. The time per output token is the gap between later tokens, one decode pass as that user experiences it. The time to the last token follows from them.

time to last token = time to first token + (answer tokens − 1) × time per output token
on an idle simulated server: 51.1 ms + 199 × 6.1 ms = 1,265 ms

The simulation behind this figure and the rest of the chapter uses a stated cost model, not measurements of real hardware. One pass costs 6 ms (the 4.8 ms of reading weights, plus overhead), 0.1 ms more for each sequence in the batch, and 0.03 ms for each prompt token that joins. These are shaped like a small model on one GPU of the kind above. The shape of every result holds for other numbers; the exact values do not.

Three consequences matter for design. The length of the answer, not the prompt, sets most of the waiting time: in the example, 1,500 prompt tokens took less time than nine answer tokens. Capping the answer with the request’s maximum output tokens is a latency control as well as a cost control. And streaming the answer as it is produced turns a 1.3 second wait into 51 ms before the reader sees something.

Serving many users: batching

A pass that serves one sequence reads 16 GB to produce one token. A pass that serves 64 sequences reads the same 16 GB and produces 64 tokens. This is batching, and on a model server it decides capacity. The simulation fills a server with a backlog of 1,000 requests and varies the largest batch it may run:

1159163.9

A larger batch gives the server more tokens a second in total and each user fewer. Somewhere between, the answer still streams faster than people read, and the server earns its cost. Choosing that point is choosing a time per output token, and it is limited from above by memory for the KV cache.

How requests join a batch matters as much as its size. Static batching takes a group of waiting requests, runs them together until the longest is finished, and only then takes the next group. Continuous batching decides at every pass: a sequence that has finished leaves, and a waiting request takes its place in the next pass. It was introduced as iteration-level scheduling in the Orca paper (OSDI 2022), which reported 36.9 times the throughput of NVIDIA’s FasterTransformer at the same latency, on a 175-billion-parameter model.

The chapter’s simulated server (server.ts) runs either policy, one loop iteration per pass. With eight requests and four slots, static batching needs 11 passes, 15 slot-passes of them padding; continuous batching needs 9. Under real load the difference grows, because with static batching a request that arrives soon after a batch starts waits for the batch’s longest answer before it is even read.

At 4 requests a second, the median time to first token is 6,729 ms with static batching and 60 ms with continuous. Static batching saturates near 1,100 tokens a second, at about 5 requests a second; continuous batching keeps up until about 11. Past either point the queue grows without limit, the behavior described in , and the load test of is how you find that point for a real server.

Modern inference servers add two refinements. PagedAttention, from the vLLM project, stores each sequence’s KV cache in small fixed-size blocks, as an operating system stores memory in pages, instead of one reserved region per sequence. Its authors reported in June 2023 that earlier systems wasted 60% to 80% of KV cache memory to fragmentation and over-reservation, and vLLM under 4%, which lets more sequences share a batch. And prefill and decode get in each other’s way: a long prompt joining the batch delays the next token of everyone already in it (the simulation includes this cost). Servers split long prompts into chunks that join over several passes, or run prefill and decode on separate GPUs. DistServe (OSDI 2024), which does the latter, reported serving up to 7.4 times more requests within the same latency targets.

An API or your own GPUsA hosted model API charges per token and batches your requests with other customers’ requests. A GPU you run yourself costs the same per hour whether its batches are full or empty. In the simulation, a full batch of 64 produces 2,601 tokens a second and a batch of one 159: whatever the hourly price, the cost per token differs sixteenfold. Running your own model pays when traffic is steady enough to keep batches full, or when data must not leave your network.

Streaming the answer

An answer of 400 tokens at 50 tokens a second takes eight seconds. Shown all at once, that is eight seconds of nothing. Shown as it is produced, reading starts within a second. explained why server-sent events suit this: one direction, text, over ordinary HTTP. Model APIs use the same format. Anthropic’s Messages API, for example, sends a message_start event, then a content_block_delta for each piece of text, then message_delta with the token counts and message_stop, with occasional ping events to keep the connection alive.

The application relays the stream to the browser, and three details break it in practice.

  • Buffering. A proxy that collects a response before forwarding it turns a stream back into one late reply. nginx buffers proxied responses by default; a response header X-Accel-Buffering: no turns that off for one response. Every hop needs checking.
  • Timeouts. A timeout on the whole response cuts off long answers. Use an idle timeout between chunks, as nginx’s proxy_read_timeout is, and pings to keep a slow stream alive.
  • Errors after success. The status 200 was sent with the first byte. A failure halfway through, such as the provider becoming overloaded, arrives as an error event inside the stream, and the browser must handle it as a failure.

Canceling needs care in the other direction. When the user closes the tab, the application should stop the model call, or the model keeps producing, and billing, tokens nobody will read. Nothing passes the browser’s departure on by itself: the relay must tie the model call to the browser’s connection.

// Relays a model's tokens to the browser as they are produced. When the browser goes away, the abort is
// passed on to the model call, so that the model stops producing (and billing) tokens nobody will read.
export async function relay(model: StubModel, prompt: string, browser: Connection, passOnCancel: boolean): Promise {
  const upstream = new AbortController();
  if (passOnCancel) browser.onClose(() => upstream.abort());
  const tokens = model.generate(prompt, { maxTokens: 1000, signal: upstream.signal });
  let id = 0;
  for (;;) {
    const next = await tokens.next();
    if (next.done) {
      browser.write(sseEvent(++id, "done", { usage: next.value }));
      return next.value;
    }
    browser.write(sseEvent(++id, "token", { text: next.value }));
  }
}

In the test, the browser leaves after 20 tokens of an answer that would have been 104 tokens long. Without passing on the cancel, the model produces all 104. With it, it produces 20.

Not every closed connection means the user has gone, though. A phone that changes from Wi-Fi to a mobile network drops the connection and reconnects a second later, and the answer should continue where it was. The fix is to make the generation belong to the response rather than to the connection: the server numbers each event, keeps the events of a running answer for a few minutes (in a shared store such as Redis, when there are several servers), and on a reconnection with a Last-Event-ID header replays what was missed. Only an explicit Stop cancels the model call.

In the test, the browser drops after event 30, reconnects, and receives events 31 to 105: none missing, none repeated, and the model ran once. A Stop pressed after 10 tokens ends the model call with 10 tokens produced and billed.

Three kinds of cache

Model calls are slow and priced per token, so caching pays. There are three kinds, at three places, and they cache different things.

Whole responses

The simplest stores the answer to a request and returns it when the same request comes again. The key must include everything that affects the answer: the model and its version, the settings, the instructions and the whole conversation. Leaving one out returns an answer made for a different request.

// Differences that do not change the meaning of a question: case, and spaces at the ends or in a row.
export function normalize(text: string): string {
  return text.trim().replace(/\s+/g, " ").toLowerCase();
}

// The key is a hash of everything that affects the answer: the model, its settings and the whole prompt.
// Leaving any of these out would return an answer produced for a different request.
export function cacheKey(request: ModelRequest, normalizeText = true): string {
  const text = (t: string) => (normalizeText ? normalize(t) : t);
  const canonical = JSON.stringify([request.model, request.temperature, request.maxTokens, text(request.system),
    request.messages.map((m) => [m.role, text(m.content)])]);
  return createHash("sha256").update(canonical).digest("hex");
}

Cache only requests at temperature 0, the setting that makes the model pick its most likely token each time; above it, the caller asked for variety. Cache only answers that are the same for every user: an answer that mentions the user’s storage plan must not be served to someone else. Give entries an expiry, because the help articles behind an answer change. In the test, 20,000 questions drawn by popularity from 240 kinds, typed with stray capitals and spaces, went through a cache of 100 entries. Exact text gave a hit ratio of 50.5%; normalizing case and spaces first gave 79.4%. shows what such a ratio is worth.

Answers to similar questions

Users rarely repeat each other word for word. A semantic cache returns the stored answer of an earlier question whose embedding () is similar enough to the new one’s. Its single setting, the similarity threshold, decides how often it answers a question that was not asked. The test caches one phrasing of each of 16 help questions and asks the other 48 phrasings, with a simple stand-in for an embedding model:

At 0.6, “Delete an album but keep the photos” is answered with the instructions for deleting a photo, close to the opposite of what was asked. A learned embedding recognizes more paraphrases than the stand-in, but the trade has the same shape: every step down in threshold buys hits with wrong answers, and a wrong answer delivered confidently costs more than a slow one. Use a semantic cache for questions with one shared answer, set the threshold from a labeled set of question pairs, and measure the wrong answers, not only the hits.

The beginning of the prompt

The third cache works inside the model server. Prefill of an identical beginning gives identical keys and values, so a server can keep the KV cache of prompts it has seen and skip prefill for any new prompt that starts the same way. Prefix caching is reusing the stored keys and values of a prompt’s beginning for a later prompt that begins with the same tokens. Servers name blocks of tokens by a hash of everything before them, so a block matches only if the whole prompt up to it matches:

// Processes one prompt. Returns how many of its tokens were found in the cache and did not need prefill.
  prefill(tokens: readonly string[]): number {
    let name = 0, matched = 0, stillMatching = true;
    const whole = Math.floor(tokens.length / this.blockTokens);
    for (let b = 0; b < whole; b += 1) {
      name = hash32(name + "|" + tokens.slice(b * this.blockTokens, (b + 1) * this.blockTokens).join(""));
      if (stillMatching && this.blocks.has(name)) matched += this.blockTokens;
      else stillMatching = false;
      this.blocks.delete(name); // store or refresh it as the most recently used
      this.blocks.set(name, true);
      if (this.blocks.size > this.capacity) this.blocks.delete(this.blocks.keys().next().value as number);
    }
    this.reused += matched;
    this.computed += tokens.length - matched;
    return matched;
  }

That rule makes the order of the prompt a performance decision. The test sends the same 200 conversations of four turns with three layouts of the same content.

Model providers expose this as prompt caching, and price it. As of October 2026, Anthropic’s documentation describes caching of the prompt up to a marked point, requiring an exact match, with a five-minute lifetime that each use renews and an optional one-hour lifetime. Writing to the cache costs 1.25 times the normal input price (twice for one hour), and reading from it a tenth or less. OpenAI caches automatically for prompts of at least 1,024 tokens, bills cached tokens at a tenth of the normal price for its current models, and gives the same advice: stable instructions and shared material first, anything that varies (a timestamp, the user’s details) last.

Cost and latency budgets

The cost of a call is its tokens times their prices, and the two kinds of token are priced differently. As of October 2026, Anthropic’s price list, older models included, runs from $0.10 to $15 per million input tokens and from $0.50 to $75 per million output tokens, depending on the model, with output priced at five times input for every model listed. Prices change often; the arithmetic does not.

cost of a call = new input tokens × input price + cached input tokens × cached price + output tokens × output price
3,000-token prompt, 80% of it cached, 400-token answer, at $2, $0.20 and $10 per million:
600 × $2 + 2,400 × $0.20 + 400 × $10 = $0.0012 + $0.00048 + $0.004 ≈ $0.0057

Each call costs $0.0057, so 50 thousand calls a day cost about $8,520 a month. The answer’s 400 tokens are 70.4% of the cost, and the prompt cache saves 43.2% compared with no cache. The reader waits 500 ms for the first word and 8.48 s for the last, which is why the answer is streamed.

Two things stand out at the default numbers. The answer is 400 tokens out of 3,400 and 70% of the cost, so a cap on the answer’s length, and instructions that ask for brevity, are the strongest cost controls. And caching 80% of the prompt cuts the cost of each call from $0.010 to $0.0057. For work nobody waits for (summarizing yesterday’s uploads, labeling photos), batch interfaces cost half: both Anthropic and OpenAI offer asynchronous batch processing at a 50% discount, within a 24-hour processing window (Anthropic says most of its batches finish within an hour).

Costs need limits for each user and each tenant, for the reasons of : one script in a loop can spend a month’s budget in an afternoon. The tool is the token bucket, counted in model tokens instead of requests. One problem is new. The size of a call is not known until it ends, because the answer’s length is not. Charging after the call lets a burst of calls that start together all pass. So a call reserves its largest possible size (the prompt plus its maximum output tokens) and returns the unused part when it ends.

// Before the call: input tokens plus the largest answer allowed (max_tokens).
  reserve(user: string, tokens: number, now: number): { ok: true } | { ok: false; retryAfterMs: number } {
    const b = this.bucket(user, now);
    if (b.tokens >= tokens) {
      b.tokens -= tokens;
      return { ok: true };
    }
    return { ok: false, retryAfterMs: Math.ceil((tokens - b.tokens) / this.refillPerMs) };
  }
  // After the call: give back what was reserved and not used. (Charging only here, with no reservation,
  // lets a burst of calls that start together all pass, and the bill arrives after the limit is long gone.)
  settle(user: string, reserved: number, used: number, now: number): void {
    const b = this.bucket(user, now);
    b.tokens = Math.min(this.capacity, b.tokens + reserved - used);
  }

In the test, ten calls of 1,500 prompt tokens and up to 1,000 output tokens start at once against a budget of 10,000 tokens. Charging after, all ten pass and use 19,730 tokens, nearly twice the budget. Reserving first, four pass and use 8,130, and the refunds let later calls through.

Latency needs a budget too, in the terms of : a target for the time to first token at the 95th or 99th percentile, and one for the speed of the stream. The levers are the ones above: a smaller model for easy questions, a shorter prompt (less prefill), a cap on the answer, a prefix cache, and streaming. Retrieval and tool calls before the model call add to the time to first token and belong in the same budget.

The gateway: limits, routing and fallback

described a gateway that handles concerns every API shares. An AI gateway is an API gateway in front of model providers, applying the same ideas with tokens as the unit. As of October 2026, Cloudflare’s AI Gateway, one example, lists caching, rate limiting, routing rules, fallback to another model when one is unavailable, logging, cost tracking and content filtering.

Fallback is the circuit breaker of with a second destination. It applies only to failures another provider might not share: a rate limit (429), the provider’s own errors (500 and above, including the 529 some use for “overloaded”). A malformed request fails everywhere and is not worth sending twice.

export class Gateway {
  private readonly providers: readonly Provider[];
  private readonly breakers = new Map();
  constructor(providers: readonly Provider[], threshold = 3, coolDownMs = 5_000) {
    this.providers = providers;
    for (const p of providers) this.breakers.set(p.name, new Breaker(threshold, coolDownMs));
  }
  complete(prompt: string, now: number): { reply: Reply; servedBy?: string; tried: string[] } {
    const tried: string[] = [];
    let last: Reply = { ok: false, status: 503 };
    for (const p of this.providers) {
      const breaker = this.breakers.get(p.name) as Breaker;
      if (!breaker.allows(now)) continue;          // known to be failing: do not wait for it to fail again
      tried.push(p.name);
      last = p.call(prompt, now);
      breaker.record(last.ok || !worthFallingBack(last.status), now);
      if (last.ok) return { reply: last, servedBy: p.name, tried };
      if (!worthFallingBack(last.status)) break;
    }
    return { reply: last, tried };
  }
}

In the test, 600 calls arrive one every 100 ms while provider A is overloaded from 10 to 40 seconds. Without a fallback, 302 calls fail (two more than the outage, while the breaker waits out its cool-down). With provider B behind A, none fail. In both, the breaker keeps A’s share of the outage to 8 calls of 300: three failures open it, and then one test call every five seconds.

Two cautions. A retried model call repeats its whole cost and its whole wait, so a gateway that retries at every layer multiplies both (). And a fallback model is a different model: it may follow instructions differently, so it needs the same evaluation as the primary (). Record the model that served each call, so that a change in quality can be traced to a change in routing.

In an interview. For “design a chat assistant”, say where the time goes before drawing boxes: “the first token comes after queueing and prefill, the rest at the decode speed, so we stream over SSE and cap the answer length”. Then name the controls in the gateway: per-user token budgets with reservation, response and prefix caching with stable content first, fallback across providers behind a breaker, and logs of tokens and cost per call. If the model is self-hosted, say continuous batching and that KV cache memory bounds the batch.

Key points

  • Everything about a model call is counted in tokens: its price, its limits, its speed. A token is about four characters of English.
  • Prefill reads the prompt in one pass; decode writes the answer one pass per token. The answer’s length sets most of the waiting time and, at five times the price, much of the cost.
  • Each decode pass reads the whole model from memory, so batching many sequences multiplies a server’s output, at the price of a slower stream for each user. KV cache memory limits the batch.
  • Continuous batching admits requests at every pass instead of waiting for a batch to finish. In the simulation it served more than twice the load of static batching, with a first token in tens of milliseconds instead of seconds.
  • Stream with server-sent events, without buffering, with idle timeouts. Pass a user’s Stop on to the model, but let a dropped connection resume.
  • Cache whole responses only for identical, shared, temperature-0 requests; treat semantic caching’s threshold as a dial between hits and wrong answers; put stable content first so prefix caching works.
  • Budget tokens per user by reserving the maximum before a call and settling after it. Route, fall back and log in a gateway.

Check yourself

A prompt of 2,000 tokens gets an answer of 300 tokens. Which part takes longer to process, and why?

Usually the answer. The prompt is read in one prefill pass, with all its tokens processed in parallel. The answer is produced one token per decode pass, each pass reading the whole model from memory. 300 passes take far longer than one, even a large one: on the chapter’s simulated server, prefill of 2,000 tokens takes about 66 ms and 300 decode steps about 1.8 s.

Why does batching raise a model server’s throughput so much, and what does it cost each user?

Decode is limited by reading the model’s weights from memory, and one read can serve every sequence in the batch. So 64 sequences get 64 tokens for little more than the time of one. Each pass takes a little longer as the batch grows, so each user’s tokens arrive more slowly: in the simulation, 164 tokens a second alone and 43 in a batch of 64.

What limits how large a batch can be, apart from the speed each user needs?

Memory for the KV cache. Every sequence in the batch keeps the keys and values of all its tokens in GPU memory, about 131 KB per token for an 8-billion-parameter Llama 3 model in 16 bits. Long conversations fill memory quickly, which is why techniques such as PagedAttention, which waste less of it, let a server batch more sequences.

With static batching, a request arrives a moment after a batch of 64 has started. What decides when its first token arrives?

The longest answer in the running batch. The new request is not read until the whole batch is done, so it waits for that answer to finish, then for its own prefill. Continuous batching would admit it at the next pass after any sequence finishes.

A user closes the tab while an answer is streaming. What should happen, and what if the connection dropped because the phone changed networks?

If the user meant to leave or pressed Stop, the application should abort the model call so that it stops producing and billing tokens. A dropped connection is different: the browser will reconnect with the id of the last event it received. Tie the generation to the response, keep its numbered events briefly, and replay the missed ones. Cancel only on an explicit stop, or when no one has reconnected after a grace period.

Your system prompt starts with “Today is 14 October 2026, 14:03:07.” and is 2,000 tokens long. Why is the provider’s prompt cache not helping, and what is the fix?

A cached block matches only if every token before it matches, and the time changes every second, so no two prompts share even their first block. Move the date to the end of the prompt, after the stable instructions, or round it to the day. In the chapter’s simulation, putting the time first took prefix reuse from 90.1% to 0%.

Why must a per-user token budget reserve tokens before a call instead of charging them after?

The answer’s length is unknown until it ends. If the budget is charged only afterward, a burst of calls that start together all see a full budget and all pass. Reserving the largest possible size (prompt plus maximum output tokens) before the call, and returning what was unused after, keeps the total within the budget. In the test, charging after let ten calls use 19,730 tokens of a 10,000-token budget.
