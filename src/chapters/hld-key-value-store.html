The problem

The problem. Design a distributed key-value store. Clients put and get values by key. It must hold far more data than one machine, keep working when machines fail, and accept writes even during a network partition.

The interface is two operations, and every hard part is underneath them. Keys must be spread over machines so that adding one moves little data. Each key needs copies on several machines, and those copies will disagree whenever a write misses one of them. The system must decide, for every read, how many copies to ask, and must repair the copies that fell behind without comparing everything with everything. The mechanisms are in , and ; this chapter puts them together and measures them.

The availability line is the one that makes this a Dynamo-style store. A store that may refuse writes during a partition can use a leader for each key range and consensus, as describes, and many do. Asking for writes during a partition rules that out and brings conflicts in.

The 4 TB a node and the 1 GB/s a new node can absorb are assumptions; 10 bits a key gives a Bloom filter about a 1% false-positive rate (). The numbers say three things. The store is sized by disk, not by operations: 31,000 a second is comfortable for one machine with SSDs. Every node needs gigabytes of memory for filters alone. And the time to rebuild a failed node depends on how many other nodes hold copies of its data, which is decided by how keys are placed. The calculator places them.

→ 204 No Content

  • Context. A read returns an opaque context, the merged version vectors of what it saw, and a write must send it back. That is how the store knows which earlier versions a write replaces and which it is concurrent with (step 6d).
  • Several values. A read can return more than one value when writes were concurrent. The client merges them and writes the result with the context, which replaces them all.
  • Per-request quorums. r and w choose how many copies to wait for. A request that cannot reach enough copies fails with 503, and a write that failed may still have been stored on the copies it reached (step 6b).

A delete cannot remove the key, because a copy that missed the delete would later hand the old value back during repair. It writes a tombstone instead (), which must be kept longer than the longest time a copy can go unrepaired.

Step 5: The design

A key’s preference list is the list of nodes that should hold it: the first three distinct nodes clockwise from its position on the ring, followed by the nodes after them, which stand in when one of the three is down. Any node can coordinate a request, usually one the client library already knows holds the key. The coordinator sends the request to the key’s replicas and answers once enough have replied. A client library that knows the ring sends each request straight to one of the key’s replicas and saves a network hop; any other node would forward it.

Inside a replica, a write is appended to the commit log, flushed to disk, and inserted into the memtable before the replica confirms it. A read looks in the memtable and then in the sorted files from newest to oldest, and each file’s Bloom filter answers “certainly not here” for most of them without a disk read. The node keeps the newest version it finds, or all of them if they are siblings.

More tokens make the ring more even and spread a rebuild over more nodes, so that it is limited by what the new node can absorb rather than by what a few neighbors can send; the calculator above turns that into hours. A node joining took about 1% of the data in every case, as consistent hashing promises. The last column is the cost. With one token, two nodes fail “together” for some key only if they are neighbors on the ring: 4% of pairs. With 256 tokens every pair of nodes shares some key range, so any two nodes failing at once leave some keys with one copy and no quorum of two. Cassandra reduced its default from 256 tokens to 16 in version 4.0 for this reason and for faster repairs, and added an allocator that places the 16 tokens deliberately rather than by hash, which removes most of the unevenness shown above. Dynamo’s paper reached a similar end by another road: fixed, equal-sized partitions handed out to nodes.

Adding capacity follows from the same numbers. A node joining the default ring of the calculator takes 3.95 TB, about one 76th of what is stored, from the nodes whose ranges its 16 tokens split. At 1 GB/s that is about 66 minutes of streaming, during which those nodes serve their normal traffic as well; operators add nodes one at a time and throttle the streams.

Step 6b: Quorums when replicas are slow or down

The overlap rule of says that W + R greater than N rules out stale reads. The simulation tests it with a key written every 10 ms and read 1,000 times a second, over a network where each message takes a fraction of a millisecond and 1% are delayed by 20 ms, as by a pause on the receiving node. A read is stale if it returns a version older than the newest write already confirmed when the read began.

The overlap rule held: every configuration with W + R greater than 3 returned no stale reads. The latency columns show the other reason for asking all three replicas and waiting for two. Waiting for all three meets the slowest one on every request, and 1% of requests then take 21 ms. Waiting for two of three lets the fastest two answer and hides the slow one, which keeps the 99th percentile at 1.4 ms. With one replica down there is nothing left to hide behind: W = 2 must wait for both survivors, and the slow message reaches the 99th percentile. A failed node costs latency before it costs availability. The store’s default is Dynamo’s common setting, N = 3, W = 2, R = 2.

A strict quorum stops working when two of a key’s three replicas are unreachable. A sloppy quorum sends the write to the next healthy nodes on the preference list instead, with a hint naming the intended owner (). The simulation cut two of three replicas off for 30 seconds, with 1,000 keys written 200 times a second and read 1,000 times a second, a failure detector that noticed after 2 seconds, and hints delivered 10 seconds after the replicas returned.

The strict quorum accepted no writes and answered no reads during the cut. The sloppy quorum accepted all of them once the detector had noticed, and paid twice. During the cut, a read answered by the two stand-ins found nothing for keys not written since the cut began: 5.0% of reads were stale, most in the first seconds. After the healing, reads went back to the home replicas, two of which had missed 30 seconds of writes, and 14.9% of reads were stale until the hints arrived; with read repair, 2.8%. A sloppy quorum keeps the store writable by giving up the overlap guarantee for a while. One more measured effect: a write reported to the client as failed was not undone on the replicas it reached, and with the strict quorum 3,337 later reads returned such a write. A failed write in this design means “not confirmed”, never “not stored”, which is why clients retry with the same value.

The sloppy quorum depends on the failure detector. During the 2 seconds before it noticed, the coordinator still sent writes to the unreachable home replicas, and every write failed, sloppy or not. It is the detector, tuned as in , that decides how quickly writes route around a failure; the quorum rule only decides what happens after.

Step 6c: Repair

Hints and read repair fix what was written during a failure and what is read afterward. Anything else, a lost hint or a key nobody reads, waits for anti-entropy: the copies of each key range compare Merkle trees, as showed, and exchange only the keys under hashes that differ. The simulation compared two copies of a million keys, counting what crosses the network in both directions.

For a few differences, the trees cut the exchange by four orders of magnitude. The depth is a trade: deeper trees send fewer keys but more hashes and take more memory, and a shallow tree of 256 leaves sent 3.1 MB to find 10 differences, because each differing leaf holds about 3,900 keys. Two operational facts follow. A tree is valid only for the data it was built from, so nodes rebuild them, which reads the whole range from disk; repairs are scheduled, not continuous. Reading 4 TB at 500 MB/s, a rate a node might spare without hurting live traffic, takes over two hours, so a full repair of every range is spread over days. And the repair interval sets how long tombstones must be kept: a copy that missed a delete and is repaired after the tombstone has gone would bring the value back.

Step 6d: Concurrent writes

With writes accepted on either side of a partition, or simply by two coordinators at once, a key can receive two writes that did not see each other. The store must either pick one or keep both. Picking by timestamp, last write wins, depends on clocks (). Keeping both needs to know which writes saw which: each version carries a version vector, the vector clock of applied to one key, and a write replaces exactly the versions its context had seen. Versions that neither replaces the other are siblings, returned together on the next read for the client to merge.

export class SiblingRegister {
  private siblings: { vv: VersionVector; items: ReadonlySet }[] = [];

  read(): { items: Set; context: VersionVector } {
    const items = new Set();
    let context: VersionVector = {};
    for (const s of this.siblings) {
      for (const i of s.items) items.add(i);
      context = mergeVectors(context, s.vv);
    }
    return { items, context };
  }
  // A write carries the context it read. It replaces exactly the siblings that context had seen.
  write(writer: string, context: VersionVector, items: ReadonlySet): void {
    const vv = { ...context, [writer]: (context[writer] ?? 0) + 1 };
    this.siblings = this.siblings.filter((s) => !descends(vv, s.vv));
    this.siblings.push({ vv, items });
  }
  get count(): number {
    return this.siblings.length;
  }
}

The simulation ran Dynamo’s example: two clients adding items to one shopping cart, each reading the cart and writing it back a few milliseconds later, 500 items each, with clocks 30 ms fast and 20 ms slow. Last write wins kept 630 of the 1,000 items. In 358 cases the write that came later in real time lost, because the other client’s clock ran ahead. Version vectors kept all 1,000, with never more than two siblings at once. The cost is moved to the client, which must know how to merge: a union for a cart, which can bring back an item that one side deleted. Dynamo’s paper reports that in 24 hours of its cart service, 99.94% of requests saw exactly one version, so the merge code runs rarely but must be right.

At ten times the data, 750 nodes: the ring and the protocol are unchanged, and gossip still converges in a few rounds (). What changes is how often something is broken: with 750 machines, failures are routine rather than rare, so rebuilds and repairs must be automatic and throttled so that they do not starve live traffic. At a hundred times, and across regions, each region keeps its own ring and copies, writes in each region are accepted locally, and siblings from different regions are merged the same way as siblings from a partition.

In the real world

  • Dynamo, described by Amazon in 2007, used consistent hashing with virtual nodes and later equal-sized partitions, (N, R, W) commonly set to (3, 2, 2), sloppy quorums with hinted handoff, Merkle trees for each key range, and vector clocks truncated after about 10 entries. Its services were measured at the 99.9th percentile, for example 300 ms at 500 requests a second.
  • DynamoDB shares the name and little of the design. Its 2022 paper describes replication groups that use Multi-Paxos to elect a leader, which alone serves writes and strongly consistent reads; any replica can serve eventually consistent reads. During Prime Day 2021 it peaked at 89.2 million requests a second.
  • Cassandra places data on a ring of tokens, as Dynamo did. Version 4.0 changed the default from 256 tokens per node to 16, with a token allocator aware of the replication factor, because many tokens slowed repairs and made availability degrade earlier.

In an interview. Ask early whether writes must be accepted during a partition; the answer decides between this design and a leader per range. Then draw the ring, the preference list and one write with a node down, because that one picture shows placement, quorums and hinted handoff together. Spend the deep dives on quorum arithmetic with failures and on what happens to conflicting writes, and mention Merkle-tree repair and tombstones before the time runs out.

Key points

  • A Dynamo-style store follows from one requirement: accept writes during a partition. Without it, a leader per range is simpler.
  • The store is sized by disk; the time to rebuild a node depends on how many nodes share its data.
  • With one token per node placed by hash, the fullest of 100 nodes held 2.3 times the average; with 16, 1.4; with 256, 1.13. More tokens also make every pair of nodes share some key.
  • W + R greater than N gave no stale reads in the simulation; asking all three replicas and waiting for two also hides a slow one.
  • A sloppy quorum kept writes available through a partition and paid with stale reads during it and afterward, until hints and read repair caught up.
  • A write that fails is not undone: failure means unconfirmed.
  • Merkle trees found a few differences among a million keys with kilobytes instead of 40 MB.
  • Last write wins lost 37% of the items in the cart simulation; version vectors kept them all as siblings for the client to merge.

Check yourself

Which single requirement leads to this design instead of a leader per key range?

Accepting writes while a network partition separates the replicas. A leader-based design must refuse writes on the side without the leader; a leaderless one with sloppy quorums accepts them and resolves the conflicts later.

Why does a store with 256 tokens per node rebuild a failed node faster than one with a single token?

With 256 tokens the failed node’s data is spread over ranges whose other copies sit on almost every other node, 99 of 100 in the simulation, so all of them can send in parallel. With one token only a few neighbors hold copies, 4 in the simulation, and the rebuild is limited by their combined speed.

With N = 3, why choose W = 2 and R = 2 over W = 3 and R = 1, when both overlap?

W = 3 waits for the slowest replica on every write and fails whenever one replica is down. In the simulation its 99th percentile write took 21 ms against 1.4 ms, and with one replica down every write failed. Two of three tolerates a slow or failed replica on both paths.

A sloppy quorum accepted every write during a partition. What did it give up?

The overlap guarantee. During the partition, reads answered by stand-ins missed older keys: 5.0% were stale. When the home replicas returned, reads that reached them found old versions: 14.9% were stale until the hints were delivered, 2.8% with read repair.

A client is told its write failed. Can a later read return that value?

Yes. The write may have reached one replica before the coordinator gave up, and nothing removes it. In the strict-quorum simulation, 3,337 reads returned such writes. The client should treat the outcome as unknown and retry the same write.

Why must a tombstone be kept longer than the repair interval?

A copy that missed the delete still holds the value. If the tombstone has been purged by the time anti-entropy compares the copies, the old value looks like data the others are missing and is copied back.

Why can the shopping cart not use last write wins?

Two concurrent additions are two writes that did not see each other, and last write wins keeps only one of them, chosen by clocks that may be wrong. In the simulation it kept 630 of 1,000 items. Version vectors detect that the writes are concurrent and keep both for the client to merge.
