Finding rows without reading everything

A table is stored on disk as a sequence of fixed-size blocks called pages, 8 KB each in PostgreSQL and 16 KB in MySQL’s default engine. Rows are placed in pages roughly in the order they were inserted. To answer SELECT * FROM photos WHERE owner_id = 42 with no other help, the database has one option: read every page of the table and check every row. This is a sequential scan, or full table scan.

For a table of a thousand rows that is fine. For a photos table of 100 million rows at about 100 rows per page, it is a million pages, or 8 GB, to find perhaps thirty rows. Even from a fast SSD that takes seconds, and it competes with every other query for memory and disk while it runs.

An index is a separate structure, maintained by the database alongside the table, that is organized for finding rows by the value of one or more columns. It is the same idea as the index at the back of a textbook: a sorted list of terms, each with the page numbers where it appears. You read a small sorted structure to learn where to look, then go straight there.

The B-tree

The default index in nearly every relational database is the B-tree. It keeps keys in sorted order in a tree of pages that is very wide and very shallow.

Three properties make this structure so useful.

  • It is shallow. Each page holds hundreds of keys, so each level multiplies the number of rows the tree can address by hundreds. A lookup reads one page per level.
  • It is sorted. The leaf pages hold all keys in order and are linked to their neighbors. Once the database has found the first matching key it can walk along the leaves, which makes range conditions (BETWEEN, >, <), prefix matches (LIKE 'abc%') and ORDER BY efficient as well as equality.
  • It stays balanced. When a page fills up it splits in two, and the tree grows a new level only when the root itself splits. Every leaf is always the same distance from the root, so lookups have predictable cost.

A tree 4 levels deep with 300 keys per page can index up to 8.1 billion rows, so this table could grow 81 times before the index gains another level. Depth grows with the logarithm of the table size, which is why indexed lookups stay fast as data grows.

The upper levels of an index are small and are read constantly, so they stay in memory. In practice a lookup by an indexed key costs one or two reads from disk at most, and often none.

What an index costs

If indexes make reads fast, why not index every column? Because each one is paid for on every write.

  • Writes do more work. Inserting a row means inserting an entry into every index on the table. A table with six indexes turns one insert into seven writes. Updating an indexed column means removing one entry and adding another.
  • Space. Indexes are often as large as the table, and sometimes larger in total.
  • Memory. The database keeps frequently used pages in memory. Every index competes for that space, and indexes that do not fit in memory are far slower.

The working rule is to create indexes for the queries the application actually runs, and to remove indexes nothing uses. Databases keep usage statistics for each index, so unused ones can be found with a query.

Where the rows live: heaps and clustered indexes

Databases differ in what the leaf of an index contains, and the difference has practical consequences.

In PostgreSQL the table is a heap: rows sit in no particular order, and every index, including the primary key, holds pointers to row locations. In MySQL’s InnoDB engine the table is the primary key’s B-tree, with the full rows stored in its leaves. This is called a clustered index. Every other index, called a secondary index, stores the primary key value as its pointer.

Heap table (PostgreSQL)Clustered table (MySQL InnoDB, SQL Server by default)
Lookup by primary keyIndex, then one more read for the rowThe row is in the index leaf. No extra read.
Range scan by primary keyRows may be scattered across pagesRows are physically adjacent. Very fast.
Lookup by secondary indexIndex, then the rowSecondary index, then the primary key’s tree, then the row. Two tree descents.
Size of secondary indexesIndependent of the primary keyEach entry includes the primary key, so a wide key makes every index larger

One consequence deserves attention because it surprises people. In a clustered table, rows are stored in primary key order. If keys arrive in increasing order, every insert goes to the end of the tree, onto a page that is already in memory. If keys are random, as version 4 UUIDs are, every insert lands on a random page somewhere in the tree. Pages must be fetched from disk and split, and the table becomes fragmented. On large tables this slows inserts considerably. The remedy is a key that increases with time: an auto-incrementing number, or a time-ordered identifier such as UUID version 7, which PostgreSQL 18 can generate with a built-in uuidv7() function. covers the options.

Indexes on several columns

An index can cover more than one column. A composite index on (owner_id, created_at) sorts its entries by owner first and, among entries with the same owner, by creation time. A telephone directory sorted by surname and then first name is the same structure.

CREATE INDEX photos_owner_created_idx ON photos (owner_id, created_at);

The order of columns is the whole design. The index is useful for a query that constrains a leading part of it:

  • WHERE owner_id = 42: yes.
  • WHERE owner_id = 42 AND created_at > '2026-10-01': yes, and efficiently.
  • WHERE owner_id = 42 ORDER BY created_at DESC LIMIT 20: yes, and with no sorting step, because the entries are already in order. The database reads twenty entries and stops.
  • WHERE created_at > '2026-10-01': not in the ordinary way, because the matching entries are spread through every owner’s section.
Skip scanSome databases can use a composite index without a condition on its first column, by treating it as many small indexes, one per distinct leading value, and searching each. PostgreSQL added this in version 18. It helps when the leading column has few distinct values and is no substitute for the right index.

Two rules cover most cases. Put the columns compared with = first and the column used for a range or for sorting last. And let one composite index do the work of several: an index on (owner_id, created_at) also serves every query that an index on (owner_id) alone would, so the single-column one is redundant.

Covering, partial and expression indexes

Three refinements are worth knowing, because each turns a slow query into a fast one without touching application code.

A covering index contains every column a query needs, so the database can answer from the index without visiting the table at all. This is called an index-only scan. Extra columns can be attached to an index purely for this purpose:

CREATE INDEX photos_owner_created_idx ON photos (owner_id, created_at) INCLUDE (caption);

A partial index covers only the rows that match a condition. If a jobs table has ten million rows of which a few hundred are pending, an index on only the pending ones is tiny and stays in memory:

CREATE INDEX jobs_pending_idx ON jobs (run_at) WHERE status = 'pending';

An expression index indexes the result of a function instead of a raw column. This matters because a condition that wraps a column in a function cannot use an ordinary index on that column. WHERE lower(email) = 'ana@example.com' needs an index on lower(email).

A unique index does double duty: it speeds up lookups and it enforces that no two rows share a value. It is the only reliable way to guarantee uniqueness. Checking in application code and then inserting leaves a gap in which two requests can both pass the check ().

The query planner

SQL says what you want and leaves the method to the database. The component that chooses the method is the query planner, or optimizer. For each query it considers different ways to produce the result, such as which index to use, in which order to join tables and by which algorithm, estimates the cost of each, and runs the cheapest.

Its estimates come from statistics the database keeps about each column: how many rows the table has, how many distinct values a column holds, which values are most common. From these it predicts how many rows each condition will match. When the statistics are out of date or the prediction is wrong, the planner chooses badly, and a query that ran in a millisecond yesterday takes ten seconds today with no change to the code.

You can ask the database to show its plan. In PostgreSQL, EXPLAIN shows the plan it would use, and EXPLAIN ANALYZE runs the query and reports what happened. Reading this output is the most valuable database skill an application developer can have.

EXPLAIN ANALYZE
SELECT id, caption FROM photos WHERE owner_id = 42 ORDER BY created_at DESC LIMIT 20;

-- Before
Limit  (actual time=8421.5..8421.6 rows=20)
  ->  Sort  (actual time=8421.5..8421.5 rows=20)
        Sort Key: created_at DESC
        ->  Seq Scan on photos  (actual time=0.9..8420.3 rows=1288)
              Filter: (owner_id = 42)
              Rows Removed by Filter: 99998712
Execution Time: 8421.7 ms

-- After
Limit  (actual time=0.03..0.06 rows=20)
  ->  Index Scan Backward using photos_owner_created_idx on photos
        (actual time=0.03..0.05 rows=20)
        Index Cond: (owner_id = 42)
Execution Time: 0.08 ms

Read a plan from the innermost line outward. In the first plan the database read all 100 million rows, discarded all but 1,288, sorted those, and returned 20. The line to notice is Rows Removed by Filter: a large number there means the database examined rows it did not need. In the second plan it walked the index backward from Ana’s newest photo, took 20 entries and stopped. There is no sort and nothing was discarded. The timings are illustrative, and the shape of the two plans is what real output looks like.

Why the database is not using your index

Sometimes an index exists and the planner still scans the table. Usually it is right to. Fetching rows through an index means jumping around the table, one row at a time, and that is slower per row than reading pages in order.

An index on a column with few distinct values, such as a status that is 'active' for 95% of rows, is useless for finding active rows and excellent for finding the other 5%. This property is called selectivity. The other common reasons an index is passed over are mistakes in the query:

  • A function or calculation on the column: WHERE date(created_at) = '2026-10-10'. Rewrite it as a range on the bare column, or create an expression index.
  • A type mismatch: comparing a text column with a number makes the database convert every row before comparing.
  • A leading wildcard: LIKE '%sunset%' cannot use a B-tree, because the sorted order is only helpful when the start of the value is known.
  • The wrong column order in a composite index, as in the figure above.
  • Out-of-date statistics, typically after a bulk load. Running ANALYZE fixes this.

How joins are executed

A join can be carried out in three ways, and the planner picks one from its row estimates.

AlgorithmHow it worksChosen when
Nested loopFor each row on one side, look up the matching rows on the other, ideally through an indexOne side is small and the other has an index on the join column. The usual plan for application queries.
Hash joinBuild an in-memory hash table from the smaller side, then scan the larger side and probe itBoth sides are large and there is no useful index. Typical of reports.
Merge joinWalk two inputs that are already sorted on the join column, side by sideBoth sides arrive sorted, for example from indexes

The practical lesson is that foreign key columns should nearly always be indexed. PostgreSQL indexes primary keys automatically and does not index the column that refers to them. Without an index on comments.photo_id, loading the comments for one photo scans every comment in the system, and deleting a photo does the same while it checks for references.

The N+1 problem

The most common query problem in application code involves no slow query at all. It is too many fast ones.

// N+1: one query for the list, then one more for each item. 21 round trips.
const photos = await db.query("SELECT * FROM photos ORDER BY created_at DESC LIMIT 20");
for (const photo of photos) {
  photo.owner = await db.queryOne("SELECT * FROM users WHERE id = $1", [photo.owner_id]);
}

// Fix 1: let the database join. One round trip.
const rows = await db.query(`
  SELECT p.id, p.caption, u.username
  FROM photos p JOIN users u ON u.id = p.owner_id
  ORDER BY p.created_at DESC LIMIT 20`);

// Fix 2: fetch the related rows in one batch. Two round trips.
const ownerIds = [...new Set(photos.map((p) => p.owner_id))];
const owners = await db.query("SELECT * FROM users WHERE id = ANY($1)", [ownerIds]);

Each query in the first version takes a fraction of a millisecond to execute. The cost is the round trip between the application and the database, around half a millisecond each inside a data center. Twenty-one of them is some 10 ms where one would do, and a page that lists 200 items with three relations each makes 601 queries. The pattern usually hides inside an object-relational mapper, where reading photo.owner quietly runs a query. It also hides from slow-query logs, since no individual query is slow. Count the queries per request during development, and use your mapper’s option for loading relations in advance.

The same problem appears in GraphQL servers, where each field resolver fetches its own data (), and the same fix applies: collect the keys and fetch them in one batch.

Pagination, seen from the database

compared offset and cursor pagination from the client’s side. The database’s side explains the performance difference. OFFSET 100000 LIMIT 20 does not jump to row 100,000. The database produces the first 100,020 rows in order and throws the first 100,000 away. Every page is slower than the one before it.

SELECT id, caption, created_at
FROM photos
WHERE owner_id = 42
  AND (created_at, id) < ('2026-10-01 18:04:00', 871)   -- values from the last row of the previous page
ORDER BY created_at DESC, id DESC
LIMIT 20;

With an index on (owner_id, created_at, id), this goes directly to the right place in the index and reads 20 entries, however deep into the list the user has scrolled. The id is included as a tiebreaker so that two photos with the same timestamp have a definite order.

Connections are a limited resource

Queries run over connections, and database connections are expensive in a way that HTTP connections are not. PostgreSQL starts a separate operating system process for each one, and each uses several megabytes of memory. The default limit is 100 connections. Opening one involves a network handshake, authentication and process creation, which can take tens of milliseconds.

Applications therefore keep a connection pool: a small set of open connections that requests borrow and return. Two things go wrong at scale.

  • The pools add up. Fifty application instances with a pool of 20 each want 1,000 connections. Autoscaling makes it worse, since adding application servers during a traffic spike adds database connections at the moment the database is busiest.
  • More connections do not mean more throughput. A database server has a fixed number of CPU cores and disks. Beyond a few connections per core, extra concurrent queries only contend with each other, and total throughput falls.

The standard answer is a connection pooler between the application and the database, such as PgBouncer. Thousands of application connections share a few dozen real ones, each borrowed only for the duration of a transaction. Serverless functions make a pooler essential, because each function instance would otherwise open its own connection. returns to that.

Common mistake. When requests start timing out waiting for a database connection, the instinct is to raise the pool size. If the database is already saturated, that makes each query slower and the queue longer. Find out first whether connections are being held too long, for example by a transaction left open while the code calls another service, or whether the queries themselves need attention.

Working on a slow query

  1. Find out which queries matter. Look at total time, which is the number of calls multiplied by the average duration. Databases can report this, in PostgreSQL through the pg_stat_statements extension. A 2 ms query that runs a million times an hour matters more than a 5-second report that runs twice a day.
  2. Read the plan with EXPLAIN ANALYZE, using realistic data. A plan from a development database with a hundred rows tells you nothing.
  3. Compare estimated rows with actual rows. A large gap means the planner was misinformed.
  4. Look for rows read and thrown away, and for sorts that an index could have avoided.
  5. Fix the cheapest thing first: rewrite the condition so it can use an existing index, then add or change an index, then restructure the query, and only then consider caching or changing the schema.
  6. Measure again, and check that writes to the table have not become noticeably slower.

In production. Creating an index on a large table takes time and, done the default way in PostgreSQL, blocks writes to the table for the duration. Use CREATE INDEX CONCURRENTLY, which builds the index without blocking writes at the price of taking longer. covers this kind of change.

In an interview. When you write down a table, write down its indexes too, and derive them from the queries: “the feed query filters by owner and sorts by time, so a composite index on owner and creation time”. Then mention the cost: “this table is write-heavy, so I would keep it to two indexes”. That link from access pattern to index to write cost is what interviewers are listening for.

Common mistakes

  • No index on foreign key columns. Joins and deletes scan whole tables.
  • One index per column instead of composite indexes matched to real queries.
  • Indexes nobody uses, slowing every write.
  • Wrapping an indexed column in a function in the WHERE clause.
  • Queries in a loop. The N+1 pattern, usually inside an object-relational mapper.
  • SELECT * in hot paths, which fetches columns nobody reads and prevents index-only scans.
  • Deep OFFSET pagination.
  • Random primary keys on a large clustered table.
  • Testing with a hundred rows and discovering the plan with a hundred million.
  • Raising the connection limit instead of pooling.

Key points

  • Without an index a database reads the whole table. With a B-tree it reads one page per level, and four or five levels are enough for billions of rows.
  • Every index speeds up some reads and slows down every write. Create them for real queries and remove the unused ones.
  • In a composite index, column order decides which queries it serves: equality columns first, the range or sort column last.
  • Covering, partial and expression indexes solve specific problems cheaply.
  • The planner chooses a plan from statistics. EXPLAIN ANALYZE shows what it did, and rows read and discarded are the thing to look for.
  • An index is used only when a condition is selective and the column appears bare in the query.
  • Many fast queries in a loop are as harmful as one slow query. Batch them or join.
  • Paginate by key, not by offset, and put a pooler in front of the database.

Check yourself

You have an index on (country, city). Which of these can use it efficiently: a filter on country, a filter on city, a filter on both?

A filter on country and a filter on both. The entries are sorted by country and then by city, so all rows for one country are adjacent, and within them all rows for one city. A filter on city alone matches entries scattered through every country’s section.

A query has WHERE lower(email) = 'ana@example.com' and there is an index on email. Why is it slow, and what are two fixes?

The index is sorted by the original value, and the query compares a transformed value, so the index order is no help and every row is checked. Either create an expression index on lower(email), or store emails in lower case and compare the bare column.

Why might the planner ignore an index on a status column when you query for status = 'active'?

If most rows are active, the condition is not selective. Using the index would mean fetching most of the table one row at a time in index order, which is slower than reading the pages in sequence. The planner is making the right choice.

A page loads in 400 ms. The slow-query log is empty. The page shows 100 orders, each with its customer and its items. What do you suspect?

The N+1 pattern: one query for the orders and then one or two more per order, around 200 fast queries whose round trips add up. No single query is slow, so nothing is logged. Count the queries made by the request, then load the customers and items in batches or with joins.

Why does page 5,000 of an offset-paginated list take far longer than page 1?

The database cannot jump to an offset. It generates all the preceding rows in order and discards them, so the work grows with the page number. Keyset pagination avoids this by using the last row’s sort values as a starting point that an index can seek to directly.

Your service runs 40 instances, each with a pool of 25 connections, against one PostgreSQL server. What is wrong, and what would you change?

That is up to 1,000 connections to a server that can usefully run a few dozen queries at once, and whose default limit is 100. Each connection also costs memory. Put a connection pooler in front of the database so the instances share a small number of real connections, and reduce each instance’s pool.
