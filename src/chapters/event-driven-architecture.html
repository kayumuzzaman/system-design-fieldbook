Events, commands and queries

Services exchange three kinds of message, and the differences between them shape a system more than the choice of broker does.

CommandEventQuery
SaysDo thisThis happenedTell me this
Named asAn instruction: ResizePhotoA fact in the past tense: PhotoUploadedA question: GetPhoto
Addressed toOne specific receiverNobody in particularOne specific receiver
Can be refusedYesNo. It has already happened.Yes
The sender knowsWho will act and what they will doNothing about who is listeningWho holds the answer

The row that matters is the last one. A command couples the sender to the receiver: the upload service must know that a thumbnail service exists and what to ask of it. An event reverses the direction of knowledge. The upload service announces PhotoUploaded and knows nothing further. The thumbnail service knows that it cares about uploads. A sixth consumer can be added next year without the upload service changing or even being redeployed.

An event-driven architecture is one in which services communicate mainly by publishing and reacting to events. The benefit is that kind of independence. The cost is that nobody is in charge of the overall flow, which later sections return to.

A message can be sent through a broker and still be a command in disguise. If the upload service publishes PhotoUploaded but the event exists only so that one particular service will resize the photo, and the uploader breaks if that does not happen, the coupling is still there. It has only been hidden.

Four things “event-driven” can mean

Martin Fowler observed in 2017 that people use the term for four distinct patterns. Telling them apart prevents most arguments about whether event-driven design is a good idea.

PatternThe ideaWeight
Event notificationAnnounce that something changed, with little detail. Interested services call back for more.Light
Event-carried state transferPut the changed data in the event, so that consumers keep their own copy and need not call backModerate
Event sourcingStore the events themselves as the system of record, and compute current state from themHeavy
CQRSUse separate models, often separate stores, for changing data and for reading itModerate to heavy

The first two are about what crosses the boundary between services. The last two are about how one service stores and serves its own data. They can be combined freely or used alone.

A notification is small and cannot carry stale data, since the consumer fetches the current state. The cost is a call back from every consumer for every event, which adds load to the publisher and means consumers stop working when it is down. The independence the event bought is partly given back.

State transfer removes the call back. The search indexer needs nothing from the photo service at run time, because everything it needs arrived in events. This is how services become able to survive each other’s outages. In exchange, events are larger, data is duplicated across services, and each copy lags the source by however long delivery takes.

A workable default: carry in the event the fields that consumers commonly need, along with a version number so that a consumer can tell old from new, and leave rarely needed detail to be fetched.

Designing events

An event is a public interface with an unusual property: it is stored. Events published last month may be read next year, by code that did not exist when they were written. That raises the stakes on getting their shape right.

The envelope

Every event needs the same handful of facts about itself, separate from its business content. The CloudEvents specification, a Cloud Native Computing Foundation standard, gives them common names so that tools and services from different teams agree.

{
  "specversion": "1.0",
  "id": "0199c2f4-7a10-7c3e-9d2b-5f1e8a4b6c70",     // unique: consumers deduplicate on this
  "source": "/photo-service",                         // who published it
  "type": "com.example.photo.uploaded.v1",            // what happened, with a version
  "subject": "photos/871",                            // what it is about
  "time": "2026-10-10T09:14:03.120Z",                 // when it happened, not when it was sent
  "datacontenttype": "application/json",
  "data": {
    "photoId": 871,
    "ownerId": 42,
    "caption": "Sunrise",
    "version": 7                                      // lets consumers ignore older updates
  }
}

What to put inside

  • Describe what happened in business terms. OrderCancelled with a reason tells consumers something. OrderRowUpdated with a list of changed columns makes every consumer reverse-engineer your intent, and breaks them when your table changes.
  • Publish deliberately. The events a service shares are a contract. Its internal tables are not. Exposing raw database changes as public events couples every consumer to your schema ( returns to this).
  • Give each event a key. Use the ID of the entity, so that a log keeps that entity’s events in order ().
  • Include a version of the entity. Delivery can duplicate and reorder. A consumer that stores the highest version it has applied can discard anything older ().
  • Treat personal data with care. A log is designed not to forget, which conflicts with a person’s right to have their data deleted. Keep personal data out of long-lived events where you can and refer to it by ID. Where you cannot, one technique is to encrypt each person’s data with their own key and delete the key when they ask to be forgotten.

Changing a schema without breaking consumers

Producers and consumers are deployed at different times by different teams. For a while, old and new versions of both are running, and old events remain in the log. A schema change is safe only if it is compatible in the direction that matters.

CompatibilityMeaningSafe changesDeploy first
BackwardNew consumers can read old eventsAdd an optional field with a default. Remove a field.Consumers
ForwardOld consumers can read new eventsAdd a field. Remove an optional field.Producers
FullBoth of the aboveAdd or remove optional fields onlyEither

In practice: add optional fields, never change the meaning or type of an existing field, and never reuse a name. When a change cannot be made compatibly, publish a new event type, such as photo.uploaded.v2, alongside the old one, and retire the old one when its last consumer has moved.

A schema registry enforces this mechanically. Producers register each event’s schema, written in a format such as Avro, Protocol Buffers or JSON Schema. The registry rejects a new version that breaks the configured compatibility rule, before any incompatible event can be published. Without one, the first notice of a broken schema is a consumer failing in production.

In production. Keep a catalog of events: what each means, who publishes it, its schema and who consumes it. The AsyncAPI format does for events what OpenAPI does for HTTP APIs. In an event-driven system the list of consumers is not visible in any code, and “who will break if I change this?” has no answer unless someone has written it down.

Event sourcing

Most services store current state. A wallet row says the balance is 50. When money moves, the row is overwritten. How the balance came to be 50 is lost, unless a separate audit table records it, and then there are two records that can disagree.

Event sourcing stores the changes and nothing else. The wallet is a sequence of events: deposited 100, withdrew 20, withdrew 30. The balance is not stored. It is computed by applying the events in order. Accountants have worked this way for centuries: a ledger is never erased, and the balance is the sum of the entries.

The code has a characteristic shape. Two pure functions hold all the logic. apply computes state from events. decide checks a command against the current state and returns new events. Neither touches a database, which makes the business rules easy to test.

// Events: facts, named in the past tense. Amounts are in cents.
type WalletEvent =
  | { type: "Deposited"; amount: number }
  | { type: "Withdrawn"; amount: number }
  | { type: "Frozen"; reason: string };

interface WalletState { balance: number; frozen: boolean; }
const initial: WalletState = { balance: 0, frozen: false };

// State is computed from events and from nothing else.
function apply(state: WalletState, event: WalletEvent): WalletState {
  switch (event.type) {
    case "Deposited": return { ...state, balance: state.balance + event.amount };
    case "Withdrawn": return { ...state, balance: state.balance - event.amount };
    case "Frozen":    return { ...state, frozen: true };
  }
}

type Command =
  | { type: "Deposit"; amount: number }
  | { type: "Withdraw"; amount: number };

// The rules live here: check the command against current state, and return
// the events that follow. Nothing is saved and nothing is sent.
function decide(state: WalletState, command: Command): WalletEvent[] {
  if (state.frozen) throw new Error("wallet is frozen");
  if (command.amount <= 0) throw new Error("amount must be positive");
  switch (command.type) {
    case "Deposit":
      return [{ type: "Deposited", amount: command.amount }];
    case "Withdraw":
      if (command.amount > state.balance) throw new Error("insufficient funds");
      return [{ type: "Withdrawn", amount: command.amount }];
  }
}

class EventStore {
  private streams = new Map();

  read(streamId: string): WalletEvent[] {
    return this.streams.get(streamId) ?? [];
  }

  // Append only if nobody else has appended since we read.
  append(streamId: string, expectedVersion: number, events: WalletEvent[]): void {
    const stream = this.read(streamId);
    if (stream.length !== expectedVersion) throw new Error("concurrent update: reload and retry");
    this.streams.set(streamId, [...stream, ...events]);
  }
}

function handle(store: EventStore, walletId: string, command: Command): void {
  const history = store.read(walletId);
  const state = history.reduce(apply, initial);            // rebuild current state
  store.append(walletId, history.length, decide(state, command));
}

const store = new EventStore();
handle(store, "wallet-42", { type: "Deposit", amount: 10_000 });
handle(store, "wallet-42", { type: "Withdraw", amount: 2_000 });
handle(store, "wallet-42", { type: "Withdraw", amount: 3_000 });

store.read("wallet-42").reduce(apply, initial).balance;     // 5000

// A question nobody planned for, answered from the same events:
const largestWithdrawal = Math.max(
  ...store.read("wallet-42").filter((e) => e.type === "Withdrawn").map((e) => e.amount));   // 3000

The condition in append is the optimistic concurrency control of . If two withdrawals are handled at once, both read a stream of two events, and only one append of a third can succeed. The other reloads, sees the lower balance and is checked again. Without that condition, both could pass the balance check and overdraw the wallet.

What it gives you

  • A complete history for free. The audit trail is the data itself, so it cannot drift from the truth.
  • Answers to questions asked later. The last lines of the example compute something no table was designed for. New read models can be built at any time by replaying events from the start.
  • State at any past moment. Replay up to a date to see what the balance was then, or to reproduce a bug exactly as it occurred.
  • Events to publish. The service already has a reliable record of everything that happened, in order.

What it costs

  • Events are forever. A table can be migrated. Stored events cannot be rewritten without undermining the point of them, so code must be able to read every version of every event ever written, usually by converting old versions to the current shape as they are loaded.
  • Reads need projections. “All wallets with a balance over 1,000” cannot be answered by scanning event streams. You maintain read models, which brings eventual consistency inside a single service.
  • Long streams are slow to replay. A wallet with a million events needs a snapshot: the state saved at some event number, so that loading replays only what came after.
  • Deleting is hard. Removing a person’s data from an append-only history needs the techniques mentioned earlier.
  • It is unfamiliar. Every engineer who joins has to learn a different way to think about data.

Event sourcing earns its cost where history is the point: ledgers, payments, orders, anything audited, anything where “how did it get into this state?” is asked often. For a service that stores user preferences, it is a great deal of machinery for no benefit. It is a choice for one service at a time, never a style for a whole system. builds a full design on it.

CQRS and read models

The data shape that makes writes safe is rarely the one that makes reads fast. Writes want normalized data and enforced rules. Reads want exactly what one screen needs, already joined and sorted.

Command query responsibility segregation, or CQRS, accepts this and splits them. Commands go to a write model built for correctness. Changes flow out of it as events. Separate read models, also called projections or materialized views, are kept up to date from those events, each shaped for one kind of query and stored in whatever suits it.

You have already met mild forms of this. A read replica is a read model with the same shape as the write model (). A search index kept in step with a database is a read model in a different store (). A cache is a read model that can be discarded. Full CQRS only makes the idea explicit and uses events as the feed.

The essential property of a read model is that it is disposable. It holds nothing that cannot be recomputed from the write side. If its design turns out wrong, build a new one beside it from the event history, switch over and delete the old one.

CQRS and event sourcing are often mentioned together and are independent. A service can keep ordinary tables and still publish events to feed read models. A service can be event-sourced with a single simple read model. Use each only where it pays.

Living with eventual consistency

Every pattern in this chapter introduces a delay between a change and its visibility elsewhere. Usually it is milliseconds. Under load or after a failure it can be minutes. The design has to be correct at any length of delay.

The user who cannot see their own change. Ana renames an album, the page reloads from a read model that has not yet caught up, and the old name appears. This is the read-your-writes problem of . Common answers:

  • Return the new state in the response to the command, and have the client display that.
  • Update the interface optimistically, without waiting.
  • Have the command return a version number, and have the read side wait briefly until it has reached that version.
  • Read that user’s own data from the write model for a short time after they change it.

Duplicates and reordering. Events are delivered at least once and, across partitions, in no particular order. Projections must be idempotent and should use entity versions to ignore stale updates.

A projection that falls behind or goes wrong. Monitor each projection’s lag as you would a consumer’s. Keep the ability to rebuild one from scratch, and rehearse it. A projection that cannot be rebuilt has quietly become a source of truth.

Losing an event at the source. A service that updates its database and then publishes can crash between the two, and every downstream view is then wrong with no error anywhere. Publish through a transactional outbox () or change data capture (), never as a second, separate write.

Following a flow nobody wrote down

In a system built on direct calls, the sequence of steps for placing an order can be read in the code of whichever service makes the calls. In an event-driven system the sequence exists only as the sum of every service’s subscriptions. This is the choreography of , with the same weakness: no single place describes the process, and nothing notices if one step silently never happens.

Two identifiers on every event make the flow recoverable after the fact.

When a service handles an event and publishes another, it copies the correlation ID and sets the causation ID to the ID of the event it handled. With distributed tracing in place (), the trace context does the same job across both calls and messages.

For a process with a defined beginning and end, where a missing step must be detected and compensated, such as fulfilling an order, events alone are the wrong tool. Use an orchestrator or workflow engine that owns the process and knows what should have happened by now (). Events suit open-ended reactions. Workflows suit processes that must complete.

When it helps and when it hurts

Event-driven design fits whenIt is a poor fit when
Several independent services react to the same occurrencesOne service needs an answer from another to continue
New reactions are added often, by different teamsThe process has strict steps that must all complete, in order
Consumers must keep working when the producer is downUsers must see every change immediately everywhere
The load is uneven and work can be deferredThe system is small and one team owns all of it
History and audit are requirementsThe data is simple and its history has no value

A small system does not need any of this. One service with one database and a jobs table is easier to build, reason about and debug. Event-driven design is a way of managing the cost of many teams and many services, and it has costs of its own that are only worth paying against that one.

In an interview. When you say “this service publishes an event”, add what kind: “a state-carrying event keyed by order ID, with a version, published through an outbox”. If you propose event sourcing or CQRS, say what it buys in this problem and name the cost: “event sourcing here because the wallet needs a full audit trail and reproducible balances, and the price is that reads come from projections that lag”. Proposing either as a default is a warning sign to an interviewer.

Key points

  • A command tells one receiver what to do. An event states what happened and leaves the reaction to whoever cares. Events move knowledge of the relationship from the sender to the receiver.
  • “Event-driven” covers four patterns of very different weight: notification, state transfer, event sourcing and CQRS.
  • Events that carry state let consumers work without calling back, at the price of duplicated data that lags.
  • Events are stored interfaces. Give them an envelope, a key and a version, and change schemas only compatibly.
  • Event sourcing stores changes as the record and derives state. It gives history and replay, and costs permanent schemas and projections.
  • CQRS separates the model that decides from the models that answer. Read models are disposable and lag behind.
  • Design the interface and every consumer for delay, duplicates and reordering.
  • Use events for open-ended reactions and a workflow for processes that must complete.

Check yourself

The upload service publishes “GenerateThumbnails” to a topic. Is that an event? Why does the distinction matter?

It is a command sent through a broker. It is an instruction, in the imperative, and it presumes a particular receiver doing a particular thing. The uploader still knows about thumbnails, so adding or removing reactions still means changing it. An event would be “PhotoUploaded”, with the thumbnail service deciding for itself that uploads need thumbnails.

A search indexer receives thin “photo.updated” events and calls the photo service for details. What happens to search during a photo service outage, and how would you change the events?

The indexer cannot fetch details, so it stalls or fails for the whole outage, although search itself is healthy. Carrying the fields the indexer needs in the event, with a version number, removes the call back, and the indexer keeps working from events alone.

You need to add a required field to an event that five teams consume. What is the safe sequence?

A new required field is not compatible in both directions. Add it as an optional field with a default, so that old consumers ignore it and new consumers cope with old events that lack it. Deploy producers to populate it. If it must be required with different semantics, publish a new event type alongside the old one and retire the old one after every consumer has migrated.

In the event-sourced wallet, two withdrawals of 60 arrive at the same moment against a balance of 100. What prevents an overdraft?

Both handlers load the same stream and both decide the withdrawal is allowed. Each tries to append with the expected version it read. The store accepts the first and rejects the second, because the stream is now longer than expected. The second reloads, computes a balance of 40 and is refused for insufficient funds.

Name two things event sourcing makes easy and two it makes hard.

Easy: a complete and trustworthy audit trail, and building new views or answering new questions from history, including state as of any past time. Hard: changing event schemas, since old events must stay readable forever, and queries across many entities, which need separately maintained read models. Deleting personal data is a third difficulty.

After saving a profile change, a user is shown their old profile. The system uses CQRS. What is happening, and what are two fixes?

The page was read from a read model that had not yet processed the event for the change. Fixes: return the updated profile in the command’s response and display that, or have the read wait until the read model reaches the version the command returned. Reading that user’s own data from the write side for a short time also works.

An order sometimes ends up paid but never shipped, in a system where services react to each other’s events. Why is this hard to detect, and what design addresses it?

With choreography no component knows the whole process, so nothing expects the shipment and nothing notices its absence. An orchestrator or workflow engine that owns the order process records each step and can time out, retry or compensate when a step does not happen. Correlation IDs at least allow the incomplete flow to be found afterward.
