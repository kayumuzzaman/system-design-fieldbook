One meaning, three encodings

HTTP is best understood as two things that happen to share a name. The first is a set of semantics: what a method means, what a status code means, how caching and content negotiation work. The second is a wire format, the way a message is turned into bytes, and there are three of those in use: HTTP/1.1, HTTP/2 and HTTP/3.

The semantics are the same across all three versions. A GET that returns 200 with a Cache-Control header means the same thing whether it traveled as text over TCP or as binary frames over QUIC. That is why an application can sit behind a load balancer that speaks HTTP/3 to browsers and HTTP/1.1 to the application, and nothing in the application has to know.

This chapter takes the semantics first, because they are what you design with, then the versions, then TLS.

Methods and what they promise

A method does more than name an action. Each one makes promises about its effects, and every intermediary between the client and your code relies on those promises to decide what it may do.

  • A method is safe if it only reads. The client is not asking for anything to change.
  • A method is idempotent if making the same request several times leaves the server in the same state as making it once.
  • A method is cacheable if a stored response may be used to answer a later request.
MethodMeaningSafeIdempotentCacheable
GETRead a resourceYesYesYes
HEADRead only the headersYesYesYes
OPTIONSAsk what is allowedYesYesNo
QUERYRead, with the query in the request bodyYesYesYes
PUTReplace a resource with this representationNoYesNo
DELETERemove a resourceNoYesNo
POSTCreate something, or run an actionNoNoRarely
PATCHChange part of a resourceNoNot necessarilyNo
A new methodQUERY was standardized in June 2026 as RFC 10008, the first addition to the core methods in many years. It fills a long-standing gap: a read whose parameters are too large or too structured for a URL. Until now such searches were sent with POST, which told every cache and retry mechanism, wrongly, that they were unsafe to repeat. Support in servers, proxies and client libraries will take time to spread.

These properties decide real behavior:

  • Retries. When a connection breaks mid-request, the client cannot tell whether the server acted. Browsers, proxies and client libraries retry idempotent methods automatically and leave the others alone. If your GET handler changes something, an automatic retry will change it twice.
  • Caching and prefetching. Caches store responses to safe methods. Browsers and crawlers may fetch a GET link before anyone clicks it. A “delete” link implemented as a GET will eventually be followed by a crawler.
  • Making POST retryable. Creating a payment is naturally a POST, and it must not happen twice. The standard remedy is for the client to send a unique key with the request so the server can recognize a repeat. shows the pattern.

Common mistake. Returning 200 OK with an error described in the body. Monitoring, load balancers, caches and retry logic all read the status code and nothing else. A failure dressed as a success is counted as healthy, may be cached, and will never be retried.

Headers, by the job they do

There are hundreds of headers. They fall into a few groups, and knowing the groups is enough to find the right one when you need it.

If-Match deserves a note because it solves a common problem cheaply. Two people load the same record, both edit it, and the second save silently overwrites the first. If the client sends the ETag it loaded in an If-Match header with its update, the server can refuse with 412 Precondition Failed when the record has changed in between. This is optimistic concurrency control, done in HTTP. covers the idea in general.

Cookies

HTTP is stateless, and cookies are how browsers carry state anyway. A server sends Set-Cookie, and the browser returns that cookie on every later request to the same site. Since cookies are sent automatically, their attributes are security controls:

AttributeEffectUse
SecureSent only over HTTPSAlways, for anything sensitive
HttpOnlyInvisible to JavaScriptSession cookies, so that an injected script cannot steal them
SameSiteWhether the cookie is sent on requests that start from another siteLax or Strict, to block cross-site request forgery
Max-Age, ExpiresLifetime. Without one the cookie ends with the browser session.Keep sessions as short as the product tolerates
Domain, PathWhich hosts and paths receive itAs narrow as possible

Cookies also have a performance cost that is easy to forget. Every cookie for a site is attached to every request to it, including requests for images and scripts. Large cookies inflate every request, which is one reason static files are often served from a separate, cookie-free domain or a CDN.

HTTP caching

Caching is the most valuable feature of HTTP for anyone designing for scale, because a response served from a cache costs your servers nothing. Caches exist at several points: in the browser, in CDNs and other shared proxies, and sometimes in a reverse proxy in front of your own application. All of them follow the same rules, which the response headers control.

The rules rest on two ideas. Freshness: for how long may a stored response be reused without asking? Validation: when that time is up, how can the cache check cheaply whether its copy is still good?

Freshness is set with Cache-Control. Its directives combine, and these are the ones that matter:

DirectiveMeaning
max-age=NFresh for N seconds from when it was generated.
s-maxage=NThe same, for shared caches such as CDNs only. Overrides max-age there.
publicAny cache may store it.
privateOnly the user’s own browser may store it. For anything personalized.
no-cacheMay be stored, and must be revalidated with the origin before each use. The name misleads.
no-storeMust not be stored anywhere. For sensitive data.
immutableWill never change while fresh, so do not revalidate even on reload.
stale-while-revalidate=NAfter it goes stale, it may still be served for N more seconds while the cache fetches a new copy in the background.
stale-if-error=NIf the origin is failing, a stale copy may be served for N more seconds.

Validation uses an ETag, an opaque identifier for one version of a response, such as a hash of its content or a version number. The cache sends it back in If-None-Match. If the current version has the same tag, the server answers 304 Not Modified with no body.

declare function loadPhoto(id: string): Promise<{ id: string; version: number }>;

export async function GET(request: Request): Promise {
  const id = new URL(request.url).pathname.split('/').pop()!;
  const photo = await loadPhoto(id);
  const etag = `"${photo.version}"`;

  // The caller already holds this version: answer with headers only.
  if (request.headers.get('If-None-Match') === etag) {
    return new Response(null, { status: 304, headers: { ETag: etag } });
  }

  return Response.json(photo, {
    headers: {
      ETag: etag,
      // A CDN may reuse this for 60 s, then serve it stale for up to 5 min while it refetches.
      'Cache-Control': 'public, s-maxage=60, stale-while-revalidate=300',
    },
  });
}

Four recipes cover most of what a web system serves.

ContentHeaderReasoning
Files with a hash in the name, such as app.3f9a2c.jspublic, max-age=31536000, immutableThe content of that URL never changes. A new build produces a new name. Cache for a year.
HTML pagesno-cacheAlways check, so users get new deployments at once. With an ETag, the check usually costs a 304.
Public API data that tolerates slight stalenesspublic, s-maxage=60, stale-while-revalidate=300The CDN absorbs nearly all the traffic, and users never wait for a refresh.
Personal or sensitive responsesprivate, no-storeMust never be stored in a shared cache or left on disk.

The first recipe is worth dwelling on, since it sidesteps the hardest problem in caching. You cannot reliably tell every browser in the world to discard a cached file. You can make the problem disappear by never changing a file in place: put a fingerprint of the content in its name, cache it forever, and refer to the new name when the content changes.

VaryOne URL can have several representations: compressed or not, English or Bengali. The Vary header names the request headers that select between them, so a cache stores each separately. Vary: Accept-Encoding is routine. Varying on a header with many values, such as User-Agent or Cookie, splits the cache into so many variants that it stops being useful.

Common mistake. Sending a personalized response without private. If a shared cache stores one user’s account page and serves it to the next visitor, you have a data breach caused by a missing header. Make responses uncacheable by default in your framework and opt specific public ones in. Never rely on a cache’s guess.

The three versions, under the hood

Each version of HTTP changed how messages share a connection, to remove a bottleneck in the version before.

HTTP/1.1

Messages are text. A connection carries one request at a time: the next cannot start until the previous response has finished. Browsers compensate by opening up to six connections per site, each paying for its own handshakes and slow start. Developers compensated with tricks, such as merging many small files into one and spreading resources across several hostnames to get more connections. It remains the common language between proxies and application servers, where connections are short and plentiful.

HTTP/2

Messages are split into binary frames, and each request and response pair is a numbered stream. Frames from many streams are interleaved on a single connection, so dozens of requests proceed at once without waiting for each other. Headers, which repeat almost unchanged from one request to the next, are compressed against a table both sides remember.

One connection per site means one handshake and one congestion window that warms up and stays warm. The 1.1 workarounds become unnecessary, and some turn harmful. The weakness, described in Chapter 9, is that all streams share one TCP byte stream, so one lost packet stalls them all.

HTTP/3

The same streams and frames, moved onto QUIC. Each stream is delivered independently, connection setup takes one round trip including encryption, and connections survive a change of network. For a user on a good fixed connection the difference from HTTP/2 is small. On a lossy mobile network it can be large.

Two more features of the modern protocol are worth knowing:

  • Early hints. A server can send an interim 103 response naming files the page will need, before the real response is ready, so the browser starts fetching them while the server is still working.
  • Compression. Text responses are compressed with gzip or Brotli, and newer browsers also accept Zstandard. A 2025 standard additionally lets a browser use a file it already has, such as last week’s version of a script, as a dictionary for compressing the new one, which can shrink an update to a small fraction of its size.

In production. Which version is used between the browser and your edge is decided by your CDN or load balancer settings, and turning on HTTP/3 there is normally a switch. The hop from the edge to your servers is separate and is often plain HTTP/1.1 with keep-alive, which is fine. One case needs care: gRPC requires HTTP/2 all the way to the application, so every proxy on that path must support it.

TLS

TLS gives a connection three properties. Confidentiality: nobody on the path can read it. Integrity: nobody can alter it undetected. Authentication: the client knows which server it is talking to. HTTPS is HTTP over a connection with those properties.

The current version is TLS 1.3, published in 2018. Its predecessors 1.0 and 1.1 are formally deprecated, and 1.2 remains in use for older clients. Version 1.3 removed a long list of options that had caused vulnerabilities and cut the handshake to one round trip.

The handshake

  1. ClientHello. The client sends the versions and ciphers it supports, a freshly generated public value for key agreement, the hostname it wants (the SNI, server name indication), and the application protocols it speaks, such as HTTP/2 (the ALPN list).
  2. ServerHello. The server chooses among those and sends its own public value. Both sides can now compute the same secret keys, which nobody watching the exchange can derive.
  3. Certificate and proof. Encrypted under those keys, the server sends its certificate chain and a signature over the handshake made with the certificate’s private key. That signature proves it owns the certificate.
  4. Finished. Each side confirms it saw the same handshake. The client can send its first request together with its confirmation.

The keys come from a fresh exchange for every connection and are discarded afterward. This property is forward secrecy: if a server’s long-term private key is stolen next year, traffic recorded today still cannot be decrypted.

Certificates and trust

A certificate is a signed statement: “this public key belongs to www.example.com”. The signer is a certificate authority (CA). Browsers and operating systems ship with a list of root authorities they trust, and trust is extended from those roots through a chain.

Before accepting a certificate, the client checks four things: the name on it matches the hostname requested, the current date is within its validity period, the signatures chain to a trusted root, and it has not been revoked. A failure of any check produces the full-page browser warning, and for an API client, a refused connection.

To obtain a certificate you prove to an authority that you control the domain, by serving a file it asks for or by creating a DNS record. The ACME protocol automates this exchange, which is what lets a server or a CDN obtain and renew certificates with no human involved.

The fourth check, revocation, has never worked well, and the industry’s answer is reshaping how certificates are operated.

  • Online revocation checking is being retired. The protocol for asking an authority “is this certificate still valid?” leaked browsing activity to the authority and often failed open. Let’s Encrypt, the largest authority, switched its service for it off in August 2025.
  • Lifetimes are shrinking in its place. A certificate that expires soon does not need to be revoked. The maximum lifetime of a public certificate fell to 200 days in March 2026, and falls to 100 days in March 2027 and 47 days in March 2029. Let’s Encrypt made certificates that last about six days generally available in January 2026, and plans to cut its default from 90 days to 45.
  • Issuance is public. Authorities must record every certificate in public Certificate Transparency logs. You can watch those logs for certificates issued for your domains that you did not request.

The consequence for design is simple and firm: certificates must be issued and renewed by automation, and their expiry must be monitored. At 47 days, a manual process is an outage on a schedule.

Two changes in progressThe hostname in the ClientHello has always been sent unencrypted, which reveals the site being visited. Encrypted Client Hello, standardized in March 2026 as RFC 9849, hides it. Separately, key exchange is moving to a hybrid that resists future quantum computers, which Chapter 2 covered. Both are handled by browsers and by your CDN or TLS library, so staying current is mostly a matter of keeping those updated.

Where TLS ends

Somebody has to decrypt the traffic, and where that happens is an architectural decision.

PatternAdvantagesCosts
Terminate at the edgeCertificates live in one place. The balancer can route by URL, cache and compress. Application servers do no cryptography.Traffic is readable inside your network. Often unacceptable under security or compliance rules.
Terminate and re-encryptAll of the above, with encryption on every hop.Certificates to manage on the application servers too, usually from an internal authority.
Pass throughEnd-to-end encryption. The balancer sees nothing.The balancer can route only by address and port. No path routing, caching or request-level features.

Inside a system, TLS is also used in both directions. With mutual TLS (mTLS), the client presents a certificate as well, so each service proves its identity to the other. It is the basis of most zero-trust service-to-service security, and it is usually set up by a service mesh, as describes.

Two response headers finish the job on the public side. Strict-Transport-Security tells a browser to use only HTTPS for your site from now on, so that a user who types the bare domain is never sent over plain HTTP. And every HTTP endpoint that remains should do nothing except redirect to HTTPS.

Looking at real traffic

Two commands show most of what this chapter described.

# Everything about one request: the TLS version, the HTTP version negotiated, all headers
curl -sv -o /dev/null https://www.example.com/

# Only the response headers, to check caching and security settings
curl -sI https://www.example.com/app.3f9a2c.js

# The certificate a server presents: who it is for, who issued it, when it expires
openssl s_client -connect www.example.com:443 -servername www.example.com /dev/null \
  | openssl x509 -noout -subject -issuer -dates

The browser’s developer tools show the same information per request, including the protocol version and whether a response came from cache. Checking the Cache-Control header of your own site’s main page and of one of its scripts takes a minute and often turns up a surprise.

In an interview. HTTP knowledge is rarely asked about directly and is noticed constantly. Use the right method and status code when you sketch an API. Say which responses are cacheable and with what lifetime. When you draw the load balancer, say where TLS terminates and whether internal traffic is encrypted. When you mention retries, tie them to idempotency. Each of these takes one sentence and shows you have built real services.

Key points

  • HTTP’s semantics are shared by all versions. Versions differ only in how messages are carried.
  • Safe methods only read, and idempotent methods can be repeated. Intermediaries retry, cache and prefetch on the strength of those promises, so keep them.
  • Choose status codes for what clients and monitoring will do with them. Never report a failure as 200.
  • Caching is controlled by freshness, through Cache-Control, and validation, through ETag. Fingerprint static files and cache them for a year, revalidate HTML, and mark personal data private or no-store.
  • HTTP/1.1 sends one message at a time per connection. HTTP/2 multiplexes streams over one TCP connection. HTTP/3 moves those streams to QUIC and removes head-of-line blocking.
  • TLS 1.3 provides confidentiality, integrity and server identity in one round trip, with forward secrecy.
  • Certificates chain to trusted roots. Their lifetimes are shrinking toward 47 days, so issuance and renewal must be automated.
  • Decide where TLS terminates: at the edge, at the edge with re-encryption, or passed through to the application.

Check yourself

A client sends PUT /users/42 with a new profile and the connection drops before any response arrives. Is it safe to send the request again? What if it had been POST /payments?

PUT is idempotent: sending the same full replacement twice leaves the same result, so retrying is safe. POST /payments is not, and a blind retry could charge twice. It needs a mechanism such as an idempotency key that lets the server recognize the repeat.

Your site’s JavaScript bundle is served as /app.js with Cache-Control: max-age=86400. You deploy a fix. What goes wrong, and how should it be set up?

Browsers that fetched the old file keep using it for up to a day, possibly alongside new HTML that expects the new code. Name the file by a hash of its content, cache it for a year with immutable, and serve the HTML that refers to it with no-cache, so each deployment points at new file names.

What is the difference between no-cache and no-store?

no-cache allows a response to be stored and requires the cache to revalidate it with the origin before every use. no-store forbids storing it at all. The first is right for HTML you want always current, the second for sensitive data.

A user reports seeing another customer’s order page. The application code is correct. What configuration error could cause this?

A shared cache, such as a CDN or reverse proxy, stored a personalized response and served it to someone else. The response lacked Cache-Control: private or no-store, or the cache was configured to ignore cookies when building its cache key.

Your load balancer terminates TLS and forwards plain HTTP to application servers in a private subnet. Give one argument for this design and one against.

For: certificates and cryptographic work are in one place, and the balancer can use every request-level feature. Against: anyone who gains a foothold inside the network can read all traffic, including credentials, and many compliance regimes require encryption in transit everywhere. Re-encrypting to the servers addresses that.
