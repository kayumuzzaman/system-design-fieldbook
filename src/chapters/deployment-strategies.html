Change is the main cause of failure

ended with an uncomfortable observation: redundancy protects against things breaking, and most large incidents are caused by changes that reached every copy at once. A team that deploys rarely does not escape this. It makes each deployment larger, harder to understand and harder to undo.

The strategies in this chapter all pursue four properties.

PropertyMeansAchieved by
SmallEach change does little, so its effect is easy to predict and its cause easy to findFrequent releases from one main branch
GradualA fault reaches a few users before it can reach allRolling, canary and staged releases
ObservedA fault is noticed by a machine in minutesAutomatic comparison of new against old
ReversibleGoing back is fast and has been practicedRollback, feature flags, compatible changes

Research on software delivery supports the first row. The DORA program has surveyed engineering teams for over a decade, and it consistently finds that speed and stability go together: teams that release often also fail less and recover faster. It measures delivery with five metrics, in two groups. Throughput is change lead time, deployment frequency and failed deployment recovery time. Instability is change fail rate and deployment rework rate.

The delivery pipeline

A delivery pipeline is the automated path from a commit to production. Continuous integration is the first half: every change is merged into one main branch and automatically built and tested, many times a day. Continuous delivery is the second half: every change that passes is ready to release, and releasing is a routine, push-button or fully automatic act.

The stages are ordered by cost. Fast, cheap checks come first, so that most mistakes are caught in the minute after a commit. Slow, realistic ones come later and see only changes that survived the earlier ones. The last check is production itself, taken in small steps, which is what most of this chapter is about. No test environment reproduces real traffic, real data and real scale, so careful exposure to production is a testing stage in its own right.

Build once, promote the same thing

The output of the build stage is an artifact: the container image from , with a unique version. One rule governs it. The artifact that reaches production is the same artifact that was tested, not a second build from the same source.

A rebuild can differ from the first build in ways nobody intended: a dependency published a patch in between, a base image was updated, the build machine has a different compiler. Any such difference is untested. Promoting one immutable artifact through every environment removes the question.

For one artifact to run everywhere, whatever differs between environments must come from outside it: database addresses, credentials, feature settings. Those are supplied as configuration at start-up. The consequence is easy to miss: configuration is now a second thing that changes production, and it needs the same care as code. The largest outages of recent years were configuration changes, and a later section returns to them.

An immutable, versioned artifact also makes rollback simple. Going back means running the previous version, which still exists and was already proven in production.

Two versions at once

However a new version is introduced, there is a period when old and new run side by side. During a rolling update that period lasts minutes. With a canary it lasts hours. If a rollback happens, the old version comes back after the new one has already been writing data.

The rule that follows is short: every release must work alongside the release before it. In practice it rules out a family of changes when they are made in one step.

One-step changeWhat breaksWhere the safe version is described
Rename or drop a database columnOld code queries a column that is gone
Add a required field to an API requestOld clients do not send it
Change the meaning or format of a message fieldOld consumers misread new messages still in the queue
Change the shape of a cached valueEach version reads entries written by the otherPut a version in the cache key
Change two services that call each other togetherThey cannot be deployed at the same instantDeploy the tolerant side first

The general method is expand and contract, introduced for database schemas in the chapter on schema design. First release a version that understands both the old form and the new. When it is everywhere, start using the new form. When nothing uses the old form any more, and you are sure you will not roll back past this point, remove it. One risky change becomes three dull ones.

Rolling updates

A rolling update replaces copies of a service a few at a time. It is what an orchestrator does by default, and it needs no extra machinery.

Two numbers control the pace. The surge is how many copies beyond the normal count may exist during the update. The unavailable count is how many below the normal count may be ready. Kubernetes defaults both to 25%.

type Step = { old: number; fresh: number; ready: number };

/**
 * Replaces `replicas` old pods with new ones. Never more than replicas + maxSurge pods exist,
 * and never fewer than replicas - maxUnavailable are ready. New pods count once they are ready.
 */
export function rollingUpdate(replicas: number, maxSurge: number, maxUnavailable: number): Step[] {
  if (maxSurge === 0 && maxUnavailable === 0) throw new Error("the rollout could never move");
  const steps: Step[] = [];
  let old = replicas, fresh = 0;
  steps.push({ old, fresh, ready: old });
  while (old > 0 || fresh < replicas) {
    // start as many new pods as the surge allows
    const starting = Math.min(replicas - fresh, replicas + maxSurge - (old + fresh));
    // while they start, they are not ready: only old pods and earlier new pods serve
    const readyDuring = old + fresh;
    if (starting > 0) { steps.push({ old, fresh: fresh + starting, ready: readyDuring }); fresh += starting; }
    // now remove old pods, keeping at least replicas - maxUnavailable ready
    const removable = Math.min(old, old + fresh - (replicas - maxUnavailable));
    if (removable > 0) { old -= removable; steps.push({ old, fresh, ready: old + fresh }); }
    if (starting <= 0 && removable <= 0) throw new Error("stuck");
  }
  if (steps.at(-1)!.ready < replicas) steps.push({ old: 0, fresh: replicas, ready: replicas });
  return steps;
}
Setting, for 4 copiesBehaviorTrade
Surge 1, unavailable 0Start one, then remove one. Capacity never dropsNeeds room for one extra copy. Slowest
Surge 0, unavailable 1Remove one, then start one. Runs at three of four throughoutNo extra room needed. Less capacity during the update
Surge 4, unavailable 0Start all four new copies, then remove all four oldFast. Needs double the capacity for a moment

A rolling update depends entirely on readiness checks. The orchestrator moves on when a new copy reports ready, so a version that starts, reports ready and then fails every real request will be rolled out to the whole fleet, quickly and smoothly. A readiness check should exercise enough of the service to mean something, and a rollout should pause and reverse when new copies do not become ready.

Its weakness is that it is not selective. Every user is gradually moved onto the new version, and the only thing being judged is whether copies start. To judge whether the new version is actually better or worse, a release has to compare.

Blue-green

A blue-green deployment runs two complete environments. One, call it blue, serves all traffic. The new version is installed on the other, green, and tested there with no users. Then the router is switched.

Its strengths are a clean cutover and the fastest possible rollback: switch back. Users are never served by a mixture of versions for more than a moment.

Its costs are the second environment, which doubles capacity while both exist, and the fact that everyone moves at once. A fault that only appears under real traffic appears for all users together. Two more details need care. The environments usually share one database, so the compatibility rules above still apply in full. And requests in flight at the moment of the switch must be allowed to finish on the old side, using the connection draining from .

Canary releases

A canary release sends a small share of real traffic to the new version, compares its behavior with the old version’s, and widens the share only if the comparison is good. The name comes from the birds once carried into coal mines to give early warning of bad air.

Four choices define a canary.

What to compare. The signals that show harm to users: error rate, latency at the 99th percentile, and resource use such as memory and CPU for each request. Business signals, such as completed uploads or checkouts, catch faults that return a cheerful 200 OK with the wrong content.

Against what. Against old-version copies that are otherwise identical, as the figure explains. Comparing with fixed thresholds works too, and misses a version that is worse than before and still under the threshold.

How to split. By request is simplest. By user is better for anything visible, so that one person does not flip between versions from click to click. By tenant or by cell fits systems built as in .

How long. Long enough to see enough requests for the difference to be real and not chance. That depends on how rare the errors are and how much traffic the canary gets.

To tell an error rate of 0.5% from the usual 0.1%, with a 5% chance of a false alarm and a 90% chance of catching it, the canary needs about 1,268 requests. With 5% of 500 requests a second it receives 25 a second, so that takes 50.7 s. If the new version is bad, about 5 extra requests fail during the test. Released to everyone for the same time, about 101 would have. The statistics are satisfied quickly at this traffic. Keep the canary running for several minutes anyway, because some faults, such as memory leaks and slow queries, take time to appear.

Change the error rate to catch from 0.5% to 0.2% and the requirement rises from about 1,300 requests to about 12,000. Small regressions are expensive to detect, and a service with ten requests a minute cannot detect them with a canary at all in any useful time. For low-traffic services, lean on the earlier pipeline stages, on synthetic requests, and on a longer bake.

The decision itself can be automated. This function compares the two groups and returns one of three answers.

/** Requests a canary needs to tell error rate `bad` from `base`: 5% false alarms, 90% detection. */
export function canarySampleSize(base: number, bad: number): number {
  const z = 1.645 * Math.sqrt(base * (1 - base)) + 1.282 * Math.sqrt(bad * (1 - bad));
  return Math.ceil((z / (bad - base)) ** 2);
}

type Counts = { requests: number; errors: number };
type Verdict = "promote" | "rollback" | "wait";

/** Compares the canary with a baseline group of the old version that ran over the same period. */
export function judge(baseline: Counts, canary: Counts, minRequests: number): Verdict {
  if (canary.requests < minRequests) return "wait";
  const p1 = baseline.errors / baseline.requests, p2 = canary.errors / canary.requests;
  const pooled = (baseline.errors + canary.errors) / (baseline.requests + canary.requests);
  const se = Math.sqrt(pooled * (1 - pooled) * (1 / baseline.requests + 1 / canary.requests));
  const z = se === 0 ? 0 : (p2 - p1) / se;
  return z > 1.645 ? "rollback" : "promote";      // one-sided: only "worse" matters
}

To check that the two functions agree, 4,000 canaries of each kind were simulated at the sample size above, against a baseline drawn from the rest of the traffic. A canary with a true error rate of 0.5% was rolled back 89.8% of the time. A canary no worse than the old version was rolled back 6.7% of the time. Both are close to the 90% and 5% the formula promises. A real analysis looks at several metrics at once, which catches more and raises the false alarm rate, so thresholds need tuning against your own history.

Common mistake. A canary that nobody is judging. Sending 5% of traffic to a new version and then promoting it after ten minutes because no one complained is a slow rolling update with extra steps. The value is in the comparison and in the automatic stop.

Feature flags: separating deploy from release

So far, new code reaching a server and new behavior reaching a user have been the same event. A feature flag separates them. The new code path ships switched off, behind a condition that is read from configuration at run time. Deploying puts the code on the servers. Releasing turns it on for users, later and by degrees.

A percentage rollout must give each user a stable answer, so that a feature does not appear and vanish between page loads, and raising the percentage must only add users. Hashing the flag name with the user’s identifier does both.

import { createHash } from "node:crypto";

/** Maps a user to a bucket from 0 to 9,999 that is fixed for this flag. */
export function bucket(flag: string, userId: string): number {
  const h = createHash("sha256").update(`${flag}:${userId}`).digest();
  return h.readUInt32BE(0) % 10_000;
}

export function isEnabled(flag: string, userId: string, percent: number): boolean {
  return bucket(flag, userId) < percent * 100;
}

type Flag = { key: string; killed: boolean; allow: Set; percent: number };

export function evaluate(flag: Flag, userId: string): boolean {
  if (flag.killed) return false;                 // the off switch always wins
  if (flag.allow.has(userId)) return true;       // staff and testers first
  return isEnabled(flag.key, userId, flag.percent);
}

Over 100,000 test users, a flag at 1%, 10% and 50% enabled 1,012, 9,962 and 50,134 of them, and every user enabled at a lower percentage was still enabled at each higher one. Including the flag’s name in the hash matters: two different flags at 10% shared only 962 users, about a tenth of a tenth. Without it the same unlucky tenth of users would receive every experiment.

Flags are used for several different jobs, and it helps to keep them apart.

KindPurposeLifetime
Release flagRoll a new feature out graduallyDays or weeks, then deleted
Kill switchTurn off an optional feature under load or during an incident, as in Permanent
ExperimentShow variants to different users and measure which does betterThe length of the experiment
PermissionMake a feature available to certain plans or customersPermanent, and better kept in the product’s own data

Flags have a cost that grows quietly. Each one doubles the number of paths through the code, and old flags that nobody dares remove pile up until no one can say which combinations are live. Give every release flag an owner and a removal date, and delete it once the feature is fully on. Remember also that a flag change alters production behavior as surely as a deployment does. It deserves an audit trail, a gradual rollout of its own, and the same suspicion during an incident.

Testing with real traffic and no users

Two further techniques expose new code to production conditions before any user depends on it.

A dark launch runs the new code path for real requests and throws the result away. The photo app could compute a new feed ranking for every request, log how long it took and how it differed, and still return the old ranking. This reveals performance under real load and real data, with no user-visible risk.

Shadow traffic, also called mirroring, copies live requests to a new version of a service and discards its responses. It is the standard way to prove a rewrite, and it is the comparison step in the migration method of . One caution applies to both: the shadow path must not have side effects. A mirrored request that sends a second email or charges a card a second time is not a test.

Going back

When a release goes wrong, the first aim is to stop the harm, and understanding comes later. There are three ways to stop it, from fastest to slowest.

  1. Turn it off. If the change is behind a flag, switch the flag. Seconds.
  2. Roll back. Redeploy the previous artifact, or switch a blue-green router back. Minutes.
  3. Roll forward. Write a fix and ship it through the pipeline. Tens of minutes at best, and it means shipping new, hurried code during an incident.

Prefer the earliest option that applies. Rolling forward is right mainly when going back is impossible, and the list of things that cannot be rolled back is worth knowing before the incident.

  • Destructive schema changes. A dropped column does not return with the old code. This is why the contracting step waits.
  • Data written in a new format that the old version cannot read.
  • Effects outside the system. Emails sent, payments made, events consumed by other teams.

A rollback that has never been exercised is a hope. Some teams run one on purpose now and then, and the best signal is the simplest: how long did the last real one take? That figure, the failed deployment recovery time, is one of the five delivery metrics for good reason.

Releasing in waves

A canary limits exposure within one deployment. Large systems apply the same idea one level up, across the units they are divided into: cells, availability zones and regions.

Bake time exists because some faults are slow: a memory leak, a cache that fills, a job that runs nightly, a customer in another time zone. The schedule also follows the sun where it can, so that each wave lands in that region’s working hours with engineers awake.

The discipline has to cover everything that changes production, and the costliest incidents have been the exceptions.

On 19 July 2024 the security company CrowdStrike published a content update for its Falcon sensor on Windows. According to its root cause analysis, the update supplied 20 input values where a newer template defined 21. Reading the missing one was an out-of-bounds memory access inside a component running in the operating system kernel, and the machine crashed. No test covered the mismatch. The update went to every eligible sensor at once, and about 8.5 million Windows machines failed and could not restart unaided. Airlines, hospitals and banks were affected for days. Among the changes the company announced were releasing content updates in stages and letting customers control when they receive them.

The update was data, not a program, and data updates had been treated as low-risk and exempt from the staged rollout that code received. The Google Cloud outage in had the same shape with a policy record, and drew the general rule: whatever is applied to all places at once is not contained by any boundary. Configuration, rule sets, machine-learning models, certificates and feature flags all change behavior, and each needs a small first step and a way back.

Keeping it honest

A few practices keep a delivery process trustworthy as it grows.

  • Everything in version control. Not only code: infrastructure definitions, deployment manifests, configuration, alert rules. Production is changed by merging, and the history shows who changed what and why. When an agent in the cluster continuously applies whatever the repository says, in the reconciliation style of , the arrangement is called GitOps.
  • No manual changes. A fix applied by hand on a server is lost at the next deployment and is invisible to everyone else. During an emergency it may be necessary. Afterward it goes back through the pipeline.
  • Release in working hours. Deploy when the people who can fix it are awake and present. A process that is safe only at 3 a.m. on a Sunday is not safe.
  • Mark deployments on dashboards. The first question in any incident is “what changed?”. returns to this.
  • Freeze sparingly. Stopping all changes before a major event is sensible. Long freezes build up a backlog that is released all at once afterward, which is the large, risky change the whole approach is meant to avoid.

In an interview. When a design is otherwise complete, a sentence on how it changes safely stands out. Say that services deploy by rolling update behind readiness checks, that risky changes go to a canary compared against a baseline, and that features are released by flag. If the design has a schema change or a new message format, say it is done in compatible steps because old and new versions overlap. For a global system, say that code and configuration go out one region at a time.

These combine. A mature setup deploys by rolling update inside each cell, gates the first cell with a canary, proceeds in waves, and releases features by flag on top.

Common mistakes

  • Large, infrequent releases. Many changes at once, so that nobody knows which one broke things.
  • Rebuilding for each environment. What ships is not what was tested.
  • Assuming a deployment is instantaneous. Incompatible changes to schemas, messages or caches made in one step.
  • Readiness checks that always pass. The rollout proceeds over a broken version.
  • A canary without a comparison or an automatic stop.
  • Comparing the canary with the whole fleet. Differences in age and warmth drown the signal.
  • Treating configuration and data as safe. Pushing them everywhere at once because they are “not code”.
  • Flags that are never removed. The number of untested combinations grows until one of them fails.
  • An untested rollback. Discovered to be broken on the day it is needed.
  • Contracting too early. Dropping the old column or the old code path while rolling back is still possible.
  • Shadow traffic with side effects.

Key points

  • Changes cause most outages. The defense is to make them small, gradual, observed and reversible.
  • Build one immutable artifact and promote it through every stage. Keep environment differences in configuration, and treat configuration as a change too.
  • Old and new versions always overlap. Every release must work with the one before it, in both directions, across data, messages, caches and APIs.
  • A rolling update replaces copies gradually and judges only whether they become ready. Blue-green switches everyone at once with an instant way back.
  • A canary compares new against old on a small share of real traffic and stops automatically. How long it must run depends on how rare errors are.
  • Feature flags separate deploying code from releasing behavior. Stable hashing gives each user a consistent answer. Remove flags when they are done.
  • The fastest recovery is turning a flag off, then rolling back, then rolling forward. Know in advance what cannot be undone.
  • Apply every kind of change in waves across cells and regions, with bake time between them.

Check yourself

Why is rebuilding from the same commit for production riskier than promoting the artifact that was tested?

A second build can differ from the first without any change to your source: a dependency or base image was updated in between, or the build environment differs. That difference reaches production untested. Promoting one immutable artifact guarantees that what runs is what was tested.

A release changes a JSON field stored in a cache from a number to an object. The rollout is a rolling update. What goes wrong, and how is it avoided?

For some minutes old and new copies both run. New copies write objects that old copies cannot parse, and old copies write numbers that new copies may not expect. Avoid it by putting a version in the cache key so the two never read each other’s entries, or by first shipping a version that reads both forms.

Six copies are updated with a surge of 2 and nothing unavailable. What is the largest number of copies running at once and the smallest number ready?

At most 6 + 2 = 8 copies exist at once, and at least 6 are ready throughout, because an old copy is removed only after a new one is ready. The cluster needs room for two extra copies during the update.

Why is a canary compared with a baseline group of the old version and not with the rest of the fleet?

The rest of the fleet has been running for hours or days, with warm caches, full connection pools and a different mix of traffic. Differences from those causes would be mistaken for effects of the new code. A baseline started at the same time, at the same size and share, differs from the canary only in the version.

A service receives 20 requests a second with a normal error rate of 0.1%. You want to catch a rise to 0.2% with a 10% canary. Roughly how long must it run, and what does that suggest?

About 11,940 requests are needed. At 2 requests a second to the canary, that is about 100 minutes. For a change that small on a service this quiet, a canary is slow, so rely on other checks or accept detecting only larger regressions. The widget gives the same figure.

Why include the flag’s name in the hash that assigns users to a percentage rollout?

Without it every flag would put the same users in its first 10%, so one group would receive every experimental feature at once, and the effects of different flags could not be told apart. Hashing the name with the user ID gives each flag an independent sample while keeping each user’s answer stable.

List the three ways to stop a bad release, fastest first, and one kind of change none of them can undo.

Turn off the feature flag, roll back to the previous artifact, or roll forward with a fix. None of them undoes a destructive schema change such as a dropped column, data already written in a form the old version cannot read, or effects outside the system such as emails sent.

What do the CrowdStrike incident of July 2024 and the Google Cloud incident of June 2025 have in common, and what practice addresses both?

In both, a change that was not ordinary code, a content update in one and a policy record in the other, reached every place at once and triggered a crash in software already running everywhere. Staged rollout with bake time for every kind of change, not only code, would have confined each to the first wave.
