What a storage engine has to do

A storage engine is the component of a database that writes data to durable storage and reads it back. The layers above it parse queries, plan them and manage transactions. The engine’s job sounds simple, and three facts about hardware make it hard.

  • Memory is fast and forgets. Anything held only in RAM is gone after a crash or a power cut.
  • Disks remember and are slow. Even a fast SSD takes around a thousand times longer to read than memory does ().
  • Sequential access is much cheaper than random access. Writing to the end of a file is the cheapest operation a disk offers. Changing small pieces scattered through a large file is the most expensive. The gap was enormous on spinning disks and is smaller, and still real, on SSDs.

Every design in this chapter is a way of getting durability out of the slow device while doing as much work as possible in memory and in sequential order.

The simplest database that works

Start with a key-value store built from two parts. Writes append a record to the end of a file. An in-memory hash table maps each key to the position of its latest record in that file.

This is fast. A write is one sequential append, and a read is one hash lookup and one disk read. Its limits point directly at the two mainstream designs:

  • Every key must fit in memory, since the index lives there.
  • Range queries are impossible. A hash table has no order, so “all keys between a and c” means checking every key.
  • The file grows forever unless a background process rewrites it without the dead records.

To support ranges, the data must be kept sorted. There are two ways to keep data sorted on disk. One keeps a sorted structure and modifies it in place, which is the B-tree. The other never modifies anything, writes small sorted files and merges them later, which is the LSM tree. Before either, one mechanism that both rely on.

The write-ahead log

Suppose an engine changes its data files directly, and the machine loses power halfway through writing a page. The file now contains half of the old page and half of the new. Or the engine has made three of the five changes that belong to one transaction. There is no way to tell afterward what state the file is in.

The solution used by essentially every database is the write-ahead log (WAL). The rule is in the name: before changing anything else, append a description of the change to a log file and make sure it has reached the disk.

This ordering gives the two ACID properties that said depend on the log.

  • Durability. Once the log record is on disk, the change cannot be lost, even though the data file has not been touched. After a crash, the database reads the log from the last known-good point and reapplies everything in it. This is crash recovery.
  • Atomicity. A transaction counts as committed only when its commit record is in the log. During recovery, changes from transactions with no commit record are discarded.

It also makes commits fast. The log is written sequentially, so the only disk work a commit must wait for is one small append. The data files, which need random writes, are updated lazily. Periodically the database performs a checkpoint: it writes all changed pages to the data files, after which the older part of the log is no longer needed and can be recycled.

The step that costs time is forcing the log onto the physical disk. Operating systems buffer writes in memory, and a program must make a specific call, fsync, to wait until the data is truly stored. That call can take from a fraction of a millisecond to several milliseconds. Databases soften the cost with group commit, in which transactions that commit at nearly the same moment share one flush.

In production. Databases let you trade durability for speed here, and the setting is worth knowing. PostgreSQL’s synchronous_commit = off acknowledges commits before the flush, risking the last fraction of a second of transactions in a crash while never corrupting the database. MySQL’s innodb_flush_log_at_trx_commit offers similar choices. Relaxing it is reasonable for data you could afford to lose, such as activity logs, and a mistake for payments.

The log has a second life that matters a great deal later. Because it is a complete, ordered record of every change, shipping it to another machine and replaying it there produces an identical copy of the database. That is how works, and reading the log from outside is the basis of .

B-tree engines: update in place

described the B-tree as a structure for finding rows. As a storage engine it works like this. The database file is divided into fixed-size pages. Each page is a node of the tree. To change a row, the engine finds the page that holds it, modifies the page in memory, logs the change, and eventually writes the whole page back to the same place on disk.

The memory in which pages are held is the buffer pool, and it is the main lever on a database’s performance. When the pages a workload uses often, called its working set, fit in the buffer pool, most reads never touch the disk. When they do not fit, pages are constantly evicted and read back, and performance falls sharply. The first question about a slow database is often how the size of its data compares with its memory.

Updating in place has consequences worth understanding.

  • Reads are efficient and predictable. Each key lives in exactly one place. A lookup descends the tree once.
  • Writes are random. Rows that are inserted in no particular order land on pages all over the file, and each of those pages must eventually be written back whole. Changing 100 bytes can mean writing an 8 KB page.
  • Pages split. When a page is full, half its contents move to a new page. Over time pages end up partly empty and the file is larger than its contents. This is fragmentation.
  • Torn pages must be guarded against. A crash during a page write can leave it half written, and the log entry describing a small change cannot repair a page that is physically broken. PostgreSQL therefore puts a full copy of each page in the log the first time the page changes after a checkpoint. MySQL writes pages twice, first to a separate area.

B-tree engines have been refined for fifty years and run most of the world’s transactional databases: PostgreSQL, MySQL’s InnoDB, SQL Server, Oracle and SQLite.

LSM trees: never update, merge later

The log-structured merge tree (LSM tree) takes the opposite approach. It never changes a file once written. All writes go to memory and to a log, and sorted files are produced and combined in the background.

The parts, in the order a write meets them:

  1. The memtable. An in-memory structure that keeps recent writes sorted by key. A write inserts into it and appends to a write-ahead log for safety, and is then complete. No data file is touched.
  2. Flush. When the memtable reaches a size limit, typically tens of megabytes, it is written to disk in one sequential pass as a sorted, immutable file called an SSTable (sorted string table). A fresh memtable takes over.
  3. Compaction. Flushes produce many files with overlapping key ranges. A background process repeatedly merges files into larger ones, discarding values that have been overwritten.

Two details follow from never modifying files. An update is simply a newer entry for the same key, and the older one is ignored and later discarded. A delete cannot remove anything, so it writes a marker called a tombstone that hides older values until compaction removes both.

Reads are where the bill arrives. A key might be in the memtable or in any of several files, so a read checks them from newest to oldest until it finds the key. Two structures keep this tolerable. Each file has a small index of where key ranges begin, so only one block of the file needs reading. And each file has a Bloom filter, a compact structure that can say “this key is definitely not in this file”, which lets most files be skipped without any disk access. explains how it works.

Two ways to compactLeveled compaction keeps each level as one sorted run with no overlaps, which makes reads fast and space use tight at the cost of rewriting data many times. Size-tiered compaction merges files of similar size and rewrites data less often, which favors writes and uses more space temporarily. Databases let you choose per table, according to whether it is read more or written more.

LSM trees are the engine of write-heavy and very large databases: RocksDB and LevelDB as embeddable libraries, Cassandra, ScyllaDB, HBase and Bigtable, and, through RocksDB or engines modeled on it, the distributed SQL databases CockroachDB, TiDB and YugabyteDB. This is the reason the wide-column stores in can absorb so many writes.

The trade-off between them

Neither design is better. Each moves cost from one place to another, and a useful vocabulary for the costs is amplification: how much more work the engine does than the application asked for.

  • Write amplification: bytes written to disk per byte of data written by the application.
  • Read amplification: disk reads needed to answer one query.
  • Space amplification: bytes on disk per byte of live data.

A known result puts the situation compactly: an engine can be optimized for at most two of fast reads, fast writes and low space use, and the third suffers. B-trees lean toward reads. LSM trees lean toward writes and space.

The practical guidance is short. For a general transactional workload with mixed reads and writes, B-tree engines are the well-trodden path, and they are what the default relational databases give you. Consider an LSM engine when writes dominate, when the data is much larger than memory, or when storage cost matters enough that compression is decisive. Time-series data, event logs, messaging history and metrics are the typical cases.

Common mistake. Using an LSM-based store as a queue. Rows are inserted, read once and deleted, so the table fills with tombstones. Each read then has to step over thousands of deletion markers to find the few live rows, and latency climbs although the table is nearly empty. Among Cassandra users this is a well-known pattern to avoid.

Column files and compression

Both designs above store data by row. explained that analytical systems store data by column instead. At the storage level, a column store writes each column’s values together in large immutable files, which makes strong compression possible because neighboring values are alike.

  • Dictionary encoding replaces repeated values, such as country names, with small integers.
  • Run-length encoding stores “the value BD, 40,000 times” instead of 40,000 copies.
  • Delta encoding stores the differences between successive values, which are tiny for timestamps and counters.

A column that compresses to a tenth of its size is also ten times faster to scan, since reading from disk is the bottleneck. Apache Parquet is the common open file format built this way, and it is what most data lakes are made of. Column files are slow to update one row at a time, so these systems borrow the LSM idea: new data is written in small batches and merged in the background.

Engines that live in memory

Redis, Valkey and Memcached keep the whole data set in RAM, which removes the disk from the read path and is where their speed comes from. Durability, if wanted, uses the same ideas in simpler form. Redis offers two mechanisms that can be combined:

  • Snapshots. Periodically write the entire data set to a file. Compact and fast to load, and everything since the last snapshot is lost in a crash.
  • An append-only file. Log every write, as a write-ahead log does. By default the log is flushed to disk once a second, so a crash loses at most about a second of writes.

This is why a cache can be configured to be reasonably durable, and why the default configuration of an in-memory store should not be trusted with data you cannot rebuild until you have checked which of these is on.

How durable is “durable”?

The write-ahead log protects against the process or machine stopping. It does not protect against everything, and a designer should know the gaps.

  • The disk itself can fail, taking the log and the data with it. Protection against that is a copy on another machine, which is replication.
  • Storage can silently corrupt data. Databases keep checksums on pages to detect it. Detection is not repair. Repair needs another copy.
  • The flush may not do what it says. Some drives and virtual disks acknowledge a flush before the data is safe. In 2018 PostgreSQL developers found that when a flush failed on Linux, the kernel could discard the failed data and report success on the next attempt, so the database believed data was stored that was not. The behavior was fixed, and the episode is a reminder that durability rests on layers the database does not control.
  • Mistakes are durable too. A DELETE without a WHERE clause is faithfully logged and replicated. Only backups, with the ability to restore to a point in time, protect against that. covers them.

For a system design, the working position is that a single machine’s disk gives protection against restarts, replication gives protection against hardware loss, and backups give protection against people and software.

What this means when you design

  • Size memory against the working set. A database whose hot data fits in RAM behaves completely differently from one whose data does not.
  • Insert order matters for B-trees. Keys that increase over time keep writes on a few hot pages. Random keys spread them across the whole tree.
  • Batch your writes. Because of group commit, a thousand rows in one transaction cost little more than one row. A thousand separate commits pay for a thousand flushes.
  • Match the engine to the workload when you have the choice, and know which one your database uses when you do not.
  • Expect background work. Vacuum, checkpoints and compaction all consume disk and CPU. Capacity plans need room for them, and a database running at the limit of its disk has no room to compact.

In an interview. You are rarely asked to design a storage engine. You are asked to justify a database choice, and this is where the justification comes from: “write-heavy and append-mostly, so a store built on an LSM tree”, or “needs transactions and varied reads, so a B-tree engine such as PostgreSQL’s”. If asked how a database survives a crash, the answer is the write-ahead log: changes are logged and flushed before they are acknowledged, and replayed on restart.

Common mistakes

  • Assuming a write is on disk because the call returned. It depends on the flush settings of the database and of everything beneath it.
  • Turning off durable commits to pass a benchmark and leaving it that way for data that matters.
  • Committing row by row in a bulk load.
  • Running with far less memory than the working set and tuning queries when the problem is disk reads.
  • Queue-like delete patterns on an LSM store.
  • Filling the disk. Both designs need free space to do their background work, and LSM compaction needs the most.
  • Treating replication or the log as a backup. Neither undoes a mistaken change.

Key points

  • Storage engines exist to get durability from a slow device while doing most work in memory and in sequential order.
  • The write-ahead log records every change and is flushed before a commit is acknowledged. It provides durability, atomicity and the basis for replication.
  • B-tree engines keep one sorted structure and update pages in place: efficient, predictable reads and random writes.
  • LSM trees buffer writes in memory, flush sorted immutable files and merge them in the background: very fast writes, compact storage, and reads that may consult several files.
  • The costs are write, read and space amplification. No design minimizes all three.
  • The buffer pool is the main performance lever. Know whether your working set fits in memory.
  • One machine’s log protects against restarts. Hardware loss needs replication and mistakes need backups.

Check yourself

A database acknowledges a commit and the server loses power a millisecond later, before the changed page was written to its data file. Is the change lost?

No, provided the commit was flushed to the write-ahead log, which is the normal setting. On restart the database replays the log from the last checkpoint and reapplies the change to the page.

Why can an LSM tree accept writes faster than a B-tree?

A write goes to an in-memory structure and one sequential log append, and nothing else happens at write time. A B-tree must find and modify the specific page for each key, and those pages are scattered, so its disk writes are random. The LSM tree defers the organizing work to background merges that use sequential I/O.

How does an LSM tree handle a delete, given that its files are never modified?

It writes a tombstone, a marker saying the key is deleted. Reads that find the tombstone treat the key as absent. The old value and the tombstone are physically removed later, when compaction merges the files that contain them.

What does a Bloom filter save in an LSM read?

Disk reads of files that do not contain the key. The filter is small enough to keep in memory and can say for certain that a key is absent from a file, so the read skips that file entirely.

A bulk import of a million rows takes an hour when each row is committed separately and a minute as batches of a thousand. Why?

Each commit waits for the log to be flushed to disk. A million commits means a million flushes. Batching reduces that to a thousand flushes for the same data, and the rest of the work is cheap by comparison.

Your database has replicas in three zones. Do you still need backups?

Yes. Replication copies every change, including a mistaken delete or a bug that corrupts data, to all replicas within seconds. Only a backup that can be restored to a time before the mistake recovers from it.
