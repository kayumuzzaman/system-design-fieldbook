The server cannot speak first

Everything in follows one pattern: the client sends a request and the server sends a response. The server never starts the exchange. In most cases it could not even if it wanted to, because the client sits behind NAT and firewalls that only allow connections going out ().

That is a poor fit for anything where news originates on the server. When Ben comments on Ana’s photo, the server knows at once and Ana’s phone does not. There are only two ways out. Either the client keeps asking, or the client opens a connection and leaves it open so the server has a path to send on. Every technique in this chapter is a variation on one of those two.

Before choosing a technique, decide how fresh the data has to be. “Real time” in this chapter means soft real time: fast enough that a person perceives it as immediate, with no hard deadline. The requirement varies by two orders of magnitude between features, and the cheaper techniques are good enough more often than people expect.

FeatureDelay people tolerateDirection of data
Dashboard, order status, build status5 to 60 secondsServer to client
Notifications, live scores, feeds1 to 5 secondsServer to client
Chat, typing indicators, presenceUnder 1 secondBoth ways
Shared cursors, collaborative editingAbout 100 msBoth ways, frequent
Voice, video, fast gamesTens of milliseconds, and late data is uselessBoth ways, continuous

These are working figures for design, not measured thresholds. The two columns together pick the technique: the first tells you how much machinery is justified, and the second tells you whether a one-way channel is enough.

Short polling

The simplest approach is to ask on a timer: every few seconds the client sends an ordinary request, “anything new since I last asked?”, and the server answers at once, usually with “no”.

It needs nothing special. Any HTTP server, load balancer and cache handles it, the server keeps no per-client state, and a client that vanishes costs nothing. The price is paid in two places.

  • Delay. An event waits for the next poll. With a 5-second interval the average wait is 2.5 seconds and the worst is 5.
  • Wasted work. Most answers are empty. With 100,000 clients polling every 5 seconds the server handles 20,000 requests per second around the clock. If each user has something new about once a minute, 11 polls out of 12 return nothing.

Shortening the interval reduces the delay and raises the waste in exact proportion. That trade is the whole design space of polling.

Two refinements make it cheaper. First, make the poll a conditional request: the client sends the ETag it last saw and the server answers 304 Not Modified with no body when nothing changed (). Second, if the answer is the same for many users, such as a match score, let a CDN cache it for a second or two. Then a million viewers cost the origin about one request per second per edge location instead of a million.

In an interview. Polling is a respectable answer when updates are infrequent, a delay of several seconds is acceptable, or the data is shared and cacheable. Saying “polling every 10 seconds is enough here, and it keeps the servers stateless” shows more judgment than reaching for WebSockets by reflex.

Long polling

Long polling keeps the request-response shape and changes one thing: when the server has nothing new, it does not answer. It holds the request open until something happens or a timeout expires. The client asks again as soon as it gets an answer.

Delivery is now immediate, and empty responses happen only once per timeout instead of once per interval. For years this was how chat worked on the web, and it remains the fallback when nothing better gets through a network.

It is harder than it looks, for three reasons.

  • The server now holds state. Each waiting request occupies a connection and some memory, and something must wake the right request when an event arrives. A server built around one thread per request cannot hold tens of thousands of these.
  • Timeouts must be coordinated. Every proxy and load balancer on the path closes connections it considers idle. AWS’s Application Load Balancer, for example, does so after 60 seconds by default. The server’s hold time must be shorter than the shortest of these, so 25 to 30 seconds is typical.
  • Events can fall in the gap. Between receiving one answer and sending the next request, the client is not listening. The client must therefore say where it got to (“give me everything after event 4101”) and the server must keep recent events long enough to replay them.

The third point applies to every technique that follows. A connection can always drop, so a design that only works while the connection stays up is incomplete.

Server-sent events

Server-sent events (SSE) take long polling one step further: the server answers once and never finishes. The response has the type text/event-stream, and the server writes a small block of text to it each time something happens. It is plain HTTP, so it passes through the same infrastructure as any other response.

retry: 5000

id: 4101
event: like
data: {"photoId": 871, "by": "ben"}

: keep-alive

id: 4102
event: comment
data: {"photoId": 871, "text": "Great shot"}

Each event is a few field: value lines ended by a blank line. A line starting with a colon is a comment, which servers send every 15 to 30 seconds so that intermediaries do not see an idle connection.

The browser side is a built-in object called EventSource, and it does two useful things without being asked. It reconnects when the connection drops, after the delay given by retry. And on reconnecting it sends a Last-Event-ID header containing the last id it saw, so the server can resume from the right place. The gap problem from long polling is solved by the protocol.

import { createServer, type ServerResponse } from "node:http";

const clients = new Set();

createServer((req, res) => {
  if (req.url !== "/events") { res.writeHead(404).end(); return; }
  res.writeHead(200, {
    "Content-Type": "text/event-stream",
    "Cache-Control": "no-cache",
    "X-Accel-Buffering": "no",          // ask nginx to pass bytes through at once
  });
  res.write("retry: 5000\n\n");
  clients.add(res);
  req.on("close", () => clients.delete(res));
}).listen(8080);

export function publish(id: number, type: string, data: unknown) {
  const frame = `id: ${id}\nevent: ${type}\ndata: ${JSON.stringify(data)}\n\n`;
  for (const res of clients) res.write(frame);
}

setInterval(() => { for (const res of clients) res.write(": keep-alive\n\n"); }, 20_000);

// In the browser:
const source = new EventSource("/events");
source.addEventListener("like", (e) => showLike(JSON.parse(e.data)));

A real endpoint would also read Last-Event-ID and replay what the client missed. The limits of SSE are these:

  • One direction only. The client sends data with ordinary requests on the side. For notifications, feeds, progress bars and tickers, that is all you need.
  • Text only. Binary data has to be encoded as text, which makes it about a third larger.
  • Six connections on HTTP/1.1. Browsers open at most six connections per site over HTTP/1.1, and each event stream uses one for as long as it lives, so a user with several tabs open can exhaust them. Over HTTP/2 and HTTP/3 a stream is one of many on a shared connection (100 at once by default) and the problem goes away.
  • No custom headers from EventSource. It sends cookies but cannot add an Authorization header. Reading the same stream format with fetch removes that limit, at the cost of writing the reconnection logic yourself.
Why AI chat apps stream this wayWhen a language model writes an answer a few words at a time, the application needs to send each piece to the browser as it is produced. That is one-way, text, and over ordinary HTTP, which is exactly what SSE was built for. Most model APIs stream their output in the event-stream format. returns to this.

Common mistake. An event stream that works on a laptop and delivers nothing in production until the connection closes is almost always being buffered. A proxy or a compression step in the path is collecting the response to send it in one piece. Turn off response buffering for that route, and if you compress the stream, flush after every event.

WebSocket

A WebSocket is a long-lived connection on which either side can send a message at any time. It starts as an HTTP request asking to switch protocols. If the server agrees, the same TCP connection stops speaking HTTP and carries WebSocket messages from then on.

GET /feed HTTP/1.1
Host: rt.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

Starting as HTTP is what lets WebSockets use ports 80 and 443 and pass through infrastructure built for the web. After the 101 response, messages travel in frames with only a few bytes of overhead each, and a message can be text or binary. The URL scheme is ws://, or wss:// over TLS, and in practice you should always use the second. Besides the privacy, older proxies that do not understand the upgrade tend to break unencrypted WebSockets and leave encrypted ones alone because they cannot see inside.

A WebSocket gives you far less than HTTP does. It is a pipe for messages, and everything else is yours to design:

  • No request and response. If you want replies matched to requests, you add a message ID and match them yourself.
  • No status codes, caching, or content negotiation. You define the message format and the errors.
  • No automatic reconnection. Your client code must notice the drop, wait, reconnect and catch up.
  • No headers from the browser. The browser API cannot set an Authorization header. Cookies are sent, so cookie sessions work, but then the server must check the Origin header, or any website the user visits can open a socket using their cookies. The alternative is to send a short-lived token as the first message.
  • No backpressure in the standard browser API. If the server sends faster than a client can read, data piles up in buffers. The server has to watch for slow clients and decide what to do about them.

Libraries such as Socket.IO fill some of these gaps with reconnection, acknowledgements and named rooms. They do it by defining their own protocol on top, so both ends must use the same library. A plain WebSocket client cannot talk to a Socket.IO server.

Detecting dead connections

As explained, a TCP connection whose other end has vanished can look healthy for a long time. A phone that drives into a tunnel sends no goodbye. A server holding many connections must find the dead ones, or it will slowly fill with them. The WebSocket protocol has ping and pong frames for this purpose: the server pings on a timer, a live client answers automatically, and a client that missed the last ping is dropped.

import { WebSocketServer, type WebSocket } from "ws";

const wss = new WebSocketServer({ port: 8080 });
const alive = new WeakMap();

wss.on("connection", (ws) => {
  alive.set(ws, true);
  ws.on("pong", () => alive.set(ws, true));
});

setInterval(() => {
  for (const ws of wss.clients) {
    if (!alive.get(ws)) { ws.terminate(); continue; }   // no pong since the last ping
    alive.set(ws, false);
    ws.ping();
  }
}, 30_000);

The interval does double duty. It must be shorter than the idle timeout of every load balancer and NAT device in the path, so the traffic also keeps the connection from being closed as idle. Heartbeats are not free at scale: a million connections pinged every 30 seconds is about 33,000 pings per second of pure overhead, and on phones each one wakes the radio. Longer intervals save battery and detect failure more slowly.

Reconnecting without a stampede

The client’s half of the bargain is to reconnect, and how it does so matters more than it seems. When a server holding 500,000 connections restarts, 500,000 clients notice within the same second. If they all reconnect immediately, the surviving servers receive half a million TLS handshakes at once, some fail under the load, and their clients join the crowd. The fix is the same as for any retry: wait a random amount of time, and wait longer after each failure.

function connect(attempt = 0, lastSeq = 0): void {
  const ws = new WebSocket(`wss://rt.example.com/feed?after=${lastSeq}`);

  ws.onopen = () => { attempt = 0; };

  ws.onmessage = (e) => {
    const msg = JSON.parse(e.data);
    lastSeq = msg.seq;                                  // remember how far we got
    render(msg);
  };

  ws.onclose = () => {
    const ceiling = Math.min(30_000, 1_000 * 2 ** attempt);
    const delay = Math.random() * ceiling;              // anywhere from 0 to the ceiling
    setTimeout(() => connect(attempt + 1, lastSeq), delay);
  };
}

Spread evenly over 30 seconds, a million reconnections arrive at about 33,000 per second instead of a million in one. The after parameter does the job that Last-Event-ID does in SSE: the server replays whatever the client missed while it was away. covers backoff and jitter in general.

WebSockets on HTTP/2 and HTTP/3

The handshake above is HTTP/1.1, and it takes over a whole TCP connection. Later standards (RFC 8441 for HTTP/2 and RFC 9220 for HTTP/3) let a WebSocket run as one stream on a connection shared with ordinary requests. Support varies between browsers, servers and proxies, so do not design around it. Assume one TCP connection per WebSocket when you plan capacity.

WebTransport

WebTransport is the newest option. It runs over HTTP/3, and so over QUIC (), and it exposes what QUIC can do that TCP cannot:

  • Many independent streams on one connection. A lost packet delays only the stream it belonged to, so one slow message does not hold up the rest. A WebSocket is a single ordered stream, with the head-of-line blocking that implies.
  • Datagrams, which are small messages sent without any guarantee of arrival or order. For a player’s position in a game or a cursor on a shared canvas, the newest value replaces the old one, and retransmitting a stale one is wasted effort.

It became usable across all major browsers in March 2026, when Safari 26.4 shipped it. That is recent. Server libraries, proxies and managed load balancers are still catching up, and some networks block UDP altogether. For now, treat WebTransport as an upgrade for applications that need datagrams or independent streams, and keep a WebSocket fallback. For ordinary chat and notifications it offers little that a WebSocket does not.

WebRTC: when the data should not pass through you

For voice and video, the path through a server is itself the problem. Every extra hop adds delay, and a server relaying video for every call needs a great deal of bandwidth. WebRTC (web real-time communication) lets two browsers or apps send audio, video and arbitrary data straight to each other over UDP, encrypted, with the codecs and loss handling built into the browser.

The difficulty is that neither peer can simply connect to the other, since both are usually behind NAT. Three pieces solve that:

  • Signaling. Before they can talk directly, the peers must exchange descriptions of what they support and where they might be reachable. WebRTC does not define how. You carry these messages over any channel you already have, usually a WebSocket to your own server.
  • STUN. A small public server that tells a peer what its address looks like from the outside, so it can offer that address to the other side.
  • TURN. A relay for the cases where no direct path can be made, typically behind strict corporate firewalls. A relayed call is the expensive case, because all its media passes through your server and you pay for the bandwidth. Plan capacity for a minority of calls to need it.

The procedure that tries candidate paths and picks one that works is called ICE. Direct connections suit calls between two people. In a group call each participant would have to upload their video once for every other participant, and a home or mobile uplink runs out after a handful. Group calls therefore use a server after all: a selective forwarding unit (SFU) receives one stream from each participant and forwards it to the others without decoding it, choosing a lower-quality version for those on weak connections. looks at media delivery in more depth.

Webhooks: push between servers

Everything so far assumed a client that cannot be reached. When the receiver is a server with a public address, pushing is simple: the sender makes an HTTP request to it. A webhook is that arrangement turned into a product feature. You give a provider a URL, and the provider sends a POST to it whenever something happens: a payment succeeds, a commit is pushed, a delivery fails. It replaces polling the provider’s API to ask whether anything changed.

A webhook endpoint is a public URL that accepts instructions from the internet, so it has to be built defensively. Four rules cover most of it.

  1. Verify the signature. Anyone can send a POST to your URL. The provider signs each request with a secret you share, and you recompute the signature before believing a word of the body. Sign and verify the raw bytes, because parsing the JSON and serializing it again changes the bytes and breaks the check.
  2. Check the timestamp. A signed request captured today could be sent again next month. Including the time in the signed data and rejecting anything older than a few minutes closes that door.
  3. Reply quickly, work later. Providers wait only a few seconds for an answer. If your handler does slow work first, a busy moment causes timeouts, the provider retries, and the retries add load to a system that is already struggling. Verify, put the event on a queue (), and return 200.
  4. Expect duplicates and disorder. Retries mean the same event can arrive twice, and events can overtake each other. Record the IDs of events you have processed and skip repeats. For ordering, either compare a version or timestamp inside the event, or treat the webhook as a hint and fetch the current state from the provider’s API.

The fourth rule is delivery “at least once”, which is the subject of . The signature scheme below follows the Standard Webhooks specification, an open convention used by a growing number of providers. Others, such as Stripe and GitHub, use their own header names with the same underlying idea.

import { createHmac, timingSafeEqual } from "node:crypto";

const TOLERANCE_SECONDS = 5 * 60;

export function verifyWebhook(
  rawBody: string,
  headers: Record,
  secret: Buffer,
): boolean {
  const id = headers["webhook-id"];
  const timestamp = headers["webhook-timestamp"];
  const signatures = headers["webhook-signature"];
  if (!id || !timestamp || !signatures) return false;

  const age = Math.abs(Date.now() / 1000 - Number(timestamp));
  if (!(age <= TOLERANCE_SECONDS)) return false;        // also rejects a non-numeric timestamp

  const expected = createHmac("sha256", secret)
    .update(`${id}.${timestamp}.${rawBody}`)
    .digest();

  // The header may hold several signatures while a secret is being rotated.
  return signatures.split(" ").some((entry) => {
    const [version, value] = entry.split(",");
    if (version !== "v1" || !value) return false;
    const given = Buffer.from(value, "base64");
    return given.length === expected.length && timingSafeEqual(given, expected);
  });
}

The comparison uses timingSafeEqual instead of === because an ordinary comparison stops at the first byte that differs, and the time it takes can leak how much of a forged signature was right. explains HMAC.

If you are the one sending webhooks, the obligations reverse. You need a queue of deliveries, retries with backoff that continue for days, a way for customers to see and replay failed deliveries, and automatic disabling of endpoints that have been dead for a long time. You also need to remember that you are making requests to URLs chosen by strangers. A customer who registers http://10.0.0.5/admin as their webhook URL is asking your servers to call something inside your own network. This attack is called server-side request forgery, and covers the defenses.

Mobile and web push

A phone app that is not on screen cannot hold a connection open. The operating system suspends it to save battery. To reach it, you go through the platform: Apple Push Notification service (APNs) for Apple devices, Firebase Cloud Messaging (FCM) for Android, and the Web Push standard for browsers. Each device keeps a single connection open to its platform’s servers, shared by every app on it. Your server sends a message to the platform, addressed with a device token that the app obtained and registered with you, and the platform delivers it.

Three properties shape how you use push.

  • It is best effort. Delivery is not guaranteed and not timed. If a device is offline, the platform may keep only the most recent message for it, and users can switch notifications off entirely.
  • Payloads are small. Both APNs and FCM limit a message to about 4 KB.
  • Tokens change. Reinstalling the app or restoring a phone produces a new token, and the old one starts returning errors. Your token table needs pruning based on those errors.

The first two lead to one pattern: treat a push as a tap on the shoulder. It says “there is something new”, and the app fetches the real data from your API when it wakes. The data of record lives on your servers, and a lost push costs only some delay. designs a full notification system around this.

A short procedure covers most decisions:

  1. If a delay of several seconds is acceptable, or the data is shared by many users and can be cached, poll.
  2. If only the server needs to push, use SSE. It is the least machinery that delivers immediately.
  3. If the client also sends frequently, or you need binary messages, use a WebSocket.
  4. If late data is worthless, as in fast games and live media, look at WebTransport or WebRTC.
  5. If the receiver is another server, use a webhook. If it is an app that may not be running, use push as well as whatever you use while it is open.

Real products combine several. A chat app typically uses a WebSocket while it is open, push notifications when it is not, an ordinary HTTP API to load history, and webhooks to notify integrations.

Scaling persistent connections

The techniques from long polling onward share one property that changes the architecture: the server holds a connection for each client, for minutes or hours. argued that stateless servers are easy to scale because any server can handle any request. A server holding connections is the opposite. A message for Ana can only be delivered by the one machine that holds Ana’s connection.

How many connections fit on one server

More than intuition suggests. An idle connection consumes memory and almost no CPU. A server is not limited to 65,535 connections by port numbers either: that limit applies to connections between one pair of addresses, and each client has a different address, so the limit that matters is memory and file descriptors. If each connection costs about 10 KB across kernel buffers and application state, a million of them need about 10 GB. WhatsApp reported more than 2 million connections on a single server as long ago as January 2012.

What you can hold and what you should hold are different numbers. The practical limits are these:

  • Work per message, not idle count. A million quiet connections are cheap. A million connections each receiving ten messages a second is ten million writes a second.
  • Blast radius. When a server holding a million connections fails, a million clients reconnect at once. Many deployments cap each server well below its capacity for this reason.
  • Operating system settings. Defaults for open files and socket buffers are far too low and need raising.

In production. Measure the memory cost per connection for your own stack before sizing anything. It varies by more than a factor of ten between runtimes and libraries, and with settings such as per-connection compression, which can add tens of kilobytes to each one.

The gateway tier and the backplane

The standard structure splits the system in two. A tier of connection gateways does nothing but hold connections, authenticate them and move bytes. The application logic stays in ordinary stateless services behind them. The remaining problem is routing: when a service wants to tell Ben something, how does the message reach the gateway that holds Ben’s connection?

There are two common answers, and large systems often use both.

  • Publish and subscribe. Each gateway subscribes, on a shared message bus, to the topics its connected users care about: one per conversation, document or user. A service publishes to the topic, and the bus delivers to every gateway that subscribed. Services never need to know which gateway holds whom. Redis pub/sub and NATS are common choices for the bus.
  • A connection registry. A fast shared store maps each user to the gateway holding their connection, written on connect and removed on disconnect. A service looks up the gateway and sends to it directly. This is more efficient for messages aimed at one user, and it needs care around stale entries when a gateway dies without cleaning up.

Slack’s published design is a clear example. Gateway servers in several regions hold the WebSockets and each user’s subscriptions. Behind them, channel servers each own a subset of channels, assigned by consistent hashing on the channel ID ( explains the technique). A message goes to the channel server for its channel, which sends it to every gateway with a subscriber. Slack states that this delivers messages worldwide in about 500 ms.

A connection is not a queue

The most important design rule in this chapter is this: never let the live connection be the only place a message exists. Connections drop, phones go into pockets, and gateways restart. If the server sends a message into a socket and forgets it, any of those events loses the message.

The dependable pattern is the one in . Write the message to durable storage first, and give it a sequence number within its conversation. Then push it over the connection as an optimization. When a client connects or reconnects it says “I have everything up to 4101”, and the server sends the rest from storage. With that in place, the push path can fail in any way it likes and the result is only delay. The sequence number also lets the client detect a gap and put messages in the right order, which the network alone does not guarantee once several servers are involved. builds a complete system this way.

Operating a connection tier

Long-lived connections break several habits formed on request-response systems.

  • Load balancing happens once. A load balancer chooses a server when the connection opens and has no say afterward. After you add servers, the new ones stay empty until clients reconnect. Balance on the number of open connections, not on request counts, and see for the options.
  • Deployments disconnect people. Replacing a gateway closes every connection on it. Drain gradually: stop accepting new connections, then close the existing ones in small batches over several minutes so their reconnections are spread out.
  • Slow consumers need a policy. A client on a poor connection reads more slowly than you write. Unbounded per-connection buffers will eventually exhaust the gateway’s memory. Put a limit on each buffer and decide what happens at the limit: drop the oldest messages, merge updates so that only the latest state is sent, or close the connection and let the client resynchronize.
  • Fan-out can dwarf input. One message to a room of 100,000 people becomes 100,000 writes. For very large audiences, batch updates and send them at a fixed rate, or move that audience to polling a cached endpoint.
  • Presence is expensive. “Who is online” changes every time anyone connects or disconnects, and each change interests many people. Send presence only for the users someone is currently looking at, and tolerate it being a few seconds stale.
  • Authorization does not end at the handshake. A connection authenticated an hour ago may belong to a user who has since been removed from the conversation. Check permissions when subscribing to each topic, and have a way to close connections when access is revoked or a token expires.

Common mistakes

  • Choosing WebSockets by default. If only the server pushes, SSE gives you reconnection, resumption and ordinary HTTP infrastructure for free. If a few seconds of delay is fine, polling gives you stateless servers.
  • No resume protocol. A client that reconnects and simply starts listening again has silently lost everything sent while it was away.
  • Reconnecting immediately and without jitter. It turns every brief outage into a self-inflicted flood.
  • No heartbeat, or one longer than the idle timeout. Connections are closed by intermediaries, or dead ones accumulate on the server.
  • Doing slow work inside a webhook handler. Timeouts cause retries, and retries cause more timeouts.
  • Trusting a webhook body without verifying its signature. The URL is public, and anyone can send to it.
  • Treating a push notification as delivery. It may arrive late or never. The app must be able to fetch everything it needs from the API.

Key points

  • A server cannot start a conversation with a browser or app. Either the client keeps asking, or it opens a connection and holds it.
  • Decide the tolerable delay first. Polling with conditional requests is stateless and is enough for many features.
  • Server-sent events are the simplest immediate push from server to client, with reconnection and resumption built in.
  • A WebSocket carries messages both ways over one connection and gives you nothing else. Heartbeats, reconnection with jitter, resumption and backpressure are yours to build.
  • WebTransport adds independent streams and unreliable datagrams over HTTP/3. WebRTC sends media directly between peers.
  • Webhooks push between servers. Verify the signature, reply fast, queue the work, and expect duplicates.
  • Persistent connections make servers stateful. Separate a gateway tier that holds connections from stateless services, and connect them with pub/sub or a registry.
  • Store first, then push. The connection is a fast path for delivery and is never the record.

Check yourself

A sports site shows the same live score to two million viewers, and a delay of two seconds is acceptable. What would you use?

Polling a cacheable endpoint. Every viewer sees the same data, so a CDN can cache the response for one or two seconds and the origin answers roughly once per second per edge location. Holding two million connections open would be far more expensive and would add nothing the requirement asks for.

Your event stream works locally but in production the browser receives nothing for a minute and then everything at once. What is the likely cause?

Something between the server and the browser is buffering the response: a reverse proxy with response buffering enabled, or compression that waits for more data before flushing. Disable buffering for that route and flush after each event.

Why should a WebSocket client add randomness to its reconnection delay?

When a server fails, all of its clients notice at the same moment. Without randomness they all reconnect at the same moment too, and again after each identical backoff, which can overload the remaining servers. Random delays spread the reconnections over time.

A payment provider sends your endpoint the same “payment succeeded” event twice. Is something broken?

No. Providers retry when they do not receive a timely success response, so duplicates are normal. The handler should record the event ID after processing it and skip any event whose ID it has already seen.

A user sends a chat message while the recipient’s phone is in a tunnel. Describe how the recipient still gets it.

The service wrote the message to durable storage with a sequence number before trying to push it. The push fails or goes nowhere. When the phone reconnects it tells the server the last sequence number it has, and the server sends everything after that from storage. If the app is not open, a push notification prompts it to fetch.

You add ten gateway servers to a tier of ten, and an hour later the new ones hold almost no connections. Why?

A load balancer only places a connection when it is opened. Existing connections stay where they are, so new servers fill only as clients reconnect. To rebalance, close connections on the old servers gradually.
