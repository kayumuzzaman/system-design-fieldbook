One request, nine steps

Take the photo app from the previous chapter and assume it lives at https://www.example.com. You type https://www.example.com/photos/42 into a browser and press Enter. Before any of your application code runs, the browser has to find out which machine to talk to, open a connection to it, and agree on how to encrypt the conversation. After your code runs, the answer has to travel back and be turned into pixels.

shows the whole trip. The rest of the chapter walks through it one step at a time. For each step you will see what happens, how long it takes, and what it looks like when it fails.

Before step 1: reading the address

The address you typed is a URL (uniform resource locator), and each of its parts answers a different question for a different machine.

The scheme https says to speak HTTP over an encrypted connection. The host names the machine. The port selects one program on that machine, and is usually left out because https implies port 443 and http implies port 80. The path and query are passed to the server, which decides what they mean. The fragment after # is used by the browser alone, typically to scroll to a section.

HTTPS is now the assumed defaultChrome 154, released on 22 September 2026, turns on “Always Use Secure Connections” for everyone, so the browser asks permission before the first visit to a public site that lacks HTTPS. By Google’s count about 95% of Chrome navigations already use HTTPS. Design every public endpoint for HTTPS only.

If you type only example.com, the browser fills in the rest. Modern browsers try https:// first. A site can also tell browsers to refuse plain HTTP for it in future, using a response header called HSTS (HTTP Strict Transport Security).

Step 1: find the address with DNS

Machines on the internet are reached by numeric IP addresses such as 203.0.113.10, and people prefer names. The Domain Name System (DNS) is the distributed database that maps one to the other. No single server holds the whole mapping. It is split into a hierarchy, and a lookup walks down that hierarchy from the right-hand end of the name.

The browser first checks whether it already knows the answer, in its own cache or the operating system’s. If not, it asks a recursive resolver, a server run by your internet provider or by a public service, whose job is to chase the answer on your behalf.

  1. Your device asks the resolver: what is the address of www.example.com?
  2. The resolver asks a root server. Root servers do not know the answer.
  3. The root server replies with a referral: these servers handle everything ending in .com.
  4. The resolver asks one of the .com servers, called top-level domain (TLD) servers.
  5. The TLD server replies with another referral: these are the name servers for example.com.
  6. The resolver asks one of those. They are authoritative: they hold the records the domain’s owner published.
  7. The authoritative server replies with the address and a time to live (TTL), the number of seconds the answer may be reused.
  8. The resolver stores the answer for that long and returns it to your device, which caches it too.
Thirteen names, about two thousand machinesThere are 13 root server names, a to m.root-servers.net, run by 12 organizations. Each name is served from many places at once by a routing technique called anycast. The operators’ site, root-servers.org, listed about 1,950 instances in December 2025.

That is four round trips for one name, which sounds slow. In practice the resolver almost always has the .com referral cached, and for a popular site it has the final answer too, so a typical lookup is one short exchange with the resolver or none at all. Caching is what makes DNS fast, and it is also why a DNS change does not take effect everywhere at once: every cache keeps the old answer until its TTL runs out.

A DNS answer is a record, and there are several types. You will meet these often:

You can watch the whole walk yourself. The dig tool, with +trace, plays the resolver’s part and prints every referral:

# Follow the delegation chain from the root, as a resolver would
dig +trace www.example.com

In production. DNS is a dependency of everything, including your own internal services, and it is easy to forget because it nearly always works. In October 2025 a fault in the automation that manages DNS records for Amazon DynamoDB left that service’s regional endpoint in northern Virginia with no addresses at all. Clients could not find a healthy service, and the effects spread to other AWS services that depend on it for about fourteen and a half hours. returns to this incident.

DNS does more than look up one fixed address. An authoritative server can give different answers to different askers, which makes it the first place traffic is steered: toward the nearest region, away from a data center that is down, or 5% to a new version. covers this in full.

Between the steps: addresses and packets

With an address in hand, the browser can send data. On the internet, data travels as packets: small chunks, typically up to about 1,500 bytes, each stamped with the address it came from and the address it is going to. No machine along the way knows the whole route. Each router looks at the destination address and forwards the packet one hop closer. Packets of the same request may take different routes, arrive out of order, or not arrive at all. The Internet Protocol (IP) promises only a best effort.

IPv6 reached halfGoogle measures the share of its users who reach it over IPv6. That share passed 50% for the first time on 28 March 2026, eighteen years after measurement began. It still dips below half on working days, when more traffic comes from corporate networks. In practice a public service should answer on both protocols.

There are two versions of IP in use. IPv4 addresses are 32 bits, written as four numbers like 203.0.113.10, which allows about 4.3 billion addresses. That is fewer than the number of devices now connected, so addresses are shared and rationed. IPv6 addresses are 128 bits, written in hexadecimal like 2001:db8::10, and are in no danger of running out. explains how the two coexist.

Step 2: open a connection

An application wants more than best effort. It wants every byte to arrive, once, in order. The Transmission Control Protocol (TCP) provides that on top of IP by numbering bytes, acknowledging what arrives, and resending what does not.

Before TCP carries data, both sides exchange three small packets, known as the three-way handshake. The client sends SYN (“I want to talk, my numbering starts here”), the server answers SYN-ACK (“agreed, mine starts here”), and the client replies ACK. The client can send data together with that final packet, so the handshake costs one round trip: the time for a packet to travel there and for the reply to come back.

Round-trip time is set mostly by distance. Light in optical fiber covers roughly 200 kilometers per millisecond, so a server 3,000 km away cannot be reached and heard from in less than about 30 ms, and real routes are longer than straight lines. Every round trip in this chapter costs that much, which is why so much engineering goes into removing round trips and into moving servers closer to users.

The alternative to TCP is UDP (User Datagram Protocol), which adds almost nothing to IP: no handshake, no resending, no ordering. For a long time that made UDP the choice for things like video calls and DNS queries, and TCP the choice for everything else. That changed with QUIC, a newer transport that runs on top of UDP and rebuilds reliability there, with encryption included. It appears in the next step.

Step 3: agree on encryption with TLS

A TCP connection is a plain pipe. Anyone on the path, such as a café’s Wi-Fi router, could read or alter what passes through it. Transport Layer Security (TLS) wraps the pipe so that three things hold: nobody else can read the contents, nobody can change them unnoticed, and the browser knows it is talking to the real example.com.

The third property rests on a certificate. During the TLS handshake the server presents a certificate that binds its name to a public key, signed by a certificate authority that the browser already trusts. The server then proves it holds the matching private key. In the same exchange, both sides derive fresh encryption keys that are used for this connection only.

With the current version, TLS 1.3, the handshake takes one round trip. Added to TCP’s one, that is two round trips before the browser can send its actual request.

QUIC does the transport handshake and the TLS handshake at the same time, so a new connection is ready after one round trip. When the browser has talked to the server before, QUIC and TLS 1.3 can also resume with stored keys and send the request in the very first packet, a mode called 0-RTT. It is restricted to requests that are safe to repeat, because an attacker who captured that first packet could send it again.

Two changes to TLS are in progress as this is written, and both affect how systems are run.

  • Certificates are getting shorter-lived. The industry body that sets the rules, the CA/Browser Forum, voted in April 2025 to cut the maximum lifetime of a public certificate in stages: 200 days from 15 March 2026, 100 days from 15 March 2027, and 47 days from 15 March 2029. It had been 398 days. Renewing by hand does not survive that schedule. Certificate renewal has to be automated, usually with the ACME protocol that Let’s Encrypt introduced.
  • Key exchange is moving to post-quantum algorithms. A future quantum computer could break the mathematics behind today’s key exchange, and traffic recorded now could be decrypted then. Browsers and large providers have therefore switched to a hybrid exchange that combines the existing method with a quantum-resistant one, ML-KEM. In September 2026 Cloudflare reported that about 70% of the browser-generated traffic reaching its network already used it.

Common mistake. Treating a certificate as something you install once. An expired certificate takes a site down as completely as a crashed server, and it does so on a date that was known in advance. Monitor expiry dates and automate renewal for every certificate, including the ones on internal services.

Step 4: send the request with HTTP

Now the browser can say what it wants. The language is HTTP (Hypertext Transfer Protocol), a request-and-response protocol. The client sends a request naming a method and a path, with headers carrying extra information. The server sends back a status code, its own headers, and usually a body.

GET /photos/42?size=large HTTP/1.1
Host: www.example.com

HTTP/1.1 200 OK

The method says what kind of action is wanted. GET reads, POST creates or triggers something, PUT replaces, PATCH changes part, DELETE removes. The first digit of the status code tells you the class of outcome:

CodesMeaningExamples you will see daily
2xxIt worked200 OK, 201 Created, 204 No Content
3xxLook elsewhere, or use your copy301 Moved Permanently, 304 Not Modified
4xxThe client’s request was wrong400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 429 Too Many Requests
5xxThe server failed500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout

The split between 4xx and 5xx matters for operations. A rise in 5xx responses means your system is failing. A rise in 4xx usually means a client is misbehaving. Alerts and availability targets are normally built on the 5xx rate.

HTTP itself is stateless: each request stands alone and the protocol remembers nothing between them. Anything that must persist, such as who is logged in, is carried by the client on every request, typically in a cookie or a token. That property is what later allows any one of fifty identical servers to handle any request, and builds on it.

Three versions in use at once

The meaning of HTTP, its methods, headers and status codes, has been stable for decades. What has changed is how requests are packed onto the connection, and each version fixed a specific bottleneck in the one before.

HTTP/1.1HTTP/2HTTP/3
Standardized199720152022
Runs onTCPTCPQUIC, over UDP
Format on the wireTextBinary framesBinary frames
Requests per connectionOne at a timeMany at once, as interleaved streamsMany at once, as independent streams
If one packet is lostThat connection’s request waitsEvery stream on the connection waitsOnly the stream it belonged to waits
Round trips to set up2 with TLS 1.32 with TLS 1.31, or 0 on a repeat visit
Survives a network changeNoNoYes: connections are not tied to an IP address

With HTTP/1.1 a connection carries one request at a time, so browsers open up to six connections per site and still queue requests behind each other. HTTP/2 sends many requests over a single connection at once. That removed the queueing in HTTP, and exposed the same problem one layer down: TCP delivers bytes strictly in order, so one lost packet stalls every request sharing the connection until it is resent. This is called head-of-line blocking. HTTP/3 moves to QUIC, where each stream is ordered separately and a lost packet delays only its own stream.

How a browser learns about HTTP/3A URL does not say which HTTP version to use. The browser usually connects with HTTP/2 first, and the server’s response carries an Alt-Svc header saying “I also speak HTTP/3 here”. The HTTPS DNS record lets the browser know before it connects at all.

All three are in everyday use. In October 2026 the survey firm W3Techs found HTTP/3 in use on 40.9% of the websites it tracks. As a designer you rarely pick one. Your CDN or load balancer speaks whatever the browser supports and typically talks plain HTTP/1.1 or HTTP/2 to your servers behind it. goes deeper.

Step 5: arrive at the edge

The address that DNS returned rarely belongs to the machine that runs your code. It belongs to something placed in front, whose job is to receive traffic and pass it on.

Often the first stop is a content delivery network (CDN): a fleet of servers in hundreds of cities, run by a provider. The user’s connection, and its TLS handshake, end at a CDN server near them, which keeps the round trips short. If the CDN holds a fresh copy of what was asked for, such as an image or a stylesheet, it answers at once and your servers never hear about the request. Otherwise it forwards the request to your origin over a connection it already has open.

At your origin the request reaches a load balancer. It holds a list of application servers, checks regularly which of them are healthy, and hands each request to one that is. This single component is what lets you run more than one server, replace servers without downtime, and survive the loss of one. It is covered in , and the CDN in .

Step 6: run the application code

An application server finally receives the request. What happens next is the part you write, and it usually follows the same outline:

  1. Parse and route. Match the method and path, GET /photos/42, to a handler function.
  2. Authenticate. Work out who is asking, from the cookie or token.
  3. Authorize. Check that this user is allowed to see photo 42.
  4. Validate. Reject input that is malformed before it reaches anything important.
  5. Do the work. Run the business logic, reading and writing data as needed.
  6. Respond. Serialize the result as HTML or JSON, set headers, choose a status code.

How that code is organized into classes and layers is the subject of low-level design, in Parts IX and X. From the outside, what matters is that the server keeps nothing between requests that it cannot afford to lose. If it does, the load balancer’s freedom to choose any server disappears.

Step 7: read and write data

Almost every request needs data, and fetching it is usually the slowest thing the server does. For photo 42 the handler needs the photo’s metadata and its owner’s name.

It may first ask a cache, an in-memory store such as Redis that keeps recently used results. A cache answers in well under a millisecond. If the result is there, that is a cache hit and the database is not involved. If not, it is a cache miss: the handler queries the database, which finds the row using an index in perhaps a few milliseconds, and the handler stores the result in the cache for the next request.

The image bytes themselves are not in the database. Large files live in object storage, and the page contains only a URL pointing at them, which the browser fetches separately, normally through the CDN. Part III is about all of these stores: how they find data quickly, how they keep copies, and how they are split across machines.

Step 8: the response travels back

The response retraces the path: application server, load balancer, CDN, browser. Two things on the way back are worth knowing because they cost little and save a great deal.

Compression. Text formats such as HTML, CSS, JavaScript and JSON shrink to a fraction of their size with gzip or Brotli. The browser lists what it accepts in Accept-Encoding and the server or CDN compresses accordingly.

Caching headers. The response can say how long it may be reused, and by whom. Cache-Control: public, max-age=31536000 lets the browser and every CDN reuse a file for a year without asking. Cache-Control: private, max-age=60 lets only the user’s own browser reuse it, for a minute. A response can also carry an ETag, a fingerprint of its content. Later the browser asks “has it changed from this fingerprint?”, and if not the server replies 304 Not Modified with no body. The fastest request is the one that is never sent, and these headers are how you arrange that. treats caching at every layer.

Step 9: the browser builds the page

The browser now has HTML, and it has more work to do before anything appears.

  1. It parses the HTML into a tree of elements, the DOM.
  2. As it parses, it discovers more files to fetch: stylesheets, scripts, fonts, images. Each one is a new request that goes through some or all of the steps above, though usually on a connection that is already open.
  3. It parses the CSS and works out which styles apply to which elements.
  4. It computes the position and size of everything (layout), then draws it (paint).
  5. It runs JavaScript, which may change the DOM and cause parts of this to repeat.

Some of those files block progress. A stylesheet in the page head holds back the first paint until it arrives, and an ordinary script tag pauses HTML parsing while it downloads and runs. A page can therefore feel slow even when the server answered quickly.

Core Web VitalsGoogle’s three user-centered measures of this last step are Largest Contentful Paint (main content visible, good at 2.5 s or less), Interaction to Next Paint (response to input, good at 200 ms or less) and Cumulative Layout Shift (how much the page jumps around, good at 0.1 or less). Each is judged at the 75th percentile of real visits.

This is where back-end and front-end design meet. A back-end choice, such as returning one large response or several small ones, or rendering HTML on the server or sending JSON for the browser to render, shows up directly in how long the user waits to see something.

Where the time goes

Add the steps up for a user whose round trip to the nearest edge server takes 60 ms, with an application that needs 80 ms to produce a response. The numbers are illustrative, and the proportions are typical.

Three conclusions follow, and each one becomes a design technique later in the book.

  • Setup costs more than the work. On a first visit, 160 of the 300 ms pass before the server has seen the request. Reusing connections, and ending them at an edge server close to the user, removes most of that.
  • Distance multiplies. Every phase except server work is counted in round trips. Halve the round-trip time by moving closer and you halve all of them at once.
  • The first request is the worst case. Everything after it on the same connection skips steps 1 to 3. Performance that looks fine in a test that reuses one connection can look quite different to a real first-time visitor.

You can measure these phases against any site with curl. Each value it prints is the time elapsed since the start, so subtract neighbors to get the length of a phase.

curl -o /dev/null -s -w "dns        %{time_namelookup}s
connected  %{time_connect}s
tls done   %{time_appconnect}s
first byte %{time_starttransfer}s
total      %{time_total}s
" https://www.example.com/

What can fail at each step

A design is judged on the bad day as much as the good one. Each step has a characteristic way of failing and a characteristic defense, and from the user’s side many of them look the same: a spinner, then an error page.

In production. The edge is a shared dependency for a large part of the web. On 18 November 2025 a database permission change at Cloudflare caused an internal configuration file to double in size. The file exceeded a fixed limit in the proxy software that reads it, the proxies failed, and sites behind Cloudflare returned 5xx errors from 11:20 UTC until traffic was largely restored at 14:30. The origin servers of those sites were healthy throughout. When you draw a box in front of your system, you also take on its failures.

Key points

  • A request passes through DNS, a transport connection, TLS, HTTP, an edge or load balancer, application code and data stores, and then the browser’s rendering.
  • DNS is a cached, hierarchical lookup. Caching makes it fast and also makes changes take time to spread.
  • TCP gives ordered, reliable delivery for one round trip of setup. TLS 1.3 adds encryption and server identity for one more. QUIC combines the two.
  • HTTP’s meaning is stable. Versions 1.1, 2 and 3 differ in how many requests share a connection and what a lost packet delays.
  • On a first visit, connection setup often takes longer than your code. Round trips and distance dominate, so remove round trips and move closer.
  • Every step can fail in its own way. A design should name the defense for each.

Check yourself

You change a DNS record to point at a new server, and an hour later some users still reach the old one. Why?

Resolvers and devices cached the old answer and will keep using it until its TTL expires. If the old record had a TTL of a day, some users will be sent to the old server for up to a day. Lowering the TTL well before a planned change shortens that window.

With TCP and TLS 1.3 on a 100 ms round trip, how long is it before the browser can send its first request on a new connection? And with QUIC?

Two round trips, so about 200 ms, with TCP and TLS 1.3. One round trip, about 100 ms, with QUIC, and close to zero on a resumed connection that uses 0-RTT.

HTTP/2 removed head-of-line blocking in HTTP. Why did HTTP/3 still need to exist?

HTTP/2 multiplexes many streams over one TCP connection, and TCP delivers bytes strictly in order. One lost packet stalls all the streams until it is retransmitted. HTTP/3 runs over QUIC, which orders each stream independently, so a loss delays only the stream it belongs to.

Your monitoring shows a jump in 404 responses and no change in 5xx. Is your service down?

Probably not. 4xx codes say the request was wrong, for example a client asking for pages that do not exist, perhaps a crawler or a broken link in a new release of the front end. It is worth finding the cause, and it is a different kind of problem from the servers failing.

Why is the image for photo 42 not stored in the database row with its metadata?

Large binary files make a database bigger, slower to back up and more expensive, and a database is poor at streaming megabytes to many clients. Object storage is built for exactly that, and a CDN can serve from it directly. The row stores a reference to the object.
