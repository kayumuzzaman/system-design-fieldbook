When the default stops fitting

The advice in was to begin with a relational database and to move a workload out only when there is a reason. This chapter is about four of the most common reasons. In each case the difficulty is the same underneath. A B-tree orders data along one dimension and is superb at finding a value or a range along it. These workloads ask questions that do not reduce to one ordered dimension, or they arrive in volumes that reward a storage layout designed for nothing else.

For all four there is a middle path between “make do” and “run another database”: an extension that adds the specialized index to the database you already have. PostgreSQL has one for each. The chapter ends with how to choose.

Time-series data

A time series is a sequence of measurements of the same thing over time: CPU load on a server, temperature from a sensor, the price of a stock, requests per second to an endpoint. The workload has a very particular shape.

  • Writes are appends. New points arrive constantly, nearly in time order, and old points are almost never changed.
  • Volume is large and steady. Ten thousand servers reporting 200 metrics every 10 seconds produce 200,000 points per second, or 17 billion a day.
  • Recent data is read far more than old data, and old data is read as summaries.
  • Queries are ranges and aggregates: averages, maximums and percentiles over a window, grouped by time bucket and by some label such as host or region.

A time-series database is built around that shape, with three techniques.

Partitioning by time. Data is divided into chunks covering a fixed period, such as a day. Writes go to the current chunk, whose indexes are small and in memory. A query for the last hour opens one chunk. Old data is removed by dropping whole chunks, which is instant. This is the table partitioning from , automated.

Compression by column. Consecutive points in a series are very alike. Timestamps arrive at regular intervals, so the difference between successive differences is usually zero and can be stored in a single bit. Values change slowly, so each can be stored as its difference from the one before. Facebook’s Gorilla system, which introduced this scheme in 2015, reported an average of 1.37 bytes per point where the raw form takes 16. For the fleet above, that turns 276 GB a day into about 24 GB.

Downsampling and retention. Nobody needs ten-second resolution for last year. Older data is replaced by summaries at coarser intervals, and each level of detail has its own lifetime.

SELECT time_bucket('5 minutes', recorded_at) AS bucket,
       device_id,
       avg(temperature) AS avg_temp,
       max(temperature) AS max_temp
FROM readings
WHERE recorded_at > now() - INTERVAL '6 hours'
GROUP BY bucket, device_id
ORDER BY bucket;

The cardinality trap

The most common way to break a time-series database has nothing to do with the number of points. Each distinct combination of labels is a separate series. A metric labeled by host and endpoint, with 1,000 hosts and 50 endpoints, is 50,000 series. Add a label for user ID, with a million users, and it becomes 50 billion possible series, each needing its own index entry and memory. This is called a cardinality explosion. Labels should describe a small, bounded set of values. Anything unbounded, such as user IDs, request IDs and full URLs, belongs in logs or traces ().

A plain PostgreSQL table partitioned by month, with an index on series and time, is a perfectly good time-series store for modest volumes. Move on when write volume, storage cost or query speed over long ranges says so.

Geospatial data

“Find drivers near me” and “which delivery zone contains this address?” are questions about position. The awkwardness is that nearness is two-dimensional. An index on latitude finds everything in a horizontal band around the world, and an index on longitude a vertical one. Neither narrows the search to a neighborhood, and a B-tree can only sort by one thing. Spatial indexes solve this in one of two ways.

Dividing the map into cells

Lay a grid over the world and give each cell an identifier. A point’s cell ID is an ordinary value that a B-tree or a hash can index. Finding nearby things becomes: work out which cells the search area touches, fetch what is in them, and discard anything outside the exact radius.

The schemes differ in how cells are shaped and named.

SchemeHow it worksNotes
GeohashRepeatedly halves the world, alternating between longitude and latitude, and writes the choices as a short string. Each extra character makes the cell smaller: six characters is roughly 1.2 km by 0.6 km.Cells sharing a prefix are nested, so a prefix lookup finds a region. Two points either side of a cell boundary can have very different strings, which is why neighbors must be searched.
QuadtreeSplits a square into four whenever it holds too many points, and repeatsAdapts to density: small cells in a city center, large ones over the ocean
S2Google’s library. Projects the sphere onto a cube and numbers cells along a curve that keeps nearby cells close in number.Handles the whole globe without distortion at the poles
H3Uber’s library. Covers the globe in hexagons at sixteen resolutions.Every neighbor of a hexagon is the same distance away, which suits movement and demand analysis

Nesting boxes

The other approach is the R-tree, which is to rectangles what a B-tree is to numbers. Nearby objects are grouped inside a bounding rectangle, nearby rectangles inside a larger one, and so on up to a root. A search descends only into rectangles that overlap the search area. R-trees handle shapes as well as points, so they answer “which zone contains this point?” and “which roads cross this area?”. PostGIS, the spatial extension to PostgreSQL, uses this structure.

CREATE INDEX places_location_idx ON places USING gist (location);

SELECT id, name,
       ST_Distance(location, ST_MakePoint(151.2093, -33.8688)::geography) AS meters
FROM places
WHERE ST_DWithin(location, ST_MakePoint(151.2093, -33.8688)::geography, 2000)
ORDER BY meters
LIMIT 20;

Two details of that query catch people out. The point is written as longitude then latitude, the reverse of how coordinates are usually spoken. And the geography type computes distances over the curved surface of the Earth in meters. Treating latitude and longitude as flat coordinates gives errors that grow toward the poles.

For static places such as shops, a spatial index in the main database is all most products need. Things that move are a different workload. A fleet of drivers reporting position every few seconds is write-heavy, the data is worthless after a minute, and it is usually kept in memory, in a store such as Redis with its geospatial commands or in a purpose-built grid. designs such a system.

Graph data

introduced the graph model. The reason it needs its own storage is the cost of a hop. In a relational database, following a relationship is a join, which is an index lookup whose cost grows slowly with the size of the table. A graph database stores, with each node, direct references to its edges and neighbors. Following an edge is a pointer dereference whose cost does not depend on how large the whole graph is. For a query that follows five or six hops through a large network, the difference is between milliseconds and minutes.

SQL can express traversals with recursive queries, and for hierarchies and shallow traversals that is often enough.

WITH RECURSIVE reports AS (
  SELECT id, name, manager_id, 1 AS depth
  FROM employees
  WHERE manager_id = 42
  UNION ALL
  SELECT e.id, e.name, e.manager_id, r.depth + 1
  FROM employees e JOIN reports r ON e.manager_id = r.id
  WHERE r.depth < 10
)
SELECT * FROM reports;

A dedicated graph database earns its place when traversals are deep, varied and central to the product: fraud detection that looks for rings of accounts sharing devices and cards, recommendations from paths through purchases, permission systems where access is inherited through nested groups, and knowledge graphs. Three cautions apply.

  • Supernodes. A node with millions of edges, such as a celebrity account, makes any traversal through it explode. Queries need limits and such nodes need special handling.
  • Scaling out is hard. A graph has no natural partition key. However it is cut, some traversals cross machines, and each crossing is a network round trip.
  • It is rarely the system of record. Most deployments keep the authoritative data in a relational database and maintain the graph as a derived copy for the queries that need it.

Vector data

introduced embeddings: lists of numbers produced by a machine learning model, arranged so that similar items lie close together. A vector database, or a vector index inside another database, answers one question: given a query vector, which stored vectors are nearest to it? That question underlies semantic search, recommendations, duplicate and near-duplicate detection, and the retrieval step that supplies language models with relevant documents ().

“Nearest” needs a definition. The common measures are cosine similarity, which compares direction and ignores length, the dot product, and straight-line distance. Use whichever the embedding model was trained with.

The obvious method compares the query with every stored vector. It is exact, and for up to some tens of thousands of vectors it is fast enough and the right choice. Beyond that it is too slow, and ordinary indexes cannot help: in hundreds of dimensions there is no ordering that keeps neighbors together. The practical answer is approximate nearest neighbor search, which accepts missing a few of the true nearest in exchange for speed. The fraction of true neighbors that are found is the recall, and every such index is a dial between recall and speed.

IndexIdeaStrengthWeakness
Exact scanCompare with everythingPerfect recall, no index to buildCost grows in step with the data
IVF (inverted file)Group vectors into clusters, and search only the clusters nearest the queryCompact. Fast to build.Recall drops for queries near cluster boundaries unless more clusters are searched
HNSW (hierarchical navigable small world)A layered graph linking each vector to its near neighbors. Search hops greedily toward the query.The best trade of recall for speed in most benchmarks. The usual default.The graph is large and lives in memory. Slow to build.
QuantizationStore each vector in compressed form: fewer bits per number, or a short codeCuts memory by 4 to 30 times or moreLoses precision. Usually combined with a re-check of the top results against the full vectors.

Memory is the practical constraint, and the arithmetic is worth doing early. A vector of 1,536 numbers at 4 bytes each is about 6 KB. Ten million of them are 61 GB before any index is added. Storing each number in one byte reduces that to 15 GB, and one bit per number to under 2 GB, at a cost in accuracy.

CREATE EXTENSION vector;

CREATE TABLE photo_embeddings (
  photo_id  BIGINT PRIMARY KEY REFERENCES photos (id),
  embedding vector(1536) NOT NULL
);

CREATE INDEX ON photo_embeddings USING hnsw (embedding vector_cosine_ops);

-- The 10 photos most similar to a query vector, among one user's photos
SELECT p.id, p.caption
FROM photo_embeddings e JOIN photos p ON p.id = e.photo_id
WHERE p.owner_id = 42
ORDER BY e.embedding <=> $1
LIMIT 10;

That query hides the hardest problem in vector search, which is filtering. Real queries are rarely “the nearest vectors overall”. They are “the nearest among this user’s documents”, or “among products in stock under 50”. Filtering after the vector search can leave too few results, since the nearest ten may all belong to other users. Filtering before it may defeat the index. How well a system combines the two is one of the main differences between products, and something to test with your own data.

Embeddings are derived data. They are computed from the original text or image by a particular model, and if you change the model, every vector must be recomputed, because vectors from different models cannot be compared. Keep the source data and a record of which model produced each embedding.

Extension or dedicated system?

Each of the four workloads can be served by an extension to a database you already run, or by a separate system built for it.

WorkloadInside PostgreSQLSigns you have outgrown it
Time seriesPartitioned tables, or TimescaleDBSustained ingestion beyond what one node writes. Storage cost dominated by history. Long-range queries too slow.
GeospatialPostGISConstantly moving objects at high update rates. Global scale with strict latency.
GraphRecursive queries, or the Apache AGE extensionDeep traversals in the request path. Graph algorithms over the whole data set.
VectorpgvectorIndex no longer fits in memory. Vector queries slowing transactional ones. Recall or filtering needs you cannot meet.

The extension keeps the data in one place. It shares transactions, joins, backups, access control and operational knowledge with everything else, and there is nothing to synchronize. A dedicated system does its one job better and adds a system to run, a copy of the data to keep in step, and a new set of failure modes. The questions from return: which copy is the truth, how the copy is kept current, and how it is rebuilt.

The reasonable order is to start with the extension, measure, and move the one workload that has outgrown it. A specialized store adopted for a problem you do not yet have is cost without benefit.

In an interview. Name the specialized structure when the question calls for it, with the reason: “nearby search needs a spatial index, so a geohash prefix or PostGIS”, “metrics are append-only and read as aggregates, so a time-series store with rollups”, “similarity over embeddings, so an HNSW index”. Then say where the source of truth is. Interviewers are checking that you know the default stops fitting, and that you know what replaces it.

Common mistakes

  • Adopting a specialized database before trying an extension to the one you have.
  • Unbounded labels on time-series metrics.
  • Keeping only averages in rollups, and losing every spike.
  • Separate indexes on latitude and longitude for nearby searches.
  • Searching only the user’s own cell and missing neighbors across the boundary.
  • Flat-plane distance on latitude and longitude, and swapping their order.
  • A graph database for single-hop lookups.
  • An approximate vector index over a few thousand vectors, where an exact scan is faster and perfectly accurate.
  • Not measuring recall, so nobody knows what the approximate index is missing.
  • Mixing embeddings from different models in one index.
  • Treating any of these stores as the source of truth without a way to rebuild it.

Key points

  • Specialized stores exist for workloads whose questions do not fit one ordered dimension, or whose volume rewards a dedicated layout.
  • Time-series stores partition by time, compress by column and downsample old data. Keep label cardinality bounded.
  • Geospatial indexes map two dimensions onto cells (geohash, S2, H3) or nested rectangles (R-trees). Search neighboring cells, then check exact distance.
  • Graph databases make each hop cheap by storing direct links. They pay off for deep, varied traversals.
  • Vector indexes find approximate nearest neighbors, trading recall for speed. HNSW is the usual default, memory is the constraint and filtering is the hard part.
  • Start with an extension to your main database. Move a workload to a dedicated system when measurements show it has outgrown the extension.
  • Specialized stores usually hold derived data. Keep the source of truth elsewhere and be able to rebuild.

Check yourself

A metrics system slows down and runs out of memory after a developer adds a customer_id label to a request counter. Why?

Every distinct combination of label values is a separate time series with its own index entry and memory. A label with one value per customer multiplies the number of series by the number of customers. Remove the label and record per-customer detail in logs or traces instead.

Why does a rollup store the minimum and maximum as well as the average?

An average over five minutes hides short spikes: one second at 100% CPU and the rest at 10% averages to a little over 10%. The maximum preserves the fact that the spike happened, which is usually what you are looking for later.

A nearby search looks up only the grid cell containing the user and sometimes misses a shop 50 meters away. What is wrong?

The shop is in an adjacent cell, just across the boundary. The search must also fetch the neighboring cells that the search radius reaches, then filter the candidates by true distance.

Your product has 20,000 documents to search by embedding. Should you build an HNSW index?

Probably not. Comparing a query against 20,000 vectors exactly takes a few milliseconds and returns perfect results. An approximate index adds build time, memory and a loss of recall to solve a speed problem you do not have.

A vector search for “the ten most similar documents this user can access” returns only two results, although the user can access thousands. What is the likely cause?

The filter is applied after the vector search. The index returned its ten nearest overall, and only two of them belonged to this user. The filter needs to be applied during the search, or the search asked for many more candidates before filtering.

You switch to a newer embedding model. What has to happen to the existing vectors?

All of them must be recomputed from the original content with the new model, and the index rebuilt. Vectors from different models live in unrelated spaces, so distances between them mean nothing.
