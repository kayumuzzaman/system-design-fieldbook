Why leave one region

A cloud region is a set of data centers in one metropolitan area, divided into availability zones that are a few tens of kilometers apart and fail mostly independently. introduced both. A system spread over three zones of one region already survives the loss of a building, and for most systems that is the right place to stop.

There are three reasons to go further, and it helps to know which one applies, because they lead to different designs.

ReasonWhat it requiresWhat it does not require
Latency: users are far awayServing reads, and ideally writes, near each userEvery region able to take over from every other
Availability: survive a regional outageA second region that can carry all traffic, with current dataRegions far apart or near users
Residency: data must stay in a jurisdictionCertain data stored and processed only in certain placesAny redundancy between regions at all

The reasons also conflict. Residency says some data must not leave Europe. Availability says a copy of everything should exist somewhere else. A design has to state which requirement wins for which data.

The cost comes in the same three parts every time: more machines, more engineering in every feature that touches data, and new ways to fail. Regional outages are rare, and a multi-region design that is seldom exercised can cause more downtime through its own complexity than the outages it was built for. Go multi-region when a requirement forces it, and then only as far as that requirement goes.

The floor set by distance

Light in optical fiber travels at about two thirds of its speed in a vacuum: roughly 200,000 km a second, or 200 km per millisecond. No engineering improves on that. A request and its response must cross the distance twice, so a server 6,000 km away cannot answer in under 60 ms even if it does no work.

Real paths are longer than the straight line. Cables follow coastlines and ocean ridges, and packets pass through routers. A round trip of about one and a half times the theoretical minimum is a reasonable planning figure, and it varies widely by route.

One round trip is the best case. A new connection needs several before the first byte of the response arrives: one for the TCP handshake, one for TLS 1.3, then the request itself, as showed. HTTP/3 merges the first two.

Light in fiber covers 6,500 km in 32.5 ms, and real routes are longer, so one round trip takes about 97.5 ms. A first request over TCP and TLS 1.3 needs three round trips before the response arrives: 343 ms. Over HTTP/3 it needs two: 245 ms. On a connection that is already open it needs one: 148 ms. Server time is 50 ms of each. Only moving closer reduces the rest.

The default distance, 6,500 km, is roughly New York to Frankfurt. Two conclusions follow from the numbers.

First, much of the delay on a first request is connection setup, and that part can be fixed without a second region. A content delivery network terminates the user’s connection at a nearby point of presence and reuses warm connections to the origin, as described. For a product with one region and users everywhere, this is the first step, and often a sufficient one.

Second, what remains is one round trip to wherever the data is. To remove that, the data itself must move closer to the user, and that is where multi-region becomes hard.

The stateless parts of a system are easy in every shape: run the same containers in each region. All of the difficulty is in the data, and the sections after routing take it in order.

Getting users to a region

Something must send each user to a region. Three mechanisms do it, and large systems combine them.

  • DNS steering. The authoritative DNS server answers with a different address depending on where the question comes from, or on measured latency, as in . It is simple and universal. It is also slow to change, because resolvers cache answers for the record’s time to live and some ignore it, so a failover by DNS takes minutes for most users and longer for a few.
  • Anycast. The same IP address is announced from every region, and internet routing delivers each packet to a nearby one, as in . A region that stops announcing loses its traffic within seconds, with no caches to wait for. This is how content delivery networks and the cloud providers’ global load balancers work.
  • Application-level redirection. The client learns its region after login and then calls a regional hostname directly, such as eu.api.photos.example. The application decides, using knowledge the network does not have, such as where the user’s data lives.

Routing by nearness alone is not enough once data is involved. A user sent to the nearest region may find that their data is somewhere else, or is a second behind. Two rules keep this manageable. Keep a user on one region for the length of a session, so that they read what they wrote. Let the application override the network’s choice when the data requires it. The home-region pattern below is built on the second rule.

Data across regions

set out the choices for keeping copies in step. Distance changes their prices. Within a region, a synchronous copy costs a millisecond. Across an ocean it costs a hundred. The PACELC rule from describes exactly this: even with no failure, you choose between latency and consistency.

Asynchronous copies

One region holds the primary. Others receive its changes a moment later and serve reads from their copies. This is the “read local, write central” shape, and it is where most systems start, because every mainstream database supports it.

It has two costs. The first is that copies lag, usually by well under a second and occasionally by much more. A user in Singapore who changes their profile and reloads the page reads from the Singapore copy, which may not have the change yet. The remedies are those in and : for a short time after a write, send that user’s reads to the primary, or have the client carry a position that the copy must have reached.

The second cost appears on failover. Changes that had not yet reached the other region when the primary was lost are gone, or stranded until the old region returns. The amount is the replication lag at that moment: the recovery point objective from cannot be zero.

Consensus across regions

To lose nothing when a region fails, a write must be stored in more than one region before it is acknowledged. Databases built for this replicate every write with a consensus protocol among replicas in different regions, as described: Google Spanner, CockroachDB, YugabyteDB and Amazon Aurora DSQL are examples. Since June 2025 DynamoDB global tables also offer a strongly consistent mode across three regions, alongside their original eventually consistent mode.

The price is latency on every write. A leader must hear from a majority before it commits, so each write waits for a round trip to the nearest other replica. Where the replicas are placed decides how long that is.

The function that produced those figures is short, and worth reading because it states the rule exactly.

type Place = { name: string; lat: number; lon: number };

/** Great-circle distance in km. */
export function distanceKm(a: Place, b: Place): number {
  const rad = (d: number) => (d * Math.PI) / 180;
  const dLat = rad(b.lat - a.lat), dLon = rad(b.lon - a.lon);
  const h = Math.sin(dLat / 2) ** 2 + Math.cos(rad(a.lat)) * Math.cos(rad(b.lat)) * Math.sin(dLon / 2) ** 2;
  return 2 * 6371 * Math.asin(Math.sqrt(h));
}

const FIBER_KM_PER_MS = 200;   // light in glass travels at about two thirds of its speed in vacuum

/** Round-trip time in ms. routeFactor 1 is a straight cable, 1.5 is a typical real path. */
export function roundTripMs(a: Place, b: Place, routeFactor = 1.5): number {
  return (2 * distanceKm(a, b) * routeFactor) / FIBER_KM_PER_MS;
}

/** The leader needs acknowledgments from a majority, counting itself: wait for the nearest ones. */
export function commitMs(leader: Place, replicas: Place[]): number {
  const others = replicas.filter((r) => r !== leader).map((r) => roundTripMs(leader, r)).sort((x, y) => x - y);
  const majority = Math.floor(replicas.length / 2) + 1;
  const needed = majority - 1;            // acknowledgments beyond the leader's own
  return needed === 0 ? 0 : others[needed - 1];
}

Three consequences follow from it.

  • Nearby replicas are fast and share risks. Three regions on one continent commit in a few milliseconds and survive the loss of any one region. They do nothing for users on other continents.
  • Distant replicas are slow for everyone. Spread around the world, every write waits most of a hundred milliseconds, and a transaction with several statements waits several times.
  • The leader’s location matters most. With the leader in Tokyo instead of Virginia, the same three regions commit in about 144 ms, because both followers are far away. Users far from the leader pay to reach it before the commit even starts. These databases therefore let you choose a leader region, and some move leaders to follow the traffic.

Reads need care as well. A read that must be current has to consult the leader or prove that its local replica is up to date. Most of these systems also offer reads that are a few seconds stale from the nearest replica, which is fast and enough for much of what an application shows.

Writing anywhere without waiting

The opposite choice is to accept writes in every region immediately and replicate afterward. DynamoDB global tables in their default mode, Cassandra across data centers, and Azure Cosmos DB with multi-region writes work this way. Writes are fast everywhere and each region keeps working when cut off from the others.

The cost is conflicts. Two regions can accept different changes to the same item before either hears of the other’s, and something must decide the outcome. covered the options. The usual default is that the write with the later timestamp wins and the other is silently discarded. That is acceptable for data where the last value is all that matters, such as a profile field, and wrong for anything that accumulates, such as a counter, an inventory level or a balance. For those, either use data types designed to merge, or do not use this model.

Giving each piece of data one home

The fourth choice avoids both costs for most requests by observing that most data belongs to someone, and that person is usually in one place. Keep each user’s data in the region nearest to them, with its replicas in zones of that region or in neighboring regions. Their reads and writes are then local and strongly consistent, at single-region speed.

Some distributed SQL databases build this in. CockroachDB, for example, can pin each row of a table to a region named in one of its columns, and treats small, rarely changing reference tables as global so that every region can read them quickly. The same pattern can be built by hand on ordinary databases, one cluster per region, and that version is common enough to deserve its own section.

The home-region pattern

Each user, or each tenant, is assigned a home region when they sign up. Their data lives there. Each region runs a complete copy of the application and its own databases, which makes each region a cell in the sense of .

One small piece of data must be global: the directory that says which region each user belongs to. It is replicated to every region and read locally. It changes only when a user signs up or moves, so replicating it is cheap and a slightly stale copy does little harm.

type Decision = { serveIn: string; forwarded: boolean; reason: string };

/**
 * Reads of replicated, public data are served where the request landed.
 * Anything that touches the user's own data goes to the user's home region.
 */
export function route(
  landedIn: string,
  homeRegion: string,
  kind: "public-read" | "own-data",
  healthy: Set,
): Decision {
  if (kind === "public-read") return { serveIn: landedIn, forwarded: false, reason: "replicated data, read locally" };
  if (!healthy.has(homeRegion)) throw new Error(`home region ${homeRegion} is unavailable`);
  return landedIn === homeRegion
    ? { serveIn: homeRegion, forwarded: false, reason: "already at home" }
    : { serveIn: homeRegion, forwarded: true, reason: "forwarded to the home region" };
}

The function shows the pattern’s two limits.

What crosses regions. In the photo app, Ana in Europe follows Ben in the US. Her feed needs his public photos. The usual answer splits data by kind. Private data, such as Ana’s settings, drafts and messages, lives only at home. Public or shared data, such as Ben’s published photos, is copied asynchronously to every region so that anyone can read it locally, slightly late. Operations that must change data in two regions at once, such as a transfer between two users’ balances, need the sagas of , and are best avoided in the design where possible.

What happens when a home is down. The function throws. Ana’s data is in Europe, and if Europe is unreachable, she cannot be served from elsewhere unless a current copy exists elsewhere and is allowed to exist there. A home-region design gives every region’s users independence from other regions’ failures. It does not by itself give them protection from their own region’s failure. That needs replicas outside the region, which brings back the earlier choice between asynchronous copies that may lose the latest writes and consensus that slows every write.

Data residency

Data residency is a requirement that certain data be stored, and often processed, within a particular country or bloc. It comes from law in some countries and sectors, and more often from customer contracts: a European bank or a public agency will make it a condition of buying. This section describes the engineering. What a given law requires is a question for a lawyer, and the answer changes.

The home-region pattern is the natural fit. The tenant’s region becomes a property chosen at signup, recorded in the directory and enforced by placement, as in . The difficult part is that residency applies to every copy of the data, and a system makes more copies than its designers remember.

CopyWhy it is missed
Backups and snapshotsOften sent to another region by default, for safety

Queues and streams in transitA global event bus carries everything everywhere

Staff accessAn engineer in another country reading production data may count as a transfer
The global directory itselfIf it maps email addresses to regions, it holds personal data from every region

The last row needs a design decision. A login page must find a user’s region before it can authenticate them. Common answers are to keep only a hash of the identifier in the global directory, to put the region in the hostname the customer uses, such as acme.eu.photos.example, or to ask each region in turn.

Residency also constrains failover. If European data may not leave Europe, its standby must be a second European region, and the plan for losing both is to be unavailable. That is a legitimate outcome to write down: for this data, the residency requirement outranks availability.

Regional failover

Having a second region is not the same as being able to use it. Failover is a procedure with several steps, each of which can fail, carried out during an incident that is already going badly. Its design matters more than the standby’s existence.

Capacity for the survivors

When a region is lost, its traffic lands on the others. They must have room for it, already running.

with N regions: normal load on each ≤ (N − 1) / N of its capacity

Relying on automatic scaling to add the missing capacity at the moment of failure is a common plan and a weak one. Every other customer of the failed region is requesting capacity in the same neighboring regions at the same time, and the systems that hand it out are under their heaviest load. A survivor that receives double traffic with cold caches can also fall into the self-sustaining overload described in . Shift traffic in steps where the situation allows, and shed load before the survivor saturates.

Control planes and static stability

Cloud services have two parts. The data plane does the work: it forwards packets, serves queries, answers DNS lookups. The control plane changes things: it launches machines, edits records, alters configuration. Data planes are built to be simpler and more available than control planes, and during large incidents it is usually a control plane that is impaired. The AWS outage of October 2025 in went that way: servers kept running, and for hours new ones could not be launched.

A system is statically stable if it keeps working, and can recover, without making any change through a control plane. AWS uses the term for its own designs, and it is the most useful single test of a failover plan.

Some control planes are themselves hosted in one region, whatever region your resources are in. A failover plan that calls such an API depends on that region being healthy. Find out, for every step in your runbook, what it calls and where that runs.

Deciding and promoting

Detection. A region rarely vanishes. More often it degrades: some requests fail, some are slow, one service is broken. Health checks that test only whether a server answers will report a sick region as healthy. Check what users experience, from outside the region, and from more than one place, so that a failure of the checker is not mistaken for a failure of the region.

Who decides. Routing away from a region that stops answering can be automatic. Promoting a database in another region usually should not be, because it can lose data and is hard to undo. Many teams automate everything up to that decision and leave the decision to a person with a single command. Slack’s design in works that way.

Promotion. With asynchronous replication, promoting the standby discards whatever it had not received, and the old primary must be prevented from accepting writes if it is still alive, or the two will diverge. and the fencing tokens in cover this. A consensus-replicated store does it without a person: the surviving majority elects a leader and nothing committed is lost.

Failing back. Returning to the original region is a second migration. The old region’s data is behind, its caches are cold, and any writes it accepted in isolation must be reconciled or thrown away. Plan it with as much care as the failover, and do it at a quiet time.

Practice. A failover that has never been run does not work. The configuration has drifted, a new service was never deployed to the standby, a credential expired. Netflix has described routinely evacuating a whole region’s traffic as an exercise, and cutting the time it takes from most of an hour to about seven minutes. Teams without that scale can still fail over on a schedule, a few times a year, in working hours. Active-active designs have an advantage here: every region serves real traffic every day, so there is no untested standby.

The failures that regions do not contain

Regions isolate faults in hardware, power, networks and local software. They do not isolate anything that is applied to all regions at once, and those are now the common causes of the largest outages.

  • Global configuration. The Google Cloud incident in came from a policy change that replicated to every region within seconds and crashed the same service in all of them. Many regions gave no protection, because the change did not respect them.
  • Simultaneous deployment. The same bad build released everywhere at once.
  • Shared global services. A single identity service, DNS provider, certificate or directory that every region depends on.
  • Data. A bad write or a deletion replicates faithfully to every copy. Replication is not a backup.

The defense is to treat changes like traffic: roll out code and configuration one region at a time, wait, watch, and continue. Global configuration systems should enforce this and should be the most conservative part of the system. For each global dependency, decide what every region does when it is unreachable. The safest answer is usually to continue with the last known good copy.

What it costs

  • Capacity. At least the idle headroom from the capacity rule, and often full duplicates of systems that do not scale down.
  • Data transfer. Providers charge for each gigabyte that leaves a region. Replicating a busy database, an event stream and object storage continuously can cost more than the machines.
  • Engineering. Every feature that stores data now needs an answer to “which region, and what if it is read from another?”. Schema changes, deployments and incident response all gain a dimension. This cost recurs with every feature and is the largest.
  • Testing. Realistic tests need several regions and injected delay and partitions between them.

Much of this can be bought. A managed multi-region database, a global load balancer and an object store with built-in replication move work to the provider, at a price and with their guarantees to read closely. The decisions about consistency, conflicts, residency and failover remain yours.

In an interview. If asked to make a design “global”, first ask which of the three reasons applies. For latency, add a CDN and regional read replicas, and name the stale-read problem. For availability, add a second region with stated recovery objectives, and say how traffic and the database each fail over. For both, propose home regions with a global directory. Give one number from physics, such as 80 ms across the Atlantic, and say what your design does when a user’s home region is down.

Common mistakes

  • Going multi-region for availability before using several zones well. Most outages are caused by changes and by software, which a second region does not prevent.
  • Replicating the stateless tier and calling it done. The servers are in three regions and the database is in one.
  • Ignoring the round trips. A chatty protocol that was fine at 1 ms per call is unusable at 80 ms. Count the cross-region calls on each request path.
  • Treating replicas as current. Reading from a local copy right after writing to a distant primary.
  • Last-write-wins on data that accumulates. Counters, balances and inventories lose updates silently.
  • A standby that is never used. It will not work when needed.
  • No spare capacity in the survivors. The failover overloads them and the outage spreads.
  • A failover that needs the control plane. Launching, scaling or reconfiguring as the first step of recovery.
  • Global changes all at once. Configuration and deployments that reach every region in the same minute.
  • Residency for the database only. Backups, logs, analytics and vendors holding the same data somewhere else.
  • Hidden single-region dependencies. An authentication service, a build system or a secret store that every region calls and that lives in one.

Key points

  • There are three reasons to use several regions: latency, surviving a regional outage, and residency. They need different designs and sometimes conflict.
  • Distance sets a floor of about 1 ms of round trip per 100 km, and real paths are longer. A CDN removes connection setup. Only moving data removes the rest.
  • Stateless services are easy to run everywhere. The design is decided by where writes are accepted.
  • Asynchronous copies are fast and can lose the latest writes. Consensus across regions loses nothing and adds a quorum round trip to every write. Multi-writer stores are fast and must resolve conflicts.
  • Giving each user or tenant a home region makes most requests local and consistent, with a small global directory to find the home.
  • Residency applies to every copy: backups, logs, analytics, vendors and the directory.
  • Survivors need spare capacity already running: at most (N − 1) / N load with N regions. A failover should need no control-plane action, and must be practiced.
  • Changes applied to all regions at once defeat regional isolation. Roll out code and configuration region by region.

Check yourself

A server is 9,000 km from a user. What is the least possible round-trip time, and roughly what should you plan for? How long does a first HTTPS request over TCP take if the server needs 40 ms?

At 200 km per millisecond, 9,000 km each way is 45 ms, so 90 ms for the round trip at the physical minimum. With a path one and a half times as long, plan for about 135 ms. A first request over TCP and TLS 1.3 needs three round trips plus the server’s time: 3 × 135 + 40 = 445 ms.

A product has one region in the US and many users in India who mostly read. What are the first two steps, in order, and what problem does the second introduce?

First, a CDN, which caches static content near users and removes connection setup round trips for dynamic requests. Second, a read replica in a nearby region with reads served locally. The replica lags, so a user who writes and then reads may not see their own change unless their reads are sent to the primary for a short time or the replica is checked for a required position.

A consensus group has replicas in Virginia, Ohio and Oregon, with round trips from Virginia of 7 ms and 53 ms. What is the commit latency with the leader in Virginia? What if two more replicas are added in Ireland (82 ms) and Tokyo (163 ms)?

With three replicas the majority is two, so the leader needs one acknowledgment and waits for the nearest: about 7 ms. With five replicas the majority is three, so it needs two acknowledgments: Ohio at 7 ms and Oregon at 53 ms, giving about 53 ms. Adding distant replicas raised the latency by enlarging the majority.

Why is last-write-wins unsafe for a counter replicated between two regions that both accept writes?

Each region reads the counter, adds one and writes the result. If both do so before hearing from the other, both write the same new value, and after replication one write replaces the other. Two increments produced one. The loss is silent. A counter needs a mergeable data type or a single place where writes happen.

In a home-region design, what data must be global, and why is that acceptable?

The directory that maps each user or tenant to a region, because any region may receive a request and must know where to send it. It is acceptable because the directory is small, changes only at signup or migration, and tolerates slight staleness, so replicating it everywhere is cheap. It should hold as little personal data as possible.

Three regions each run at 75% of capacity. One is lost. What load do the survivors see, and what is the highest safe normal load?

Total load is 3 × 75 = 225 units of a region’s capacity in percent, shared by two regions: 112.5% each, which is an overload. With three regions the limit is two thirds, about 67%, and in practice lower to leave room for cold caches and retries.

What does it mean for a failover to be statically stable, and why does it matter?

It can complete without any change made through a control plane: no launching servers, scaling groups or editing configuration through an API. Standby capacity already runs, and traffic moves by mechanisms on the data path such as health checks. It matters because control planes are the part most often impaired during large incidents, and are under their heaviest load exactly when many customers fail over at once.

A company runs in five regions, and a configuration change takes all five down at once. What principle was violated?

Changes were not contained by the same boundaries as failures. Regions isolate faults only if nothing is applied to all of them simultaneously. Configuration, like code, should be rolled out one region at a time with a pause to observe, and each region should be able to keep running on its last known good configuration.
