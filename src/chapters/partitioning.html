When one machine is not enough

ended with a limit: replicas add read capacity and nothing else, because every replica holds all the data and applies every write. Three pressures eventually exceed what one leader can do.

  • Write volume. One machine’s CPU and disk can only apply so many changes per second.
  • Data size. Indexes stop fitting in memory, and queries that were fast slow down sharply ().
  • Operational weight. Backups, restores, index builds, schema changes and cleanup all take time in proportion to size. At some point a restore takes longer than the business can be down.

Partitioning splits a data set into pieces so that each piece can live on a different machine. A piece is called a partition or, when the pieces are on separate database servers, a shard. Each record belongs to exactly one partition.

The third pressure is often the one that forces the decision. When Notion split its PostgreSQL database in 2021, the triggers were not query speed. The database’s routine cleanup process could no longer keep up, and the team faced the prospect of the database refusing writes to protect itself.

Common mistake. Sharding too early. It is the most disruptive change you can make to a data layer, and it is hard to reverse. Before it, exhaust the cheaper options in order: fix the queries and indexes, add memory or move to a larger machine, add read replicas, cache, move old data to an archive, and move unrelated tables to a database of their own. A single modern server handles tens of thousands of transactions per second and terabytes of data. Many systems never need more.

Partitions are replicated too

Partitioning and replication are separate ideas, used together. Each partition is a small database with its own leader and followers.

Everything in the previous chapter applies within each partition. This chapter is about the new questions: which partition a record goes to, how that changes when machines are added, and what becomes difficult once data is split.

Deciding where each record goes

Every partitioned system has a rule that maps a record to a partition, based on one of its fields, the partition key or shard key. There are three kinds of rule.

Range partitioning

Each partition owns a continuous range of key values, like the volumes of a printed encyclopedia. Keys that are close together are stored together, so a query for a range, such as all events between two timestamps, reads from one or a few partitions.

The weakness is uneven load. If the key is a timestamp, every new record belongs to the newest range, and one partition takes all the writes while the rest sit idle. Systems that use ranges split a partition automatically when it grows too large, and the application must choose keys that do not concentrate activity. Used by HBase, Bigtable, CockroachDB, Spanner and TiDB.

Hash partitioning

Run the key through a hash function, which turns it into an evenly distributed number, and use that number to pick the partition. Similar keys land far apart, so load spreads evenly even when keys are sequential.

The price is range queries. Adjacent keys are on different partitions, so a range scan has to ask all of them. Used by Cassandra, DynamoDB, and Redis Cluster.

The two can be combined, and usually are. A compound key hashes its first part to choose the partition and keeps rows sorted by its second part inside it. This is the partition key and clustering key from : messages are spread by channel, and within a channel they are ordered by time.

Directory partitioning

Keep an explicit lookup table that says which partition holds each key or each group of keys: tenant 17 is on shard 4. This is the most flexible scheme. A large customer can be given a shard to itself, and a group can be moved by copying its data and changing one entry. The cost is that every request consults the directory, which must therefore be fast, cached and highly available.

Adding machines: the rebalancing problem

A partitioned system has to grow, and growing means moving data. How much data moves when a machine is added is the test of a partitioning scheme.

The obvious way to hash keys onto N servers is to take the hash’s remainder after dividing by N. It distributes evenly and fails badly when N changes, because the remainder of almost every number changes with the divisor.

How many keys move when the number of servers changes?

Compare assigning keys by hash modulo the server count with consistent hashing.

Keys that move with hash mod N
90.9%
Keys that move with consistent hashing
9.1%

Going from 10 to 11 servers, hashing modulo the server count sends 90.9% of keys to a different server. Consistent hashing moves 9.1%, which is only the share the new servers should take.

Moving nine tenths of the data to add one tenth more capacity is unworkable. For a cache it means nearly every lookup misses at once. For a database it means copying almost everything across the network while serving traffic. The goal is to move only what the new machine should take, and there are three ways to achieve it.

A fixed number of logical partitions

Separate the two questions. Hash each key into one of a large, fixed number of logical partitions, say 1,024, and never change that number. Separately, keep a small table saying which machine currently holds each logical partition. Adding a machine means reassigning some whole partitions to it. No key ever changes its partition, so nothing needs rehashing.

This is the most common approach in practice. Redis Cluster divides the key space into 16,384 slots. Notion hashed each workspace into one of 480 logical shards and placed them on 32 physical databases, 15 to each, so that it could later spread the same logical shards over more machines without touching the routing logic. The one decision that cannot be revisited is the number of logical partitions, so choose it generously.

Consistent hashing

Consistent hashing achieves the same result with no central table. Picture the output range of the hash function bent into a circle. Each server is placed on the circle at the position given by hashing its name. Each key is hashed to a position too, and belongs to the first server found going clockwise from there.

When a server joins, it takes over only the keys between its position and the previous server’s. When one leaves, its keys pass to the next server along. On average, a change to one server out of N moves about one Nth of the keys.

The simple version has two flaws. Servers placed by a hash land unevenly, so some own much larger arcs than others. And when a server leaves, its whole load falls on a single neighbor. Both are fixed by virtual nodes: each physical server is placed on the ring at many positions, perhaps a hundred or more. Its share of the ring becomes the sum of many small arcs, which averages out the unevenness, and when it leaves, its load is spread across many servers. A more powerful machine can be given more positions.

Consistent hashing appears wherever keys must be assigned to a changing set of servers without coordination: distributed caches, the Dynamo family of databases, the load balancers in , and CDNs choosing which cache holds an object.

Splitting as you grow

Range-partitioned systems take a third approach. They start with one partition and split any partition in two when it passes a size threshold, 512 MB by default in CockroachDB, then move partitions between machines to keep the load even. The number of partitions tracks the data size automatically. All of this is done by the database, which is a strong reason to prefer databases that have partitioning built in.

Choosing the partition key

This is the decision that matters most and is hardest to undo, because changing it means moving every record. A good key has four properties.

PropertyWhyWhat failure looks like
Many distinct valuesThe data can only be divided as finely as the keyPartitioning by country: one partition holds a third of your users and cannot be split
Even spread of loadEach partition should get a similar share of reads and writesOne very active key overloads its partition
Present in most queriesA query that includes the key goes to one partition. A query without it goes to all.Common queries fan out to every shard
Never changesChanging a record’s key means moving it between machinesPartitioning by a user’s region, and the user moves

The third property is the one that shapes the design. For the photo app, consider two choices for the photos table.

  • By owner. All of a user’s photos are on one shard. “Show Ana’s photos” touches one shard, and a transaction that updates Ana’s photo and her profile stays on one machine. The risk is a user with millions of followers and thousands of photos making one shard much busier than the others.
  • By photo ID. Load is perfectly even. “Show Ana’s photos” must now ask every shard, since her photos are everywhere.

Most applications have a natural unit that most requests stay inside: a user, a customer account, a conversation, a device. Partitioning by that unit keeps nearly all queries and transactions on one shard. For software sold to businesses, the unit is the tenant, which is why Notion chose the workspace ID. Discord uses the channel, combined with a time window so that no partition grows forever.

Hot keys and skew

Hashing spreads keys evenly. It does not spread load evenly if some keys are far more active than others, and real workloads are always uneven: a few users, products or topics receive a large share of all activity.

A partition that is overloaded while the cluster as a whole has room is a hot spot. Adding machines does not fix it. The remedies work on the key:

  • Split the hot key. Append a small number to it, so that post:871 becomes post:871#0 through post:871#9, spread over ten partitions. Writes pick one at random. Reads must fetch all ten and combine them, so this is only applied to keys known to be hot.
  • Add a time component, so that a busy entity’s data is divided into buckets by day or month.
  • Isolate the largest tenants on shards of their own, which a directory makes possible.
  • Take the reads away with a cache in front ().

The “celebrity problem” in feed design is this problem under another name, and works through it.

What you give up

On one machine, a database answers any query, joins any tables and makes any set of changes atomic. Once data is partitioned, each of those needs qualification.

CapabilityOn one machineAcross partitions
Query by the partition keyFastFast: routed to one partition
Query by anything elseFast with an indexScatter-gather: sent to every partition and the results merged. As slow as the slowest partition.
JoinsAny tablesCheap only when both sides share a partition key. Otherwise done in the application or avoided by denormalizing.
TransactionsAny rowsWithin one partition as before. Across partitions they need a coordination protocol, which is slower and can block.
Unique constraintsAny columnOnly enforceable on columns that include the partition key
Sequential IDsOne counterNo shared counter. IDs must be generated another way.
Schema changesOne operationOne per shard, with shards briefly at different versions

Scatter-gather deserves a second look, because it interacts with a result from . A query sent to 50 shards waits for the slowest of 50 responses, so its typical latency is close to a single shard’s worst case. It also consumes capacity on every shard, which means such queries do not get cheaper as you add shards. A workload dominated by them gains nothing from partitioning.

Secondary indexes face the same choice. A local index lives on each partition and covers only that partition’s rows, so writing is cheap and searching means asking everyone. A global index covers all partitions and is itself partitioned by the indexed value, so searching is cheap, and every write must update an index on another machine. Global indexes are therefore usually updated asynchronously and can lag behind the data, as DynamoDB’s do.

Cross-partition transactions are covered in , and ID generation in . The practical advice is to choose the partition key so that you need neither very often.

Finding the right partition

A client with a key needs to reach the machine that holds it, and the answer changes as partitions move. There are three arrangements.

ApproachHow it worksExamples
A routing tierClients connect to a proxy that knows the partition map and forwards each query. The application sees what looks like one database.Vitess for MySQL, MongoDB’s router process
Any node forwardsClients connect to any node. If it does not hold the key, it passes the request to the node that does.Cassandra, ScyllaDB
Smart clientsThe client library fetches the partition map and connects straight to the right nodeRedis Cluster clients, and Cassandra drivers as an optimization

In every case something must hold the authoritative map and tell everyone when it changes. That is a small, critical piece of data that must itself be consistent and highly available, and it is usually kept in a coordination service such as ZooKeeper or etcd ().

Sharding a database that is already running

Most teams reach partitioning with a live single database and users who must not notice the change. There are two routes.

The first is to adopt something that does the work: a sharding layer over the database you have, such as Vitess for MySQL or Citus for PostgreSQL, or a database with partitioning built in, such as CockroachDB, YugabyteDB, TiDB, MongoDB, Cassandra or DynamoDB. These handle routing, rebalancing and much of the cross-shard machinery.

The second is to do it in the application. The procedure Notion published is a good model, and it is the expand-and-contract pattern from applied to an entire database:

  1. Choose the key and the layout. Workspace ID, 480 logical shards on 32 databases.
  2. Double-write. Every write goes to the old database and to the new shards.
  3. Backfill. Copy existing data to the shards, taking care not to overwrite newer double-written rows. For Notion this took about three days.
  4. Verify. Compare the old and new stores, and serve some reads from both, checking that the answers match, before any user depends on the new one.
  5. Switch over, shard by shard or all at once, then stop writing to the old database.

The verification step is the one that is tempting to shorten and the one that finds the bugs.

Partitioning inside one database

The word “partitioning” is also used for something more modest. PostgreSQL and MySQL can divide one large table into several smaller physical tables on the same server, most often by time: one partition per month of an events table. This does nothing for the limits of the machine. Its benefits are different and useful.

  • Queries skip irrelevant partitions. A query for last week does not look at last year.
  • Old data is removed by dropping a partition, which is instant, instead of deleting millions of rows.
  • Indexes are per partition, so the ones for recent data stay small and in memory.
CREATE TABLE events (
  id          BIGINT NOT NULL,
  device_id   BIGINT NOT NULL,
  recorded_at TIMESTAMPTZ NOT NULL,
  payload     JSONB
) PARTITION BY RANGE (recorded_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

DROP TABLE events_2025_10;   -- a year of retention: remove the oldest month in an instant

For tables of events, logs and measurements, this is often all the partitioning that is ever needed.

In an interview. Bring up partitioning when your estimate shows the data or write rate exceeding one machine, and say three things: the key and why (“by user ID, since nearly every query is for one user”), the scheme (“hashed into a fixed number of logical partitions so we can rebalance”), and the cost (“queries across users, such as global search, will go to a separate index”). Then name the hot-key risk before the interviewer does.

Common mistakes

  • Sharding before exhausting simpler options.
  • Hash mod N with a server count that will change.
  • A partition key with few values, or one that changes.
  • A key that is absent from the common queries, turning them into scatter-gather.
  • Sequential keys with range partitioning, sending all writes to one partition.
  • Ignoring skew and discovering the hot key in production.
  • Too few logical partitions, fixed forever.
  • Assuming transactions and unique constraints still span everything.
  • Cutting over without comparing old and new data.

Key points

  • Partitioning splits data across machines to scale writes and size. Use it after cheaper options are exhausted.
  • Range partitioning keeps neighbors together and risks hot spots. Hash partitioning spreads evenly and loses range queries. A directory gives full control at the cost of a lookup.
  • Hash mod N moves almost every key when N changes. Use a fixed number of logical partitions, consistent hashing, or automatic splitting.
  • Consistent hashing moves about one Nth of the keys when one of N servers changes. Virtual nodes even out the load.
  • The partition key should have many values, spread load evenly, appear in most queries and never change.
  • Skewed load creates hot spots that more machines do not cure. Split or isolate the hot keys.
  • Queries without the key fan out to every partition. Joins, transactions and unique constraints across partitions become expensive or unavailable.
  • Partitioning a table by time within one server is a simpler tool with different benefits.

Check yourself

A cache cluster assigns keys with hash mod N. You add one server to a cluster of 20. What happens to the hit ratio, and why?

It collapses. About 95% of keys now map to a different server than the one that holds their cached value, so nearly every lookup misses until the cache refills. With consistent hashing only about one key in 21 would have moved.

An events table is range-partitioned by timestamp across ten shards. One shard is overloaded with writes and nine are idle. Why, and what would you change?

New events all have recent timestamps, so they all fall in the newest range. Partition by something that spreads writes, such as a hash of the device ID, and keep the timestamp as the sort order within each partition.

Why are virtual nodes used in consistent hashing?

With one position per server, the arcs are uneven and a departing server’s whole load lands on one neighbor. Giving each server many positions makes each server’s share an average of many small arcs, which evens the load, and spreads a departing server’s keys over many others.

You partition orders by customer ID. Which of these becomes expensive: listing a customer’s orders, looking up an order by its ID, a report of all orders placed yesterday?

Listing a customer’s orders stays on one shard. Looking up by order ID alone must ask every shard, unless the order ID encodes the customer or a global index maps one to the other. Yesterday’s report must scan every shard, and is better served from a separate analytical copy.

A cluster averages 40% utilization and one shard is at 100%. Will doubling the number of shards fix it?

Probably not. If the cause is one very active key, that key still lives on a single shard after the split. The fix is to split the hot key across partitions, isolate it, or absorb its reads with a cache.

What is the difference between partitioning a table by month inside PostgreSQL and sharding?

Table partitioning divides one table into several on the same server. It makes time-bounded queries and deleting old data cheap, and does not add capacity. Sharding places the pieces on different servers, which adds capacity and brings the costs of cross-shard queries and transactions.
