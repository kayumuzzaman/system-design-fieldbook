How one slow service takes down the rest

The photo app’s web service calls the feed service, which calls a small tags service to decorate each photo with its tags. Tags are a minor feature. One afternoon the tags service becomes slow: its responses take five seconds instead of fifty milliseconds.

Each request to the feed service now holds one of its threads, or connections, for five seconds instead of a twentieth of one. By Little’s law (), the same arrival rate needs a hundred times as many threads, and the pool has twenty. Within seconds every thread is waiting on tags. Requests that do not need tags at all queue behind them. The web service, waiting on the feed service, fills up the same way. The whole product is down because of a feature most users would not have missed.

Three observations from this shape everything that follows.

  • Slow is worse than down. A dead service refuses connections instantly, and callers move on. A slow one ties up its callers’ resources.
  • Failure travels through shared, limited resources. Threads, connections, memory, queue slots. Protecting those is the heart of resilience.
  • The right outcome was available. Photos without tags is a perfectly good page. The system failed because nothing told it to give up on the optional part.

The patterns below are introduced one at a time. The last section shows how they stack.

Timeouts and deadlines

The first defense is the simplest: never wait forever. Every network call needs a timeout, after which the caller stops waiting and treats the call as failed. Many client libraries ship with no timeout or with one measured in minutes, so this has to be set deliberately, for every dependency.

There are two to set. The connection timeout bounds how long to wait for a connection to be established, and can be short, since a healthy server accepts within milliseconds. The request timeout bounds the wait for a response.

Choosing the request timeout is the compromise of . Too long, and a slow dependency still ties up threads. Too short, and healthy but slightly slow responses are thrown away and retried, adding load. Start from measurement: a little above the dependency’s 99.9th percentile in normal operation. If that percentile is 300 ms, a timeout of 30 seconds protects nothing.

One deadline for the whole request

Separate timeouts at each layer have a flaw that only shows under stress.

Work done after the caller has given up is pure waste, and it is done exactly when the system is slowest and can least afford it. The fix is deadline propagation. The first service to receive the request decides when it must be finished, and passes that moment, or the time remaining, with every call it makes. Each service does the same for its own calls, and checks the deadline before starting anything expensive. gRPC does this as part of the protocol. Over plain HTTP it is a header that every service must read and forward.

A related rule: a caller’s timeout should be longer than the timeout of whatever it calls, so that the inner call can fail and be handled before the outer one expires.

Retries, and how they multiply

Many failures are brief: a dropped packet, an instance being replaced. Trying again usually works. gave the basic rules: retry only what might succeed, only operations that are safe to repeat, with a growing and randomized delay, and a limit.

The danger of retries is what they do under real failure. If a service is struggling because it is overloaded, each retry is additional load on it. And retries at several layers multiply.

If the service at the bottom starts failing, each user request turns into up to 27 calls to it: 3 layers, each trying 3 times. For every 1,000 user requests it receives 27 thousand calls, at the moment it is least able to cope. If every layer instead limits retries to 10% of its traffic, the same 1,000 requests become at most 1,331 calls.

Three measures keep retries from turning a small failure into a large one.

  • Retry at one layer. Usually the one closest to the failure, which knows most about whether a retry makes sense. Layers above pass the error up.
  • A retry budget. Limit retries to a fraction of normal traffic. Google’s SRE book describes a budget of 10%: a client may retry only while its retries are below a tenth of its requests. In normal conditions almost nothing needs retrying, so the budget is never reached. During an outage it caps the extra load at 10% instead of 200%.
  • Say “do not retry”. A service that is rejecting requests because it is overloaded should say so distinctly, with a 503 or 429 and a Retry-After header, and callers should respect it.

One special kind of retry is the hedged request from : send a second copy of a slow request before the first has failed. It cuts tail latency and must be limited in the same way, to a few percent of traffic.

Circuit breakers

Timeouts bound how long each call waits. If a dependency is down for ten minutes, every call during those ten minutes still waits for the full timeout before failing. A circuit breaker notices that a dependency is failing and stops calling it for a while.

type State = "closed" | "open" | "half-open";

class CircuitBreaker {
  private state: State = "closed";
  private failures = 0;
  private openedAt = 0;

  constructor(
    private threshold = 5,                       // consecutive failures before opening
    private coolDownMs = 10_000,                 // how long to stay open before testing again
    private now: () => number = Date.now,
  ) {}

  async call(action: () => Promise): Promise {
    if (this.state === "open") {
      if (this.now() - this.openedAt < this.coolDownMs) {
        throw new Error("circuit open");         // fail at once, without touching the dependency
      }
      this.state = "half-open";                  // cool-down over: let a trial request through
    }
    try {
      const result = await action();
      this.state = "closed";
      this.failures = 0;
      return result;
    } catch (error) {
      this.failures += 1;
      if (this.state === "half-open" || this.failures >= this.threshold) {
        this.state = "open";
        this.openedAt = this.now();
      }
      throw error;
    }
  }
}

In a test against a dependency that was down, twenty calls through this breaker produced five real attempts and fifteen immediate failures. After the cool-down, one trial call went through, failed, and the breaker reopened. When the dependency recovered, the next trial succeeded and traffic resumed.

Production breakers refine this in ways worth knowing.

  • They open on a failure rate over a recent window, such as more than half of the last 20 calls, instead of consecutive failures. Slow calls count as failures.
  • They allow a limited number of trial calls when half-open, not unlimited traffic.
  • They are scoped carefully. One breaker for a whole service hides a single bad instance behind the good ones. A breaker for each instance is the outlier detection of .
  • They are visible. A breaker opening is an event to log and alert on.

A breaker is only as useful as what happens when it is open. Failing fast gives the caller its thread back. What the user sees depends on the fallback, covered under graceful degradation below.

Bulkheads

A ship’s hull is divided into watertight compartments so that one breach does not flood the vessel. A bulkhead in software divides a shared resource so that one misbehaving dependency cannot consume all of it.

The simplest form is a limit on calls in progress for each dependency.

class Bulkhead {
  private inUse = 0;
  constructor(private limit: number) {}

  async run(action: () => Promise): Promise {
    if (this.inUse >= this.limit) throw new Error("bulkhead full");    // reject, do not queue
    this.inUse += 1;
    try { return await action(); } finally { this.inUse -= 1; }
  }
}

const tagsCalls = new Bulkhead(30);       // at most 30 calls to the tags service at once

Had the feed service in the opening example allowed at most a few of its twenty threads to wait on tags, the rest would have stayed free. The same idea applies at other scales: separate connection pools for separate databases, separate worker pools for cheap and expensive requests, separate queues for each tenant (), and at the largest scale, separate copies of the whole system ().

The limit rejects when full, on purpose. Queuing the excess would bring back the waiting that the bulkhead exists to prevent.

Rate limiting

The patterns so far protect a caller from its dependencies. Rate limiting protects a service from its callers: it caps how many requests each client may make in a period. It serves several purposes at once.

  • Fairness. One client’s runaway script should not use the capacity that everyone shares.
  • Abuse. Password guessing, scraping and spam all depend on making many requests.
  • Cost. Some operations cost real money each time they run.
  • A commercial boundary. Plans are often defined by request quotas.

Three decisions define a limiter: what is counted (requests, or a weighted cost), who it is counted for (an API key, a user, an IP address, a tenant), and the algorithm. There are five standard algorithms, and the differences between them are a favorite interview topic.

Token bucket

Each client has a bucket that holds up to N tokens. Tokens are added at a steady rate. A request takes one token. If the bucket is empty, the request is rejected.

Two numbers describe it: the refill rate, which is the long-run average allowed, and the bucket size, which is the largest burst. This matches how real clients behave. A page load fires eight requests at once and then nothing for a minute, which a token bucket allows while still capping sustained use. It needs two stored values for each client, the token count and the time of the last update, and it is the most widely used algorithm. Stripe and AWS API limits work this way.

A token bucket under a burst

The bucket starts full. See how long a burst is absorbed and what is rejected after that.

The bucket starts full with 50 tokens and refills at 10 a second. Requests arrive at 30 a second, so the bucket runs dry after 2.5 s, having let 75 requests through at full speed. From then on only 10 a second pass. Over 10 s, 150 of 300 requests are allowed and 150 are rejected.

class TokenBucket {
  private tokens: number;
  private last: number;

  constructor(private ratePerSecond: number, private capacity: number, now = Date.now()) {
    this.tokens = capacity;                      // start full: a new client may burst
    this.last = now;
  }

  allow(now = Date.now(), cost = 1): boolean {
    const refill = ((now - this.last) / 1000) * this.ratePerSecond;
    this.tokens = Math.min(this.capacity, this.tokens + refill);
    this.last = now;
    if (this.tokens < cost) return false;
    this.tokens -= cost;
    return true;
  }
}

The cost parameter lets expensive operations take more tokens than cheap ones, which is fairer than counting every request as one.

Leaky bucket

Requests enter a queue of fixed size and are processed at a constant rate, like water leaving a bucket through a small hole. If the queue is full, new requests are rejected. The output is perfectly smooth whatever the input looks like, which suits a downstream system that needs an even flow. The price is delay: a burst is not rejected, it waits, and a request at the back of a long queue may be stale by the time it is served. The term is also used for a meter that counts the same way without queuing anything, which behaves much like a token bucket.

Fixed window counter

Divide time into windows, such as each clock minute, and keep one counter for each client for the current window. Increment it on each request and reject when it exceeds the limit. This is the simplest algorithm and the cheapest: one counter, which in Redis is one INCR on a key that expires. Its weakness is at the edges.

Sliding window log

To be exact, store the timestamp of every request for each client. On a new request, discard timestamps older than the window, count what remains, and allow the request if the count is under the limit. There is no boundary problem, because the window is always the last sixty seconds from now. The cost is memory: a limit of 1,000 an hour means up to 1,000 timestamps for each active client, about 8 KB, which for a million clients is 8 GB. It is used where precision matters and limits are small.

Sliding window counter

The practical compromise keeps the fixed window’s two cheap counters and removes most of its error. Keep the count for the current window and for the previous one. Estimate the rate over the last full window by weighting the previous count by how much of that window still overlaps.

estimate = previous count × (share of the previous window still in view) + current count limit 50 a minute, previous minute 42, this minute 18 so far, 15 seconds in: estimate = 42 × (45 ÷ 60) + 18 = 49.5 under 50, so the request is allowed
class SlidingWindowCounter {
  private windowStart = 0;
  private current = 0;
  private previous = 0;

  constructor(private limit: number, private windowMs: number) {}

  allow(now = Date.now()): boolean {
    const start = Math.floor(now / this.windowMs) * this.windowMs;
    if (start !== this.windowStart) {
      // Move on. A gap of more than one window means the previous one was empty.
      this.previous = start - this.windowStart === this.windowMs ? this.current : 0;
      this.current = 0;
      this.windowStart = start;
    }
    const elapsed = (now - start) / this.windowMs;                     // 0 to 1 through this window
    const estimate = this.previous * (1 - elapsed) + this.current;     // weight the previous window
    if (estimate >= this.limit) return false;
    this.current += 1;
    return true;
  }
}

The estimate assumes requests in the previous window were evenly spread, which is not exactly true, and the error is small in practice. Cloudflare, which uses this approach, reported that across 400 million requests from 270,000 sources, only 0.003% were wrongly allowed or wrongly limited. In a test of the code above against the boundary burst in , a fixed window allowed all 200 requests and this counter allowed 101.

Limiting in practice

Tell the client. A rejected request gets status 429 Too Many Requests with a Retry-After header saying when to try again. Good APIs also report the limit on successful responses, so that clients can pace themselves before being rejected. An IETF draft standardizes two header fields for this, still an Internet-Draft as of October 2026.

HTTP/1.1 200 OK
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=37;t=22

HTTP/1.1 429 Too Many Requests
Retry-After: 22

The first response says the policy is 100 requests per 60-second window, with 37 remaining and 22 seconds until the window resets.

Limit at more than one level. A limit for each user does nothing against a thousand users arriving at once. Stripe has described running four limiters together: a request rate limiter for each user, a limit on each user’s concurrent requests, which catches slow, expensive calls that a rate limit misses, and two load shedders that protect the fleet as a whole, covered below.

Counting across many servers. With twenty API servers, a limit kept in each server’s memory lets a client have twenty times the intended rate. The counters must be shared, usually in Redis, and the update must be atomic. A limiter that reads the count, checks it, and writes it back in separate steps will let two simultaneous requests both pass on the last token. Use a single atomic operation, or a short server-side script. designs this in full, including what to do when the counter store is unavailable.

Decide the failure mode. If the limiter itself breaks, requests can be let through, which risks overload, or rejected, which is an outage. For most APIs letting them through is right, with the load shedding below as the backstop.

Load shedding

Rate limiting caps each client. Load shedding is the server protecting itself regardless of who is asking: when it has more work than it can do, it rejects some of it immediately.

This sounds like giving up, and it is the opposite. A server that accepts everything when overloaded becomes slow for everyone. Requests queue, wait longer than their callers will wait, and are finished after the callers have gone. The server is working at full effort and producing nothing useful.

Ways to shed, from simple to refined:

  • A cap on requests in progress. Beyond it, respond 503 at once. This is a bulkhead at the front door, and alone it prevents the collapse in the figure.
  • Bounded queues with deadlines. Never queue without limit, and discard queued requests whose deadline has passed before working on them.
  • Priorities. Not all requests are equal. Shed health-check noise and background refreshes before checkout. Google’s SRE book describes tagging every request with one of four levels of criticality and shedding the lowest first. Stripe’s load shedders reserve a share of capacity for critical API methods and drop test-mode traffic before live traffic.
  • Adaptive limits. A fixed concurrency cap is a guess. Adaptive limiters watch latency and adjust the cap continuously, raising it while latency holds and cutting it sharply when latency climbs, as TCP does with its congestion window ().

Clients can take part too. In adaptive throttling, as described in the SRE book, each client tracks how many of its recent requests the server accepted. When it sees rejections, it starts dropping a share of its own requests locally, before sending them, so that an overloaded server is spared even the cost of saying no.

probability that the client rejects a request itself = max(0, (requests − K × accepts) ÷ (requests + 1)) with K usually 2

Graceful degradation

Every pattern above ends with some call not being made or not succeeding. Graceful degradation is deciding in advance what the user gets in that case, so that a partial failure produces a reduced page instead of an error page.

When this is unavailableServe this instead
Tags, recommendations, countersThe page without them
Personalized feed rankingA simple chronological feed
Fresh dataThe last cached copy, marked as possibly stale
SearchBrowsing, with search shown as temporarily off
WritesRead-only mode, or accept the write into a queue to apply later

This requires knowing which dependencies are essential and which are optional, and it is a product decision as much as a technical one. A useful exercise is to list every dependency of a page and write beside each what the page should do without it.

Fallbacks carry a risk of their own. A fallback path that runs only during failures is code that is rarely exercised and never under load. If it is heavier than the normal path, such as falling back from a cache to the database, it will make an overload worse at the worst moment. The Cloudflare incident in was a fallback that did more work than the path it replaced. Prefer fallbacks that do less, and test them regularly.

Failures that sustain themselves

The most troublesome outages have a peculiar shape. Something triggers an overload: a deployment, a traffic spike, a brief dependency failure. The trigger is fixed within minutes. The system stays down for hours.

Researchers named these metastable failures in 2021. The system has two stable states, healthy and overloaded, and a feedback loop holds it in the bad one after the original cause is gone. The loops are usually built from the well-intentioned mechanisms in this chapter.

  • Retries. Overload causes failures, failures cause retries, retries are more load.
  • Cold caches. A restart empties the cache, so every request hits the database, which is too slow to refill the cache ().
  • Slow failure paths. Handling an error costs more than handling a success.
  • Restart storms. Every instance restarts at once and all of them load their state from the same place.

Google Cloud, 12 June 2025

A change to a quota-checking component used by most Google Cloud APIs contained a code path with no error handling for a missing field, and it had been released without a feature flag. When a policy record with blank fields was written, it replicated to every region within seconds, and the component began crashing in a loop everywhere at once. Engineers identified the cause and disabled the faulty code path in about forty minutes.

The outage did not end there. In the largest regions, the restarting tasks all fetched their data from the same database together, which overloaded it. Google’s report states that the component lacked randomized exponential backoff for this case. Recovery in one region took up to two hours and forty minutes, most of it after the original fault had been removed.

Both halves are instructive. The trigger was a change that reached every region at once, which returns to. The duration was a recovery that created its own overload.

Getting out of a metastable state means breaking the loop, which usually means reducing load well below normal: shed most traffic, turn off retries, bring instances back a few at a time, warm caches before admitting users. Preventing one means having, in advance, the limits this chapter describes: retry budgets, backoff with jitter everywhere including at startup, and load shedding that is configured and tested.

Testing that it works

Resilience code runs only when things go wrong, so in normal operation it is untested. A breaker with a mistaken threshold or a fallback that throws will be discovered during an incident unless it is exercised deliberately.

  • Inject faults. Add delay or errors to a dependency in a test environment, then in production for a small share of traffic, and confirm that callers time out, break and fall back as designed. A service mesh can inject these without code changes ().
  • Test overload, not only failure. Push a service past its capacity and check that useful throughput stays flat instead of collapsing, and that it recovers when the load drops.
  • Rehearse. Scheduled exercises in which a dependency is taken away on purpose ().

Putting the patterns together

For one outgoing call, the patterns nest. From the outside in:

For incoming requests: rate limits for each client at the edge, a concurrency cap and priority-based shedding at each service.

You will rarely write these from scratch. Libraries provide them for every major language, and a service mesh can apply timeouts, retries, breakers and outlier detection without touching application code. What cannot be delegated is the judgment: which dependencies are optional, what each timeout should be, what the fallback is, and at which single layer retries happen.

In an interview. When the interviewer asks “what if this service is slow?”, walk the stack briefly: “the caller has a timeout based on the dependency’s p99.9, a circuit breaker so that we fail fast during an outage, and a fallback, which here is the feed without recommendations. Retries happen at one layer only, with backoff, jitter and a budget, and the endpoint is idempotent.” For rate limiting, name an algorithm and say why: “token bucket for each API key, because it allows short bursts and caps the average, with counters in Redis updated atomically”. Be ready to explain the fixed-window boundary problem.

Key points

  • Failures cascade through shared, limited resources held by waiting callers. A slow dependency does more harm than a dead one.
  • Every call needs a timeout based on measured latency. Propagate one deadline so that all layers stop together.
  • Retries multiply across layers. Retry at one layer, with backoff, jitter and a budget, and only what is idempotent.
  • A circuit breaker stops calling a failing dependency and tests it periodically. A bulkhead caps how much any one dependency can consume.
  • Rate limiting caps each client. Token bucket allows bursts, leaky bucket smooths them, fixed windows are simple and leak at boundaries, sliding logs are exact and costly, sliding counters approximate well with two numbers.
  • Load shedding rejects excess work early so that useful throughput holds at capacity instead of collapsing.
  • Decide in advance what users get when each dependency is missing, and keep fallbacks lighter than the normal path.
  • Outages often outlast their trigger because retries, cold caches and mass restarts sustain the overload. Recovery needs limits too.

Check yourself

A service has 50 worker threads and normally handles 400 requests a second at 100 ms each. A dependency used by a quarter of requests slows to 10 seconds, with no timeout set. What happens, and how quickly?

About 100 requests a second need the slow dependency, and each now holds a thread for 10 seconds. The 50 threads are all occupied within half a second, and after that every request, including the three-quarters that never touch the dependency, waits for a thread. The service is effectively down in under a second. A timeout and a bulkhead on calls to that dependency would have confined the damage.

Why can a propagated deadline save more work than a separate timeout at each layer?

With separate timeouts, each layer measures from when it started, so lower layers keep working after the original caller has given up, and nobody cancels them. With one deadline passed down, every layer knows the moment after which the result is useless and stops, or declines to start. Under overload this removes exactly the work that was going to be wasted.

Four layers each make up to three attempts. A service at the bottom is failing. How many calls can one user request cause, and what are two ways to prevent it?

Three to the fourth power, 81. Retry at a single layer and let the others pass the error upward. And apply a retry budget, such as allowing retries only up to 10% of a client’s request volume, which caps the added load at about 10% for each layer however bad the failure is.

Describe the three states of a circuit breaker and what moves it between them.

Closed: calls pass through and failures are counted. When failures exceed a threshold it becomes open: calls fail immediately without reaching the dependency. After a cool-down it becomes half-open: a trial call is allowed. If the trial succeeds it closes, and if it fails it opens again for another cool-down.

A limit of 100 requests a minute uses a fixed window counter. How can a client send 200 requests in a few seconds without being limited, and which algorithms avoid this?

By sending 100 at the very end of one window and 100 at the start of the next, where the counter has reset. Each window sees only 100. A sliding window log avoids it exactly, a sliding window counter avoids it approximately with two counters, and a token bucket avoids it because the bucket, once emptied, refills only at the steady rate.

A token bucket holds 20 tokens and refills at 5 a second. A client that has been idle sends 40 requests at once. How many pass, and when can it next send one?

The bucket is full, so 20 pass and 20 are rejected. Tokens return at 5 a second, so the next request can pass 200 ms later. The size sets the largest burst, 20, and the refill rate sets the sustained maximum, 5 a second.

Why does an overloaded server that accepts every request deliver fewer useful responses than one that rejects some?

Accepted requests queue. As the queue grows, waiting time exceeds what callers will tolerate, so they time out and often retry, while the server goes on to process the abandoned requests. Its capacity is spent on work whose results are discarded. Rejecting the excess immediately keeps the queue short, so the requests it does accept finish while their callers are still waiting.

In the Google Cloud outage of June 2025 the faulty code path was disabled in about forty minutes. Why did recovery in the largest region take much longer?

When the crashed tasks restarted, they all loaded their data from the same database at once, and in the largest region that surge overloaded the database. The restarts had no randomized exponential backoff. The recovery itself created a new overload, which had to be managed by throttling task creation. It is an example of a failure that sustains itself after its trigger is gone.
