Three pictures of one design

The two previous chapters ended in code. This one is about what comes before the code: a sketch that a colleague or an interviewer can read in a minute and argue with. A diagram is a cheap place to be wrong. Moving a box costs nothing. Moving a class after three people have built on it costs a week.

UML, the Unified Modeling Language, is a standard notation for drawing software designs. It is maintained by a standards body, and its current version, 2.5.1, dates from 2017. Its full specification is enormous and mostly unused. What survives in daily practice is a small core that nearly every engineer can read, which is exactly what makes it worth learning.

DiagramQuestion it answersShowsDraw it when
ClassWhat exists, and how is it connected?Classes, interfaces and the relationships between them. No timeAlways. It is the map of the design
SequenceWho calls whom, in what order?One scenario, as messages between objects, top to bottom in timeFor each important use case, to check that the classes can carry it out
StateWhat can happen to this one object?The states an object can be in and the events that move it between themFor any object with a lifecycle: an order, a booking, an upload

The three are views of the same design and must agree. Every message in a sequence diagram has to be an operation on a class in the class diagram. Every event in a state diagram has to arrive from somewhere in a sequence. Drawing all three is the quickest way to find the hole in a design.

The example for the whole chapter is one feature of the photo app: a user uploads a file into an album. All the code shown was run, and the diagrams were checked against it.

Sketch, not blueprintUML was once promoted as a way to specify software completely before writing any. That use has faded. The use that remains is the sketch: a few boxes and arrows, drawn to think and to explain, kept only while they are useful. Draw to that standard. Correct notation matters only so far as it lets others read the sketch without asking.

Class diagrams

A class diagram shows the static structure of a design: the types that exist and the lasting connections between them. It contains no order and no time.

One class

Each class is a box with up to three compartments: the name, the attributes (TypeScript calls them fields or properties) and the operations (methods). An attribute is written name: type and an operation name(parameters): returnType, each after a mark for its visibility. The order “name, then type” is the same as in TypeScript, so translating in either direction is mechanical.

A diagram is not obliged to show everything. Constructors, getters and obvious fields are usually left out, and a box with only a name is perfectly good notation when the details do not matter to the point being made.

The lines between classes

The six lines fall into three groups, and telling the groups apart is most of what there is to know.

  • “Has” lines are solid. An association means that objects of one class hold a lasting reference to objects of another, typically in a field. A composition, drawn with a filled diamond at the owner, is the strong form: the part is created by the whole, belongs to exactly one whole, and is destroyed with it. Aggregation, the hollow diamond, claims something in between and is seldom worth the argument about whether it applies.
  • “Is” lines end in a hollow triangle, pointing at the more general type. Solid for a class extending a class, which UML calls generalization. Dashed for a class implementing an interface, which UML calls realization.
  • “Uses” is a dashed line with an open arrow. A dependency means one class mentions another without holding on to it: as a parameter, a return type or a local value. It is the weakest connection and the one most often left out to keep a diagram readable.

The direction of every arrow follows one rule: it points from the class that knows to the class that is known. Library knows about PhotoStore, and PhotoStore has never heard of Library. Getting this backward is the most common mistake in hand-drawn diagrams, and it matters, because the arrows are the design’s coupling made visible.

How many

Numbers at the ends of a line say how many objects take part. They are called multiplicities.

The last row is a reminder that a diagram can state a rule the type system cannot. “An order has at least one line” is an invariant, and writing 1..* on the diagram tells the reader that some code must enforce it ().

A whole diagram

Here is the part of the code that the top of the diagram describes. Compare them field by field.

export interface Validator {
  check(file: File): string | null; // a reason for refusing the file, or null
}
export interface Albums {
  find(id: string): Promise;
  save(album: Album): Promise;
}
export interface PhotoStore {
  save(id: string, bytes: Uint8Array): Promise;
}
export interface Notifier {
  photoAdded(album: Album, photo: Photo): void; // returns at once: sending happens later
}

export class Rejected extends Error {}

export class Uploader {
  private readonly validator: Validator;
  private readonly albums: Albums;
  private readonly store: PhotoStore;
  private readonly notifier: Notifier;
  private readonly newId: () => string;

  constructor(validator: Validator, albums: Albums, store: PhotoStore, notifier: Notifier, newId: () => string) {
    this.validator = validator;
    this.albums = albums;
    this.store = store;
    this.notifier = notifier;
    this.newId = newId;
  }
  async upload(albumId: string, file: File): Promise { /* shown with the next diagram */ }
}

The diagram shows something that is hard to see in the code: the shape of the dependencies. Four arrows leave Uploader, all ending at interfaces, and none arrives. A design in which one class has fifteen arrows leaving it, or in which arrows form a loop, shows its problem at a glance.

Sequence diagrams

A class diagram says what could talk to what. A sequence diagram shows one conversation: a single scenario, drawn as messages passing between objects, with time running down the page.

Each object taking part gets a vertical dashed line, its lifeline. A message is a horizontal arrow from the sender’s lifeline to the receiver’s, labeled with the operation being called. Reading down the page gives the order of events.

Here is the upload, first as a diagram and then as the method it describes.

async upload(albumId: string, file: File): Promise {
    const problem = this.validator.check(file);
    if (problem) throw new Rejected(problem);

    const album = await this.albums.find(albumId);
    const photo: Photo = { id: this.newId(), name: file.name, size: file.bytes.length };
    await this.store.save(photo.id, file.bytes);
    album.add(photo);
    await this.albums.save(album);
    this.notifier.photoAdded(album, photo);
    return photo;
  }
}

A test replaced the four collaborators with objects that record each call, ran upload with an acceptable file, and compared the record with the diagram: Validator.check, Albums.find, PhotoStore.save, Albums.save, Notifier.photoAdded, in that order. With a refused file, the record held one call.

Three habits make sequence diagrams useful and not merely decorative.

  • One scenario per diagram. A diagram that tries to show every branch becomes a flowchart that nobody can follow. Draw the main path, and use at most one or two frames for the branches that matter.
  • Use it to test the class diagram. As you draw each arrow, ask whether the receiving class has that operation and whether the sender has a way to reach the receiver. A missing field or method shows up at once.
  • Look at where the arrows start. In the figure every call starts at the uploader. That is one object coordinating four that do not know about each other, which is a deliberate shape. A diagram in which calls zigzag between all the objects describes a design where everything depends on everything.

The same notation serves at a larger scale. Replace objects with services and it is the sequence of calls in a distributed system, which is how the figures in the earlier parts of this book are drawn.

State diagrams

Some objects are interesting mainly for how they change. An upload is created, sends its bytes, is processed, and becomes a photo, or it fails along the way, is retried, or is canceled. What the object may do next depends on where it has got to. A state diagram shows the states one object can be in and the transitions between them.

ElementDrawn asMeaning
StateA rounded boxA condition the object stays in until something happens
TransitionAn arrow between statesA permitted move from one state to another
EventThe first word on the arrowWhat triggers the transition
GuardA condition in square bracketsThe transition happens only if this is true at that moment
ActionText after a slashSomething done as the transition happens, or on entering a state
Start and endA filled dot, and a dot in a ringWhere the object begins, and the states from which nothing more happens

The most valuable property of this diagram is what it leaves out. There is no arrow from Ready labeled cancel, so a finished upload cannot be canceled. There is no arrow from Pending labeled processed, so nothing can be processed before it has been sent. Each missing arrow is a decision, and drawing the diagram forces every one of them to be made.

Nine of the thirty-six cells are transitions. The other twenty-seven are things that must not happen, and a table has a cell for each of them, where a diagram has only an absence. Looking down a column is how omissions get noticed. Should it be possible to cancel during processing? The table shows that the present answer is no, and makes someone say whether that is intended.

The code can be a direct transcription of the table, which keeps the three in step.

export type UploadState = "pending" | "uploading" | "processing" | "ready" | "failed" | "canceled";
export type UploadEvent = "start" | "received" | "processed" | "error" | "retry" | "cancel";

// The whole state diagram as data: for each state, which events it accepts and where they lead.
const transitions: Record>> = {
  pending: { start: "uploading", cancel: "canceled" },
  uploading: { received: "processing", error: "failed", cancel: "canceled" },
  processing: { processed: "ready", error: "failed" },
  failed: { retry: "uploading", cancel: "canceled" },
  ready: {},
  canceled: {},
};

export class Upload {
  static readonly maxAttempts = 3;
  readonly id: string;
  private current: UploadState = "pending";
  private tries = 0;

  constructor(id: string) {
    this.id = id;
  }

  get state(): UploadState {
    return this.current;
  }
  get attempts(): number {
    return this.tries;
  }

  handle(event: UploadEvent): void {
    const target = transitions[this.current][event];
    if (!target) throw new Error(`an upload that is ${this.current} cannot ${event}`);
    if (event === "retry" && this.tries >= Upload.maxAttempts) throw new Error("no attempts left"); // the guard
    if (target === "uploading") this.tries += 1; // the action on the way in
    this.current = target;
  }
}

Every rule about an upload’s life is in one object, transitions, which can be read beside the diagram. The alternative is to scatter checks such as if (upload.status === "failed" || upload.status === "pending") through the code that handles each event, and a state machine implemented that way is one that nobody can draw. shows a second implementation, the state pattern, for cases where each state has substantial behavior of its own.

Common mistake. Modeling a lifecycle as a set of boolean fields: isUploaded, isProcessed, hasFailed, isCanceled. Four booleans allow sixteen combinations, of which six mean something. The rest, such as failed and processed at once, are bugs waiting for the code path that produces them. One field holding one of six named states cannot represent a state that does not exist.

Diagrams as text

A diagram drawn in a drawing tool goes stale the day after it is made, because updating it is a separate chore that nobody is asked to do. The remedy that has taken hold is to write diagrams as text, in the same repository as the code, and let a tool lay them out. They are then changed in the same commit as the code, compared line by line in review, and rendered wherever the documentation is displayed. Mermaid and PlantUML are the two widely used languages for this.

The notation is close to the picture: -->> is a dashed return, *-- a composition, ..|> a realization. The layout is the tool’s and is sometimes worse than a careful hand would manage. That is a fair price for a diagram that is still true next year.

Using the three together

In a design session or an interview the three diagrams are drawn in a loop, each correcting the others.

  1. Start with the class diagram, roughly. Write down the nouns of the problem as boxes with names only. Add the obvious connections.
  2. Walk the main scenario as a sequence. For each step, decide which object does it. This is where operations get their names and where missing classes appear: “something has to check the file, and it should not be the uploader”.
  3. Go back and fill in the class diagram with the operations the sequence needed and the fields that hold the references the arrows used.
  4. Draw a state diagram for anything with a lifecycle. Fill in the table of states and events, and decide every empty cell.
  5. Stop. Draw what settles an open question. A diagram of something everyone already agrees on is not worth the time.

In an interview. Nobody will mark you down for an arrowhead of the wrong style. They will notice if your diagram has no interfaces where behavior varies, if an arrow points the wrong way, or if you cannot trace the main use case through your own boxes. Say the scenario aloud while pointing: “the client calls upload on the uploader, which asks the validator…”. If you find you cannot, the design has a gap, and finding it yourself is a point in your favor.

Key points

  • Three diagrams carry a low-level design: class for structure, sequence for one scenario in time, state for one object’s life.
  • A class box lists a name, attributes and operations. Show only what the reader needs.
  • Solid lines mean “has”, a hollow triangle means “is a kind of” or “implements”, a dashed open arrow means “uses”. Arrows point from the knower to the known.
  • Multiplicities say how many, and can state rules the type system cannot.
  • A sequence diagram shows one scenario. Use it to test whether the classes can do what is asked.
  • A state diagram lists every permitted transition. What is not drawn is forbidden, and a state-by-event table makes each omission a visible decision.
  • The three views must agree with each other and with the code. Diagrams written as text and kept with the code stay true longest.

Check yourself

Translate into a class box: class Cart { private items: Item[] = []; readonly owner: User; add(item: Item): void; total(): number }.

A box named Cart. In the attributes compartment: − items: Item[] and + owner: User, the second marked read-only if that matters to the reader. In the operations compartment: + add(item: Item): void and + total(): number. In a fuller diagram the two attributes would more likely be drawn as lines: a composition or association from Cart to Item with multiplicity *, and an association from Cart to User with multiplicity 1.

class DiskStore implements PhotoStore and class CountingBag extends Bag. Which line and arrowhead does each get, and which way does it point?

Both end in a hollow triangle, and in both the triangle touches the more general type: PhotoStore and Bag. The first line is dashed, because a class realizes an interface. The second is solid, because a class generalizes a class.

An Order has one or more OrderLines, which are meaningless without it. A Team has members who are Users and who exist whether or not the team does. Draw the two relationships.

Order to OrderLine is a composition: a solid line with a filled diamond at Order, and multiplicity 1..* at the OrderLine end. Team to User is an association, or an aggregation with a hollow diamond at Team if you want to stress the grouping, with * at the User end. Deleting an order deletes its lines. Deleting a team does not delete its users.

In a sequence diagram, what is the difference between an arrow with a filled head, an arrow with an open head, and a dashed arrow?

A solid line with a filled head is a synchronous call: the sender waits until the receiver has finished. A solid line with an open head is an asynchronous message: the sender continues without waiting. A dashed line with an open head is a return, the answer to an earlier call.

You draw a sequence diagram and find you need an arrow from Uploader to Notifier, but in your class diagram Uploader has no connection to Notifier. What are your options?

Either the uploader should hold a notifier, in which case add the field and the association to the class diagram, or the uploader should not be the one sending the message. Perhaps the album announces changes to itself, or the uploader publishes an event that a separate listener turns into a notification. The disagreement between the two diagrams has exposed a real design decision.

An upload is Failed after three attempts and receives the event retry. Trace what the diagram and the code do.

The diagram has an arrow from Failed to Uploading labeled retry with the guard “attempts < 3”. With three attempts made, the guard is false, so the transition does not happen and the upload stays Failed. In the code, the transition table does contain an entry for retry in the failed state, and the following line checks the number of attempts and throws “no attempts left”. The only event that state now accepts is cancel.

A booking is modeled with the fields isPaid, isConfirmed and isCanceled. What is wrong, and what would you draw instead?

Three booleans allow eight combinations, and several are nonsense, such as canceled and confirmed together, or confirmed and unpaid if payment is required first. Nothing in the type prevents them. Draw a state diagram with the states that exist, perhaps Held, Paid, Confirmed, Canceled and Expired, decide the transitions with a state-by-event table, and store a single state field.
