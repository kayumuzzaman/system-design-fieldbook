A copy kept close

A cache is a store of results kept somewhere faster or nearer than the place they came from. When a result is needed again, it is taken from the cache instead of being fetched or computed afresh. Caching works because real workloads are repetitive: the same profile, product and query are requested over and over, and most data is read far more often than it changes.

You have met several caches in this book already. They sit at every layer between a user and the data.

Browser and CDN caching were covered in and , and the buffer pool in . This chapter is about the two in the middle, which you design yourself: a cache inside the application, and a shared cache service beside it.

Every cache makes the same trade. It gives speed and takes away certainty, because a copy can be out of date. All the difficulty of caching is in managing that.

What a cache buys

The benefit depends on one number, the hit ratio: the share of lookups the cache can answer. A hit costs one fast lookup. A miss costs that lookup and then the full original work.

The average falls from 20 ms without a cache to 3 ms. The 99th percentile is still a miss at 21 ms, because more than 1 request in 100 misses. A cache improves the typical request long before it improves the slowest ones.

Two lessons come out of the arithmetic. First, the load on the database follows the miss ratio, so the argument from applies here too: going from 90% to 95% hits halves the database’s work. Second, a cache does little for tail latency until the hit ratio is very high, since the slowest requests are the misses. If your problem is the 99th percentile, a cache alone will not solve it.

A third consequence is easy to overlook. Once a system depends on its cache, the database behind it is sized for the misses and not for the full load. If the cache is lost or emptied, the database receives ten times its usual traffic. A cache added for speed has become something the system cannot run without. Keep that in mind through the rest of the chapter.

Cache-aside

The standard pattern is cache-aside, also called lazy loading. The application manages the cache itself. On a read it looks in the cache first, and on a miss it loads from the database and stores the result. On a write it changes the database and removes the cached entry.

async function getPhoto(id: number): Promise {
  const key = `photo:v1:${id}`;

  const cached = await cache.get(key);
  if (cached !== null) return JSON.parse(cached);              // hit

  const photo = await db.queryOne("SELECT * FROM photos WHERE id = $1", [id]);
  if (photo) {
    const ttl = 300 + Math.floor(Math.random() * 60);          // 5 to 6 minutes
    await cache.set(key, JSON.stringify(photo), { EX: ttl });
  } else {
    await cache.set(key, "null", { EX: 30 });                  // remember "not found", briefly
  }
  return photo;
}

async function updateCaption(id: number, caption: string): Promise {
  await db.query("UPDATE photos SET caption = $1 WHERE id = $2", [caption, id]);
  await cache.del(`photo:v1:${id}`);                           // delete, do not update
}

Several decisions are packed into those few lines, and each is deliberate.

  • Every entry has a time to live (TTL), after which the cache discards it. Even with explicit deletion on writes, the TTL is the safety net that bounds how long any mistake can last.
  • The TTL is randomized. If many entries are written at the same moment with the same lifetime, they expire at the same moment. A little randomness spreads the reloads out.
  • “Not found” is cached too, for a short time. Otherwise every request for something that does not exist goes to the database.
  • The key carries a version. When the shape of the cached value changes in a new release, changing v1 to v2 makes old entries invisible to new code without having to clear anything.
  • A write deletes the entry and does not replace it. The next section explains why.

Cache-aside is popular because it fails safely. If the cache is unavailable, the code can fall through to the database. Only data that is actually requested gets cached. Its weaknesses are that the first request for anything is a miss, and that it has a race condition, described below.

Write-behind deserves caution. It is how a view counter or a “last seen” timestamp can be updated thousands of times a second without touching the database each time, and it is acceptable there because losing a few seconds of such updates does no harm. For anything that matters, the durability of the data has been handed to a system built for speed.

Invalidation

There is an old remark that the two hard problems in computing are naming things and cache invalidation. Invalidation means making sure a cached copy stops being used once the original has changed. There are only three tools.

  • Expiry. Let entries age out. Simple and always works, at the cost of serving data up to one TTL old. For much data this is fine: a follower count that is a minute behind harms nobody.
  • Explicit removal. Delete or replace the entry when the data changes. Fresher, and it requires every code path that changes the data to know every cache entry that depends on it.
  • Versioned keys. Put a version or timestamp of the underlying data in the key. When the data changes, the key changes, and the old entry is never asked for again. It expires on its own.

Explicit removal is harder than it looks, because the cache and the database are two systems with no transaction between them ().

The race in cache-aside

The window is small, since it needs a read to straddle a write, and at thousands of requests a second small windows are hit daily. This is why every entry needs a TTL even when writes delete: the TTL turns “wrong forever” into “wrong for five minutes”. For data where that is still too long, there are stronger measures:

  • Delete after commit, never before. Deleting first widens the window, because a read can reload the old value before the write lands.
  • Delete twice. Once at the write, and again a second or so later, to remove anything a slow reader stored in between.
  • Compare versions. Store a version number with each entry and refuse to overwrite a newer version with an older one.
  • Invalidate from the database’s change log. A separate process follows the stream of committed changes and deletes the affected keys. Writers no longer need to know about the cache, and no change is missed. describes the mechanism.
Why delete instead of updateIf two writers each update the database and then set the cache, their cache writes can arrive in the opposite order from their database writes, leaving the older value cached. Deleting has no such problem: whichever order the deletes arrive in, the entry ends up gone, and the next reader loads the current value.

The practical position is to decide, for each kind of data, how stale it may be. That one decision usually settles the design.

DataTolerable stalenessApproach
Like and follower counts, trending listsMinutesTTL alone

A user’s own settings, just changedNone visible to that userDelete on write, and read your own writes from the database

Eviction

A cache has a fixed amount of memory. When it is full and a new entry arrives, something must be removed. The rule for choosing what is the eviction policy, and it should keep the entries most likely to be asked for again.

PolicyRemovesGood when
Least recently used (LRU)The entry unused for the longest timeRecent use predicts future use. The usual default.
Least frequently used (LFU)The entry used the fewest timesA stable set of popular items. Resists a one-off scan flushing the cache.
First in, first outThe oldest entrySimplicity matters more than hit ratio
Shortest time to liveThe entry closest to expiringLifetimes reflect importance
NoneNothing. New writes are refused.The store holds data that must not vanish

Redis and Valkey let you choose with the maxmemory-policy setting. The default is to evict nothing and return errors on writes when memory is full, which is right for a primary data store and a surprise for a cache. Set a memory limit and a policy such as allkeys-lru deliberately. implements LRU from scratch.

How large should a cache be? Large enough to hold the working set, the items that account for most requests. Because popularity is very uneven, a cache holding a small fraction of all items often serves a large fraction of all requests. Measure the hit ratio and the eviction rate. A high eviction rate with a low hit ratio means the cache is too small for the workload.

How caches fail

Caches cause a distinctive family of outages, all variations on the database suddenly receiving traffic the cache had been absorbing.

Stampede

A popular entry expires. In the moment before anyone has reloaded it, every request for it misses, and each one runs the same expensive query. This is a cache stampede, also called a thundering herd or dogpile.

The fix is to make sure only one caller rebuilds a given entry while the rest wait for it. Within one process this is a few lines:

const inFlight = new Map>();

function singleFlight(key: string, load: () => Promise): Promise {
  const existing = inFlight.get(key);
  if (existing) return existing as Promise;        // someone is already loading it

  const promise = load().finally(() => inFlight.delete(key));
  inFlight.set(key, promise);
  return promise;
}

// Usage: the database is asked once, however many callers arrive together.
const photo = await singleFlight(`photo:${id}`, () => loadPhotoFromDatabase(id));

Across many application servers the same idea needs a lock held in the cache itself, taken with an atomic “set if absent” operation and a short expiry. Two other techniques avoid the stampede altogether. Stale-while-revalidate keeps serving the old value while one caller refreshes it in the background. Refreshing early, at a random time shortly before expiry, means a popular entry is renewed by a single request before it ever expires.

In production. Ask of every cache: if it were emptied right now, would the system survive? If the answer is no, the cache is a critical dependency and needs the treatment that implies: replication, monitoring, a tested recovery procedure, and protection for the database behind it such as load shedding ().

Where the cache lives

An in-process cache is a data structure inside the application’s own memory. It is the fastest possible, with no network involved, and each server has its own, so ten servers hold ten copies that can disagree and that all vanish on deployment. It suits small, slowly changing data such as configuration and feature flags.

A distributed cache is a separate service that all application servers share. It costs a network round trip of a fraction of a millisecond per lookup, survives deployments, and gives every server the same view. The two are often layered: a tiny in-process cache with a lifetime of a few seconds in front of a shared cache.

Valkey is the open-source fork of Redis created in 2024 and maintained under the Linux Foundation. The two remain largely compatible, and managed services offer both (). The richer data types are a real advantage. A sorted set gives a leaderboard, and an atomic increment with an expiry gives a rate limiter, with no read-modify-write in the application.

Two cautions about these stores. Replication between a cache node and its replica is asynchronous, so a failover can lose recent writes (). That is acceptable for a cache and is the reason not to keep the only copy of anything important there. And they execute commands one at a time, so a single slow command, such as listing all keys, stalls every other client.

What to cache, and what not to

Good candidates share three properties: they are read much more often than they change, they are expensive to produce, and being slightly out of date is acceptable.

  • Results of expensive queries: aggregates, counts, rankings, the first page of a popular list.
  • Assembled objects that take several queries to build, such as a profile with its counts.
  • Responses from other services, especially slow or rate-limited ones.
  • Sessions and tokens looked up on every request.
  • Rendered fragments of pages.

Poor candidates are data that changes as often as it is read, data that must be exact such as balances and stock at the moment of purchase, and results unique to one request that will never be asked for again.

Take care with keys. A cache key must include everything the result depends on. If a response varies by user, language or permission level and the key does not, one user receives another’s data, which is the same failure as the CDN one in and just as serious.

Common mistake. Adding a cache to hide a slow query. The query is still slow on every miss, the system now has invalidation bugs it did not have before, and the database is sized on the assumption that the cache works. Fix the query first (). Cache when the work is inherently expensive or the volume is inherently high.

In an interview. When you add a cache, state four things: what is cached and under what key, the pattern (usually cache-aside), how it is invalidated and how stale it can be, and what happens on a miss storm. “Redis in front of the database” with none of these is a box on a diagram. With them it is a design.

Common mistakes

  • No TTL, so a missed invalidation lasts forever.
  • Identical TTLs on entries created together.
  • Updating the cache on write instead of deleting, and invalidating before the database commit.
  • A key that omits something the value depends on.
  • No protection against stampedes on popular keys.
  • Not caching “not found”.
  • A database that cannot survive an empty cache, with no plan for when it happens.
  • Treating the cache as durable storage.
  • Never measuring the hit ratio, so nobody knows whether the cache is earning its complexity.
  • Caching to hide a problem that should be fixed.

Key points

  • A cache trades certainty for speed. Its value is set by the hit ratio, and the database’s load by the miss ratio.
  • Caches improve average latency long before they improve the tail.
  • Cache-aside is the default: read the cache, load on a miss, write the database then delete the entry.
  • Give every entry a TTL, and randomize it. Decide for each kind of data how stale it may be.
  • Invalidation spans two systems with no transaction between them, so races exist. The TTL bounds the damage.
  • When memory is full an eviction policy decides what goes. LRU is the usual choice.
  • Stampedes, mass expiry and cold starts all send the database traffic it was not sized for. Coordinate reloads and plan for an empty cache.
  • Fix slow queries before caching them.

Check yourself

A cache has a 95% hit ratio. A hit takes 1 ms and a database query 40 ms. What is the average latency, and what is the 99th percentile?

The average is 0.95 × 1 + 0.05 × 41 = 3 ms. The 99th percentile is 41 ms, because 5% of requests miss and the slowest 1% are all among them.

Why does a write delete the cached entry instead of writing the new value into it?

Two concurrent writers can update the database in one order and the cache in the other, leaving the older value cached. Deletes have no order to get wrong: the entry ends up absent and the next read loads the current value from the database.

A dashboard loads slowly for a few seconds exactly every ten minutes. What is the likely cause and fix?

A stampede. A popular entry with a ten-minute TTL expires and many requests recompute it at once. Have one caller rebuild it while the others wait or are served the old value, or refresh it shortly before it expires.

After a deployment that restarted the cache cluster, the database fell over. Why, and what would have prevented it?

The cache came back empty, so every request missed and the database received the whole load, which it had not been sized for. Prevent it by restarting cache nodes one at a time, warming the cache before taking traffic, using persistence or replicas, and limiting the rate of requests allowed through to the database.

Requests arrive for thousands of user IDs that do not exist. The cache hit ratio drops and database load rises. What is happening?

Nonexistent keys are never cached, so every one of those requests reaches the database. Cache the “not found” result for a short time, reject IDs that are malformed, and consider a Bloom filter of valid IDs in front.

Which would you cache with a five-minute TTL and which not at all: a product’s review count, a user’s permission to view a document, the stock level shown on a product page, the stock check at checkout?

The review count and the stock level shown while browsing can be cached, since a few minutes of staleness does no harm. The permission check and the stock check at checkout should read current data, because acting on a stale answer shows someone a private document or sells something that is not there.
