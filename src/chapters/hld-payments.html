The problem

The problem. Design the payment system of an online marketplace. Customers pay for orders by card; the card is charged when the order ships; sellers are paid every week, less a commission; customers can be refunded. Nobody may be charged twice, no payment may be lost, and the company’s books must agree with the payment provider’s and the bank’s to the cent.

Payments look like a simple request: charge this card this amount. What makes them hard is that the effect happens elsewhere. A payment service provider is a company that accepts card and other payments on a merchant’s behalf, talks to the card networks and banks, and pays the collected money out to the merchant’s bank account later. Every call to it can succeed, fail, or time out with the outcome unknown, and its own confirmation may come minutes later by webhook. Exactly-once delivery does not exist (), so the design has to make repeated attempts harmless and then prove, every day, that nothing slipped through. In the terms of , this is a money problem: each payment taking effect exactly once, and books that reconcile.

Payments are not a scale problem (). A hundred writes a second is easy for one relational database, and that is where the ledger belongs: one database, with transactions, constraints and serializable checks where needed (). The number that matters is the cost of a mistake. If one message in a hundred is lost on each hop and nobody uses keys, the chapter’s simulation charges about 2% of payments twice: forty thousand customers a day.

Amounts are integers in the currency’s minor unit, cents here, so 100.00 euros is 10000; a float cannot hold 0.10 exactly, and the test summed a million payments of 0.10 as floats to 100,000.00000133. Every request that moves money has an idempotency key made from the business intent, the order and the step, not from the request, so that whoever retries, from wherever, sends the same key (). Webhooks are verified by signature (), stored before they are acknowledged, and ignored if their event id has been seen.

The payment’s state, its attempts, the ledger and the inbox share one database so that “mark captured and post to the ledger” is one local transaction, and events for other services leave through an outbox in the same transaction (). Balances are not stored as numbers someone can overwrite: an account’s balance is the sum of its lines, with snapshots for speed if needed.

Step 5: The design

Money in. The order service asks the payment service for money. The payment service records the payment with its key, then asks the provider for a hosted payment page; the customer types the card number on the provider’s page, so our servers never see it, which keeps them outside most of the card industry’s security rules. A card payment happens in two steps here. Authorizing asks the card’s bank to reserve the amount; to capture is to tell it to take the money that was reserved, which a marketplace does when the order ships, as the vending machine chapter did with coins ().

The record. Every movement of money becomes a ledger transaction in the same database transaction as the state change that caused it. Other services learn about payments from events, never by reading the ledger’s tables.

Money out and the check. A payout service pays each seller what the ledger says they are owed, weekly. A reconciliation job compares the ledger, the provider’s settlement files and the bank statement every day, and sends every difference to a queue that people work through.

Step 6a: Exactly once, built from retries

A payment crosses two hops: the app or the order service calls the payment service, and the payment service calls the provider. On either hop a request can be lost, so the far side never acts, or the response can be lost, so the far side acted and the caller does not know. To the caller both look the same, a timeout, and the only safe reaction is to ask again. The chapter simulated 100,000 payments in which each message on each hop is lost with some probability, and every caller tries three times.

for (let a = 0; a < 3 && !success; a += 1) {    // the app tries three times
      if (lost()) continue;                         // request to the payment service lost
      // --- inside the payment service
      let result: string | undefined = keys === "no keys" ? undefined : done.get(appKey);
      for (let s = 0; s < 3 && result === undefined; s += 1) {   // the service tries the provider three times
        if (lost()) continue;                       // request to the provider lost
        const providerKey = keys === "one key, end to end" ? appKey : undefined;
        const id = provider.charge(order, providerKey);
        if (lost()) continue;                       // the provider charged, but its answer was lost
        result = id;
      }
      if (result !== undefined && keys !== "no keys") done.set(appKey, result);
      // --- back to the app
      if (result === undefined) continue;           // the service answers 504: outcome unknown
      if (lost()) continue;                         // the answer to the app was lost
      success = true;
    }

With no keys, about twice the loss rate of orders were charged more than once: 1,996 of 100,000 when one message in a hundred is lost on each hop. A key sent by the app to the payment service halved that, to 980, because the payment service now recognized the app’s retries. It did not stop the payment service’s own retries to the provider, which charged again whenever the provider’s answer was lost. Only the same key carried all the way to the provider, which then returns its saved result for a repeated key, brought double charges to zero at every loss rate tested. This is the end-to-end argument in money (): each layer that retries must pass the key down, and the layer where the effect happens must check it.

Keys solve repeats; they do not solve not knowing. At 5% loss, 78 payments in 100,000 ended with the card charged and the app told that it failed, because all three of the app’s attempts timed out. So a timeout must never be recorded as a failure. The payment stays in a state that says “unknown”, and two things resolve it: the provider’s webhook, which arrives when it arrives, and a job that asks the provider for the outcome of every payment unknown for more than a few minutes, by the same id. The order service shows “payment processing” meanwhile, and the customer is not invited to pay again.

Common mistake. Generating a fresh key for each attempt. A key made per HTTP request protects nothing, because a retry is a new request. Make the key from the intent, such as the order and the step, and store it before the first attempt.

Step 6b: The ledger

Double-entry bookkeeping records every movement of money as a transaction of two or more lines on different accounts whose amounts add up to zero, so that money is only ever moved, never created or lost, and the sum of all balances is always zero. Debits are positive and credits negative. The marketplace’s accounts are what the provider owes it, what it owes each seller, its commission, the provider’s fees as an expense, and its bank account.

// Posting is idempotent by transaction id: the same id twice records it once.
  post(id: string, at: number, memo: string, lines: Line[]): boolean {
    if (this.ids.has(id)) return false;
    if (lines.length < 2) throw new LedgerError("a transaction needs at least two lines");
    for (const l of lines) if (!Number.isSafeInteger(l.amount) || l.amount === 0) throw new LedgerError(`not a whole, non-zero amount: ${l.amount}`);
    if (lines.reduce((sum, l) => sum + l.amount, 0) !== 0) throw new LedgerError(`lines of ${id} do not add up to zero`);
    const previous = this.journal.length ? (this.journal[this.journal.length - 1] as Transaction).hash : "";
    const tx: Transaction = { id, at, memo, lines: lines.map((l) => ({ ...l })), previous, hash: "" };
    tx.hash = hashOf(tx);
    this.journal.push(tx);
    this.ids.add(id);
    for (const l of lines) this.balances.set(l.account, (this.balances.get(l.account) ?? 0) + l.amount);
    return true;
  }

The rules live in the one method that writes. A transaction whose lines do not add up to zero is refused; so is an amount that is not a whole number of cents. A transaction id seen before is recorded once, so a retried webhook cannot post a capture twice. Nothing updates or deletes a line: a mistake is corrected by a new transaction that reverses it, and the history shows both, the same append-only discipline as the expense-sharing chapter () at the scale of a company.

The test ran 100,000 random operations, captures, refunds, settlements and payouts, producing 152,283 transactions. The trial balance, the sum of every account, was zero after every one. Replaying the journal from the start produced the same 54 balances, and replaying it up to any moment gives the books as they stood then, which is what an auditor asks for (). Each transaction also carries a hash of the one before it, so the journal is a chain: the test changed two lines of transaction 1,234 by a cent each, keeping it balanced, and the chain check pointed to exactly that transaction. Ledger databases offer this tamper evidence as a feature (); in an ordinary database it is a column and a check.

Two practical points keep a ledger fast. Balances needed on every request, such as what a seller is owed, are kept in a balance table updated in the same transaction as the lines, and rebuilt from the lines to check it. And the ledger is written by one service only; everyone else reads events or reports, so that the rules cannot be bypassed.

Step 6c: Reconciliation

Settlement is the provider paying out the money it has collected for a merchant, less its fees, together with a file that lists every payment, refund and fee included. Matching that file, line by line, against the ledger is the daily reconciliation that introduced. The bank statement is the third record: the provider’s deposit must equal the file’s total.

for (const o of ours.filter((x) => x.day === day)) {
    seen.add(o.payment);
    const lines = byPayment.get(o.payment) ?? [];

    if (lines.length > 1) { add("charged twice"); continue; }
    const t = lines[0] as Theirs;
    if (t.gross !== o.amount) add("amount differs");
    else if (t.fee !== fee(t.gross)) add("fee differs");
    else add(t.day === day ? "matched" : "matched a day late");
  }
  for (const [payment, lines] of byPayment) if (!seen.has(payment) && lines.some((l) => l.day === day)) add("in their file, not in ours");

The match key is our own payment id, which the payment service sends to the provider with every call and which the provider prints in its file. The test built a day of 10,000 payments with problems put in on purpose, in known numbers, and the job found each one and reported nothing else.

The 42 payments captured shortly before the provider’s daily cutoff appeared in the next day’s file. Matched against today’s file alone, they were reported missing, 50 alarms instead of 8, which is how reconciliation jobs drown their readers in false alarms until nobody looks. The other categories each have their own repair: a missed webhook is recorded from the file; a capture we recorded that the provider does not have is reversed in the ledger and the order is checked; a second charge is refunded at once.

Some differences arrive weeks later. A chargeback is the reversal of a card payment by the customer’s bank after the customer disputes it, which takes the money back from the merchant along with a fee, whatever the merchant’s own records say. It appears in a settlement file as a negative line, is posted to the ledger as its own transaction against the seller or the marketplace, and is reconciled like everything else.

At ten times the orders, about a thousand payments a second at the peak, one database still holds the ledger, with read replicas for reports. At a hundred times, the ledger is partitioned, and the natural key is the account that most transactions touch, such as the seller, so that most transactions stay on one partition; a transaction across partitions then needs the techniques of the next chapter (). Reconciliation grows with volume but stays a daily batch job, run in parallel by provider and by day ().

In the real world

  • Stripe’s API documentation (as of October 2026) saves the status code and body of the first request made with an idempotency key, including errors, and returns them for retries; keys are up to 255 characters, may be removed after 24 hours, and a reused key with different parameters is an error.
  • Stripe’s documentation on placing holds (as of October 2026) says an authorization for an online card payment is usually valid for 7 days (5 for some merchant-initiated Visa payments), after which the funds are released and the payment canceled, and that capturing less than was authorized releases the rest.
  • Under the card industry’s security standard, PCI DSS 4.0.1, merchants that fully outsource payment processing, such as through a provider’s hosted page, qualify for the shortest self-assessment questionnaire, SAQ A, as an article of 11 March 2025 summarizes the standards council’s clarification.

In an interview. Draw the provider early and say the card never touches your servers. Then spend the time on correctness: a key per intent carried to the provider, a payment state for “unknown”, webhooks through an inbox, a double-entry ledger in integer cents written in the same transaction as the state change, and a daily reconciliation with a day of slack. Throughput will not be the question; double charges will.

Key points

  • A provider’s hosted page keeps card numbers off your servers; authorize at checkout and capture on shipment.
  • Every step that moves money carries a key derived from the intent, passed through every hop to the provider. Anything less leaves double charges.
  • A timeout means unknown, not failed. Resolve it with webhooks and status queries.
  • Record money in a double-entry ledger in whole cents: transactions that add up to zero, posted once by id, never edited, written in the same transaction as the state change.
  • Replaying the journal reproduces any past balance; a hash chain shows if history was altered.
  • Reconcile every day against the provider’s files and the bank, with a window for the cutoff, and treat each difference as work for a person.

Check yourself

The payment service passes the app’s key check, then calls the provider without a key and retries on timeout. Where can a double charge still come from?

From its own retries: if the provider charged but the answer was lost, the retry is a new charge. In the simulation that left 980 double charges per 100,000 at 1% loss. The key must be passed to the provider.

Why should the idempotency key be derived from the order and the step rather than generated per request?

Because a retry, from any caller, must send the same key. A key per request changes with every attempt and so never matches; a key from the intent is the same however often, and from wherever, the step is attempted.

Why is authorize-then-capture useful to a marketplace?

It reserves the money at checkout without taking it, so an order that cannot ship is released rather than refunded, and the customer is charged only when the goods leave. The authorization lapses after about a week, so capture must happen within that time.

Every transaction’s lines add up to zero. What does that guarantee about the whole ledger, and how is it checked?

That the sum of all account balances is zero: money moves between accounts but is never created or lost. The trial balance, the sum of every balance, is checked; in the test it was zero after each of 152,283 transactions.

A support agent wants to fix a wrong capture by changing its amount. What should happen instead?

A new transaction that reverses the wrong one, and another with the right amount. History then shows the mistake, the correction and who made it, and replaying the journal still reproduces every past state.

Why match against tomorrow’s settlement file as well as today’s?

Payments captured shortly before the provider’s cutoff appear in the next day’s file. Without that slack they look missing; in the test, 42 such payments turned 8 real alarms into 50.

The provider’s webhook for a payment arrives before the payment service has stored the payment. What should happen?

Store the event in the inbox and acknowledge it; process it when the payment exists, or retry later. Dropping it would lose the outcome; failing it would make the provider retry, which is acceptable but noisy. Its event id makes processing it twice harmless.
