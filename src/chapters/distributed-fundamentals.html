What changes when there is more than one machine

Part III ended with data copied and split across many machines. Each of those chapters met the same difficulties from a different side: a follower that falls behind, a failover that cannot tell a dead leader from a slow one, a cache that disagrees with its database. Part IV studies those difficulties directly.

A distributed system is a set of computers that work together by exchanging messages over a network. Three things that a single computer gives you for free are missing.

  • Failure is all or nothing on one machine. If the power fails, everything stops together. Across machines, any subset can fail while the rest carry on. This is partial failure, and it is the defining difficulty of the field.
  • There is no shared memory. One machine can learn about another only by receiving a message from it, and the message may be late, lost or out of date by the time it arrives.
  • There is no shared clock. Every machine has its own idea of the time, and the ideas differ.

The practical consequence is that no machine ever knows the current state of the whole system. It knows what it was told, some time ago, by whoever managed to reach it. Every technique in this part is a way of acting correctly on that kind of knowledge.

Eight assumptions that are false

In the 1990s engineers at Sun Microsystems listed the assumptions that newcomers to networked programming make without noticing. They are known as the fallacies of distributed computing, and code that looks correct usually fails because it relies on one of them.

The assumptionThe realityWhat it breaks
The network is reliablePackets are lost, connections reset, cables are cutCalls with no timeout and no retry
Latency is zeroEvery call takes time, and sometimes a great dealChatty designs that make hundreds of small calls
Bandwidth is infiniteLinks saturateSending whole objects where a small change would do
The network is secureAnything on the wire can be read or forged unless protectedTrusting internal traffic
Topology does not changeMachines are added, moved and replaced constantlyHard-coded addresses
There is one administratorParts of the path belong to other teams and other companiesAssuming you can fix or even see every problem
Transport cost is zeroSerializing data and moving it costs CPU and moneyIgnoring data transfer in the bill
The network is homogeneousDifferent hardware, software versions and configurations coexistAssuming every node behaves like the one you tested

A local function call obeys all eight. A remote call obeys none, and looks exactly the same in code. That resemblance is the trap.

What can happen to a message

When one machine sends a request to another and waits for the reply, six things can go wrong, and the sender can observe none of them directly.

  • The request is lost on the way.
  • The request is delayed, in a queue or on a congested link.
  • The receiver has crashed, or crashes while handling it.
  • The receiver is alive and has stopped responding for a while.
  • The receiver handled the request and the reply is lost.
  • The reply is delayed.

The sender’s only evidence in every case is silence. It cannot tell “the work was not done” from “the work was done and I was not told”. This single ambiguity is why retries can duplicate work, why payments can be charged twice, and why exists as a chapter.

Networks do fail in practice. Published surveys of real incidents record data centers split in two by a misconfigured switch, links that passed traffic in one direction only, and network cards that corrupted a fraction of packets. A network fault that cuts some machines off from others while both groups keep running is called a network partition.

The timeout is the only detector

Since a failed machine sends no announcement, the only way to detect failure is to wait for a reply and give up after some time. That time is a timeout, and choosing it is a compromise with no correct answer.

  • Too short, and healthy machines that are briefly slow are declared dead. The work is retried elsewhere, adding load to a system that was slow because it was already loaded, and possibly being done twice.
  • Too long, and every real failure costs that much waiting before anything reacts.

There is no safe value because delays have no upper limit. A packet can sit in a queue. A machine can freeze for seconds, as a later section shows. On an ordinary network and ordinary hardware, anything that usually takes a millisecond will occasionally take a second.

The conclusion to hold on to is that a timeout tells you a machine is unresponsive. It never tells you the machine is dead. A design that acts as if the two were the same will, sooner or later, have two machines doing a job meant for one. This was the split brain of . In practice, systems measure response times and set timeouts from the observed distribution, such as a high percentile with a margin, and combine them with retries and limits on retries ().

Kinds of failure

To reason about a system, you need to say which failures it is expected to survive. The standard categories, from mildest to worst:

Failure modelThe nodeExample
Crash-stopStops and never returnsA machine is destroyed
Crash-recoveryStops, and may return later having lost whatever was only in memoryA process restarts after a power cut
OmissionRuns and fails to send or receive some messagesA full queue drops requests
TimingResponds correctly and too lateA long pause, an overloaded disk
ByzantineDoes anything at all, including sending wrong or contradictory answersCorrupted memory, a bug, a compromised machine

Most systems inside one organization are designed for crash-recovery failures and an unreliable network, and assume that a node which responds is telling the truth. Tolerating Byzantine failures, where nodes may lie, costs far more machines and messages. It is the province of blockchains and of some aerospace systems, and this book does not go further into it.

The failures that cause the longest outages are often none of the clean cases above. A machine that is slow, that drops one request in ten, or that is reachable from some peers and not others, passes its health checks and keeps receiving work. These are sometimes called gray failures. They are the reason for the passive health checks in : judge a machine by what happens to real requests.

A machine can stop without knowing

One failure deserves its own section because it defeats code that looks obviously correct. A running program can be suspended for seconds at any point, between any two lines, and has no way of noticing.

  • Garbage collection. Some language runtimes stop all application threads to reclaim memory. Pauses are usually milliseconds and can reach seconds with large heaps.
  • Virtual machines. The hypervisor can suspend a virtual machine, for example to move it to another host.
  • The operating system. A process can be descheduled in favor of others, or stall while waiting for a slow disk or for memory that was swapped out.

A lease is a lock with an expiry time: “you are the leader for the next ten seconds”. The figure shows why a node’s own belief that it still holds one is worthless. The fix cannot be on the paused node, since it does not know it was paused. It has to be on the receiving side: the storage system must be able to recognize and reject a write from a holder whose lease has passed. The mechanism is a fencing token, a number that increases every time the lease is granted, and explains it.

The general lesson is that a node cannot trust its own view of its role. Whether a node is the leader, holds a lock or is even considered alive is decided by the rest of the system, usually by a majority vote, and a node must be prepared to discover that the decision changed while it was not looking.

Two kinds of clock

Every computer has a clock, driven by a quartz crystal that counts oscillations. Operating systems expose it in two forms, and using the wrong one is a classic bug.

Time-of-day clockMonotonic clock
AnswersWhat time is it?How long since I last asked?
ValueSeconds since 1 January 1970, UTCAn arbitrary counter, meaningless on its own
Can jump backwardYes, when it is correctedNo
Comparable between machinesRoughlyNot at all
Use forTimestamps shown to people, expiry datesTimeouts, durations, rate limits
 
// Wrong: the time-of-day clock can be adjusted while the work runs
const start = Date.now();
await doWork();
const elapsedMs = Date.now() - start;        // can be negative, or far too large

// Right: a monotonic clock only moves forward
const t0 = performance.now();
await doWork();
const elapsed = performance.now() - t0;

The time-of-day clock is kept roughly correct by the Network Time Protocol (NTP), in which each machine periodically asks time servers and adjusts itself. An adjustment can move the clock backward. So can a leap second, an extra second occasionally added to the world’s official time to keep it in step with the Earth’s rotation.

At midnight UTC on 1 January 2017 a leap second was inserted. Cloudflare’s DNS software computed how long a lookup had taken by subtracting one time-of-day reading from another. For some lookups that straddled the leap second, the answer was negative. The negative number eventually reached a random number function that does not accept negative input, and the code failed. At the peak about 0.2% of DNS queries to Cloudflare were affected, and the fix took until 06:45 UTC to reach every data center. The root cause, in Cloudflare’s words, was the belief that time cannot go backward.

The end of leap secondsLeap seconds have caused enough trouble that the international body responsible for time standards voted in 2022 to stop inserting them by 2035. Until then, many large operators avoid the jump by “smearing” the extra second: running their clocks very slightly slow for a day so that no single second repeats.

Clocks disagree

Quartz crystals do not all run at the same rate, and the rate changes with temperature. The gradual divergence is clock drift, and the difference between two clocks at a given moment is clock skew. Synchronization keeps skew bounded and never removes it.

  • Over the public internet, NTP typically keeps a machine within some tens of milliseconds of true time, and worse when the network is congested.
  • Inside a well-run data center, a few milliseconds or better is usual.
  • Cloud providers now offer much tighter synchronization from their own reference clocks. AWS reported in 2023 that its time service keeps instances within 100 microseconds over NTP, and within 40 with hardware support.
  • A misconfigured or isolated machine can be wrong by seconds, minutes or years, and nothing on the machine itself will say so.

Even a small skew makes timestamps from different machines unsafe for deciding which of two events came first.

This is the weakness of the “last write wins” rule from : “last” is judged by clocks that do not agree. Rules to take from it:

  • Never order events on different machines by their wall-clock timestamps when the order affects correctness.
  • Never use a timestamp alone as a unique identifier or a version number. Two events can share one.
  • Expiry by wall-clock time needs a margin at least as large as the worst skew you are prepared to tolerate.
  • Monitor clock offset on every machine and remove from service any that drift too far.

Logical clocks: order without time

If physical time cannot order events, something else must. The insight, due to Leslie Lamport in 1978, is that for correctness we rarely need to know when something happened. We need to know what could have influenced what. Event A happened before event B if they occurred in that order on the same machine, or if A was the sending of a message and B was its receipt, or through a chain of such steps. If neither happened before the other, they are concurrent: neither could have known about the other.

A Lamport clock captures this with one counter per machine and two rules. Increase the counter for every local event and every message sent, and attach it to the message. On receiving a message, set the counter to one more than the larger of its own value and the value in the message.

class LamportClock {
  private time = 0;

  tick(): number {                       // before a local event, or before sending
    return ++this.time;
  }

  receive(remote: number): number {      // on receiving a message stamped `remote`
    this.time = Math.max(this.time, remote) + 1;
    return this.time;
  }
}

Lamport timestamps give every event a number such that causes always have smaller numbers than their effects. Break ties with a machine ID and you have a total order that all machines agree on, which is enough to build many protocols. What they cannot do is run the inference backward. From the numbers 3 and 4 alone, you cannot tell whether the events were related or concurrent.

A vector clock can. Each machine keeps a counter for every machine, not only itself, and messages carry the whole list. Comparing two lists entry by entry shows whether one event preceded the other or whether they were concurrent. That is exactly what a replicated database needs to know when it finds two versions of a value: if one descends from the other, keep the newer, and if they are concurrent, there is a real conflict to resolve. The cost is a list that grows with the number of participants.

Modern databases often combine physical and logical time. A hybrid logical clock stays close to wall-clock time, so timestamps are meaningful to people, and adds a logical counter that preserves the ordering guarantees of a Lamport clock when physical clocks are tied or run backward. CockroachDB and YugabyteDB work this way. Google’s Spanner takes another route: its clock service reports an interval that is guaranteed to contain the true time, using GPS receivers and atomic clocks to keep the interval to a few milliseconds, and a transaction waits out the uncertainty before committing so that timestamp order matches real order.

Designing for an unreliable world

The facts of this chapter translate into a short list of habits that appear in every later chapter.

BecauseDo thisCovered in
Any call can fail or hangPut a timeout on every remote call, and decide what happens when it fires
A missing reply does not mean the work was not doneMake operations safe to repeat, then retry
Messages arrive late, twice and out of orderNumber them, and make receivers tolerate all three
Clocks disagreeOrder by sequence numbers or logical clocks, not wall timeThis chapter
A node cannot judge its own statusDecide by majority, and fence out stale holders
Failures are partialLimit what one failure can affect, and degrade instead of stopping
You cannot foresee every interleavingTest by injecting faults: kill nodes, delay and drop messages, skew clocks

The last row matters more than it looks. Distributed bugs live in rare orderings of events that ordinary testing never produces. The teams that run these systems well test them by breaking them deliberately, and independent analyses such as the Jepsen project have found correctness bugs in most distributed databases they have examined, including widely used ones.

Common mistake. Treating a remote call as a function call. A library that makes a network request look like user.getOrders() hides that the line can take thirty seconds, fail halfway, or succeed on the other side while failing on yours. Keep remote calls visible in the code, and give each one a timeout and an answer to “what if this never returns?”.

In an interview. When a design has two services talking, expect the question “what if this call fails?”. A strong answer distinguishes the cases: “if the request never arrived, a retry is harmless, and if it arrived and the reply was lost, a retry would repeat it, so the operation carries an idempotency key”. Saying that a timeout cannot distinguish slow from dead, and designing so that it does not need to, shows you understand the field.

Common mistakes

  • Remote calls with no timeout.
  • Assuming a timeout means the operation did not happen.
  • Retrying operations that are not safe to repeat.
  • Measuring durations with the time-of-day clock.
  • Ordering events from different machines by timestamp, or resolving conflicts by “latest timestamp”.
  • Check-then-act on a lease or lock with nothing on the other side to reject a stale holder.
  • Assuming a node that answers its health check is healthy.
  • Testing only the case where everything works.

Key points

  • Distributed systems fail partially. No machine knows the current state of the whole.
  • A missing reply does not reveal whether the request was lost, the receiver failed, or the work was done and the reply lost.
  • A timeout detects unresponsiveness and cannot distinguish a slow machine from a dead one.
  • A process can be paused for seconds without knowing, so a node’s belief about its own role may be out of date.
  • Use monotonic clocks for durations. Time-of-day clocks can jump, and they differ between machines.
  • Do not order events across machines by wall-clock time. Logical clocks order events by causality instead.
  • Design for it: timeouts on every call, operations that are safe to repeat, decisions by majority, and testing by fault injection.

Check yourself

A service calls a payment provider and the call times out. Has the customer been charged?

It is impossible to know from the timeout. The request may never have arrived, the provider may have failed before charging, or the charge may have succeeded and the reply been lost. The safe designs are to send the request with an idempotency key so it can be repeated without charging twice, or to query the provider for the outcome.

Why is there no correct value for a timeout?

Network and processing delays have no fixed upper bound. Any finite timeout will sometimes fire for a machine that is merely slow. Shortening it detects real failures sooner and wrongly condemns more healthy machines. Lengthening it does the opposite.

A function logs Date.now() before and after an operation and occasionally reports a negative duration. What happened, and what should it use?

The time-of-day clock was adjusted backward between the two readings, by a time synchronization correction or a leap second. Durations should be measured with a monotonic clock, such as performance.now(), which never goes backward.

Two replicas accept writes to the same key 50 ms apart and resolve the conflict by keeping the higher timestamp. Under what condition is the later write lost?

When the clock of the replica that took the earlier write is more than 50 ms ahead of the other. Its timestamp is then higher although its write came first, and the later write is discarded.

Event X has Lamport timestamp 12 and event Y has 15. What can you conclude?

Only that Y did not happen before X. X may have happened before Y, or the two may be concurrent. Lamport timestamps guarantee that a cause has a smaller number than its effect, and a smaller number does not prove causation. Vector clocks are needed to tell the two cases apart.

A worker checks that it holds a lock, then writes to storage. How can two workers both write, and where must the fix be applied?

The first worker can be paused after the check, for longer than the lock’s expiry. The lock is given to a second worker, and when the first resumes it writes as well. The paused worker cannot detect this, so the storage system must reject writes carrying an older fencing token than one it has already seen.
