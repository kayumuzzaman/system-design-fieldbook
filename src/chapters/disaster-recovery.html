What redundancy does not cover

Earlier chapters made the photo app hard to stop. The database has replicas in three zones. Objects are stored with eleven nines of durability. A failed server is replaced within a minute. Then an engineer, meaning to clean up a test table, runs a DELETE on the production table.

Every protection listed works exactly as designed. The delete is written durably, replicated to all three zones in milliseconds, and survives any hardware failure. The data is gone from every copy at once. This is the sense in which replication is not a backup: replication keeps copies identical, so it copies mistakes as faithfully as it copies everything else.

A backup is a copy that differs from the live data in three ways, and it needs all three.

  • Separate in time. It holds the data as it was, so a change made now does not alter it.
  • Separate in place. It survives the loss of the site, region or provider that holds the original.
  • Separate in authority. The credentials, people and software that can damage the original cannot damage it.

Disaster recovery, shortened to DR, is the wider discipline: the plans, copies and standby systems that bring a service back after an event that ordinary redundancy cannot absorb.

Two objectives

defined the two numbers that every recovery design is built to.

  • The recovery point objective, RPO, is how much recent data you can afford to lose, measured as time. An RPO of one hour means that after recovery, at most the last hour of changes is missing.
  • The recovery time objective, RTO, is how long the service may be down while you recover.

Both are business decisions with engineering prices. Each step toward zero costs more, steeply at the end. They also differ by data. In the photo app, losing an hour of uploaded photos is serious and visible. Losing an hour of “recently viewed” history is nothing. Classify the data and set objectives for each class, because protecting everything to the standard of the most precious part is expensive, and protecting everything to the standard of the least is negligent.

The third row is a design opportunity. Data that can be recomputed from other data does not need backing up, only a tested way to rebuild it, as discussed.

Kinds of backup

A full backup copies everything. It is simple and self-contained, and for a large database it is slow and expensive to take every day. Two schemes reduce the cost by copying only changes between full backups.

type Backup = { day: number; kind: "full" | "incremental" | "differential"; sizeGb: number };

/** The backups needed to restore the state as of the end of `day`. */
export function restoreSet(backups: Backup[], day: number): Backup[] {
  const upTo = backups.filter((b) => b.day <= day).sort((a, b) => a.day - b.day);
  const lastFull = upTo.findLastIndex((b) => b.kind === "full");
  if (lastFull < 0) throw new Error("no full backup to start from");
  const after = upTo.slice(lastFull + 1);
  const lastDiff = after.findLastIndex((b) => b.kind === "differential");
  // a differential replaces everything between the full backup and itself
  const tail = lastDiff >= 0 ? after.slice(lastDiff) : after;
  return [upTo[lastFull], ...tail];
}

For a 500 GB database that changes by 10 GB a day, a week of incrementals stores 560 GB and a week of differentials stores 710 GB. Restoring Thursday reads 540 GB either way, from five backups in one case and two in the other. The count matters more than it looks: one unreadable incremental breaks every restore that comes after it in the chain.

Whatever the method, a backup must be consistent: it must represent the data at one moment, not half of one transaction and half of the next. Database backup tools arrange this. Copying a running database’s files with an ordinary file copy does not, and produces something that may or may not start.

Point-in-time recovery

A nightly backup has an RPO of up to a day: whatever happened since the last one is lost. Closing that gap uses something the database already produces. explained that every change is first written to a log. If that log is copied somewhere safe as it is written, then a backup plus the log can reproduce the database at any moment after the backup, by replaying changes up to that moment and stopping. This is point-in-time recovery, PITR.

It was tested for this chapter on a real PostgreSQL 16 server. The setup is three settings and one command.

wal_level = replica
archive_mode = on
archive_command = 'test ! -f /backup/archive/%f && cp %p /backup/archive/%f'
pg_basebackup -D /backup/base -c fast

The test then followed the scenario from the start of the chapter. A table had 1,000 rows when the base backup was taken. Another 500 were added. A few seconds later a DELETE with no WHERE removed all 1,500, and one new row was inserted after that. To recover, the base backup was copied to a new directory and given a target time two seconds before the delete.

restore_command = 'cp /backup/archive/%f %p'
recovery_target_time = '2026-10-10 16:52:46.469874+00'
recovery_target_action = 'promote'
LOG:  starting point-in-time recovery to 2026-10-10 16:52:46.469874+00
LOG:  restored log file "000000010000000000000002" from archive
LOG:  restored log file "000000010000000000000003" from archive
LOG:  recovery stopping before commit of transaction 733, time 2026-10-10 16:52:48.492862+00

The recovered database had 1,500 rows, the largest ID was 1,500, and the row inserted after the mistake was absent. The last log line shows the server reaching the delete’s commit and declining to apply it.

Three practical points come with it.

  • Recovering loses what came after. The row inserted after the delete is gone from the recovered copy. For that reason the usual practice is to recover into a new database, copy the lost rows back into the live one, and leave later legitimate changes in place. That requires knowing when the mistake happened, which is one more job for the deployment markers and audit logs of .
  • Replay takes time. Recovery replays every change since the base backup. A base backup taken weekly means up to a week of log to replay. Frequent base backups keep recovery short.
  • The archive is part of the backup. A gap in the archived log ends recovery at the gap. Monitor that archiving is succeeding, and store the archive with the same care as the backups.

Managed database services provide this as a setting, usually with a retention period of days to weeks. Turn it on, and find out what the retention is before you need it.

Where backups live

A long-standing rule of thumb, attributed to the photographer Peter Krogh, is called 3-2-1: keep three copies of anything important, on two different kinds of storage, with one of them off-site. Two extensions are now common: one copy that cannot be altered or deleted, and zero errors when a restore is tested.

Each element of the figure answers a threat from the table above.

  • Another region survives the loss of a site.
  • Another account, with its own administrators, survives a compromised or deleted production account. Production should be able to write new backups there and unable to read, change or delete old ones.
  • Immutability. Object stores can lock an object so that it cannot be overwritten or deleted until a date passes, even by the account’s owner. Combined with the versioning described in , it is the main defense against ransomware, which looks for backups and destroys them first.
  • Encryption, with the keys backed up separately. An encrypted backup whose only key was on the machine that burned is noise.

Not everything worth backing up is in a database. A recovery also needs the definitions of the infrastructure, the configuration, the secrets, the container images and the DNS records. If those exist only in the environment that was lost, the data has nowhere to be restored to. Keeping infrastructure as code in version control, as advised, is a large part of disaster recovery for everything that is not data.

How long to keep them

Backups must reach back further than the time it takes to notice a problem. A bug that corrupts a little data each day may go unseen for weeks. Keeping every daily backup forever is costly, so retention is usually thinned with age: every day for a week, one a week for a month, one a month for a year.

type Keep = { daily: number; weekly: number; monthly: number };

/** Given the dates of existing backups (newest first), returns the ones to keep. Dates are YYYY-MM-DD. */
export function retain(dates: string[], keep: Keep): Set {
  const sorted = [...dates].sort().reverse();
  const kept = new Set(sorted.slice(0, keep.daily));
  const pick = (bucketOf: (d: string) => string, n: number) => {
    const seen = new Set();
    for (const d of sorted) {
      const b = bucketOf(d);
      if (seen.has(b)) continue;          // only the newest backup in each week or month
      seen.add(b);
      if (seen.size > n) break;
      kept.add(d);
    }
  };
  const weekOf = (d: string) => { const t = new Date(d + "T00:00:00Z"); const day = (t.getUTCDay() + 6) % 7; t.setUTCDate(t.getUTCDate() - day); return t.toISOString().slice(0, 10); };
  pick(weekOf, keep.weekly);
  pick((d) => d.slice(0, 7), keep.monthly);
  return kept;
}

Applied to 400 daily backups with a policy of 7 daily, 4 weekly and 12 monthly, it keeps 20 and reaches back more than ten months. Retention has a legal side too. Some records must be kept for years, and personal data that a user asks you to delete must eventually leave the backups as well, which argues for a stated maximum age.

A backup is not proven until it is restored

Backup jobs fail quietly. The job reports success and wrote an empty file. The tool’s version no longer matches the database. The credentials expired in March. The disk filled and the last good backup is from the spring. None of these is visible until someone tries to restore, and the worst time to find out is during the disaster.

The only evidence that a backup works is a restore. Make it routine and automatic:

  1. On a schedule, restore the latest backup into a fresh, isolated environment.
  2. Start the database and run checks: it starts, the row counts are plausible, the newest record is recent, a few known queries return the expected answers.
  3. Record how long it took. That figure, and not the one in a planning document, is the copy-and-replay part of your RTO.
  4. Alert if any step fails, and alert if no backup has succeeded within the expected interval. The absence of a backup is the condition to watch for, since a job that never ran reports no error.

How long a restore takes

Restore time grows with the data, and it is easy to hold an RTO that was true two years ago. The arithmetic is short.

Copying 500 GB back at 100 MB a second takes 85.3 min. Add 45 min to notice, decide, provision and verify, and the service returns after about 2.17 hours. With a backup every 24 hours and no log archiving, up to 24 hours of changes are gone. When the data has grown ten times, the same restore takes 15 hours unless the speed grows with it.

Two parts of the bar are often forgotten. The first half hour is people: noticing, understanding, and deciding to declare a disaster, which nobody does lightly. And the restore speed in the widget is whatever the slowest link allows, be it the backup storage, the network or the new disks. Measure it. When the answer no longer fits the objective, the options are a faster path, smaller units to restore through partitioning, or a standby that is already running.

Standby strategies

Restoring from backups into nothing is the cheapest plan and the slowest. Shorter objectives need part of the system to exist in the recovery location beforehand. AWS’s guidance names four strategies in order of cost, and the terms are widely used.

StrategyIn the recovery region, alwaysTo recover
Backup and restoreBackupsCreate infrastructure, deploy, restore data
Pilot lightA replicated database and the definitions of everything elseStart the application servers, promote the database, redirect traffic
Warm standbyA complete, small, running copyScale it up, promote the database, redirect traffic
Active-activeA full copy already serving usersStop sending traffic to the failed region

The last two are the multi-region designs of , and everything said there about failover applies: spare capacity must already exist, the procedure should need as little as possible from control planes during the incident, and a standby that never takes traffic is a standby nobody has tested.

These strategies protect against losing a site. None of them replaces backups. A warm standby with a replicated database receives the mistaken delete as quickly as any other replica. Recovery from bad data and recovery from a lost site are separate problems, and a complete plan has an answer to each.

The recovery plan

The technical pieces are worth little without a plan people can follow under stress, at night, possibly without the colleague who knows the system best.

  • A written runbook for each scenario: commands, in order, with expected results and what to do when a step fails. Stored where it can be read when the main systems are down. A runbook kept only in the wiki that the outage took down is a known and repeated mistake.
  • An order of recovery. Services depend on each other. Identity, DNS, the secrets store and the network usually have to come back before anything else can start. Work out the order beforehand, and watch for circular dependencies, such as a deployment system that needs the service it is trying to restore.
  • Authority. Who may declare a disaster and start a failover that may lose data? Hesitation over this decision is often the largest part of an outage.
  • Emergency access. If single sign-on is down, how do engineers reach the cloud console? Sealed emergency credentials, tested and monitored, answer this.
  • Communication. Who tells customers, through what channel, hosted where? A status page should not share fate with the product.

Then practice. A tabletop exercise walks through a scenario on paper and finds gaps in the plan cheaply. A game day does it for real: restore the database from backup, fail over to the other region, on a planned date with everyone watching. Each exercise finds something, usually something small and fatal: an expired credential, a missing permission, a step that only one person knew.

Three incidents

GitLab, January 2017: five mechanisms, one accident

GitLab’s own published account is one of the most instructive documents on this subject, because nothing in it is exotic. On 31 January 2017 the secondary database of GitLab.com fell too far behind the primary to catch up, and an engineer set about rebuilding it, which begins with emptying its data directory. Late in the evening, after hours of trouble, the command to empty the directory was run on the primary by mistake. It was stopped within seconds. About 300 GB was already gone.

The lessons are the content of this chapter.

  • Backups that are not tested are not backups. The nightly dumps had been failing silently because the job used an older version of the tool than the database it was dumping.
  • Failures must be visible. The job’s error emails existed and were being rejected before anyone saw them. Nothing alerted on the absence of a recent backup.
  • Replication is not a backup, and here it was the thing being repaired when the accident happened.
  • Restore time is part of the design. Copying 300 GB at the roughly 60 megabits a second those disks allowed takes over eleven hours on arithmetic alone.
  • People make mistakes under pressure, late at night, on the wrong one of two similar servers. The company said afterward that its focus would shift from preventing such commands toward making recovery fast and making it obvious which machine a session is on.

Among the changes GitLab committed to were continuous log archiving for point-in-time recovery, automated testing of restores, and monitoring of the backups themselves.

OVHcloud, March 2021: the backup in the same building

On 10 March 2021 a fire destroyed one of OVHcloud’s data centers in Strasbourg and damaged a second on the same campus. Many customers lost their servers, and some then found that their backups were gone too, because the backups had been stored in the same building or the one beside it. In 2023 French courts awarded damages to two customers. In one case the contract had described the backup as physically isolated from the server, and the court found that it had not been.

The lesson is the “1” in 3-2-1, with a sharper edge: know where your backups physically are. A backup service bought from the same provider, in the same region, at the default settings, may be closer to the original than its name suggests.

UniSuper, May 2024: the provider deletes the account

UniSuper is an Australian pension fund with more than 600,000 members. In May 2024 its services went offline for over a week. A joint statement with Google Cloud explained that a misconfiguration during the provisioning of UniSuper’s private cloud had led to the deletion of its subscription. UniSuper had duplicated its environment across two geographies as protection against outages, and the deletion removed both.

What made recovery possible, according to the statement, was that UniSuper also held backups with a different service provider.

The event is rare. Its lesson is about what “separate” means. Two regions under one account are separate places and one authority. Whatever can delete the account, whether a provider’s error, a billing dispute, an attacker or your own automation, deletes both. For data whose loss would end the organization, one copy belongs under different control entirely.

Ransomware changes the assumptions

Most of this chapter assumes accidents. An attacker who has taken over administrative access behaves differently: they look for the backups first, delete or encrypt them, and only then encrypt the live data and ask for payment. Backups reachable with production credentials do not survive this.

The defenses are the separations already described, taken seriously: backups in a different account with different administrators, locked against deletion for a fixed period, with deletion of anything backup-related raising an alarm. Recovery speed matters as much here as anywhere, because the pressure to pay grows with every hour offline, and a restore that takes two weeks is a weak bargaining position.

The cheapest recovery: not really deleting

The commonest “disaster” is small: a user deletes something by accident, or a support agent removes the wrong account. Restoring a database to recover one album is slow and heavy. Three inexpensive habits handle most such cases without touching a backup.

  • Soft deletion. Mark rows as deleted and hide them, and remove them for good after a waiting period. covered the pattern and its costs.
  • Versioned object storage. Deleting or overwriting an object keeps the earlier version, which can be brought back.
  • Delayed destruction. For large, irreversible operations such as deleting a tenant, a table or a storage bucket, schedule the destruction for days later and make canceling it easy.

These turn most recoveries into an “undo”. They are not a substitute for backups: they do not survive a bug that ignores the deleted flag, an attacker, or the loss of the store itself.

In an interview. When asked about durability or “what if the database is lost”, separate the two problems. Replicas and multiple zones handle hardware and site failures. Backups with point-in-time recovery, stored in another region and account, handle mistakes and corruption. State an RPO and an RTO for the main data, say that restores are tested on a schedule, and point out which data is derived and can be rebuilt instead of backed up.

Common mistakes

  • Calling replicas backups. They share every mistake, instantly.
  • Never restoring. The backups are discovered to be empty, corrupt or unreadable on the day they are needed.
  • No alert on a missing backup. The job stopped in March and nothing noticed.
  • Backups beside the original. The same disk, building, region or account.
  • Backups deletable with production credentials. One compromise removes both.
  • Retention shorter than detection. The corruption is three weeks old and the oldest backup is two.
  • Losing the key. Encrypted backups, and the key lived only on what was lost.
  • An RTO from a document. Nobody has timed a restore since the data was a tenth of its size.
  • Backing up data and nothing else. No infrastructure definitions, configuration or secrets to restore into.
  • A plan only one person knows, or a runbook stored inside the system it describes.
  • A standby that replaces backups. It protects against losing a site and not against bad data.

Key points

  • Replication protects against hardware failure and copies mistakes, bugs and attacks to every replica. A backup is separate in time, in place and in authority.
  • Set a recovery point objective and a recovery time objective for each class of data. Derived data needs a rebuild procedure, not a backup.
  • Continuous log archiving turns periodic backups into point-in-time recovery: any moment since the last base backup can be restored.
  • Keep three copies on two kinds of storage with one off-site, at least one immutable, in an account that production credentials cannot damage.
  • A backup is proven only by restoring it. Automate restores, check the result, time it, and alert when a backup is missing.
  • Restore time grows with data. When it exceeds the objective, a standby must already exist: pilot light, warm standby or active-active.
  • Standbys protect against losing a site, and backups against bad data. A complete plan has both, written down and rehearsed.

Check yourself

A database has synchronous replicas in three zones. An engineer runs a destructive update without a WHERE clause. Why do the replicas not help, and what would?

Replication applies every committed change to every replica, including this one, within milliseconds. All copies now hold the damaged data. Point-in-time recovery from a base backup and archived log, to a moment just before the statement, would recover it. Soft deletion or a delayed replica might also, for some kinds of mistake.

Name the three ways a backup must be separate from the data it protects, and one threat each addresses.

Separate in time, so that a mistake or bug made now does not change it. Separate in place, so that a fire or regional outage does not take it. Separate in authority, so that a compromised credential, a ransomware attack or a deleted account cannot remove it.

A full backup is taken on Sunday and incrementals on each day after. Wednesday’s incremental turns out to be unreadable. Which days can still be restored?

Sunday, Monday and Tuesday. Each incremental depends on every one before it back to the full backup, so Wednesday and all later days in that chain are lost. With differentials, only Wednesday itself would be lost, because each differential depends on the full backup alone.

With continuous log archiving, a base backup every Sunday, and a mistake at 15:00 on Thursday, what is restored and what work does recovery involve?

The database can be recovered to any moment up to just before 15:00 on Thursday. Recovery restores Sunday’s base backup and replays four days of archived log up to the target time. That replay may be long, which is the argument for more frequent base backups.

A 2 TB database restores at 80 MB a second. The team’s RTO is two hours. Does a restore from backup meet it?

2 TB is 2,048 GB, about 2.1 million MB, which takes about 26,200 seconds, or 7.3 hours, for the copy alone, before detection, provisioning, log replay and verification. It misses by a wide margin. They need a faster restore path, a smaller unit to restore, or a standby that is already running.

What is the difference between a pilot light and a warm standby, and what does each cost?

A pilot light keeps the data replicated in the recovery region and everything else defined and switched off, so recovery means starting servers: tens of minutes, at low standing cost. A warm standby keeps a small complete copy running, so recovery means scaling it up and redirecting traffic: minutes, at the cost of running that copy all the time.

A company runs active-active in two regions with a consensus-replicated database. Why does it still need backups?

The design protects against the loss of a region. It does not protect against bad data: a mistaken delete, a corrupting bug or an attacker’s changes are committed and replicated to both regions like any other write. It also does not protect against the loss of the account that owns both regions.

What did the working recovery mechanism at GitLab in 2017 have in common with the one at UniSuper in 2024?

In both, the copy that saved the data was outside the system that failed. At GitLab it was a snapshot taken for a different purpose and held on a different machine, when the intended backups had silently stopped. At UniSuper it was a backup with a different provider, when the account covering both regions was deleted. Separation, more than the number of copies, is what counted.
