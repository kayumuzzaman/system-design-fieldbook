The problem

The problem. Design a file storage and sync service. Users keep files in a folder on each of their devices. A change on one device appears on the others. Users can share folders, recover earlier versions of a file, and keep working offline.

What makes it hard is that files are large and edits are small. A one-line change to a 32 MiB file must not upload 32 MiB, over a phone connection that drops every few minutes. The same file is often edited in two places at once, by one person with two devices or by colleagues in a shared folder, and nothing may be lost when that happens. And hundreds of millions of devices sit idle almost all the time, yet each must hear about a change within seconds. In the terms of , it is a storage problem whose difficulty is the cost of change: what moves over the network when one byte changes, and what happens when two changes collide.

Step 2: Estimates

Following , start from the users and their behavior. Assume 60% of saves change an existing file and 40% add a new one, and that a changed file averages 2 MB.

Four conclusions follow. Upload bandwidth is dominated by new files once edits send only changed chunks; the 79 KiB per edit is measured later in this chapter. Storage grows by hundreds of petabytes a year, which only object storage handles at a sensible cost (). Metadata is small per row but arrives at tens of thousands of transactions a second and is never deleted while history lasts, so it must be sharded. And the devices waiting for changes are mostly idle connections, tens of millions of them, which is a memory problem, not a CPU one ().

Step 3: The API

The client never uploads a file. It uploads blocks the server lacks, then commits a list of hashes as the new version. Each block is named by the SHA-256 hash of its bytes (), and the ordered list of a file’s block hashes, its blocklist, is the file’s content as far as the metadata is concerned.

Three properties make this safe to retry over a bad network. A block upload is idempotent by construction: the same bytes always have the same name, and storing them twice changes nothing. A commit names the revision it started from, so a commit that arrives after someone else’s fails with 409 instead of overwriting it. And the commit carries an idempotency key, so a retry after a lost response returns the same revision instead of creating a duplicate (). The changes list is paged by a cursor that is a position in the namespace’s journal, which is what lets a device that was offline for a week catch up exactly ().

Step 4: The data model

Files are grouped into namespaces. A user’s own files are one namespace; each shared folder is another, mounted into the tree of every member. A namespace is the unit of ordering and the shard key: every change to it gets the next number in its journal, and one database shard owns it.

BlockSHA-256 of its bytesUp to a few MiB of file content, never changedObject storage

A relational database fits the metadata because a commit is a small transaction with a condition: check that the parent revision is still current, insert the journal entry, update the current file. That is optimistic concurrency control on a row (), and putting a whole namespace on one shard keeps it a single-shard transaction (). The blocks need nothing a database offers: they are immutable, large and addressed by key, which is object storage’s job.

Step 5: The design

The client does more work than in most designs. It watches the folder for changes, splits each changed file into chunks, hashes them, and keeps a local database of what it believes is synced. Dropbox describes its client as holding three trees: the remote state, the local disk, and the last state known to be the same on both. The third works like the merge base in version control, telling a file deleted locally apart from a file added remotely.

Notifications carry no content. A device holds one long poll () listing its cursor in each namespace, and the reply says only which namespaces changed. The device then fetches the changes through the ordinary API. A lost notification costs nothing but delay, since the next poll or a periodic check catches up from the cursor, so the notification service can be simple, stateless and lossy.

Downloads of popular shared files can come from a CDN or through signed URLs straight from object storage (). Uploads go through the block service, which checks every block’s hash before storing it, because a client with a memory error can produce a block whose bytes do not match its name.

Step 6a: Chunking by content

Sending only what changed needs a way to name the parts of a file that did not change. The obvious way is to cut the file every 4 MiB, or every 64 KiB, and compare the hashes of the pieces. That works for an edit that overwrites bytes in place, and fails for one that inserts or deletes them, which is most edits to documents.

Inserting 100 bytes shifts every later byte by 100 positions. A fixed boundary is a position, so every piece after the insertion now holds different bytes and a different hash. Content-defined chunking places boundaries where the content itself has some rare property, so a boundary moves with the bytes around it. The usual property is that a hash of the last few dozen bytes, updated one byte at a time, falls below a threshold. The LBFS file system introduced the idea in 2001, with boundaries roughly every 8 KB; FastCDC (2016) is a faster version of the same idea, and the chapter’s chunker is a simplified form of it.

// Content-defined chunks: a boundary wherever a rolling hash of the last 32 bytes is small
// enough. The boundaries depend on the content near them, not on their distance from the start,
// so an insertion moves only the boundaries next to it.
export class ContentDefinedChunker implements Chunker {
  readonly name: string;
  private readonly min: number;
  private readonly max: number;
  private readonly threshold: number; // a hash below this ends a chunk
  private readonly gear: Uint32Array;
  constructor(average: number, seed = 86) {
    this.min = Math.floor(average / 4);
    this.max = average * 4;
    // After the minimum, each byte ends the chunk with probability 1 / (average − min).
    this.threshold = Math.floor(2 ** 32 / (average - this.min));
    this.gear = gearTable(seed);
    this.name = `content-defined ${average}`;
  }
  ends(data: Uint8Array): number[] {
    const out: number[] = [];
    const gear = this.gear;
    let start = 0;
    while (start < data.length) {
      const limit = Math.min(start + this.max, data.length);
      let end = limit;
      let h = 0;
      for (let i = start; i < limit; i += 1) {
        h = ((h << 1) + (gear[data[i] as number] as number)) >>> 0; // the oldest byte shifts out after 32 steps
        if (i + 1 - start >= this.min && h < this.threshold) {
          end = i + 1;
          break;
        }
      }
      out.push(end);
      start = end;
    }
    return out;
  }
}

The minimum and maximum keep chunks from being tiny or unbounded: without a maximum, a long run of identical bytes would never produce a boundary. Each boundary depends only on the 32 bytes before it, so after an insertion the chunker finds the old boundaries again within one chunk. The figure below measures what that is worth on a 32 MiB file of random bytes.

Fixed chunks of 4 MiB re-upload a whole chunk for a 100-byte change, and fixed chunks of 64 KiB do better there. But both re-upload half the file for an insertion in the middle and all of it for an insertion at the start, while content-defined chunks send one chunk of 33 to 96 KiB for each of these edits. Appending is cheap for all three, which is why logs and video recordings sync well with any chunking.

The average chunk size is a trade-off between bytes uploaded and metadata kept. Each chunk costs a 32-byte hash in every version that lists it, a reference to count, and an entry in the block store. The chapter’s code measured both sides on a 16 MiB file, inserting 100 bytes at twelve random places:

Step 6b: Storing each block once

Naming a block by the hash of its bytes is content addressing: the name is derived from the content, so equal content has equal names. It gives deduplication, storing identical data once however many times it is uploaded, with no extra machinery: before uploading, the client asks which hashes the server lacks. In the chapter’s test, a second user saving the same 4 MiB file uploaded 0 bytes.

Within one user, the large saving is version history. Every save creates a version, and versions share most of their blocks. The test saved a 16 MiB file twenty times, each save a small random insertion, deletion or overwrite:

Content-defined, 64 KiB on average17.9 MiB5.6%

Two consequences need care.

Deleting is garbage collection. A block may be listed by versions of many files and many users, so deleting a file cannot delete its blocks. Each version that lists a block holds a reference to it. When versions leave the history, their references are released, and a collector later deletes blocks with none left. It runs in the background and waits a grace period, often days, because a client may have uploaded a block a moment ago and be about to commit a version that lists it. Deleting from inside the commit path, or without that wait, is how such systems lose data.

Deduplication across users leaks information. If uploading a file takes no time, the file was already stored by someone. An attacker can test whether a particular document, or a form with a guessed salary filled in, exists anywhere in the service. Research on cloud storage has described this side channel since 2010. Services that care deduplicate only within a user or an organization, or always transfer the bytes and deduplicate silently on the server side, giving up the bandwidth saving to keep the storage one.

Step 6c: Ordering changes and resolving conflicts

Every commit to a namespace gets the next number in its journal. That number is the revision, and the journal is the namespace’s history in one order that every device replays. A device stores the last position it has applied, its cursor, and asks for everything after it. Because positions are assigned by the one shard that owns the namespace, every device sees the same changes in the same order, and catching up after a week offline is the same request as catching up after a second.

The commit itself is a compare-and-set on the parent revision:

commit(req: CommitRequest): CommitResult {
    // A version may only refer to blocks that are already stored.
    const missing = this.blocks.missing(req.blocks);
    if (missing.length > 0) return { kind: "need-blocks", missing };
    const cur = this.current.get(req.path) ?? null;
    if (this.policy === "revision") {
      // Compare and set: the edit must start from the version that is current now.
      if ((cur?.rev ?? null) !== req.parentRev) return { kind: "conflict", current: cur };
    } else if (cur !== null && req.time <= cur.time) {
      return { kind: "committed", version: cur }; // last write wins: the older save is dropped
    }
    // In a real store, these lines are one transaction: the version, the journal entry, the references.
    const version: Version = { ...req, rev: this.journal.length + 1 };
    this.journal.push(version);
    this.current.set(req.path, version);
    this.blocks.addRefs(version.blocks);
    return { kind: "committed", version };
  }

When the check fails, the client keeps both versions. The current one takes the file’s name, and the device’s own edit is saved beside it as a conflicted copy, a new file whose name records whose edit it was. Dropbox names them with the editor, the words “conflicted copy” and the date. It is not elegant, but nothing is lost and the person who can merge the two edits is told.

if (r.kind === "conflict") {

      this.conflicts += 1;

      this.files.set(this.uniqueName(copy), { bytes: f.bytes, baseRev: null, dirty: true });
      if (r.current) this.install(r.current);

The alternative, last write wins (), keeps the save with the later timestamp. The chapter’s code simulated a month of a shared folder: four devices, forty files of which a few are edited most, one edit per device per hour, and spells offline of varying length between four-hour spells online. Each file’s content records which edits it includes, so a lost edit can be counted at the end.

Offline time is what creates concurrent edits, and their number grows quickly with it. The revision check turns each into a conflicted copy, which can hold several edits made in one offline spell, and loses none. Last write wins loses them silently, and loses some even when every device is always online: the devices’ clocks differed by up to two minutes, so a save made shortly after another could carry an earlier time and be discarded. With clocks that agreed exactly and no offline time, it lost nothing, which is the case that tests usually cover ().

Common mistake. Identifying files by path. A rename then looks like a delete and an add, history is cut, and a rename on one device racing an edit on another loses the edit. Give every file a permanent id, and make the path an attribute of it; a move of a folder with 100,000 files is then one change to one row, not 100,000.

Folders bring harder cases than files. One device moves folder A into B while another moves B into A, and each move is valid alone. The server must refuse the second, because it would create a cycle, and the client must recover. Dropbox’s 2020 rewrite of its sync engine made moves atomic for subtrees of any size, and the team reported running tens of millions of randomized test runs of the engine every night, which says something about how many such cases exist.

At ten times the scale, a billion daily users, every number in the estimate grows tenfold: about 116,000 commits a second on average, and several exabytes of new storage a year. The design holds, with more metadata shards and more notification servers. Two things start to hurt. Huge shared namespaces, a company folder with tens of thousands of members, become hot shards and fan their notifications out to every member’s devices, so they are split by subfolder. And storage cost dominates the bill, which favors moving old versions and rarely read files to colder tiers () and erasure coding over replication ().

At a hundred times, the service is one of the largest storage systems in the world, and a dedicated block store, built for immutable chunks and nothing else, becomes worth its cost. Dropbox’s Magic Pocket, below, is one.

In the real world

  • Dropbox’s protocol, as described in 2014: every file is split into 4 MB blocks, the blocks are hashed with SHA-256, and the list of hashes, which Dropbox also calls a blocklist, identifies the file. A commit to the metadata server answers that blocks are needed if any are missing; the client uploads them to the block server and commits again, and a new row is added to the server file journal.
  • Dropbox’s block store, Magic Pocket, described in 2016: an immutable store of blocks up to 4 MB, usually keyed by their SHA-256 hash, grouped into 1 GB buckets that are later erasure coded, with every block in at least two zones. The post calls it “a multi-exabyte behemoth”.
  • Dropbox’s sync engine was rewritten in Rust and shipped to all users by 2020, with a protocol giving files and shared folders globally unique ids and atomic moves. The client keeps the remote, local and synced trees described above, and the team runs tens of millions of seeded random tests of it every night.
  • Compression on the wire. Dropbox reported in 2020 that compressing blocks before transfer cut the data sent for uploads by about a third and median sync latency by more than 30%.
  • Version history and conflicts, as of Dropbox’s help pages in 2025: 30 days of versions on its Basic, Plus and Family plans, 180 or 365 days on business plans, and a conflicted copy named with the editor, “conflicted copy” and the date.

Key points

  • Split the service into metadata, small ordered transactions in a sharded database, and blocks, large immutable objects in object storage.
  • Name blocks by the hash of their bytes. Uploads become “send what the server lacks”, retries are harmless, and identical data is stored once.
  • Chunk by content, not by position. In the test, 100 bytes inserted at the start of a 32 MiB file re-uploaded the whole file with fixed chunks and 33 KiB with content-defined ones.
  • The average chunk size trades bytes uploaded per edit against hashes kept per GiB, in equal measure.
  • Give each namespace a journal. Its positions are revisions, a device’s cursor is a position, and catching up is reading from there.
  • Commit with the parent revision, and keep both edits on conflict. Last write wins lost edits in the simulation even with every device online.
  • Deleting is garbage collection with a grace period, and cross-user deduplication is a privacy decision as well as a cost one.

Check yourself

Why does inserting one byte at the start of a file re-upload the whole file with fixed-size chunks, and not with content-defined ones?

Fixed boundaries are positions. After the insertion every byte sits one position later, so every chunk holds different bytes and gets a new hash. Content-defined boundaries are where a hash of the preceding bytes is small, so they move with the bytes; after the first chunk the old boundaries are found again and every later chunk is unchanged.

A client uploads three blocks and loses its connection before committing. What happens to them?

They stay in the block store with no version referring to them. When the client reconnects, it asks which blocks are missing, the three are not, and it commits. If it never returns, the garbage collector deletes them after the grace period.

Why must the garbage collector wait days before deleting a block with no references?

Because uploading blocks and committing the version that lists them are separate steps. A block can be uploaded, or found to exist already, a moment before the commit that refers to it. Deleting it in between would let the commit succeed with a block that is gone.

Two devices edit revision 7 of a file offline. Describe what the server and the second device do.

The first to reconnect commits with parent 7 and creates revision 8. The second commits with parent 7, and the server refuses with a conflict naming revision 8. The second device saves its own edit under a new name as a conflicted copy, downloads revision 8 to the original name, and uploads the copy as a new file. Both edits survive.

In the simulation, last write wins lost 9 edits although no device was ever offline. How?

The devices’ clocks differed by up to two minutes. When one device saved shortly after another, its timestamp could still be earlier, so the server kept the older save and discarded the newer one. With clocks that agreed exactly, it lost none.

Why do notifications carry only “this namespace changed” and not the change itself?

So that a lost, delayed or duplicated notification cannot corrupt anything. The device fetches changes from the journal after its cursor, which gives every change exactly once and in order. The notification only decides when it asks.

What can an attacker learn from cross-user deduplication, and what are the options?

Whether a given file is already stored anywhere in the service, by uploading it and seeing that nothing was transferred. The options are to deduplicate only within one user or organization, or to always transfer the bytes and deduplicate on the server, keeping the storage saving and losing the bandwidth one.
