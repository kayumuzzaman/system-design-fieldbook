The problem

The problem. Design the booking core of a cinema’s ticketing system. A customer picks a show, chooses seats on a seat map and pays. The seats are held for a few minutes while they pay. No seat may be sold twice, a failed payment must free the seats, and nobody may end up paying for seats they did not get.

In the terms of , this is handing out a limited resource, the shape of . Three things make it harder: one order takes several seats, a claim lasts only minutes, and a payment sits in the middle. Sales of a hit concert to a hundred thousand people at once, with waiting rooms and inventory spread over many servers, are the subject of .

Step 4: The classes

The decision that shapes everything is where a seat’s state lives. A seat belongs to a screen and exists for every show, so it cannot say whether it is sold. That fact belongs to the pair of a show and a seat, and the show owns all such pairs for its screening. Every rule about seats is then a method of one object that sees all of them: the place that can promise each seat to one customer.

Payment and time come in through interfaces, a port for each, as in . The tests use a fake provider that can approve, decline or wait until told, and a clock that moves only when the test moves it, so a ten-minute hold takes no time to test, as with the clock of .

Step 6: The code

Seats, and holds that lapse by themselves

// What one seat is doing at one show. A hold carries the time at which it lapses. A lapsed hold
// is left as it is and read as available: nothing has to run at the moment a hold runs out.
export type SeatState =
  | { readonly kind: "available" }
  | { readonly kind: "held"; readonly holdId: string; readonly until: number }
  | { readonly kind: "booked"; readonly bookingId: string };

// Free means available, or held by a hold that has lapsed.
  isFree(seatId: SeatId, now: number): boolean {
    const s = this.state(seatId);
    return s.kind === "available" || (s.kind === "held" && s.until <= now);
  }

  heldBy(seatId: SeatId, holdId: string, now: number): boolean {
    const s = this.state(seatId);
    return s.kind === "held" && s.holdId === holdId && s.until > now;
  }

  // All or nothing. Every seat is checked before any is changed, and there is no await in between,
  // so no other call can run between the check and the claim.
  hold(holdId: string, seatIds: readonly SeatId[], now: number, until: number): HoldAnswer {
    this.validate(seatIds);
    const unavailable = seatIds.filter((id) => !this.isFree(id, now));
    if (unavailable.length > 0) return { ok: false, unavailable };
    for (const id of seatIds) this.seats.set(id, { kind: "held", holdId, until });
    return { ok: true };
  }

A held seat stores when its hold ends. Nothing changes it at that moment: every reader compares the end with the clock, and a hold whose end has passed reads as available. Expiring by reading instead of by a timer removes a whole class of bugs. There is no timer to lose when a server restarts, and no timer firing in the middle of a payment. A hold is a claim on seats that lapses at a stated time unless it is turned into a booking, a lease on seats.

hold checks every seat before it changes any, so a customer who asks for C5 to C7 when C7 is taken gets nothing and is told which seat was the problem. The test sent 2,000 overlapping requests for one to four adjacent seats of one row, one a second, with holds of 5 to 60 seconds: 265 were granted whole and 1,735 refused with nothing held, and after every request each live hold still had all its seats. Taking seat by seat and stopping at the first taken one would have left 284 seats held for customers who had been told no, up to 9 of the row’s 10 at once.

The method has no await between the check and the claim. In one Node.js process nothing else can run in between (), which the test checks with 1,000 customers arriving within two milliseconds for pairs of seats: 42 holds granted, 84 seats, none twice.

Checkout: payment in the middle

// Pay for a hold and turn it into a booking. A retry with the same key gets the same answer from the
  // same single attempt, even while that attempt is still waiting for the payment.
  checkout(holdId: string, key: string): Promise {
    const known = this.checkouts.get(key);
    if (known) return known;
    const attempt = this.pay(this.holdOf(holdId), key);
    this.checkouts.set(key, attempt);
    return attempt;
  }

  private async pay(hold: Hold, key: string): Promise {
    if (hold.status === "booked") return { kind: "booked", booking: this.bookings.get(hold.bookingId as string) as Booking };
    if (hold.status === "paying") return { kind: "busy" };
    const start = this.clock.now();
    const until = Math.max(hold.expiresAt, start + this.policy.payGraceMs);
    if (hold.status !== "held" || !hold.show.extend(hold.id, hold.seats, start, until)) return { kind: "expired" };
    hold.expiresAt = until;
    hold.status = "paying";

    const charge = await this.payments.charge({ key, amount: hold.amount, customer: hold.customer });
    // Anything may have happened while we waited, including the hold lapsing and the seats being sold.
    const now = this.clock.now();
    if (!charge.ok) {
      hold.show.release(hold.id, hold.seats);
      hold.status = "released";
      return { kind: "declined", reason: charge.reason };
    }
    const bookingId = `B${this.next++}`;
    if (hold.show.book(hold.id, hold.seats, bookingId, now, this.policy.lapsedMayBook)) {
      const booking: Booking = { id: bookingId, holdId: hold.id, showId: hold.show.id, customer: hold.customer, seats: hold.seats, amount: hold.amount, chargeId: charge.chargeId };
      this.bookings.set(bookingId, booking);
      hold.status = "booked";
      hold.bookingId = bookingId;
      return { kind: "booked", booking };
    }
    hold.status = "refunded";
    await this.payments.refund(charge.chargeId);
    return { kind: "refunded", chargeId: charge.chargeId };
  }

Checkout is where the money meets the seats, and it is written around the await. Before it, the hold must still be live, and it is marked paying and extended by the policy’s grace, so that a customer who presses pay with ten seconds left is not punished for a slow bank. After it, anything may have happened, including the hold lapsing and someone else holding the seats. So the code asks the show again, and the show books the seats only if they are still this hold’s.

Every way out leaves the books balanced. A declined payment frees the seats at once instead of ten minutes later. An approved payment books the seats or, if they are gone, is refunded. The simulation checks after every event that the money taken equals the money for booked seats plus the money refunded.

Two customers, one seat

With several servers, the seat states live in a shared store, and every question to it is a round trip. Code that asks whether seats are free and then, in a second call, writes the customer’s name has a gap between the two calls, and another customer’s question can fall into it.

The test measured the gap with a store that takes 1 to 3 milliseconds a call. Customers each wanted two adjacent seats of a 100-seat hall, chosen at random. One run:

Two customers rarely collide, which is why the bug survives testing by hand. A hundred at once, the opening minute of a popular show, and over half the hall is promised twice. Even spread over a second, a few seats were. Check and set never promised a seat twice in any trial.

In SQL the check and the write become one statement. The parking lot claimed one space with a conditional UPDATE (); here an order claims several seats, and a hold can lapse, so the condition includes the time and the statement counts what it changed.

// All or nothing: a conditional UPDATE changes only seats that are free now. Unless it changed every one, nothing is kept.
export function holdSeats(db: DatabaseSync, showId: string, holdId: string, seatIds: readonly SeatId[], now: number, until: number): boolean {
  return inTransaction(db, () => {
    const { changes } = db.prepare(`
      UPDATE show_seats SET status = 'held', hold_id = ?, held_until = ?
      WHERE show_id = ? AND seat_id IN (${marks(seatIds.length)})
        AND (status = 'available' OR (status = 'held' AND held_until <= ?))`).run(holdId, until, showId, ...seatIds, now);
    return Number(changes) === seatIds.length;
  });
}

BEGIN IMMEDIATE makes SQLite take the write lock when the transaction starts, so two connections cannot both be inside it at once. If the update changed fewer rows than seats were asked for, some seat was not free, and the rollback undoes the rest. The rule that no seat is sold twice is also written into the schema: booked_seats has the primary key (show_id, seat_id), so a second booking of a seat fails whatever code path tries it. That is the last line of defense against a bug elsewhere, or against a second sales channel written by another team ().

The test ran this for real: 8 worker threads, each with its own connection to one database file, released at the same instant 20 times to hold the same 3 seats. Reading then writing told all 8 customers yes in every round, 160 in all; only the primary key kept the bookings to one a round, leaving 7 customers each time who had been promised seats they could not buy. The conditional update told exactly one customer yes every round.

Paying late, and paying twice

A payment that answers after the hold has ended is the case most designs forget. The two policies treat it differently; the test ran each case under both.

The answer arrivesSTRICT: no grace, late is refusedGRACE: five more minutes, late but free is fine
90 seconds after the hold’s original end, seats untouchedRefundedBooked
30 minutes after, seats still freeRefundedBooked
After the end, with the seats held by someone elseRefundedRefunded
Declined, at any timeThe seats are free at once

Neither policy ever sells a seat twice; they differ in how often they refund someone who could have been served. GRACE is kinder, and the design keeps it a setting because a box office may prefer the rule that is simplest to explain.

Paying twice is the other danger. A customer double-clicks, or the page retries after a timeout, and the server sees the same checkout several times. An idempotency key makes those one attempt: the service keeps the promise of the first call under its key and hands the same promise to every repeat, even while the payment is still running, and passes the key to the provider, which Stripe, for example, documents as returning the saved result for a repeated key. In the test, three calls with one key made one charge and one booking. A later call with a new key found the hold already booked and returned the same booking, and a second key while the first payment was still running was told busy. Without the key and the paying state, the same three calls charged the card three times, booked once and refunded twice.

How long to hold

A hold protects a customer who is paying, and costs everyone else the seats of a customer who has left. Seats in abandoned holds follow : on average, the number in the system equals the rate they arrive times how long each stays.

seats held by people who left = holds an hour ÷ 60 × share abandoned × seats a hold × minutes a hold lasts
= 500 ÷ 60 × 0.25 × 2.25 × 10 ≈ 46.9 seats

The simulation tested the formula in a hall too large to fill, so nobody was turned away: 242 of 1,000 customers abandoned, with 557 seats. The formula predicts 557 ÷ 120 minutes × 10 = 46.4 seats held by people who had left; the simulation measured 44.5, the shortfall coming from holds still running at the end of the two hours.

On average 46.9 seats are held by people who have already left, 47% of the hall, a large share to keep out of reach while people who would pay are being turned away.

The formula gives the cost of a long hold, not the best length, because a short hold has a cost too: customers still paying lose their seats. The simulation plays a day of sales for one 100-seat show. A thousand customers arrive over two hours, each wanting one to four adjacent seats; a quarter of those who get seats leave without paying; the rest press pay after 30 seconds plus a random wait averaging two and a half minutes. Most payments take seconds, some take minutes, 3% take ten minutes or more, and one in ten is declined. These are assumptions, not data from a real cinema. Each day was run for nine hold times on the same seeded customers, through the real BookingService with the manual clock.

With one-minute holds, 254 customers on average lost their seats before they could pay, and the hall sold out at minute 86. With thirty-minute holds, nobody lost seats while paying, but 514 customers were turned away while abandoned holds sat on enough seats for them, and only 13 of the 20 days sold out within two hours. In between, five to seven minutes sold out soonest, near minute 39. The best value depends on how long real customers take to pay, which a real system measures. The shape of the trade-off does not. In the test, one seeded day at five hold times, with the invariants checked after every one of more than 1,100 events each, no seat was promised twice and the money always balanced.

Step 7: Walk it

Follow Ana booking C5 and C6 at 17:00 with ten-minute holds and the GRACE policy.

  1. The page calls hold("S1", "ana", ["C5", "C6"]). The show finds both free, stores them as held by H1 until 17:10, and returns the hold. Price: two standard seats, 18.00.
  2. At 17:09 she presses pay. The page sends checkout("H1", key), with a key it made when the page loaded and reuses on every retry.
  3. The service finds no attempt under that key, sees H1 still held, extends it to 17:14, marks it paying, and asks the provider for 18.00 with the same key.
  4. The page times out and retries. The retry finds the key and waits on the same promise. No second charge is made.
  5. The provider approves at 17:10:30, after the original end. The show finds C5 and C6 still held by H1, which now lasts until 17:14, and books them. Both calls return the same booking.

Key points

  • A seat’s state belongs to the show, not the seat: available, held by one hold until a time, or booked.
  • Let holds lapse by being read. Store the end time and compare it with an injected clock; no timer has to fire.
  • Claim all the seats of an order or none, and check before changing anything.
  • Never put a round trip between checking seats and claiming them. Read-then-write promised over half the hall twice with 100 customers at once.
  • In the database: one conditional update that counts its rows, and a unique key on booked seats as the last line.
  • Around the payment: an idempotency key, a release on decline, a fresh check after the await, and a refund when the seats are gone.
  • Hold length is a trade-off between customers lost while paying and seats locked by people who left. Little’s law prices the second.

Check yourself

Why does a seat’s state belong to the show and not to the seat?

A seat is part of a screen and exists for every show on it. Whether it is sold is a fact about one seat at one show, and putting all such facts for a show in one object gives one place that can promise each seat to only one customer.

A hold ended at 17:10 and nothing has touched it since. At 17:12, is the seat free?

Yes. The stored state still says held until 17:10, but every reader compares that time with the clock, so the seat reads as available and the next customer can hold it. Nothing had to run at 17:10.

Ben asks for C7 to C9 while Ana holds C7. What should he get, and why not C8 and C9?

Nothing, and a message naming C7. A partial hold would keep C8 and C9 from other customers for minutes while Ben, who wanted three seats together, is told no.

The seat check and the write are each atomic statements. Why can two customers still get the same seat?

Because the pair is not atomic. Between one customer’s read and write, another customer’s read sees the same free seats. The fix is a single statement whose condition is the check: UPDATE … WHERE status = 'available' …, with the number of changed rows telling whether it worked.

Ana’s bank approves her payment at 17:20; her hold ended at 17:14, and Ben holds her seats. What happens?

The service asks the show to book the seats; the show refuses because they belong to Ben’s live hold; the service refunds Ana’s charge and tells her so. The money taken still equals the money for booked seats plus refunds.

A page sends checkout three times with the same key while the first payment is still running. How many charges are made?

One. The service stores the first attempt’s promise under the key and returns it to every repeat, and the provider treats the repeated key as the same charge. In the test, three calls made one charge and one booking.

500 holds an hour, a quarter abandoned, 2.25 seats each, 10-minute holds. How many seats are held by people who have left, and what happens if holds last 20 minutes?

500 ÷ 60 × 0.25 × 2.25 × 10 ≈ 47 seats on average, and twice that, about 94, at 20 minutes: nearly the whole of a 100-seat hall while demand lasts.
