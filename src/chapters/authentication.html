Who is calling?

Ana opens the photo app and sees her own private albums. Ben, on the same server a millisecond later, sees his. Every request arrives as bytes on a connection, and nothing in those bytes is Ana or Ben until the system has a reason to believe it.

Two questions are asked of every request, in this order, and they are easy to blur.

  • Authentication establishes who the caller is, by checking something only that caller should be able to present. It answers “who are you, and how do I know?”.
  • Authorization decides whether that caller may do the thing requested. It answers “are you allowed?”, and it is the subject of .

The two fail differently. An authentication failure lets a stranger act as Ana. An authorization failure lets Ana, correctly identified, read Ben’s photos. HTTP has a status code for each: 401 means “I do not know who you are”, and 403 means “I know who you are, and the answer is no”.

The thing a caller presents is a credential: a password, a key, a token, or anything else whose possession is accepted as evidence of an identity. Credentials come in three kinds, usually called authentication factors: something you know, something you have, and something you are.

FactorExamplesHow it fails
Something you knowA password, a PINGuessed, reused on another site that leaks it, or typed into a fake page
Something you haveA phone, a security key, a private key stored on a deviceLost, stolen, or copied if the secret can leave the device
Something you areA fingerprint, a faceCannot be changed once copied, so it is used to unlock a device, not sent to a server

Authentication has two parts that are designed separately. The first is the sign-in: a caller proves an identity once. The second is everything after it: the server must recognize the same caller on the next thousand requests without repeating the proof. This chapter starts with passwords, because nearly every system still has them and the rules for storing them are precise. Then sessions and tokens, which carry the result of a sign-in. Then second factors and passkeys, the credentials that are replacing passwords. Letting one system rely on another’s sign-in, and authenticating programs instead of people, are the subject of .

Storing passwords

If a server can check a password, it holds something derived from that password, and servers get broken into. The design goal is that a copy of the users table should be worth as little as possible to whoever takes it. Here are three ways of storing a password, and what each reveals when the table leaks.

Plain text exposes every account at once, here and on every other site where those users chose the same password. Encrypting the column is little better, because the application must hold the key, and whoever took the table has usually been able to take the key too. A password should not be recoverable by anyone, including you.

So passwords are hashed: passed through a one-way function, with only the result stored. To check a sign-in the server hashes what was typed and compares. covers hash functions in general. For passwords, an ordinary fast hash such as SHA-256 is the wrong tool, for the two reasons visible in .

  1. Equal passwords give equal hashes. An attacker can hash a list of common passwords once and look every row up in it. The fix is a salt: a random value, different for every password and stored beside the hash, that is mixed in before hashing so that the same password produces a different result in every row.
  2. Fast hashes are fast for the attacker too. SHA-256 was designed to process gigabytes a second. One high-end graphics card can try on the order of ten billion guesses a second against a salted SHA-256 hash. Every eight-letter lowercase password, all 209 billion of them, is covered in about twenty seconds.

The fix for the second is a password hashing function: a hash built to be deliberately expensive, with a cost you can set. The good ones are also memory-hard, meaning that each guess needs a large block of memory as well as time. That matters because an attacker’s advantage comes from running thousands of guesses in parallel on graphics cards or custom chips, and memory is the resource that is hardest to multiply cheaply.

Tune the cost by measuring on your own servers. A few hundred milliseconds is invisible to a person signing in and multiplies the attacker’s work by millions. Your servers pay the same cost on every sign-in, so the sign-in endpoint needs rate limiting, or it becomes an easy way to exhaust them.

The code below uses scrypt because it ships with every version of Node.js. Argon2id is preferable where you have it: current Node.js releases include it as crypto.argon2, Node.js 22 does not, and maintained libraries exist for every major language.

import { randomBytes, scrypt, timingSafeEqual } from "node:crypto";

// Cost settings travel with the hash, so they can be raised later.
const CURRENT = { n: 2 ** 17, r: 8, p: 1, keyLength: 32 };

function derive(password: string, salt: Buffer, c: typeof CURRENT): Promise {
  return new Promise((resolve, reject) => {
    const options = { N: c.n, r: c.r, p: c.p, maxmem: 256 * 1024 * 1024 };
    scrypt(password.normalize("NFKC"), salt, c.keyLength, options, (err, key) => (err ? reject(err) : resolve(key)));
  });
}

export async function hashPassword(password: string): Promise {
  const salt = randomBytes(16); // unique for every password, stored beside the hash
  const key = await derive(password, salt, CURRENT);
  return `scrypt$n=${CURRENT.n},r=${CURRENT.r},p=${CURRENT.p}$${salt.toString("base64url")}$${key.toString("base64url")}`;
}

export async function verifyPassword(password: string, stored: string): Promise<{ ok: boolean; rehash: boolean }> {
  const [scheme, params, saltText, keyText] = stored.split("$");
  if (scheme !== "scrypt") return { ok: false, rehash: false };
  const found = Object.fromEntries(params.split(",").map((kv) => kv.split("=")));
  const expected = Buffer.from(keyText, "base64url");
  const cost = { n: Number(found.n), r: Number(found.r), p: Number(found.p), keyLength: expected.length };
  const actual = await derive(password, Buffer.from(saltText, "base64url"), cost);
  const ok = timingSafeEqual(actual, expected); // compares every byte, however early they differ
  return { ok, rehash: ok && (cost.n < CURRENT.n || cost.r < CURRENT.r) };
}

Three details in that code are worth copying.

  • The settings travel with the hash. The stored string names the algorithm, its cost, the salt and the result. That is what makes it possible to raise the cost next year: verifyPassword reports when a hash was made with weaker settings, and the caller stores a fresh one while it still has the password in hand. There is no other moment when you can.
  • The comparison takes the same time whether the first byte differs or the last, so response times reveal nothing about how close a guess was.
  • The work is asynchronous. Half a second of hashing on the thread that serves requests would stall everything else on it.
PepperA pepper is a secret key, the same for every user, mixed into the hash and kept outside the database, in a secrets manager or a hardware module. A thief with only the table then cannot test a single guess. It is an extra layer, not a substitute for a slow hash, and it has to be rotated like any other key.

How long a stolen hash lasts

The strength of a password is measured in bits: a password chosen at random from 2n equally likely possibilities has n bits, and an attacker finds it after trying half of them on average. The calculator starts with a hash that takes 250 ms, an attacker with a thousand times the speed of one of your cores, and a password of 40 bits.

One hash takes 250 ms on your server, so one core can check 4 sign-ins a second. An attacker with 1,000 times that speed makes 4,000 guesses a second against each stolen hash, and finds a password of 40 bits in 4.36 years on average. Behind a fast hash the same password would last 55 s. The slow hash multiplies every password’s lifetime by 2.5 million. It cannot save a password that is on a list of common ones.

The slow hash moves every password the same distance to the right, a factor of 2.5 million at these settings, which is the difference between seconds and years for a middling password. It does almost nothing for a password that is on a list: the ten thousand most common ones fall in about a second either way. People do not choose passwords at random, so the rules below matter as much as the hash.

Rules that help and rules that do not

For years, sites demanded an uppercase letter, a digit and a symbol, and a new password every ninety days. The results were Password1! and then Password2!. The United States standards body NIST reversed that advice, and the 2025 edition of its digital identity guidelines forbids both demands outright.

DoDo not
Require length: at least 15 characters when the password is the only factor, at least 8 when a second factor is also requiredRequire mixtures of character types
Accept long passwords, at least 64 characters, including spaces and any Unicode characterForce a change on a schedule. Force one only when there is evidence of compromise
Reject passwords found on a blocklist of common and breached onesOffer password hints or security questions
Let password managers fill the field, and allow pasteTruncate the password, silently or otherwise
Limit failed attempts for each accountStore anything from which the password can be recovered

Checking a password against a public list of breached ones seems to require sending it to somebody. It does not. The widely used Pwned Passwords service is queried with only the first five characters of the password’s SHA-1 hash. It returns every breached hash that starts with those characters, hundreds of them, and the comparison is finished locally.

Common mistake. Writing passwords to a log. It happens indirectly: a request logger that records every body, or an error report that includes the form. Exclude credential fields by name, at the logger, and test that the exclusion works. The same applies to tokens and session identifiers.

None of this addresses the larger problem: people reuse passwords, and other sites leak them. In credential stuffing, an attacker takes name and password pairs leaked from one site and tries them against another, automatically and by the million. The defenses come later in this chapter: a second factor, and credentials that cannot be reused at all.

Sessions and cookies

HTTP has no memory. Once Ana has proved who she is, the server needs a way to recognize her next request without asking for the password again. The oldest answer is still the right default for a website.

A session is a record on the server that says “the holder of this identifier signed in as this user, at this time”. The identifier is a long random string. The browser receives it in a cookie and returns it with every request.

The identifier means nothing by itself. It is a reference to facts the server holds, and the server can change those facts at any moment. Signing out deletes the record. So does “sign out everywhere”, a password change, or an administrator disabling the account.

The cost is a lookup on every request, which is why sessions are kept in a fast shared store that any server can reach (). A session record is small: the user, when it was created and last used, and often the device it came from, so that users can review where they are signed in.

Getting the cookie right

The session identifier is a credential. Anyone who obtains it is Ana until it expires, without needing her password or her second factor. Its protection is mostly a matter of the attributes set when the cookie is issued.

The cookie above has no Max-Age, so it lasts until the browser closes. Add one to keep users signed in longer. The real expiry is enforced on the server either way, along with three more rules.

  • Generate at least 128 bits from a cryptographic random generator. An identifier that can be predicted or counted through is no credential at all.
  • Issue a new identifier at sign-in. In session fixation, an attacker obtains an identifier before signing in, tricks the victim’s browser into using it, and waits for the victim to sign in. If signing in keeps the old identifier, the attacker now holds a signed-in session. Issuing a fresh one at every change of privilege closes this.
  • Expire sessions twice. An idle timeout ends a session that has not been used for a while. An absolute timeout ends it however active it is. NIST suggests at most 30 days for low-risk services and, for services that need a second factor, at most 24 hours overall and an hour of inactivity. A bank will choose minutes. A photo app will choose weeks and ask again before anything sensitive.
Stolen cookiesMalware on a user’s computer can copy session cookies from the browser, and the thief then skips the password and the second factor entirely. Chrome 146 on Windows began shipping Device Bound Session Credentials in 2026: the browser holds a key in the machine’s security chip and must prove possession of it to renew a short-lived cookie, so a copied cookie soon stops working elsewhere.

Tokens that carry their own proof

A session makes every request depend on one store. That is a small price for a website and a larger one in a system of forty services, where each service would have to ask the store who the caller is. The alternative is to hand the caller a statement that any service can verify without asking anyone.

A JSON Web Token, or JWT, is a small signed document. It states who it is about, who issued it, who it is meant for and when it expires, and it carries a signature that proves the issuer wrote it and nothing has been changed since. Each statement inside it is called a claim.

Two properties follow from the structure, and both surprise people.

  • The contents are readable by anyone. The first two parts are only encoded so that they survive being put in a header. Paste a token into any decoder and the claims appear. A token protects integrity, not secrecy.
  • A token is a bearer token: whoever holds it can use it, exactly like cash. Nothing in it ties it to the device it was issued to.

The signature can be made in two ways. With a shared-secret algorithm such as HS256, the same key signs and verifies, so every service able to check a token is also able to forge one. With a public-key algorithm such as ES256, the issuer signs with a private key that never leaves it, and services verify with the matching public key, which the issuer publishes. Across more than one service, use a public-key algorithm. explains both kinds of signature.

The verifier below is complete. It uses HS256 because that needs nothing beyond the standard library. In production use a maintained library, and read this as a description of what that library must be told to do.

import { createHmac, timingSafeEqual } from "node:crypto";

export type Claims = { iss: string; sub: string; aud: string; exp: number; iat: number; [name: string]: unknown };

const encode = (value: object) => Buffer.from(JSON.stringify(value)).toString("base64url");
const sign = (input: string, key: Buffer) => createHmac("sha256", key).update(input).digest();

export function issue(claims: Claims, key: Buffer): string {
  const input = `${encode({ alg: "HS256", typ: "JWT" })}.${encode(claims)}`;
  return `${input}.${sign(input, key).toString("base64url")}`;
}

export function verify(token: string, key: Buffer, expect: { iss: string; aud: string }, now = Date.now() / 1000): Claims {
  const parts = token.split(".");
  if (parts.length !== 3) throw new Error("malformed token");
  const header = JSON.parse(Buffer.from(parts[0], "base64url").toString());
  // 1. The verifier chooses the algorithm. The token does not get a say.
  if (header.alg !== "HS256") throw new Error("unexpected algorithm");
  // 2. Check the signature before trusting a single claim.
  const given = Buffer.from(parts[2], "base64url");
  const wanted = sign(`${parts[0]}.${parts[1]}`, key);
  if (given.length !== wanted.length || !timingSafeEqual(given, wanted)) throw new Error("bad signature");
  // 3. Only now read the claims, and check each one that limits the token.
  const claims = JSON.parse(Buffer.from(parts[1], "base64url").toString()) as Claims;
  if (claims.iss !== expect.iss) throw new Error("wrong issuer");
  if (claims.aud !== expect.aud) throw new Error("meant for another service");
  if (typeof claims.exp !== "number" || claims.exp <= now) throw new Error("expired");
  return claims;
}

The order of the checks is the point. The token is supplied by the caller, so every byte of it is untrusted until the signature has been verified with a key and an algorithm that the verifier chose. Most well-known token vulnerabilities violate that sentence.

MistakeWhat an attacker doesDefense
Trusting the header’s algorithmSends a token whose header says "alg": "none" and has no signature, or says HS256 and is signed with the public key as if it were a shared secretAccept only the algorithms you configured
Not checking the audienceTakes a valid token issued for one service and presents it to anotherEvery service checks that aud names itself
Long lifetimesUses a stolen token for daysMinutes, plus a refresh token
Reading claims before verifyingForges whatever the code reads firstVerify, then parse

The price: a token cannot be taken back

The property that makes a signed token useful is that nobody needs to be asked. The same property means nobody can be told. If Ana signs out, or her phone is stolen, every token already issued remains valid until it expires, at every service, and there is no record to delete.

The standard answer is to split the credential in two.

  • An access token is the short-lived token that is sent to APIs. Lifetimes from five minutes to an hour are common, and this chapter uses fifteen minutes. The lifetime bounds how long a stolen one is useful.
  • A refresh token is a long-lived credential whose only use is to obtain new access tokens. It is sent to one place, the server that issued it, and that server keeps a record of it. Revoking it is an ordinary delete.

Signing out now means deleting the refresh token. The access token outlives it by minutes. Where even that is too long, services can consult a small list of revoked token identifiers, which is a session store again in a reduced form.

A refresh token is the most valuable thing a client holds, so it gets one more protection. With refresh token rotation, every use of a refresh token returns a new one and retires the old. A retired token that turns up again is evidence of theft.

Rotation does not prevent theft. It bounds it: the first time both copies are used, the session ends for both. Current security practice for OAuth, the protocol in , requires that refresh tokens issued to browser and mobile apps either rotate like this or be bound to a key held by the client, so that a copied token is useless without the key.

The two are routinely combined: a session cookie between the browser and one backend, and signed tokens from that backend onward. explains why that arrangement is the recommended one for web applications.

A second factor

A password alone fails in three common ways: it is guessed, it is reused on a site that leaks it, or it is typed into a fake page. Multi-factor authentication, or MFA, requires evidence of two different kinds, usually a password and something the user has, so that a stolen password is no longer enough on its own.

Any second factor defeats credential stuffing. The factors differ sharply in what else they stop.

Second factorHow it worksWeaknessStops real-time phishing
Code by text messageThe server sends a code to the user’s phone numberPhone numbers can be transferred to an attacker’s SIM card, and messages can be intercepted. NIST classes it as restrictedNo
Code from an appThe phone and the server share a secret and each derive a code from it and the timeThe user can be persuaded to type the code into a fake pageNo
Push approvalThe user taps “approve” on a phoneA user flooded with prompts eventually approves oneNo, unless the prompt requires typing a number shown on the sign-in page
Security key or passkeyA device signs a challenge with a key that is bound to the real siteLoss of the device, and whatever recovery replaces itYes

The app-generated code is simple, and it shows exactly where the weakness lies. A time-based one-time password, or TOTP, is a short code computed from a shared secret and the current time, so that it changes every thirty seconds. The secret is exchanged once, as the QR code the user scans during setup.

import { createHmac } from "node:crypto";

// RFC 6238: a counter derived from the clock, fed to the HOTP function of RFC 4226.
export function totp(secret: Buffer, atSeconds = Date.now() / 1000, step = 30, digits = 6): string {
  const counter = Buffer.alloc(8);
  counter.writeBigUInt64BE(BigInt(Math.floor(atSeconds / step)));
  const mac = createHmac("sha1", secret).update(counter).digest();
  const offset = mac[mac.length - 1] & 0x0f; // the last nibble picks four bytes
  const number = mac.readUInt32BE(offset) & 0x7fffffff;
  return String(number % 10 ** digits).padStart(digits, "0");
}

// Accept the current step and one on either side, to allow for clock drift,
// and never accept the same step twice.
export function checkTotp(secret: Buffer, code: string, lastUsedStep: number, atSeconds = Date.now() / 1000): number | null {
  const current = Math.floor(atSeconds / 30);
  for (const step of [current, current - 1, current + 1]) {
    if (step > lastUsedStep && totp(secret, step * 30) === code) return step;
  }
  return null;
}

Three consequences follow from those few lines.

  • The server must store the secret in a recoverable form, because it has to compute the same code. Unlike a password it cannot be hashed. Encrypt it, with a key kept outside the database.
  • A six-digit code is one guess in a million, and three in a million once neighboring time steps are accepted. Without a strict limit on attempts, a script finds it in minutes.
  • The code is the same wherever it is typed. Nothing in it knows which site it was meant for.

That last point is what attackers now exploit at scale. A phishing page no longer stores a password for later. It relays everything to the real site while the victim is still typing.

A credential is called phishing-resistant when what it produces is bound to the site it was registered with, so that nothing a user can be tricked into doing on another site yields anything usable. Codes and push approvals are not, however they are delivered. Passkeys and security keys are. NIST’s current guidelines require services at the second assurance level to offer at least one phishing-resistant option.

In production. In September 2022 an attacker who had bought a contractor’s password sent push prompts to the contractor’s phone for more than an hour, then posed as IT support in a message and asked for one to be approved. One was, and the attacker was inside Uber’s internal network. The lesson drawn across the industry was number matching: the user must type into the phone a number displayed on the sign-in page, which cannot be done absent-mindedly or for somebody else’s sign-in.

Two more decisions come with any second factor. Recovery codes are single-use codes issued at setup for the day the phone is lost. Store them hashed, like passwords. Step-up authentication means asking for a factor again, or for a stronger one, immediately before a sensitive action such as changing the email address or deleting everything, even though the session is otherwise valid.

Passkeys

Every credential so far is a secret that both sides know, or that travels to the server to be checked. A passkey is a credential built on a key pair: the user’s device creates a private key that never leaves it and gives the server the matching public key. Signing in means signing a fresh challenge. There is nothing on the server worth stealing and nothing a user can be tricked into typing.

The browser interface that makes this work is WebAuthn, a W3C standard whose third edition became a Recommendation in August 2026. In its terms the site is the relying party and the thing holding the key is the authenticator: a phone, a laptop’s security chip, a password manager or a hardware security key.

Three properties do the work, and each removes an attack described earlier.

PropertyWhat it meansAttack it ends
No shared secretThe server stores only a public keyA leaked users table yields nothing to guess or reuse. Credential stuffing has nothing to stuff
Bound to the siteThe browser offers a passkey only to the site it was created for, and the signature covers the site’s originPhishing, including the real-time relay
Unlocked locallyThe fingerprint, face or PIN is checked by the device and never sentA stolen device is not a stolen account, and no biometric data reaches the server

In the page, each ceremony is one call to the browser: navigator.credentials.create to register and navigator.credentials.get to sign in. The guarantees are enforced by what the server checks when a signature comes back:

  1. the challenge is the one this server issued, and has not been used before;
  2. the origin recorded by the browser is the server’s own;
  3. the site identifier that the authenticator signed for matches;
  4. the authenticator reports that a person was present and unlocked it;
  5. the signature verifies with the public key stored for this account.

A check written to that list was run against a response from a real browser with a simulated authenticator. It accepted the response and rejected each of four variations: another challenge, another origin, another site identifier, and a signature with one bit changed. Use a maintained WebAuthn library, which also handles registration and the other key types.

Synced and device-bound

Passkeys come in two kinds, and the difference is a trade between convenience and assurance.

Synced passkeyDevice-bound passkey
Where the private key livesIn a password manager or platform account, encrypted and copied to the user’s other devicesIn one hardware security key or one device’s security chip, and it cannot be exported
Losing a deviceThe passkey is still on the othersThe passkey is gone. A second key, registered in advance, is essential

NIST’s guidelines accept synced passkeys at the second assurance level and require a key that cannot be exported at the third. The server can tell the two apart from flags in the authenticator’s response.

In October 2025 the FIDO Alliance, drawing on figures from Amazon, Google, Microsoft, PayPal, Target and TikTok, reported that sign-ins with a passkey succeeded 93% of the time, took 73% less time than other methods, and cut sign-in help desk incidents by as much as 81%. The source is an industry body that promotes passkeys, and the figures are from large consumer services.

Common mistake. Adding passkeys and leaving a weak way around them. If the account can still be entered with a password and a text message, or reset through its email inbox, it is exactly as strong as that path. Strengthen the fallback, and let users remove the password entirely.

Recovery, guessing and abuse

Attackers rarely break the cryptography. They reset the password, or guess it from a list, or ask support nicely.

Account recovery is authentication

A “forgot password” link is a second way to sign in, and it deserves the same care as the first.

  • The reset link contains a random token of at least 128 bits. Store only its hash, let it work once, and expire it within the hour.
  • Completing a reset ends every existing session and notifies the user.
  • A reset never bypasses the second factor. Control of the mailbox should get an attacker no further than a password would.
  • Support staff are the same path with a human in it. Give them a procedure that they cannot be talked around.

Do not confirm who has an account

Account enumeration is learning which names or email addresses have accounts, from differences in how a system responds. “No such user” on one attempt and “wrong password” on another turns the sign-in form into a lookup service, and the list it produces feeds every other attack. Answer identically in both cases: “name or password is incorrect” at sign-in, and “if an account exists for that address, we have sent a link” on reset. The timing has to match as well, so hash a dummy password when the user does not exist.

Limit guessing without locking users out

Guessing against the live system is far slower than guessing against a stolen table, and it is still worth an attacker’s time if nothing pushes back. NIST requires that failed attempts on an account be limited, to no more than a hundred in a row. The obvious mechanism, locking the account after five failures, hands attackers a way to lock out any user they choose. Better tools exist:

  • Delays that grow with each failure, applied per account and per source address ().
  • A second factor when a sign-in comes from a device not seen before.
  • Detection of the pattern itself: one address trying one password against each of a thousand accounts looks nothing like a user who has forgotten theirs.

Record every sign-in, failure, reset, new device and change of factor. Show the user part of that record (“signed in from a new device”) and alert on the whole (): a sudden rise in failed sign-ins is often the first evidence of an attack.

Choosing for a real system

For the people who use the photo app, the decisions come out like this. None of them is exotic, and that is the intent.

DecisionChoiceWhy

In production. Authentication is the clearest case in this book for not building it yourself. The flows are standardized, the failure modes are subtle, and the attackers are practiced. Use an identity provider, or the authentication library that your framework’s maintainers support. You still choose the lifetimes, the cookie attributes, the fallback paths and what each service verifies, and those choices are where systems built on excellent libraries still fail.

Key points

  • Authentication establishes who the caller is. Authorization, a separate step, decides what that caller may do.
  • Store passwords only as salted hashes from a slow, memory-hard function, with the settings kept beside the hash so that they can be raised later.
  • Prefer long passwords and a breached-password check to composition rules and scheduled changes.
  • A session is a random reference to facts held on the server. It costs a lookup on every request and can be ended at once.
  • A signed token carries its own facts. It needs no lookup and cannot be taken back, so it is kept short-lived and paired with a refresh token that rotates.
  • Verify a token’s signature with an algorithm and key you chose before reading any claim, then check issuer, audience and expiry.
  • Any second factor stops reused passwords. Only credentials bound to the site, such as passkeys, stop real-time phishing.
  • A passkey leaves only a public key on the server, so there is nothing there to steal, guess or reuse.
  • An account is as strong as its weakest way in, and that is usually recovery.

Check yourself

Your password hash takes 250 ms. An attacker with a thousand times the speed of one of your cores steals the table. How long does a randomly chosen 40-bit password last on average, and what is the limit of this protection?

The attacker makes 4,000 guesses a second. Half of 240 is about 550 billion guesses, which takes a little over four years. Behind a fast hash at ten billion guesses a second it would last under a minute. The limit is that people do not choose at random: a password on a list of common ones falls in seconds whatever the hash.

A user reports a stolen laptop. With server-side sessions, and with 15-minute access tokens plus refresh tokens, what does “sign out everywhere” do in each case?

With sessions, the server deletes every session record for the user, and the stolen cookie refers to nothing from the next request. With tokens, the server deletes the user’s refresh tokens. An access token already on the laptop keeps working until it expires, at most fifteen minutes, unless services also check a list of revoked tokens.

A token verifier reads the alg field from the token’s header and uses whatever algorithm it names. Describe an attack.

The attacker writes any claims they like, sets the header to "alg": "none" and omits the signature, and a verifier that honors the header accepts it. A second form targets services that verify with a public key: the attacker sets the algorithm to HS256 and signs with the public key, which is not secret, used as the shared secret. The fix is the same for both: the verifier decides which algorithms are acceptable.

A refresh token is used once by the real app and then presented again by someone else. What should the server do, and why not simply refuse the second use?

It should revoke every token descended from that refresh token, so that the newer one stops working too. A second use proves the token was copied, but the server cannot tell whether the thief used it first or second. If the thief was first, the thief now holds the newest valid token, and refusing only the old one would leave the thief signed in and lock out the owner.

An account is protected by a password and a six-digit code from an authenticator app. Explain how a phishing page can still take over the session, and why the same page fails against a passkey.

The page relays what the victim types to the real site immediately. The code is valid for the current thirty seconds wherever it is entered, so the real site accepts it and gives the attacker a session. A passkey is offered by the browser only to the site it was registered for, so on the look-alike domain there is nothing to use, and a signature includes the origin, so one made for another origin would be rejected.

A service adds passkeys but keeps “reset by email link” exactly as it was. What has it gained?

Less than it appears. Sign-in itself is now protected from phishing and password reuse, but anyone who controls a user’s mailbox can still reset the account and get in. The account is as strong as its weakest path, so recovery has to require a second factor, end existing sessions and notify the user.
