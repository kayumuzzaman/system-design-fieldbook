Duplicates are a certainty

established that a sender who receives no reply cannot tell whether its request was lost or was carried out with the reply lost. The only useful response to silence is to try again. Retrying is therefore built into every layer of a real system:

  • A user taps “Pay” twice because the screen did not change.
  • A mobile app retries after a timeout on a weak connection.
  • A load balancer retries a request on another server.
  • A message queue redelivers a message that was not acknowledged in time.
  • A webhook sender repeats a delivery until it gets a success response.
  • A batch job is run again after failing halfway.

In each case the same logical operation may reach its destination more than once. If the operation is “charge 42.00”, that is a serious problem. The solution is not to stop retrying, which would mean losing operations. It is to make repetition safe.

An operation is idempotent if performing it several times has the same effect as performing it once. Some operations are idempotent by nature and others are not.

Idempotent by natureNot idempotent
Set the caption to “Sunset”Append “!” to the caption
Delete photo 871Delete the newest photo
Mark order 5512 as shippedCreate an order
Set the balance to 100Add 10 to the balance
Add user 42 to the set of likersIncrease the like count by one

The left column describes a resulting state. The right column describes a change relative to whatever the state happens to be. That distinction is the key to most of this chapter.

Three delivery guarantees

When a message is handed from one party to another, with a queue or a network in between, there are three promises a system might make about how many times it is processed.

GuaranteeHowFailure it permitsAcceptable for
At most onceAcknowledge, then process. Never retry.LossData where a gap is harmless: a metrics sample, a “user is typing” signal
At least onceProcess, then acknowledge. Retry until acknowledged.DuplicatesNearly everything, provided the receiver handles repeats
Exactly onceSee belowNeitherWhat everyone wants

Exactly-once delivery does not exist. The reason is the lost acknowledgment. Any scheme needs the receiver to tell the sender “I have it”, and that message can be lost too. The sender must then either resend, risking a duplicate, or not resend, risking loss. No protocol escapes that choice, however many confirmations are layered on.

What can be achieved is the same result by another route: deliver at least once, and make the processing idempotent, so that duplicates have no further effect. This is properly called effectively-once processing, and it is what products mean when they advertise exactly-once. The rest of the chapter is the set of techniques for the second half.

Designing operations to be idempotent

The cheapest technique is to phrase the operation so that repetition does nothing, following the left column of the earlier table.

Instead ofUseWhy it is safe
“Increment the like count”“Record that user 42 likes photo 871”, with a unique constraint on the pairThe second insert is rejected or ignored, and the count is derived from the rows
“Add 10 to the balance”“Apply transfer 881, of 10”, where each transfer ID is applied onceThe transfer either exists or does not
“Create a comment”“Create comment 3f9c…”, with the ID chosen by the clientA repeat hits the primary key
“Move the order to the next state”“Move order 5512 from paid to shipped”If it is already shipped, the condition fails and nothing changes
“Send the welcome email”“Send the welcome email for user 42, if not already recorded as sent”A record of having done it guards the action

Three tools recur. A client-supplied identifier for the thing being created turns a create into “make sure this exists”. A unique constraint lets the database reject the repeat, atomically, even under concurrency (). And a conditional update that names the expected current state makes a state change apply once.

Idempotency keys

When an operation cannot be rephrased, the general solution is an idempotency key: a unique value that the client generates once for each logical operation and sends with every attempt. The server remembers which keys it has handled and what it answered. A request with a key it has seen is not executed again. The stored answer is returned.

Stripe’s payment API is the best-known implementation and a good model. The client sends an Idempotency-Key header of up to 255 characters, typically a random UUID. Stripe saves the status code and body of the first response for that key, including error responses, and returns them for any repeat. It rejects a repeat whose parameters differ from the original, and it lets keys expire after 24 hours.

async function createOrder(userId: number, key: string, body: OrderInput): Promise {
  const fingerprint = sha256(JSON.stringify(body));

  return db.transaction(async (tx) => {
    const claimed = await tx.query(
      `INSERT INTO idempotency_keys (user_id, key, fingerprint)
       VALUES ($1, $2, $3)
       ON CONFLICT (user_id, key) DO NOTHING`, [userId, key, fingerprint]);

    if (claimed.rowCount === 0) {                       // seen before: replay, do not repeat
      const prior = await tx.queryOne(
        "SELECT fingerprint, response FROM idempotency_keys WHERE user_id = $1 AND key = $2",
        [userId, key]);
      if (prior.fingerprint !== fingerprint) {
        return { status: 422, body: { error: "This key was used for a different request." } };
      }
      return prior.response;
    }

    const order = await insertOrder(tx, userId, body);  // the real work, in the same transaction
    const response = { status: 201, body: order };
    await tx.query(
      "UPDATE idempotency_keys SET response = $3 WHERE user_id = $1 AND key = $2",
      [userId, key, response]);
    return response;
  });
}

The details carry the correctness.

  • The key and the effect commit in one transaction. If they were saved separately, a crash between them would leave either a key with no order, so the retry is wrongly ignored, or an order with no key, so the retry creates a second one. This is the dual-write problem from again.
  • A unique constraint decides who is first. Two copies of the request arriving at the same instant both try to insert the key. The database lets one through and makes the other wait, then see the conflict. Checking with a SELECT first and inserting afterward would let both pass.
  • Keys are scoped to the caller. Otherwise one client could collide with, or read the stored response of, another.
  • The request is fingerprinted. Reusing a key with different contents is a client bug, and it is better to say so than to return an answer to a question that was not asked.
  • Keys expire. Keep them longer than any client could plausibly retry, a day is common, and then delete them.

The key must be created where the operation originates and reused for every retry of it. A key generated afresh on each attempt protects against nothing. For a button in an app, generate the key when the form is shown or the button first pressed, not inside the function that sends the request.

When the effect is outside your databaseIf the work is a call to another system, such as a payment provider, it cannot share your transaction. Record the key as “started” and commit. Call the provider, passing the same key on to it so that it deduplicates too. Then record the outcome. A retry that finds “started” with no outcome knows the call may have happened, and asks the provider what became of that key instead of calling blindly.

Deduplicating on the receiving side

Messages from a queue arrive at least once, so every consumer needs the same protection. Messages carry a unique ID assigned by the producer, and the consumer records the IDs it has processed. The record must be written in the same transaction as the work, for the same reason as before. This is sometimes called the inbox pattern, the mirror image of the outbox.

async function handleOrderCreated(msg: Message): Promise {
  await db.transaction(async (tx) => {
    const fresh = await tx.query(
      `INSERT INTO processed_messages (consumer, message_id)
       VALUES ('shipping', $1) ON CONFLICT DO NOTHING`, [msg.id]);
    if (fresh.rowCount === 0) return;            // a redelivery: already handled

    await createShipment(tx, msg.payload);       // commits together with the row above
  });
  await msg.ack();                               // acknowledge last
}

Some queues offer deduplication themselves. Amazon SQS FIFO queues discard a message whose deduplication ID repeats one sent in the previous five minutes. That removes duplicates created by a producer retrying a send. It does not remove redelivery to a consumer that processed a message and failed to acknowledge it, and it does nothing after the five minutes. Treat such features as a reduction in duplicates, and keep the consumer idempotent.

Versions against stale and reordered messages

Retries also disturb order. A delayed first attempt can arrive after a later message. If a profile is updated to “Ana B.” and then to “Ana Bell”, and the first update is redelivered late, a consumer that blindly applies each message ends with the older name.

The defense is a version number on each entity that increases with every change. Each message carries the version it produces, and the consumer applies a message only if its version is higher than the one it holds:

UPDATE profiles SET display_name = 'Ana Bell', version = 7
WHERE user_id = 42 AND version < 7;

A duplicate and a late arrival are both discarded by the same condition. This is why change events are best designed to carry the entity’s full new state and a version, in place of an instruction to modify the previous state.

The check must be end to end

It is tempting to think a lower layer has already taken care of duplicates. TCP discards duplicate packets. The message queue has a deduplication feature. The database write is transactional. Each of those is true and none of them is sufficient, because a duplicate can be introduced above whichever layer is deduplicating.

TCP removes duplicate packets within one connection. When the app times out, opens a new connection and sends the request again, TCP sees a new, valid request. A queue that deduplicates sends cannot know that the user pressed the button twice and produced two distinct messages. Only the two ends of the whole operation, the place where the intent originates and the place where the effect is recorded, can decide what “the same operation” means.

This is an instance of a classic principle of system design, the end-to-end argument: a guarantee about a whole operation can only be fully implemented at its endpoints, and help from the layers between is an optimization. For idempotency, it means the key is generated at the origin, carried through every hop unchanged, and checked where the effect is committed.

What “exactly once” means in products

Stream processing systems such as Apache Kafka advertise exactly-once semantics, and the claim is accurate within limits worth understanding. Kafka gives each producer an ID and numbers its messages, so a broker can discard a resend. It also supports transactions that atomically combine “I consumed these input messages” with “I produced these output messages”, so a processing step that crashes and restarts neither loses nor duplicates its output.

The guarantee holds as long as everything stays inside the system. The moment a step has an effect outside, such as writing to another database, calling an API or sending an email, that effect is back to at-least-once and needs the techniques of this chapter. covers the mechanism.

Retrying well

Idempotency makes retries safe. They still need to be sensible, and covers the subject fully. The essentials:

  • Retry what might succeed. Timeouts, connection failures and responses such as 503 and 429 are worth retrying. A 400 or 404 will fail the same way again.
  • Wait longer each time, with randomness, so that many clients do not retry in step ().
  • Stop eventually. After a bounded number of attempts or a deadline, give up and record the failure where someone or something will deal with it, such as a dead-letter queue ().
  • Retry at one layer. Three layers each retrying three times turn one failure into twenty-seven requests.
  • Respect HTTP’s rules. GET, PUT and DELETE are defined as idempotent and may be retried by intermediaries. POST is not, which is why it is the method that needs a key ().

Common mistake. Checking for a duplicate and then acting, as two separate steps: “look up the order by its reference, and if none exists, create it”. Two retries arriving together both find nothing and both create. The check and the action have to be one atomic operation, which in practice means a unique constraint or a conditional write, never a read followed by a write.

In production. Test for duplicates deliberately, because they will not occur in ordinary testing. Deliver every message twice in a test environment. Replay yesterday’s events against a copy of the system and check that nothing changes. Kill a consumer between its work and its acknowledgment. A system that passes these has earned the word idempotent.

In an interview. Any design involving payments, orders or messaging will be probed with “what if the request is retried?” or “what if the consumer crashes after processing?”. The answer has a standard shape: “delivery is at least once, so the operation carries an idempotency key that the server stores with the result in the same transaction, and a retry returns the stored result”. Saying “exactly-once delivery” without that qualification usually draws a follow-up.

Common mistakes

  • Assuming a request is processed once because retries are rare in testing.
  • Read-then-write duplicate checks with no unique constraint.
  • Storing the idempotency key separately from the effect it guards.
  • Generating a new key for every attempt.
  • Relative operations in messages (“add 1”) where absolute ones (“set to 5, version 12”) would do.
  • Acknowledging a message before processing it when losing it matters.
  • Relying on a queue’s deduplication window as the only defense.
  • Applying messages in arrival order with no version check.
  • Retrying non-idempotent calls to third parties without passing a key.
  • Unbounded or multi-layer retries.

Key points

  • Retries are unavoidable, so every operation may arrive more than once.
  • Acknowledging before processing gives at most once and can lose messages. Processing before acknowledging gives at least once and can repeat them.
  • Exactly-once delivery is impossible. At-least-once delivery with idempotent processing gives the same result.
  • Prefer operations that state a result over operations that state a change, and let unique constraints and conditional updates reject repeats.
  • An idempotency key identifies a logical operation. Store it with the result, in the same transaction as the effect, and replay the result on a repeat.
  • Consumers record processed message IDs in the same transaction as their work, and use version numbers to discard stale or reordered messages.
  • Deduplication has to be end to end, from where the intent originates to where the effect is committed.
  • Check and act in one atomic step, never as a read followed by a write.

Check yourself

A consumer takes a message, sends an email and then acknowledges. It crashes between sending and acknowledging. What happens, and which delivery guarantee is this?

The queue receives no acknowledgment and delivers the message again, so the email is sent twice. This is at-least-once delivery. To avoid the duplicate, the consumer needs a durable record that this message’s email was sent, checked before sending.

Why is “exactly-once delivery” impossible, and what do systems provide instead?

The receiver’s acknowledgment can be lost, leaving the sender unable to tell whether to resend. Resending risks a duplicate and not resending risks loss. Systems instead deliver at least once and make processing idempotent, so that duplicates change nothing. The outcome is as if each message were processed once.

An API stores the idempotency key in a cache and the order in the database. Describe a failure that creates two orders.

The order is committed to the database and the process crashes before writing the key to the cache, or the cache loses the entry. The client retries with the same key, the server finds no record of it and creates a second order. The key must be stored in the same transaction as the order.

A client library generates a fresh UUID as the idempotency key inside its send() function, which is called again on each retry. What is wrong?

Each attempt carries a different key, so the server sees unrelated requests and executes every one. The key must be created once for the logical operation, before the first attempt, and reused for all retries.

Rewrite “increment the view count of photo 871” so that a redelivered message does no harm.

Give each view event its own ID and record it with a unique constraint, deriving the count from the recorded events, so a repeat is ignored. Or, if exact counts do not matter, accept the occasional double count. What does not work is applying “plus one” on every delivery.

TCP already discards duplicate packets. Why does an application still need idempotency keys?

TCP deduplicates within a single connection. When a client times out and retries, it sends a new request, often on a new connection, which TCP correctly treats as new data. Only the application knows that the two requests represent the same intended operation.
