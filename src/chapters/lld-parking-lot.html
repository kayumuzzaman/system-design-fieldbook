The problem

The problem. Design the software for a multi-level parking garage. Vehicles of different sizes come in through several entry gates, are given a ticket and a space, and pay when they leave according to how long they stayed.

In the terms of , this is a problem of handing out a limited resource. The same shape returns as seats in a cinema, rooms in a hotel and tables in a restaurant, so the reasoning here is worth more than the parking.

Step 1: Clarify

QuestionAssumed answer for this design
What kinds of vehicle, and what sizes of space?Motorcycles, cars and vans. Small, medium and large spaces
May a vehicle use a larger space than it needs?Yes, when nothing of its own size is free
Who chooses the space?The system, at the gate: the nearest suitable one, lower floors first
How is the fee worked out?For each started hour, by kind of vehicle. The first 15 minutes are free, and there is a maximum for each day
How many gates?Several entries and exits, in use at the same time
What is out of scope?Taking the payment, reservations, electric charging, monthly passes, the barrier hardware

That gives three use cases: a vehicle enters and is given a ticket for a space, a vehicle leaves and is charged, and the sign at the entrance shows how many spaces of each size are free.

Steps 2 and 3: The model and its invariants

The nouns are vehicle, space, floor, gate, ticket and fee. Sorting them as in :

ConceptKindWhy
SpotEntityEach one is tracked individually and changes between free and taken
TicketEntity, written as an immutable recordOne vehicle’s claim on one spot from a moment in time. It is the relationship between vehicle and spot, promoted to a type
VehicleValueA plate and a kind. The lot has no interest in the vehicle beyond those
FloorA field of the spotNothing in scope happens to a floor as a whole. A class for it would have no behavior
GateA caller, outside the modelGates invoke the lot. Their hardware is out of scope
FeeA number of cents, produced by a pricing functionThe rule varies, so it is a strategy

Two of these decisions are worth defending in an interview. Leaving out a Floor class and a Gate class is deliberate: a noun becomes a class when it has data and rules of its own, and here neither does. If the interviewer adds “close a floor for cleaning”, a floor gains state and earns a class at that moment.

Step 4: The classes

The fitting rule is a table of data, and that is the point of drawing it. An if for every pairing of vehicle and spot would work for three kinds and become unmanageable at five. A table that the code reads can be changed by editing one row.

Step 5: What varies

Pricing is the part of a parking lot that changes most often and differs most between lots: weekend rates, event days, a free first quarter of an hour. It is a strategy in the sense of , and because each rule modifies another, the strategies wrap each other.

export type VehicleKind = "motorcycle" | "car" | "van";

// The pricing strategy: from what was parked and for how many minutes, to a fee in cents.
export type Pricing = (kind: VehicleKind, minutes: number) => number;

// Every started hour is charged in full.
export const hourly = (centsPerHour: Record): Pricing => (kind, minutes) =>
  Math.ceil(minutes / 60) * centsPerHour[kind];

// A short stay costs nothing. Past the grace period the whole stay is charged.
export const withGrace = (freeMinutes: number, inner: Pricing): Pricing => (kind, minutes) =>
  minutes <= freeMinutes ? 0 : inner(kind, minutes);

// No single day costs more than the cap. Each full day costs exactly the cap.
export const withDailyCap = (capCents: Record, inner: Pricing): Pricing => (kind, minutes) => {
  const days = Math.floor(minutes / 1440);
  const rest = minutes - days * 1440;
  return days * capCents[kind] + Math.min(capCents[kind], inner(kind, rest));
};

// The policy used in this chapter, assembled from the three parts.
export const standardPricing: Pricing = withGrace(
  15,
  withDailyCap({ motorcycle: 800, car: 2400, van: 4000 }, hourly({ motorcycle: 100, car: 300, van: 500 })),
);

Two smaller things also vary and need less machinery. Which spot a vehicle is offered is decided by the table of acceptable sizes and by the ordering used for “nearest”. A lot that wants to fill from the top floor, or keep large spots for vans, changes that table or that comparison function.

Common mistake. A class hierarchy for vehicles: Car extends Vehicle, Motorcycle extends Vehicle, each with a method returning its size. The kinds of vehicle differ in one value and in no behavior, so subclasses add nothing a string does not. Inheritance is for different behavior ().

Step 6: The code

export type SpotSize = "small" | "medium" | "large";
export type TicketId = string & { readonly __brand: "TicketId" };

// Which sizes each kind of vehicle may use, best choice first.
const acceptable: Record = {
  motorcycle: ["small", "medium", "large"],
  car: ["medium", "large"],
  van: ["large"],
};

export interface Vehicle {
  readonly plate: string;
  readonly kind: VehicleKind;
}

export class LotError extends Error {}

// Owns the rule "one spot, at most one vehicle".
export class Spot {
  readonly id: string;
  readonly floor: number;
  readonly number: number;
  readonly size: SpotSize;
  private heldBy: TicketId | null = null;

  constructor(floor: number, number: number, size: SpotSize) {
    this.floor = floor;
    this.number = number;
    this.size = size;
    this.id = `F${floor}-${size[0]?.toUpperCase()}${number}`;
  }
  get free(): boolean {
    return this.heldBy === null;
  }
  occupy(ticket: TicketId): void {
    if (this.heldBy) throw new LotError(`spot ${this.id} is taken`);
    this.heldBy = ticket;
  }
  vacate(ticket: TicketId): void {
    if (this.heldBy !== ticket) throw new LotError(`spot ${this.id} is not held by ticket ${ticket}`);
    this.heldBy = null;
  }
}

export interface Ticket {
  readonly id: TicketId;
  readonly vehicle: Vehicle;
  readonly spot: Spot;
  readonly enteredAt: Date;
}
export interface Receipt {
  readonly ticket: TicketId;
  readonly plate: string;
  readonly minutes: number;
  readonly feeCents: number;
}

// Nearest first: lower floors before higher ones, lower numbers before higher ones.
const nearer = (a: Spot, b: Spot): boolean => a.floor < b.floor || (a.floor === b.floor && a.number < b.number);

export class ParkingLot {
  private readonly pricing: Pricing;
  private readonly freeSpots: Record> = { small: new MinHeap(nearer), medium: new MinHeap(nearer), large: new MinHeap(nearer) };
  private readonly open = new Map();
  private readonly inside = new Set(); // plates of vehicles currently parked
  private issued = 0;

  constructor(spots: Spot[], pricing: Pricing) {
    this.pricing = pricing;
    for (const spot of spots) this.freeSpots[spot.size].push(spot);
  }

  // Entry: claim the nearest spot of the smallest size that fits, and issue a ticket for it.
  park(vehicle: Vehicle, now: Date): Ticket {
    if (this.inside.has(vehicle.plate)) throw new LotError(`${vehicle.plate} is already parked here`);
    const spot = this.claim(vehicle.kind);
    if (!spot) throw new LotError(`no space for a ${vehicle.kind}`);
    const ticket: Ticket = { id: `T${(this.issued += 1)}` as TicketId, vehicle, spot, enteredAt: now };
    spot.occupy(ticket.id);
    this.open.set(ticket.id, ticket);
    this.inside.add(vehicle.plate);
    return ticket;
  }

  // Exit: work out the fee from the ticket's own times, and put the spot back.
  leave(ticketId: string, now: Date): Receipt {
    const ticket = this.open.get(ticketId as TicketId);
    if (!ticket) throw new LotError(`no open ticket ${ticketId}`);
    const minutes = Math.ceil((now.getTime() - ticket.enteredAt.getTime()) / 60_000);
    if (minutes < 0) throw new LotError("a vehicle cannot leave before it arrived");
    const feeCents = this.pricing(ticket.vehicle.kind, minutes);
    ticket.spot.vacate(ticket.id);
    this.freeSpots[ticket.spot.size].push(ticket.spot);
    this.open.delete(ticket.id);
    this.inside.delete(ticket.vehicle.plate);
    return { ticket: ticket.id, plate: ticket.vehicle.plate, minutes, feeCents };
  }

  // What the sign at the entrance shows.
  get freeCounts(): Record {
    return { small: this.freeSpots.small.size, medium: this.freeSpots.medium.size, large: this.freeSpots.large.size };
  }

  private claim(kind: VehicleKind): Spot | undefined {
    for (const size of acceptable[kind]) {
      const spot = this.freeSpots[size].pop();
      if (spot) return spot;
    }
    return undefined;
  }
}

The free spots are kept in three heaps, one for each size. A heap is a structure that always hands back its smallest item, here the nearest spot, and takes a number of steps proportional to the logarithm of its size to add or remove one. The choice is worth a sentence when asked how the nearest free spot is found.

How free spots are keptFind and take the nearestGive one backReasonable when
Scan all spots for the first free oneProportional to the number of spotsConstantA few hundred spots. Say so, and move on
A heap of free spots for each sizeLogarithmicLogarithmicAny size. Forty lines of code, in this chapter’s folder
An index in a database, ordered by floor and numberLogarithmicLogarithmicSeveral servers, as shown below

Because a spot is removed from its heap at the moment it is offered, the first invariant is protected twice: a spot that is taken is not in any heap to be found, and Spot.occupy would refuse it even if it were.

The row with the second van is the design’s one questionable behavior, and it is better to raise it than to have it found. Letting cars overflow into large spots fills the lot and can turn vans away. Whether that is right is a business decision, and it is one line of the fitting table.

A second test ran 20,000 random arrivals and departures against a three-floor lot. After every event it checked that the number of occupied spots equaled the number of open tickets and that free and occupied spots together equaled the total. Both held throughout, with 9,066 vehicles parked and 1,905 turned away at a full lot.

Step 7: Walk it

Several gates at once

The interviewer’s next question is certain: two cars arrive at two gates at the same instant, and one spot is left. The answer depends on where the lot’s state lives, and it is worth giving in two parts.

In one process. ParkingLot.park contains no await. On a single-threaded runtime it runs from its first line to its last without interruption, so the second gate’s call cannot start until the first has taken the spot (). The danger appears as soon as entering involves waiting, for a ticket printer or a database, and the wait is put in the wrong place.

// Two ways to write an entry gate when issuing the ticket involves waiting, for a printer or a database.
export class Gates {
  private readonly free: Spot[]; // nearest first
  private readonly printTicket: () => Promise;

  constructor(free: Spot[], printTicket: () => Promise) {
    this.free = [...free];
    this.printTicket = printTicket;
  }

  // Broken: looks at the nearest free spot, waits, and only then takes it.
  async enterRacy(): Promise {
    const spot = this.free[0];
    if (!spot) return null;
    await this.printTicket(); // the other gate runs here and sees the same spot
    this.free.shift();
    return spot;
  }

  // Fixed: takes the spot out of the free list first, and gives it back if printing fails.
  async enterClaimFirst(): Promise {
    const spot = this.free.shift();
    if (!spot) return null;
    try {
      await this.printTicket();
      return spot;
    } catch (error) {
      this.free.unshift(spot);
      throw error;
    }
  }
}

With one spot left and two gates entering together, the first version gave F1-M7 to both. The second gave it to one and nothing to the other, and when the printer was made to fail, the spot was back in the list for the next car. In a threaded language the same method would hold a lock around the check and the claim, and release it before printing.

With several servers. A real garage has a controller at each gate, or a service running as several copies. No lock in one process protects another, so the claim must be made by the shared database, as a single statement.

// With several servers, or several gate controllers, the claim has to be made by the database.
export function createTables(db: DatabaseSync): void {
  db.exec(`
    CREATE TABLE spots (id TEXT PRIMARY KEY, floor INTEGER NOT NULL, number INTEGER NOT NULL, size TEXT NOT NULL, plate TEXT);
    CREATE UNIQUE INDEX one_spot_for_each_vehicle ON spots (plate) WHERE plate IS NOT NULL;`);
}

// One statement finds the nearest free spot of an acceptable size and takes it. No other session can get in between.
export function claimSpot(db: DatabaseSync, plate: string, sizes: string[]): string | null {
  const marks = sizes.map(() => "?").join(", ");
  const row = db.prepare(`
    UPDATE spots SET plate = ?
    WHERE id = (SELECT id FROM spots WHERE plate IS NULL AND size IN (${marks}) ORDER BY floor, number LIMIT 1)
      AND plate IS NULL
    RETURNING id`).get(plate, ...sizes);
  return row ? String(row["id"]) : null;
}

export function releaseSpot(db: DatabaseSync, plate: string): boolean {
  return db.prepare("UPDATE spots SET plate = NULL WHERE plate = ?").run(plate).changes === 1;
}

Run against SQLite with two medium spots and one large, four cars claimed F1-M2, F1-M3 and F1-L4, and the fourth was told there was nothing. A second claim for a car already inside was refused by the unique index, which enforces “one spot for each vehicle” whatever the application code does. The statement works because the database applies an UPDATE as one indivisible change: the row is free when the statement begins or it is not updated (). In PostgreSQL the same idea is usually written by selecting the candidate row FOR UPDATE SKIP LOCKED, so that gates working at the same moment each take a different spot without waiting for each other.

Key points

  • The parking lot is a problem of handing out a limited resource. Its central invariant is one vehicle for each spot.
  • Separate the resource from the claim on it: the spot, and the ticket.
  • Kinds of vehicle and sizes of spot are values, and what fits what is a table of data.
  • Pricing is a strategy. Small rules such as a grace period and a daily cap wrap each other as functions.
  • Keep free spots in a structure that hands back the nearest one, and remove a spot from it at the moment it is offered.
  • Pass the time in, so that fees can be tested without a clock.
  • With several gates, checking for a free spot and taking it must be one step: no waiting in between in one process, and one statement in a shared database.
  • Most extensions change one table or add one function. Say which, and say what stays the same.

Check yourself

Why is there a Ticket type, when a spot could simply record the plate of the vehicle in it and when it arrived?

The ticket represents a stay: one vehicle’s claim on one spot from a moment in time. That is a different thing from the spot, which outlives thousands of stays. With a ticket, the fee is computed from the ticket’s own data, a ticket can be charged exactly once, and later needs such as paying before exit, lost tickets and a history of stays have an object to attach to.

With the pricing in this chapter, what does a car pay for 15 minutes, 16 minutes, 8 hours and 26 hours?

Nothing for 15 minutes, which is inside the grace period. 3.00 for 16 minutes: past the grace period, and the first started hour is charged in full. 24.00 for 8 hours, which is eight hours at 3.00 and exactly the daily cap. 30.00 for 26 hours: one full day at the cap, and two hours of the next day.

An interviewer says: “Vans should never be turned away while a car is sitting in a large spot.” What are two ways to change the design?

The simplest is to change the fitting table so that cars accept only medium spots. Then large spots are kept for vans, at the cost of turning cars away while large spots stand empty. A middle path is to let cars overflow only while more than some number of large spots remain free. Both are changes to the allocation rule, and neither touches Spot, Ticket or pricing.

Explain exactly how two gates could assign the same spot, and what removes the possibility in a single process.

A gate reads the nearest free spot, then waits for something slow such as a printer, and only afterwards marks the spot as taken. During the wait, the other gate reads the same list and sees the same spot as free. The repair is to remove the spot from the free structure in the same uninterrupted step as reading it, before any waiting, and to put it back if the rest of the entry fails.

The garage’s software now runs on three servers behind a load balancer. Why is a lock or the claim-first rule inside ParkingLot no longer enough, and what replaces it?

Each server has its own memory, so each has its own lock and its own idea of which spots are free. Two servers can both hand out the same spot. The claim has to move to the store they share: one UPDATE that takes a free spot only if it is still free and returns which one, backed by a uniqueness constraint so that a mistake in the application cannot break the rule.

Why does the design have no Floor class, and what request would make you add one?

Within the stated scope a floor has no data or behavior of its own. It is a number on a spot, used for ordering. Adding a class for it would produce an empty container. A request such as “close a floor for cleaning” or “show a count on each floor’s sign” gives the floor state and operations, and then it should become a class.

How would you test that a stay of exactly 24 hours and one of 24 hours and one minute are charged correctly?

Call the pricing function directly with 1,440 and 1,441 minutes and compare with the expected fees: 24.00, and 27.00 for one capped day and one started hour of the next. No lot, ticket or clock is needed, because pricing is a pure function of the kind of vehicle and the minutes, and leave receives the current time as an argument.
