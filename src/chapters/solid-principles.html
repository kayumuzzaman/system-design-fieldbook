What a design principle is for

The previous chapter ended with two measures of a design: coupling between parts should be low, and cohesion within each part should be high. Those say what good looks like. They do not say what to do on a Tuesday afternoon with a class that has grown to six hundred lines. Principles are the next level down: rules of thumb, each aimed at one common way that code becomes hard to change.

The best-known set was assembled by Robert C. Martin around 2000 from his own work and that of others, and later given the acronym SOLID.

PrincipleIn one sentenceThe trouble it prevents
SSingle responsibilityA class should have one reason to changeA change for one purpose breaking another
OOpen/closedAdd behavior by adding code, not by editing code that worksEvery new case reopening tested functions
LLiskov substitutionAnything that claims to be a subtype must behave like oneCode that is correct for the type failing for one of its subtypes
IInterface segregationCallers should not depend on methods they do not useWide interfaces that are hard to implement, fake and change
DDependency inversionThe important code should not depend on the replaceable codeBusiness rules welded to a database or a framework

They are guidelines and not laws. Each has a cost, usually more classes and more indirection, and the last section of this chapter is about paying it only where it buys something. The examples continue with the photo app. Every “before” and “after” below was run, and where the two are supposed to behave identically a test confirmed that they do.

Single responsibility

The photo app emails each user a monthly summary of the storage they use. The first version is one class.

export type StoredPhoto = { bytes: number; deleted: boolean };
export type Usage = { photos: number; gigabytes: number };
type Send = (to: string, html: string) => void;

// Before: one class answers to three different people.
export class UsageReportBefore {
  private readonly photos: StoredPhoto[];
  private readonly send: Send;

  constructor(photos: StoredPhoto[], send: Send) {
    this.photos = photos;
    this.send = send;
  }

  usage(): Usage { // the finance team decides what counts toward a bill
    const kept = this.photos.filter((p) => !p.deleted);
    return { photos: kept.length, gigabytes: Math.ceil(kept.reduce((sum, p) => sum + p.bytes, 0) / 1e9) };
  }
  html(): string { // the design team decides how it looks
    const u = this.usage();
    return `
Your storage
${u.photos} photos, ${u.gigabytes} GB
`;
  }
  email(to: string): void { // the operations team decides how mail is delivered
    this.send(to, this.html());
  }
}

// After: one piece for each of them.
export function usageOf(photos: StoredPhoto[]): Usage {
  const kept = photos.filter((p) => !p.deleted);
  return { photos: kept.length, gigabytes: Math.ceil(kept.reduce((sum, p) => sum + p.bytes, 0) / 1e9) };
}

export function usageAsHtml(usage: Usage): string {
  return `
Your storage
${usage.photos} photos, ${usage.gigabytes} GB
`;
}

export class ReportMailer {
  private readonly send: Send;
  constructor(send: Send) {
    this.send = send;
  }
  deliver(to: string, html: string): void {
    this.send(to, html);
  }
}

The class is short and it works. The problem is who asks for it to change. Finance changes what counts toward a bill: perhaps deleted photos should count for thirty days. Design changes the wording and layout. Operations changes how mail is sent. Three groups, with unrelated reasons and unrelated schedules, edit the same file. When design reworks the HTML and accidentally alters a line that usage relied on, a billing figure is wrong, and nobody in finance was told the file had been touched.

The single responsibility principle says that a class or module should have only one reason to change, where a reason is a person or group who can ask for the change. In the second version a request from finance touches usageOf and nothing else. Both versions produced the same email in a test.

Two misreadings are common. The principle does not say a class should do one small thing: Album in the previous chapter has five methods and one responsibility. And it does not say to split everything: code that always changes together belongs together. The test is the question “if this were wrong, who would notice, and who would ask for it to be fixed?”. If the answer names two different groups, there are two responsibilities.

Open/closed

Storage plans have prices and limits. The simplest code is a function for each question, with a branch for each plan.

// Before: every question about plans is a function that lists the plans. Prices are in cents.
export type PlanName = "free" | "plus" | "family";

export function monthlyPriceBefore(plan: PlanName, gigabytes: number): number {
  if (plan === "free") return 0;
  if (plan === "plus") return 300 + Math.max(0, gigabytes - 100) * 2;
  return 800 + Math.max(0, gigabytes - 500) * 2;
}

export function albumLimitBefore(plan: PlanName): number {
  if (plan === "free") return 10;
  if (plan === "plus") return 200;
  return 1000;
}

// After: a plan is an object that answers the questions about itself.
export interface Plan {
  readonly name: string;
  readonly albumLimit: number;
  monthlyPrice(gigabytes: number): number;
}

const withAllowance = (name: string, base: number, included: number, albumLimit: number): Plan => ({
  name,
  albumLimit,
  monthlyPrice: (gigabytes) => base + Math.max(0, gigabytes - included) * 2,
});

export const free: Plan = { name: "free", albumLimit: 10, monthlyPrice: () => 0 };
export const plus = withAllowance("plus", 300, 100, 200);
export const family = withAllowance("family", 800, 500, 1000);

export class Plans {
  private readonly byName = new Map();

  constructor(plans: Plan[]) {
    for (const plan of plans) this.byName.set(plan.name, plan);
  }
  named(name: string): Plan {
    const plan = this.byName.get(name);
    if (!plan) throw new Error(`no plan called ${name}`);
    return plan;
  }
}

// A year later: a new plan with a rule of its own. Nothing above this line is edited.
export const pro: Plan = {
  name: "pro",
  albumLimit: 5000,
  monthlyPrice: (gigabytes) => 2000 + Math.ceil(Math.max(0, gigabytes - 2000) / 1000) * 500, // sold in blocks of a terabyte
};

Then the business adds a Pro plan, priced differently from the others.

The open/closed principle says that a module should be open for extension and closed for modification: it should be possible to add new behavior by writing new code, without editing code that already works. In the second version the Pro plan is one new object, and the registry and every caller are untouched. A test confirmed that the object version gives the same price and limit as the functions for every existing plan.

The mechanism is the polymorphism of . What the principle adds is a way to decide where to use it. No design can be closed against every possible change, and trying produces abstractions nobody needs. Choose the direction in which the code has already changed more than once. Plans get added. So plans are the thing to make pluggable. A sensible rule: write the simple branch the first time, and introduce the interface when the second or third variation arrives and shows what varies.

Liskov substitution

The principle is named for Barbara Liskov, who stated it in 1987. A subtype must be usable anywhere its supertype is expected, without the program going wrong. The compiler checks part of this: that the methods exist with compatible types. It cannot check the rest, which is that they behave as the supertype promised.

The photos service takes a snapshot of its store every night for backups. A snapshot can be read and must never be written. It is tempting to make it one more kind of store.

// A snapshot of last night's photos. It has the right shape, and it breaks the promise that save works.
export class SnapshotStore implements PhotoStore {
  private readonly source: PhotoStore;
  constructor(source: PhotoStore) {
    this.source = source;
  }
  async save(): Promise {
    throw new Error("a snapshot cannot be changed");
  }
  load(id: string): Promise {
    return this.source.load(id);
  }
}

// Written for "any PhotoStore". It compiles with a snapshot as the destination, and fails when run.
export async function copyAll(from: PhotoStore, to: PhotoStore, ids: string[]): Promise {
  let copied = 0;
  for (const id of ids) {
    const bytes = await from.load(id);
    if (bytes) {
      await to.save(id, bytes);
      copied += 1;
    }
  }
  return copied;
}

copyAll is correct. It was written against the PhotoStore interface and uses nothing else. Handed a SnapshotStore as the destination, it compiles and then fails on the first photo.

The Liskov substitution principle says that if code works with a type, it must keep working when given any subtype of that type. A subtype breaks it in four typical ways.

The subtypeExample
Refuses something the supertype acceptsA store whose save rejects files over 1 MB when the interface set no limit
Delivers less than the supertype promisedA save that returns before the data is stored, when callers rely on being able to load it at once
Throws where the supertype does notThe snapshot’s save, or any method whose body is “not supported”
Breaks a rule the supertype maintainedA subclass of Album that lets the cover be a photo outside the album

A method that exists only to throw “not supported” is the clearest sign. The type is claiming to be something it is not. The fix is rarely inside the subtype. It is to make the promise smaller, so that it can be kept.

// After: two smaller promises. A type now claims only what it can keep.
export interface PhotoReader {
  load(id: string): Promise;
}
export interface PhotoWriter {
  save(id: string, bytes: Uint8Array): Promise;
}

export class Snapshot implements PhotoReader {
  private readonly source: PhotoReader;
  constructor(source: PhotoReader) {
    this.source = source;
  }
  load(id: string): Promise {
    return this.source.load(id);
  }
}

With a function declared as copyAllSafely(from: PhotoReader, to: PhotoWriter, …), passing a snapshot as the destination is rejected by the compiler. The same mistake that failed in production now cannot be written.

Interface segregation

The fix above is the next principle arriving early. Here it is from the caller’s side. The photos service uses a media library that can resize images, find faces, read text out of pictures and convert video. A function that makes thumbnails needs one of those four.

type Image = { width: number; height: number };

// Before: one interface for everything the media library can do.
export interface MediaTools {
  resize(image: Image, width: number): Image;
  detectFaces(image: Image): number;
  readText(image: Image): string;
  transcodeVideo(path: string, format: string): string;
}

export function thumbnailBefore(tools: MediaTools, image: Image): Image {
  return tools.resize(image, 200); // uses one method of four
}

// After: one interface for each thing a caller might need.
export interface Resizer {
  resize(image: Image, width: number): Image;
}
export interface FaceDetector {
  detectFaces(image: Image): number;
}

export function thumbnail(resizer: Resizer, image: Image): Image {
  return resizer.resize(image, 200);
}

// One class can still do several jobs. Each caller sees only the part it asked for.
export class ImageTools implements Resizer, FaceDetector {
  resize(image: Image, width: number): Image {
    return { width, height: Math.round((image.height * width) / image.width) };
  }
  detectFaces(): number {
    return 0;
  }
}

The interface segregation principle says that no caller should be forced to depend on methods it does not use. The cost of ignoring it showed up in the test for this code. To exercise thumbnailBefore, the test had to supply an object with all four methods, three of them written only to throw. To exercise thumbnail, it supplied an object with one. The same burden falls on every real implementation, and a class that can resize and cannot transcode video ends up with a method that throws, which is the Liskov violation again.

  • Design interfaces from the caller’s side. Ask what this function needs from its collaborator, and name that. Resizer describes a role. MediaTools describes a product.
  • One class may play several roles. ImageTools implements two interfaces. Splitting interfaces does not require splitting classes.
  • Narrow parameter types cost nothing in TypeScript. Because types are matched by shape, a function can ask for { resize(…): Image } and accept any existing object that has it.

Dependency inversion

Some code in a system is the reason the system exists: the rule that only an album’s owner may share it. Other code is plumbing that could be swapped: which database, which mail service. The first kind should be the most stable and the easiest to test. In the natural way of writing it, the opposite happens.

// Before: the rule about sharing creates its own database and mail clients.
export class ShareAlbumBefore {
  private readonly albums = new SqlAlbums();
  private readonly mailer = new SmtpMailer();

  run(albumId: string, by: string, withUser: string): void {
    const album = this.albums.find(albumId);
    if (album.owner !== by) throw new Error("only the owner can share an album");
    if (!album.sharedWith.includes(withUser)) album.sharedWith.push(withUser);
    this.albums.save(album);
    this.mailer.send(withUser, `${by} shared an album with you`);
  }
}

// After: the rule says what it needs, as interfaces it owns. Something else decides what to plug in.
export interface Albums {
  find(id: string): Album;
  save(album: Album): void;
}
export interface Mailer {
  send(to: string, text: string): void;
}

export class ShareAlbum {
  private readonly albums: Albums;
  private readonly mailer: Mailer;

  constructor(albums: Albums, mailer: Mailer) {
    this.albums = albums;
    this.mailer = mailer;
  }

  run(albumId: string, by: string, withUser: string): void {
    const album = this.albums.find(albumId);
    if (album.owner !== by) throw new Error("only the owner can share an album");
    if (!album.sharedWith.includes(withUser)) album.sharedWith.push(withUser);
    this.albums.save(album);
    this.mailer.send(withUser, `${by} shared an album with you`);
  }
}

// The one place that knows which real classes exist. It runs once, when the program starts.
export function buildShareAlbum(): ShareAlbum {
  return new ShareAlbum(new SqlAlbums(), new SmtpMailer());
}

In the first class, the rule cannot be run without a database and a mail server. A test that tried got “no database is reachable from here”. Everything about the database client, its connection settings, its failures and its upgrade schedule, has become the sharing rule’s problem.

The dependency inversion principle says that code expressing policy should not depend on code handling details. Both should depend on an abstraction, and the abstraction should be shaped by what the policy needs. In the second version ShareAlbum declares two small interfaces, and the database class conforms to them. The test ran the rule with two fakes of three lines each, and checked that sharing twice adds a person once and that a non-owner is refused.

Two terms are often confused with the principle and are worth separating.

  • Dependency injection is the technique that makes it work: an object receives the things it depends on, usually through its constructor, instead of creating them. It needs no framework. The constructor of ShareAlbum is dependency injection.
  • The composition root is the one place in a program, near its entry point, where the real objects are created and connected. buildShareAlbum is a small one. It is the only code that names both the rule and the concrete database class.

At the scale of a whole application, the same idea arranges the layers (), and it is what makes the testing approach of possible.

Four shorter rules

SOLID is about the shape of classes. Four older rules are about habits of mind, and they are quoted at least as often.

Do not repeat yourself

DRY, for “do not repeat yourself”, says that every piece of knowledge should have one authoritative place in a system. The word that matters is knowledge. The rule that a free plan allows ten albums is knowledge. If it is written in the web server, in the mobile app and in a database constraint, the three will one day disagree.

The principle is not about text that happens to look alike. An album title and a display name may both be limited to 60 characters today. They are two decisions, made by different people for different reasons, and merging them into one validateName function ties together things that will want to change separately. Removing that kind of duplication creates coupling where there was none. A useful guard is to wait for the third occurrence before extracting anything, and to ask whether the copies would have to change together. If the answer is no, leave them alone. A little duplication is far cheaper to live with than the wrong abstraction.

Keep it simple, and build it when you need it

KISS, usually read as “keep it simple”, says to prefer the most direct design that meets the requirements. YAGNI, “you aren’t gonna need it”, says not to build something for a need you only expect. Both push against the principles above, and that is their purpose.

The argument for YAGNI is about cost. A feature or an extension point built on speculation costs the time to build it, the time to carry it through every later change, and the distortion it leaves in the design when the real need turns out to have a different shape. It pays off only if the guess was right in detail. The cheap alternative is code that is simple enough to change when the need is real. YAGNI is not an argument against tests, clear names or small functions. Those are what keep a later change cheap.

The Law of Demeter

The Law of Demeter, also called the principle of least knowledge, says that a method should call only its own object, its parameters, objects it creates and objects its own object holds. In short: talk to your neighbors, not to your neighbors’ neighbors. It is named for a research project at Northeastern University, where it was formulated in 1987.

// Before: plain records, and a caller that walks through three of them.
type PlanData = { maxPhotoBytes: number };
type OwnerData = { active: boolean; plan: PlanData };
type AlbumData = { owner: OwnerData; photoCount: number };

export function canUploadBefore(album: AlbumData, bytes: number): boolean {
  return album.owner.active && album.owner.plan.maxPhotoBytes >= bytes && album.photoCount < 1000;
}

// After: each object answers a question about itself, and asks its neighbor about the rest.
export class Plan {
  private readonly maxPhotoBytes: number;
  constructor(maxPhotoBytes: number) {
    this.maxPhotoBytes = maxPhotoBytes;
  }
  allows(bytes: number): boolean {
    return bytes <= this.maxPhotoBytes;
  }
}

export class Owner {
  private readonly active: boolean;
  private readonly plan: Plan;
  constructor(active: boolean, plan: Plan) {
    this.active = active;
    this.plan = plan;
  }
  canStore(bytes: number): boolean {
    return this.active && this.plan.allows(bytes);
  }
}

export class Album {
  private readonly owner: Owner;
  private photoCount = 0;
  constructor(owner: Owner) {
    this.owner = owner;
  }
  canAccept(bytes: number): boolean {
    return this.photoCount < 1000 && this.owner.canStore(bytes);
  }
}

The first function knows the structure of three types. A decision to give owners several plans, or to move the size limit somewhere else, breaks code that thought it was working with an album. In the second version each object answers a question about itself, a style often summarized as “tell, don’t ask”. The two gave the same answers in a test.

The law concerns objects with behavior. A chain through plain data, such as order.address.city on a record that came from JSON, is reading a document and not a violation. Nor is a fluent chain in which every call returns the same kind of object, such as array methods.

Applying them without overdoing it

Read as commands to be maximized, the principles produce bad software of a recognizable kind: an interface for every class, a factory for every constructor, twelve files to follow before finding the line that does anything. The principles are answers to problems. Where the problem is absent, the answer is only cost.

PrincipleUnder-appliedOver-appliedA reasonable trigger
Single responsibilityClasses that everyone edits for unrelated reasonsDozens of tiny classes that only make sense togetherTwo groups, or two schedules, changing one file
Open/closedEvery new case reopens working code in several placesExtension points for variations that never arriveThe second or third variation of the same thing
Liskov substitutionMethods that throw “not supported”Hard to overdo. This one is closer to a correctness ruleAlways, whenever you write extends or implements
Interface segregationFakes with ten stubbed methodsOne-method interfaces nobody can findA caller that uses a fraction of what it is given
Dependency inversionBusiness rules that need a database to runAn interface with exactly one implementation, forever, for something that is not a boundaryA boundary: storage, network, clock, another team’s service
DRYThe same rule in three places, drifting apartUnrelated code forced through one shared functionThe third copy, of the same knowledge

The principles also pull against each other, and knowing the tensions is most of the skill.

  • Open/closed against YAGNI. One says prepare for extension, the other says do not prepare. Resolve it with evidence: extend along the lines the code has already changed.
  • DRY against low coupling. Sharing code between two services removes duplication and ties their releases together. Across a service boundary, a little duplication is usually the better trade ().
  • Single responsibility against simplicity. Each split adds a name to learn and a connection to follow. A fifty-line class with two mild responsibilities may be better left alone.

One question settles most cases: what change am I making easier, and has that change ever been asked for?

In an interview. Do not recite the acronym. Use the principles as reasons while you design: “pricing varies by plan and plans get added, so that is an interface”, “the booking rule should not know about the payment provider, so it takes a gateway through its constructor”. If asked to critique code, look for the three concrete signs from this chapter: a class two teams would edit, a switch on type repeated in several places, and a method that exists only to throw.

Common mistake. Introducing an abstraction to remove a duplication you have seen twice, then bending it with flags and optional parameters as the two uses drift apart. A function with five boolean parameters is usually two or three functions that were merged too early. Putting the duplication back is a legitimate refactoring.

Key points

  • Principles exist to keep change cheap. Each one targets a specific way that code becomes hard to change.
  • Single responsibility: group code by who asks for it to change, and separate what answers to different people.
  • Open/closed: where the same kind of variation keeps arriving, make it something you add and not something you edit.
  • Liskov substitution: a subtype must keep every promise of its supertype. A method that only throws is a broken promise.
  • Interface segregation: design interfaces from the caller’s needs, small and named for a role.
  • Dependency inversion: business rules declare the interfaces they need and receive implementations from outside. One place assembles the real objects.
  • DRY is about knowledge, not similar text. KISS and YAGNI say to solve the problem you have.
  • The Law of Demeter: ask the nearest object, and do not reach through it.
  • Every principle has a cost in indirection. Apply one when its problem has shown up, not before.

Check yourself

An Invoice class calculates tax, renders a PDF and writes itself to the database. Which principle does it strain, and how would you decide where to split it?

Single responsibility. Ask who would request each change: tax rules come from finance or the law, the PDF layout from design or customers, and persistence from the engineers who run the database. Those are three reasons to change, so three pieces: a calculation, a renderer and a repository. If in practice only one person ever touches all three together, the split is less urgent.

A function computes shipping cost with a switch over five carriers. Is that a violation of the open/closed principle?

Not by itself. One switch in one place is simple and easy to read. It becomes a problem when carriers are added regularly and the same switch appears in several functions, such as cost, tracking link and label format, so that each new carrier means editing all of them. At that point a Carrier interface with one object for each carrier turns the change into an addition.

ReadOnlyList extends List and overrides add to throw. A function that accepts a List and appends to it receives one. What principle is broken, by which class, and what is the fix?

Liskov substitution, by ReadOnlyList: it claims to be a list and cannot keep the promise that add works. The function is not at fault. The fix is to make the promise smaller: a ReadableList interface with only the reading methods, which both kinds implement, and a separate interface for writing. Functions then ask for exactly what they need, and passing a read-only list where writing is required fails at compile time.

Why did the test for a function taking the four-method MediaTools need three stubs that throw, and why does that matter beyond the test?

Because the parameter type demanded all four methods although the function uses one. The test is the first caller to feel it, and every real implementation feels it too: a library that can resize but not transcode video must still provide something for transcodeVideo. A change to any of the four methods also forces a recompile and review of code that never called it. Asking for a Resizer removes all three costs.

What is the difference between dependency inversion and dependency injection?

Dependency inversion is a principle about direction: important policy code should depend on abstractions it defines, and detail code should conform to them. Dependency injection is a technique: an object is given its collaborators from outside instead of constructing them. Injection is the usual way to achieve inversion, but you can inject a concrete class and gain testability without inverting anything, and the principle says nothing about frameworks or containers.

Two functions, one validating album titles and one validating display names, contain identical code. Should they be merged under DRY?

Only if they represent the same piece of knowledge, meaning that a change to one rule must always be a change to the other. Here they are separate decisions that happen to coincide, so merging couples them: the day display names are allowed emoji and album titles are not, the shared function grows a flag. Leave them separate, or share a small helper for the mechanical part, such as measuring length.

Rewrite order.customer.wallet.balance >= order.total to follow the Law of Demeter, and say what was gained.

Ask the order: order.canBePaid(), which asks its customer canPay(total), which asks its wallet covers(amount). The caller now depends only on Order. The customer can change how it holds money, to several wallets or a credit line, without any caller of the order being edited. The check also has one home, so it cannot be written slightly differently in ten places.
