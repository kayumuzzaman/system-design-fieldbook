The problem

The problem. Design a web crawler that downloads two billion pages a month for a search engine or a research archive, starting from a list of seed URLs. It must respect site owners’ rules, never overload a site, avoid fetching the same content twice, and keep its copy of important pages fresh.

The difficulty is that the crawler’s speed is limited by other people’s servers. A crawler could fetch a thousand pages a second from one site, and must instead wait seconds between requests to it, so the only way to be fast is to fetch from thousands of sites at once. Meanwhile the crawler is turning a graph of unknown size, full of duplicates and traps, into a queue it can finish. In the terms of , it is a throughput problem shaped by a constraint the designer does not control, and the central structure is the queue of URLs to fetch.

Step 2: Estimates

The average page size comes from a real crawl: Common Crawl’s August 2026 archive held 2.14 billion pages in 360 TiB, uncompressed, about 185 KB per page including headers. The rest follows from the target (), with assumptions stated:

fetch rate: 2 billion pages ÷ 30 days ≈ 772 pages a second, steady, since the crawler sets its own pace
bandwidth: 772 × 185 KB ≈ 143 MB a second ≈ 1.1 Gbit/s; storage: about 370 TB a month before compression
fetches in flight: 772 a second × 1 s per fetch = 772 at once, by Little’s law ()
sites in progress: one request per site every 1 s fetch + 2 s pause ⇒ at least 772 × 3 ≈ 2,300 sites being crawled at every moment
seen-URL filter: 10 billion URLs × 9.6 bits at 1% false positives ≈ 12 GB

The bandwidth and storage are ordinary. The two numbers that shape the design are the 2,300 sites that must be in progress at once, which rules out any queue that takes URLs in the order they were found, and the tens of billions of URLs that must be checked against everything seen before, which rules out keeping their full text in memory.

A crawler’s most important interface is the one it presents to other people’s servers. It identifies itself, asks only for what changed, and accepts compressed responses.

Fetchers lease batches of URLs rather than taking them for good. A fetcher that crashes stops renewing its lease, and the URLs return to the frontier when it expires, so a lost machine costs a few minutes of work rather than a hole in the crawl. Reporting results twice is harmless, because recording a fetch is keyed by URL and time ().

Everything is keyed by host first, because the host is the unit of politeness. Partitioning the crawl by a hash of the host () puts every URL of a site, its robots rules and its timing on one machine, so politeness never needs coordination between machines. Links that point to a host owned by another machine are batched and sent to it.

Step 5: The design

The loop runs on many machines, each owning the frontier for its share of hosts and running hundreds of fetchers. The fetchers keep caches of DNS answers and robots rules per host, since asking the DNS for every one of 772 fetches a second would be slow and impolite to DNS servers too ().

Step 6a: The frontier and politeness

The URL frontier is the crawler’s list of URLs waiting to be fetched, together with the rules for which comes next. Those rules carry politeness: limiting how often and how heavily a crawler requests pages from one site, so that crawling never degrades the site for its real users. A single first-in, first-out queue cannot do it. The links on a page mostly point to the same site, so a queue fills with runs of URLs from one host, and a polite crawler must wait seconds before each, with everything behind it waiting too.

The answer, from the Mercator crawler of 1999, is a queue for each host and a heap that orders hosts by the time each may next be fetched. A free fetcher takes the host at the top. A host that was fetched a moment ago goes back into the heap with a later time and delays only its own URLs.

// A queue for each host, and a heap of hosts ordered by the earliest time each may be fetched
// again. A free fetcher takes the host that is ready first, so a slow or busy host delays only
// its own URLs. Mercator's "back queues" work the same way.
export class HostQueueFrontier implements Frontier {
  private readonly queues = new Map();
  private readonly ready = new MinHeap<{ at: number; host: string }>((a, b) => a.at < b.at);
  private readonly waiting = new Set(); // hosts in the heap or being fetched
  private readonly allowed = new Map();
  private readonly delay: number;
  private count = 0;
  constructor(delay: number) {
    this.delay = delay;
  }
  add(url: string, host: string): void {
    let q = this.queues.get(host);
    if (!q) this.queues.set(host, (q = []));
    q.push(url);
    this.count += 1;
    if (!this.waiting.has(host)) {
      this.waiting.add(host);
      this.ready.push({ at: this.allowed.get(host) ?? 0, host });
    }
  }
  next(now: number): Next | null {
    const top = this.ready.pop();
    if (!top) return null;
    const url = (this.queues.get(top.host) as string[]).shift() as string;
    this.count -= 1;
    return { url, host: top.host, start: Math.max(now, top.at) };
  }
  fetched(host: string, end: number): void {
    const at = end + this.delay;
    this.allowed.set(host, at);
    if ((this.queues.get(host) as string[]).length > 0) this.ready.push({ at, host });
    else this.waiting.delete(host);
  }
  earliest(): number | null {
    return this.ready.peek()?.at ?? null;
  }
  size(): number {
    return this.count;
  }
}

The chapter’s code crawled 20,000 pages of a synthetic web of 5,000 hosts, generated so that 80% of links stay on their own host, with 100 fetchers, half a second per fetch on average, and a pause of 2 seconds between requests to one host.

One polite queue managed 0.61 pages a second, whatever the number of fetchers: each run of same-host URLs was fetched one at a time, three seconds apart. Ignoring politeness was fast, 198 pages a second, and 15,666 of the 20,000 requests went to a host that had been asked less than two seconds before. A queue per host was as fast as the impolite queue, 197 pages a second, with no impolite requests at all, and it kept scaling with fetchers, to 870 pages a second with 800, as long as there were enough hosts with URLs ready. The figure above shows what happens when there are not: fetchers idle while every host waits out its pause. That is why a crawl must spread across thousands of sites, and why the estimate asked how many must be in progress.

The pause itself can adapt. Making it a multiple of the time the host’s last response took means a slow, struggling server is asked less often, and a crawler should back off further on errors and on 429 or 503 responses (). Real frontiers also have a layer in front of the host queues that orders URLs by priority, so that important and frequently changing pages are fetched first, and a schedule for revisiting each page based on how often it has changed before.

Step 6b: Not fetching the same thing twice

Duplicates arrive in three forms, and each needs its own filter.

The same URL, spelled differently. HTTPS://News.Example:443/p/7#top and https://news.example/p/7 are one page. URL normalization rewrites every URL into one canonical form before it is compared: lower-case scheme and host, no default port, no fragment, no tracking parameters, the other parameters sorted.

const tracking = /^(utm_[a-z]+|fbclid|gclid|sid|sessionid)$/i;

export function normalize(raw: string): string | null {
  let u: URL;
  try {
    u = new URL(raw);
  } catch {
    return null;
  }
  if (u.protocol !== "https:" && u.protocol !== "http:") return null;
  u.hash = ""; // the server never sees the fragment
  const params = [...u.searchParams].filter(([k]) => !tracking.test(k)).sort(([a], [b]) => (a < b ? -1 : a > b ? 1 : 0));
  u.search = new URLSearchParams(params).toString();
  return u.toString(); // URL already lower-cases the scheme and host and drops a default port
}

In the simulated web, where 15% of links were written with a capitalized host, a fragment or a tracking parameter, crawling without normalization spent 3,668 of 20,000 fetches, 18.3%, on pages it had already fetched.

A URL already seen. Every link found must be checked against every URL the crawler has ever accepted, tens of billions of them. A Bloom filter answers in memory with about 9.6 bits per URL for a 1% error rate; in the test, a filter for 200,000 URLs took 239,627 bytes and wrongly reported 1.00% of unseen URLs as seen. Its errors fall in the safe direction for a crawler: it never reports a seen URL as new, and a false “seen” means a page is skipped. Used in the crawl, sized for the 55,000 URLs it would end up holding, it skipped 74 of about 55,000 new URLs, 0.13%, fewer than 1% because the filter is emptier for most of the crawl. A page skipped this way is often found again through another link later, after the filter is rebuilt.

The same content at another URL. Mirrors, printer-friendly versions and pages that differ only in an advertisement are separate URLs with the same or nearly the same content. Exact copies are caught by a hash of the content: in the test, 196 of 20,000 fetched pages had been seen before, from mirror hosts. Mercator found 8.5% of its successful downloads were exact duplicates. Near copies need a fingerprint in which similar pages differ by a few bits, such as SimHash ().

With word triples as features, a copy with a new 12-word footer differed from the original in 0 to 11 of 64 bits, a copy with 5% of its words changed in 1 to 21, and unrelated articles in 17 to 43. A threshold of 3 bits caught only 42% of the footer copies; a threshold of 10 caught 99.9% of them, 48% of the edited ones, and no unrelated pages. The threshold must be measured on real pages, because it depends on the features chosen and on how much difference still counts as the same page.

Step 6c: Robots rules and traps

Site owners state their rules in /robots.txt, a long-standing convention standardized as RFC 9309 in 2022. A crawler reads the groups that apply to its user agent, follows the most specific matching rule, and caches the file, but per the RFC should not use a cached copy for more than 24 hours unless the file cannot be fetched. Two of its rules are easy to get backwards. A missing file, a 404, means everything may be crawled; a server error or no answer means nothing may be, until the file can be read. And the RFC states plainly that “these rules are not a form of access authorization”: they ask for good behavior, and a crawler that respects them is choosing to.

A crawler trap is a site, usually unintentionally, that generates an unbounded number of distinct URLs: a calendar with a link to the next day forever, session ids added to every link, search pages for every combination of filters. In the test, a crawl that started at an endless calendar fetched 2,000 calendar pages, all it was allowed, and had more queued. Politeness alone limited the damage to 0.40 pages a second, but that is about 34,700 pages a day, forever. A budget of 100 URLs for the host stopped it at 100.

Common mistake. Detecting traps only by URL length or depth. A calendar’s URLs are short and its pages are one link apart. Give every host a budget that grows with its importance, such as the number of other sites linking to it, and strip session parameters during normalization; then a trap costs a bounded number of fetches however it is built.

At ten times the scale, 20 billion pages a month, the arithmetic gives 7,700 pages a second, 11 Gbit/s and 23,000 sites in progress: more machines and more hosts, the same design. The URL store grows into hundreds of billions of records and becomes the main cost, and choosing what not to crawl, by priority and budgets, matters more than crawling faster. At a hundred times, the limit is the web itself: there are not enough distinct, useful pages to fetch that fast politely, and the work shifts to revisiting, deciding how often each page changes and fetching it about that often.

In the real world

  • Mercator (Heydon and Najork, 1999) gave each worker thread its own first-in, first-out queue and put all URLs of a host into the same one, so that “at most one worker thread will download documents from a given Web server”. Over an eight-day crawl of 77.4 million requests it averaged 112 documents a second, and 8.5% of successful downloads were duplicates of content already fetched.
  • IRLbot (Lee, Leonard, Wang and Loguinov, 2008) crawled 6.3 billion valid HTML pages in 41 days on a single server, about 1,789 pages a second, and was designed around three problems: checking URL uniqueness at that scale, spam sites with endless links, and per-host rate limits.
  • Common Crawl’s August 2026 archive, crawled from 7 to 20 August, holds 2.14 billion pages, 360 TiB uncompressed, of which 0.7 billion URLs had not been in earlier crawls.
  • Googlebot, per Google’s documentation updated in February 2026, “shouldn’t access your site more than once every few seconds on average” for most sites, and crawls the first 2 MB of a supported file type and the first 64 MB of a PDF.

Key points

  • A crawler’s rate is limited by politeness to each site, so it is fast only by fetching from thousands of sites at once.
  • Give each host its own queue and order hosts by when each may be fetched next. In the test that was 197 pages a second with no impolite requests, against 0.61 for one polite queue.
  • Normalize every URL before comparing it. Without it, 18.3% of fetches in the test were pages already fetched.
  • A Bloom filter holds tens of billions of seen URLs in gigabytes, and its false “seen” costs a skipped page, which a crawler can tolerate.
  • Catch exact copies with a content hash and near copies with SimHash, and measure the threshold on real pages.
  • Read robots.txt with its failure rules the right way round, and give every host a budget so that no trap costs more than it allows.
  • Partition everything by host, so politeness needs no coordination between machines.

Check yourself

Why does a single first-in, first-out queue make a polite crawler slow, even with hundreds of fetchers?

Links mostly point to the same site, so the queue holds runs of URLs from one host. To be polite, the URL at the head must wait out its host’s pause, and in a single queue everything behind it waits too. In the test the rate stayed near 0.6 pages a second whatever the number of fetchers.

The crawl must fetch 772 pages a second with a 2-second pause per site and 1 second per fetch. How many sites must be in progress?

Each site can give one page every 3 seconds, a third of a page a second, so at least 772 × 3 ≈ 2,300 sites must be in progress at every moment, and in practice many more, since many sites have few pages left to fetch.

A Bloom filter of seen URLs reports a new URL as seen. What happens, and why is that acceptable here?

The URL is not queued, so its page is skipped in this crawl. That is the safe direction for a crawler: the filter never reports a seen URL as new, so it never causes a duplicate fetch, and a skipped page is often found again through another link or in a later crawl.

Why partition the crawl by host rather than by a hash of the whole URL?

Politeness is per host. With all of a host’s URLs, its robots rules and its last request time on one machine, that machine can enforce the pause alone. Partitioning by URL would spread one site over every machine, which would then have to coordinate every request to it.

Fetching robots.txt for a site returns 503. May the crawler fetch the site’s pages?

No. RFC 9309 treats a server error or an unreachable file as a complete disallow, until the file can be read. Only a 4xx response, such as 404, means there are no rules and everything may be crawled.

A calendar page links to the next day, forever. Why does politeness alone not solve this, and what does?

Politeness limits the rate, not the total: one fetch every few seconds is still tens of thousands of pages a day, for as long as the crawl runs, and the frontier and seen filter keep growing. A budget of URLs per host, sized by the site’s importance, caps the total.

Why are near duplicates found with SimHash instead of an ordinary hash of the page?

An ordinary hash changes completely when one character changes, so a page with a new footer or advertisement looks unrelated. SimHash is built so that pages sharing most of their features differ in only a few bits of the fingerprint, and comparing the number of differing bits with a threshold finds them.
