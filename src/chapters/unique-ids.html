What an ID has to do

Identifiers have appeared throughout this book: primary keys in , partition keys, idempotency keys, message IDs, trace IDs. The one firm requirement is uniqueness. Beyond that, schemes differ in properties that pull against one another.

PropertyWhy it matters
Generated without coordinationAny server, or the client, can create one with no network call. Essential for availability and for creating IDs offline.
SmallIDs are stored in every row, every index and every foreign key. Eight bytes against sixteen is a real difference over billions of rows.
Roughly ordered by timeNew rows land together in indexes, and sorting by ID approximates sorting by creation time
UnpredictableAn outsider cannot guess other valid IDs or learn how many exist
Convenient to handleSafe in URLs, in JSON and in every programming language, and short enough to read out when needed

No scheme has all five. Time ordering reveals when something was created. Unpredictability needs randomness, which needs bits. Coordination-free generation rules out a simple counter. The question is which properties each use needs.

Counters in a database

The simplest scheme lets the database assign the next number: 1, 2, 3 and so on. Every relational database offers it, as an auto-incrementing column or a sequence. The IDs are small, perfectly ordered and easy to read.

The limits appear with scale and with exposure.

  • One source. Every ID comes from one database, which every insert must reach. With several databases, as after sharding (), their counters collide.
  • The ID exists only after the insert. A client cannot name an object before the server has stored it, which rules out the client-chosen IDs that make creation idempotent ().
  • They leak information. If your order confirmation shows order 10,482 and next week’s shows 11,907, anyone can work out your sales. If /invoices/1001 is yours, /invoices/1002 is worth a try.

Two old techniques stretch counters across machines. Give each database a different starting point and the same step, so that with two databases one issues odd numbers and the other even. Or have each application server claim a block of a thousand IDs at a time from a central counter and hand them out from memory, so that the central counter is contacted rarely. Both work, and both are awkward to change later. For a single database, a counter remains a good internal key. For anything distributed or exposed, the schemes below are better.

UUIDs

A UUID (universally unique identifier) is a 128-bit value, usually written as 36 characters such as 01929f5e-7b1a-7c3e-9d2f-4a6b8c0d1e2f. The standard, most recently revised as RFC 9562 in 2024, defines several versions that fill those bits differently. Two matter today.

Version 4: random

A version 4 UUID is 122 random bits. Any machine can generate one with no coordination, and the chance of two being equal is so small that it is treated as zero. The arithmetic behind that confidence is the birthday problem: with 122 bits, you would need to generate about 100 trillion UUIDs before the chance of even one collision reached one in a billion. To reach an even chance of a collision, you would have to generate a billion per second for about 86 years.

That assumes a good source of randomness. A broken or poorly seeded random number generator, such as one initialized identically in many copies of a virtual machine, has produced real collisions. Use the platform’s cryptographic generator, which is what crypto.randomUUID() does in JavaScript.

The weakness of random UUIDs is where they land in an index.

explained the cost. An index is sorted, so each new random key belongs on an arbitrary page. Once the index is larger than memory, most inserts need a page read from disk first, pages split throughout the tree, and write throughput falls. Ordered keys keep all the activity on the most recent pages.

Version 7: time-ordered

UUID version 7 fixes this while keeping the format. Its first 48 bits are the current time in milliseconds, and the remaining 74 are random. Two version 7 UUIDs created at different milliseconds sort in order of creation. Within one millisecond, 74 random bits make a collision vanishingly unlikely, and generators may also increment within the millisecond to keep one machine’s IDs strictly increasing.

It is the sensible default for a new system that wants UUIDs. Support is now widespread: PostgreSQL 18 has a built-in uuidv7() function, and libraries exist for every major language. Two cautions apply to all UUIDs.

  • Store them as 16 bytes. Use the database’s UUID or binary type. Stored as text they take 36 bytes, and every index on them more than doubles.
  • A version 7 UUID reveals its creation time to anyone who sees it. If that is sensitive, as it might be for a user ID that reveals when an account was opened, use version 4 for that field.

Snowflake-style IDs

When 16 bytes is too many, or IDs must be numeric, the standard design is the one Twitter published in 2010 under the name Snowflake: a 64-bit integer assembled from three parts.

  • A timestamp, 41 bits of milliseconds since a starting date the system chooses.
  • A node number, 10 bits identifying the machine or process generating the ID.
  • A sequence number, 12 bits that count up within one millisecond on one node.

Uniqueness is guaranteed by construction, with no randomness and no coordination at generation time. Two IDs from different nodes differ in the node bits. Two from the same node differ in the timestamp or the sequence. The IDs fit in a standard 64-bit integer column and sort roughly by time.

Dividing the bits

A signed 64-bit integer has 63 usable bits. How they are split decides how long the scheme lasts, how many generators it supports and how fast each can go.

This layout uses every available bit. Each added timestamp bit doubles the lifetime, each added node bit doubles the number of generators, and each added sequence bit doubles how many IDs one generator can issue in a millisecond.

const EPOCH = 1735689600000n;               // 1 January 2025, UTC: this system's starting point

class SnowflakeGenerator {
  private lastMs = -1n;
  private sequence = 0n;

  constructor(private readonly nodeId: bigint) {
    if (nodeId < 0n || nodeId > 1023n) throw new Error("nodeId must fit in 10 bits");
  }

  next(): bigint {
    let now = BigInt(Date.now());
    if (now < this.lastMs) throw new Error("clock moved backward; refusing to issue IDs");

    if (now === this.lastMs) {
      this.sequence = (this.sequence + 1n) & 4095n;       // 12 bits
      if (this.sequence === 0n) {                         // 4,096 issued this millisecond: wait for the next
        while (now <= this.lastMs) now = BigInt(Date.now());
      }
    } else {
      this.sequence = 0n;
    }

    this.lastMs = now;
    return ((now - EPOCH) << 22n) | (this.nodeId << 12n) | this.sequence;
  }
}

The scheme moves the coordination problem instead of removing it, and three details need care.

  • Node numbers must be unique. Two generators with the same node number will eventually issue the same ID. Something has to assign them: static configuration, or a lease from a coordination service at start-up (). In an environment where instances come and go constantly, this is the hard part.
  • The clock must not go backward. showed that it can. If it does, the generator might reissue IDs it produced earlier. The code above refuses to continue. Waiting until the clock catches up is the other common policy.
  • The starting date is permanent. Forty-one bits of milliseconds last about 69.7 years from whatever date you choose, so choose a recent one.

Variations are common. Instagram described generating IDs inside PostgreSQL with 41 bits of time, 13 bits for a logical shard and 10 bits of sequence, so that an ID also says where its row lives. Discord and many others use layouts close to the original.

Common mistake. Sending 64-bit IDs as JSON numbers. JavaScript represents every number as a 64-bit float, which holds integers exactly only up to 9,007,199,254,740,991, about 9 quadrillion. A Snowflake ID is larger. JSON.parse('{"id": 1867812345678901234}').id returns 1867812345678901200, a different ID, with no error. Send large IDs as strings in every API. This is why Twitter’s API has carried both id and id_str fields.

ULIDs, and short codes

A few other formats are worth recognizing.

A ULID has the same content as a version 7 UUID, 48 bits of time and 80 of randomness, written as 26 characters in an alphabet that avoids easily confused letters. It sorts correctly as plain text and is more compact in a URL. It predates UUID version 7, which now covers the same need within the standard.

Random strings are used where an ID must be short and unguessable, such as a share link. The safe length depends on how many you will issue, by the same birthday arithmetic. With 8 characters from an alphabet of 62 there are about 218 trillion possibilities, which sounds ample. After a million IDs the chance that some two collide is 0.2%, and after ten million it is 20%. Either check for collisions on insert, which a unique constraint does for you, or use more characters: at 12, the chance after a hundred million IDs is about one in a million.

Encoded counters give the shortest codes of all. A URL shortener can take a sequential number and write it in base 62, using digits and both cases of letters, so that seven characters cover 3.5 trillion values. The result is compact and never collides. It is also sequential underneath, so anyone can enumerate the links unless the number is scrambled first. works through that design.

IDs are names, not locks

An unguessable ID is useful, and it is not access control. IDs appear in URLs, logs, browser histories, referrer headers and screenshots. A design in which knowing the ID is sufficient to read the object will leak, sooner or later. Every request must be checked against what the caller is allowed to see (). The failure to do so is common enough to have a name, insecure direct object reference, and it is among the most frequent serious flaws found in web applications.

Where a value really is a secret, such as a password reset link, a session token or an API key, generate it from a cryptographic random source with at least 128 bits, give it an expiry, and store only a hash of it. That is a different job from identifying a row.

How far to trust the order

Time-ordered IDs are sorted by the clocks of the machines that made them, and those clocks disagree (). Two IDs generated a few milliseconds apart on different machines may sort in the wrong order. Within one machine the order is reliable, and across machines it is approximate.

That is enough for the purposes these IDs serve: keeping index inserts together, paginating a feed, giving a rough timeline. It is not enough when exact order affects correctness, such as the sequence of changes to one account. There, use a counter owned by a single authority, such as a per-entity version number or a position in a log ().

Choosing

  • A single database, IDs never shown outside: a 64-bit sequence.
  • A new system with no special constraints: UUID version 7, stored in a native UUID column.
  • IDs created by clients, or offline: a UUID, version 7 or version 4.
  • Billions of rows where every byte counts, or a requirement for numeric IDs: Snowflake-style, with a plan for assigning node numbers.
  • IDs that must reveal nothing, including creation time: UUID version 4, accepting the index cost, or keep an ordered internal key and expose a random one.
  • Short links and codes: a random string with a uniqueness check, or an encoded counter.

The last option in the fifth item deserves a mention. Many systems use two identifiers for one row: a compact, ordered internal key for joins and indexes, and a random public identifier that appears in URLs and APIs. It costs one extra indexed column and separates the concerns cleanly.

In an interview. If you write “id” on a table in a distributed design, be ready to say how it is generated. “Snowflake-style 64-bit IDs: timestamp, node and sequence, so they are unique without coordination and roughly time-ordered, which also lets us paginate by ID” is a complete answer. For a URL shortener or anything with public codes, discuss length against collision probability and whether codes are guessable.

Common mistakes

  • Sequential IDs in public URLs, exposing volume and inviting enumeration.
  • Relying on an ID being hard to guess in place of an authorization check.
  • Random UUIDs as the primary key of a very large, write-heavy table without measuring the index cost.
  • UUIDs stored as text.
  • 64-bit IDs as JSON numbers.
  • Snowflake generators with duplicate node numbers, or no handling for a clock that goes backward.
  • Short random codes with no uniqueness constraint.
  • Using a non-cryptographic random generator for IDs that must be unpredictable.
  • Treating time-ordered IDs as an exact ordering of events across machines.
  • A timestamp alone as an ID. Two events in the same millisecond collide.

Key points

  • IDs trade off size, coordination, ordering and predictability. No scheme wins on all of them.
  • Database sequences are small and ordered, come from one place, and leak counts when exposed.
  • Random UUIDs need no coordination and reveal nothing. They scatter inserts across an index.
  • UUID version 7 puts a millisecond timestamp first, keeping new rows together. It is the general default.
  • Snowflake-style IDs pack a timestamp, node number and sequence into 64 bits. They need unique node numbers and a clock that does not run backward.
  • Send 64-bit IDs as strings in JSON. JavaScript numbers cannot hold them.
  • The length of a random code must be chosen from the number you will issue, and backed by a uniqueness check.
  • An ID identifies. It never authorizes, and its order across machines is approximate.

Check yourself

A table with two billion rows uses random version 4 UUIDs as its primary key, and inserts have become slow. Why, and what would you change for new rows?

Each new key belongs at a random position in the index, so inserts touch pages across the whole tree. The index no longer fits in memory, so most inserts wait for a disk read, and pages split everywhere. Time-ordered keys such as version 7 UUIDs send all new rows to the end of the index, where the pages are already in memory.

In a Snowflake-style ID with 41 timestamp bits, 10 node bits and 12 sequence bits, what happens if one node needs 10,000 IDs in the same millisecond?

The sequence allows 4,096 per millisecond. After issuing those, the generator must wait for the next millisecond before continuing, so the 10,000 take about three milliseconds. If that rate is sustained, give the sequence more bits by taking them from the node number or the timestamp.

An API returns {"id": 9223372036854775807} and a browser client shows a different number. What happened and how should the API change?

JavaScript parses JSON numbers as 64-bit floats, which represent integers exactly only up to about 9 quadrillion. The value was rounded to the nearest representable number. The API should return the ID as a string.

You plan to issue 50 million share links using random 8-character codes from 62 symbols. Is that safe?

Not without a collision check. There are about 218 trillion possible codes, and the chance of at least one collision already reaches 20% at ten million codes, so at 50 million collisions are effectively certain. Add a unique constraint and retry on conflict, or lengthen the code.

Why is “the order IDs are UUIDs, so nobody can view someone else’s order” not a sufficient security argument?

IDs are not secrets. They appear in URLs, logs, emails and referrer headers, and can be shared or leaked. Access must be decided by checking that the authenticated caller owns or may view the order, on every request.

Two events on different servers receive time-ordered IDs, and the one that happened second has the smaller ID. How is that possible?

The IDs take their timestamps from each server’s own clock, and the clocks differ by some milliseconds. If the first server’s clock is ahead, its earlier event gets a later timestamp. Time-ordered IDs give an approximate order across machines, which is not suitable where exact order matters.
