The problem

The problem. Design an in-memory cache with a fixed capacity. It supports get(key) and put(key, value), and both must run in constant time. When the cache is full and a new key arrives, it evicts the least recently used entry. Then: do the same for least frequently used.

described eviction policies from the outside, as a setting to choose. Here the task is to build one. In the terms of , it is a data structure with a contract, and the design is mostly the choice of structures that make the contract cheap to keep.

Step 1: Clarify

QuestionAssumed answer for this design
What is the capacity measured in?Entries. Measuring in bytes is a follow-up
What does get return for a missing key?undefined. A miss is not an error
Does reading count as use?Yes. So does updating an existing key
Does updating an existing key ever evict?No. Only a new key into a full cache does
In LFU, which of two equally used entries goes first?The one used longer ago
What is out of scope at first?Expiry by time, use from several threads, loading missing values. All three are follow-ups

“Constant time” needs one sentence of care. It means that the number of steps does not grow with the number of entries. It is usually written O(1), and a hash map’s operations are counted as constant, as is conventional ().

Steps 2 and 3: The contract and its invariants

// The contract every cache in this chapter keeps: a fixed capacity, and a rule for what leaves when it is full.
export interface Cache {
  get(key: K): V | undefined;
  put(key: K, value: V): void;
  delete(key: K): boolean;
  readonly size: number;
  readonly capacity: number;
}

There are no entities to discover in this problem. The model is the interface, and the invariants are about the structure behind it.

InvariantWhy it matters
The cache never holds more than its capacityThat is the point of having one
The entry evicted is exactly the one the policy namesEvicting a different entry still “works”, and silently lowers the hit ratio
The lookup structure and the ordering structure hold the same keysA key in one and not the other is a leak, or a crash on the next eviction
Every operation is constant timeA cache sits on the hot path of whatever uses it

The second row is why this problem needs more testing than it appears to. A cache with a broken eviction order returns correct values for every key it holds. Nothing fails. It is merely worse, and only a test that knows which entry should have gone can tell.

Least recently used

The cache has to answer two questions quickly. Where is the entry for this key? And which entry was used longest ago? No single common structure answers both.

StructureFind by keyFind the least recently usedMark as used
Hash map aloneConstantMust look at every entryConstant, with a timestamp
List in order of use, aloneMust walk the listConstant: it is at the endConstant once found
Hash map of nodes, and the nodes in a doubly linked listConstantConstantConstant

The list must be doubly linked, meaning each node points to both of its neighbors. Removing a node from the middle requires joining its two neighbors to each other, and with a link in one direction only, a node cannot reach the one before it without a walk from the start.

interface Node {
  key: K;
  value: V;
  newer: Node;
  older: Node;
}

// Least recently used, with a hash map for finding an entry and a doubly linked list for the order of use.
// Every operation touches a fixed number of nodes, whatever the size of the cache.
export class LruCache implements Cache {
  readonly capacity: number;
  private readonly nodes = new Map>();
  // Two sentinels that are never removed, so that every real node always has a neighbor on each side.
  private readonly newest = {} as Node;
  private readonly oldest = {} as Node;

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new Error("capacity must be a whole number of at least 1");
    this.capacity = capacity;
    this.newest.older = this.oldest;
    this.oldest.newer = this.newest;
  }

  get size(): number {
    return this.nodes.size;
  }

  get(key: K): V | undefined {
    const node = this.nodes.get(key);
    if (!node) return undefined;
    this.unlink(node);
    this.linkAsNewest(node); // reading is a use
    return node.value;
  }

  put(key: K, value: V): void {
    const existing = this.nodes.get(key);
    if (existing) {
      existing.value = value;
      this.unlink(existing);
      this.linkAsNewest(existing);
      return;
    }
    if (this.nodes.size === this.capacity) {
      const victim = this.oldest.newer; // the real node next to the old-end sentinel
      this.unlink(victim);
      this.nodes.delete(victim.key);
    }
    const node = { key, value } as Node;
    this.nodes.set(key, node);
    this.linkAsNewest(node);
  }

  delete(key: K): boolean {
    const node = this.nodes.get(key);
    if (!node) return false;
    this.unlink(node);
    return this.nodes.delete(key);
  }

  // Newest first. For tests and for drawing: not part of the contract.
  keys(): K[] {
    const keys: K[] = [];
    for (let node = this.newest.older; node !== this.oldest; node = node.older) keys.push(node.key);
    return keys;
  }

  private unlink(node: Node): void {
    node.newer.older = node.older;
    node.older.newer = node.newer;
  }
  private linkAsNewest(node: Node): void {
    node.older = this.newest.older;
    node.newer = this.newest;
    this.newest.older.newer = node;
    this.newest.older = node;
  }
}

Two details make the code short and hard to get wrong.

  • Sentinels. The list always contains two extra nodes, one at each end, that hold no entry and are never removed. Every real node therefore always has a neighbor on both sides, and unlink and linkAsNewest need no special case for an empty list or for the first or last entry.
  • Two small private operations. Every public method is a combination of unlink and linkAsNewest. Getting four pointers right in two places is manageable. Getting them right inline, in each of four methods, is where interview answers go wrong.

The same policy with a Map

JavaScript’s Map remembers the order in which keys were added. That is enough to express the policy without writing a list: deleting a key and adding it again moves it to the end, so the first key in the map is always the least recently used.

// The same policy in the way most TypeScript code writes it. A Map remembers the order in which keys were added,
// so deleting a key and adding it again moves it to the end, and the first key is always the least recently used.
export class LruMapCache implements Cache {
  readonly capacity: number;
  private readonly entries = new Map();

  constructor(capacity: number) {
    this.capacity = capacity;
  }
  get size(): number {
    return this.entries.size;
  }
  get(key: K): V | undefined {
    if (!this.entries.has(key)) return undefined;
    const value = this.entries.get(key) as V;
    this.entries.delete(key);
    this.entries.set(key, value);
    return value;
  }
  put(key: K, value: V): void {
    if (this.entries.has(key)) this.entries.delete(key);
    else if (this.entries.size === this.capacity) this.entries.delete(this.entries.keys().next().value as K);
    this.entries.set(key, value);
  }
  delete(key: K): boolean {
    return this.entries.delete(key);
  }
  keys(): K[] {
    return [...this.entries.keys()].reverse();
  }
}

This is what most TypeScript code does, and in an interview it is worth showing after the linked list, as evidence that you know both the structure and the language. It has a cost that only measurement reveals, and the section on speed returns to it.

Least frequently used

The second policy evicts the entry that has been used the fewest times. The obvious structure, a counter on each entry and a search for the smallest at eviction time, looks at every entry. A heap ordered by count improves that to a logarithmic number of steps (). Constant time takes one more idea: group the entries by their count.

  • All entries used once are in one group, all entries used twice in another, and so on.
  • Using an entry moves it from its group to the next one up. It can only ever move by one.
  • The cache remembers which group has the fewest uses. The victim is the oldest entry in that group.
// Least frequently used, in constant time. Entries are grouped by how many times they have been used.
// Within a group, a Map keeps them in order of last use, so ties are broken by evicting the least recent.
export class LfuCache implements Cache {
  readonly capacity: number;
  private readonly entries = new Map();
  private readonly groups = new Map>(); // uses -> keys with that many uses, oldest first
  private fewestUses = 0; // the smallest number of uses that any entry has

  constructor(capacity: number) {
    if (!Number.isInteger(capacity) || capacity < 1) throw new Error("capacity must be a whole number of at least 1");
    this.capacity = capacity;
  }
  get size(): number {
    return this.entries.size;
  }

  get(key: K): V | undefined {
    const entry = this.entries.get(key);
    if (!entry) return undefined;
    this.promote(key, entry);
    return entry.value;
  }

  put(key: K, value: V): void {
    const existing = this.entries.get(key);
    if (existing) {
      existing.value = value;
      this.promote(key, existing);
      return;
    }
    if (this.entries.size === this.capacity) {
      const group = this.groups.get(this.fewestUses) as Map;
      const victim = group.keys().next().value as K; // least used, and among those, least recently used
      group.delete(victim);
      this.entries.delete(victim);
    }
    this.entries.set(key, { value, uses: 1 });
    this.groupFor(1).set(key, true);
    this.fewestUses = 1; // a new entry always has the fewest uses
  }

  delete(key: K): boolean {
    const entry = this.entries.get(key);
    if (!entry) return false;
    const group = this.groups.get(entry.uses) as Map;
    group.delete(key);
    if (group.size === 0) this.groups.delete(entry.uses);
    return this.entries.delete(key); // the cache is no longer full, and the next new entry resets fewestUses
  }

  // Moves an entry from its group to the next one up.
  private promote(key: K, entry: { value: V; uses: number }): void {
    const group = this.groups.get(entry.uses) as Map;
    group.delete(key);
    if (group.size === 0) {
      this.groups.delete(entry.uses);
      if (this.fewestUses === entry.uses) this.fewestUses += 1; // the entry itself is about to be in the next group
    }
    entry.uses += 1;
    this.groupFor(entry.uses).set(key, true);
  }
  private groupFor(uses: number): Map {
    let group = this.groups.get(uses);
    if (!group) this.groups.set(uses, (group = new Map()));
    return group;
  }
}

The one subtle line is the upkeep of fewestUses. It can change in only two ways. A new entry always has one use, so after any insertion the answer is one. And when the last entry leaves the lowest group by being used, that entry lands in the next group up, so the answer rises by exactly one. Because counts only ever move by one, the cache never has to search for the lowest group.

Testing against a slow reference

How do you know that the right entry is evicted, a hundred thousand operations in? Hand-written cases cover the first few steps. For the rest, the technique is to write the policy a second time in the most obvious way possible, with no concern for speed, and check that the two never disagree.

The reference versions here keep a plain array of entries with a counter and a time of last use on each, and search the whole array for a victim. They are about thirty lines between them, and it is easy to convince yourself they are right. Each fast cache was then run beside its reference through 200,000 random reads, writes and deletions on a small set of keys, comparing every value returned and the size after every step. The linked-list LRU, the Map LRU and the grouped LFU all matched throughout.

This is the property-testing idea of in its most useful form: a clever implementation checked against a simple one. A small key set is deliberate. With 60 keys and room for 16, evictions and re-insertions of the same keys happen constantly, which is where bugs hide.

Is it constant time?

The claim can be measured. Each implementation was filled to capacity and then given a mix of four reads to one write, on keys spread over twice the capacity.

Nanoseconds for one operation100 entries1,00010,000100,000
Hash map and linked list7788111198
Scan every entry for the victim5109228,341not run
Map insertion order1131003991,518

The first two rows are what theory predicts. The linked list rises gently, from 77 to 198 nanoseconds across a thousandfold growth in size, which is the cost of memory that no longer fits in the processor’s own caches. The scan is ten times slower at ten times the size.

The last two rows are a surprise, and a useful one. Both lean on a Map to find “the first key”, and both slow down sharply at 100,000 entries. A separate measurement isolated the cause: using a Map of 100,000 entries as a queue, removing the first key and adding a new one took about 65,000 nanoseconds when the first key was found with keys().next(), and about 150 when the same keys were deleted without asking for the first. Finding the first key gets slower as deletions accumulate at the front of the map. That is a property of this JavaScript engine, Node.js 22, and not of the language, and it may differ elsewhere.

The practical reading: for a cache of a few thousand entries the Map version is fine and is less code to maintain. For a large one, use the linked list, or an LFU whose groups are linked lists too. And measure, because “it is a hash map, so it is constant time” was true of the algorithm and not of the program.

Which policy

Speed says nothing about which entries are worth keeping. For that, the three policies were given the same 200,000 requests for 10,000 items, with popularity following the uneven pattern typical of real traffic, in which a few items receive most of the requests.

Hit ratio on steady traffic, by cache sizeFIFOLRULFU
1% of the items34%39%50%
2%43%47%57%
5%54%59%66%
10%63%67%73%
20%73%76%80%

Three things stand out.

  • Any policy with a small cache does a great deal. Holding 5% of the items served more than half of the requests even under first in, first out. Popularity is uneven enough that a small cache covers much of the traffic, as said.
  • LFU is the best while popularity holds still, and through scans. A job that read a thousand cold items every two thousand requests cost LRU almost five points on ordinary requests, because each scan pushed the popular entries out. LFU lost a fraction of a point: entries used once cannot displace entries used a hundred times.
  • LFU is the worst when popularity moves. When a new set of items became popular, LFU’s hit ratio fell to 31%, far below even FIFO. Yesterday’s favorites kept their large counts and their places, and new arrivals were evicted before they could build a count.

That last failure is why plain LFU is rarely used as written. Production caches keep the idea of frequency and add forgetting. Redis approximates both LRU and LFU by examining a few randomly chosen keys at each eviction, and its LFU counters decay over time. The Caffeine library for Java admits a new entry to its main space only if a compact frequency estimate says it is likely to be more useful than the entry it would replace, and ages that estimate. For an interview, LRU is the expected default, and being able to say when LFU beats it and when it collapses is the mark of having thought about it.

No eviction policy can do better on this pattern of popularity, and a real one does somewhat worse because it has to discover which items are popular. The gap between 5% of the items and 69.4% of the requests is what makes caching worthwhile.

For the test’s own settings the limit is 69%. LFU reached 66% of requests, LRU 59% and FIFO 54%, so the policies differ in how much of an available 69% they capture.

import type { Cache } from "./cache.ts";

// A cache that fetches what it does not have. It stores the promise of a value, so that many callers
// asking for the same missing key at once share one fetch. A failed fetch is not remembered.
export class LoadingCache {
  private readonly cache: Cache>;
  private readonly load: (key: K) => Promise;

  constructor(cache: Cache>, load: (key: K) => Promise) {
    this.cache = cache;
    this.load = load;
  }

  get(key: K): Promise {
    const cached = this.cache.get(key);
    if (cached) return cached;
    const loading = this.load(key);
    this.cache.put(key, loading); // before any await, so the next caller finds it
    loading.catch(() => {
      if (this.cache.get(key) === loading) this.cache.delete(key); // do not keep an error in the cache
    });
    return loading;
  }
}

Fifty requests for the same missing key, made at the same moment, caused one fetch, and all fifty received its result. A fetch that failed was not kept: the next caller tried again. The reasoning is that of and : store the promise before the first await, so that there is no gap in which a second caller sees nothing.

In an interview. Start by asking the two questions a hash map alone cannot answer together, and draw the map and the list side by side. Write unlink and linkAsNewest first, with sentinels, and build get and put out of them. Then run three or four operations by hand on a cache of capacity two, saying the order aloud after each. If LFU follows, describe groups by count and the rule that the lowest count changes only by going to one on insertion or up by one. Expect “how would you make it thread-safe?” and “what about expiry?” as the closing questions.

Key points

  • A cache must find an entry by key and find its eviction victim, both in constant time. That takes two structures holding the same entries.
  • LRU is a hash map of nodes, with the nodes in a doubly linked list ordered by use. Use moves a node to the front, and eviction takes the node at the back.
  • Sentinel nodes and two small helper operations remove the special cases from the list code.
  • In JavaScript the insertion order of a Map gives LRU in a few lines. It is fine for small caches, and measurably slower for large ones.
  • LFU in constant time groups entries by their number of uses and remembers the lowest group.
  • A wrong eviction order fails silently. Test by asserting which key was evicted and by comparing with a slow, obvious implementation.
  • LFU keeps the most on steady traffic and through scans, and fails when popularity shifts. LRU is the safer default.
  • Reads modify an LRU cache, which is what makes it hard to share between threads.

Check yourself

An LRU cache of capacity 2 receives: put(1, a), put(2, b), get(1), put(3, c), get(2), put(4, d). What does it hold at the end, and what did each get return?

After the two puts it holds 2 and 1, newest first. get(1) returns a and makes 1 the newest. put(3, c) evicts 2, the least recently used, leaving 3 and 1. get(2) returns nothing: a miss. put(4, d) evicts 1, leaving 4 and 3.

Why does the list have to be doubly linked?

To remove a node from the middle in constant time, the cache must join the node before it to the node after it. With links in one direction, a node knows only its successor, so finding its predecessor means walking from the start of the list, which takes time in proportion to its length.

What do the two sentinel nodes buy?

They guarantee that every real node always has a neighbor on each side. Linking and unlinking are then the same four pointer assignments in every situation, with no checks for an empty list, a single entry, or the first or last node. Fewer branches means fewer places for a pointer bug.

In the grouped LFU, why can the cache always know the lowest count without searching?

The lowest count changes in only two ways. Inserting a new entry makes it one, since a new entry has one use. And if the last entry in the lowest group is used, it moves up by exactly one, so the lowest count rises by one with it. Since evictions are always followed by an insertion, which resets the value to one, no other case arises.

A nightly job reads every row of a table through an LRU cache that normally serves a small set of popular rows. What happens to the cache, and which policy would have behaved better?

Each row the job reads is the most recently used, so the scan pushes the popular rows out and fills the cache with rows that will not be asked for again. Ordinary requests then miss until the popular rows are reloaded. A frequency-based policy would have kept the popular rows, because rows read once cannot displace rows read many times. In the chapter’s measurement, frequent scans cost LRU almost five points of hit ratio and LFU less than half a point.

Why is plain LFU a poor choice for a news site’s article cache?

What is popular changes every few hours. Under plain LFU, last week’s most-read article has a count in the millions and is never evicted, while today’s new article enters with a count of one and is the first to go. The cache fills with stale favorites. LRU adapts at once, and practical frequency-based caches age their counts for this reason.

Two versions of a cache return the right value for every key they hold, but one has a bug in its eviction order. How would a test find it?

Not by checking stored values, since both return those correctly. Assert directly which key is missing after an eviction, in small hand-worked cases. Then run the cache beside a slow reference implementation of the same policy through many random operations on a small set of keys, and compare the result of every read. The first time the buggy cache evicts a different key, a later read will hit in one and miss in the other.
