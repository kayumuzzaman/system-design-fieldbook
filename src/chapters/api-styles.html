An API is a contract

An application programming interface (API) is the set of operations one program offers to others, together with the rules for calling them. Internally, your system can be rearranged whenever you like. The API cannot, because other people’s code is written against it: a mobile app released last year, a partner’s integration, another team’s service.

That makes API design unlike most engineering work. A slow query can be fixed next week. A badly named field or an operation that cannot be retried safely stays for years. Three qualities are worth aiming for from the start:

  • Predictable. Someone who has used one part can guess how the rest behaves.
  • Hard to misuse. The obvious way to call it is the correct way, and mistakes produce clear errors.
  • Able to evolve. New capabilities can be added without breaking existing callers.

Three styles dominate today. They differ in what they treat as the basic unit: a resource, a graph of data, or a function call.

REST: resources and representations

REST (representational state transfer) is the style of the web itself, described by Roy Fielding in 2000. Its central idea is that an API exposes resources, each identified by a URL, and that clients act on them using the standard HTTP methods. What travels over the wire is a representation of a resource’s state, usually JSON.

For the photo app, the resources and operations might be:

RequestMeaningSuccess response
GET /photosList photos, a page at a time200 with a page of photos
POST /photosCreate a photo201, with Location: /photos/871
GET /photos/871Read one photo200 with the photo
PATCH /photos/871Change its caption200 with the updated photo
DELETE /photos/871Remove it204
GET /photos/871/commentsList its comments200 with a page of comments
POST /photos/871/likesLike it201 or 204

A few conventions carry most of the weight. URLs name things with plural nouns, and the method supplies the verb. Nesting expresses ownership and stops at one level: /photos/871/comments is clear, and five levels deep is not. Because REST uses HTTP as designed, everything from applies without extra work: reads are cacheable, methods carry their safety and idempotency promises, and status codes mean what intermediaries expect.

How RESTful is “REST”?Fielding’s definition includes a constraint almost nobody implements: responses should contain links that tell the client what it can do next, so that clients discover the API by following them. Most APIs called REST are better described as “JSON over HTTP with resources and proper methods”. That is a perfectly good design, and it is what this chapter means by the term.

Not everything fits the resource mold. Actions such as “cancel this order” or “resend the invoice” are verbs. The usual solutions are to model the action as a resource of its own, POST /orders/55/cancellation, or to accept an action sub-path, POST /orders/55/cancel. Either is fine if applied consistently.

REST’s structure leaves several decisions open. Every API has to make them, and making them once, consistently, matters more than which option you choose.

Pagination

Any endpoint that returns a list must return it in pages, with a maximum page size enforced by the server. An unbounded list works in testing and takes the service down the day a customer has a million rows. There are two ways to ask for “the next page”.

Offset paginationCursor pagination
Request?limit=20&offset=40?limit=20&after=eyJjcmVh…
MeaningSkip 40 rows, return the next 20Return the 20 rows after this position
Jump to page 50YesNo, only forward and sometimes backward
When rows are added or removed while pagingItems repeat or are skippedStable
Cost of a deep pageThe database reads and discards every skipped row, so it grows with the offsetConstant: an index seek to the cursor position
SuitsSmall, slowly changing lists. Admin tables with page numbers.Feeds, timelines, large or fast-changing lists, and any export

A cursor is the sort position of the last item the client received, encoded as an opaque string. The server decodes it and continues from there. The sort order must be unique, so a tie-breaker such as the ID is added to the main sort key.

type Photo = { id: string; createdAt: string; url: string };
type Page = { items: T[]; nextCursor: string | null };
type Position = Pick;
interface Db { query(sql: string, params: unknown[]): Promise }

// Clients must treat the cursor as opaque, so we are free to change what is inside it.
const encode = (p: Position) => Buffer.from(JSON.stringify([p.createdAt, p.id])).toString('base64url');
const decode = (s: string): Position => {
  const [createdAt, id] = JSON.parse(Buffer.from(s, 'base64url').toString());
  return { createdAt, id };
};

export async function listPhotos(db: Db, limit: number, cursor?: string): Promise> {
  const size = Math.min(Math.max(limit, 1), 100);   // the server decides the maximum
  const after = cursor ? decode(cursor) : null;

  // Fetch one extra row to learn whether another page exists.
  const rows = await db.query(
    `SELECT id, created_at AS "createdAt", url
       FROM photos
      WHERE $1::timestamptz IS NULL OR (created_at, id) < ($1, $2)
      ORDER BY created_at DESC, id DESC
      LIMIT $3`,
    [after?.createdAt ?? null, after?.id ?? null, size + 1],
  );

  const items = rows.slice(0, size);
  const last = items.at(-1);
  return { items, nextCursor: rows.length > size && last ? encode(last) : null };
}

Errors

An error response should let a program decide what to do and let a person understand what happened. That takes three things: the right status code, a stable machine-readable error type, and a human-readable explanation. A standard format exists, called problem details, and using it saves inventing your own.

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/caption-too-long",
  "title": "The caption is too long",
  "status": 422,
  "detail": "Captions may have at most 2,200 characters. This one has 2,431.",
  "instance": "/photos/871",
  "maxLength": 2200
}

Clients branch on type, which never changes, and show detail, which may be reworded freely. Do not put stack traces, SQL or internal hostnames in an error. They help an attacker more than a caller.

Safe retries for unsafe operations

Networks fail in the middle of requests. A client that sends POST /payments and gets a timeout cannot know whether the payment happened. If it retries, the customer may be charged twice. If it does not, the payment may never have been made.

The solution is an idempotency key. The client generates a unique value for each operation it intends, and sends the same value on every attempt.

POST /payments HTTP/1.1
Host: api.example.com
Idempotency-Key: 7f1c9e3a-52d4-4b8e-9a6f-0c2d7e41b3aa
Content-Type: application/json

{ "orderId": "55", "amount": 4200, "currency": "BDT" }

The server records each key together with the outcome of the request. When a request arrives with a key it has seen, it returns the recorded outcome and does nothing else. The first attempt and the tenth have the same effect, which is the definition of idempotent. The details that make this correct, such as storing the key in the same transaction as the payment and handling two attempts that arrive at the same moment, are worked through in .

Versioning and change

Sooner or later the API must change. Changes divide into two kinds.

Compatible: existing clients keep workingBreaking: some existing client fails
Adding a new endpointRemoving or renaming an endpoint or field
Adding an optional request fieldMaking an optional field required
Adding a field to a responseChanging a field’s type or meaning
Adding a new value where clients were told to expect new onesAdding a value to a set clients believed was closed
Relaxing a validation ruleTightening a validation rule

The first discipline is to prefer compatible changes and to tell clients, in the documentation from day one, to ignore fields they do not recognize. Most evolution can then happen with no version change at all.

For the breaking changes that remain, there are three common places to put a version:

  • In the path, /v2/photos. Visible, easy to route and easy to explain. The most common choice.
  • In a header, such as Accept: application/vnd.example.v2+json. Keeps URLs stable and is easier to get wrong.
  • By date, where each client is pinned to the API as it was on a given day and the server translates. Fine-grained, and costly to build.

Whichever you choose, the expensive part is the same: running old and new side by side until the last client has moved, announcing a removal date, and measuring who still calls the old version. A version nobody is able to retire is a permanent cost.

Smaller conventions that prevent real bugs

  • IDs are strings. Even if they are numbers today. Large integers lose precision in JavaScript, and you may change the scheme.
  • Times are UTC in a standard format, such as 2026-10-10T08:30:00Z. Never local time without an offset.
  • Money is an integer count of the smallest unit, plus a currency code. Floating-point numbers cannot represent most decimal amounts exactly.
  • Enumerations may grow. Say so, and have clients handle an unknown value gracefully.
  • Lists are wrapped in an object, { "items": [...], "nextCursor": ... }, so that fields can be added later.
  • Limits are stated and enforced: page sizes, request body size, rate limits. A request over the rate limit gets 429 with a Retry-After header.
  • Slow operations answer 202 at once and return a URL where the client can check on the job. A request that holds a connection for a minute fails in ways that are hard to retry.

A REST API is normally described in an OpenAPI document, a machine-readable file listing every endpoint, parameter and response. From it you can generate documentation, client libraries and request validators, and you can check automatically that a change is not a breaking one.

GraphQL: ask for exactly what you need

REST gives each resource its own endpoint with a fixed shape. That causes two inefficiencies for rich clients. A screen that needs a user, their latest photos and the comment count on each must make several requests, some of which can only be made after earlier ones return. And each response includes every field of the resource, although the screen uses three of them. These are called under-fetching and over-fetching.

GraphQL, developed at Facebook and released publicly in 2015, turns the arrangement around. The server publishes a schema: a typed description of all the data available and how it is connected. The client sends a query that states exactly which fields it wants, following connections as deep as it needs. One request, one response shaped like the query.

type User  { id: ID!  name: String!  photos(first: Int = 10, after: String): PhotoPage! }
type Photo { id: ID!  url: String!  caption: String  commentCount: Int! }
type PhotoPage { items: [Photo!]!  nextCursor: String }
type Query { user(id: ID!): User }

# The client asks for exactly these fields and receives exactly this shape.
query ProfileScreen {
  user(id: "42") {
    name
    photos(first: 3) {
      items { url commentCount }
      nextCursor
    }
  }
}

The benefits are real, especially where many different clients share one back end. Mobile apps make fewer round trips on slow networks. Front-end teams add a field to a query without waiting for a new endpoint. The schema is a typed contract that tools can check queries against at build time.

The flexibility is paid for on the server, and each cost needs a deliberate answer.

CostWhy it arisesThe usual answer
The N+1 problemEach field is resolved by its own function. A query for 50 photos and the author of each naively runs 1 query for the photos and 50 for the authors.Batching: collect the keys requested during one step and fetch them in a single query. The DataLoader library made this pattern standard.
Caching is harderQueries are usually sent as POST to one URL, so HTTP caches and CDNs cannot tell them apart.Persisted queries: the client sends an ID for a query registered in advance, using GET. Caching inside the client library.
Unbounded costA client can write a query that is cheap to send and enormously expensive to answer, by nesting deeply.Limits on depth and on a computed cost per query. Allowing only registered queries in production.
Authorization everywhereAny field can be reached by many paths through the graph.Enforce permissions in the data layer under the resolvers, not in each resolver.
Errors look like successesA response can contain partial data and a list of errors, usually with status 200.Monitoring that reads the response body. Clients that handle partial results.

GraphQL is a strong choice for a product API consumed by your own web and mobile clients, particularly when several teams build screens against shared data. It is a weaker choice for a simple public API, where REST’s cacheability and familiarity count for more, and for service-to-service calls, where nobody needs flexible queries.

gRPC: calling a function on another machine

The third style does not model resources or graphs. It models remote procedure calls (RPC): a service exposes functions, and calling one from another machine looks like calling a local function. gRPC, released by Google in 2015, is the most widely used modern form.

You start by writing the contract in a Protocol Buffers file, which defines the messages and the functions.

syntax = "proto3";
package photos.v1;

service PhotoService {
  rpc GetPhoto (GetPhotoRequest) returns (Photo);
  rpc ListPhotos (ListPhotosRequest) returns (ListPhotosResponse);
  rpc WatchLikes (WatchLikesRequest) returns (stream LikeEvent);   // server streaming
}

message GetPhotoRequest { string id = 1; }

message Photo {
  string id = 1;
  string url = 2;
  string caption = 3;
  int64 created_at_ms = 4;
}

From this file a compiler generates client and server code in each language you use. Calling the service is then an ordinary typed function call, and a caller that passes the wrong type fails at compile time.

Three properties make gRPC the common choice between services inside a system.

  • Compact and fast. Messages are binary. Field names are not sent, only the small numbers assigned in the file, so payloads are a fraction of the size of the equivalent JSON and cheaper to parse.
  • Streaming is built in. Running over HTTP/2, a call can be a single request and response, a stream from the server, a stream from the client, or both at once.
  • Deadlines travel with the call. A caller states how long it will wait, and that deadline is passed down through every service the request touches. When time runs out, everyone stops working on a request nobody is waiting for.

The field numbers also define how the contract may evolve. Adding a field with a new number is compatible: old code ignores it. A number must never be reused for a different meaning, and a field’s type must not change, because old and new code would then read the same bytes differently.

The costs are mostly at the edges of the system. Browsers cannot speak native gRPC, so a web client needs a translating proxy or a variant protocol. Binary messages cannot be read or sent with curl and a text editor. And because the contract is code, every consumer must regenerate its client when the contract changes.

In production. gRPC keeps one long-lived HTTP/2 connection per destination and sends every call down it. A load balancer that works at the connection level therefore sends all of a client’s calls to whichever server that one connection landed on, and newly added servers receive nothing. gRPC traffic needs a balancer that understands HTTP/2 and distributes individual requests, or client-side balancing across several connections. explains the difference.

Other styles you will meet

  • tRPC and similar tools are RPC for teams whose client and server are both TypeScript. The server’s function types are shared with the client directly, with no schema file and no code generation. Convenient inside one codebase, and not meant for outside consumers.
  • JSON-RPC is a minimal convention for RPC with JSON messages: a method name, parameters and an ID. It is the basis of the Model Context Protocol that connects AI models to tools, among other things.
  • SOAP is the XML-based RPC of the early 2000s, still running in banking, government and enterprise integration. You are more likely to call one than to build one.
  • Webhooks reverse the direction: the server calls the client when something happens. They complement all of the above and are covered in .

Real systems seldom pick one. A common arrangement uses each where it is strongest.

Some rules of thumb for the choice:

  • Outsiders will call it: REST. They can use it from any language with no special tooling, and it caches.
  • Your own apps with many screens and several client teams: GraphQL is worth its cost. With one client and a few screens, REST endpoints designed for that client are simpler.
  • Services calling services: gRPC, for the typed contract, speed, streaming and deadlines.
  • Something must be pushed from server to client: none of these alone. See the next chapter.

In an interview. When asked to “design the API”, write four or five concrete endpoints with method, path, the key request fields and the response, and say how lists are paginated and how a failed write is retried safely. That is worth more than a discussion of styles. If you choose GraphQL or gRPC, give the reason in one sentence tied to the problem: “the feed screen needs data from four services and I don’t want four round trips from a phone.”

Mistakes that are expensive later

  • Exposing your database tables as your API. The API then changes whenever the schema does, and internal details become promises. Design the API for its callers and map it to storage behind the scenes.
  • Returning unbounded lists. Add pagination and a maximum page size before the first client ships.
  • Leaving retries undefined. For every operation that changes something, decide what happens when it is sent twice.
  • Inconsistent naming. createdAt in one place, creation_date in another, created in a third. Pick conventions once and enforce them with a linter.
  • No plan for removal. If you cannot see who calls an old endpoint, you cannot retire it. Log callers by version from the first day.
  • Chatty designs. An API that needs twenty calls to draw one screen multiplies latency and failure. Look at the client’s actual use and offer what it needs in one or two calls.

Key points

  • An API is a long-lived contract. Aim for predictable, hard to misuse, and able to evolve.
  • REST exposes resources at URLs and uses HTTP methods, status codes and caching as designed. It is the default for public APIs.
  • Paginate every list. Cursors stay correct and fast on large, changing data, and offsets do not.
  • Give errors a stable machine-readable type. Make unsafe operations retryable with idempotency keys.
  • Prefer compatible changes, and have clients ignore unknown fields. Version only for breaking changes, and plan how old versions are retired.
  • GraphQL lets clients choose the shape of the response in one round trip. The server must handle batching, cost limits, caching and authorization.
  • gRPC offers typed, compact, streaming calls with deadlines, best between internal services, and needs request-level load balancing.
  • Most systems combine styles: REST or GraphQL at the edge, gRPC inside.

Check yourself

An endpoint returns comments with ?offset=100000&limit=20 and has become slow. Why, and what would you change?

The database must find and discard the first 100,000 rows before returning 20, so the cost grows with the offset. Switch to a cursor on a unique, indexed sort key such as (created_at, id), so that each page is an index seek to a known position.

A mobile app sends POST /orders, loses signal and retries when it returns. How does the server avoid creating two orders?

The app generates an idempotency key when the user confirms the order and sends it with every attempt. The server stores the key with the result, and on a repeat returns the stored result without creating anything.

You want to rename the response field userName to displayName. How can you do it without breaking clients?

Add displayName alongside userName, which is a compatible change, and return both. Move clients over, watch usage of the old field, announce a removal date, and remove it only when nothing reads it, or in the next major version.

A GraphQL query for 100 photos with each photo’s author takes two seconds, and the database log shows 101 queries. What is happening and what fixes it?

The N+1 problem: one query for the photos and one per photo for its author. Batch the author lookups, so that all the author IDs needed in that step are fetched with a single query.

After adding five servers to a gRPC service, the original servers are still overloaded and the new ones are idle. Why?

gRPC clients hold long-lived HTTP/2 connections, and the load balancer is distributing connections, not requests. Existing connections stay where they are. Use a balancer that distributes individual HTTP/2 requests, or client-side load balancing, and have connections recycled periodically.
