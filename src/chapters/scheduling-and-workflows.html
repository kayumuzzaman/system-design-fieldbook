Work that nobody is waiting for

The systems so far have reacted to requests and to messages. Three further kinds of work have no such trigger.

KindExamples in the photo appWhat it needs
RecurringNightly usage report. Hourly cleanup of abandoned uploads. Monthly invoices.A schedule, and exactly one run for each scheduled time
Delayed“Your trial ends in three days.” Delete an account 30 days after the request.A durable timer for each item, possibly millions of them
Multi-stepPrinting a photo book: render, charge, send to the printer, wait for shipping, email the customer.Memory of how far the process has got, across failures and long waits

All three share a requirement that request handling does not have. The work is promised for the future, so the promise has to survive restarts, deployments and machine failures between now and then.

Cron

The oldest scheduler is cron, a Unix program from the 1970s that runs commands at times described by five fields: minute, hour, day of month, month and day of week.

┌───────── minute (0–59)
│ ┌─────── hour (0–23)
│ │ ┌───── day of month (1–31)
│ │ │ ┌─── month (1–12)
│ │ │ │ ┌─ day of week (0–6, Sunday is 0)
│ │ │ │ │
0 2 * * *        every day at 02:00
*/15 * * * *     every 15 minutes
0 9 * * 1-5      at 09:00, Monday to Friday
0 0 1 * *        at midnight on the first of each month
30 3 * * 0       at 03:30 every Sunday

The syntax has outlived the program. Kubernetes CronJobs, cloud schedulers and most job libraries accept it, so it is worth being able to read.

What goes wrong on one machine

Cron on a single server works until something happens that it has no answer for.

  • The machine is down at the scheduled time. The run is skipped and nothing records that it was.
  • The job fails. Cron does not retry and, by default, tells nobody.
  • The job overruns. A job scheduled every five minutes that takes seven starts a second copy on top of the first, and then a third.
  • There is no history. Did last Tuesday’s run happen? How long did it take? Cron cannot say.
  • Everyone picks the top of the hour. If a thousand jobs across a company run at 0 * * * *, shared databases see a spike at minute zero of every hour. Spread schedules out, and add a random delay of a few seconds or minutes to anything that does not need precision.

Time zones and daylight saving

A schedule is a statement about clock time, and local clock time is not continuous.

Schedule in UTC by default. Where a job is tied to local time, such as “send the daily summary at 8 in the morning in each user’s own time zone”, store the time zone’s name, compute the next run with a proper time zone library, and decide deliberately what should happen on the two unusual days.

Cron across many machines

The fix for “the machine was down” is to stop depending on one machine. That immediately creates the opposite problem. If three servers each run the scheduler, the nightly invoice job runs three times. The requirement is now precise: for each scheduled time, the job should run exactly once, on some machine.

Exactly once is not available, as established. What can be built is at-least-once triggering with duplicates made harmless. The design has three parts.

  1. One scheduler decides. Several instances run, and one holds a lease as leader (). Only the leader turns schedules into runs.
  2. Each run has an identity. When 02:00 arrives, the leader records a run whose key is the job’s name plus the scheduled time, such as daily-report/2026-10-10T02:00Z, under a unique constraint. If an old leader and a new one both try, the second insert is rejected. The key identifies the intended run, whatever time it really starts.
  3. Workers execute, idempotently. The run is placed on a queue and a worker picks it up. A worker can crash halfway, in which case the run is retried, so the job itself must be safe to repeat. The scheduled time is passed to the job, so that a report for 10 October computes the same thing whether it starts at 02:00 or, after a retry, at 02:40.

Passing the scheduled time in, instead of letting the job read the clock, is the single most useful habit in scheduled work. It makes runs repeatable, makes late runs correct, and makes it possible to run a job for a date in the past.

Two policies to choose

Missed runs. If the scheduler was down from 01:00 to 05:00, should the 02:00 job run when it comes back? For a daily report, yes: run it late. For “send a reminder five minutes before the meeting”, a run four hours late is worse than none. And if an hourly job missed four runs, should it run four times or once? Each job needs a declared answer: catch up, run once, or skip.

Overlap. If the previous run is still going when the next is due, the choices are to allow both, to skip the new one, or to cancel the old one. Skipping is the safe default for most jobs.

Kubernetes CronJobs expose both as settings, startingDeadlineSeconds and concurrencyPolicy. Its documentation is also candid about the limits of the guarantee: under some conditions a CronJob may create two jobs for one scheduled time, or none, so the jobs should be idempotent. That is true of every scheduler, and few say so as plainly.

In production. The failure that hurts most is the job that silently stops running. Nothing errors, because nothing runs. Alert on absence: for each important job, record the time of its last successful completion and raise an alarm when that is older than it should be. This is sometimes called a dead man’s switch. An alert on failures alone will never fire for a job that never starts.

Background jobs

Scheduled runs are one source of background work. The other is the application itself: “send this email”, “resize this photo”, “export this user’s data”. These are jobs placed on a queue by request handlers and executed by workers, which is the queue pattern of with more bookkeeping around each item.

A job system adds what a bare queue lacks.

  • State for each job that can be inspected: pending, running, done, failed, and how many attempts so far.
  • Retries with backoff, a limit on attempts, and a place for jobs that exhaust it.
  • Timeouts and heartbeats, so that a job whose worker died is noticed and given to another.
  • Scheduling: run this at a given time, or after a delay.
  • Uniqueness: do not enqueue a second “rebuild index for user 42” while one is waiting.
  • Limits: at most 50 jobs at once against the payment provider, at most 5 for any one customer.

A relational database makes a sound job queue for a great many systems, as argued. The decisive advantage is that a job can be enqueued in the same transaction as the data change that calls for it, so the two cannot disagree.

CREATE TABLE jobs (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  kind         text        NOT NULL,
  payload      jsonb       NOT NULL DEFAULT '{}',
  run_at       timestamptz NOT NULL,
  status       text        NOT NULL DEFAULT 'pending',   -- pending, running, done, dead
  attempts     int         NOT NULL DEFAULT 0,
  locked_until timestamptz,
  dedupe_key   text UNIQUE                               -- for example 'daily-report/2026-10-10'
);
CREATE INDEX jobs_due ON jobs (run_at) WHERE status = 'pending';

-- The scheduler records a run. A second scheduler doing the same changes nothing.
INSERT INTO jobs (kind, run_at, dedupe_key)
VALUES ('daily-report', '2026-10-10 02:00+00', 'daily-report/2026-10-10')
ON CONFLICT (dedupe_key) DO NOTHING;

-- A worker claims up to ten due jobs. Rows locked by another worker are skipped, not waited for.
UPDATE jobs
   SET status = 'running', attempts = attempts + 1, locked_until = now() + interval '5 minutes'
 WHERE id IN (
   SELECT id FROM jobs
    WHERE status = 'pending' AND run_at <= now()
    ORDER BY run_at
    LIMIT 10
    FOR UPDATE SKIP LOCKED)
RETURNING id, kind, payload, attempts;

-- A sweeper returns jobs whose worker went silent.
UPDATE jobs SET status = 'pending'
 WHERE status = 'running' AND locked_until < now();

The locked_until column is a lease, with the property leases always have (): a slow worker can still be running when its lease expires and another worker takes the job. The job runs twice. Long jobs should extend their lease as they go, and every job should be idempotent regardless.

Millions of timers

“Remind me in three days” is easy to state and surprisingly easy to get wrong. An in-memory timer, such as setTimeout, is lost when the process restarts, which in a system deployed daily means nearly every three-day timer is lost.

The durable form is the table above. A timer is a row with a run_at in the future. The partial index on run_at keeps finding due rows cheap however many rows are waiting, because the index is ordered by time and the poller only reads its front. Ten million pending reminders cost storage and nothing else until they fall due.

Polling introduces a small delay, at most one polling interval. For most uses a second or two is immaterial. Where it is not, the two approaches are combined: the database holds everything, and each scheduler loads the timers due in the next minute into memory and fires them precisely.

Timing wheels

Inside one process, the efficient structure for a large number of timers is the timing wheel. Keeping timers in sorted order makes each insertion cost more as the number grows. A wheel avoids sorting altogether.

For long delays, wheels are stacked like the hands of a clock: one for seconds, one for minutes, one for hours. A timer due in two hours waits in the hours wheel and moves down as its time approaches. Network stacks, the Linux kernel and message brokers use this structure for connection timeouts and delayed messages.

Processes with many steps

Ana orders a printed book of her album. Fulfilling the order takes several steps across several systems.

  1. Collect the album’s photos.
  2. Render a print-ready file, which takes a few minutes.
  3. Charge her card.
  4. Send the file to the printing company.
  5. Wait, up to ten days, for the printer to report that it has shipped.
  6. Email her the tracking number. If the printer never confirms, refund her and apologize.

Any step can fail. The process outlives any single server and any deployment. The ten-day wait must not hold a thread or a connection. And if step 4 fails after step 3 succeeded, a card has been charged for nothing unless something knows to try again or to refund.

The usual first implementation is a status column on the order, a queue message for each step, and a scheduled job that sweeps for orders stuck in one status too long. This works, and what has been built is a workflow engine, spread across a table, several queue consumers and a cron job, with its logic visible in no one place. As steps and exceptions accumulate, nobody can say with confidence what happens to an order that fails at step 4 on its third retry during a deployment.

Two kinds of tool exist to make such processes explicit.

DAG orchestrators for data pipelines

In data engineering the steps are batch jobs with dependencies: load two tables, then join them, then build three reports from the result. The structure is a directed acyclic graph, or DAG: tasks as nodes, and “must finish before” as arrows, with no cycles.

An orchestrator such as Apache Airflow, Dagster or Prefect takes the graph and a schedule, and provides the rest: starting each task when its dependencies have succeeded, running independent tasks in parallel, retrying failures, alerting, and a record of every run. Airflow, the most widely used, is at version 3 as of October 2026.

The idea to carry away is the data interval. Each run is for a specific period of data, such as 9 October, and every task receives that period as a parameter. A task written this way can be rerun for any date and produce the same output, which makes two operations routine: retrying last night’s failed task this morning, and backfilling, which is running the pipeline for the past 90 days after its logic has changed. It is the scheduled-time principle from earlier in the chapter, applied to data.

Durable execution

For business processes like the photo book, with waits, branches and compensation, a second kind of engine has become standard: durable execution. Temporal, AWS Step Functions and Azure Durable Functions are examples. introduced them as the practical way to run a saga.

The promise sounds impossible: write the process as an ordinary function, with ordinary variables, loops and await, and the engine will keep it running across crashes and restarts, for days or months, as if the machine never failed. The mechanism behind it is simple once seen.

Every interaction with the outside world, called a step or activity, goes through the engine. When a step finishes, the engine saves its result to a durable history before the function continues. If the worker crashes, another worker starts the function again from the first line, with the history in hand. Each step that already has a recorded result returns it immediately without doing anything. The function races through everything it did before, arriving at the same point with the same variables, and continues for real from there. This is replay.

A working miniature is short.

type History = { step: string; result: unknown }[];

class Workflow {
  private cursor = 0;

  constructor(private history: History, private save: (history: History) => void) {}

  // Run a step once. On a replay, return its recorded result instead of running it again.
  async step(name: string, run: () => Promise): Promise {
    const recorded = this.history[this.cursor];
    if (recorded) {
      if (recorded.step !== name) {
        throw new Error(`history has "${recorded.step}" here, but the code ran "${name}"`);
      }
      this.cursor += 1;
      return recorded.result as T;
    }
    const result = await run();
    this.history.push({ step: name, result });
    this.save(this.history);                       // made durable before the workflow moves on
    this.cursor += 1;
    return result;
  }
}

// The workflow is ordinary code. It may be run from the top any number of times.
async function printPhotoBook(wf: Workflow, albumId: number): Promise {
  const photos  = await wf.step("list photos", () => listPhotos(albumId));
  const pdfKey  = await wf.step("render book", () => renderBook(photos));
  const receipt = await wf.step("charge card", () => chargeCard(albumId, 2500));
  return wf.step("send to printer", () => sendToPrinter(pdfKey, receipt));
}

In a test of this code, the first run failed at the printer after charging the card. The second run, started with the saved history, completed. The charge function had been called once in total, and the printer function twice. A third run with the full history called nothing at all.

Real engines add what makes this production-grade: timers that last for months without holding any resource, signals so that the outside world can wake a waiting workflow, such as the printer’s shipping confirmation, retries with backoff for each step, timeouts, and a console showing every running workflow and exactly where it is.

The rules that replay imposes

Replay works only if the function takes the same path every time it is run with the same history. That places requirements on the code which are easy to state and easy to break.

  • Workflow code must be deterministic. It must not read the clock, generate random numbers, or call a database or API directly. All of those go through a step, so that their results are recorded. Reading the time directly would give one answer on the first run and another on replay, and the function could take a different branch.
  • Steps run at least once. If a worker crashes after a step’s effect and before its result is saved, the step runs again on replay. In the miniature above, that is the gap between run() returning and save completing. Every step that has an outside effect needs an idempotency key ().
  • Changing code under running workflows needs care. A workflow started last week has a history recorded by last week’s code. If today’s code performs steps in a different order, replay fails, as the check in step shows. Engines provide versioning mechanisms, and ignoring them is the most common way teams are hurt.
  • Histories are finite. Each step adds to the history, and replay reads all of it. Engines cap the size. AWS Step Functions, for example, limits a standard workflow to one year and 25,000 history events. A process that loops indefinitely must periodically restart itself with a fresh history.

When a state machine is enough

A workflow engine is one more critical system to run or pay for, with its own model to learn. For a process with a handful of states and no long waits, an explicit state machine in your own database is often the better choice.

  • A status column with a fixed set of values.
  • A table, in code, of the allowed transitions between them.
  • Each transition as one guarded update, UPDATE … SET status = 'paid' WHERE id = … AND status = 'pending', so that two concurrent attempts cannot both succeed ().
  • A job enqueued in the same transaction for whatever the new state requires.
  • A scheduled sweep for anything that has been in a non-final state too long.

The difference from the accidental workflow engine described earlier is that it is deliberate: the states and transitions are written down in one place and enforced. Move to an engine when the process gains long waits, many branches, compensation logic, or when people regularly ask “where is this order stuck, and why?” and the answer takes an engineer an hour.

Operating scheduled work

  • Recovery creates a surge. After an outage, every missed job and every expired timer becomes due at once. Limit how fast the backlog is released, or the recovery will cause the next outage ().
  • One tenant can starve the rest. A customer who enqueues a million export jobs will occupy every worker if jobs are taken strictly in order. Limit concurrency for each tenant, or take jobs from tenants in rotation ().
  • Deployments interrupt running jobs. Workers should stop taking new jobs when asked to shut down, and finish or cleanly release the ones in hand. Jobs longer than the shutdown grace period should save progress and resume.
  • Poison jobs exist here too. Cap attempts, park failures where they can be inspected, and alert on them.
  • Keep jobs small. A job that processes a million rows in one go loses everything on a failure at row 900,000. Break it into batches that each commit and record progress.

Reminders and delayed actions, at any volumeRows with a due time, polled through an index
Batch data pipelines with dependenciesA DAG orchestrator
A short business process with a few statesAn explicit state machine in the database
A long-running process with waits, branches and compensationA durable execution engine

In an interview. When a design includes “a cron job that…”, expect to be asked what happens if it runs twice, or not at all. Have the answer built in: “the scheduler runs with leader election, each run is keyed by job and scheduled time so that a duplicate trigger is rejected, the job takes the scheduled time as input and is idempotent, and we alert if the last success is older than expected”. For multi-step flows, say where the state lives and who notices a stuck one.

Key points

  • Scheduled, delayed and multi-step work is a promise about the future, so it has to be stored durably and survive restarts.
  • Cron’s syntax is everywhere. Cron on one machine skips runs, does not retry, allows overlaps and keeps no history.
  • Across machines, one leader decides that a run is due, each run is keyed by job and scheduled time, and workers execute idempotently.
  • Pass the scheduled time into the job. Never have the job read the clock to decide what to do.
  • Schedule in UTC, and alert on the absence of success as well as on failure.
  • A timer is a row with a due time behind an index. Timing wheels handle large numbers of timers in memory.
  • DAG orchestrators run dependent batch tasks for a given data interval, which makes retries and backfills routine.
  • Durable execution records each step’s result and replays the function after a crash. Workflow code must be deterministic, and steps must be idempotent.
  • For a small process, an explicit state machine in the database is enough.

Check yourself

A service runs on six instances, and each has the same nightly cron entry. What happens, and what are the two parts of the fix?

The job runs six times each night. First, only one instance should trigger it, through leader election or a single external scheduler. Second, because leadership can change at the wrong moment, each run is recorded under a unique key of job name and scheduled time, so that a second trigger for the same time is rejected, and the job itself is idempotent.

A daily report job computes “yesterday” from the current time. It fails at 23:50 and is retried at 00:10. What goes wrong, and how should the job be written?

The retry runs after midnight, so “yesterday” is now a different day. One day’s report is produced twice and another is never produced. The job should receive its scheduled time or data date as a parameter and compute from that, so that a late or repeated run does the same work as the original would have.

Why is a job scheduled for 02:30 local time a poor idea in a region that observes daylight saving?

On the day clocks move forward, the hour from 02:00 to 03:00 does not exist, so the job is skipped. On the day they move back, that hour occurs twice, so the job runs twice. Scheduling in UTC avoids both.

Ten workers poll the same jobs table. How does FOR UPDATE SKIP LOCKED prevent two of them from taking the same job without making them wait for each other?

The claiming query locks the rows it selects. Another worker running the same query at the same moment does not block on those locked rows. It skips them and takes the next available ones. Each worker therefore gets a different set, immediately.

A worker claims a job with a five-minute lock and then takes eight minutes. What happens, and what two measures limit the damage?

After five minutes the sweeper returns the job to pending and a second worker starts it while the first is still running. The job runs twice, concurrently. Long jobs should extend their lock periodically while they make progress, and the job must be idempotent so that a duplicate run does no harm.

In a durable execution engine, a workflow has completed three steps when its worker crashes. Describe what happens when another worker picks it up.

The new worker runs the workflow function from the beginning, supplied with the saved history. For each of the first three steps the engine returns the recorded result without executing the step. The function reaches the fourth step with the same variable values as before, and executes from there normally.

Why must workflow code not call Date.now() or Math.random() directly?

On replay the function must take exactly the path it took originally. A direct call returns a different value each time, so a condition could go the other way and the code would attempt steps that do not match the recorded history. The time and random values must be obtained through the engine, which records them the first time and returns the same values on replay.
