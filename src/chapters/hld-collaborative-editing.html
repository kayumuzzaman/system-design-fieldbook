The problem

The problem. Design a collaborative document editor. Several people open the same document and type at the same time; each sees their own typing immediately and everyone else’s within a fraction of a second, along with their cursors. People can keep editing offline and have their changes merged when they reconnect. Every copy must end up identical, and no acknowledged edit may be lost.

The obvious designs fail. Locking the document, or a paragraph, makes people wait for each other. Sending whole versions and keeping the newest, as file sync does with its conflict copies (), throws away someone’s typing every second. And sending each keystroke as “insert x at position 8” breaks the moment two people type at once, because position 8 on one screen is not position 8 on the other. What is needed is a way to apply edits made concurrently, in any order, so that every copy ends the same and each edit still does what its author meant. This is the replication of with every keyboard a leader. In the terms of , this is concurrent edits converging to one document.

Each document is small and busy, so it lives in the memory of one server, and the whole system is many such servers. The log grows by terabytes a day and must be compacted. An operation names the revision it was made on, its base, which is how the server knows what its author had not yet seen. The client_seq numbers each client’s operations, so an operation sent again after a reconnect is recognized and acknowledged instead of applied twice (). Restoring a version does not rewrite history: it appends an operation, so people editing at that moment are transformed past it like any other edit.

Step 5: The design

Everyone in a document connects, through any gateway (), to the one document server that holds it. A directory, kept by a coordination service with leases, says which server that is; the first person to open a document makes a server load it from the latest snapshot and the log after it. The document server does what the sequencer does in : it puts every operation in one order and gives it a revision number. Then it makes each operation fit that order, which is the subject of the first deep dive, appends it to the log and broadcasts it.

Step 6a: Operational transformation

Operational transformation (OT) is a technique for concurrent editing in which an operation made on an older version of a document is rewritten, before it is applied, to account for the operations it did not see, so that it has the effect its author intended. In the figure above, Bob’s delete removed three characters before position 8, so Alice’s insert at 8 is transformed into an insert at 5.

The chapter’s code represents an operation as a walk over the whole text: a positive number keeps that many characters, a string inserts it, and a negative number deletes that many. Alice’s insert on the 14-character text is [8, "on ", 6]; Bob’s delete is [5, -3, 6]. Transforming two such operations walks both at once.

// Given a and b made on the same document, returns [a', b'] such that
// apply(apply(doc, a), b') === apply(apply(doc, b), a'). When both insert at the same place, a's text goes first.
export function transform(a: Op, b: Op): [Op, Op] {
  const a2: Op = [], b2: Op = [];
  let i = 0, j = 0;
  let x: Part | undefined = a[0], y: Part | undefined = b[0];
  const nextA = () => { i += 1; x = a[i]; }, nextB = () => { j += 1; y = b[j]; };
  while (x !== undefined || y !== undefined) {
    if (typeof x === "string") { push(a2, x); push(b2, x.length); nextA(); continue; }   // a inserts: b keeps it
    if (typeof y === "string") { push(a2, y.length); push(b2, y); nextB(); continue; }   // b inserts: a keeps it
    if (x === undefined || y === undefined) throw new Error("operations of different lengths");
    if (x > 0 && y > 0) {                       // both keep
      const n = Math.min(x, y); push(a2, n); push(b2, n);
      x -= n; y -= n; if (x === 0) nextA(); if (y === 0) nextB();
    } else if (x < 0 && y < 0) {                // both delete the same characters: nothing left to do
      const n = Math.min(-x, -y);
      x += n; y += n; if (x === 0) nextA(); if (y === 0) nextB();
    } else if (x < 0) {                         // a deletes what b keeps
      const n = Math.min(-x, y as number); push(a2, -n);
      x += n; y = (y as number) - n; if (x === 0) nextA(); if (y === 0) nextB();
    } else {                                    // b deletes what a keeps
      const n = Math.min(x, -(y as number)); push(b2, -n);
      x -= n; y = (y as number) + n; if (x === 0) nextA(); if (y === 0) nextB();
    }
  }
  return [a2, b2];
}

The function must satisfy one property: applying a and then the transformed b gives the same text as applying b and then the transformed a. The test checked it on 20,000 random pairs of inserts and deletes, and it held for every one. When both insert at the same place, one of them must go first in both orders; here it is the first argument, which the server always gives to the operation arriving later, so every copy breaks ties the same way.

The client is simple because of the server. A client keeps at most one operation in flight; edits made while waiting for its acknowledgment are combined into one operation that waits its turn. Each operation arriving from the server is transformed past the client’s own unacknowledged ones and applied. This arrangement goes back to the Jupiter system of 1995, whose authors adapted an earlier, fully distributed algorithm and observed that the central server made it much simpler: with one order decided in one place, only the property above is needed. Without a server, operations can meet in many orders, and OT needs a second, much harder property as well.

The test simulated 200 runs of four people each making 30 edits, an edit every 300 ms on average, over connections with 100 ms of delay each way and messages in order on each connection. With transformation, every copy matched the server in all 200 runs. Applying each edit at the position where it was typed, the obvious approach, left the copies different in all 200.

The server’s work grows with delay. With ten people each making two edits a second, each operation was transformed past 0.35 others at 10 ms of delay, 3.63 at 100 ms and 8.37 at a second. Fewer operations were sent as the delay grew, 1,200 at 10 ms but 223 at a second, because clients combined their keystrokes while waiting. The extreme case is a person returning from offline: someone away for ten minutes while others made 20 edits a second has one combined operation to transform past 12,000. It is a burst of work, not a correctness problem, and the server can do it before taking the next operation.

Step 6b: CRDTs

A CRDT, a conflict-free replicated data type, is a data structure designed so that replicas can apply each other’s changes in any order and still converge, with no central server deciding an order. For text, the idea is to stop using positions. Every character gets an id that never changes, made of a counter and the replica that created it, and an insert says which id it goes after. A delete marks its character as deleted but keeps it, because other changes may still refer to it: a tombstone, as in .

Two inserts after the same character are ordered by their ids, the higher first, on every replica, and because counters follow Lamport’s rule (), anything typed after a character inside one of them has a higher id still, so a single comparison skips it. That is the RGA algorithm, and the chapter’s version is under a hundred lines. A change that refers to a character not yet received waits until it arrives.

The test ran 300 random sessions of four replicas, 200 steps each, delivering changes in random order and some of them twice. All four replicas ended with the same text in every session. It also checked a known weakness of some text CRDTs: two people typing “hello” and “world” at the same place at the same moment. Some algorithms interleave such words letter by letter (Kleppmann and others, 2019); in RGA each letter goes after the previous one, so the words stay whole: “aworldhellob”. The OT editor gave the same text, because waiting edits are combined into one operation.

The cost is metadata. After 13,000 keystrokes by three people, with backspaces and jumps, the document showed 10,448 characters but kept 11,724, of which 1,276 were deleted. Stored naively, with ids for every character, that is about 20 bytes per character shown. Characters typed in a row by one person form runs, 2,840 of them here, and storing a run once, as Yjs does, brings it to about 6. Tombstones can only be dropped when every replica has seen the delete, which a system with offline clients rarely knows; Yjs instead discards a deleted run’s content and keeps only its length.

For a product with a server, which is almost every product, both work. OT keeps clients light and gives one authoritative history; a CRDT makes offline and peer-to-peer editing natural and lets the server relay and store without understanding the edits.

Step 6c: Cursors and presence

Presence here is who is in the document and where their cursors and selections are, the same idea as in at a finer grain. It has three properties that set it apart from edits.

  • It is not stored. A cursor position is useless a second later. The document server keeps the latest one per person in memory and broadcasts it; nothing goes to the log, and a lost update is replaced by the next one.
  • It must move with the text. A cursor at position 8 is wrong once someone deletes three characters before it. With OT, each client transforms other people’s cursors past every operation it applies, like an insert of nothing; with a CRDT, a cursor is stored as the id of the character it follows, and needs no updating.
  • It is the larger stream. Every update goes to everyone else, so messages grow with the square of the people. With ten people the calculator’s defaults give 180 operations and 360 cursor updates a second out of one server. So updates are limited to a few a second per person and combined, only changes are sent, and beyond some number of people, Google Docs uses 100, newcomers get a view without presence or editing.

Step 7: Failures and growth

At ten times the people, 500 million a day, there are ten times as many open documents, each still small: more document servers and gateways, and a log of over 100 TB a day before compaction. Nothing about one document changes. At a hundred times, the pressure is the log and its history, so operations are compacted sooner into snapshots and coarse versions. The one thing that does not scale out is a single document with thousands of editors, which is why products cap editors per document and serve everyone else a read-only stream.

In the real world

  • Google wrote on 22 September 2010 that the new Google Docs uses operational transformation, that edits reduce to inserting text, deleting text and applying styles, and that a document is displayed by replaying its revision log from the beginning.
  • Google Docs lets up to 100 people with view, edit or comment access work on a file at the same time; beyond that, only the owner and some editors can edit (help page, checked October 2026).
  • Jupiter (Nichols and others, UIST 1995) introduced the central-server form of OT used here.
  • Figma described its multiplayer system on 16 October 2019: not OT, and inspired by CRDTs without being one, with the server as the authority, the last value received winning for each property, a separate process for each document, and WebSockets to the clients.
  • Yjs implements the YATA algorithm (Nicolaescu and others, 2016). Its internals document says consecutive characters inserted in order by one client are stored as a single item, deleted items are flagged, and with garbage collection their content is discarded (checked October 2026).

Key points

  • Positions change meaning when others edit; any design must account for that or copies diverge.
  • With one server per document, OT is simple: the server orders operations and transforms each past what its author had not seen.
  • The transformation must make both orders agree; test it on many random pairs, and the whole system in a simulated network.
  • The server’s work per operation grows with delay; editors combine keystrokes while waiting.
  • A CRDT gives characters permanent ids and inserts after ids, so changes merge in any order, at the cost of ids and tombstones.
  • Presence is ephemeral, must move with the text, and grows with the square of the people: throttle it, never store it.
  • A snapshot plus the log rebuilds any revision, and lets another server take over a document.

Check yourself

The text is “abc”. Ann inserts “X” at 0 while Bo deletes the “c” at 2. What must Ann’s copy do with Bo’s delete, and Bo’s with Ann’s insert?

Ann’s copy reads “Xabc”, so Bo’s delete must move to position 3. Bo’s copy reads “ab”, and Ann’s insert at 0 is unaffected by a delete after it. Both end with “Xab”.

Why does a central server make operational transformation much easier?

The server decides one order for all operations, so each client only needs to transform incoming operations past its own unacknowledged ones, and the server only needs to transform each operation past those its author had not seen. That needs only the property that both orders of two operations agree. Without a single order, operations can meet in many different orders and a second, much harder property is needed.

Why does a client keep only one operation in flight?

So that the server always knows exactly which revision each operation was made on, and the client has a single pending operation to transform incoming ones against. Edits made meanwhile are combined into one waiting operation, which also reduces how many operations are sent when the network is slow.

In a CRDT, why are deleted characters kept?

Because changes made elsewhere may refer to them: an insert after a character that has since been deleted must still find its place. Removing the tombstone is safe only when every replica has seen the delete, which a system with offline clients rarely knows.

Two inserts arrive saying “after id 3@A”. How do all replicas agree on their order?

By comparing the inserts’ own ids: the higher counter first, and the higher replica name on a tie. Every replica uses the same rule, so they agree without coordinating, in whatever order the inserts arrived.

Why are cursor updates not written to the operation log?

They are valid for a moment and are replaced by the next one, so storing them adds most of the log’s volume for nothing. They also grow with the square of the people. They are held in memory, broadcast and throttled.

A document server crashes. How do the editors continue without losing anything acknowledged?

Its lease on the document expires and another server loads the latest snapshot and the log after it. Acknowledged operations are in the log. Clients reconnect, learn the revision, and resend their unacknowledged operations with the same sequence numbers, so any that had arrived are recognized instead of applied twice.
