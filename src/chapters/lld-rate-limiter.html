The problem

The problem. Design a rate limiter. Given a client and a request, it decides whether the request may proceed, under limits such as 100 requests a minute for each user. It must support several limiting algorithms, and it will be used to protect an HTTP API.

explained why services limit their callers and how the five standard algorithms behave. That chapter treated each algorithm as a small class on its own. This one asks the questions of : what is the contract, which rules must hold, what varies, and where the state lives. In the terms of , a rate limiter is a data structure with a contract, like the cache of the previous chapter, with a stronger concurrency question attached. The last answer is a design decision. A limiter that calls Date.now() can be tested only by waiting or by replacing the clock. One that is given the time is tested with plain numbers, and this chapter’s tests simulate hours of traffic in seconds ().

Step 4: The classes

The central decision is visible in the shape of Algorithm. It does not store anything. It has two functions: start, which returns the state for a client seen for the first time, and decide, which takes a state, the time and a cost, and returns a decision together with the state that should follow. The resilience chapter’s SlidingWindowCounter was one object per client that decided and updated in a single call. Splitting the two has three consequences, each used later.

  • Storage is someone else’s concern. A state is a small value, so it can live in a map, a bounded cache or another process.
  • Asking is separate from charging. A caller can find out what an algorithm would decide without changing anything, and store the new state only if it wants to. Combining several limits correctly depends on this.
  • Tests are arithmetic: a list of times in, decisions out.

Each algorithm is a strategy in the sense of , chosen when a KeyedLimiter is built. The HTTP layer is a decorator (): it wraps any handler and either passes the request through or answers for it.

Step 6: The code

The algorithms

// Each algorithm is a pair of pure functions: the state a new client starts with, and a decision that returns
// the next state. Nothing here reads a clock or stores anything. Times are milliseconds.
export interface Decision {
  allowed: boolean;
  remaining: number;    // requests that could still be made now
  retryAfterMs: number; // 0 if allowed; otherwise the wait before one request would be allowed
  resetMs: number;      // the wait, if nothing more arrives, until the whole allowance is back
}
export interface Algorithm {
  readonly name: string;
  readonly limit: number;
  readonly windowMs: number;
  start(now: number): S;
  decide(state: S, now: number, cost: number): { decision: Decision; next: S };
}

// Token bucket, counted in integers: one token is `windowMs` units of credit, and `limit` units arrive each millisecond.
export const tokenBucket = (limit: number, windowMs: number): Algorithm<{ credit: number; at: number }> => ({
  name: "token bucket", limit, windowMs,
  start: (now) => ({ credit: limit * windowMs, at: now }),
  decide(state, now, cost) {
    const credit = Math.min(limit * windowMs, state.credit + (now - state.at) * limit);
    const need = cost * windowMs;
    const full = (left: number) => Math.ceil((limit * windowMs - left) / limit);
    if (credit >= need) return { decision: { allowed: true, remaining: Math.floor((credit - need) / windowMs), retryAfterMs: 0, resetMs: full(credit - need) }, next: { credit: credit - need, at: now } };
    return { decision: { allowed: false, remaining: Math.floor(credit / windowMs), retryAfterMs: Math.ceil((need - credit) / limit), resetMs: full(credit) }, next: { credit, at: now } };
  },
});

The bucket counts in integers. A natural version would add limit ÷ windowMs tokens for every millisecond, which for 3 a second is 0.003 recurring, and fractions that cannot be stored exactly accumulate small errors over millions of updates. Here one token is worth windowMs units of credit, and limit units arrive each millisecond, so every quantity is a whole number. The refusal also says how long to wait: the missing credit divided by the rate at which it returns, rounded up.

The second algorithm is the leaky bucket in its form as a meter, known as the generic cell rate algorithm, or GCRA. It comes from Asynchronous Transfer Mode (ATM) networks, where it policed the rate of fixed-size cells, and is specified in ITU-T Recommendation I.371. It stores a single number: the time at which the client’s bucket would next be empty if nothing more arrived. Each request pushes that time later by one interval, and a request is allowed if the result is no more than one window ahead of now.

// GCRA, the leaky bucket as a meter. It stores one number: the time at which the bucket would next be empty.
export const gcra = (limit: number, windowMs: number): Algorithm<{ emptyAt: number }> => {
  const interval = windowMs / limit; // the time one request takes to leak away
  return {
    name: "GCRA", limit, windowMs,
    start: (now) => ({ emptyAt: now }),
    decide(state, now, cost) {
      const emptyAt = Math.max(state.emptyAt, now) + cost * interval;
      if (emptyAt - now <= windowMs) return { decision: { allowed: true, remaining: Math.floor((windowMs - (emptyAt - now)) / interval), retryAfterMs: 0, resetMs: Math.ceil(emptyAt - now) }, next: { emptyAt } };
      return { decision: { allowed: false, remaining: Math.max(0, Math.floor((windowMs - (state.emptyAt - now)) / interval)), retryAfterMs: Math.ceil(emptyAt - now - windowMs), resetMs: Math.ceil(Math.max(0, state.emptyAt - now)) }, next: state };
    },
  };
};

Written this way, it is the token bucket in disguise. The distance from now to emptyAt is the credit the bucket has used, measured in time instead of tokens. The test confirms it: on three runs of 50,000 requests at random intervals, with limits of 10 a second, 100 a minute and 5 a second, the two returned identical decisions, including the remaining count and the time to wait. GCRA is worth knowing because it stores one number instead of two, which matters when millions of states sit in a shared store.

The other three follow the same interface, and are as described in and the sections after it. The state of each is one line of the class diagram: a window start and a count, a list of times, or a window start and two counts.

Five algorithms, one stream of requests

With the algorithms behind one interface, comparing them is a loop. The chapter’s code sends the same twenty requests from one client through each of them, with a limit of 4 a second, and the figure is drawn from what it printed.

Every row agrees on the first burst: four allowed, two refused. They part company at one second. The fixed window counter starts again from zero, and lets four of the second burst through, so eight requests passed between 0.80 and 1.09 seconds. The sliding log refuses all six, because the last second already contains four. The token bucket lets one through, at 1.06 seconds, because tokens return at one every 250 milliseconds and one has accumulated since the first request. On the steady requests afterwards, the sliding counter allows the request at 1.4 seconds that the log refuses: it assumes the first burst was spread evenly across the first second, when in fact it all came at the end and still lies within the last second.

Common mistake. Two implementations of the sliding counter can differ by one request. The resilience chapter’s version allows a request while the estimate is below the limit. This one requires the estimate after the request to stay within the limit, as every other algorithm here does. On that chapter’s worked example, an estimate of 49.5 against a limit of 50, the earlier version allows and this one refuses. Neither is wrong, but a test that compares them will find the difference, so decide which one you mean.

How far above the limit each can go

The figure shows a pattern chosen to expose the boundary. A broader test sends 100,000 requests in bursts of up to 30, separated by quiet gaps of up to two seconds, with a limit of 10 a second, and asks two questions of each algorithm. What is the largest number of requests it allowed in any one-second span? And how many did it allow on average?

The averages say that every algorithm enforces the limit over time. The first group says what “10 a second” means to each. Only the sliding log allowed at most 10 in every second. The token bucket allowed 19 in one span: a full bucket of 10, emptied at once, and nine more tokens returning over the following second. That is by design, and is the meaning of the bucket’s size. The fixed window reached 20, the boundary burst. The surprise is the sliding counter, which also reached 19. Its estimate assumes last window’s requests were evenly spread. When they all came at the end of that window, it underestimates the true count, and lets nearly a second burst through.

This does not contradict Cloudflare’s finding that the counter was wrong for 0.003% of real requests, since real traffic is rarely shaped like this test. But a limit against an adversary, such as on login attempts, is judged by its worst case, and only the log guarantees that.

A state for each client

// One algorithm, a state for each key, and a bound on how many keys are remembered.
export class KeyedLimiter {
  readonly algorithm: Algorithm;
  private readonly states: LruCache;
  private latest = -Infinity; // the largest time seen so far

  constructor(algorithm: Algorithm, maxKeys: number) {
    this.algorithm = algorithm;
    this.states = new LruCache(maxKeys); // the least recently active key is forgotten first
  }

  // Works out the decision and the state that would follow, without storing anything.
  check(key: string, now: number, cost = 1): { decision: Decision; commit: () => void } {
    if (!Number.isInteger(cost) || cost < 1 || cost > this.algorithm.limit) {
      throw new RangeError(`cost ${cost} can never be allowed by a limit of ${this.algorithm.limit}`);
    }
    now = Math.max(now, this.latest); // a clock that steps back must not hand out a fresh allowance
    this.latest = now;
    const state = this.states.get(key) ?? this.algorithm.start(now);
    const { decision, next } = this.algorithm.decide(state, now, cost);
    return { decision, commit: () => this.states.put(key, next) };
  }

  tryAcquire(key: string, now: number, cost = 1): Decision {
    const { decision, commit } = this.check(key, now, cost);
    commit();
    return decision;
  }

  get keys(): number {
    return this.states.size;
  }
}

Three lines in check are defensive, and each answers a question an interviewer may ask.

  • A cost that can never be allowed is an error, not a refusal. A request costing 11 against a limit of 10 would be refused forever, with a time to wait that is a lie. It throws instead, so that the mistake is found where it was made.
  • Time cannot go backward. The time of day on a server is corrected by synchronization and can step back (). In the test, a fixed window counter given the times 1000, 1001 and 1002, and then 999, believed a new window had begun and allowed a fourth request. Through KeyedLimiter, the 999 is treated as 1002 and refused.
  • Nothing is stored by check. It returns the decision and a commit function. tryAcquire is the common case of checking and committing at once.

Remembering clients

A limiter that keeps a state for every key it has ever seen grows without end, and a client that rotates through IP addresses can make it grow on purpose. So the states live in the least-recently-used cache of , which forgets the client that has been quiet longest. Forgetting is safe only under a condition, and the test shows what happens without it.

A client that has been quiet for a whole window is back where it started: a full bucket, an empty log, a counter that has rolled over. Forgetting it changes nothing, because start would recreate the same state. A client that is forgotten while still being limited is different. On its next request it gets a fresh state, and with it a full allowance.

The test sent 200,000 requests over ten seconds from 1,000 clients chosen at random, each asking for about twice its limit of 10 a second. With room for every client, about half were allowed, as they should be. With room for 900, the share rose to 87%. With room for 500, every client was forgotten before it had used its ten, and the limiter, returning correct-looking answers throughout, limited nobody.

The rule: if the limiter can remember as many clients as are active within any one window, an LRU never forgets a client that is still being limited. A client forgotten and back within a window would mean that it and every client used since were active within one window, more than the limiter holds. A second test checked this on 30 clients taking turns, with at most 12 in any one-second span. With room for 12, decisions matched a limiter with unlimited memory exactly. With room for 8, they did not.

How much memory that takes depends on the algorithm. The chapter’s code measured the heap used for each client, with every client at its limit, in Node 22.

Several limits at once

A limit for each user does not protect a service from a thousand users arriving together, so real APIs apply two or more limits to the same request: one for the user, one for the whole service, perhaps one for the route (). The obvious code calls tryAcquire on each limit in a loop and stops at the first refusal. It breaks the third invariant: when a later limit refuses, the earlier ones have already taken their share for a request that will not run.

The test measured how much this matters. For ten simulated seconds, a service limit of 100 a second and a user limit of 10 a second were applied to a spammer sending a request every millisecond and to nine ordinary users sending about five a second each. With the limits checked in turn, service first, the ordinary users were served 5 times out of 455. The spammer’s refused requests had emptied the service limit. With the version below, they were served all 455 times, and the spammer received 109: ten a second, plus the bucket that was full at the start.

// Several limits that must all agree: for example one for each user and one for the whole service.
// Nothing is consumed unless every limit allows the request.
export interface Limit {
  readonly name: string;
  readonly limiter: KeyedLimiter;
  readonly keyOf: (request: { user: string; route: string }) => string;
}
export function allOf(limits: readonly Limit[]) {
  return (request: { user: string; route: string }, now: number): { decision: Decision; blockedBy: string | null } => {
    const checks = limits.map((limit) => ({ limit, ...limit.limiter.check(limit.keyOf(request), now) }));
    const refused = checks.filter((c) => !c.decision.allowed);
    if (refused.length === 0) {
      for (const c of checks) c.commit();
      const closest = checks.reduce((a, b) => (b.decision.remaining < a.decision.remaining ? b : a)); // the limit nearest to running out
      return { decision: closest.decision, blockedBy: null };
    }
    const worst = refused.reduce((a, b) => (b.decision.retryAfterMs > a.decision.retryAfterMs ? b : a));
    return { decision: worst.decision, blockedBy: worst.limit.name };
  };
}

This is where splitting check from commit pays for itself. Every limit is asked first, and nothing is stored until all have agreed. When several refuse, the answer reports the one with the longest wait, since retrying before then is certain to fail again. Putting the user limit first would have avoided this failure but caused another: users charged for requests the service limit refused.

Rules, and the HTTP edge

Different requests deserve different limits. Login attempts should be limited tightly and by address, since the attacker does not have an account yet. Uploads are expensive. Everything else can be generous. A list of rules, tried in order, says which applies.

export interface Request { user: string; route: string; ip: string }
export interface Response { status: number; headers: Record; body: string }

// Which limit applies to a request: the first rule that matches.
export interface Rule { name: string; matches: (r: Request) => boolean; perMinute: number; keyOf: (r: Request) => string }
export const ruleFor = (rules: readonly Rule[], request: Request): Rule => {
  const rule = rules.find((r) => r.matches(request));
  if (!rule) throw new Error(`no rate limit rule matches ${request.route}`); // the list should end with a catch-all
  return rule;
};

// The decision, in the form of the IETF draft's header fields, and Retry-After when refused.
export function headersFor(decision: Decision, policy: string, limit: number, windowS: number, resetS: number): Record {
  const headers: Record = {
    "RateLimit-Policy": `"${policy}";q=${limit};w=${windowS}`,
    "RateLimit": `"${policy}";r=${decision.remaining};t=${resetS}`,
  };
  if (!decision.allowed) headers["Retry-After"] = String(Math.ceil(decision.retryAfterMs / 1000));
  return headers;
}

// A decorator around any handler: the handler runs only when the limiter allows it.
export function rateLimited(
  handler: (r: Request) => Response,
  decide: (r: Request) => { decision: Decision; rule: Rule },
): (r: Request) => Response {
  return (request) => {
    const { decision, rule } = decide(request);
    const headers = headersFor(decision, rule.name, rule.perMinute, 60, Math.ceil(decision.resetMs / 1000));
    if (!decision.allowed) return { status: 429, headers, body: "Too many requests" };
    const response = handler(request);
    return { ...response, headers: { ...response.headers, ...headers } };
  };
}

The test’s rules are login at 5 a minute keyed by ip: and the address, uploads at 20 a minute keyed by user:, the user and :upload, and a last rule matching everything at 600 a minute for each user. Three details carry most of the weight.

  • The key belongs to the rule. The same user has separate allowances for uploads and for everything else, because the keys differ. Login is counted by IP address.
  • The list ends with a rule that matches everything. Without it a new route would have no limit at all, silently. ruleFor throws if nothing matches, so that the mistake shows up in the first test that touches the route.
  • The handler runs only when the request is allowed. In the test, seven login attempts in the same instant got 200 five times and then 429 twice, and the handler ran five times. The refusal carried Retry-After: 12, since a limit of 5 a minute returns one token every 12 seconds, and RateLimit: "login";r=0;t=60: nothing left, and all five back in a minute. At 12 seconds the next attempt succeeded. An attempt from another address was allowed throughout.

The header fields follow the IETF draft “RateLimit header fields for HTTP”, version 11 of May 2026, still a draft. RateLimit-Policy describes the limit: a quota q in a window of w seconds. RateLimit reports the current position: r remaining, and t seconds until the quota is restored. That second number is why Decision carries resetMs as well as retryAfterMs: the wait for one more request and the wait for the whole allowance are different questions. Status 429 itself is defined in RFC 6585. The rate limiting module of NGINX answers 503 by default unless limit_req_status is set, telling clients the server is unavailable rather than that they should slow down.

In production. When several limits apply, the draft allows a server to report only the one closest to running out. That is what allOf does when every limit allows: it returns the decision of the limit with the fewest requests remaining.

Concurrency

In one Node process, KeyedLimiter is safe without a lock. check and commit are synchronous, and nothing else runs between reading a state and storing the next one, so each decision is atomic by construction (). That changes the moment the state moves out of the process. With twenty servers behind a load balancer, each server’s own limiter would let a client make twenty times its limit, so the states must be shared, typically in Redis. Every access to them now involves a wait, and the obvious code reads, decides and writes in three steps.

// Read, decide, write: three steps, with waits between them where other requests can read the same old state.
export async function racyAcquire(store: StateStore, algorithm: Algorithm, key: string, now: number): Promise {
  const state = (await store.get(key)) ?? algorithm.start(now);
  const { decision, next } = algorithm.decide(state, now, 1);
  await store.set(key, next);
  return decision;
}

// The same decision, made inside one atomic update.
export function atomicAcquire(store: StateStore, algorithm: Algorithm, key: string, now: number): Promise {
  return store.update(key, (state) => {
    const { decision, next } = algorithm.decide(state ?? algorithm.start(now), now, 1);
    return { next, result: decision };
  });
}

The test used a store that waits one millisecond on every call, standing in for the network. Twenty requests for the same client were started at once against a limit of 10. Reading, deciding and writing in separate calls allowed all twenty, because every request read the full bucket before any of them wrote. Sending the decision as one atomic update allowed exactly ten. This is the race of , and it needs no threads: an await between reading and writing is enough.

The atomic version is possible only because the algorithm is a pure function of the state. The whole decision can be sent to wherever the state lives and run there. In Redis that is a short script, which Redis runs with nothing else interleaved. In a SQL database it is an UPDATE whose new values are computed from the old ones in the same statement, or a transaction that locks the row. designs that service, including what to do when the store cannot be reached.

In a language with threads, the in-memory limiter needs a lock even in one process. Rather than one lock around the map, divide the keys among several independently locked maps by hash, or keep each state in an atomic reference and replace it by compare-and-set, retrying on conflict. A retry is harmless because decide has no side effects.

Step 7: Walk it

Follow one upload from Ana through a server with two limits: her rule, uploads at 20 a minute, and a service limit of 1,000 a second.

  1. The decorator receives POST /photos. ruleFor skips the login rule and matches the upload rule, whose key is user:ana:upload.
  2. allOf asks the upload limiter whether it would allow the request now. It finds Ana’s state, or starts a full bucket, and the algorithm returns “allowed, 7 remaining” and the next state. Nothing is stored.
  3. It asks the service limiter the same question for the key all. Allowed.
  4. Both agreed, so both commit their new states.
  5. The handler runs, and its response leaves with RateLimit-Policy: "upload";q=20;w=60 and RateLimit: "upload";r=7;t=39: seven more uploads now, and the full twenty after 39 seconds, since thirteen tokens are out and one returns every three seconds.
  6. Had either limit refused, nothing would have been stored, the handler would not have run, and the answer would have been 429 with Retry-After set from the longer of the waits.

Key points

  • Make each algorithm a pure function: a state, a time and a cost in; a decision and the next state out. Storage, time and HTTP stay outside it.
  • Pass the time in. Tests become arithmetic, and the limiter can refuse to let time go backward.
  • Token bucket and GCRA are one algorithm. On 150,000 random requests they made identical decisions.
  • “10 a second” means different things: only the sliding log kept every one-second span at 10. The bucket, the fixed window and, on bursty traffic, the sliding counter reached 19 or 20.
  • Bound the memory with an LRU of clients, sized for every client active within one window. Smaller than that, the limiter forgets clients mid-limit, and can stop limiting altogether.
  • Combine limits by checking all and committing only if all agree. Charging as you go lets refused requests drain shared limits.
  • Once the state is shared, each decision must be one atomic update where the state lives. A read and a write with a wait between them let twenty requests through a limit of ten.

Check yourself

Why does Algorithm return the next state instead of updating a field?

So that deciding and storing are separate. A caller can ask what would happen without changing anything, which combining limits needs. The state can live in a map, a cache or another process. And the decision can be run atomically inside a shared store, which fixes the race between servers.

A token bucket allows 10 a second. What is the most it can allow in one second, and is that a bug?

Close to 20: a full bucket of 10 spent at once, plus up to 10 more tokens returning during the following second. The test measured 19 in one span. It is the documented behavior. The size of the bucket is the burst the limiter is willing to accept. If no span may exceed 10, use a sliding log, or a bucket smaller than the rate.

A limiter keeps client states in an LRU cache with room for 10,000. On a busy day 50,000 clients are active within each minute, against a limit of 100 a minute. What happens?

Clients are forgotten while they are still being limited, and each one returns to a fresh state with a full allowance. Depending on the order of requests, the limiter may refuse almost nothing. In the chapter’s test, room for half of the active clients made it refuse nothing. The cache must hold at least as many clients as are active within one window.

A request must pass a per-user limit and a service-wide limit. The code calls tryAcquire on each in turn. What goes wrong?

When the first limit allows and the second refuses, the first has already been charged for a request that does not run. With the service limit first, a client making many refused requests drains the shared limit, and other clients are refused. In the test, ordinary users were served 5 times out of 455. Check all limits, then commit all only if all allow.

Why is the in-memory limiter safe without a lock in Node, and when does that stop being true?

check and commit are synchronous, so no other request runs between reading a state and writing the next. Once there is a wait between the two, as with separate reads and writes to a remote store, every request in flight can read the same old state.

Login attempts are limited to 5 a minute, keyed by user name. What is wrong with that key, and what is better?

An attacker trying one password against many accounts is never limited, since each account sees one attempt, and anyone can lock a real user out with five failed attempts in their name. Limit by address as well, tightly, and keep any account limit generous.

The server’s clock is corrected backward by two seconds. What can a fixed window limiter do wrong, and how does the chapter’s design prevent it?

A time earlier than the current window’s start looks like a new window, with its counter at zero, so a client that had used its whole allowance gets a fresh one. In the test, a fixed window given 1000, 1001, 1002 and then 999 allowed the fourth request. KeyedLimiter never lets time go backward: it treats any time earlier than the latest seen as the latest, and the request is refused.
