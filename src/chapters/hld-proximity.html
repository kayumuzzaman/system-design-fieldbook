The problem

The problem. Design two features of a location app. Nearby places: given a position and a radius, return the businesses inside it, nearest first, optionally of one category. Nearby friends: users who opt in see which of their friends are within 8 km, with the distance, updated as people move.

Nearness is two-dimensional, and ordinary indexes sort by one value, so the first problem is turning “within 2 km of here” into something a database or a key-value store can look up quickly. The second problem has almost no search in it. A million people move every few seconds, and each move matters to a handful of friends, so it is a fan-out problem like a chat system’s, with positions instead of messages. In the terms of , the first is a read-heavy indexing problem and the second a write-heavy push problem, and recognizing which is which is most of the interview.

The two halves come out differently (). Places are a read problem with a small index: 3.2 GB fits in the memory of every server, so the search can run against an in-memory index replicated as many times as the read rate needs, with the details in an ordinary database with read replicas. Friends are a write and fan-out problem: hundreds of thousands of updates a second, multiplied twentyfold, through ten million connections (). Nothing in it is a search.

A search returns distances, not raw coordinates of everything nearby, and pages by an opaque cursor (). The friends channel is a stream in both directions; the client sends its position every 30 seconds while the app is open and stops in the background. The server sends a distance rather than a friend’s exact position, which keeps the default private; showing a precise position is a separate, explicit choice by the person sharing it.

The expiry on the current location is what makes the cache correct without any cleanup. A phone that dies, loses signal or closes the app simply stops renewing its key, and after ten minutes its owner stops appearing to friends, which is exactly the meaning of “nearby now”.

Step 5: The design

Nearby places. A search goes to a stateless location service, which works out which cells of the spatial index can contain places within the radius, reads the place ids in those cells, computes the true distance of each, keeps those inside the circle, and sorts them. Details for the page of results come from a cache in front of the places database. Because places change rarely, the index can be rebuilt every night, or kept current from the database’s change stream (), and every search server holds a full copy. The read rate decides only how many copies there are.

Nearby friends. Each phone holds a WebSocket to one of many socket servers. A location update is written to the location cache and published on the user’s own channel in a publish and subscribe cluster (). A socket server subscribes to the channels of the online friends of each user it holds, and filters by distance before sending anything down.

Step 6a: Turning a circle into lookups

The common trick, introduced in , is to divide the map into cells with names that an ordinary index can store. A geohash is such a name: the world is halved by longitude, then by latitude, then by longitude again, each halving adding one bit for the side the point is on, and every five bits written as one character. Gustavo Niemeyer published it in 2008 and put it in the public domain.

// Each character holds 5 bits; bits alternate between longitude (first) and latitude.
export function encode(lat: number, lon: number, precision: number): string {
  let latLo = -90, latHi = 90, lonLo = -180, lonHi = 180;
  let out = "", bits = 0, value = 0, even = true;
  while (out.length < precision) {
    if (even) {
      const mid = (lonLo + lonHi) / 2;
      if (lon >= mid) { value = value * 2 + 1; lonLo = mid; } else { value *= 2; lonHi = mid; }
    } else {
      const mid = (latLo + latHi) / 2;
      if (lat >= mid) { value = value * 2 + 1; latLo = mid; } else { value *= 2; latHi = mid; }
    }
    even = !even;
    if (++bits === 5) { out += BASE32[value]; bits = 0; value = 0; }
  }
  return out;
}
// The longest geohash whose cells are at least `radius` wide and high: then a circle around any
// point inside a cell stays within that cell and its eight neighbors.
export function precisionFor(radius: number, lat: number): number {
  let p = 1;
  while (p < 12) {
    const c = cellSize(p + 1, lat);
    if (c.width < radius || c.height < radius) break;
    p += 1;
  }
  return p;
}

Two properties make it useful. Points in the same cell share its name as a prefix, so in a sorted list all places of a cell are one contiguous range, found with one binary search: a B-tree index, a sorted set in Redis or a sorted file all answer it. And each extra character divides a cell into 32. At latitude 40 the chapter’s code gives these sizes:

A point near the edge of its cell has neighbors across the edge whose names share nothing with its own. So a search never looks in one cell. It picks the length whose cells are at least as wide and high as the radius, then reads the cell containing the point and its eight neighbors; a circle around any point in the middle cell cannot reach beyond them. For a 1 km radius at latitude 40 that is length 5, nine cells of 3.7 by 4.9 km.

Step 6b: How much each index has to read

Nine cells are always enough and often far too many. The chapter’s code placed 200,000 places in a synthetic city 50 km across, 60% of them in thirty dense neighborhoods, and searched from random places with each method, checking every answer against a full scan.

The alternative to fixed cells is a tree that adapts to density. A quadtree divides a square into four whenever it holds more than a set number of points, and repeats, so its leaves are small where points are dense and large where they are sparse. In the test, with at most 100 places per leaf, the 4,012 leaves ranged from 0.01 km² in the densest neighborhood to 2.4 km² in empty country. A search visits the leaves that touch the square around the circle.

private insert(n: QNode, p: Place, depth: number): void {

The nine-cell search examined up to nineteen times as many places as it returned, because a radius slightly above a cell size forces the next size up, 32 times larger. Covering the circle with cells one size smaller cut the work by three to ten times at the price of 11 to 72 range lookups instead of 9, and the quadtree did about as well. All of them beat a full scan of 200,000 by a wide margin. For places, which are read millions of times between edits, the choice is mostly about what the storage can do: a geohash column works in any database or key-value store, a quadtree is a structure the search servers build in memory, and Google’s S2 and Uber’s H3 cells, described in , cover the sphere with less distortion. Ranking by rating as well as distance happens after this step, on the few hundred places found.

Common mistake. Querying with latitude and longitude as two separate ranges, lat BETWEEN … AND lon BETWEEN …, with an index on each. Each index finds a band around the whole world, and the database must intersect two huge sets. Index one value that captures both, a cell, or use a spatial index such as PostGIS’s.

Step 6c: Moving friends at scale

Searching would be the wrong tool for friends. With 333,000 updates a second, running a radius search for each would mean hundreds of thousands of searches a second over an index that changes with every one of them. Instead, each update goes only to the people allowed to see it, through a channel named after the user. A socket server that holds Ben subscribes to Ana’s channel while both are online; an update on that channel reaches Ben’s server, which knows Ben’s position and drops it if Ana is more than 8 km away.

Three details make this hold up. The channels are spread over the publish and subscribe servers by a hash of the channel name (), so adding servers moves only a share of the channels. Delivery can be fire-and-forget, with no queue or acknowledgment, because a lost position is replaced by the next one 30 seconds later, and a fresh connection reads the latest positions from the location cache rather than replaying anything. And sharing is checked when subscribing, not when delivering, so a user who stops sharing is unsubscribed from everyone at once.

A variant shows people nearby who are not friends. Then there is no friend list to subscribe to, and channels are named after geohash cells instead: each phone publishes in its cell and its server subscribes to the cell and its eight neighbors. The measurements above apply directly, with deliveries in place of places examined: nine cells of the size forced by an 8 km radius would deliver many times more updates than anyone sees, so smaller cells and more subscriptions are the better trade.

In production. Precise location is among the most sensitive data a service holds. Keep the current position only as long as it is useful, with the cache’s expiry; keep history only if the user asked for it, for a stated time; send distances rather than coordinates by default; and make both people opt in before either sees the other.

At ten times the scale, places grow little: the number of businesses on Earth does not grow tenfold, so more replicas carry more searches. Friends grow linearly in connections and updates, and in deliveries by the number of online friends too: 100 million connections and 67 million deliveries a second need ten times the socket and publish and subscribe servers, which scale out as long as no channel is huge. A user with a million followers sharing location is the celebrity problem of ; it is avoided by limiting live sharing to friends. At a hundred times, the fan-out cost dominates, and the usual relief is to send updates less often: only when a user has moved more than some distance, and less often when no friend is nearby.

In the real world

  • Redis’s geospatial commands, as documented in 2026, store each member in a sorted set with a score made by interleaving latitude and longitude bits into a 52-bit integer, and answer radius and box searches “by checking the 1+8 areas needed to cover the whole shape and discarding elements outside it”. Distances use the haversine formula on a spherical Earth, with errors up to 0.5% in the worst case, and latitudes beyond about 85.05 degrees cannot be indexed.
  • Facebook’s Nearby Friends, announced on 17 April 2014 for Android and iPhone in the United States, was optional and worked only between friends who had both turned it on. It showed that a friend was nearby, and a person could choose to share a precise location with a chosen friend for a set time, such as an hour.
  • Geohash was invented by Gustavo Niemeyer, who put it in the public domain in February 2008.

In an interview. If you are given both features, say early that they are different problems and design them separately. For places: estimate the index size, show that it fits in memory, explain geohash with neighbors and how to choose the length, and mention quadtrees and S2 as alternatives. For friends: estimate updates and deliveries, draw socket servers, a cache with expiry and a channel per user, and say where the distance check happens. Ten minutes on each deep dive is about right.

Key points

  • Nearby places and nearby friends are different problems: an index read millions of times, and a stream of updates pushed to a few people each.
  • A geohash names a cell by halving longitude and latitude in turn. Points in one cell share a prefix, so a cell is one range in any sorted index.
  • Search the cell and its eight neighbors, with cells at least as large as the radius. Each character is a factor of 32, so nine cells checked up to nineteen times more places than they found in the test.
  • Smaller cells with more lookups, or a quadtree that adapts to density, cut the places checked by three to ten times.
  • The places index is small enough to hold in memory on every server; replicate it.
  • For friends, publish each update on the user’s channel, subscribe on behalf of online friends, filter by distance at the subscriber, and let a lost update be replaced by the next.
  • Keep current positions with an expiry, and treat location as sensitive data from the first design.

Check yourself

Why can a single B-tree on a geohash column answer a radius search, when two B-trees on latitude and longitude cannot do it well?

All points in a cell share its geohash as a prefix, so each cell is one contiguous range in the sorted index, and a radius search becomes nine or so range scans. Separate indexes on latitude and longitude each return a band around the world, and intersecting them means reading far more rows than are near the point.

Why must a search read the eight neighboring cells as well as the point’s own?

A point near the edge of its cell can have places across the edge, in cells whose names share little or nothing with its own. If every cell is at least as wide and high as the radius, the circle around any point in the middle cell stays within the nine.

For a 1 km radius at latitude 40 the code picks geohash length 5, not 6. Why, and what does it cost?

Length 6 cells are about 0.94 by 0.61 km, smaller than the radius, so nine of them might not cover the circle. Length 5 cells are 3.7 by 4.9 km, so nine cover about 11 by 15 km for a circle of about 3 km². In the test that meant examining 20,451 places to find 1,059.

What makes a quadtree examine fewer places than nine geohash cells in a dense city?

Its leaves are sized by how many points they hold, not by a fixed grid, so in dense neighborhoods they are small. The leaves that touch the circle’s bounding square cover little more than the circle.

Ana and Ben are friends sharing locations. Where is the 8 km check done, and why there?

On the socket server that holds Ben, when Ana’s update arrives on her channel. That server already knows Ben’s current position, and Ana’s server would otherwise have to know where every one of her friends is.

Why is it acceptable for the publish and subscribe system to lose a location update?

Only the latest position matters, and the next one arrives within 30 seconds. A newly connected phone reads positions from the location cache, so nothing needs to be replayed. A queue that guaranteed delivery would only build backlogs of stale positions.

Why does each current location have an expiry of ten minutes?

So that a phone that stops sending, because it lost signal, ran out of battery or closed the app, disappears from friends’ lists without any cleanup job. It also keeps the store from holding positions longer than they are useful, which matters for privacy.
