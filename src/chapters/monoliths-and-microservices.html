What is being decided

The photo app has grown. It has sign-up and login, uploads, image processing, a social graph, a feed, comments, notifications and billing. All of that code has to be organized into something that can be built, deployed and run. The two ends of the range are these.

  • A monolith: the whole application is built and deployed as one unit. All of its code runs in the same process and usually shares one database.
  • Microservices: the application is a set of services, each built and deployed on its own, each owning its own data, communicating over the network.

The word “micro” has misled many teams. Size is not the defining property. The defining property is independent deployment: a team can change its service and release it without coordinating with any other team and without redeploying anything else. A service that can do that is a microservice whether it is 500 lines or 500,000. A system of 40 small services that must all be released together is a monolith with extra steps.

Between the two lies a third option that is often the right one.

What a monolith gives you

A monolith is the simplest thing that works, and for a long time it works very well.

  • Calls are function calls. They take nanoseconds, cannot time out, and either the whole process is up or it is not.
  • Transactions are available. Placing an order and reducing stock can commit or fail together, with no saga ().
  • Changes that cross boundaries are easy. Renaming a function used in ten places is one commit, checked by the compiler.
  • There is one of everything. One build, one pipeline, one deployment, one set of dashboards, one place to look when something breaks.
  • It runs on a laptop. A new engineer can start the whole system and step through a request in a debugger.

Its problems arrive with growth, of the codebase and especially of the team.

  • Deployment becomes a queue. Fifty engineers merging into one deployable means every release carries many unrelated changes. One bad change blocks or rolls back all the others.
  • Everything fails together. A memory leak in the image-processing code takes down login.
  • Everything scales together. If thumbnails need ten times the CPU, you run ten copies of the whole application.
  • Boundaries erode. Nothing stops billing code from reaching into the feed’s tables. Under deadline pressure it will, and after a few years every part depends on every other. This state has a name, the big ball of mud.
  • Builds and tests slow down, and with them every engineer’s working day.

Notice that most of these are about people. A monolith worked on by eight engineers has almost none of these problems. The same monolith worked on by eighty has all of them.

What microservices cost

Splitting into services addresses those problems. Each team deploys alone, a failure can be contained, and each service scales to its own load. The price is that every boundary between services becomes a network.

On top of that comes operational weight. Each service needs its own repository or build target, pipeline, deployment configuration, dashboards, alerts, on-call rotation, security patching and capacity planning. That is affordable if a platform team has made each of those cheap, and crushing if every team builds them by hand.

So microservices exchange one set of problems for another. They trade the problems of many people in one codebase for the problems of a distributed system. That trade is worth making only when the first set has become the more expensive one.

Conway’s law

In 1968 Melvin Conway observed that organizations produce designs that copy their own communication structure. If four teams build a compiler, it will have four passes. The observation has held up well enough to be called a law.

It explains why architecture and team structure cannot be chosen separately. Two teams that share a service must coordinate every release, which is slow, so in practice the code drifts into two halves along the team line whatever the diagram says. A service owned by no team decays. A team that owns six unrelated services cannot hold them all in mind.

The practical reading is that a service boundary should be a team boundary. The purpose of a microservice is to let one team own something end to end, and change it at its own pace. From that follow some rough guides.

  • The number of services should be comparable to the number of teams, not ten times larger. A handful of services per team at most.
  • If you have one team, you have no need for the independence that services provide, and you will pay their full cost.
  • If you want a different architecture, you may need to change the team structure first. This is sometimes called the inverse Conway maneuver.

The modular monolith

Most of what teams want from microservices is clear boundaries: code that cannot be reached into, data that has one owner, the ability to understand one part without understanding all of it. None of that requires a network. It requires discipline, and tooling that enforces it.

A modular monolith is a single deployable divided into modules that obey the same rules services would.

  • Each module has a small public interface. Everything else in it is private.
  • Other modules call only that interface.
  • Each module owns its tables. No other module reads or writes them, or joins against them.
  • The rules are checked automatically on every change. Rules that depend on people remembering them last about a year.

The check can be as small as a script run in the build.

// Rule: code in one module may import another module only through that module's index file.
const MODULE = /^src\/modules\/([^/]+)\//;

function moduleOf(path: string): string | undefined {
  return MODULE.exec(path)?.[1];
}

function resolve(fromFile: string, specifier: string): string {
  const parts = fromFile.split("/").slice(0, -1);              // the importing file's folder
  for (const piece of specifier.split("/")) {
    if (piece === "..") parts.pop();
    else if (piece !== ".") parts.push(piece);
  }
  return parts.join("/");
}

function findViolations(files: Map): string[] {
  const violations: string[] = [];
  for (const [path, source] of files) {
    const from = moduleOf(path);
    for (const match of source.matchAll(/from\s+["'](\.[^"']*)["']/g)) {
      const target = resolve(path, match[1]);
      const to = moduleOf(target + "/");
      const isPublicEntry = /^src\/modules\/[^/]+(\/index)?$/.test(target);
      if (to && to !== from && !isPublicEntry) {
        violations.push(`${path} reaches inside "${to}" (${match[1]})`);
      }
    }
  }
  return violations;
}

// src/modules/orders/refund.ts:   import { db } from "../billing/internal/db";
//   -> src/modules/orders/refund.ts reaches inside "billing" (../billing/internal/db)
// src/modules/orders/place-order.ts:   import { chargeCard } from "../billing";
//   -> allowed: it goes through billing's public entry point

Lint plugins and dependency-checking tools do the same job more thoroughly. The principle is what matters: the boundary is enforced by a machine.

The modular monolith keeps the monolith’s advantages: function calls, transactions where they are really needed, one deployment. It removes the worst of its problems, the erosion of boundaries. And it keeps the option of extraction open. A module with a clean interface and its own tables can be moved into a separate service later with modest effort, when there is a concrete reason. A tangled monolith cannot.

Shopify is the best-documented example. Its core application is one of the largest Ruby on Rails codebases in existence, worked on by more than a thousand developers. In 2019 its engineers described choosing to restructure it into components organized by business domain, each with a public interface and exclusive ownership of its data, in preference to splitting it into microservices. Their reasoning was that microservices would have solved the problems they had and brought “another whole suite of problems” with them.

Finding boundaries

Whether the parts are modules or services, the hard question is where the lines go. A badly placed boundary is worse than none, because it is expensive to cross and expensive to move.

The principle is old: high cohesion within a part, low coupling between parts. Things that change for the same reason belong together, and things that change for different reasons belong apart. Several tests help apply it.

  • Follow business capabilities, not data tables. “Billing” and “media processing” are capabilities. “The user table” is not. Domain-driven design calls a region with its own consistent vocabulary and model a bounded context, and these are natural boundaries ().
  • Look at what changes together. The history of your repository shows which files are edited in the same commits. Draw the line where few commits cross it.
  • Look for different rates of change and different needs. Billing changes slowly and must be exact. The feed changes weekly and can be approximate. Image processing needs GPUs. Those differences are reasons for a boundary.
  • Count the calls. If serving one request means a dozen calls back and forth between two parts, they are one part.
  • Ask whether a part can be useful when its neighbors are down. If notifications cannot do anything without a live call to the user service, the two are coupled more than the diagram admits.

The commonest error is a service for each noun: a user service, a photo service, a comment service, each a thin wrapper around one table. Nothing useful can be done inside any one of them, so every feature becomes a conversation among several. These are sometimes called entity services, and they produce the system described next.

Boundaries are hard to see before a system exists. The domain is not yet understood, and the first guess is usually wrong. That is the strongest argument for starting with a monolith: moving a boundary inside one codebase is a refactoring, and moving one between services is a project.

The distributed monolith

The worst outcome is to split the code and keep the coupling.

The signs are easy to recognize once named.

SymptomWhat it shows
Services must be released in a particular order, or all at onceTheir interfaces are not independently versioned
Several services read and write the same tablesThe database is the real interface, and nobody owns it
One user request passes through a long chain of synchronous callsAvailability and latency multiply down the chain
A shared library holding business logic must be upgraded everywhere at onceCoupling has moved into the library
Most features need changes in several servicesThe boundaries are in the wrong place
No service can be tested without starting most of the othersThey are one system

The shared database is the usual root. A database is an excellent integration mechanism within one service and a poor one between services, because every table and column becomes a public interface that some unknown number of readers depend on. The rule that prevents it is strict: a service’s data is reached only through that service.

Data when every service owns its own

That rule removes two things a monolith provided for free, and both need a replacement.

Queries that join across services. The feed needs the names of the people whose photos it shows, and names belong to the identity service. Three options, from simplest to most dependable:

  • Ask at read time. Fetch the photos, then ask identity for the names in one batched call. Simple, and it couples the feed’s availability and latency to identity’s.
  • Keep a copy. The feed service subscribes to events from identity and stores the names it needs. Reads are local and survive an identity outage. The copy lags slightly ().
  • Build a read model. For complex views, a separate store fed by events from several services ().

Changes that span services. Placing an order touches orders, payment and stock. There is no transaction across them. The answer is a saga with compensating steps (), with events published through an outbox.

Reporting across everything is done outside the services altogether, in a warehouse fed by change data capture ().

If a design needs many synchronous joins or many multi-service transactions, treat that as information. The parts involved probably belong together.

Getting from one to the other

Rewriting a working system from scratch as microservices is the approach with the worst record. The old system keeps changing while the new one is built, the new one must match years of accumulated behavior, and nothing is delivered until the end. The alternative is incremental and has a name, the strangler fig pattern, after a plant that grows around a tree and gradually replaces it.

For each capability to be extracted, the order of work matters.

  1. Draw the boundary inside the monolith first. Give the capability a clean interface and stop other code from reaching past it. If this cannot be done in one codebase, it will not become easier across a network.
  2. Separate its data. Stop other code from touching its tables, remove joins and foreign keys that cross the line, then move the tables to their own database. This is the hardest step and the one most often skipped.
  3. Move the code to its own deployable, behind the same interface.
  4. Shift traffic gradually, comparing results, with the old path kept until confidence is high ().

Choose the first extraction for learning, not for importance: something with few dependencies and a clear edge, such as notifications. And remember that the pattern does not require finishing. A monolith with three services split off for good reasons is a legitimate architecture.

What the evidence says

Public accounts from companies that have gone in both directions are more useful than opinion.

  • Uber, toward more structure. By 2020 Uber had about 2,200 critical microservices and found the result hard to work in: a single feature could touch dozens of services owned by many teams. Its response was to group services into about 70 domains, each with one gateway as its entry point, and to restrict which domains may depend on which. The services remained. The lesson was that thousands of services need the same modular structure that code does.
  • Segment, back to one service. Segment ran a separate service and repository for each of its many integrations. Shared libraries drifted to different versions in each, and in its engineers’ words velocity plummeted while the defect rate exploded. In 2018 it described consolidating them into one service and one repository. It accepted the loss of fault isolation between integrations as the price.
  • Prime Video, one component. In 2023 a Prime Video team described a monitoring tool built from serverless functions and a workflow service, passing video frames between steps through object storage. It reached about 5% of the load it needed, and the orchestration and storage calls dominated its cost. Moving the steps into a single process, with frames passed in memory, cut its cost by 90%. This was one tool within a company that runs a very large number of services, and it shows a boundary drawn in the wrong place, not a verdict on services in general. looks at it more closely.
  • Shopify, a modular monolith, as described above.

The common thread is that the companies which did well chose their boundaries for stated reasons and revisited them when the reasons changed. The ones that suffered had adopted a shape because it was the fashion.

Choosing

SituationReasonable shape
A new product, a small team, a domain still being learnedA monolith, kept modular from the first day
One codebase, several teams, releases beginning to collideA modular monolith with enforced boundaries, and faster builds and tests
One part has very different needs: scaling, hardware, release pace, complianceExtract that part as a service
Many teams, each owning a clear capability, held back by shared releasesServices along team lines, with a platform that makes each one cheap to run
Hundreds of services and nobody can follow a requestGroup services into domains with gateways, and consider merging the chattiest

A fair default is to begin with a modular monolith and extract a service when you can name the specific pressure that the extraction relieves: this team is blocked by that release train, this workload needs to scale on its own, this component must be isolated for compliance. “Microservices are best practice” is not such a pressure.

In an interview. A system design answer is normally drawn as services, and that is fine: the boxes show responsibilities. Be ready for “would you really build it as microservices?” A strong answer separates the logical design from the deployment: “These are the capabilities and their data ownership. With one team I would ship them as modules in one deployable and split out media processing first, because it scales differently. With ten teams, each box becomes a service.” That shows you know what the split costs and what it buys.

Key points

  • A microservice is defined by independent deployment and ownership of its data, not by size.
  • A monolith’s strengths are function calls, transactions and one of everything. Its problems come mainly from many people working in one deployable.
  • Microservices replace those problems with the problems of a distributed system. Every boundary becomes a network call that is slower, can fail alone and cannot join a transaction.
  • Service boundaries should follow team boundaries. Architecture and organization are chosen together.
  • A modular monolith gives clear, enforced boundaries without the network, and keeps extraction possible.
  • Draw boundaries around business capabilities, where things that change together sit together.
  • Splitting code while sharing a database produces a distributed monolith, the worst of both.
  • Migrate incrementally behind a router, separating data before code. Extract a service when you can name the pressure it relieves.

Check yourself

A system has 30 small services that are always released together on Thursdays. Is it a microservice architecture?

No. The defining property of a microservice is that it can be deployed independently. Services that must be released together have the operational cost of thirty deployables and the coupling of one. It is a distributed monolith, and the reason they cannot be released separately, usually shared data or unversioned interfaces, is what needs fixing.

A request passes through eight services in sequence, each available 99.95% of the time. Roughly what availability does the request see, and what are two ways to improve it without making any service more reliable?

About 99.6%, since 0.9995 to the eighth power is 0.996. That is around 35 hours of failure a year. Shorten the chain, by merging services that always call each other or by having services keep local copies of the data they need. Or make steps asynchronous, so that the request does not depend on all eight being up at that moment.

What does a modular monolith keep from a monolith, what does it take from microservices, and what does it give up?

It keeps one deployable, in-process calls and the availability of transactions. It takes enforced boundaries: public interfaces between modules and each module owning its tables. It gives up independent deployment, independent scaling and failure isolation between modules.

Why is “one service per database table” a poor way to draw boundaries?

A table is a storage detail, not a capability. Almost every feature needs several tables, so almost every feature needs several of those services, called in sequence. Changes span many services and teams, latency and failure multiply, and no service can do anything useful alone. Boundaries should surround business capabilities, so that most features stay inside one.

A team wants to extract billing from a monolith. In what order should they do the work, and which step is most often skipped?

First establish the boundary inside the monolith: a clean interface, with no other code reaching past it. Then separate the data: no outside access to billing’s tables, no joins or foreign keys across the line, and then a separate database. Then move the code to its own deployable and shift traffic gradually. Separating the data is the step most often skipped, and skipping it yields a shared database.

What does Conway’s law predict about a service owned jointly by three teams?

That it will not stay one coherent service. Every change needs agreement among three teams, so the code will divide along team lines into parts that each team treats as its own, with awkward interfaces between them, or one team will stop contributing. Ownership should be one team for each service.

A founder with four engineers asks whether to build the new product as microservices “so that it scales”. What do you say?

That services help organizations scale more than they help traffic scale. Four engineers have no coordination problem to solve and would take on the full cost of a distributed system: network failures, no transactions, many pipelines. A monolith scales to very large traffic by running more copies. Build a modular monolith, learn where the real boundaries are, and extract services when a specific pressure appears.
