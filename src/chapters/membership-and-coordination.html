Who is here, and who is in charge?

A load balancer needs the list of healthy servers. A database client needs to know which node is the leader. A partitioned store needs to know which node holds which range. A pool of workers needs exactly one of them to run the nightly job. Underneath, these are all two questions.

  • Membership: which nodes are currently part of the system and working?
  • Coordination: given those nodes, who holds each role, lock or piece of data?

Both would be simple if failures announced themselves. They do not. established that the only evidence of a failure is silence, and that silence cannot tell a dead machine from a slow one or a broken network path. Every technique in this chapter is a way of acting sensibly on that weak evidence.

The techniques fall into two families, and the difference between them is the theme of the chapter.

Heartbeats and timeouts

The basic failure detector is a heartbeat: a small message a node sends on a fixed schedule to say it is alive. A node whose heartbeats stop for longer than a timeout is treated as failed. The health checks of are the same thing in the other direction, with the checker asking instead of the node telling.

Two numbers define the detector, the interval and the timeout, and they set a trade that cannot be escaped.

  • Detection time. A failure is noticed, at the earliest, one timeout after it happens. With a one-second heartbeat and a ten-second timeout, a dead leader goes unnoticed for up to ten seconds, and replacing it starts only then.
  • False alarms. A healthy node that pauses or loses a few packets for longer than the timeout is declared dead. The shorter the timeout, the more often this happens.

The cost of the first is easy to put a number on. An availability target of 99.99% allows 4.4 minutes of downtime a month (). If each failover takes 30 seconds from failure to recovery, one failover uses 11% of the month’s allowance. The cost of the second depends on what a false alarm sets off. Removing a server from a load balancer’s list for a few seconds is cheap. Promoting a new database leader while the old one is still running is how data gets lost.

That gives the first rule of failure detection: match the timeout to the cost of being wrong. Cheap, reversible reactions can use short timeouts. Expensive ones need longer timeouts and, as later sections show, protection for the case where the detector was wrong anyway.

Who sends heartbeats to whom?

The obvious arrangements both have problems as the cluster grows.

With every node checking every other, a cluster of 100 sends 9,900 heartbeats each interval and a cluster of 1,000 sends 999,000. With one monitor, the monitor is a single point of failure, and it has a subtler flaw: it reports whether it can reach a node, which is not the same as whether the node’s clients can. A node can be reachable from the monitor and cut off from half its peers, or the reverse. Partial failures of this kind are common, and no single observer sees them correctly.

Suspicion instead of a verdict

A fixed timeout is a blunt instrument. On a quiet network, heartbeats arrive like clockwork and three seconds of silence is damning. On a busy one, they arrive irregularly and three seconds may mean nothing. A fixed value is too slow for the first and too jumpy for the second.

The phi accrual failure detector, proposed by Naohiro Hayashibara and colleagues in 2004, replaces the yes-or-no answer with a level of suspicion. It records the gaps between recent heartbeats from each node and so learns what normal looks like for that node. At any moment it computes a number, phi, from how unusual the current silence is compared with that history. Each step of one in phi means the silence is ten times less likely to be an ordinary delay. The application chooses the level at which to act.

Cassandra uses this detector, with a default threshold of 8. DataStax’s documentation for it suggests raising the threshold to 10 or 12 on congested networks, and advises against values above 12 or below 5. The practical benefit is that one setting works across quiet and noisy environments, where a fixed timeout would need tuning for each.

Gossip

A gossip protocol spreads information the way a rumor spreads through a crowd. On a regular schedule, typically once a second, each node picks a few other nodes at random and exchanges what it knows with them. Nobody has the full picture to begin with, nobody is in charge, and within a few rounds everybody knows.

What makes this work is that spreading is exponential. One node tells three, those four tell twelve more, and so on. The number of rounds needed grows with the logarithm of the cluster size, which means it barely grows at all.

In the simulation behind , 100 nodes all heard the news in about 6 rounds, 1,000 in about 8, and 10,000 in about 10. Ten times as many nodes cost two more rounds. At one round a second, a cluster of any practical size converges in well under a minute, and each node’s workload, a few small messages a second, does not change with the size of the cluster.

Gossip has properties that suit large systems.

  • No special nodes. Any node can fail and gossip continues. There is nothing to elect and nothing to fail over.
  • Tolerant of loss. A dropped message does not matter. The same news will arrive by another path a moment later.
  • Bounded load. Each node sends a fixed number of messages per round, whatever the cluster size.

And one that limits what it can be used for.

  • It is eventually consistent. For some seconds after any change, different nodes hold different views of the cluster. Two nodes can disagree about whether a third is alive. Gossip gives no moment at which everyone is known to agree.

What is gossiped

Cassandra is the standard example. Once a second, each node exchanges state with up to three others. The state is a small table with an entry for every node the sender knows: its address, a heartbeat counter that the node itself increments, and facts such as which data ranges it owns, its schema version and its load. Every entry carries a version number, so when two nodes compare tables, each keeps whichever copy of an entry is newer. A node whose counter stops advancing in everyone’s tables is, by that fact, suspected.

A new node has to find someone to gossip with. It is given the addresses of a few seed nodes, contacts them, and learns of everyone else from the first exchange. Seeds have no other role. They are an introduction, not a leader.

The same exchange-and-reconcile idea repairs data as well as membership. Dynamo-style databases have replicas periodically compare summaries of their data and copy whatever differs, a process called anti-entropy that appeared in .

SWIM: asking for a second opinion

Detecting failure through gossiped heartbeat counters has a weakness: it is slow to distinguish “this node is dead” from “I cannot reach this node”. SWIM, a protocol published in 2002, addresses that directly and is the basis of the membership library used by Consul, Nomad and many other systems.

In each round, a node picks one member at random and pings it. If the reply comes back, nothing more happens. If it does not, the node does not jump to a conclusion. It asks a few other members to ping the silent node on its behalf.

If nobody can reach the node, it is still not declared dead. It is marked suspected, and the suspicion is gossiped. A node that hears it is suspected can refute the claim by announcing a higher version of itself. Only if the suspicion stands for a set time is the node declared dead. All of this news travels piggybacked on the pings themselves, so there are no extra messages.

HashiCorp’s implementation added a refinement it called Lifeguard, based on an observation from production: most false accusations came from nodes that were themselves overloaded and slow to process replies. A node that notices its own probes timing out more than expected now trusts its own judgment less and waits longer before accusing others.

When a private opinion is not enough

With gossip, each node decides for itself who is alive, and for a while nodes disagree. Whether that matters depends entirely on what is done with the answer.

If the reaction is to stop sending requests to a node, disagreement is harmless. Some nodes route around it a few seconds before others do, and if the suspicion was wrong, traffic returns. This is why leaderless databases, where any replica can accept any write, are comfortable running on gossip alone.

If the reaction is to give a role to someone else, disagreement is dangerous. Suppose two nodes each decide, from their own view, that the leader is dead and that they should replace it. Now there are two leaders, or three counting the original, which was only slow. This is split brain, and it cannot be fixed by tuning a detector, since no detector can be certain.

The decision itself has to be made in one place that cannot contradict itself. That is consensus (), and the practical way to get it is a coordination service.

In an interview. A useful line to draw out loud: “liveness information can be approximate and spread by gossip, but anything that grants an exclusive role goes through a consensus-backed store”. It shows you know there are two problems and which tool fits each.

Coordination services

A coordination service is a small, strongly consistent data store run as a cluster of three or five servers that agree on every write using a consensus algorithm. The widely used ones are Apache ZooKeeper, etcd and HashiCorp Consul. Their common ancestor is Chubby, a lock service Google described in 2006.

They store very little: who the leader of each service is, which nodes are registered, which node owns which shard, a few configuration values. etcd, for example, limits a request to 1.5 MiB and its whole data set to 2 GiB by default, with 8 GiB as the suggested maximum. What they offer in return is that every client sees the same data in the same order, and that the service keeps working as long as a majority of its servers can talk to each other.

A consistent key-value store alone would not be enough to coordinate anything. Three additional features turn it into a coordination tool.

Three building blocks

Keys that vanish with their owner. A client opens a session with the service and keeps it alive by sending periodic keep-alive messages. It can create keys that are tied to that session. If the client crashes, or is cut off for longer than the session’s time limit, the service deletes those keys itself. This turns “is that process alive?” into a question with one agreed answer: the key exists or it does not. A time-limited claim of this kind is called a lease.

Notification of changes. A client can ask to be told when a key, or anything under a prefix, changes. This is a watch. Without it, every client would have to poll, and would learn of a change late or load the service heavily.

Conditional writes with a global order. A write can be made to succeed only if a condition holds: the key does not exist, or it still has the version the client last read. This is the compare-and-set of , made available across machines. Every change is also stamped with a number that only increases, which gives all clients one agreed order of events.

Leader election

Many jobs must be done by exactly one process at a time: running scheduled tasks, assigning shards, being the single writer to some resource. Several copies of the process run for availability, and one of them must be chosen. With the three building blocks, the recipe is short.

  1. Every candidate tries to create the same key, for example /photo-app/scheduler/leader, attached to its own lease, on the condition that the key does not exist.
  2. The store accepts exactly one of those writes. That candidate is the leader, and it keeps its lease alive.
  3. The others watch the key and wait.
  4. If the leader crashes or is cut off, its keep-alives stop, the lease expires and the store deletes the key. The watchers are notified and try again from step 1.
// What the code needs from a coordination service. etcd, ZooKeeper and Consul
// all provide these operations under different names.
interface Lease {
  keepAlive(): Promise;            // false if the lease has already expired
  revoke(): Promise;                  // give it up now, deleting its keys
}
interface Coordinator {
  grantLease(ttlSeconds: number): Promise;
  // Create the key only if it does not exist. Returns an ever-increasing
  // revision number on success, or null if another holder got there first.
  createIfAbsent(key: string, value: string, lease: Lease): Promise;
  untilDeleted(key: string): Promise; // a watch: resolves when the key goes away
}

type Work = (token: number, stillLeader: () => boolean) => Promise;

async function campaign(store: Coordinator, key: string, me: string, lead: Work): Promise {
  for (;;) {
    const lease = await store.grantLease(10);
    const token = await store.createIfAbsent(key, me, lease);

    if (token === null) {                   // someone else is the leader
      await lease.revoke();
      await store.untilDeleted(key);        // sleep until that changes, then try again
      continue;
    }

    let leading = true;
    const renew = setInterval(async () => {
      const ok = await lease.keepAlive().catch(() => false);
      if (!ok) leading = false;             // cannot confirm the lease: stop acting as leader
    }, 3_000);

    try {
      await lead(token, () => leading);     // returns when leadership is lost or the work ends
    } finally {
      clearInterval(renew);
      await lease.revoke().catch(() => {}); // let the next candidate start at once
    }
  }
}

Three details in this code carry the safety of the scheme.

  • The leader stops when it cannot renew. A leader cut off from the store cannot know whether its lease is still valid, so it must assume it is not. The renewal interval is shorter than the lease, so a cut-off leader stops before the store gives the role away. In a test of this code, a leader cut off from the store stopped within one renewal interval, about seven seconds before its successor started. For that interval nobody led, which is the intended outcome. A gap is recoverable. Two leaders may not be.
  • The work checks stillLeader between steps. Leadership is a claim that expires, and it has to be rechecked, not assumed.
  • The token goes with every write. Even this is not airtight. A leader can be paused for longer than its lease between checking and acting, as showed. The revision number returned when the key was created is a fencing token. The resource the leader writes to must reject any token lower than the highest it has seen ().

Kubernetes provides this recipe as a built-in object called a Lease. Its own control-plane components elect their leaders with it, by default with a 15-second lease, a 10-second deadline for renewing and a retry every 2 seconds. An application running on Kubernetes can use the same mechanism through the client libraries and never run a coordination service of its own.

Distributed locks

A distributed lock is the same idea applied to a resource instead of a role: whoever holds the key may act, and everyone else waits. It deserves a section of its own because it is one of the most misused tools in distributed systems.

A lock inside one program is trustworthy for a reason that does not carry over. When a thread holds a lock, no other thread can take it, and the lock is released when the thread finishes or the whole process dies. Across machines, the holder can crash while holding the lock, so the lock must expire. And once a lock can expire, it can expire while its holder is still working and only paused or slow. Then a second holder acquires it, and two processes are inside the section that the lock was meant to protect.

So a distributed lock is always a lease, and a lease is always a promise that depends on timing. The honest question to ask is what the lock is for.

PurposeIf two holders overlapWhat is sufficient
Efficiency: avoid doing the same work twiceSome wasted work, such as a report generated twice or a duplicate emailAny lock with an expiry, including a single Redis key. Make the work idempotent as well.
Correctness: prevent conflicting changesCorrupted or lost dataA lock from a consensus-backed store, plus a fencing token checked by the resource. The lock alone is not enough.

When many clients wait for the same lock, there is a detail worth knowing. If all of them watch the lock key, all of them are woken when it is released, all rush to acquire it, and all but one fail. This herd effect can overload the service. The standard recipe gives each waiter a numbered key and has it watch only the one in front.

Locks in Redis, and the Redlock debate

The most common distributed lock in practice is a single Redis command, because most systems already run Redis.

SET lock:report-2026-10 7f3a9c NX PX 30000
    NX: only if the key does not exist.  PX 30000: expire after 30 seconds.
    7f3a9c: a random value that identifies this holder.

To release, delete the key only if it still holds your value, as one atomic script:
    if redis.call("get", KEYS[1]) == ARGV[1] then return redis.call("del", KEYS[1]) else return 0 end

The random value matters. Without it, a holder whose lock has already expired would delete the lock of whoever took it next.

This lock has two limits. It expires on a timer, with the consequences already described. And Redis replicates asynchronously, so if the primary fails just after granting the lock, the promoted replica may never have heard of it and will grant it again ().

Redis’s creator proposed an algorithm called Redlock to address the second limit: acquire the lock on a majority of five independent Redis servers within a time bound. In 2016 Martin Kleppmann published a critique arguing that Redlock is unsafe for correctness, because it relies on bounded network delays, bounded process pauses and well-behaved clocks, which real systems do not guarantee, and because it produces no fencing token. Redis’s creator replied in defense of the algorithm’s assumptions. The exchange is worth reading in full, and the practical conclusion most engineers draw from it is the table above. For efficiency, a single-server Redis lock is simpler than Redlock and good enough. For correctness, neither is adequate. Use a consensus-backed store and fencing.

Before adding any lock service, check whether the database you already have can do the job. A unique constraint makes “only one of these may exist” true without a lock. A row lock or a conditional update makes “only one of these changes at a time” true inside a transaction (). PostgreSQL also offers advisory locks, which are application-defined locks held by a database session. If the thing being protected is in that database, these are safer than an external lock, because the lock and the data cannot disagree.

Common mistake. Taking a 30-second lock around work that usually takes two seconds, and assuming that is safe. One slow dependency or one long pause, and the lock expires in the middle of the work while the holder carries on. If overlap would corrupt data, an expiry time is not protection. The write itself must carry something the resource can check: a fencing token, a version number or a unique key.

Service discovery

Instances of a service start, stop and move constantly, and their callers need current addresses. Service discovery is membership offered as a lookup.

  1. Each instance registers itself in a registry when it starts, with a key tied to a lease or backed by a health check.
  2. When an instance dies, its lease expires or its health check fails, and it is removed.
  3. Callers look up the service by name and receive the addresses of the live instances, and they watch for changes so that their list stays current.

The lookup is frequently offered through DNS, so that existing software needs no changes: in Kubernetes, a service name resolves to a stable address that forwards to healthy instances, and Consul answers DNS queries from its catalog. The caveats of DNS caching apply (). covers the full picture, including client-side balancing and service meshes.

Other uses

  • Shard and partition assignment. The map of which node owns which partition is exactly the small, critical, must-agree data these services are built for ().
  • Handing out node numbers. A Snowflake-style ID generator needs a number no other running generator has (). Each instance claims one from a small range by creating a key for it under a lease.
  • Configuration and feature flags. Values that every instance must see change at the same time, delivered by watches.
  • Group membership for consumers. Kafka tracks the consumers in a group through heartbeats to one of its brokers and reassigns partitions when one stops, by default sending a heartbeat every 3 seconds and declaring a consumer gone after 45 seconds in its classic protocol ().

Depending on a coordination service safely

A coordination service concentrates risk. It is small and reliable, and everything depends on it. When it has trouble, the trouble arrives everywhere at once.

Roblox’s outage of October 2021 is the clearest public example. The platform was down for 73 hours. Its services used Consul for discovery, health checks, locks and configuration, and its container scheduler and its secrets store depended on Consul as well. Two problems inside Consul, contention in a newly enabled streaming feature under very high load and a performance problem in the storage library that held its log, made the cluster unable to keep up with writes. With Consul unhealthy, services could not find each other, new containers could not be scheduled and secrets could not be read. Diagnosis was slow because the monitoring systems depended on the same Consul cluster. Roblox’s published follow-up actions included removing that circular dependency, splitting workloads across separate Consul clusters, and moving toward more than one data center.

The lessons apply to any system built on such a service.

  • Keep it off the request path. Services should hold the last addresses, configuration and assignments they received and continue with them if the coordination service is unreachable. An outage should stop changes, such as new leaders and new instances, and not stop traffic that was already flowing.
  • Keep it small and quiet. Every write goes through consensus. Storing fast-changing or bulky data in it, such as metrics, queues or per-request state, is the usual way it is overloaded.
  • Do not let everything share one cluster. Separate critical uses, so that one misbehaving workload cannot starve leader election for all the others.
  • Beware mass expiry. If the service itself stalls for longer than the session time limit, every session can expire at once. Every ephemeral key vanishes, every leader steps down and every client reconnects in the same instant. Time limits should be long enough to ride out the service’s own pauses, and clients should reconnect with random delays.
  • Monitor it from outside. The tools you need during its outage must not depend on it.

In production. Run three or five servers, an odd number, spread across failure domains, and never two. Three tolerate one failure and five tolerate two (). Put them on fast disks, because every write waits for a disk flush on a majority, and watch that latency. On a managed platform you may never operate one directly: Kubernetes hides its etcd, and managed databases hide the store that runs their failover. It is still there, and its limits still shape what the platform can do.

Key points

  • Failure detection is always a guess based on silence. Choose timeouts by what a wrong guess costs.
  • Adaptive detectors such as phi accrual output a level of suspicion learned from each node’s history, in place of a fixed timeout.
  • Gossip spreads membership with no central part and constant load per node, and reaches thousands of nodes in about ten rounds. Its views are approximate and briefly inconsistent.
  • SWIM asks other nodes to confirm before suspecting one, which separates failed nodes from failed paths.
  • Decisions that must not be made twice, such as who leads or who holds a lock, belong in a consensus-backed coordination service.
  • Those services are built from three things: keys that vanish with their owner’s lease, watches, and conditional writes with an increasing number.
  • A distributed lock is a lease that can expire while its holder is still working. For correctness, the resource must check a fencing token.
  • A coordination service is a shared critical dependency. Keep it small, keep it off the request path, and keep serving from cached state when it is down.

Check yourself

A team shortens its database failover timeout from 30 seconds to 2 seconds to improve availability. What new risk have they taken on?

False failovers. A leader that pauses or loses packets for more than two seconds is now declared dead while still running. Each unnecessary failover costs downtime of its own and risks two leaders accepting writes. Because promotion is an expensive and dangerous reaction, it calls for a longer timeout and for fencing of the old leader.

Why can Cassandra rely on gossip to decide which nodes are down, while a single-leader database cannot use gossip to choose its leader?

In Cassandra any replica can serve any request, so the only reaction to “node down” is to route around it. If nodes briefly disagree, nothing breaks. Choosing a leader grants an exclusive role. If two nodes acted on different views there would be two leaders, so that decision has to be made once by a majority, through consensus.

A gossip cluster grows from 1,000 to 10,000 nodes. Roughly how does the time for news to reach every node change, and how does each node’s workload change?

Spreading time grows with the logarithm of the size, so it rises by only a couple of rounds, from about 8 to about 10 when each node tells three others per round. Each node still sends the same few messages per round, so its workload does not change.

In SWIM, node A cannot reach node B. Why does A ask other nodes to ping B before doing anything else?

A’s failed ping shows only that the path from A to B is not working, or that A itself is slow. If another node can reach B, then B is alive and should not be reported as failed. Indirect probing removes most false accusations caused by local network problems or an overloaded prober.

A worker takes a lock with a 30-second expiry from a coordination service, then pauses for 40 seconds before writing to storage. What happens, and what prevents damage?

The lease expires during the pause and another worker acquires the lock and starts writing. When the first worker resumes, it still believes it holds the lock and writes too. The lock service cannot stop this. The storage system must: each grant of the lock carries a higher fencing token, and storage rejects a write whose token is lower than one it has already seen.

Why must a Redis lock be released with “delete only if the value is mine” and not with a plain delete?

If the holder’s lock has already expired and another client has acquired it, a plain delete removes the other client’s lock, and a third client can then enter. Storing a random value unique to each holder and deleting only on a match ensures that a client can release only its own lock.

Your service looks up its dependencies’ addresses in a coordination service on every request. What happens during a five-minute outage of that service, and what would you change?

Every request fails for five minutes, although all the dependencies are healthy. The service should look up addresses once, keep them in memory, update them from watches, and continue with the last known list when the coordination service is unreachable. The outage then delays changes of membership without stopping traffic.
