The problem

The problem. Design three small libraries for use inside one service: a logger with levels, per-request context and several destinations; an in-process publish-subscribe bus; and a scheduler that runs tasks at a time, after a delay or periodically, with retries. None of them may take the application down, and all of them must be testable without waiting for real time to pass.

calls this shape “a small library that other code builds on: interfaces first”. The users are other programmers, the requirements are about behavior under stress, and the design is mostly a matter of choosing the few points where callers can plug in their own code. Those points are where the patterns of and appear: strategy, observer, chain of responsibility and decorator, each for a reason.

Step 6: The code

Time as a dependency

// Where time comes from. Every library in this chapter is given a Clock instead of reading the time itself.
export interface Clock {
  now(): number;
  // Calls `fn` once, at `time` or soon after. Returns a function that cancels the call.
  at(time: number, fn: () => void): () => void;
}

Every library is given a clock instead of calling Date.now() or setTimeout itself (). The fake clock keeps its timers in the same min-heap as the scheduler and moves time only when a test asks, firing each timer due on the way and letting the code it wakes run until it waits again. A test of a nightly task with backoff of up to ten seconds then takes milliseconds, and gives the same answer every time; the whole test file runs in about six seconds.

The real clock has one detail worth knowing. A setTimeout delay is stored as a 32-bit signed integer, so nothing longer than 2,147,483,647 ms, about 24.8 days, can be scheduled in one call. In the test, a delay of 231 ms fired after 10 ms, with a TimeoutOverflowWarning. The system clock waits in steps of the longest allowed delay, and the test checks that a timer 231 ms away does not fire.

The logger

// The three things that vary, each behind a small interface.
export interface Sink {
  write(record: LogRecord): void | Promise; // where records go (a strategy)
}
export type Filter = (record: LogRecord) => LogRecord | null; // change it, pass it on, or stop it (a chain)
export type Format = (record: LogRecord) => string; // what a record looks like as text (a strategy)

A record is data: a time, a log level, which is how serious the record is, from debug through info and warn to error, a message, and fields. A sink is a destination for records: standard output, a file, a collector. A logger has a level, and records below it are discarded before any other work is done. child returns a logger that adds fields, such as a request id, to every record and shares the rest, so the code handling a request never repeats them.

// Never throws. Returns a promise only when a sink is still working on the record, for callers that must wait.
  log(level: Level, msg: string, fields: Fields = {}): Promise | undefined {
    if (RANK[level] < RANK[this.core.level]) return undefined; // the cheapest test first
    let record: LogRecord | null = { time: this.core.clock.now(), level, msg, fields: { ...this.context, ...fields } };
    try {
      for (const filter of this.core.filters) if ((record = filter(record)) === null) return undefined;
    } catch (error) {
      this.failed("filters", error); // a broken filter must not let an unredacted record through
      return undefined;
    }
    const waits: Promise[] = [];
    for (const sink of this.core.sinks) {
      try {
        const done = sink.write(record);
        if (done) waits.push(done.catch((error) => this.failed(sink, error))); // never an unhandled rejection
      } catch (error) {
        this.failed(sink, error); // one sink failing does not stop the others
      }
    }
    return waits.length > 0 ? Promise.all(waits).then(() => undefined) : undefined;
  }

Logging must never be the reason a request fails. Each filter and each sink runs inside its own try, and a sink that returns a promise has its rejection caught. In the test, a logger with one sink that throws, one that rejects and one that works took 1,000 calls without throwing: the healthy sink got all 1,000 records, both failures were counted 1,000 times, the error handler was told once about each instead of a thousand times, and there were no unhandled rejections. A filter that throws stops the record instead of passing it on, because the filter may be the one that hides passwords: redaction replaced card and a nested password with [redacted]. Sampling kept 110 of 1,000 debug records at a rate of 0.1.

Formatting has its own trap. JSON.stringify throws on an object that contains itself and on a BigInt, both of which turn up in log fields. The JSON format replaces a cycle with "[circular]", writes a BigInt as a string and an Error as its name and message, and the test checks that the same object appearing twice is not mistaken for a cycle.

A slow sink, and a bounded queue

Writing to a file or a network collector is slower than calling a function. BufferedSink is a decorator: it accepts records into a queue and hands them to the slow sink later, one at a time. The queue must be a bounded queue, one that never holds more than a fixed number of items, because an unbounded one turns a slow sink into a process that runs out of memory. When it is full, something has to give.

// Returns nothing when the item was dealt with at once, or, under "block", a promise that
  // resolves when a full queue has taken the item.
  put(item: T): Promise | undefined {
    if (this.items.length < this.capacity) return void this.items.push(item);
    switch (this.overflow) {
      case "drop-newest":
        this.dropped += 1;
        return;
      case "drop-oldest":
        this.items.shift();
        this.items.push(item);
        this.dropped += 1;
        return;
      case "block":
        return new Promise((resolve) => this.blocked.push({ item, resolve }));
    }
  }

block is backpressure (): the caller gets a promise and should wait for room. The test sent a burst of 1,000 records, ten a millisecond, into a buffer of 100 in front of a sink that writes one a millisecond.

Each policy is right somewhere. Dropping the newest keeps the start of an incident, which usually explains it; dropping the oldest keeps the latest state; blocking keeps everything and makes the application pay. A logger usually drops and counts what it dropped, because a log that slows the service down to the speed of its disk turns a logging problem into an outage. An audit trail blocks.

Publish and subscribe

The bus is the observer pattern of with topics: publishers name a topic, subscribers register a handler for it, and neither knows the other. The type parameter maps each topic name to its message type, so publish("photo.added", …) is checked against what that topic’s subscribers expect.

// Every subscriber is offered the message, whatever the others do. The promise, when there is one,
  // resolves once every subscriber has taken it: handled it, or queued it, or (under "block") made room for it.
  publish(topic: K, message: Topics[K]): Promise | undefined {
    const waits: Promise[] = [];
    for (const subscription of [...(this.topics.get(topic) ?? [])]) { // a copy: handlers may unsubscribe
      try {
        const done = subscription.deliver(message);
        if (done) waits.push(done.catch((error) => this.onError(error, topic)));
      } catch (error) {
        this.onError(error, topic);
      }
    }
    return waits.length > 0 ? Promise.all(waits).then(() => undefined) : undefined;
  }

Two choices matter. First, a failing subscriber is reported and the others still get the message; the test had one subscriber throw and one reject, and the third got every message. Second, when does a subscriber run? With sync delivery the handler runs inside publish. That is simple, but an async handler is started for every message without waiting for the last one. In the test, 100 messages a millisecond apart to a handler taking 1 to 20 ms ran up to 15 handlers at once, and 68 messages finished before one published earlier. With queued delivery each subscriber has its own bounded queue and one consumer, so its messages are handled one at a time, in order, which the test checked.

Queued delivery also decides who waits for a slow subscriber. With one subscriber taking 1 ms a message and another 10 ms, each with a queue of 50, and 1,000 messages a millisecond apart, the dropping policies let the publisher finish at 1,000 ms while the slow subscriber handled 150 messages; blocking delivered all 1,000 to both, and the publisher finished at 9,491 ms. One slow subscriber slows every publisher of its topic. That is why block is chosen per subscriber, for the ones that must see everything.

The scheduler

The scheduler keeps every future run as an entry in a min-heap ordered by start time, and arms exactly one timer, for the earliest. Adding a task costs O(log n), however many are waiting, and the process holds one timer instead of thousands.

// Starts what is due, as far as the concurrency limit allows, then sets one timer, for the earliest entry.
  private wake(): void {
    this.disarm?.();
    this.disarm = null;
    const now = this.clock.now();
    for (let top = this.heap.peek(); top !== undefined && top.at <= now && this.running < this.limit; top = this.heap.peek()) {
      this.heap.pop();
      if (!top.task.canceled) this.start(top, now);
    }
    const next = this.heap.peek();
    if (next !== undefined && this.running < this.limit) this.disarm = this.clock.at(next.at, () => this.wake());
  }

  private start(entry: Entry, now: number): void {
    const { task, attempt } = entry;
    let due = entry.due;
    const period = task.options.every;
    if (period !== undefined && attempt === 1 && now >= due + period) {
      // The next run is already due, so this one was missed: the process was paused, or the last run overran.
      const latest = due + Math.floor((now - due) / period) * period;
      const policy = task.options.missed ?? "once";
      if (policy === "skip") return this.push(task, latest + period, latest + period, 1); // wait for the next one
      if (policy === "once") due = latest; // one run stands for all the missed ones
      // "catch-up" runs this one as it is, and the next will be found missed too, until the task is on time again
    }
    this.running += 1;
    Promise.resolve()
      .then(() => task.fn({ due, attempt }))
      .then(
        () => this.finish(task, due, attempt, false),
        (error: unknown) => this.finish(task, due, attempt, true, error),
      );
  }

  private finish(task: Task, due: number, attempt: number, failed: boolean, error?: unknown): void {
    this.running -= 1;
    const { retry, every } = task.options;
    if (failed && retry !== undefined && attempt < retry.attempts && !task.canceled) {
      this.push(task, this.clock.now() + retry.backoff(attempt), due, attempt + 1);
    } else {
      if (failed) this.report(error, task.name); // this run has used all its attempts
      // The next run is added only now, so a periodic task never overlaps itself, and a failure never ends its schedule.
      if (every !== undefined && !task.canceled) this.push(task, due + every, due + every, 1);
    }
    this.wake();
  }

wake pops entries that are due, skipping canceled ones, until it reaches one in the future or the concurrency limit; then it arms the timer for the new top. In the test, ten 100 ms tasks due together under a limit of 3 started at 0, 0, 0, 100, 100, 100, 200, 200, 200 and 300 ms. Canceling only marks the task, and its entries are dropped when they reach the top, so canceling costs nothing.

finish holds two decisions. A failed run is pushed back with a delay from the retry policy, keeping the time it was due, so the task knows which run it is retrying. And the next run of a periodic task is added only when the current one has finished, which is what stops a task from overlapping itself. The test checks a periodic export that fails twice: the first run uses both of its attempts and is reported once, the second run fails once and succeeds on its retry, and the schedule continues.

Periodic tasks that fall behind

A periodic task falls behind in two ways: a run takes longer than the period, or the process stops for a while, paused by a debugger or a busy machine, or a laptop asleep. JavaScript’s setInterval ignores both: it starts the next run when the period comes round, finished or not. Measured with Node’s real timers, an interval of 10 ms with an async task of 25 ms had up to three runs going at once. A nightly job that runs twice at the same time is how data gets processed twice.

The scheduler never overlaps a task with itself, and when a run starts late, a policy decides what to do about the runs that fell due in the meantime: catch-up makes every one of them, once makes one run stand for all of them, and skip waits for the next due time.

With runs of 25 seconds every 10, catch-up started each run further behind its due time, 15, 30 and then 45 seconds late, a backlog that never shrinks. After a 40-second pause, it made five runs back to back. once made one run at once and was then back on schedule; skip waited until 60. Which is right depends on the task: a task that sends a report for each hour must catch up, a task that refreshes a cache needs one run, and a heartbeat should skip.

Retries, backoff and jitter

A failed run is retried after a delay chosen by a Backoff, a function from the attempt number to milliseconds.

// How long to wait before retry number `attempt` (counted from 1), in milliseconds.
export type Backoff = (attempt: number) => number;

export const exponential = (base: number, cap: number): Backoff => (attempt) => Math.min(cap, base * 2 ** (attempt - 1));

// Full jitter: a random wait between zero and what the inner backoff says.
export const fullJitter = (inner: Backoff, random: () => number): Backoff => (attempt) => Math.floor(random() * inner(attempt));

With exponential backoff, each wait is a constant times two to the number of attempts so far, up to a cap: here 100 ms, 200, 400 and so on to at most 10 seconds. A task that kept failing made attempts at 0, 100, 300, 700, 1,500 and 3,100 ms. Backoff gives a struggling dependency room to recover, but it does nothing about clients that failed together, because they all wait the same time and return together. Full jitter fixes that by waiting a random time between zero and the exponential delay, which on average halves each wait and spreads the clients out. The name comes from Marc Brooker’s comparison of jitter strategies at AWS, which found backoff without jitter both the slowest and the most work.

The test reproduced the effect with the scheduler: 1,000 tasks fall due at the same moment and call one dependency that serves at most 10 calls in each 10 ms, refusing the rest at once. Each task may make 10 attempts.

Without jitter, every retry of the 900 refused tasks landed in the same 10 ms, 990 calls for 10 places, again and again: 9,550 calls in all, 100 tasks succeeded and 900 gave up after their tenth attempt at 32.7 seconds. With full jitter, all 1,000 succeeded with 4,278 calls, the last at 3.4 seconds, and the busiest 10 ms after the start had 166 calls instead of 990. With the dependency down altogether, 1,000 clients retrying five times sent all 1,000 retries into one 10 ms without jitter, and at most 151 with it.

Step 7: Walk it

Follow a nightly export, scheduled with every(86_400_000, exportPhotos, { name: "export", missed: "once", retry: { attempts: 5, backoff: fullJitter(exponential(1_000, 60_000), Math.random) } }).

  1. every adds an entry due in 24 hours. wake finds nothing due and arms the one timer for the heap’s top.
  2. At midnight the timer fires. wake pops the entry; start sees it is on time and calls exportPhotos, which logs “export started” through a child logger with { job: "export" }.
  3. The storage service refuses. The run’s promise rejects, and finish pushes attempt 2 with a random wait of up to 1 second, keeping the same due time.
  4. Attempt 2 succeeds. The task publishes export.done on the bus; the mailer’s queued subscription takes it and sends the email later, outside the task. finish adds the next run, 24 hours after this one was due.
  5. If the machine was asleep at midnight and wakes at 3:00, start sees the next run is not yet due, so this one is late but not missed, and runs it once.

Key points

  • Design a library from its variation points: each becomes a one-method interface, and the patterns follow.
  • Infrastructure must fail quietly. A log call never throws, one subscriber cannot stop the others, a failed task is reported and its schedule goes on.
  • Put a bounded queue wherever a fast producer meets a slow consumer, and choose what happens when it is full: drop newest, drop oldest, or block.
  • A scheduler is a min-heap of future runs and one timer for the earliest. Schedule a periodic task’s next run when the current one finishes.
  • Decide what a late periodic run means: catch up, run once, or skip.
  • Retry with capped exponential backoff and full jitter. Without jitter, clients that fail together retry together.
  • Inject the clock. Every result in this chapter came from a fake one, in milliseconds, the same on every run.

Check yourself

A filter that redacts passwords throws on an unusual record. Should the logger write the record unfiltered or drop it?

Drop it, count it and report the failure once. Writing it unfiltered could put a password in the logs, which is worse than losing one record.

A buffered sink holds 100 records and its disk writes one a millisecond. The application logs 10 a millisecond for 100 ms. What does each overflow policy do?

Drop newest keeps the first records and every later one that finds room: 200 of 1,000 written in the test. Drop oldest keeps the latest. Block writes all 1,000 and slows the application to the disk’s pace, about nine times longer.

Why does an async handler subscribed with synchronous delivery see messages out of order?

Because publish starts the handler and returns without waiting for it, so the next message starts another run while the first is still waiting. Runs that wait less finish first. A queue per subscriber, consumed one at a time, keeps the order.

Why does the scheduler add the next run of a periodic task in finish instead of when the run starts?

So that a run that takes longer than the period cannot overlap the next. The next entry does not exist until the current run is over, and a failure goes through the same path, so it does not end the schedule.

A cache refresh runs every minute. The laptop running it sleeps for an hour. Which missed-run policy fits, and what would catch-up do?

once: one refresh brings the cache up to date. catch-up would run it sixty times in a row for nothing.

With waits of 100 ms doubling to at most 10 s, when does the tenth attempt of a task that always fails happen?

The nine waits are 100, 200, 400, 800, 1,600, 3,200, 6,400, 10,000 and 10,000 ms, so the tenth attempt is at 32,700 ms. With full jitter each wait is on average half, so about 16 seconds.

1,000 clients fail at the same moment and retry after exactly 100 ms. What happens, and what does full jitter change?

All 1,000 arrive in the same instant, probably fail again for the same reason, and return together again. With full jitter the first retries spread over the 100 ms, about 100 in each 10 ms, and in the test all 1,000 tasks eventually succeeded instead of 100.
