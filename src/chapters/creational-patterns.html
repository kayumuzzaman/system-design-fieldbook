Patterns, and the trouble with new

The previous three chapters gave principles and a notation. This one and the next two give vocabulary. A design pattern is a named, reusable arrangement of classes and objects that solves a problem which keeps recurring in software design. The names were fixed by a 1994 book whose four authors are known as the Gang of Four. It cataloged 23 patterns in three groups: five about creating objects, seven about composing them, and eleven about how they cooperate.

The lasting value of the catalog is the names. “Put a decorator around the store” or “that should be a strategy” conveys in a few words a design that would otherwise take a diagram. That is worth learning even where the pattern itself turns out to be one line of TypeScript.

Three cautions apply to all three chapters.

  • A pattern is an answer to a problem. Each section here starts with the problem. If you do not have the problem, you do not want the pattern.
  • Patterns cost indirection. Every one adds a class or a layer between the caller and the work. The code is harder to follow in exchange for being easier to change in one particular direction.
  • The book was written for C++ and Smalltalk in 1994. Several patterns exist to work around what those languages lacked. TypeScript has functions as values, object literals and closures, and each of those makes some pattern smaller. This chapter shows both forms.

The problem that creational patterns address is this. A class that follows the principles of depends on interfaces. But the expression new DiskStore("/data") names a concrete class, and whatever contains that expression depends on it. Somewhere, objects must be created. The question is where, and by whom.

Factory

The photo app accepts JPEG, PNG and HEIC files, and each needs different code to produce a thumbnail. The class to use depends on the file that arrives.

// Before: every piece of code that needs a thumbnail repeats the choice of class.
export function thumbnailBefore(type: string, bytes: Uint8Array): string {
  let processor: ImageProcessor;
  if (type === "image/jpeg") processor = new JpegProcessor();
  else if (type === "image/png") processor = new PngProcessor();
  else if (type === "image/heic") processor = new HeicProcessor();
  else throw new Error(`cannot process ${type}`);
  return processor.thumbnail(bytes, 200);
}

// After: one function knows which classes exist. Everyone else asks it.
const makers = new Map ImageProcessor>([
  ["image/jpeg", () => new JpegProcessor()],
  ["image/png", () => new PngProcessor()],
  ["image/heic", () => new HeicProcessor()],
]);

export function processorFor(type: string): ImageProcessor {
  const make = makers.get(type);
  if (!make) throw new Error(`cannot process ${type}`);
  return make();
}

// A new format is registered from outside. This file is not edited.
export function registerProcessor(type: string, make: () => ImageProcessor): void {
  makers.set(type, make);
}

The first function works. The problem is that the same chain of if will be needed wherever a processor is wanted: in the upload handler, in the job that regenerates thumbnails, in the importer. Each copy names all three classes, and a fourth format means finding every copy.

A factory is a function or object whose job is to create other objects, hiding from its callers which concrete class it chose. processorFor returns an ImageProcessor. What stands behind that interface is the factory’s business alone.

In a test the two versions produced identical thumbnails for all three formats, and a processor for a fourth format was added through registerProcessor without editing the file. That last step is the open/closed principle applied to creation: the table can grow from outside.

The original catalog describes a variant called factory method, in which the creating function is a method that subclasses override: a base class Importer runs the import and calls its own createReader(), and ZipImporter and FolderImporter each supply a different reader. It is the same idea, reached through inheritance. In TypeScript a plain function, or a function passed in as a parameter, does the job with less machinery, and the subclass form is worth using mainly when a framework is built around it.

Common mistake. A factory for a class that has only one implementation and no choice to make. UserFactory.create(name) that does nothing but call new User(name) adds a layer and hides nothing. A constructor is already a perfectly good way to create an object when the caller knows which class it wants.

Abstract factory

In production the photos service keeps files in cloud object storage and sends work to a cloud queue. On a developer’s laptop it uses a folder and an in-memory queue. These come in sets. A cloud store paired with an in-memory queue would be a bug: thumbnails requested on the laptop for files that are somewhere else.

An abstract factory is an interface for creating a family of related objects, with one implementation of the interface for each family, so that code which is handed a factory can only ever receive objects that belong together.

export interface Store {
  put(key: string, bytes: Uint8Array): string; // returns where the file went
}
export interface Queue {
  send(message: string): string; // returns what was sent where
}

// The abstract factory: one object that creates a whole matching set.
export interface Platform {
  createStore(): Store;
  createQueue(): Queue;
}

// …four small classes: S3Store, SqsQueue, FolderStore and MemoryQueue…

export const cloudPlatform: Platform = {
  createStore: () => new S3Store(),
  createQueue: () => new SqsQueue(),
};
export const localPlatform: Platform = {
  createStore: () => new FolderStore(),
  createQueue: () => new MemoryQueue(),
};

// Application code is handed a platform and never names a concrete class.
export function startUploads(platform: Platform): (key: string, bytes: Uint8Array) => string {
  const store = platform.createStore();
  const queue = platform.createQueue();
  return (key, bytes) => queue.send(`make thumbnail of ${store.put(key, bytes)}`);
}

Run with each platform in turn, the same startUploads sent “make thumbnail of s3://photos-prod/p1.jpg” to a cloud queue, and “make thumbnail of file:./data/p1.jpg” to a queue in memory. It contains no branch on the environment. The choice was made once, by whoever passed the platform in, and the type system guarantees that the pieces match.

The pattern earns its place when there are at least two families and at least two kinds of product. With one product kind it is an ordinary factory. With one family it is nothing at all.

Builder

A search over a user’s photos has an owner, an optional date range, any number of tags, a sort order and a page size. Some combinations are invalid: a range that ends before it starts, a page size of ten thousand. A constructor with six positional parameters, four of them optional, produces calls such as new PhotoQuery("ana", undefined, undefined, ["lisbon"], false, 20), which nobody can read and anybody can get wrong.

A builder is a separate object that gathers the parts of something complicated through a series of small calls and then creates the finished thing in a single step. It has two benefits. The calls are named, so the code reads like a sentence. And the finished object is checked as a whole and can be made immutable, because it is never seen half-made.

// The builder: collects choices one call at a time, and checks them together at the end.
export class PhotoQueryBuilder {
  private readonly owner: string;
  private from: Date | null = null;
  private to: Date | null = null;
  private readonly tags: string[] = [];
  private newest = true;
  private max = 50;

  constructor(owner: string) {
    this.owner = owner; // the one thing every query must have
  }
  takenBetween(from: Date, to: Date): this {
    this.from = from;
    this.to = to;
    return this;
  }
  tagged(tag: string): this {
    this.tags.push(tag);
    return this;
  }
  oldestFirst(): this {
    this.newest = false;
    return this;
  }
  limit(max: number): this {
    this.max = max;
    return this;
  }
  build(): PhotoQuery {
    return checked({ owner: this.owner, from: this.from, to: this.to, tags: this.tags, newestFirst: this.newest, limit: this.max });
  }
}

// The lighter alternative in TypeScript: one object of named options, with defaults.
export function photoQuery(options: { owner: string; from?: Date; to?: Date; tags?: string[]; newestFirst?: boolean; limit?: number }): PhotoQuery {
  return checked({
    owner: options.owner,
    from: options.from ?? null,
    to: options.to ?? null,
    tags: options.tags ?? [],
    newestFirst: options.newestFirst ?? true,
    limit: options.limit ?? 50,
  });
}

The last function in the listing is the form most TypeScript code uses instead. An object literal already gives named, optional, order-free arguments, which was the main reason for builders in languages without them. A test confirmed that both forms produce equal, frozen queries from the same choices, and that both refuse a reversed date range and an oversized limit.

Use an options object whenUse a builder when
All the choices are known at one place in the codeThe choices are gathered over time or by different pieces of code: a query assembled as filters are applied
Each option is a simple valueSteps do real work: adding to a list, building a nested part, converting units
Readability is already goodA fluent chain reads noticeably better, as in test data or query construction

Whichever form is used, keep the two properties: validate once, at the point of creation, and return something that cannot be changed afterward. An object that is valid when created and never changes is valid forever.

Singleton

Some things should exist once in a running program: the pool of database connections, the loaded configuration, the object that hands out identifiers. A singleton is a class written so that only one instance of it can exist, with a globally reachable way to obtain that instance.

// The textbook form: the class guards its own single instance.
export class Settings {
  private static instance: Settings | undefined;
  readonly maxUploadBytes = 20_000_000;

  private constructor() {} // nobody outside can call new

  static get(): Settings {
    Settings.instance ??= new Settings();
    return Settings.instance;
  }
}

// The same thing in a module: this line runs once, however many files import it.
export const settings = { maxUploadBytes: 20_000_000 } as const;

The second form shows that the class machinery is rarely needed in TypeScript. A module is evaluated once, however many files import it, so a value defined at the top of a module is already a single shared instance.

Singleton is probably the best-known pattern in the catalog and certainly the most criticized. The need it answers, one instance, is real. The harm comes from the second half of the definition, global access.

ProblemWhat happens
Hidden dependenciesA function that calls Database.get() in its body depends on the database, and its signature does not say so. Nobody can tell what a piece of code needs without reading all of it
Tests interfere with each otherState left in the single instance by one test is seen by the next. Tests pass alone and fail together, or the reverse
No substitutesCode that fetches its own collaborator cannot be handed a fake one, which is the dependency inversion problem again
“One” turns out to be wrongA second database, a second tenant, or a second configuration for a test arrives, and the assumption is built into every caller

The remedy keeps the single instance and drops the global access. Create the one pool where the program starts, and pass it to whatever needs it (). There is still exactly one. But each class now states what it uses, and a test can supply its own.

Creating it once, when creation takes time

One real difficulty remains even with a well-placed single instance: making sure it is created only once when creation is asynchronous. Node.js runs JavaScript on one thread, so two lines of code never run at the same instant. But a function that waits gives other code a chance to run during the wait.

// Wrong: check, wait, then remember. A second caller arrives during the wait and also sees nothing.
let pool: Pool | undefined;
export async function getPoolRacy(): Promise {
  if (!pool) pool = await connect();
  return pool;
}

// Right: remember the promise at once. Every caller, however early, gets the same one.
let pending: Promise | undefined;
export function getPool(): Promise {
  pending ??= connect();
  return pending;
}

In a test, two calls made together to the first function created two pools, and each caller got a different one. Two calls to the second created one pool, and a third call later received the same one. The rule generalizes to any work that must happen once: store the promise as soon as the work starts. returns to this kind of bug, which is a race condition without threads.

Prototype

Ana has an editing preset called Portrait, with a crop size and a list of filters, and wants a second preset that starts the same and differs in one detail. Building the new one from nothing means repeating every setting. Copying the existing one is the obvious move, and it has one trap.

export type Preset = { name: string; crop: { width: number; height: number }; filters: string[] };

// A copy made with spread shares everything below the first level.
export function shallowCopy(preset: Preset, name: string): Preset {
  return { ...preset, name };
}

// structuredClone copies all the way down. It is built into the language runtime.
export function deepCopy(preset: Preset, name: string): Preset {
  return { ...structuredClone(preset), name };
}

// For a class with methods, the object knows best how to copy itself.
export class EditPreset {
  readonly name: string;
  private readonly crop: { width: number; height: number };
  private readonly filters: string[];

  constructor(name: string, crop: { width: number; height: number }, filters: string[]) {
    this.name = name;
    this.crop = crop;
    this.filters = filters;
  }

  clone(name: string): EditPreset {
    return new EditPreset(name, { ...this.crop }, [...this.filters]); // new containers, so the copies are independent
  }
  narrowTo(width: number): void {
    this.crop.width = width;
  }
  describe(): string {
    return `${this.name}: ${this.crop.width}x${this.crop.height}, ${this.filters.join("+")}`;
  }
}

The prototype pattern creates new objects by copying an existing one. The catalog’s version gives each class a clone method, as EditPreset has. The reason it needs care is the difference between two kinds of copy.

  • A shallow copy duplicates the top level of an object and shares everything it refers to. In the test, changing the crop of a shallow copy changed the original’s crop from 1350 to 1920, and adding a filter to the copy added it to the original.
  • A deep copy duplicates the object and everything reachable from it. structuredClone, built into Node.js and browsers, does this for plain data. The same edits to a deep copy left the original untouched.

structuredClone has a limit that matters for classes: it copies data and not behavior. Applied to an EditPreset, it returned a plain object that had the fields, was no longer an EditPreset, and had no describe method. For objects with methods and private state, a clone method written by the class is the right tool, because only the class knows which of its parts need copying and which can safely be shared.

The cheapest way to avoid the whole problem is not to modify things. If presets are immutable, sharing their inner objects is harmless, and “a copy with one change” is a new object that reuses everything else. That is the approach the query in the builder section takes.

Who calls new?

Step back from the five patterns and one answer covers most cases. Divide the code into two kinds.

Code that does the workCode that assembles
ContainsRules, calculations, coordinationCalls to new, configuration, the choice of implementations
Depends onInterfacesConcrete classes
How much of itNearly all of the programA few lines near the entry point: the composition root
TestedThoroughly, with fakes passed inBy starting the program

When objects are assembled in one place and handed to the code that uses them, most creational problems do not arise. There is one pool because one was made. The store and the queue match because one function chose both. A creational pattern is then needed only where creation cannot happen at startup:

  • when the class depends on data that arrives later, such as a file’s type, which calls for a factory;
  • when objects are made repeatedly during the program’s life from accumulating choices, which calls for a builder;
  • when a new object should begin as a copy of one a user already has, which calls for a prototype.

One more creational technique is worth knowing by name although the 1994 catalog left it out. An object pool keeps a set of expensive objects, creates them ahead of use, lends them out and takes them back, instead of creating and destroying one for each task. Database connections are the usual case (), and worker threads are another.

In an interview. Creational patterns rarely need to be the center of a low-level design answer. Mention a factory where the type of object depends on input, such as a vehicle type in a parking lot or a piece type in chess, and say that long-lived services are created once at startup and passed in. If you write a singleton, expect to be asked about testing and about concurrent first use. It is usually better to say “there is one instance, created at startup and injected” and avoid the pattern.

Key points

  • A design pattern is a named answer to a recurring design problem. Learn the names for communication, and apply a pattern only when you have its problem.
  • The word new ties code to a concrete class. Creational patterns control where that happens.
  • A factory puts the choice of class in one place and returns an interface. In TypeScript it is usually a function and a table.
  • An abstract factory hands out a whole family of objects that belong together.
  • A builder collects choices and creates a complete, valid, immutable object at the end. An options object often does the same with less code.
  • The need for a single instance is legitimate. Global access to it is what does the damage: create one at startup and pass it in.
  • For work that must happen once and takes time, remember the promise, not the result.
  • A shallow copy shares its inner objects with the original. Copy deeply, or do not mutate.

Check yourself

Notification channels are chosen from a user’s settings at run time: email, push or text message. Where should the code that says new PushNotifier() live, and what should it return?

In one factory, for example a function notifierFor(channel) backed by a table from channel name to a function that creates the object. It should return the Notifier interface. Callers then hold a notifier without knowing its class, and adding a channel means adding one entry to the table.

What does an abstract factory guarantee that three separate factory functions do not?

That the products come from the same family. With three independent functions, a caller could obtain a cloud store and a local queue. With one factory object for each family, a caller that is handed a factory can only ever get a matching set, and switching family is a change in one place.

A class has a constructor with eight parameters, five optional. Give two ways to improve it in TypeScript, and say when you would choose the heavier one.

An options object: a single parameter with named, optional properties and defaults. Or a builder: an object with a method for each choice and a build method at the end. The options object is enough when the caller knows everything at once. The builder is worth its extra class when the choices are accumulated across several steps or functions, or when the steps do real work.

Why is “validate in build() and freeze the result” better than validating in each setter of a mutable object?

Rules that involve several fields, such as “from must not be after to”, cannot be checked while only one of the fields has been set, so setter validation either forbids legitimate intermediate states or misses the rule. Checking once at the end sees the whole object. Freezing the result means the check never has to be repeated, because nothing can change afterward.

A service class calls Config.getInstance() and Database.getInstance() inside its methods. Name two problems and the fix.

Its dependencies are invisible: the constructor and method signatures say nothing about configuration or a database. And it cannot be tested in isolation, because it will always fetch the real ones, and state left in them leaks between tests. The fix is to pass a configuration and a database into the constructor, create the single instances at startup, and inject them.

let cache; async function getCache() { if (!cache) cache = await load(); return cache; } Two requests call it within a millisecond of each other, and load takes a second. What happens, and how is it fixed?

Both calls see cache empty, because the first has not finished waiting, and both call load. The work is done twice, and the two callers may briefly hold different objects. Fix it by storing the promise before awaiting: pending ??= load(); return pending;. The second caller then receives the promise already in progress.

After const b = { ...a }, the line b.tags.push("x") also changes a.tags. Why, and what are three ways to prevent it?

Spread copies the top-level properties. tags holds a reference to an array, and the reference is what was copied, so both objects point at one array. Prevent it by deep copying with structuredClone(a), by copying the nested parts explicitly as in { ...a, tags: [...a.tags] }, or by treating the data as immutable and building a new array with [...a.tags, "x"].
