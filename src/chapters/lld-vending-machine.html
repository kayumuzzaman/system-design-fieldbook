The problem

The problem. Design the software for a vending machine. A customer chooses a product, inserts coins, and receives the product and any change. An operator restocks the machine and collects the cash.

Like the elevator of the previous chapter, this is a machine with modes (). The difference is that here each mode has substantial behavior of its own, which is the situation the state pattern was made for.

Step 1: Clarify

QuestionAssumed answer for this design
Does the customer choose first or pay first?Choose first. The machine shows the price and waits for coins
What money is accepted?Coins of 5, 10, 25, 100 and 200 cents. Cards are a follow-up
Does it give change?Yes, from its own coins and those inserted for this sale. If exact change cannot be made, the sale does not happen
Can the customer cancel?Yes, at any time before the product is released, and gets the same coins back
How does the software know the product came out?A sensor in the tray reports delivered or failed
What does the operator do?Opens the machine with a key, refills slots and takes cash, leaving a float of coins for change
What is out of scope?The mechanics, the display’s graphics, remote monitoring, several products in one sale

The fifth question is the one most often skipped, and it changes the design. Without a delivery signal the software must assume that telling the motor to turn is the same as the product arriving. With one, there is a period of waiting between the two, and that period is a state.

The states

Consider what inserting a coin should do. While the machine is idle, the coin is returned, because nothing has been chosen. While it awaits payment, the coin counts toward the price. While it is dispensing, or open for service, the coin is returned again. One event, three different meanings. Written without the pattern, insert would begin with a switch on the state, and so would select, cancel and every other method. The state pattern of turns that table on its side: one class for each state, holding everything that state does.

Step 4: The classes

The hardware interface deserves a comment. The software never touches a motor. It calls release, returnCoins and show on an object it was given, and receives delivered or failed in return. In production that object drives real devices. In the tests it is a fake of a few lines that records every call (), and that is what allows a test to drive the whole machine through twenty thousand events.

Step 6: The code

// The port to the physical machine. In tests it is a fake that records what it was told to do.
export interface Hardware {
  release(slot: string): void;        // turn the spiral; the machine reports back with delivered() or failed()
  returnCoins(coins: Coin[]): void;   // drop coins into the tray
  show(message: string): void;
}

// …Slot and CashBox: a count that cannot go below zero, and coins counted by denomination…

export type StateName = "idle" | "awaiting payment" | "dispensing" | "maintenance";

// Every state answers every event, and returns the state the machine is in afterward.
interface MachineState {
  readonly name: StateName;
  select(m: VendingMachine, code: string): MachineState;
  insert(m: VendingMachine, coin: Coin): MachineState;
  cancel(m: VendingMachine): MachineState;
  delivered(m: VendingMachine): MachineState;
  failed(m: VendingMachine): MachineState;
  openService(m: VendingMachine): MachineState;
  closeService(m: VendingMachine): MachineState;
}

// The default answers: a coin that is not wanted is handed straight back, and everything else changes nothing.
abstract class Base implements MachineState {
  abstract readonly name: StateName;
  select(m: VendingMachine, _code: string): MachineState { m.hardware.show("Please wait"); return this; }
  insert(m: VendingMachine, coin: Coin): MachineState { m.hardware.returnCoins([coin]); return this; }
  cancel(_m: VendingMachine): MachineState { return this; }
  delivered(_m: VendingMachine): MachineState { return this; }
  failed(_m: VendingMachine): MachineState { return this; }
  openService(_m: VendingMachine): MachineState { throw new MachineError(`cannot open for service while ${this.name}`); }
  closeService(_m: VendingMachine): MachineState { throw new MachineError("the machine is not open for service"); }
}

class Idle extends Base {
  readonly name = "idle";
  override select(m: VendingMachine, code: string): MachineState {
    const slot = m.slots.get(code);
    if (!slot) { m.hardware.show(`No slot ${code}`); return this; }
    if (!slot.sellable) { m.hardware.show(`${slot.name} is sold out`); return this; }
    m.hardware.show(`${slot.name}: ${slot.priceCents}`);
    return new AwaitingPayment(slot);
  }
  override insert(m: VendingMachine, coin: Coin): MachineState {
    m.hardware.show("Choose a product first");
    return super.insert(m, coin);
  }
  override openService(): MachineState { return new Maintenance(); }
}

class AwaitingPayment extends Base {
  readonly name = "awaiting payment";
  private readonly slot: Slot;
  private readonly inserted: Coin[] = []; // held for the customer, not yet the machine's

  constructor(slot: Slot) { super(); this.slot = slot; }

  override select(m: VendingMachine, code: string): MachineState {
    if (this.inserted.length > 0) { m.hardware.show("Cancel first to choose again"); return this; }
    return new Idle().select(m, code);
  }
  override insert(m: VendingMachine, coin: Coin): MachineState {
    this.inserted.push(coin);
    const paid = total(this.inserted);
    if (paid < this.slot.priceCents) { m.hardware.show(`${this.slot.priceCents - paid} more`); return this; }
    // Enough has been paid. Change may come from the cash box or from the coins just inserted.
    const pool = new CashBox(m.cash.available); pool.add(this.inserted);
    const change = makeChange(paid - this.slot.priceCents, pool.available);
    if (!change) {
      m.hardware.show("Cannot give change. Use the exact amount");
      m.hardware.returnCoins(this.inserted);
      return new Idle();
    }
    m.hardware.release(this.slot.code);
    return new Dispensing(this.slot, this.inserted, change);
  }
  override cancel(m: VendingMachine): MachineState {
    if (this.inserted.length > 0) m.hardware.returnCoins(this.inserted);
    return new Idle();
  }
}

class Dispensing extends Base {
  readonly name = "dispensing";
  private readonly slot: Slot;
  private readonly inserted: Coin[];
  private readonly change: Coin[];

  constructor(slot: Slot, inserted: Coin[], change: Coin[]) { super(); this.slot = slot; this.inserted = inserted; this.change = change; }

  // Only now, with the product in the tray, does the customer's money become the machine's.
  override delivered(m: VendingMachine): MachineState {
    this.slot.takeOne();
    m.cash.add(this.inserted);
    m.cash.remove(this.change);
    if (this.change.length > 0) m.hardware.returnCoins(this.change);
    m.hardware.show("Thank you");
    return new Idle();
  }
  override failed(m: VendingMachine): MachineState {
    this.slot.markJammed();
    m.hardware.returnCoins(this.inserted);
    m.hardware.show("Sorry, that did not work. Your money has been returned");
    return new Idle();
  }
}

// The context: it owns the stock and the money, and passes every event to its current state.
export class VendingMachine {
  readonly slots = new Map();
  readonly cash: CashBox;
  readonly hardware: Hardware;
  private current: MachineState = new Idle();

  constructor(hardware: Hardware, slots: Slot[], float: CoinCounts) {
    this.hardware = hardware;
    this.cash = new CashBox(float);
    for (const slot of slots) this.slots.set(slot.code, slot);
  }
  get state(): StateName { return this.current.name; }

  // The customer's buttons and the coin slot.
  select(code: string): void { this.current = this.current.select(this, code); }
  insert(coin: Coin): void { this.current = this.current.insert(this, coin); }
  cancel(): void { this.current = this.current.cancel(this); }
  // Signals from the delivery sensor.
  delivered(): void { this.current = this.current.delivered(this); }
  failed(): void { this.current = this.current.failed(this); }
  // The operator's key.
  openService(): void { this.current = this.current.openService(this); }
  closeService(): void { this.current = this.current.closeService(this); }

  // …restock and collectCash, which are refused unless the state is maintenance…
}

Three things about this code are worth pointing out in an interview.

  • The machine’s methods are one line each. Every event is passed to the current state, and whatever comes back becomes the current state. All the decisions are in the state classes.
  • A base class supplies the dull answers. By default a coin is returned and nothing else changes. Each state overrides only the events it cares about, so Dispensing is two methods long.
  • States carry their own data. The coins inserted so far live in the AwaitingPayment object, and nowhere else. When the machine returns to idle, that object is discarded and the coins with it. A field such as insertedCoins on the machine would exist in every state and mean something in only one.

The scenario test followed a sale of water at 125 paid with two coins of 100. A coin inserted before choosing came straight back. After the first coin the display read “25 more”. After the second, the product was released, and at that moment the cash box still held its original 175 and the stock was unchanged. On the delivery signal, three coins of 25 were returned, the cash box rose to 300 and the stock fell by one.

Step 7: Walk it

Keeping the customer’s money apart

The design choice that makes refunds simple is where inserted coins are held. They are not added to the cash box as they arrive. They stay in the state object, as the customer’s money in the machine’s keeping, until the sensor confirms delivery. Canceling, a jam and a failure to make change all become the same operation: hand back what was being held.

A design that adds each coin to the cash box at once has to subtract on every unhappy path, and must then find coins to refund with, which may no longer be the ones inserted. The same idea appears wherever money waits on an outcome, as an escrow account or as a payment that is authorized first and captured later ().

The conservation rule was tested directly. Twenty thousand random selections, coins and cancel requests were fed to a machine whose hardware failed one delivery in twenty. After every event that left the machine idle, the test confirmed that the coins in the cash box plus all coins ever returned equaled the opening float plus all coins ever inserted. At the end, 695 sales had been made, 44 jams had been refunded in full, and the cash box had grown by 98,030 cents, which was exactly the total price of what had been sold.

Giving change

One method in the listing hides a real problem: makeChange. The amount due is easy to compute. Finding coins that add up to it, from a supply in which any denomination may have run out, is not.

The method everyone uses at a till is to give the largest coin that fits, and repeat. It is called a greedy algorithm: one that makes the best-looking choice at each step and never revisits it.

export type Coin = 5 | 10 | 25 | 100 | 200; // values in cents
export const denominations: readonly Coin[] = [200, 100, 25, 10, 5];
export type CoinCounts = Readonly>>;

// Largest coin first. Fast, and wrong when a coin it wants has run out.
export function greedyChange(amount: number, available: CoinCounts): Coin[] | null {
  const given: Coin[] = [];
  let left = amount;
  for (const coin of denominations) {
    let have = available[coin] ?? 0;
    while (left >= coin && have > 0) {
      given.push(coin);
      left -= coin;
      have -= 1;
    }
  }
  return left === 0 ? given : null;
}

// Finds a way to pay exactly `amount` from the coins available, using as few coins as possible, or null if there is none.
// fewest[a] is the smallest number of coins that add up to a, using only the coins considered so far.
export function makeChange(amount: number, available: CoinCounts): Coin[] | null {
  if (!Number.isInteger(amount) || amount < 0) return null;
  const fewest = new Array(amount + 1).fill(Infinity);
  const picked = new Array(amount + 1);
  fewest[0] = 0;
  picked[0] = [];
  for (const coin of denominations) {
    for (let n = 0; n < (available[coin] ?? 0); n += 1) {       // each physical coin can be used once
      for (let a = amount; a >= coin; a -= 1) {                 // downward, so this coin is not counted twice
        if ((fewest[a - coin] as number) + 1 < (fewest[a] as number)) {
          fewest[a] = (fewest[a - coin] as number) + 1;
          picked[a] = [...(picked[a - coin] as Coin[]), coin];
        }
      }
    }
  }
  return picked[amount] ?? null;
}

export const total = (coins: readonly Coin[]): number => coins.reduce((sum, coin) => sum + coin, 0);

The second function is a small example of dynamic programming: solving a problem by recording the answers to smaller versions of it. Here the record is, for each amount up to the one wanted, the fewest coins that make it. Each physical coin is considered once, and may extend any amount already reachable.

The comparison with the elevator is instructive. There, the states were labels and a single tick method with three branches was the clearest form. Here, four states respond differently to seven events and two of them hold data, so a class for each state is clearer. The choice between a table and state objects is made on that basis, as set out.

In an interview. Draw the state diagram first, before any class, and ask yourself aloud what each event means in each state. That exercise produces the design. Then say the two rules about money: check that change can be made before releasing the product, and keep the customer’s coins apart until delivery is confirmed. Most answers have the states and miss both rules. If time allows only one piece of code, write AwaitingPayment.insert, since it contains the price check, the change check and the transition.

Key points

  • A vending machine is a state machine in which the same event means different things in different states. That is the case for the state pattern.
  • Give each state a class, put the default responses in a base class, and let the machine forward every event to its current state.
  • Data that exists only in one state, such as the coins inserted so far, belongs in that state’s object.
  • Ask how the software knows the product was delivered. The answer adds a dispensing state.
  • Hold the customer’s coins apart from the cash box until delivery is confirmed, so that every unhappy path is the same refund.
  • Check that exact change can be made before releasing the product.
  • With a limited supply of coins, the largest-coin-first method can fail when change exists. A search over reachable amounts cannot.
  • Put the hardware behind an interface, and the whole machine can be tested, including a conservation check over thousands of random events.

Check yourself

What does inserting a coin do in each of the four states, and where in the code is each behavior written?

In idle the coin is returned with the message “Choose a product first”, in Idle.insert. In awaiting payment it is added to the coins held and may complete the sale, in AwaitingPayment.insert. In dispensing and in maintenance it is returned without comment, which is the default in the base class that neither state overrides.

A machine has two coins of 25 and four of 10 and must give 40 in change. What does largest-coin-first give, and what does the search give?

Largest first takes 25, then cannot take another 25 since only 15 remains, takes one 10, and is left needing 5 with no coin of 5: it fails. The search finds 10, 10, 10, 10. Greedy fails here for the same reason as in the chapter’s example: its first choice ruled out the only solution.

Why are inserted coins kept in the AwaitingPayment object and not added to the cash box immediately?

Until the product is delivered the money is still the customer’s. Keeping it apart means that canceling, a jam and a failure to make change are all the same simple action, returning exactly those coins, and the cash box always contains only money the machine has earned. It also keeps the conservation rule easy to state and to test.

The machine checks whether change can be made before it releases the product. What goes wrong if the order is reversed?

The product is already out when the machine discovers it cannot pay what it owes. It must then either keep the customer’s overpayment or give back more or less than the right amount, and the product cannot be taken back. Checking first means the only consequence of a shortage of coins is a refused sale and a full refund.

Why does this design use state objects when the elevator in the previous chapter used a single field and a switch?

In the elevator the states were labels: one method, tick, branched on three values, and no state held data of its own. Here four states each respond to seven events, mostly differently, and two of them own data such as the coins held and the planned change. A class for each state keeps each state’s behavior and data together, where a switch would repeat in every method.

How would you add a rule that a customer who has inserted coins and done nothing for 30 seconds gets them back?

Add a timeout event to the state interface, with a default in the base class that does nothing. AwaitingPayment overrides it to behave like cancel. The timer itself is supplied from outside, started when a coin is inserted and reset on each event, so that tests can fire the timeout directly without waiting.

State the money conservation rule precisely, and say how you would test it.

At any moment when no sale is in progress, the coins in the cash box plus all coins ever returned to customers equal the opening float plus all coins ever inserted. Test it by driving the machine with thousands of random events through a fake hardware object that records returned coins and sometimes reports a failed delivery, checking the equation after every event that leaves the machine idle.
