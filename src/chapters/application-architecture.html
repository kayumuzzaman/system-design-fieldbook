Three kinds of knowledge in one function

The previous chapter built an Order that guards its own rules. Something still has to receive the HTTP request, find the order, call it, store the result and reply. Here is that something, written the way most services begin.

export function placeOrderHandler(db: DatabaseSync, sendEmail: (to: string, text: string) => void) {
  return (req: IncomingMessage, res: ServerResponse): void => {
    const id = req.url?.split("/")[2] ?? "";                                                     // HTTP
    const order = db.prepare("SELECT status, customer FROM orders WHERE id = ?").get(id);        // SQL
    if (!order) { res.writeHead(404).end(); return; }                                            // HTTP
    const lines = db.prepare("SELECT quantity, unit_cents FROM order_lines WHERE order_id = ?").all(id); // SQL
    if (order["status"] !== "draft" || lines.length === 0) { res.writeHead(422).end(); return; } // a business rule
    const total = lines.reduce((sum, l) => sum + Number(l["quantity"]) * Number(l["unit_cents"]), 0); // a business rule
    db.prepare("UPDATE orders SET status = 'placed' WHERE id = ?").run(id);                      // SQL
    sendEmail(String(order["customer"]), `Your order of ${total / 100} is placed`);              // a side effect
    res.writeHead(200, { "content-type": "application/json" }).end(JSON.stringify({ id, total })); // HTTP
  };
}

It works. A test confirmed that it answers 200 and sends the email. The comments on the right show the difficulty: nine lines, and four different concerns interleaved. Each consequence follows directly.

  • It cannot be tested without a database and an HTTP exchange. The test had to create tables, insert rows, start a server and send a real request to check one business rule.
  • It cannot be reused. An operator’s command-line tool or a queue worker that also needs to place orders must copy the rules, and the copies will drift.
  • The rules are hostage to the tools. Changing the web framework or the database means editing, and risking, the logic about what makes an order placeable.
  • The rules are hard to find. “An order must be a draft with at least one line” is half of an if between two SQL statements.

Application architecture is the arrangement of code inside one deployable program: what the parts are, and which may depend on which. It is a different question from the architecture between services that Part VI covered, and it applies equally to a monolith and to each microservice.

Layers

The oldest answer is to sort code into layers, each a group of code with one kind of responsibility, stacked so that each uses only the one beneath it.

LayerKnows aboutIn the order example
PresentationThe protocol: routes, status codes, JSONParsing the path, choosing 404 or 422
ApplicationWhat the system can be asked to do, and in what sequenceLoad the order, place it, save it, announce it
DomainThe rules of the businessOrder.place() and its checks
Data access, or infrastructureHow things are stored and what external systems look likeThe SQL, the email client

This is already a large improvement over the single handler, and for many applications it is enough. It has one structural flaw. If each layer depends on the one below, the domain depends on data access. The business rules, the most valuable and most stable code in the system, sit on top of the most replaceable. In practice the domain objects become shaped by the database tables, and rules migrate into SQL.

The dependency rule

The repair is to reverse one arrow.

The application layer states what it needs from storage as an interface: “something that can get an order and save an order”. The SQL code implements that interface. At run time the calls still flow from the application to the database, as before. In the source code, the dependency now points the other way: the SQL file imports the application’s interface, and the application imports nothing about SQL. This is the dependency inversion principle of , applied to a whole program.

Stated as a rule: source code dependencies point inward only, toward the business rules. Code in an inner layer never names anything in an outer one: no class, no function, no type. Three named architectures are built on this rule, and they differ mainly in vocabulary.

Ports and adapters

The clearest of the three is hexagonal architecture, also called ports and adapters, described by Alistair Cockburn in 2005. Its stated aim was for an application to be driven equally by users, other programs, automated tests and batch scripts, and to be developed and tested in isolation from its databases and devices.

  • A port is an interface at the edge of the application, written in the application’s own terms. It describes a conversation, with no reference to any technology.
  • An adapter connects a port to something real: a web framework, a database, a queue, a test. It is the adapter pattern of in a fixed place.
  • Driving adapters call the application. Driven adapters are called by it.

The hexagon has no significance beyond leaving room to draw several ports. What matters is that there is an inside and an outside, and that the inside owns the interfaces between them. The driven ports for the print shop are short.

// Driven ports: what the application needs from the outside world, stated in its own terms.
export interface OrderRepository {
  get(id: OrderId): Promise;

The driving port is the application’s own interface: the list of things it can be asked to do. Its inputs and outputs are plain data.

// The driving port: everything the outside world can ask this application to do.
export interface OrderApp {
  startOrder(input: { orderId: string; customerId: string }): Promise;
  addPrints(input: { orderId: string; photoId: string; size: PrintSize; quantity: number }): Promise;
  placeOrder(input: { orderId: string }): Promise;
  getOrder(input: { orderId: string }): Promise;
}

// …view(order) copies an Order’s fields into a plain OrderView…

export function createOrderApp({ orders, publisher, clock, prices }: Ports): OrderApp {
  const load = async (id: string): Promise => {
    const order = await orders.get(id as OrderId);
    if (!order) throw new NotFoundError(`no order ${id}`);
    return order;
  };

  // Load, tell, save, publish. A conflict means someone else saved first, so start again from their version.
  const change = async (id: string, apply: (order: Order) => void, attempts = 3): Promise => {
    for (let attempt = 1; ; attempt += 1) {
      const order = await load(id);
      apply(order);
      try {
        await orders.save(order);
      } catch (error) {
        if (error instanceof ConflictError && attempt < attempts) continue;
        throw error;
      }
      for (const event of order.pullEvents()) await publisher.publish(event);
      return order;
    }
  };

  return {
    async startOrder({ orderId, customerId }) {
      const order = new Order(orderId as OrderId, customerId as CustomerId);
      await orders.save(order);
      return view(order);
    },
    async addPrints({ orderId, photoId, size, quantity }) {
      return view(await change(orderId, (order) => order.addPrints(photoId as PhotoId, size, quantity, prices.priceOf(size))));
    },
    async placeOrder({ orderId }) {
      const order = await change(orderId, (o) => o.place());
      return { ...view(order), placedAt: clock.now().toISOString() };
    },
    async getOrder({ orderId }) {
      return view(await load(orderId));
    },
  };
}

This file imports the domain and the port definitions, and nothing else. It does not know whether it is being called from a web request or a test, or whether orders live in memory or in a database. Now the adapters, one of each kind.

export class SqliteOrders implements OrderRepository {
  // …the constructor creates two tables, and get() reads an order and its lines from them…

  // The whole aggregate in one transaction, and only if the version is still the one that was loaded.
  async save(order: Order): Promise {
    const data = order.toSnapshot();
    const expected = this.loadedAt.get(order) ?? 0;
    this.db.exec("BEGIN IMMEDIATE");
    try {
      const written = expected === 0
        ? this.db.prepare("INSERT INTO orders (id, customer, currency, status, version) VALUES (?, ?, ?, ?, 1) ON CONFLICT (id) DO NOTHING").run(data.id, data.customer, data.currency, data.status)
        : this.db.prepare("UPDATE orders SET status = ?, version = version + 1 WHERE id = ? AND version = ?").run(data.status, data.id, expected);
      if (written.changes !== 1) throw new ConflictError(`order ${order.id} was changed by someone else`);
      this.db.prepare("DELETE FROM order_lines WHERE order_id = ?").run(data.id);
      const insert = this.db.prepare("INSERT INTO order_lines (order_id, position, photo, size, quantity, unit_cents) VALUES (?, ?, ?, ?, ?, ?)");
      data.lines.forEach((line, position) => insert.run(data.id, position, line.photo, line.size, line.quantity, line.unitCents));
      this.db.exec("COMMIT");
      this.loadedAt.set(order, expected + 1);
    } catch (error) {
      this.db.exec("ROLLBACK");
      throw error;
    }
  }
}

// A driving adapter. Its whole job is translation: a request into a call, a result or an error into a response.
export function createRouter(app: OrderApp) {
  return async (method: string, path: string, body: Record): Promise => {
    const [, resource, orderId, action] = path.split("/");
    if (resource !== "orders" || !orderId) return { status: 404, body: { error: "not found" } };
    try {
      if (method === "PUT" && !action) return { status: 201, body: await app.startOrder({ orderId, customerId: String(body["customerId"]) }) };
      if (method === "GET" && !action) return { status: 200, body: await app.getOrder({ orderId }) };
      if (method === "POST" && action === "prints") {
        const size = body["size"];
        if (size !== "10x15" && size !== "13x18" && size !== "20x30") return { status: 400, body: { error: "size must be 10x15, 13x18 or 20x30" } };
        return { status: 200, body: await app.addPrints({ orderId, photoId: String(body["photoId"]), size, quantity: Number(body["quantity"]) }) };
      }
      if (method === "POST" && action === "place") return { status: 200, body: await app.placeOrder({ orderId }) };
      return { status: 404, body: { error: "not found" } };
    } catch (error) {
      if (error instanceof NotFoundError) return { status: 404, body: { error: error.message } };
      if (error instanceof DomainError) return { status: 422, body: { error: error.message } };
      if (error instanceof ConflictError) return { status: 409, body: { error: "the order was changed at the same time, try again" } };
      throw error;
    }
  };
}

The first row deserves a name. A contract test is one suite of expectations written against a port and run against every adapter that implements it. It is what entitles a fast in-memory adapter to stand in for the real one in other tests: both have been shown to keep the same promises.

A request, end to end

Two things cross each boundary in that figure and both are translated there.

  • Data. Each layer has its own representation, and none is passed through to the next. The HTTP body becomes a plain input object. The application returns a plain OrderView, not the Order, so that no outside code can call place() on it or come to depend on its internals. Rows become an Order inside the adapter. Objects that exist only to carry data across a boundary are called data transfer objects.
  • Errors. The domain throws a DomainError with a message about orders. Only the HTTP adapter knows that this should be a 422, that a missing order is a 404 and a version conflict a 409. A command-line adapter would turn the same errors into text and an exit code. develops this.

The translation is real work, and it is the main cost of the approach. It buys the freedom to change one representation without changing the others: a column can be renamed, or a field added to the API, with no effect on the rules.

The hexagonal description draws one boundary and stops. The other two also divide the inside into rings, domain within application, as this chapter’s folders do. Choose whichever vocabulary your team already uses. The rule in the last row is the part that matters.

The composition root, and where frameworks belong

If no layer may name a concrete adapter, something outside the layers has to. That place is the composition root, introduced in : the one file that creates every concrete object and hands each to whatever needs it.

const prices = new FixedPrices({ "10x15": Money.of(25, "EUR"), "13x18": Money.of(60, "EUR"), "20x30": Money.of(450, "EUR") });

// Production wiring: a real database file, the real clock, events written to the log.
export function production(databasePath: string): OrderApp {
  return createOrderApp({
    orders: new SqliteOrders(new DatabaseSync(databasePath)),
    publisher: { publish: async (event) => console.log("event", JSON.stringify(event)) },
    clock: { now: () => new Date() },
    prices,
  });
}

// Test wiring: everything in memory, and handles on the fakes so a test can look inside.
export function forTests(overrides: Partial = {}) {
  const publisher = new RecordingPublisher();
  const ports: Ports = { orders: new InMemoryOrders(), publisher, clock: new FixedClock("2026-10-11T09:00:00Z"), prices, ...overrides };
  return { app: createOrderApp(ports), publisher, ports };
}

if (import.meta.main) {
  createHttpServer(production("orders.db")).listen(8080, () => console.log("listening on http://localhost:8080"));
}

Production and tests get the same application, built from different parts. Swapping a database, or running against fakes, is a change to this file alone.

The same reasoning settles where a framework goes. A web framework, an object-relational mapper and a queue client are all details of how the program talks to the world, so they belong in the outer ring, used by adapters. Two habits follow.

  • Keep framework types out of the core. A use case that accepts the framework’s request object, or a domain class that extends the mapper’s base class or carries its annotations, has pointed a dependency outward. The framework can then no longer be upgraded or replaced without touching the rules.
  • Let the framework do its job at the edge. Routing, parsing, validation of shape, serialization and connection pooling are what it is good at. The adapter in this chapter uses Node’s bare HTTP server to stay dependency-free. Replacing it with a framework would change adapters/http.ts and nothing else.

Keeping the rule true

A dependency rule that lives in a wiki is broken within months, by one convenient import at a time. It has to be checked by a machine. The check for this chapter’s code is under forty lines: read every file’s import statements, work out which layer each file is in, and compare against a table.

// What each layer is allowed to import. Dependencies point inward: adapters -> application -> domain.
const allowed: Record = {
  domain: ["domain"],
  application: ["application", "domain"],
  adapters: ["adapters", "application", "domain"],
  root: ["root", "adapters", "application", "domain"],
};

The test suite runs this check and found 20 imports between the nine files, none pointing outward. It also confirmed that the check has teeth: given one extra import from domain/order.ts to adapters/sqlite.ts, it reported exactly that one as a violation. In a real project the same job is done by a lint rule that restricts imports by folder, such as ESLint’s no-restricted-imports, or by a tool that analyzes the dependency graph, such as dependency-cruiser, run on every commit.

Folders: by layer or by feature

Layers describe how one feature is built. They are a poor first division for a whole codebase, because every change then cuts across every top-level folder, and nothing separates one feature’s internals from another’s. Divide first by what the business does, along the bounded contexts of , and apply the layers inside each part. Give each part one public entry file, and extend the import check so that no feature reaches into another’s folders.

The result is the modular monolith recommended in . It also makes later extraction cheap: a module that is already reached only through its own interface can be moved behind a network call by writing one new adapter.

What it buys, and what it costs

The largest practical gain is in testing. The same scenario, start an order, add two lines and place it, was run 500 times at two levels.

How the scenario was run500 runsEach
Calling the application directly, with in-memory adaptersAbout 27 msAbout 0.05 ms
Through an HTTP server and a SQLite database, each started freshAbout 2.6 sAbout 5 ms

A hundredfold difference decides how tests get written. At a twentieth of a millisecond each, every rule and every edge case can have a test, and the whole suite runs on every save. The slower level is still needed, for a handful of tests that prove the adapters are wired correctly.

The costs are also real: more files, an interface and a mapping for each boundary, and a layer of indirection to follow when reading. Whether they are worth paying depends on how much there is to protect.

The application isA fitting structure
A script, a prototype, a tool with a short lifeOne file. Structure can be added when it survives
Mostly forms over tables, with little logicThe framework’s conventions, with handlers that talk to the database through a thin data layer. Ports around every table would be ceremony
Real business rules, expected to live for yearsA domain model, use cases, and ports for the database and for each external system
Several teams or several bounded contextsThe same, as modules with enforced boundaries

The decision need not be uniform. One application can keep a plain handler for its settings page and a full hexagon around its billing.

In an interview. In a low-level design round, show the rule without lecturing on it: put the rules in domain classes, give storage and any external service an interface, and pass those interfaces in. If asked how you would test or how you would change the database, the answer is then already in the design. In a system design round, “what is inside this box?” is answered by the same picture: handlers at the edge, use cases, a domain model, and adapters to the stores and queues drawn elsewhere on the board.

Key points

  • A service holds three kinds of knowledge: protocol, business rules and storage. They change for different reasons and should not share functions.
  • Plain layering leaves the domain depending on data access. Reverse that one arrow.
  • The dependency rule: source code dependencies point inward, toward the business rules, and never outward.
  • A port is an interface the application owns. An adapter connects a port to a technology. Driving adapters call the application, and driven adapters are called by it.
  • Hexagonal, onion and clean architecture are three vocabularies for the same rule.
  • Data and errors are translated at each boundary. Domain objects and framework types do not cross.
  • The composition root is the one place that names concrete classes. Frameworks live in the outer ring.
  • Check the rule with a tool on every build, and divide a large codebase by feature before dividing by layer.
  • The structure pays for itself where there are rules worth protecting, and is overhead where there are none.

Check yourself

In a traditional four-layer stack, which dependency is the problem, and what exactly is done to fix it?

The domain layer depending on the data access layer, which makes the business rules depend on the database code. The fix is for the application or domain to declare an interface for the storage it needs, and for the data access code to implement that interface. The calls at run time are unchanged. The source code dependency now points from the database code toward the core.

Classify each as a driving adapter, a driven adapter, or neither: a REST controller, a class that sends email through a provider’s API, a nightly job that calls a use case, the Order class, an in-memory repository used in tests.

The REST controller and the nightly job are driving adapters: they call the application. The email sender and the in-memory repository are driven adapters: the application calls them through a port. Order is neither. It is part of the domain at the center.

A colleague defines the port interface Database { query(sql: string): Promise<Row[]> } and passes it to the use cases. Why does this not achieve what a port is for?

The use cases must still write SQL and understand rows, so they depend on the storage technology in every way that matters. The interface inverts nothing. A port should be stated in the application’s terms, such as get(id) and save(order), so that an implementation with no SQL at all, in memory or over a network, can satisfy it.

The application returns an OrderView of plain data where it could return the Order itself. Give two reasons.

An Order has methods that change it, so handing it out would let outer code alter state without going through a use case or a save. And outer code, including API clients through serialization, would come to depend on the internal structure of the domain object, so that refactoring it would break them. The view is a stable, deliberately chosen shape.

Which file in this chapter’s code is allowed to import SqliteOrders, and why only that one?

main.ts, the composition root, and tests that set up the adapter. It is the one place whose job is to choose concrete implementations and connect them. If the application or domain imported it, they would depend on SQLite and the dependency rule would be broken.

What is a contract test, and what does it allow you to do safely?

One suite of expectations written against a port and run against every adapter that implements it, here the in-memory and SQLite repositories. Because both are shown to behave the same way where it matters, including refusing a stale save, the fast in-memory adapter can be used in the many tests of the use cases, with confidence that the results carry over to the real one.

A team has a three-screen internal tool that reads and writes four tables with almost no rules. A new member proposes ports, adapters and use-case classes for all of it. What would you say?

That the structure protects business rules from technology, and there are almost none here to protect. It would add interfaces, mappings and files to every change for no benefit. Use the framework’s defaults with a thin data layer. If one part later grows real rules, give that part a domain model and ports, and leave the rest alone.
