The problem

The problem. Design an object storage service like Amazon S3. Users create buckets and put, get, list and delete objects of any size by key. Objects must not be lost.

described the service as its users see it. Building it raises questions the user never sees. An object of 10 KB and one of 5 TB must be stored by the same system. Every byte must survive disks, machines and whole racks failing, at a cost close to one copy rather than three. Listing a prefix and reading an object written a moment before must both be correct, at a scale where the list of objects alone is tens of terabytes. And a delete only marks space as free; something has to take it back.

Storing 100 PB as 6 + 3 takes 150 PB of disk, 7,500 disks, of which about 2 fail each week. Rebuilding a failed disk reads 120 TB from the others, and with 24 hours to rebuild, a given object is lost with a chance of 1 in 2.75 trillion a year from independent disk failures alone, beyond eleven nines.

Set the parity to 2 and the data pieces to 1 to see three copies: twice the disks, and fewer nines than 6 + 3 at every repair time. Step 6b explains the model behind the last line and checks it.

A listing is a range read on the metadata: start after the continuation key, return the next thousand keys of the prefix. A prefix with ten million keys takes ten thousand pages, each a cheap read on one shard, and a delimiter such as / lets the service return common prefixes, the “folders”, instead of every key beneath them. Partitioning the metadata by hash would spread load more evenly, but then listing cats/ would ask every shard. Partitioning by key range keeps a prefix together, at the price of hot ranges when many keys share one prefix, which the service handles by splitting busy ranges ().

Step 5: The design

The defining choice is to separate the data path from the metadata path. Bytes move between clients, front ends and storage nodes, through machines built for throughput. Facts about bytes, which key, which version, which pieces where, live in a smaller store built for consistency. A put writes the bytes first and the metadata last, so an object becomes visible in one atomic step, and a failure in between leaves only unreferenced bytes for the garbage collector.

Step 6a: Volumes and placement

Thirteen million objects on each disk rules out a file for each object: the file system’s own metadata would need several disk reads before the object’s first byte. Facebook’s Haystack, which stored over 260 billion photos in 2010, set the pattern most stores follow. Objects are appended to a few large volume files, and each storage node keeps the index of its volumes, object to offset and length, in memory, so that reading an object costs at most one disk operation.

Redundancy is then applied to volumes, not to objects. A stripe is a group of k data pieces and the m parity pieces computed from them, stored on k + m different disks, any k of which rebuild the data (). Small objects are appended to an open volume kept as three copies, where appends are cheap, and when the volume is full and sealed it is encoded as 6 + 3 stripes and the copies are dropped. Objects of a few megabytes and more are encoded as they arrive, as in .

A volume therefore has a life of its own. It is opened on three disks in three racks chosen by the placement service, takes appends until it reaches its size, perhaps a gigabyte, and is sealed. A background job encodes it into stripes on nine disks in nine racks, records the new locations in the volume’s metadata, and frees the copies, which takes it from three times its size on disk to one and a half. Objects do not move during any of this: their metadata names the volume and offset, and the volume’s own record says where the volume now lives.

Where the pieces go decides which failures they survive. The placement service chooses disks from the cluster map, and the rule that matters is one piece in each failure domain. The simulation placed 100,000 stripes on 12 racks of 10 disks and destroyed one rack.

At random, 0.040% of objects stored as three copies and 0.262% of those stored as 6 + 3 had more pieces in the destroyed rack than their code can lose. The wider code fared worse, because nine pieces over twelve racks often put four in one. Across 100 billion objects, 0.262% is 262 million objects lost to one rack fire. With one piece in each rack, a rack holds at most one piece of any object and nothing is lost. The same rule applies one level up: a service that must survive the loss of a data center spreads pieces across three or more of them.

Step 6b: How many nines

Durability claims are computed, not measured, because a loss rate of one object in a hundred billion a year cannot be observed directly. The usual figure is the mean time to data loss: the expected time until more pieces of one stripe have failed at once than its code can lose. The chapter’s model treats a stripe as a chain of states, zero, one, two failed pieces and so on: each healthy piece fails at the disk failure rate, each failed piece is rebuilt in the repair time, and the stripe is lost on reaching m + 1 failed pieces.

export function meanHoursToLoss(k: number, m: number, annualFailureRate: number, repairHours: number): number {
  const n = k + m;
  const fail = -Math.log(1 - annualFailureRate) / HOURS_A_YEAR; // per piece, per hour
  const repair = 1 / repairHours;
  let tau = 0, total = 0;
  for (let j = 0; j <= m; j++) {
    tau = (1 + j * repair * tau) / ((n - j) * fail);
    total += tau;
  }
  return total;
}

A model is only as good as its check. The chapter simulates 120 disks in 12 racks holding 5,000 stripes for 200 years, with disks failing at random and each failed disk replaced and refilled after a fixed time, at failure rates high enough to count losses: 50% a year with 14 days to repair. Three copies lost 0.00139 stripes a year each against 0.00134 from the model, and 6 + 3 lost 0.00517 against 0.00490. The model is close at those rates, so it can be trusted at real ones.

At Backblaze’s 1.36% and a day to rebuild a disk, three copies give 10.2 nines, 6 + 3 gives 12.4 and 10 + 4 gives 15.6, while storing 3, 1.5 and 1.4 times the data. Repair time matters as much as the code: cutting it from a day to six hours adds about two nines to 6 + 3. That is why the rebuild of a failed disk is spread over every disk that holds a piece of its stripes, and why wide codes cost network: rebuilding one piece of a 6 + 3 stripe reads six others, so a failed 20 TB disk means 120 TB read across the cluster against 20 TB for three copies.

The model leaves out what loses data in practice: failures that are not independent. A batch of disks that wear out together, a rack or a building lost at once, a bug in the repair code, and the operator who deletes the wrong prefix. Placement across failure domains answers the first two, checksums verified on every read and in background scrubbing answer silent corruption, and versioning answers the last.

Scrubbing has a cost that is easy to estimate. Reading all 150 PB once every two weeks is about 124 GB/s across the fleet, 16.5 MB/s for each of 7,500 disks, a small fraction of what a disk can read, but not free: it competes with client reads and is throttled when they are busy. A corrupt piece found by a scrub is repaired like a failed disk’s, before a second fault in the same stripe can make it matter.

Step 6c: Versions, deletes and garbage

With versioning on, nothing a client does destroys data at once. A put adds a version; a delete without a version id adds a delete marker, a version that says the key is deleted, so that a get answers 404 while every earlier version stays readable by its id. Removing the marker undeletes the object. Only a delete that names a version, or a lifecycle rule, removes data for good.

// Without a version id: with versioning, a delete marker becomes the current version; without, the key goes.
  // With a version id: that version is removed for good.
  delete(key: string, now: number, versionId?: string): { garbage: Version[] } {
    const versions = this.keys.get(key) ?? [];
    if (versionId) {
      const i = versions.findIndex((x) => x.versionId === versionId);
      if (i < 0) return { garbage: [] };
      const [gone] = versions.splice(i, 1);
      if (versions.length === 0) this.keys.delete(key);
      return { garbage: gone && !gone.deleteMarker ? [gone] : [] };
    }
    if (!this.versioning) {
      this.keys.delete(key);
      return { garbage: versions.filter((v) => !v.deleteMarker) };
    }
    return { garbage: this.add(key, { versionId: `v${++this.counter}`, deleteMarker: true, location: null, size: 0, at: now, noncurrentSince: null }, now).garbage };
  }

The test walks the cases: a delete frees no bytes, an old version stays readable, removing the marker brings the object back, and a lifecycle rule frees versions that have been noncurrent for more than 30 days. Freed versions become garbage in their volumes, and the bytes come back only when a volume is compacted: its live objects are copied into the open volume and the old one is released. The threshold for compacting is a trade between disk and rewriting, which the simulation measured over two years of puts and deletes with lifetimes of a day, a month and a year.

Compacting a volume once 10% of it is garbage held only 3% more disk than the live data, but wrote 3.7 times the bytes that clients put, because live objects were copied again and again. Waiting until 90% held 4.3 times the live data. Halfway, at 50%, held 1.5 times and wrote 1.5 times. For erasure-coded volumes, holding 1.5 times the live data on top of the code’s 1.5 is the same disk as three copies, so stores compact well before half a volume is garbage, and they compact the emptiest volumes first, which free the most space for the least copying.

At ten times the data, 75,000 disks fail about 20 times a week and the metadata reaches 500 TB in three copies: more shards and more automation, but no new component. At a hundred times, the cost of disk dominates everything, so cold data moves to wider codes and cheaper media by lifecycle rules, and the service spans several data centers in each region, with stripes spread across them so that losing one loses no object.

In the real world

  • Haystack, Facebook’s photo store, described in 2010: over 260 billion images and 20 PB, a billion new photos a week and over a million images served a second at peak. Many photos are stored in each large file, with the metadata small enough to keep in memory, so that a read needs at most one disk operation.
  • f4, its successor for warm data, described in 2014, held over 65 PB and lowered the effective replication factor of warm data, read far less often than new data, from 3.6 to 2.8 or 2.1 with erasure coding.
  • Backblaze reports the failure rates of its drives every year: 1.36% across about 344,000 drives in 2025, down from 1.55% in 2024. The calculator uses that figure.
  • Ceph computes where data goes with an algorithm, CRUSH, published in 2006, from a description of the cluster’s hierarchy of failure domains, rather than storing a location for every object.

Key points

  • Separate the data path from the metadata path: bytes in large append-only volumes, facts about them in a consistent, range-partitioned store.
  • Write the bytes first and commit the metadata last, so a new version appears in one step and failures leave only garbage.
  • Pack small objects into volumes with an in-memory index, and apply redundancy to volumes, as replicas while open and as erasure codes once sealed.
  • Place one piece of each stripe in each failure domain: at random, one rack lost took 0.262% of 6 + 3 objects in the simulation; with one piece a rack, none.
  • Durability is a model of failure rate, repair time and code: at a 1.36% failure rate and a day to repair, 3 copies give 10.2 nines and 6 + 3 gives 12.4 at half the disk.
  • Faster repair buys nines; wide codes buy disk and pay in repair traffic.
  • Versioning and delete markers protect against the losses the model does not cover, and compaction thresholds trade disk against rewriting.

Check yourself

Why are the data path and the metadata path separate?

They need different stores. Bytes need cheap, high-throughput capacity and never change once written. Metadata needs ordered keys for listing, consistency for read-after-write, and atomic updates to make a version visible. One store cannot be good at both at a hundred petabytes.

A put has stored all nine pieces when the front end crashes, before the metadata commit. What does a reader see?

The old version, or 404 for a new key. The object becomes visible only with the metadata commit. The nine pieces are unreferenced and the garbage collector removes them; the client retries the put.

Why do small objects go into large volumes instead of their own files?

With thirteen million objects on a disk, files would need several metadata reads before the first byte and waste space in small blocks. A volume with an in-memory index finds any object with one disk read.

At random placement, why did 6 + 3 lose more objects to one rack than three copies did?

Nine pieces over twelve racks put four or more in one rack more often than three copies put all three together, and four lost pieces exceed what 6 + 3 can lose. Spreading one piece to a rack removes the problem for both.

Why does a durability figure need a repair time?

Loss requires more failures than the code tolerates within one repair window. Halving the window makes overlapping failures far less likely: in the model, 6 + 3 goes from 12.4 nines with a day to rebuild to 14.2 with six hours.

Why does rebuilding a failed disk cost more network with 6 + 3 than with three copies?

A missing piece of a 6 + 3 stripe is computed from six others, so each byte rebuilt needs six read. With copies, one byte is read for each byte rebuilt: 20 TB against 120 TB for a 20 TB disk.

A user deletes a prefix by mistake in a versioned bucket. What can be recovered, and how?

Everything. Each delete added a marker and freed nothing. Removing the markers makes the previous versions current again, as long as a lifecycle rule has not yet expired those noncurrent versions.
