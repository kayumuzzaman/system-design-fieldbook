Why put a queue in the middle

When Ana uploads a photo to the photo app, several things have to happen. The photo must be stored. Thumbnails must be generated in three sizes. The search index must learn about it. Her followers must be notified. Only the first of these has to finish before Ana sees “uploaded”.

If the upload service calls the other services directly and waits for each, it inherits all of their problems.

  • Their latency. The user waits for the sum of every call.
  • Their failures. If the notification service is down, uploads fail, although nothing is wrong with storing photos.
  • Their capacity. A burst of uploads becomes an equal burst on every downstream service at the same instant.
  • Their existence. Adding a fifth thing that should happen on upload means changing and redeploying the upload service.

A message broker is a service that accepts messages from senders, stores them, and delivers them to receivers. With one in the middle, the upload service stores the photo, sends a message saying “photo 871 was uploaded”, and returns. The other services receive the message when they are ready.

This buys four things.

  • Independence in time. The sender and receiver do not need to be running at the same moment. If the thumbnail service is down for five minutes, its messages wait.
  • Load leveling. A burst fills the queue instead of overwhelming the receivers, which work through it at a steady rate.
  • Independent scaling. If thumbnails fall behind, add thumbnail workers. Nothing else changes.
  • Built-in retry. A message that could not be processed is delivered again, with no code in the sender.

And it costs four things.

  • No immediate result. The sender cannot say “and here are your thumbnails”. The work is done later, so the product must be designed around that ().
  • Duplicates. Retrying means the same message can arrive more than once. Receivers must be written to tolerate that.
  • Harder debugging. A request no longer has one stack trace. Its effects are spread over several services and several minutes.
  • One more system. The broker must be run, monitored and sized, and it is now on the critical path of everything that uses it.

The rule of thumb: if the caller needs the answer to continue, call directly. If the caller only needs the work to happen, send a message.

Queues and topics

Brokers offer two basic delivery patterns, and most real systems combine them.

A queue holds messages for one kind of consumer. Each message is delivered to one consumer, and several consumers reading the same queue share the work between them. This is how a pool of thumbnail workers divides up resize jobs.

A topic, in the pattern called publish-subscribe or pub/sub, delivers a copy of each message to every subscriber. The publisher does not know who the subscribers are or how many exist. This is how one “photo uploaded” message reaches thumbnails, search and notifications.

The standard arrangement puts the two together: publish to a topic, and give each subscribing service its own queue fed by that topic. Each service then gets every message, can run as many workers as it needs on its own queue, and falls behind or fails without affecting the others. On AWS this is an SNS topic delivering to SQS queues. In RabbitMQ it is an exchange bound to queues. In Google Pub/Sub it is a topic with several subscriptions.

A third model, the log, keeps messages after they are read and lets each consumer track its own position. It behaves differently enough to need its own chapter, . The differences in brief:

The life of a message

The central mechanism of a queue is how it decides that a message has been dealt with. The broker cannot see inside the consumer. It only knows what it is told.

  1. A consumer receives a message. The broker does not delete it. It hides it from other consumers for a period, called the visibility timeout in SQS and the acknowledgment deadline in Google Pub/Sub.
  2. The consumer does the work.
  3. The consumer sends an acknowledgment, or ack. The broker deletes the message.
  4. If no acknowledgment arrives before the timeout, because the consumer crashed, hung or was simply slow, the message becomes visible again and is delivered to another consumer.

This design means a message is never lost because a consumer died halfway. It also means the same message can be processed twice. The consumer may have finished the work and crashed before acknowledging, or may still be working when the timeout expires. The guarantee is at-least-once delivery, and the consequence, covered in , is that every consumer must be safe to run twice on the same message.

A queue fits in a page of code, and reading it makes the behavior concrete.

interface Message {
  id: string;
  body: T;
  receiveCount: number;      // how many times it has been handed out
  visibleAt: number;         // hidden from consumers until this time
}

class Queue {
  private messages: Message[] = [];
  readonly deadLetters: Message[] = [];

  constructor(private visibilityTimeoutMs = 30_000, private maxReceives = 5) {}

  send(id: string, body: T, delayMs = 0, now = Date.now()): void {
    this.messages.push({ id, body, receiveCount: 0, visibleAt: now + delayMs });
  }

  // Hand out the next visible message and hide it until the timeout passes.
  receive(now = Date.now()): Message | undefined {
    for (const m of [...this.messages]) {
      if (m.visibleAt > now) continue;                 // delayed, or in flight with another consumer
      if (m.receiveCount >= this.maxReceives) {        // tried too often: set it aside
        this.remove(m.id);
        this.deadLetters.push(m);
        continue;
      }
      m.receiveCount += 1;
      m.visibleAt = now + this.visibilityTimeoutMs;
      return m;
    }
    return undefined;
  }

  // The consumer finished. Only now is the message gone.
  ack(id: string): void {
    this.remove(id);
  }

  private remove(id: string): void {
    this.messages = this.messages.filter((m) => m.id !== id);
  }
}

Real brokers add durability, replication and scale, but receive and ack behave as they do here. Notice that “delayed” and “in flight” are the same mechanism: a time before which the message is not handed out.

The timeout has to be chosen with care. SQS defaults to 30 seconds and allows up to 12 hours. Pub/Sub defaults to 10 seconds and allows up to 10 minutes. Both let a consumer extend the deadline while it works.

Common mistake. A visibility timeout shorter than the work. If resizing a large video takes two minutes and the timeout is 30 seconds, the message reappears while the first worker is still busy. A second worker starts the same job, then a third. The queue appears to have a mysterious duplication problem, and the workers are overloaded with repeated work. Set the timeout well above the slowest normal processing time, and for long jobs have the worker extend it periodically while it is still making progress.

Routing and filtering

Not every subscriber wants every message. Brokers offer ways to select.

MechanismHow it selectsExample

Filtering in the consumerReceive everything and discard what is not wantedSimple, and wasteful when most messages are discarded

Filtering in the broker saves the cost of delivering messages that would be thrown away. Keep the rules simple. Routing logic that lives in broker configuration is invisible to anyone reading the code, and a subscription that silently matches nothing is a hard bug to find.

Ordering

It is natural to assume a queue delivers messages in the order they were sent. With more than one consumer, it does not, and cannot.

Suppose two messages concern the same photo: “caption changed to Sunset” and then “caption changed to Sunrise”. Two workers each take one. The second worker happens to finish first. The caption ends up as “Sunset”, which is wrong. Retries reorder in the same way: a message that fails and is redelivered arrives after messages that were sent later.

There are three ways to deal with this, in rising order of cost.

  1. Make order irrelevant. Put a version number or timestamp from the source in each message, and have the consumer ignore any message older than what it has already applied (). This works with any broker and any number of consumers, and it is the most durable solution.
  2. Order within a key. Give each message a key, such as the photo ID. The broker guarantees that messages with the same key are delivered in order, to one consumer at a time, while different keys are processed in parallel. SQS FIFO queues call this a message group, and Pub/Sub an ordering key. A log does it with partitions.
  3. One consumer. A single consumer processing one message at a time sees them in order. Throughput is limited to what that one consumer can do.

Total order across all messages is almost never needed. What matters is the order of events for one photo, one user or one account. Ask which it is before paying for ordering.

Ordering has a side effect to plan for. If the message at the head of a group cannot be processed, everything behind it in that group waits. This head-of-line blocking is the correct behavior, since skipping ahead would break the order, and it means a single bad message can stall one customer’s work indefinitely unless something removes it.

Retries, poison messages and dead-letter queues

Consumers fail for two different kinds of reason, and they call for opposite responses.

  • Transient failures. A dependency timed out or a database was briefly unavailable. Trying again later will probably work.
  • Permanent failures. The message is malformed, refers to something that does not exist, or triggers a bug. Trying again will fail forever. Such a message is called a poison message.

Redelivery handles the first kind automatically. Left alone, it turns the second kind into an endless loop: the poison message is delivered, fails, becomes visible, and is delivered again, consuming a worker each time.

The standard protection is a limit on deliveries. The broker counts how many times each message has been received. Past the limit, it moves the message to a separate dead-letter queue, where it no longer blocks anything and waits for a person to look at it. Pub/Sub allows between 5 and 100 attempts and defaults to 5. In SQS you choose the number.

A dead-letter queue is only useful if somebody watches it.

  • Alert when it is not empty. Each message in it is work that did not happen.
  • Keep the reason. Log the error with the message ID, so that the cause can be found without reproducing it.
  • Be able to redrive. After fixing the bug, move the messages back to the main queue. Without this the queue is only a place where failures are stored.

Between the first failure and the dead-letter queue, retries should be spaced out. Retrying at once hits a struggling dependency again while it is still struggling. Waiting a second, then several, then a minute gives it time to recover. Brokers support this in different ways: Pub/Sub has a retry policy with exponential backoff, SQS lets the consumer set a longer visibility timeout on a failed message, and RabbitMQ 4.3, released in April 2026, added delayed retries inside its quorum queues. covers backoff and jitter.

In production. Decide in the consumer which errors are worth retrying. A validation error will never succeed, so send that message straight to the dead-letter queue instead of burning five attempts. A timeout should be retried. Treating all errors alike either wastes capacity on hopeless messages or gives up too early on recoverable ones.

Delays, schedules, expiry and priority

Delayed delivery. A message can be sent now and delivered later: “check in ten minutes whether the payment completed”. SQS supports delays of up to 15 minutes, and other brokers have similar features. Inside the broker a delayed message is stored with its due time and becomes visible when that time arrives, exactly as in the miniature queue above. For delays of hours or days, or for jobs that recur, use a scheduler ().

Expiry. Some messages lose their value with time. A “your driver is two minutes away” notification is worthless after ten minutes. A time-to-live on the message lets the broker discard it instead of delivering it late. Queues also have an overall retention limit: SQS keeps a message for 4 days by default and at most 14.

Priority. It is tempting to give urgent messages a higher priority in one queue. Brokers that support this deliver higher priorities first, and the danger is starvation: under sustained load, low-priority messages never get their turn. The simpler and more predictable design is a separate queue for each priority, each with its own workers, so that the urgent queue has guaranteed capacity and the bulk queue still makes progress.

Backlog and backpressure

A queue absorbs a burst by letting messages wait. That only works if, averaged over time, consumers process faster than producers send. The arithmetic is the queueing of again.

The consumers can process 1,000 messages a second and 800 arrive, so the queue shrinks by 200 a second and the backlog of 500 thousand clears in 41.7 min. At 80% utilization there is little room for a burst: 46 consumers would bring it down to 70%.

Two measurements tell you how a queue is doing, and one of them matters more.

  • Depth: how many messages are waiting. Easy to measure, hard to interpret. Ten thousand waiting messages is trivial for a queue that processes fifty thousand a second and a disaster for one that processes ten.
  • Age of the oldest message: how long the message at the front has waited. This is what users experience, and it is the number to alert on. “Thumbnails are 40 minutes behind” needs no interpretation.

If arrivals exceed capacity for long enough, something must give. A queue with no limit hides the problem while making it worse: messages wait for hours, the work is stale by the time it is done, and the queue eventually exhausts memory or disk. The honest responses are these.

  • Add consumers. Scale them automatically on the age of the oldest message or on backlog per consumer. Check that the next thing down, usually a database, can take the extra load.
  • Push back. Give the queue a maximum size and refuse new messages when it is full, so that producers slow down or fail fast. This is backpressure: the overload is reported upstream, where something can be done about it, instead of accumulating silently.
  • Shed load. Drop or sample what matters least. For data that goes stale, drop the oldest first.
  • Limit how much each consumer takes. A consumer that pulls a thousand messages into memory and then crashes sends a thousand messages back for redelivery. RabbitMQ’s prefetch count and similar settings cap the number of unacknowledged messages a consumer may hold.

When the buffer is the thing that fails

On 14 November 2024 Cloudflare lost about 55% of the logs it would normally have delivered to customers over a period of roughly three and a half hours. The pipeline that delivers those logs keeps a separate buffer for every customer log job, ordinarily more than a million of them.

A configuration change produced an empty configuration for the service at the front of the pipeline. The change was reverted within five minutes. But that service had an old safety behavior: when its configuration was missing, it failed open and forwarded logs for all customers, not only those with jobs configured. The buffering system downstream began creating a buffer for each of them, about forty times the usual number. It became unresponsive and had to be fully reset.

The buffering system did have a mechanism to protect itself against this kind of overload. According to Cloudflare’s own account, it had not been configured. Three lessons generalize.

  • A buffer needs a limit, and the limit must be switched on and tested. Protection that exists but is not configured is not protection.
  • Failing open multiplies load. A fallback that does more work than the normal path will be exercised at the worst moment.
  • Test overload on purpose. Cloudflare’s follow-up included regular overload tests, alongside the failure tests it already ran.

Durability, and sending reliably

A message accepted by the broker should survive the broker crashing. That depends on settings you choose.

  • Persistence. Messages kept only in memory are fast and are lost on restart. Durable queues write them to disk.
  • Replication. One broker with a disk is a single point of failure. Managed services replicate across availability zones for you. RabbitMQ’s quorum queues replicate each queue with Raft ().
  • Confirmation to the sender. A send can fail in transit. Use the acknowledgment the broker returns, called a publisher confirm in RabbitMQ, and retry until it arrives. A sender that does not wait for it will lose messages without knowing.

Retrying a send can itself create a duplicate, if the first attempt succeeded and only its confirmation was lost. So duplicates enter from both ends, and consumer-side idempotency covers both.

The hardest reliability problem lies just before the broker. The upload service must save the photo’s row in its database and send the message. If it saves and then crashes, no message is sent and no thumbnails are ever made. If it sends first and the save fails, consumers act on a photo that does not exist. The two systems cannot be updated in one transaction. The solution is the transactional outbox of : write the message into a table in the same database transaction as the row, and have a separate process forward it to the broker.

Designing the message

A message is an interface, and it outlives the code that first sent it. Messages sent today may be read next week by a consumer deployed tomorrow.

  • Identify it. Include a unique message ID for deduplication, the time the thing happened, and the ID of the request that caused it so that the flow can be traced across services ().
  • Name the type and version. A consumer must be able to tell what it is looking at without guessing.
  • Evolve compatibly. Add optional fields. Do not remove or rename fields, or change their meaning, while any consumer still reads them. The rules are those of API versioning in , with the difference that you cannot see who the clients are.
  • Keep it small. Brokers limit message size: 1 MiB in SQS. Large messages also slow everything down. For a large payload, store it in object storage and send a reference to it. This is called the claim check pattern, after the ticket you receive for a coat.
  • Include what consumers need, and no secrets. A message that only says “photo 871 changed” forces every consumer to call back for details. One that carries the relevant fields does not. weighs the two.

In an interview. When you add a queue to a design, say three things without being asked: what the delivery guarantee is (“at least once, so the consumer deduplicates on message ID”), what happens to messages that keep failing (“a dead-letter queue with an alert”), and what you watch (“age of the oldest message”). Those three sentences separate someone who has drawn a queue from someone who has run one.

Key points

  • A broker lets a service hand off work and move on. It trades an immediate answer for independence from the receiver’s speed, failures and capacity.
  • A queue shares messages among identical workers. A topic copies each message to every subscriber. The usual design is a topic feeding one queue per subscribing service.
  • A message is deleted only when acknowledged. Anything else leads to redelivery, so delivery is at least once and consumers must tolerate duplicates.
  • With several consumers there is no global order. Use versions in messages, or ordering by key.
  • Limit deliveries and send repeated failures to a dead-letter queue that someone is alerted about and can redrive.
  • A queue only absorbs bursts. Sustained overload needs more consumers, backpressure or load shedding. Watch the age of the oldest message.
  • Buffers need limits that are configured and tested.
  • Saving data and sending a message about it cannot be made atomic directly. Use an outbox.

Check yourself

A consumer processes a payment message, charges the card, and crashes before acknowledging. What happens next, and what must the design include?

The visibility timeout expires and the broker delivers the message again, to this consumer or another. Without protection the card is charged twice. The consumer must be idempotent: for example it records the message ID in the same transaction as the charge record and skips messages it has already handled, and it passes an idempotency key to the payment provider.

Thumbnails, search indexing and notifications must all react to each upload. Why is one queue read by all three services the wrong design?

A queue delivers each message to one consumer, so each upload would reach only one of the three services. Each needs its own copy. Publish to a topic and give every service its own queue subscribed to it. Each service can then scale, fail and fall behind independently.

A queue receives 500 messages a second. Each takes 100 ms to process. How many consumers are needed, and why is the bare minimum a bad choice?

One consumer handles 10 a second, so 50 consumers exactly match the arrival rate. At 100% utilization any burst creates a backlog that never clears, and normal variation makes the queue grow without bound. Around 70% utilization, about 72 consumers, leaves room to absorb bursts and drain backlogs.

Two messages about the same order are processed out of order by two workers. Name two ways to prevent the wrong outcome and the cost of each.

Carry a version or sequence number in each message and have the consumer ignore anything older than what it has applied. This costs a stored version per entity and works with any broker. Or use ordering by key, so that messages for one order go to one consumer in sequence. This costs some throughput and means a failing message blocks later ones for that order.

What is a poison message, and why does a retry policy alone not handle it?

A message that can never be processed successfully, because it is malformed or triggers a bug. Retrying it fails every time, so it is redelivered forever, wasting capacity and, in an ordered group, blocking everything behind it. A limit on deliveries with a dead-letter queue removes it from the flow so that someone can inspect it.

Your alert fires when queue depth exceeds 10,000. Why is that a weak alert, and what is better?

Depth has no meaning without the processing rate. Ten thousand messages may be half a second of work or a day of it, and the threshold goes stale as traffic grows. Alert on the age of the oldest message, which measures the delay users experience and stays meaningful at any scale.

In the Cloudflare incident of November 2024, the faulty configuration was reverted within five minutes. Why did the outage last hours?

The empty configuration triggered a fail-open behavior that forwarded logs for all customers, and the buffering system tried to create about forty times its normal number of buffers. It became unresponsive and needed a full reset, which took hours. Its overload protection existed but had not been configured. The trigger was brief, and the overloaded buffer was the outage.
