The problem

The problem. Design the leaderboard of an online game. Players earn points for each match they finish. The game shows the top 10 players of the month, each player’s own rank with the five players above and below, and updates both within a second of a match ending. Boards start again every month, and past months stay viewable.

A leaderboard is a list of players ordered by score, where any player can ask for their position. The top of the list is a cheap query in any database. The position of one player in the middle is not, because it is defined by how many players have more points, and the obvious way to know that is to count them. With fifty million players and thousands of score changes a second, the design needs an index that answers “how many are ahead of me?” without counting. In the terms of , this is a ranking problem: the rank of one player among millions, updated with every score.

Scores come only from game servers, which know the result of the match; a player’s app never reports its own points, which removes the easiest kind of cheating. The match id makes the write idempotent (): a game server that times out and sends the result again gets the same answer, and the points count once. The board is addressed by month, so “this month” is a name the server resolves, and last month’s board is the same API with another name. Ranks are counted from 1 in the API, though the store counts from 0.

Step 5: The design

Writes. A score service receives match results from game servers. In one database transaction it inserts the match, which fails harmlessly if the id is already there, and adds the points to each player’s monthly total. Then it writes each new total into the month’s sorted set. It writes the total, not the increment, and only if it is higher than what the set holds, which the next deep dives show is what makes retries safe.

Reads. A stateless leaderboard service answers board views with three commands on the sorted set, usually on its replica: the top ten, the player’s rank, and the range around it. Names come from a profile cache, since a board shows the same few thousand top players to everyone.

Housekeeping. A reconciliation job compares the sorted set with the database totals every hour and repairs differences (). At the start of a month the service writes to a new key. A week later an archive job saves the old board’s final ranks and deletes the key.

Step 6a: A rank without counting

Start with the relational version, since many games begin there. A table of players with an index on the score answers the top ten by reading the first ten index entries, and the players around someone by reading five entries on each side. A rank is the problem:

SELECT count(*) + 1 FROM scores WHERE score > $1;   -- $1: the player's own score

The index gives the order, but a B-tree does not record how many entries lie before a given one (), so the database walks every entry above the player and counts. The chapter ran this on PostgreSQL 16 with a million players and an index on the score. The top ten took 0.08 ms and a player’s neighbors 0.14 ms. The rank took 0.05 ms for the 10th player, 1.5 ms for the 10,000th, 14 ms for the 100,000th and 78 ms for the 999,000th: proportional to the rank. A window function, rank() OVER (ORDER BY score DESC), ranks everyone to find one player, and took 912 ms.

There is a relational design that works, with a different promise: compute every rank in one pass every few minutes into a table keyed by player. Rebuilding that table for a million players took 1.9 seconds, and reading a rank from it 0.05 ms. At fifty million players the rebuild would take on the order of a hundred seconds by the same rate, so ranks would be a few minutes old. For a game that shows ranks on a profile page, that is a fine design. For one that shows a new rank at the end of every match, it is not.

The structure that answers ranks directly is a sorted set: a collection of unique members, each with a numeric score, kept in score order so that a member’s position, its score and the members at any range of positions can all be found in logarithmic time. Redis documents its sorted sets as a hash table, from member to score, beside a skip list ordered by score; adding a member costs O(log n), and so does finding its rank.

A skip list is a sorted linked list with extra levels: every node is in the bottom list, about a quarter of them also in the list above, a quarter of those in the one above that, and so on, chosen at random as nodes are inserted. A search runs along the top level until the next step would go too far, drops a level and continues, and so skips most of the list. The detail that turns it into a rank index is that each pointer records how many nodes it jumps, its span. Adding up the spans on the way down gives the position without visiting the nodes skipped.

// ZREVRANK: 0 for the highest score.
  revRank(member: string): number | undefined {
    const score = this.scores.get(member);
    if (score === undefined) return undefined;
    this.steps = 0;
    let rank = 0;
    let x = this.head;
    for (let i = this.level - 1; i >= 0; i -= 1) {
      for (let n = x.next[i]; n && !before(member, score, n); n = x.next[i]) {
        rank += x.span[i] as number;
        x = n;
        this.steps += 1;
      }
      if (x.member === member && x !== this.head) return this.count - rank;
    }
    return undefined;
  }

The chapter’s skip list matched a plain sorted list on 20,000 random operations, including ranks, ranges and counts. Finding a rank took 11.6 steps on average among 1,000 players, 19.3 among 10,000 and 23.4 among 100,000, where counting would take 500, 5,000 and 50,000. Insertion keeps the spans right by adding one to every pointer that passes over the new node, which costs the same as the search.

On a real Redis 7.0, with a million members, the board used 109 bytes per member, including the hash table and the skip list. A rank took 57 microseconds from a client on the same machine, of which a plain PING took 35: the command itself is a small part of a round trip. One client sending score updates in batches of 100 reached about 90,000 a second, fifteen times the estimate’s peak. These are one run on one machine, and they say that the estimates fit one node with room to spare.

Step 6b: Ties, retries and months

A sorted set orders by one number. Equal scores are ordered by member name, which Redis documents, and the reverse commands that leaderboards use reverse that too. The test gave Carol, Alice and Bob 500 points each, reached in that order: by points alone they ranked Carol, Bob, Alice, on the chapter’s skip list and on Redis alike. Nobody would accept losing a tie because of their name.

export const SLOT = 2 ** 22;

export function packed(points: number, secondsIntoMonth: number): number {
  if (!Number.isInteger(points) || points < 0 || points >= 2 ** 31) throw new RangeError("points out of range");
  if (!Number.isInteger(secondsIntoMonth) || secondsIntoMonth < 0 || secondsIntoMonth >= SLOT) throw new RangeError("time out of range");
  return points * SLOT + (SLOT - 1 - secondsIntoMonth);
}

Packing the time into the low bits fixes the order: more points first, and for equal points the earlier time, because the packed value subtracts it. A double holds every integer up to 253 exactly, which Redis also documents for scores, and 31 bits of points with 22 bits of time fit in that. With packed scores the test ranked Carol, Alice, Bob. A game that prefers shared ranks, “1, 2, 2, 4”, keeps points alone as the score and computes a rank as one plus the number of players with strictly more points, which a sorted set also counts in logarithmic time.

Retries are the other trap. Incrementing the set for each match (ZINCRBY) counts a match twice if the request is retried after a timeout, and nothing in the set can tell. The test delivered 50,000 matches with 5% sent twice and some pairs out of order: incrementing left 1,567 of 4,665 players with the wrong score. Writing the total from the database instead, where the match id is unique, with ZADD GT, which only raises a score, left none wrong. A monthly total only grows, so the highest total is the newest, and a late or repeated write cannot lower it ().

Months are keys. The score service writes to board:2026-10 during October and to a new, empty key from the first second of November in the board’s time zone; nothing is reset or deleted at midnight. A game with daily, weekly and monthly boards writes each total to three keys, and keeps a separate total for each in the database.

Step 6c: When one machine is not enough

A board outgrows one node when its memory does, at about ten times the estimate, or when players in several regions each need a nearby copy. Splitting a sorted set is splitting an index whose main question, the rank, involves all of it (). There are two ways to cut it.

By a hash of the player. Every shard holds an even share of the players, and a score update touches one shard. The top ten is the top ten of each shard, merged: one call per shard, a scatter-gather (). A rank is the sum, over all shards, of how many players there score higher than this one: in the test with eight shards, nine calls per rank, one to find the player’s score and one count per shard. The answers equaled one big board’s on 923 random players. The cost is that every rank waits for the slowest of all shards ().

By score range. Shard 1 holds the lowest scores and shard 8 the highest. A rank is the player’s position in their own shard plus the sizes of the shards above, and the top ten lives in one shard. But scores are not spread evenly, and they move.

With eight equal ranges of points, 45,842 of 46,276 players sat in the bottom shard at the end of the month in the test, because few players score high. Ranges chosen from last month’s results, an eighth of the players each, balanced at the end of the month but not at mid-month, when the bottom shard held 1.8 times its share, since everyone starts each month at zero. And 30.8% of all updates moved a player from one shard to the next, a delete and an insert on two machines. Range sharding fits boards whose distribution is stable, and costs a rebalancing job.

The practical answer for the largest boards is to stop ranking everyone exactly. Exact positions matter to the players near the top. Keep a sorted set of only the players above some threshold, say the top hundred thousand, and tell everyone else their percentile. A histogram of points in buckets that grow by 6% each, updated with every score, did this in the test with an average error of 0.37 percentage points and at most 1.12, for a structure of 200 counters: “top 23%” costs nothing to compute and nobody checks it to the decimal place ().

Key-value databases meet the same problem in another form. DynamoDB’s documentation uses a leaderboard to introduce global secondary indexes: an index keyed by game title and sorted by top score returns the top scorers of a game. Every write for that game lands on one partition key, so busy games need write sharding, adding a suffix such as 1 to 200 to the key and merging the results of one query per suffix when reading, which is the hash design above.

At ten times the players, the board needs about 55 GB, and the choice is between a larger node, hash shards with scatter-gather for ranks, or an exact top board with percentiles below it. At a hundred times, only the last remains reasonable. Writes grow with matches, not players, and a few tens of thousands a second still fit a handful of nodes. Regional boards, one per region, are often what the game wanted in the first place, and they divide the problem by itself.

In the real world

  • Redis’s documentation (as of October 2026) describes sorted sets as a skip list and a hash table, with O(log n) insertion and rank; names leaderboards as their first use; orders equal scores lexicographically; and states that scores are 64-bit floating point numbers that represent integers exactly between −253 and 253.
  • Google Play Games Services (documentation updated 8 October 2026) creates daily, weekly and all-time versions of every leaderboard automatically. Daily boards reset at UTC−7 all year, weekly ones between Saturday and Sunday, and a submitted score replaces a player’s entry only if it is better.
  • Amazon DynamoDB’s documentation (as of October 2026) uses a game-scores table with an index on game title and top score as its example of a global secondary index, notes that such indexes are updated asynchronously, usually within a fraction of a second, and describes write sharding with key suffixes and merged reads.

In an interview. Show why the database alone struggles: the top ten is an index read, a rank is a count. Then introduce the sorted set and explain the skip list with spans in a sentence. Spend the rest on what makes it correct: packed scores for ties, totals with ZADD GT for retries, the database as the record and the set as an index you can rebuild. Finish with sharding only if asked, and propose percentiles for the long tail.

Key points

  • The top of a board is an index read; a rank is a count, which a B-tree must do by walking every entry above.
  • A sorted set keeps a hash map and a skip list whose pointers record their spans, so a rank takes about log n steps.
  • Keep matches and totals in a database and treat the sorted set as an index over them that can be rebuilt.
  • Pack points and time into one exact number so that ties go to whoever got there first.
  • Write totals with ZADD GT, not increments, so retries and reordering cannot corrupt the board.
  • A new key per period replaces any reset job.
  • Past one machine: hash shards cost a call to every shard per rank; score ranges skew and move; exact ranks for the top with percentiles below often serves players best.

Check yourself

Why is the top ten fast in a relational database but a rank slow, with the same index?

The top ten reads the first ten entries of the index in order. A rank needs the number of entries before the player’s, and a B-tree does not store counts, so the database walks and counts them all; the cost grows with the rank.

What does a span in a skip list record, and why does that make rank cheap?

How many nodes the pointer jumps over. Summing the spans of the pointers followed during a search gives the member’s position directly, so the search visits about log n nodes rather than every node before the member.

Ana and Ben both have 700 points; Ana got there first. With points as the score, who ranks higher in ZREVRANGE, and how do you fix it?

Ben, because equal scores are ordered by member name and the reverse command reverses that. Pack the time into the score, subtracting it so that earlier is higher: points × 222 + (222 − 1 − seconds into the month).

A game server times out and resends a match result. Walk through why the board stays right.

The database refuses the second insert of the same match id, so the total does not change. The service reads the same total and writes it with ZADD GT, which changes nothing because the set already holds it. With ZINCRBY, the points would have been added twice.

Why might ranges taken from last month’s final scores still leave shards unbalanced?

Every player starts the month at zero, so early in the month nearly everyone is in the lowest ranges and the top shards are almost empty. The ranges fit only the end of the month, and players keep crossing them as they score.

With eight shards by hash, how many calls does one player’s rank take, and why?

Nine: one to the player’s own shard for their score, then one to every shard to count the players with a higher score there. The rank is the sum of the eight counts.

Fifty million players, but only the top few thousand care about their exact position. What design follows?

An exact sorted set for players above a threshold, and a histogram of points for everyone, which gives a percentile such as “top 23%” in constant time and small memory. In the test, a 200-bucket histogram was within 0.37 percentage points on average.
