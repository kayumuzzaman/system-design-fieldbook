The problem

The problem. Design a notification service. Other services ask it to tell a user something: a login code, an order update, a new follower, a weekly offer. It delivers by push notification, email or SMS, as the user prefers, and the marketing team can send a campaign to millions of users at once.

The service does not deliver anything itself. It hands each notification to a provider, such as Apple’s or Google’s push service, an SMS gateway or an email service, and those providers are best effort, rate limited and sometimes down. Between the requesting service and the provider sit several layers, each of which may retry, so the same notification can arrive twice. And the traffic is lumpy: a campaign of 50 million lands at once, while a login code queued behind it is useless after a few minutes. gave the rule for push, treat it as a tap on the shoulder, and this chapter builds the service around it. The method of takes these in order.

  • Retries. The idempotency key is chosen by the caller from the event that caused the notification, such as the order’s shipping event. A repeated request with the same key returns the first answer and sends nothing ().

  • Errors. 400 for an unknown template or missing data, 404 for an unknown user, 429 for a caller over its quota (). Results from providers come back by webhook, signed and checked ().

Step 5: The design

The API does two things before answering: it claims the idempotency key and appends the request to a durable log. Everything else is routers and senders reading queues. The routers decide: is this category allowed on this channel for this user, is it quiet hours where the user is, has the user reached today’s cap for this category, and in which language should the template be rendered. A frequency cap is a limit on how many notifications of a kind one user receives in a period, such as three marketing notifications a day. Quiet hours are the hours in the user’s own time zone during which only critical notifications are sent; others wait in a delayed queue until the morning (). Checking these when sending, not when the request arrived, means a user who opts out at 9:00 receives nothing queued at 8:59.

A transactional notification is one caused by the user’s own activity or account, such as a code or a receipt, as opposed to a marketing notification sent to many users at once. The two differ in urgency, in what may be sent twice and in the law: in many countries marketing needs consent and an easy unsubscribe. So the router gives each notification a priority from its category, and every channel has a queue per priority.

The flows show two kinds of protection. A collapse key is an identifier sent with a notification so that a device, or the provider holding notifications for it, shows only one of several notifications that carry it; APNs calls it apns-collapse-id and FCM collapse_key. The idempotency key stops a request that has already been accepted, before any work. The collapse key stops a send that may already have reached the phone, after the provider may have acted.

Step 6a: Duplicates, and what removes them

Exactly-once delivery is not on offer (), and a notification crosses several layers that each deliver at least once. The simulation sent a million notifications through a pipeline with typical faults: 2% of producers call again because an answer was lost, the log hands 0.5% of messages to a second worker, the provider fails 3% of calls outright and leaves 1% unanswered, having sent half of those, and one worker in 2,000 dies after the provider accepted a notification but before recording it.

Sending once loses 3.4% and still duplicates, because upstream copies are sent too. Retries remove the losses and add duplicates. The idempotency key removes the upstream copies, the most common kind, which brings duplicates from 30,902 to 5,700 per million. What remains comes after the provider may have acted: a call with no answer, and a worker that died before recording success. The key cannot help there, because it records only that someone started.

export class DedupStore {
  private readonly keys = new Map();
  // Atomic "set if absent", as in Redis SET NX or a conditional write: true if this caller claimed the key.
  claim(key: string): boolean {
    if (this.keys.has(key)) return false;
    this.keys.set(key, 'sending');
    return true;
  }
  state(key: string): KeyState | undefined {
    return this.keys.get(key);
  }
  markSent(key: string): void {
    this.keys.set(key, 'sent');
  }
}

When the outcome is unknown, the sender has to choose what to risk, and the right choice depends on the notification. A login code is retried: a second code is harmless, a missing one locks the user out. A marketing email is not: in the simulation that choice lost 5,136 per million and duplicated none. A push is retried with a collapse key, which makes the second copy replace the first, so the simulation shows none lost and none visible twice. That is the policy step 1 asked for. Where an email or SMS provider accepts a request id of its own and ignores a repeat, it plays the part of the collapse key, and the choice disappears.

Step 6b: Priorities and campaigns

A campaign is millions of notifications created at once. If they enter the same queue as everything else, everything else waits. The simulation gave the senders 5,000 calls a second, 2,000 notifications a second of everyday traffic, 5% of them critical, and then queued a campaign of 2 million.

With one queue, critical notifications created after the campaign waited a median of 221 seconds and up to 400, long after a login code expires. With a queue per priority, served strictly in order, they waited less than a tenth of a second, and so did the normal ones; the campaign used what was left and finished after 628 seconds instead of 400. Separate queues are a bulkhead (). Two rules complete it: campaigns are also throttled to a rate the providers accept, and they are spread over the user’s daytime, which quiet hours require anyway.

The campaign itself is a fan-out, like a post to millions of followers (). A campaign service reads the segment in pages of a few thousand users and turns each page into requests with keys made from the campaign and the user, so that a restarted campaign does not send twice. It releases pages at the campaign’s rate with a token bucket (): 50 million users at 20,000 a second is the 42 minutes of step 2. Each user’s preferences and quiet hours are checked as their notification is routed, so a user in a time zone where it is night is held until morning, and the campaign becomes a wave that follows daylight around the world. Starting slowly, with a small share of the segment first, lets a mistake in the template or the segment be caught before it reaches everyone.

Caps and digests are the same idea seen from the user. Low-priority notifications of one category within an hour can be merged into one (“5 people liked your photo”), which also cuts the volume.

Step 6c: When a provider fails

Providers fail in their own ways: a push service throttles, an SMS gateway goes down, an email service rejects a burst. The simulation took the provider down for 60 seconds while 2,000 notifications a second kept arriving, with up to 10 attempts per notification, and compared four ways of retrying.

PolicyCalls to the failing providerNotifications lostNormal notifications, 99th percentile
Retry at once300,5008,52968.7 s
Retry after 1 s296,4017,11269.6 s
Backoff with jitter298,52218779.9 s
Backoff and a circuit breaker187059.3 s

Retrying at once or after a fixed second spends the attempts during the outage: thousands of notifications ran out of attempts and were lost. Backoff with jitter spreads the attempts over minutes and loses few, but the senders still call the dead provider as fast as they can, because new notifications keep failing. A circuit breaker () stops calling once most calls fail, tests with a single call every 5 seconds, and leaves the notifications in their queues with their attempts unspent. It made 187 calls during the outage and lost nothing. In every case the backlog cleared 37 to 40 seconds after the provider recovered, because the senders then work at full speed on a queue that is already ordered by priority.

Three more rules follow from the providers’ own behavior. A notification past its expiry is dropped, not sent late: a code from ten minutes ago is noise. For SMS, a second provider takes over when the breaker for the first stays open. And a response that says a device token is no longer valid, 410 from APNs, removes the token, so the system stops paying for sends that cannot arrive.

The signals that show these failures early are few: the age of the oldest item in each priority’s queue, each provider’s error rate and breaker state, the share of requests stopped by the dedup store, and the rate at which tokens are found dead. A sudden rise in dedup hits means a producer is retrying hard; a rise in dead tokens after an app release means registration is broken ().

At ten times the volume, 580,000 notifications a second at peak, the routers and senders grow with their queues, and the dedup store holds a terabyte of keys, partitioned. The providers’ limits become the constraint: more connections to APNs, more sender accounts, campaigns spread over longer windows. At a hundred times, which only a few companies reach, each region runs its own pipeline for its own users, and the providers’ own regional endpoints are used.

In the real world

  • APNs. Apple’s documentation, checked in October 2026, calls APNs a best-effort service that may reorder notifications. A provider connects over HTTP/2 with TLS 1.2 or later, and a payload may be up to 4 KB. If a device is offline, APNs stores the notification for up to 30 days depending on apns-expiration, but only one per app: usually the latest. apns-collapse-id merges notifications that carry the same value. A 410 answer means the device token is no longer active; Apple’s guide says not to retry such answers, and that answers in the 500s may be retried after 15 minutes, with back-off.
  • FCM. Google’s documentation, checked in October 2026, says a collapsible message may be replaced by a newer one not yet delivered, with at most four collapse keys per device at a time. Up to 100 non-collapsible messages are stored for an offline device; beyond that all are discarded and the app is told. A message lives up to 28 days, the default, and a data payload is at most 4 KB.
  • LinkedIn, 2018. LinkedIn described Air Traffic Controller, a service built on Samza and Kafka that decides for each of over a billion requests a day whether to notify, through which channel and when, with deduplication, aggregation and rate limits. LinkedIn reported that member complaints were cut in half, and that the 90th percentile latency of push notifications for messages between members fell from about 12 seconds to about 1.5.

Key points

  • Accept, record and answer; route and send later, from queues.
  • Duplicates come from upstream copies, from crashes after a send, and from calls with no answer. An idempotency key removes only the first kind.
  • When the outcome is unknown, choose per category: retry codes, do not retry offers, and give pushes a collapse key.
  • A queue per channel and priority keeps a campaign from delaying a login code by minutes.
  • Back off with jitter, and open a circuit breaker when a provider is down, so attempts are not spent and nothing is lost.
  • Check preferences, quiet hours and caps when sending; drop what has expired.

Check yourself

The order service times out calling the notification API and calls again. How does the design avoid two notifications?

Both calls carry the same idempotency key, derived from the order’s event. The first claims the key with an atomic set-if-absent; the second finds it claimed and gets the first answer without sending anything.

With retries and an idempotency key, the simulation still showed 5,700 duplicates per million. Where do they come from?

From calls to the provider that got no answer although the provider had sent, and from workers that died after the provider accepted but before recording it. Both happen after the provider acted, which the key cannot see.

Should a sender retry a login code whose call timed out? A marketing email?

The code, yes: a duplicate code is harmless and a missing one blocks the user. The email, no: a missed offer costs little and a duplicate annoys. In the simulation, not retrying when unsure gave no duplicates and lost about 0.5%.

How does a collapse key make a retried push safe?

Both copies carry the same collapse key, so the device, or the provider before delivery, keeps one of them. The user sees one notification even if both were sent.

A 2-million campaign is queued. Why do critical notifications not wait?

Each priority has its own queue and senders serve critical, then normal, then bulk. The campaign gets only the capacity left over; in the simulation critical notifications waited under 0.1 s instead of up to 400 s.

Why did immediate retries lose notifications during a one-minute outage?

Each failed notification went straight back and failed again, using up its 10 attempts within the outage. Backoff spreads the attempts over minutes, and a circuit breaker stops calling altogether, so the attempts are still there when the provider recovers.

A user opts out of marketing at 9:00. A campaign queued at 8:00 reaches them at 9:30. Is that a bug?

Yes. Preferences must be checked when sending, not when the request was accepted, and opt-outs must reach the router’s cache at once.
