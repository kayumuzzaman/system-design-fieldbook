One fact, many copies

When Ana changes a photo’s caption, the new caption belongs in the photo table. It also belongs in the search index, so that the photo can be found by it. A cached copy of the photo page must be discarded. The analytics warehouse needs to know. A recommendation service keeps its own table of photos and their tags.

The photo table is the system of record, the authoritative copy. The rest are derived data: copies in other shapes for other purposes, which could in principle be rebuilt from the original. The question is how each change gets from the first to the others, every time, in the right order.

Why writing to both does not work

The first idea is for the application to do it: update the database, then update the search index. This is a dual write, and and have already warned against it. There are two separate ways it goes wrong.

Partial failure. The application can crash, or lose its connection, after the first write and before the second. One store has the change and the other never will. Reversing the order only reverses which store is wrong.

Racing writers. Even when every write succeeds, two concurrent updates can reach the two stores in different orders. Each store ends with a different final value, and both believe they are up to date.

Both failures are silent and permanent. No exception is thrown and no alert fires. Weeks later a user searches for a photo by its caption and does not find it. The underlying cause is that two systems are being written independently with nothing ensuring they see the same changes in the same order. The fix is to have a single ordered sequence of changes that both follow.

Ways to capture changes

The database already receives every change. Change data capture, or CDC, means getting those changes out of the database as a stream that other systems can follow. There are four techniques.

TechniqueHow it worksWeakness
PollingA job repeatedly asks for rows whose updated_at is newer than its last runMisses deletes and intermediate values, can skip rows, and loads the database
TriggersA database trigger copies each change into a changes table, which a job readsAdds work to every write, and the trigger logic is hidden in the database
OutboxThe application writes a message row in the same transaction as the changeCaptures only what the code remembers to write. Reliable for designed events.
Log-basedA connector reads the database’s replication logMore to set up and operate. Captures everything.

The trouble with polling

Polling deserves a closer look, because it is what most teams build first and it fails in a way that is hard to see.

The usual patch is to poll with an overlap, asking for changes since a minute before the last poll, and to rely on the consumer ignoring repeats. That narrows the hole without closing it, since a transaction can stay open longer than any overlap. Polling also cannot see a deleted row, cannot see values a row held between two polls, and puts a query load on the primary database that grows with how fresh you want the data. It is acceptable for small tables and loose requirements. It is not a foundation.

Reading the database’s log

Every serious database already produces exactly the stream that is needed. To survive crashes it writes each change to a write-ahead log before applying it (). To feed replicas it ships that log to them (). The log contains every committed change, in commit order, including deletes, with nothing skipped.

Log-based CDC connects to the database as if it were a replica, reads that log, and turns each change into an event.

Compared with the alternatives:

  • Nothing is missed. If it committed, it is in the log. That includes changes made by a migration script, an administrator at a console or a second application, none of which pass through your code.
  • Order is the database’s own. The log is the definitive sequence in which changes took effect, so followers cannot disagree about it.
  • No extra load on queries. Reading the log does not run queries against tables.
  • It is close to real time. Changes typically arrive within a second.
  • The application is unchanged. No code in the write path, so no dual write.

Each database exposes its log differently. PostgreSQL offers logical decoding, which translates the write-ahead log into row-level changes. MySQL has the binary log, or binlog, in row format. MongoDB has change streams, built on its operation log. The most widely used open-source tool is Debezium, which has connectors for these and many other databases and publishes to Kafka. Version 3.6 was released in July 2026. Cloud providers offer managed equivalents.

What a change event contains

{
  "op": "u",                                   // c = create, u = update, d = delete, r = read (snapshot)
  "before": { "id": 871, "caption": "Sunset",  "owner_id": 42 },
  "after":  { "id": 871, "caption": "Sunrise", "owner_id": 42 },
  "source": {
    "db": "photoapp", "table": "photos",
    "lsn": 24023128,                           // position in the log: the ordering key
    "txId": 5571,
    "ts_ms": 1791623643120                     // when the database committed it
  }
}

The log position, called the LSN in PostgreSQL, is the important field. It increases with every change, so it works as a version number for free: a consumer that remembers the position of the last change it applied to each row can ignore anything older.

Setting it up in PostgreSQL

-- In postgresql.conf:  wal_level = logical

CREATE PUBLICATION photo_changes FOR TABLE photos, comments;

SELECT pg_create_logical_replication_slot('search_indexer', 'pgoutput');

A publication names the tables to expose. A replication slot is the database’s record of one consumer’s position in the log. The database promises not to discard any log that a slot has not yet read, which is what makes delivery reliable. It is also the main operational hazard, as a later section explains.

Starting on a table that already has data

The log goes back only so far. Old log files are deleted once nothing needs them. A new consumer, such as a search index being built for the first time, needs all the existing rows and then every change after them, with no gap and no missed update in between.

A snapshot of a large table can take hours. Newer connectors can take it incrementally, in chunks interleaved with live changes, so that the stream is not held up and the snapshot can be paused, resumed or rerun for a single table. The technique was published by Netflix as DBLog and adopted by Debezium.

What consumers must handle

CDC delivers at least once. A connector that crashes after publishing a change and before recording its position will publish that change again on restart. And although the database’s log is totally ordered, the stream is usually published to a partitioned log, where order is kept for each key and not across keys ().

A correct consumer therefore needs three properties.

  • Changes are keyed by primary key, so that all changes to one row stay in order.
  • Applying a change twice is harmless. Write the whole row by key instead of applying differences.
  • Older changes do not overwrite newer ones, and a row that has been deleted is not brought back by a late update.
interface ChangeEvent {
  op: "c" | "u" | "d" | "r";                  // create, update, delete, or read during the snapshot
  key: number;                                // the row's primary key
  after: Record | null;      // the row after the change; null for a delete
  lsn: number;                                // position in the database's log, always increasing
}

class SearchIndexSink {
  private docs = new Map; lsn: number }>();
  private deletedAt = new Map();           // remember deletes, and where they happened

  apply(event: ChangeEvent): void {
    const seen = this.docs.get(event.key)?.lsn ?? this.deletedAt.get(event.key) ?? -1;
    if (event.lsn <= seen) return;                         // a duplicate or an older change: ignore it

    if (event.op === "d") {
      this.docs.delete(event.key);
      this.deletedAt.set(event.key, event.lsn);
    } else {
      this.docs.set(event.key, { doc: event.after!, lsn: event.lsn });
      this.deletedAt.delete(event.key);
    }
  }

  get(key: number): Record | undefined {
    return this.docs.get(key)?.doc;
  }
}

Fed four changes to two rows, this sink reaches the same final state whichever of the 24 possible orders they arrive in, and however many times each is repeated. The record of deletions is what prevents a late update from resurrecting a deleted row. In a real system that record can be dropped after a period longer than any plausible delay.

Two more things arrive in the stream and need a plan.

  • Schema changes. When a column is added or renamed in the source, the events change shape. Connectors can publish schemas to a registry (), and the expand-and-contract migrations of keep the changes compatible.
  • Transactions. One transaction that touches five rows appears as five separate events. A consumer may briefly see some and not others. If consumers need changes grouped as the transaction made them, the transaction ID is in each event.

CDC with an outbox

Raw CDC publishes your tables. Consumers that read those events are coupled to your schema: rename a column, split a table, and every downstream system breaks. For feeding your own search index or cache, that is acceptable, since you own both ends. For events that other teams consume, it turns your private storage layout into a public interface.

The answer combines the two reliable techniques. The application writes designed business events to an outbox table in the same transaction as its changes, as in . CDC is pointed at the outbox table alone and publishes its rows as events. This gives:

  • events that are atomic with the change, because they are written in the same transaction,
  • prompt delivery without a polling relay, because CDC streams from the log,
  • a deliberately designed public contract, because the events are written by code and not derived from table structure.
StreamContainsUse it for
Raw table changesRows as stored, before and afterYour own derived stores: search, caches, replicas, the warehouse
Outbox eventsBusiness events with a designed schemaOther services and other teams

Operating CDC

CDC attaches a new dependency to your primary database’s most critical internal structure. Most of the risks are specific and well known.

A stalled consumer can fill the database’s disk. A replication slot makes the database keep all log that the slot has not consumed. If the connector stops, for an hour or for a week, the log accumulates. When the disk fills, the database stops accepting writes. An abandoned slot, left behind by a decommissioned consumer, does this slowly and with no other symptom.

SELECT slot_name, active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

Alert on that number. Set max_slot_wal_keep_size so that a slot which falls too far behind is invalidated instead of taking the database down with it. The consumer then needs a new snapshot, which is a far better failure than an outage of the primary.

  • Failover. When the primary fails and a replica is promoted, the connector must continue from the right position on the new primary. PostgreSQL has been able to synchronize logical slots to standbys since version 17. Earlier versions need extra tooling or a fresh snapshot.
  • Log retention. In MySQL the binlog is deleted on a schedule regardless of consumers. A connector that is down for longer than the retention period has lost its place and must snapshot again.
  • Very large transactions. A bulk update of ten million rows becomes ten million events. Batch such jobs, and warn the owners of downstream systems.
  • Lag. Monitor the delay between a commit and its arrival downstream, end to end. Every derived store is stale by at least that much.
  • Sensitive columns. Everything in a published table flows out. Exclude or mask columns such as password hashes and personal data at the connector.

Common mistake. Creating a replication slot for an experiment and forgetting it. Nothing reads from it, so the database retains write-ahead log from that moment on. Weeks later the disk fills and writes stop, and the cause is a slot nobody remembers. List slots as part of routine monitoring, and drop any that are inactive without a known reason.

From changes to analytics

The largest consumer of change data in most companies is analytics. The transactional database is built to read and write single rows quickly. Analytical questions, such as uploads per country per week for the past two years, scan billions of rows and belong in a system built for that (). A data pipeline moves and reshapes data from where it is produced to where it is analyzed.

ETL and ELT

The two acronyms differ in the order of the same three steps: extract, transform, load.

ETLELT
OrderTransform in a separate system, then load the resultLoad the raw data, then transform it inside the warehouse
Raw dataUsually not keptKept
Transformations written inA pipeline tool or custom codeSQL, version-controlled and tested like code
Fixing a mistake in a transformationExtract from the sources again, if they still have the dataCorrect the SQL and rerun it over the raw data
Arose whenWarehouse storage and compute were expensiveBoth became cheap and elastic

ELT is the usual choice today. Storage is cheap enough to keep everything, and warehouses are powerful enough to do the transforming. Tools such as dbt manage the SQL transformations as a dependency graph with tests. ETL remains right where data must be reduced or scrubbed before it is allowed to land, for example to remove personal data.

Warehouses, lakes and lakehouses

  • A data warehouse is a database built for analytical queries over structured tables, with columnar storage (). Snowflake, BigQuery and Redshift are examples.
  • A data lake is files in object storage, in open formats such as Parquet, queried by separate engines. It is cheap and flexible, and without discipline it turns into a heap of files nobody trusts.
  • A lakehouse adds a table format on top of those files, which tracks which files make up each table and provides atomic commits, schema evolution and the ability to query a table as it was at an earlier time. Apache Iceberg and Delta Lake are the main formats. Several engines can then read and write the same tables safely.

Whichever is used, data arrives by one of two routes: periodic batch loads, which are simple and hours behind, or streaming ingestion from CDC and event logs, which is minutes or seconds behind and needs the machinery of the next chapter.

Keeping pipelines trustworthy

A pipeline that silently produces wrong numbers is worse than one that fails. The defenses are the ones this book keeps returning to, applied to data.

  • Idempotent, rerunnable steps. A step that runs twice, or is rerun for last Tuesday, must produce the same result. Overwrite a partition instead of appending to it.
  • Contracts on the inputs. Schema checks at ingestion, so that an upstream column change fails loudly at the door.
  • Tests on the outputs. Row counts, uniqueness, null rates and totals that must reconcile with the source ().
  • Freshness alerts. A table that has not been updated on schedule should alert before someone makes a decision from stale figures.
  • Lineage. A record of which tables feed which, so that the effect of a change or an error can be traced.

The database, inside out

Step back and a pattern is visible. Inside a database, the log is the truth, and tables, indexes and materialized views are structures derived from it and kept up to date automatically. CDC extends the same arrangement beyond the database’s walls. The search index is an index. The cache is a materialized view. The warehouse is a replica in a different shape. All of them follow one log.

This view has practical consequences. Derived stores hold nothing original, so they can be rebuilt from the source by taking a snapshot and replaying. A new kind of derived store can be added without touching the application. And the question of whether two stores agree has a definite answer: each is at some position in the same log, and a store is exactly as stale as its position is behind.

In an interview. Whenever your design has the same data in two stores, expect the question “how do they stay in sync?”. “The service writes to both” is the answer that loses points. Say “the database is the source of truth, and the index follows it through change data capture, so it is eventually consistent with a lag of about a second, and it can be rebuilt from a snapshot”. That one sentence covers correctness, staleness and recovery.

Key points

  • One store is the system of record. Everything else is derived data that should follow it and be rebuildable from it.
  • Dual writes diverge silently, through crashes between the writes and through concurrent writes arriving in different orders.
  • Polling on timestamps can skip rows permanently and cannot see deletes.
  • Log-based CDC reads the database’s own replication log, so it captures every committed change in commit order with no code in the write path.
  • Start a new consumer with a snapshot taken at a known log position, then stream from that position.
  • Delivery is at least once and ordered for each key. Consumers upsert by key and use the log position as a version.
  • For other teams, publish designed events through an outbox, not raw table changes.
  • A replication slot that is not consumed will fill the primary’s disk. Monitor and cap it.
  • In analytics pipelines, keep the raw data, make every step rerunnable, and test the outputs.

Check yourself

A service updates PostgreSQL and then Elasticsearch in the same request handler. Describe two different ways they can end up disagreeing with no error reported.

The process can crash or lose its connection after the database commit and before the index update, so the index never receives the change. Or two concurrent requests update the same row, and their writes reach the database in one order and the index in the other, leaving each with a different final value while every write succeeded.

A poller selects rows where updated_at is later than its previous run. Why can it miss a row permanently?

The timestamp is set when the statement runs, and the row becomes visible only when its transaction commits. If the transaction commits after a poll has already advanced past that timestamp, the next poll asks for later timestamps and never returns the row. Polling also cannot detect deleted rows or values that were overwritten between polls.

Why can log-based CDC capture changes made by a migration script that the application’s code knows nothing about?

It reads the database’s write-ahead or binary log, which records every committed change whatever made it. Capture that depends on application code, such as dual writes or an outbox, sees only what that code writes.

A new search index must be built from a table of 500 million rows that is being updated constantly. How do you avoid missing changes made during the copy?

Record the log position, read all existing rows as of that position, then start streaming the log from that same position. Any change made during the copy lies after the position and will be delivered by the stream. Rows that are both copied and then delivered again are handled by making the consumer idempotent.

A CDC consumer receives an update for a row and then, late, an older update for the same row. What should it do, and what does it need in order to know?

It should ignore the older update. It needs a version for each row that increases with every change, and the log position in each event serves that purpose. The consumer stores the position of the last change it applied to each key and discards anything not newer.

Your PostgreSQL primary runs out of disk although the data has not grown. A logical replication slot exists. What probably happened, and how do you prevent it?

The slot’s consumer stopped or was removed, and the database kept every write-ahead log segment since then because the slot had not consumed them. Monitor how much log each slot retains, alert on it, set a maximum so that a lagging slot is invalidated instead of filling the disk, and drop slots that have no active consumer.

Why is exposing raw CDC events from your tables to other teams a design risk, and what is the alternative?

Consumers become dependent on your table and column names and on your storage layout, so you can no longer rename, split or restructure tables without breaking them. Write designed business events to an outbox table in the same transaction as the change and publish those. The schema of the events is then a deliberate contract, separate from how you store data.
