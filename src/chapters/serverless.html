What the word means

There are still servers. The word describes who looks after them. With a serverless service you never see a machine, choose its size, patch it, or decide how many to run. Three properties together separate it from ordinary hosting:

  • No capacity to manage. You do not pick a number of instances. The provider adds and removes copies as load changes.
  • It scales to zero. With no traffic, nothing of yours is running.
  • You pay for use. The bill counts requests and running time, so no traffic means no charge for computing.

The best-known form is functions as a service, shortened to FaaS: AWS Lambda, Google Cloud Run functions, Azure Functions, Cloudflare Workers. The same three properties describe other services you have already met: object storage in , managed queues in , and databases billed by the request. A serverless design usually combines several of them, with functions as the glue.

The figure places functions on a line of options, by how much the provider takes over.

Every step to the right is a trade. You lose control over the machine, the operating system and how long a process lives, and you gain time not spent on them. Whether that is a good trade depends on the workload, and the rest of this chapter is about telling which is which.

Functions as a service

A function is a piece of code with one entry point, called the handler. The platform calls the handler with an event, and the handler returns a result. The photo app’s smallest function could look like this.

type Db = { query(sql: string): Promise };

// Runs once per execution environment, during a cold start.
const dbReady: Promise = connect();

export async function handler(event: { userId: string }) {
  const db = await dbReady;               // reused on every warm invocation
  const rows = await db.query("select ...");
  return { statusCode: 200, body: JSON.stringify({ user: event.userId, rows }) };
}

There is no server code in it: nothing listens on a port, parses HTTP or manages threads. The platform does all of that and hands the function one event at a time.

The execution environment

Your code runs inside an execution environment: an isolated sandbox with some memory, a share of a processor, the language runtime and a copy of your code. On AWS Lambda each one is a small virtual machine built with Firecracker, a virtual machine monitor written for this purpose. The Firecracker project reports that it starts a virtual machine in as little as 125 ms with under 5 MiB of memory overhead, which is what makes it practical to give every customer’s function its own.

An environment goes through three stages.

  1. Init. The platform creates the environment, loads your code, starts the runtime, and runs everything outside the handler: imports, configuration, the connect() call above.
  2. Invoke. The handler runs for one event. When it returns, the environment is frozen: its memory is kept and it gets no processor time. The next event thaws it and runs the handler again. This repeats, possibly thousands of times.
  3. Shutdown. After a period with no events, or when the provider wants the capacity back, the environment is destroyed.

In the classic model one environment handles one request at a time. If a second request arrives while the first is running, the platform uses a second environment. This single fact explains most of how functions behave: their scaling, their cold starts, their trouble with databases, and their bill.

Cold starts

A request that finds a frozen environment waiting is a warm start: only the handler runs. A request that needs a new environment is a cold start: the whole init stage happens first, while the caller waits.

How long a cold start takes depends mostly on things you choose. A small function in a light runtime such as Node.js or Python adds on the order of a hundred milliseconds or a few hundred. A large application on a runtime with a slow start, such as a Java framework that scans its classes at boot, can add several seconds. AWS caps the init stage at 10 seconds.

How often cold starts happen depends on traffic. To see why, here is a small simulator that follows the rule above: one request per environment, and an environment is discarded after sitting idle for some time.

type Sim = { coldStarts: number; peakEnvironments: number; requests: number };

/** Each environment serves one request at a time and is discarded after idleMs unused. */
export function simulate(arrivalsMs: number[], durationMs: number, idleMs: number): Sim {
  const freeAt: number[] = [];            // for each environment: when it is next free
  let cold = 0, peak = 0;
  for (const t of [...arrivalsMs].sort((a, b) => a - b)) {
    // discard environments idle for too long
    for (let i = freeAt.length - 1; i >= 0; i--) if (t - freeAt[i] > idleMs) freeAt.splice(i, 1);
    // pick a warm, free environment: the most recently used one
    let pick = -1;
    for (let i = 0; i < freeAt.length; i++) if (freeAt[i] <= t && (pick < 0 || freeAt[i] > freeAt[pick])) pick = i;
    if (pick < 0) { cold++; freeAt.push(t + durationMs); }
    else freeAt[pick] = t + durationMs;
    peak = Math.max(peak, freeAt.length);
  }
  return { coldStarts: cold, peakEnvironments: peak, requests: arrivalsMs.length };
}

Steady traffic almost never starts cold, because a warm environment is always about to become free. Two shapes are different. A sudden burst is cold for every request beyond the environments already warm. Sparse traffic is cold every time, because each environment is discarded before the next request comes. The real idle limit is not published and varies, so do not design around a specific number.

Across all its customers, AWS said in April 2025 that cold starts typically occur in under 1% of invocations. That average hides the two bad cases: for a rarely used internal tool, the figure is close to 100%.

Common mistake. Judging cold starts by the average. A function with a 2-second cold start on 1% of requests has a fine median and a 99th percentile of two seconds. If a page calls five such functions, about 5% of page loads include at least one cold start. This is the tail arithmetic from .

Reducing them

  • Do less at init. Ship less code, import only what the handler uses, and delay loading rarely used parts until they are needed. This is the cheapest fix and often the largest.
  • Do the right things at init. Work that every request needs, such as opening a database connection or reading configuration, belongs outside the handler so that it runs once per environment instead of once per request.
  • Keep environments ready. AWS calls this provisioned concurrency, and Cloud Run calls it minimum instances: you pay for a number of environments to stay initialized. Requests up to that number never start cold. You are now paying for idle capacity again, at a lower rate.
  • Start from a snapshot. Lambda SnapStart runs the init stage once when you publish a version, saves the memory and disk of the initialized environment, and starts new environments by restoring that snapshot. As of October 2026 it supports Java 11 and later, Python 3.12 and later, and .NET 8 and later. AWS describes the effect as taking start-up from several seconds to under a second in good cases. Anything unique that init created, such as a random seed or an identifier, is now shared by every environment restored from the snapshot, so it must be generated after the restore.
  • Use a lighter sandbox. Cloudflare Workers run code in V8 isolates, the mechanism a browser uses to separate tabs, instead of a virtual machine per function. An isolate starts in a few milliseconds. The price is a narrower environment: JavaScript and WebAssembly, 128 MB of memory, and a limit of one second for start-up code.

Concurrency and scaling

The unit of capacity for functions is concurrency: the number of requests in progress at the same moment, which is also the number of environments in use. It follows from two numbers you can estimate.

concurrency = requests per second × average duration in seconds

This is Little’s law from . At 400 requests a second and 250 ms each, 100 environments are busy. If a slow dependency stretches the duration to 2.5 seconds, the same traffic needs 1,000. Duration is under your influence and the request rate is not, so a slow downstream call is the usual way a function runs into its limit.

Scaling is automatic and it is bounded twice. The figures are for AWS Lambda as of October 2026.

  • A total. An account may run 1,000 concurrent executions in a region by default, shared by all its functions. The limit can be raised on request. Beyond it, requests are rejected with status 429, which is called throttling.
  • A rate. Each function can add at most 1,000 environments every 10 seconds. A burst larger than that is throttled until capacity catches up.

Because the total is shared, one runaway function can use all of it and throttle every other function in the account. Two settings prevent that. Reserved concurrency sets aside a number of executions for one function and also caps it at that number. It is a bulkhead in the sense of : the function that processes uploads cannot starve the function that serves logins, and the reverse.

The database connection problem

Automatic scaling moves the bottleneck to whatever the function calls. The classic case is a relational database. A PostgreSQL or MySQL server accepts a limited number of connections, often a few hundred, because each one costs it memory. A long-running application server opens a small pool and shares it among all its requests, as described. Functions cannot share: each environment is a separate sandbox with its own connection.

There are three ways out, and they combine.

  • A pooling proxy between the functions and the database, such as PgBouncer, or Amazon RDS Proxy as a managed service. Functions connect to the proxy, which is cheap, and the proxy multiplexes their queries over a small pool of real connections.
  • A cap on the function. Reserved concurrency below the database’s connection limit guarantees the function alone cannot exhaust it.
  • A database reached over HTTP. Stores built for this style, such as DynamoDB, have no connection limit of this kind because every request stands alone.

The general lesson applies to any downstream system with a fixed capacity: a third-party API with a rate limit, a legacy service, a search cluster. Something that scales without limit should not call something that does not without a limit in between. A queue is the usual buffer, as the next section shows.

What starts a function

A function runs because something invoked it. There are three ways, and they differ in who waits and who retries.

StyleTypical sourcesCaller waits?On failure
SynchronousAn HTTP request through an API gateway or a function URLYes, for the responseThe caller gets the error and decides
AsynchronousAn object was stored, a notification was published, a schedule firedNo. The platform queues the event internallyThe platform retries, then discards or dead-letters
PollingA queue, a stream, a database change streamNo. The platform reads batches and invokes the functionThe batch returns to the source and is delivered again

For asynchronous events, Lambda retries a failed invocation twice by default, and events that still fail go to a dead-letter queue or failure destination if you configured one. If you did not, they are dropped. For polling sources the queue’s own rules apply: the visibility timeout and redelivery count from .

In every non-synchronous style the same event can arrive more than once, so handlers must be idempotent, for the reasons in . With a batch there is a second concern: if one message in ten fails, the other nine should not be processed again. Queue triggers let the handler report which messages failed.

type Message = { messageId: string; body: string };
type BatchResult = { batchItemFailures: { itemIdentifier: string }[] };

interface ProcessedStore {
  has(id: string): Promise;
  add(id: string): Promise;
}

export async function handleBatch(
  messages: Message[],
  done: ProcessedStore,
  work: (body: string) => Promise,
): Promise {
  const failures: { itemIdentifier: string }[] = [];
  for (const m of messages) {
    try {
      if (await done.has(m.messageId)) continue;   // a duplicate delivery: skip it
      await work(m.body);
      await done.add(m.messageId);                 // recorded only after success
    } catch {
      failures.push({ itemIdentifier: m.messageId });  // only this one is retried
    }
  }
  return { batchItemFailures: failures };
}

The order of the three lines inside try matters. Recording the message before doing the work would mean that a failure leaves it marked as done, and the retry would skip it: the message is lost. Recording after the work means a crash between the two lines repeats the work once, which is the safe direction. To close that gap completely, write the record in the same database transaction as the work’s result, as showed.

In production. A queue between an event source and a function is also a throttle. Set the function’s maximum concurrency for that queue to what the downstream system can take, and a burst waits in the queue instead of arriving all at once. AWS recommends a queue visibility timeout of at least six times the function’s timeout, so that a message being retried inside the function is not handed to a second copy.

An example: thumbnails for the photo app

When Ana uploads a photo, the app needs three smaller versions of it. This is work with an event that starts it, no user waiting on the result, a few seconds of processing, and a rate that follows uploads: quiet at night, busy in the evening, very busy after a public holiday.

Two details in the figure are deliberate. The thumbnails go to a different prefix from the originals, and the trigger listens only to originals/. A function that writes into the location that triggers it invokes itself without end, and the bill grows until someone notices. The queue and its dead-letter queue mean that a corrupt image fails five times and is set aside for a person to look at, instead of failing silently or blocking the photos behind it.

State

A function must be written as if every invocation ran on a new machine, because some will. The stateless rule from is enforced here by the platform.

Kind of stateIn a function
Variables outside the handlerSurvive between invocations in the same environment. Useful as a cache and for connections. Never the only copy of anything, and never shared across environments.
Local diskA temporary directory, private to the environment and lost with it. Use it for scratch files within one invocation.
Sessions, counters, anything sharedIn an external store: a database, a cache, object storage.
Long-lived connections from clientsHeld by a gateway, which invokes the function for each message. The function never holds a WebSocket itself.
Work after the responseNot reliable. Once the handler returns, the environment may be frozen at once.

The last row surprises people moving from ordinary servers. Code that sends a response and then, in the background, writes a log line or flushes metrics will sometimes be frozen in the middle and finish minutes later, or never. Finish everything before returning, or hand the follow-up to a queue.

The size limits shape designs. A 6 MB ceiling on a synchronous response rules out returning a large file through a function, which is one more reason to hand clients a link to object storage instead. What it costs

A function’s bill has two parts: a small fee per request, and a fee for GB-seconds, which is the memory you configured multiplied by the time your code ran.

monthly cost = requests × (duration in seconds × memory in GB × price per GB-second + price per request)

For AWS Lambda on x86 in the us-east-1 region, as of October 2026, the prices are $0.0000166667 per GB-second and $0.20 per million requests. Arm processors are about 20% cheaper per GB-second. Each month the first 1 million requests and 400,000 GB-seconds are free. Since August 2025 the init stage of a cold start is billed like any other running time.

At these prices the function costs about $12.00 a month before any free allowance: $10.00 for compute and $2.00 for requests. On average 0.463 copies are running at once, so an always-on server would sit idle most of the time. The function stays cheaper than the $60 alternative up to about 50 million requests a month.

The third result explains the economics. Ten million requests a month sounds large and is under four a second. At 120 ms each, less than half of one copy of the function is busy on average. A single small server can run dozens of such requests at once, so it would be idle nearly all the time, and you would want two of them for availability. Paying per use wins because most of the capacity you would otherwise rent is unused.

The crossing point moves with the shape of traffic. Steady load around the clock is the worst case for functions, because a server would be well used. Spiky load is the best case, because a server sized for the peak sits idle the rest of the time and a function does not.

The function’s own charge is seldom the whole bill. An API gateway in front is priced per request too, and for small, fast functions it can cost more than the function. Logs are billed by volume, and a function that logs every event generously can spend more on logging than on computing. Add data transfer and whatever the function calls. A fair comparison covers the full path of a request, not one line of it.

The server’s bill is incomplete as well. It leaves out the hours someone spends patching, resizing and being paged for it. For a small team that time is usually worth more than either figure in the chart.

A case: Prime Video’s monitoring service

In 2023 a team at Amazon Prime Video published an account of rebuilding a service, and it became the most discussed serverless story of the year. The service checks live video streams for defects: frozen frames, corrupted blocks, audio out of step with the picture.

The first version was assembled from serverless parts. A workflow service, AWS Step Functions, coordinated a chain of Lambda functions: one split the stream into frames and audio, others ran defect detectors on them, another combined the results. Frames passed between functions by way of object storage.

According to the team’s account, it stopped scaling at about 5% of the load they expected. Two things were responsible:

  • The workflow was too fine-grained. It performed several state transitions for every second of every stream. Step Functions bills per transition and limits how many an account may make, and the service hit that limit.
  • The data moved the long way round. Every frame was written to object storage by one function and read back by another. That is a large number of storage requests for data that lived only a moment.

The rebuilt version runs all the steps in one process on container instances. Frames stay in memory and pass from step to step as ordinary function calls. The team reported that infrastructure cost fell by 90%, and the service could handle the load.

The story was widely read as “serverless failed” or “microservices failed”. The account supports a narrower conclusion.

  • The grain was wrong for this workload. A per-step billed workflow suits steps that happen a few times per business event: an order, a signup, an upload. It does not suit steps that happen many times a second on a continuous stream. That is a steady, high-volume, data-heavy job, which is the profile where pay-per-use loses.
  • Passing bulk data between functions is expensive. Functions share nothing, so anything large must travel through storage or the network. Steps that exchange a lot of data belong in one process.
  • The first version was not a mistake. By the team’s own description it let them build the service quickly. The cost of that speed appeared only at scale, and by then they knew enough to design the replacement. This is the “start simple, then change what measurement shows” advice from , arriving from the opposite direction.

What fits and what does not

The case gives one side of a general pattern. Functions suit work that is driven by events, short, and uneven. They do not suit work that is steady, long, or needs to hold on to something.

Most systems have work of both kinds, and mixing is normal. The photo app can serve its feed from long-running containers and still make thumbnails, send the weekly digest and receive payment webhooks with functions.

Shapes to avoid

  • Functions calling functions and waiting. While function A waits for function B, both are billed, both count against concurrency, and both must stay inside A’s timeout. A chain of three is three bills for one piece of work. Put the code in one function, or connect them with a queue so that nobody waits.
  • One function per tiny step. Dozens of functions with a few lines each give you a distributed system to debug in exchange for nothing. A function should be a unit you would deploy on its own for a reason.
  • One function that does everything. The opposite extreme: a whole web application behind a single handler. It works, and it brings a large package, slow cold starts and one set of permissions for everything. It can be a reasonable way to move an existing application. For new code, group by what changes and scales together.
  • A function that triggers itself. Writing to the place you are triggered from, as in the thumbnail example, or publishing to the queue you consume without a stop condition.

Serverless containers and the edge

Functions are one point on the line in the first figure. Two neighbors are worth knowing, because they remove some of the limits above.

Serverless containers. Services such as Google Cloud Run, AWS Fargate and Azure Container Apps run a container image of yours and manage the machines under it. On Cloud Run the container is an ordinary web server, and one instance handles many requests at once: up to 80 by default and at most 1,000, as of October 2026. That removes the one-request-per-environment rule and most of what follows from it. An instance can keep a shared connection pool, a burst needs fewer new instances, and cold starts affect fewer requests. It still scales to zero unless you set a minimum. You bring the web server and the image, which is more to maintain than a handler and far less than a cluster. Lambda has moved in the same direction: since late 2025 it can also run functions on instances that serve several requests each.

Edge functions. Platforms such as Cloudflare Workers run your code in the provider’s points of presence, close to users, using the isolates described under cold starts. They suit short work on the request path: authentication checks, redirects, rewriting headers, assembling a page from cached pieces. covers them. The usual catch is data: code that runs in 300 cities and queries a database in one of them has moved the computation closer to the user and left the slow part where it was.

Long-running work

A single invocation is short-lived by design. Work that takes hours or waits on people, such as “resize, then wait for moderation, then publish, and send a reminder after three days”, needs something that remembers where it is. explained the idea: record each completed step, and after any interruption replay the record to get back to the same point.

Serverless platforms offer this in two forms. A workflow service such as AWS Step Functions holds the state machine outside your code and invokes a function for each step. Durable functions let you write the whole flow as one ordinary function. Azure has offered this for years, and AWS Lambda added it in late 2025. In Lambda’s version the code wraps each unit of work in a step, whose result is checkpointed, and calls a wait to pause. During a wait nothing is running and nothing is billed. When it is time to continue, the platform invokes the function again from the top and feeds it the stored results of the steps already done, so those steps are skipped. Each invocation is still limited to 15 minutes, and the whole execution may last up to a year.

The constraint is the one from that earlier chapter. Because the code is replayed, it must be deterministic outside its steps: no reading the clock, no random numbers, no network calls, except inside a step whose result is recorded.

The Prime Video case is the caution to keep beside this section. These tools are for flows with a modest number of steps per business event. They are not a way to process a stream.

Operating functions

Observability. A request that passes through a gateway, a function, a queue and another function leaves its evidence in four places. Give every event a correlation identifier and log it everywhere, as in . Watch four numbers for each function: invocations, errors, duration at the 99th percentile, and throttles. For queue-triggered functions add the age of the oldest message, the signal from that tells you the function is not keeping up.

Timeouts. Set the function’s timeout deliberately, a little above its measured worst case, and below the timeout of whatever calls it. The default advice from applies with extra force, because a function waiting on a dead dependency is billed for every second it waits.

Permissions. Each function runs with its own identity. Give it only what it needs: the thumbnail function may read originals/ and write thumbs/, and nothing else. Small, separate permissions are one of the real security gains of the model, and they are lost if every function shares one broad role.

Testing. Keep the handler thin. It should translate the platform’s event into a call to plain code that knows nothing about the platform, and translate the result back. The plain code can then be tested like any other, and the handler has almost nothing in it to get wrong. Test the wiring, meaning triggers, permissions and limits, by deploying to a real test environment, since local emulators reproduce it only partly.

Lock-in. The handler is the easy part to move. The triggers, the permissions, and the queues, stores and gateways around it are specific to one provider. The thin-handler habit keeps your logic portable. The architecture around it is not, and that is usually an acceptable price for not operating it yourself. Decide it knowingly.

In an interview. Propose functions for the event-driven edges of a design, such as processing uploads, scheduled jobs and webhooks, and say why they fit: uneven load and nobody waiting. Then name the two limits before you are asked. First the concurrency ceiling, with the arithmetic of rate times duration. Second, what protects the database or API behind the function. For a request path with a strict latency target, say that you would use long-running instances or keep a minimum warm, and why.

Three questions settle most cases. How even is the traffic, and what fraction of rented capacity would sit idle? What is the latency target at the tail, and can a cold start fit inside it? What does the code call, and can that survive the function scaling by a thousand in ten seconds?

Common mistakes

  • Assuming it scales without limit. There is a regional total and a scaling rate, and both produce throttling. Know your limit and request an increase before the launch, not during it.
  • Ignoring what is downstream. A function scales and its database does not. Use a pooling proxy, a concurrency cap, or a queue.
  • Heavy initialization. Large dependencies and frameworks loaded on every cold start. Measure init time and trim it.
  • Initialization in the wrong place. Opening a connection inside the handler, so every request pays for it.
  • Treating memory outside the handler as storage. It is a cache that can vanish, and each environment has its own.
  • Work after the response. Background tasks that are frozen halfway.
  • Handlers that are not idempotent. Every asynchronous trigger can deliver twice.
  • No dead-letter destination. Failed asynchronous events are discarded after the retries unless you say where they go.
  • Synchronous chains of functions. Paying several times over for waiting.
  • Extrapolating the bill. A cost that is trivial at a thousand requests a day is not trivial at a thousand a second. Recompute the break-even as traffic grows, and include the gateway and the logs.

Key points

  • Serverless means no capacity to manage, scaling to zero, and paying for use. Functions are its best-known form.
  • Code runs in execution environments that are created on demand, reused while traffic continues, frozen between requests and discarded when idle. In the classic model each handles one request at a time.
  • A cold start is the cost of creating an environment. Steady traffic rarely sees one. Bursts and sparse traffic see many. Trim init code first, then pay for warm capacity or snapshots if the tail still matters.
  • Concurrency is request rate times duration. It is capped in total and in how fast it can grow, and whatever the function calls needs protecting from it.
  • Asynchronous and polled triggers deliver at least once. Handlers must be idempotent and failures need a dead-letter destination.
  • The bill is a straight line through zero. It beats rented capacity when that capacity would be mostly idle and loses when it would be busy.
  • Functions suit short, uneven, event-driven work. Steady streams, bulk data passed between steps, long computations and held connections belong in long-running processes.

Check yourself

A function receives 600 requests a second and each takes 200 ms. How many execution environments are busy? What happens to that number if a dependency slows each request to 2 seconds?

600 × 0.2 = 120 environments. At 2 seconds it becomes 1,200, which is above the default regional limit of 1,000 on AWS Lambda, so some requests are throttled. The traffic did not change. The duration did.

An internal tool is used about once every 20 minutes. Its users complain that it is always slow, while a busy public endpoint built the same way is fast. Why?

Environments are discarded after sitting idle, so with one request every 20 minutes almost every request finds no warm environment and pays the full cold start. The busy endpoint always has warm environments becoming free. The fixes are a lighter init stage, a kept-warm environment, or accepting it for an internal tool.

Why does code outside the handler run only sometimes, and what belongs there?

It runs during the init stage, once for each new execution environment, and not on warm invocations. Work every request needs and that can be reused belongs there: opening connections, loading configuration, building clients. Per-request data does not, because the environment is reused across requests from different users.

A function with a concurrency of 500 queries a PostgreSQL server that accepts 200 connections. Give three ways to stop it exhausting them.

Put a pooling proxy between them so that many environments share a few real connections. Cap the function’s concurrency below the database’s limit. Feed the function from a queue with a maximum concurrency so that bursts wait. A fourth is to use a store reached by independent HTTP requests instead of held connections.

In a batch handler, why record a message as processed after doing the work and not before?

If the record is written first and the work then fails, the redelivered message is seen as already processed and skipped, so its work never happens. Writing the record after the work means a crash in between repeats the work, which idempotent work tolerates. Writing both in one transaction removes the gap.

A function runs for 80 ms with 1,024 MB of memory, 30 million times a month. Using $0.0000166667 per GB-second and $0.20 per million requests, what does it cost before the free allowance?

Compute: 30,000,000 × 0.08 s × 1 GB = 2,400,000 GB-seconds, which costs $40.00. Requests: 30 × $0.20 = $6.00. Total $46.00 a month. The average concurrency is about 11.6 requests a second × 0.08 s, under one environment.

What two properties of the first Prime Video design made it expensive and unable to scale, and what kind of workload do they point to?

A workflow that made several billed, rate-limited state transitions for every second of every stream, and frames passed between functions through object storage. Both point to a steady, high-frequency, data-heavy workload, where per-step billing and share-nothing functions cost the most.

How does one instance of a serverless container differ from one function environment, and what does the difference change?

A container instance is a web server that handles many requests at once, where a classic function environment handles one. So an instance can share a connection pool, a burst needs far fewer new instances, and fewer requests meet a cold start. In exchange you maintain the server and its image.
