The problem

The problem. Design the control software for the elevators in an office building. There are several cars. People call a car from a landing by pressing up or down, and choose their floor on a panel inside the car.

In the terms of , this is a machine with modes. A car behaves differently when it is resting, traveling and standing with its doors open, and the heart of the design is a state machine ().

Step 1: Clarify

QuestionAssumed answer for this design
How many floors and cars?Any number, set when the system is created. Examples use 10 or 20 floors and 1 to 3 cars
What buttons are there?Up and down on each landing. One for each floor inside each car
What does “time” mean in the software?The system is advanced by a regular tick. A moving car travels one floor in a tick, and doors stay open for two
Is there a limit on how many people fit?Not in the first version. A full car is a follow-up
What matters most?Nobody waits forever, and waits are short on average
What is out of scope?Motors, door sensors, fire service mode, the displays

The question about time is the one that makes the problem tractable. Real controllers react to sensors. For a design exercise, a tick that advances every car by one step gives the same structure and can be run and tested as ordinary code.

Two kinds of request come out of the answers, and they must not be merged.

  • A hall call is made from a landing. It has a floor and a direction, and it is addressed to the system: any car may answer it.
  • A car call is made inside a car. It has a floor only, and it is addressed to that car: no other car can serve it.

The third is a different kind of rule from the others. The first two say that something bad never happens. The third says that something good eventually does, and it is the one that rules out some attractive scheduling ideas, as the section on ordering stops will show.

Step 4: The classes

The car as a state machine

export type Direction = "up" | "down";
export type CarState = "idle" | "moving" | "doorsOpen";

const delta = { up: 1, down: -1 } as const;
const reverse = { up: "down", down: "up" } as const;

export class ElevatorError extends Error {}

// One elevator car. It is a state machine advanced by tick(): one tick moves a moving car by one floor.
export class Car {
  static readonly dwell = 2; // ticks the doors stay open at a stop

  readonly id: string;
  readonly topFloor: number;
  private at: number;
  private heading: Direction | null = null;
  private mode: CarState = "idle";
  private dwellLeft = 0;
  private readonly inside = new Set(); // floors chosen on the panel in the car
  private readonly hall: Record> = { up: new Set(), down: new Set() }; // hall calls given to this car
  private readonly onStop: (car: Car) => void;

  constructor(id: string, topFloor: number, startFloor = 0, onStop: (car: Car) => void = () => {}) {
    this.id = id;
    this.topFloor = topFloor;
    this.at = startFloor;
    this.onStop = onStop;
  }

  get floor(): number { return this.at; }
  get direction(): Direction | null { return this.heading; }
  get state(): CarState { return this.mode; }
  get pending(): number { return this.inside.size + this.hall.up.size + this.hall.down.size; }

  // A passenger in the car presses a floor button.
  pressFloor(floor: number): void {
    this.mustExist(floor);
    if (floor === this.at && this.mode === "doorsOpen") return; // already here, doors open
    this.inside.add(floor);
  }

  // The dispatcher gives this car a call made from a landing.
  assignHallCall(floor: number, direction: Direction): void {
    this.mustExist(floor);
    if (this.mode === "doorsOpen" && floor === this.at && (this.heading === direction || this.heading === null)) {
      this.heading = direction; // the car is standing here with its doors open: hold them
      this.dwellLeft = Car.dwell;
      this.onStop(this);
      return;
    }
    this.hall[direction].add(floor);
  }

  tick(): void {
    if (this.mode === "doorsOpen") {
      this.dwellLeft -= 1;
      if (this.dwellLeft === 0) this.closeDoors();
    } else if (this.mode === "idle") {
      if (this.pending > 0) this.depart();
    } else {
      this.at += delta[this.heading as Direction]; // only a car in the moving state changes floor
      if (this.shouldStop()) this.openDoors();
    }
  }

  // The rule of collective control: stop for anyone inside, for a hall call in the direction of travel,
  // and for a hall call the other way only when there is nothing further to go to.
  private shouldStop(): boolean {
    const heading = this.heading as Direction;
    return this.inside.has(this.at) || this.hall[heading].has(this.at) || (!this.anyBeyond(heading) && this.hall[reverse[heading]].has(this.at));
  }

  private openDoors(): void {
    this.mode = "doorsOpen";
    this.dwellLeft = Car.dwell;
    this.inside.delete(this.at);
    this.heading = this.directionFromHere();
    if (this.heading) this.hall[this.heading].delete(this.at);
    this.onStop(this); // passengers get out, and those going this car's way get in and press buttons
  }

  private closeDoors(): void {
    const next = this.directionFromHere();
    if (next !== null && next !== this.heading && this.hall[next].has(this.at)) {
      this.heading = next; // someone here is waiting to go the other way: serve them before leaving
      this.openDoors();
      return;
    }
    this.heading = next;
    this.mode = next === null ? "idle" : "moving";
  }

  private depart(): void {
    if (this.inside.has(this.at) || this.hall.up.has(this.at) || this.hall.down.has(this.at)) {
      this.openDoors();
      return;
    }
    const stops = [...this.inside, ...this.hall.up, ...this.hall.down];
    const nearest = stops.reduce((best, floor) => (Math.abs(floor - this.at) < Math.abs(best - this.at) ? floor : best));
    this.heading = nearest > this.at ? "up" : "down";
    this.mode = "moving";
  }

  // Keep going while there is a reason to. Turn around only when there is nothing ahead. Otherwise rest.
  private directionFromHere(): Direction | null {
    const current = this.heading;
    if (current && (this.anyBeyond(current) || this.hall[current].has(this.at))) return current;
    const other: Direction = current ? reverse[current] : "up";
    if (this.anyBeyond(other) || this.hall[other].has(this.at)) return other;
    if (!current && (this.anyBeyond("down") || this.hall.down.has(this.at))) return "down";
    return null;
  }

  private anyBeyond(direction: Direction): boolean {
    const ahead = (floor: number) => (floor - this.at) * delta[direction] > 0;
    return [...this.inside, ...this.hall.up, ...this.hall.down].some(ahead);
  }

  private mustExist(floor: number): void {
    if (!Number.isInteger(floor) || floor < 0 || floor > this.topFloor) throw new ElevatorError(`there is no floor ${floor}`);
  }
}

The states here are labels with rules about which moves are legal, so the machine is written as a field and a tick method that branches on it. That is the table form of . State objects would add three classes and no clarity.

Look at where the first invariant lives. No line checks “are the doors closed?” before moving. The floor changes in exactly one place, the last branch of tick, which is reached only in the moving state. A test stepped a car through a full journey and confirmed that the floor never changed on a tick that began in any other state.

Step 5, part one: The order of stops

A car with several stops to make must choose an order. The obvious choice, the order in which buttons were pressed, is poor.

// Two orders in which one car could visit a list of requested floors. Each returns the floors in the order visited.

// First come, first served: the order the buttons were pressed.
export const fcfsOrder = (requests: readonly number[]): number[] => [...requests];

// LOOK: keep going in one direction to the furthest request, then turn and take the rest on the way back.
export function lookOrder(start: number, requests: readonly number[], first: "up" | "down" = "up"): number[] {
  const above = requests.filter((f) => f > start).sort((a, b) => a - b);
  const below = requests.filter((f) => f < start).sort((a, b) => b - a);
  const here = requests.filter((f) => f === start);
  return first === "up" ? [...here, ...above, ...below] : [...here, ...below, ...above];
}

export const floorsTraveled = (start: number, order: readonly number[]): number =>
  order.reduce((sum, floor, i) => sum + Math.abs(floor - (i === 0 ? start : (order[i - 1] as number))), 0);

For a car at floor 5 with seven floors requested, serving them as pressed meant 63 floors of travel, and sweeping up and then down meant 22. The sweeping rule is called LOOK: travel in one direction as far as the furthest request, then reverse. Computer science knows the rule from disk drives, where the arm that reads the platter faces the same problem, and operating system textbooks call it the elevator algorithm.

RuleTravelCan a request wait forever?
First come, first servedPoor. The car crosses the building repeatedlyNo
Nearest request nextGood at each stepYes. A steady stream of requests near the car keeps it away from a distant one. This is starvation
LOOKGoodNo. Each sweep ends, and every request lies on the next sweep at the latest

Passengers add one refinement, because a hall call has a direction. A car heading up should stop for someone who wants to go up, and should pass someone who wants to go down, since stopping would take them the wrong way first. The complete rule, called collective control, is the shouldStop method in the car: stop for anyone inside, stop for a hall call in the direction of travel, and stop for a hall call in the other direction only when there is nothing further ahead.

Step 5, part two: Which car answers

With several cars, each hall call has to be given to one of them. This is the dispatching decision, and it is a strategy in the plainest sense: a function from a call and the cars to a car.

export interface HallCall {
  readonly floor: number;
  readonly direction: Direction;
}

// The dispatching strategy: which car should answer this call?
export type Dispatch = (call: HallCall, cars: readonly Car[]) => Car;

const least = (cars: readonly Car[], cost: (car: Car) => number): Car =>
  cars.reduce((best, car) => (cost(car) < cost(best) ? car : best));

// Takes turns, whatever the cars are doing.
export const roundRobin = (): Dispatch => {
  let turn = 0;
  return (_, cars) => cars[(turn++) % cars.length] as Car;
};
// The car whose position is closest right now, even if it is moving away.
export const nearestCar: Dispatch = (call, cars) => least(cars, (car) => Math.abs(car.floor - call.floor));
// The car that would reach the caller soonest, counting everything it has already promised to do.
export const soonestArrival: Dispatch = (call, cars) => least(cars, (car) => car.ticksToServe(call.floor, call.direction));

export class ElevatorSystem {
  readonly cars: readonly Car[];
  private readonly dispatch: Dispatch;
  private readonly waiting = new Map(); // hall calls not yet answered, and the car each was given to

  constructor(carCount: number, topFloor: number, dispatch: Dispatch, onStop: (car: Car) => void = () => {}) {
    this.dispatch = dispatch;
    this.cars = Array.from({ length: carCount }, (_, i) => new Car(`car ${i + 1}`, topFloor, 0, (car) => { this.answered(car); onStop(car); }));
  }

  // A button on a landing. Pressing it twice does not send two cars.
  callFrom(floor: number, direction: Direction): Car {
    const key = `${floor}:${direction}`;
    const already = this.waiting.get(key);
    if (already) return already;
    const car = this.dispatch({ floor, direction }, this.cars);
    this.waiting.set(key, car);
    car.assignHallCall(floor, direction);
    return car;
  }

  tick(): void {
    for (const car of this.cars) car.tick();
  }

  private answered(car: Car): void {
    for (const direction of ["up", "down"] as const) {
      if (car.direction === direction || car.direction === null) {
        const key = `${car.floor}:${direction}`;
        if (this.waiting.get(key) === car) this.waiting.delete(key);
      }
    }
  }
}

The third strategy asks each car a question only the car can answer: given everything you have already promised, how long until you could open your doors for this caller? The car answers by running a copy of itself forward, in ticksToServe, which keeps the dispatcher free of any knowledge of how cars order their stops.

A small test shows the difference. Car 1 is at floor 12 on its way up to 19, and car 2 is resting at floor 2. Someone at floor 9 presses down. The nearest-car rule chose car 1, three floors away and heading in the wrong direction. Soonest arrival chose car 2.

To compare the strategies on something larger, the same 300 simulated passengers were sent through a 20-floor building with three cars, once for each strategy and for two patterns of traffic.

Average wait, in ticksMixed trafficMorning rush, 85% from the lobby
Round robin21.515.9

All 300 passengers arrived under every strategy, and none was ever let into a car going the wrong way. Two results are worth remembering. Nearest car, the answer most people give first, did worse than taking turns in the morning rush: when most calls come from the lobby, the nearest car is always the same one, and it does all the work while the others stand by. And the strategy that estimates real arrival time cut the average wait by about a third in mixed traffic and by half or more in the rush, without any change to the cars.

These numbers come from a simple model: unlimited room in each car, one tick for each floor, a seeded random crowd. They show how the strategies rank on that model, and should not be read as predictions for a real building.

Stopping takes more of the trip than traveling does, which is usual: faster doors help more than a faster motor. Real cars bunch together, so treat this as the best case.

Many buttons at once

Button presses arrive from many places at arbitrary moments, while the cars are being advanced. The shared state is each car’s sets of stops and the system’s map of unanswered calls. Two designs keep it consistent.

  • One loop owns everything. Button presses are placed on a queue as small messages. A single control loop takes messages from the queue, applies them, and advances the cars, one step at a time. Nothing else touches the cars, so nothing needs a lock. This is the “one owner, send it messages” approach of , and it is how the code in this chapter behaves on a single-threaded runtime: callFrom, pressFloor and tick each run to completion.
  • A lock for each car. In a threaded design where presses are handled on their own threads, each car guards its sets with a lock, held briefly by pressFloor, assignHallCall and tick. The dispatcher reads several cars to compare them, and should read each under that car’s lock in turn, never holding two at once.

The first is simpler and is the better answer for a control system, where the order of events matters and the work for each event is tiny.

In an interview. Draw the two layers before anything else, and say that you will take them one at a time: how one car orders its stops, then how a call is given to a car. Most candidates blend them into one “scheduler” class and run out of time untangling it. Then give the three states and the one-line safety rule, write tick and shouldStop, and present dispatch as a function type with the nearest-car version written and the better one described. If asked why not nearest-request-first inside a car, the word wanted is starvation.

Key points

  • An elevator system has two separate decisions: the order in which a car visits its stops, and which car is given each hall call.
  • Hall calls have a floor and a direction and belong to the system. Car calls have a floor and belong to one car.
  • A car is a state machine with three states: idle, moving and doors open. The floor changes only in the moving state, which is what keeps it from moving with open doors.
  • LOOK, sweeping to the furthest request and then reversing, travels far less than serving requests in order, and unlike nearest-first it cannot starve a request.
  • Collective control adds direction: stop for calls going your way, and for others only at the turning point.
  • Dispatching is a strategy. Choosing by distance alone is poor, and choosing by estimated arrival time is much better.
  • Drive the model with a tick, so that it can be simulated, tested and measured.
  • Give the cars one owner that applies button presses from a queue, and no locks are needed.

Check yourself

A car at floor 6 has these floors requested, in this order: 2, 9, 4, 12, 7. How many floors does it travel serving them as pressed, and how many with LOOK going up first?

As pressed: 6 to 2 is 4, to 9 is 7, to 4 is 5, to 12 is 8, to 7 is 5, a total of 29. With LOOK going up first, the order is 7, 9, 12, then 4, 2: 6 to 12 is 6 floors and 12 down to 2 is 10, a total of 16.

Why can “always go to the nearest requested floor” leave someone waiting indefinitely, and why can LOOK not?

If new requests keep arriving near the car, each is nearer than a distant request, so the distant one is never chosen. Nothing bounds its wait. Under LOOK the car continues in its direction only as far as the furthest request and must then reverse, so every request is reached within two sweeps of the building at most, whatever else arrives.

A car is at floor 3 going up, with a passenger for floor 8. There is a down call at floor 5 and an up call at floor 6. Where does it stop, in order?

At 6, for the up call, since that caller is going its way. Then at 8, for its passenger, and for whatever floor the person from 6 chose above. It passes 5 on the way up, because that caller wants to go down. Once it has nothing further above, it turns and stops at 5 on the way down.

The design has no check for “doors closed” before a car moves. What prevents a car from moving with its doors open?

The structure of the state machine. The car is in exactly one of three states, and its floor is changed by one line that runs only in the moving state. With the doors open the car is in a different state, so that line cannot run. An illegal combination was made impossible to represent, which is stronger than checking for it.

In the simulation, why did nearest-car dispatching do worse than round robin in the morning rush?

Most calls came from the lobby. The car nearest the lobby is usually the one that most recently returned to it, so it received call after call while the other cars, a few floors away, received almost none. Distance ignores how busy a car already is and which way it is going. Taking turns at least spread the work.

How would you add a limit on the number of passengers in a car?

Give the car a capacity and a count of people aboard, updated when people get in and out. A full car should stop only where someone inside wants to get out, and should not stop for hall calls. The system needs to learn that a hall call was passed, and give it to another car, and the dispatcher’s estimate should treat a full car as unavailable until its next stop.

Buttons can be pressed at any instant on any floor. Describe a design that needs no locks.

Each press becomes a message on a queue. One control loop is the only code that touches the cars and the map of unanswered calls: it drains the queue, applies each press, then advances every car by one tick, and repeats. Because a single thread of control owns all the state and handles one thing at a time, no two operations can interleave.
