A database with no center

Chapter 2 showed one lookup: a resolver walking from the root servers to the .com servers to the servers for example.com. This chapter looks at the system behind that walk, because its design explains both why DNS scales so well and why its failures are so wide.

The Domain Name System dates from 1983, when the single file that listed every host on the network stopped being manageable. It replaced the file with a database that has three properties worth keeping in mind throughout:

  • It is hierarchical. Names form a tree, and responsibility for each branch is handed to whoever runs it.
  • It is distributed. No server holds everything. Each knows its own branch and where to send you for the branches below.
  • It is cached. Every answer comes with a lifetime, and everyone who sees an answer may reuse it until that lifetime ends.

Names, zones and delegation

A domain name is read from right to left. In www.example.com, the rightmost label com is the top-level domain (TLD), example is registered beneath it, and www is a name its owner chose. Above them all is the unnamed root, sometimes written as a trailing dot.

A zone is a part of the tree managed as one unit by one organization. Where one zone ends and another begins there is a delegation: the parent zone holds NS records naming the servers that are authoritative for the child. The referrals a resolver follows are exactly these delegations.

Several parties are involved in getting a name to work, and it helps to know which is which when something breaks.

PartyRoleExample
RegistryRuns a top-level domain and its zoneThe operator of .com
RegistrarSells names in that TLD and tells the registry which name servers a name usesThe company you bought the domain from
RegistrantHolds the nameYou

Recursive resolverLooks names up on behalf of users and caches the answersAn internet provider’s resolver, or a public one such as 1.1.1.1, 8.8.8.8 or 9.9.9.9
Stub resolverThe small client in an operating system that asks a recursive resolverWhat your code calls when it resolves a hostname

The registrar and the DNS provider are often the same company and need not be. Keeping the distinction clear matters because they fail separately: a lapsed registration takes the name away entirely, while a DNS provider outage leaves the name registered and unanswered.

Records

A zone is a list of resource records. Each has a name, a type, a time to live and a value. Written in the traditional zone file format, a small zone looks like this:

$ORIGIN example.com.
$TTL 3600
@      IN SOA   ns1.example.com. hostmaster.example.com. (
                2026101001 7200 900 1209600 300 )
@      IN NS    ns1.example.com.
@      IN NS    ns2.example.net.
@      IN A     203.0.113.10
@      IN AAAA  2001:db8::10
www    IN CNAME example.com.
api    IN A     203.0.113.20
@      IN MX    10 mail.example.com.
@      IN TXT   "v=spf1 mx -all"
@      IN CAA   0 issue "letsencrypt.org"

The @ stands for the zone’s own name, called the apex. These are the record types a system designer meets:

TypeValuePurpose and notes
A, AAAAAn IPv4 or IPv6 addressThe basic answer. A name may have several, and resolvers return them all.
CNAMEAnother nameAn alias: “look up that name instead”. Used to point a name at a CDN or load balancer. A name with a CNAME may hold no other records.
NSA name serverWhich servers are authoritative for a zone. Present in the zone and in its parent.
SOAZone metadataOne per zone. Its last field controls how long “no such name” answers are cached.
MXA mail server and a priorityWhere email for the domain is delivered.
TXTFree textProof of domain ownership for third-party services, and the email authentication policies SPF, DKIM and DMARC.
SRVA host, a port and a weightLocating a service, including its port. Common in internal service discovery.

HTTPSConnection parametersTells a browser before it connects that HTTP/3 is available, along with other hints.
PTRA nameThe reverse mapping, from address to name. Used by mail servers and in logs.

The apex problemThe rule that a CNAME cannot share a name with other records collides with the apex, which must hold SOA and NS records. So example.com itself cannot be a CNAME to a CDN, though www.example.com can. DNS providers work around it with a feature called ALIAS, ANAME or CNAME flattening: the provider looks up the target itself and returns plain address records.

Caching and TTL

The whole system depends on caching. Without it the root servers would be asked about every page view on Earth. With it they are asked rarely, because resolvers remember.

Every record carries a time to live (TTL) in seconds. Whoever receives the record may reuse it for that long without asking again. An answer passes through several caches on its way to your code: the recursive resolver, the operating system, sometimes the browser, and sometimes the application runtime. Each keeps its own copy and counts its own lifetime down.

The TTL is a dial that the zone’s owner sets, and it trades two things against each other.

Short TTL, such as 60 secondsLong TTL, such as a day
A change takes effectWithin about a minuteOver the following day
Queries to your DNS providerMany, which may cost moreFew
Lookup delay for usersMore requests pay for a fresh lookupAlmost always answered from cache
If your DNS provider is downNames stop resolving within a minuteCached answers carry most users through a short outage
SuitsRecords used for failover or traffic steeringRecords that almost never change, such as NS and MX

The fourth row is easy to overlook. A short TTL makes you agile and also makes you dependent on your DNS provider answering at every moment. Five minutes is a common middle value for records in front of services.

Failed lookups are cached too. If a name does not exist, the resolver remembers that for a period set in the zone’s SOA record. This negative caching has a practical consequence: if you look up a new name before creating its record, you may be told it does not exist for several minutes after you add it.

Common mistake. Talking about “DNS propagation” as if changes were pushed around the world. Nothing is pushed. Your authoritative servers have the new record within seconds. What takes time is every cache that holds the old answer waiting for its TTL to expire. You control that wait, and only in advance, by what TTL the old record had.

Changing a record without an outage

The right procedure follows directly, and it applies whenever a name must move to a new address: a new load balancer, a new CDN, a new data center.

  1. Lower the TTL well ahead of time, and wait at least as long as the old TTL so that every cache has picked up the short one.
  2. Change the record. Keep the old destination running and serving correctly.
  3. Watch traffic move over the next few minutes. If something is wrong, changing back takes effect just as fast.
  4. Raise the TTL again once you are confident, and only then retire the old destination.

Expect a thin tail of traffic at the old address for hours or days. Some resolvers and client libraries hold answers longer than the TTL allows, and long-lived connections opened before the change simply stay open.

On the wire, and encrypted DNS

A classic DNS query is a single small packet sent over UDP to port 53, answered by a single packet. No connection is set up, which is why a lookup can cost one round trip. When an answer is too large to fit safely in one packet, the server says so and the client asks again over TCP.

Classic DNS is unencrypted. Anyone on the path, such as a Wi-Fi operator or an internet provider, can see which names a device looks up and can alter the answers. Three newer transports wrap the same queries in encryption:

NameRuns overPortNotes
DNS over TLS (DoT)TCP with TLS853Common for system-wide settings on phones and in resolvers talking to each other.
DNS over HTTPS (DoH)HTTPS443Built into browsers. Looks like ordinary web traffic, so it is hard to block or inspect.
DNS over QUIC (DoQ)QUIC853The newest. Avoids the head-of-line blocking of the TCP-based options.

These protect the conversation between a device and its resolver. They do not prove that the answer is the one the domain’s owner published. That is the job of DNSSEC, covered below. For a designer, the main effect of encrypted DNS is on corporate networks, where security tools that relied on reading DNS queries no longer see them when a browser uses its own resolver.

DNS as a traffic director

An authoritative server is free to give different answers to different questions about the same name. That makes DNS the first place where traffic can be steered, before any connection exists.

Managed DNS services offer a standard set of policies:

PolicyThe answer depends onUsed for
Round robinNothing. Several addresses are returned in rotating order.Crude spreading of load across a few servers
WeightedConfigured proportions, such as 95 to 5Shifting a share of traffic to a new version or provider
Latency or geolocationWhere the query appears to come fromSending users to the nearest region, or keeping a country’s users in that country
FailoverHealth checks run by the DNS providerReplacing a failed region’s address with a standby

DNS steering is simple and works for any protocol, which is why nearly every multi-region system uses it at the top level. It is also blunt, and its limits decide where other tools are needed.

  • It acts on resolvers, not on users. The authoritative server sees the address of the recursive resolver, which may be far from the person asking. An extension called EDNS Client Subnet lets a resolver pass along part of the user’s address, and not all resolvers send it.
  • It is only as fast as the TTL. With a five-minute TTL, a failed region keeps receiving traffic from caches for up to five minutes after the DNS provider notices, and longer from clients that ignore the TTL.
  • It cannot see load. One answer handed to a large provider’s resolver may be used by a million users, and another by ten. DNS decides per lookup and has no idea how many requests follow each one.
  • It knows nothing about requests. It cannot route by URL path, retry a failed request or drain a server gracefully.

The alternatives make different trade-offs, and large systems combine them.

A typical arrangement uses DNS or anycast to choose a region and a load balancer inside the region to choose a server.

DNS inside your system

DNS is also how services find each other internally. Instead of configuring a service with the addresses of its dependencies, you give it a name, and the name is kept pointing at whatever instances are currently healthy. In Kubernetes, for example, every service receives a name of the form orders.shop.svc.cluster.local, resolved by a DNS server that runs inside the cluster.

Networks commonly use split-horizon DNS as well: the same name resolves to a private address for clients inside the network and to a public one, or to nothing, for clients outside.

Using DNS for discovery brings its caching behavior into your own failure handling, and three problems recur.

  • Clients that cache too long. Some language runtimes and HTTP libraries resolve a name once and keep the answer for the life of the process, or for a fixed period that ignores the TTL. After a failover they keep calling an address that is gone. Check what your runtime does and configure it.
  • Connection pools that never look again. A pool of open connections has no reason to consult DNS. If a database fails over to a new address, existing connections must break and be re-established before the new answer matters. Set a maximum lifetime on pooled connections so they are refreshed periodically.
  • Lookups that multiply. Resolver settings can turn one logical lookup into several. Kubernetes’ default search configuration makes a lookup for an external name such as api.partner.com try several internal suffixes first, so one call can cost several queries. Under load the cluster’s DNS server becomes a bottleneck that nobody thought to monitor.

Richer discovery mechanisms exist for cases where DNS is too coarse, and covers them.

Security

DNS was designed without authentication. A resolver accepts an answer if it appears to come from the right server and matches a question it asked. Several attacks follow from that.

AttackHow it worksDefense
Cache poisoningAn attacker races the real server with forged answers. If one is accepted, the resolver caches a false address and gives it to every user.Randomized query ports and identifiers, which resolvers adopted after a 2008 disclosure showed how practical the attack was. DNSSEC.
Registrar or account takeoverThe attacker gets into the account that controls the domain and repoints it.Strong authentication on registrar and DNS accounts, registry lock for important domains.
Subdomain takeoverA CNAME still points at a cloud resource you deleted. The attacker creates a resource with that name and now serves content on your subdomain.Remove DNS records when you remove what they point to. Audit for dangling records.
Denial of serviceA flood aimed at a domain’s authoritative servers, so that nobody can resolve it.Anycast DNS providers with large capacity. A second provider.
AmplificationThe attacker sends small queries with a victim’s address forged as the source. Servers send large answers to the victim.Mostly a concern for whoever runs open resolvers. Rate limiting of responses.

DNSSEC

DNSSEC adds digital signatures to DNS so that a resolver can verify an answer is exactly what the zone’s owner published. Each zone signs its records with its own key. Its parent zone publishes a signed fingerprint of that key. Following those links upward leads to the root, whose key every validating resolver is configured to trust.

Changing the key at the topThe root zone’s master key is replaced only rarely, in a ceremony planned years ahead, because every validating resolver in the world must learn the new key first. The second replacement in the system’s history is scheduled for 11 October 2026. The first was in October 2018, after a year’s postponement to give operators more time.

DNSSEC proves that an answer is authentic and unmodified. It does not hide queries, which is what encrypted DNS is for, and it does not protect the connection made afterward, which is what TLS is for. It also adds an operational risk of its own: if signatures expire or keys are rotated incorrectly, validating resolvers treat the whole zone as forged and it disappears for their users. Adoption is partial for that reason, and whether to sign a zone is a judgment about which risk worries you more.

How DNS fails

When DNS fails, everything that depends on names fails with it, including tools you would use to diagnose the problem. Three incidents show the range.

  • An attack on a provider. On 21 October 2016 a flood of traffic from compromised home devices hit Dyn, a managed DNS provider. Its customers’ servers were fine. Their names could not be resolved, and for much of a day large sites were unreachable for many users.
  • A self-inflicted withdrawal. In the Facebook outage of October 2021, described in Chapter 7, the company’s DNS servers took themselves off the internet when they lost contact with its data centers.
  • A configuration error at a resolver. On 14 July 2025 Cloudflare’s public resolver 1.1.1.1 was unreachable for 62 minutes. An earlier configuration change had mistakenly tied the resolver’s address blocks to an unrelated service, and a routine update that evening withdrew those blocks from the internet worldwide. People whose devices used only that resolver could not look up any name. The same resolver reached through DNS over HTTPS mostly kept working, because that path uses a different hostname and different addresses.

To these add the AWS incident of October 2025 from Chapter 6, in which automation left a service’s endpoint with no records at all. In every case the application servers were healthy and unreachable.

The defenses are unglamorous and effective.

RiskDefense
Your authoritative provider is downUse two providers for important zones, serving the same records. Avoid very short TTLs on records that do not need them.
The registration lapses or is stolenAuto-renew, more than one contact, strong authentication, registry lock.
A bad record is publishedManage zones as reviewed code. Validate changes before applying. Keep TTLs short during a change so a mistake can be undone quickly.
A resolver your servers depend on is downConfigure at least two resolvers run by different operators. Run a local caching resolver that can serve expired answers for a while if it cannot reach anyone.
Your own tools depend on the names that are brokenKeep an access path for emergencies that does not need your DNS: known addresses, a separate domain, or a separate provider.

In production. Monitor DNS as a user would: resolve your important names from several networks and several public resolvers, and alert when the answer is missing or unexpected. Also alert on the calendar. Domain registrations and DNSSEC signatures expire on known dates, and both have taken down well-run services.

A small toolkit

The dig command asks DNS questions and shows exactly what came back. These six uses cover most debugging.

# The address a name resolves to, nothing else
dig +short www.example.com A

# The full answer, including the remaining TTL in seconds
dig www.example.com A +noall +answer

# Ask one specific resolver, to compare what different caches hold
dig @1.1.1.1 www.example.com A

# Ask the authoritative server directly, to see the truth with no cache involved
dig @ns1.example.com www.example.com A

# Follow the delegations from the root, as a resolver would
dig +trace www.example.com

# Reverse lookup: which name is registered for this address
dig -x 203.0.113.10

The comparison between the third and fourth commands is the one to remember. If the authoritative server gives the new answer and a resolver gives the old one, nothing is broken. You are looking at a cache, and the TTL in the output tells you how long it has left.

In an interview. DNS usually enters a design in one sentence, “DNS routes users to the nearest region”, and a good interviewer will push on it. Be ready with the limits: failover is bounded by the TTL, the decision is made per resolver and cannot see load, and so a load balancer or anycast layer is still needed underneath. Mention that the DNS provider itself must not be a single point of failure.

Connects to

  • Caching. DNS is the oldest large-scale cache in everyday use, and it shows every trade-off of in miniature: freshness against load, and the difficulty of invalidating copies you do not hold.
  • Availability. DNS failover is one of the standard ways to move between regions. Its recovery time is part of your RTO. See .
  • Email. Mail delivery and anti-spoofing rest entirely on DNS records: MX, and the TXT records for SPF, DKIM and DMARC.
  • Certificates. Certificate authorities check control of a domain through DNS, and CAA records limit who may issue. covers the rest of that process.
  • Law and governance. Who may hold a name, and what happens in a dispute, is decided by registries and by ICANN’s policies. A domain is rented, never owned.

Key points

  • DNS is a hierarchical, distributed, cached database. The tree is cut into zones, each run independently and delegated from its parent.
  • A record has a name, type, TTL and value. Know A, AAAA, CNAME, NS, MX, TXT, and that a CNAME cannot sit at the zone apex.
  • Changes are not pushed. Old answers live in caches until their TTL expires, so lower the TTL in advance of any planned change.
  • A short TTL buys agility and makes you depend on your DNS provider being up at every moment.
  • DNS can steer traffic by weight, location and health. It decides per resolver, reacts no faster than the TTL and cannot see load.
  • Inside a system, watch for clients and connection pools that never re-resolve.
  • DNSSEC authenticates answers, and encrypted DNS hides queries. They solve different problems.
  • DNS outages make healthy servers unreachable. Use two providers, two resolvers, and an emergency path that does not need your own names.

Check yourself

A record has a TTL of 86,400 seconds. You change it at noon and cut the TTL to 300 in the same edit. When can you be confident that almost all users see the new value?

At about noon the next day. Caches that fetched the record just before the change hold the old value with the old one-day lifetime. The new, shorter TTL applies only to answers fetched after the change. The TTL should have been lowered a day earlier.

Why can www.example.com be a CNAME to a CDN while example.com cannot?

A name that has a CNAME may have no other records, and the apex of a zone must carry SOA and NS records. Providers offer ALIAS or CNAME flattening to get the same effect, by resolving the target themselves and answering with address records.

You use DNS failover with a 60-second TTL to move users from a failed region to a healthy one. Give three reasons some users are still sent to the failed region after two minutes.

The DNS provider needs time to detect the failure before it changes the answer. Some resolvers and client libraries keep answers longer than the TTL. And clients with open connections or pooled connections keep using the old address without looking it up again.

A service calls a database by hostname. The database fails over to a standby with a new address and DNS is updated at once, yet the service keeps failing for ten minutes. What are the likely causes?

The service’s runtime or driver cached the old address beyond the TTL, or its connection pool keeps trying to reuse connections to the old address without resolving the name again. Bounded DNS caching in the runtime and a maximum connection lifetime in the pool address both.

Does DNSSEC stop your internet provider from seeing which sites you look up?

No. DNSSEC signs answers so that tampering can be detected. The queries and answers still travel in the clear. Hiding them requires an encrypted transport such as DNS over HTTPS or DNS over TLS.
